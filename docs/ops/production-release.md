# Production release controls

**Status: the controller and denial tests are implemented locally; the hosted release pipeline is deliberately blocked.** This setup does not authorize a customer release. `production-release.yml` has a preparation job and exactly one job referencing the protected **Production** environment. Preparation cannot succeed until the real evidence/adapter wiring is complete, so no empty or synthetic release summary reaches an approval request.

## One approval contract

The preparation path must consume stage-only qualification and previously recorded production expectations. The new `loadStagingQualification` authenticates a successful staging producer, the exact `minted-staging-qualification-<run>-<attempt>` artifact and archive digest, originating successful main CI, current main, a historical stage-only G0 preflight, and a distinct delivered-candidate/served-check receipt. It never reads Production credentials or claims production eligibility.

`loadProductionBaselineAttestation` separately authenticates `minted-production-baseline-<run>-1`, containing `production-baseline.json`, from a successful Production workflow with the required actual approval. Its original recording time must lie inside that producer run. The closed envelope binds the production target, recorded served app/configuration/schema/lineage, desired configuration identity and installed extension set. It explicitly returns `HISTORICAL_ONLY` and does not pretend these are fresh observations. A missing trusted attestation blocks nomination. These helpers verify envelopes; actual collector, artifact emission and nomination wiring remain incomplete.

`prepareProductionApproval` now composes those two GitHub loaders and `approvalSummary`. The closed `production-approval-intent` embeds their exact authenticated envelopes and archive identities, the new production run/attempt/workflow SHA, and its original preparation time. It pins source, tested staging deployment and receipt, exact additive/no-change plan, previously recorded production deployment/app/configuration/schema/lineage, desired production configuration, installed extension set, required checks/scopes and freshness limits. The tested staging plan must start from the same schema and migration lineage as the recorded production expectation. Production requirements inherit the authenticated staging producer's trusted policy; there is no operator policy/PASS override. A future difference between staging and production requirements needs a reviewed contract change.

The old `loadRelease` prototype accepting full production G0 in a staging artifact has been removed. Preparation accepts stage-only qualification and historical production expectations; it has no production collector/credential parameter and cannot establish production eligibility. The historical baseline stays `HISTORICAL_ONLY` with backup eligibility `NOT_EVALUATED`.

The approved backup rule is **fresh matching selection after the single approval**. The immutable intent pins `fresh-matching-after-approval`, the exact production database reference, baseline schema and lineage, a maximum 24-hour backup age, every required recovery scope, a maximum 4-hour demonstrated restore, and a compatible app-only rollback within the 5-minute recovery target. It intentionally contains no exact production backup artifact. The embedded staging evidence still includes its own staging backup; it cannot satisfy production recovery.

`executeApprovedProduction` authenticates the exact approval artifact and actual GitHub review before invoking `collectProductionEligibility`. It then calls unchanged full production G0 validation and `bindProductionEligibility`. Every approved identity and policy must match; record creation, actual production observation and backup verification must occur after selection begins. All target/schema/lineage, availability, backup age, exact restored artifact, scope, proof freshness and recovery duration checks remain mandatory. A fresh backup may predate approval, but selecting and verifying it for this release happens afterward. The full resulting record's canonical digest seals the chosen backup and its restoration evidence into the execution identity.

During execution the same immutable approval artifact, actual reviewer/protection settings, current main and stage qualification freshness are rechecked. The existing controller additionally compares fresh actual snapshots, including the exact chosen backup, immediately before each mutation. It cannot silently select another backup after sealing the execution record, renew proof timestamps, replace a changed production baseline, or weaken requirements. A detected change or expiry stops the run; any attempted mutation retains its lease for reconciliation as described below. These are tested control paths with simulated providers; real collectors, immutable output emission and hosted execution remain blocked.

First-use baseline enrollment also needs an explicit capture-only mode inside the same protected Production job. After the setup enrollment approval it may collect and emit a baseline attestation, with no build, migration or domain operation. The mode, collectors and output wiring are still pending; the current source cannot fabricate enrollment from fixtures or use an unapproved production identity. Setup enrollment must not silently become a second approval for every normal release.

`loadApprovalRequest` verifies `minted-approval-<run>-1` containing the closed `approval-request.json` intent against the same production run and exact archive digest. Its preparation time cannot predate that run. Artifact ID and provider archive digest must come from trusted preparation job outputs; neither an input filename nor a caller's JSON object authenticates the intent. `verifyProductionApproval` fetches actual GitHub run review history and Production protection settings. It requires the sole approved reviewer ID **261707544** (sonny303), the exact Production environment ID, self-review allowed, administrative bypass disabled and one custom branch rule for main of type branch. An environment name or local `approved: true` value is insufficient. [GitHub review-history API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run).

Review history does not document per-review attempt timestamps. This version therefore permits production **run attempt 1 only**. Rerunning a job cannot reuse approval; start a fresh workflow dispatch with a new summary and approval. A new source, workflow, configuration, schema/ledger, plan, supported extension set, production baseline or expired backup/proof similarly requires a new eligible record. The preparation artifact upload, job-output pins and provider collector integration remain implementation prerequisites before activation; the existing workflow does not claim those steps already happen.

Production deployment/database/test credentials belong exclusively in the protected Production environment and are exposed only to that single approved job. This source slice references no such credentials; scoped provisioning and actual provider composition remain pending. Repository/org secrets and alternative privileged workflows must be quarantined separately; deleting references from one workflow does not revoke credentials.

## Executable controller order

The tested `executeDelivery` control core requires readiness and verified approval, then:

1. In the production composition boundary, authenticate the approved intent, select/verify a matching fresh production backup and collect full production G0. Match all approved identities and seal the exact execution record. Then validate that record and the actual current production baseline. Build a production-configured candidate with `vercel deploy --prod --skip-domain`, validate its exact source/project/configuration/release binding, withheld domains and READY state, then run candidate checks. Candidate creation is after approval.
2. Acquire the shared production lease and repeat approval, G0 freshness and actual baseline checks. Rehearse and prove the exact compatible additive plan before applying it; apply no database changes for a no-change plan.
3. Collect the actual result schema/ledger and data postconditions. Recheck the candidate and declared supported installed production extensions after database application. Compare current deployment/configuration/database/backup/aliases again immediately before promotion.
4. Promote that exact Production candidate ID and verify the served app. A Preview deployment is never promoted directly: Vercel documents that this would create a different production build. [Vercel deploy](https://vercel.com/docs/cli/deploy), [Vercel promote](https://vercel.com/docs/cli/promote).
5. If a served-app check fails, obtain a fresh receipt proving the previous app works with both the **current database** and the **declared installed extension versions**. Recheck actual state immediately before rolling back the app. Verify recovery before releasing the same lease. Otherwise retain the lease and stop for reconciliation.

There is no automatic database undo, rollback approval job, separate extension Store approval in this web/database flow, forceful release cancellation or lease stealing. A provider timeout may conceal a successful mutation; it stops the controller rather than triggering a blind retry or overwriting a newer release. Staging/production use separate target leases shared by CI and supported local release commands. This version provides no supported local production publication command.
