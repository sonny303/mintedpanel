# Production release controls

**Status: the controller and denial tests are implemented locally; the hosted release pipeline is deliberately blocked.** This setup does not authorize a customer release. `production-release.yml` has a preparation job and exactly one job referencing the protected **Production** environment. Preparation cannot succeed until the real evidence/adapter wiring is complete, so no empty or synthetic release summary reaches an approval request.

## One approval contract

The preparation path must consume stage-only qualification and previously recorded production expectations. The new `loadStagingQualification` authenticates a successful staging producer, the exact `minted-staging-qualification-<run>-<attempt>` artifact and archive digest, originating successful main CI, current main, a historical stage-only G0 preflight, and a distinct delivered-candidate/served-check receipt. It never reads Production credentials or claims production eligibility.

`loadProductionBaselineAttestation` separately authenticates `minted-production-baseline-<run>-1`, containing `production-baseline.json`, from a successful Production workflow with the required actual approval. Its original recording time must lie inside that producer run. The closed envelope binds the production target, recorded served app/configuration/schema/lineage, desired configuration identity and installed extension set. It explicitly returns `HISTORICAL_ONLY` and does not pretend these are fresh observations. A missing trusted attestation blocks nomination. These helpers verify envelopes; actual collector, artifact emission and nomination wiring remain incomplete.

The earlier `loadRelease` and `approvalSummary` prototype still expects a full production G0 record in the staging artifact. **It is not an activation-ready preparation path**: producing fresh private production evidence there conflicts with keeping production credentials behind the single gate. Do not wire that prototype into hosted preparation. Full production G0 eligibility must be collected and validated only after approval against the immutable approved intent; changed identities must fail rather than rewrite that intent.

The backup rule is an unresolved user decision. Pinning a backup artifact from a prior approved run eventually conflicts with the 24-hour age limit: one-time enrollment cannot refresh that identity indefinitely. The pending choice is either permit selection and verification of a fresh matching backup after the single approval, under fixed target/schema/lineage/recovery requirements, or keep an exact artifact pin and accept an additional refresh approval when stale. No helper silently chooses between them; the baseline envelope intentionally contains no backup policy or backup eligibility claim.

First-use baseline enrollment also needs an explicit capture-only mode inside the same protected Production job. After the setup enrollment approval it may collect and emit a baseline attestation, with no build, migration or domain operation. The mode, collectors and output wiring are still pending; the current source cannot fabricate enrollment from fixtures or use an unapproved production identity. Setup enrollment must not silently become a second approval for every normal release.

`loadApprovalRequest` verifies the summary artifact against the same production run and its exact archive digest. `verifyProductionApproval` fetches actual GitHub run review history and Production protection settings. It requires the sole approved reviewer ID **261707544** (sonny303), the exact Production environment ID, self-review allowed, administrative bypass disabled and one custom branch rule for main of type branch. An environment name or local `approved: true` value is insufficient. [GitHub review-history API](https://docs.github.com/en/rest/actions/workflow-runs#get-the-review-history-for-a-workflow-run).

Review history does not document per-review attempt timestamps. This version therefore permits production **run attempt 1 only**. Rerunning a job cannot reuse approval; start a fresh workflow dispatch with a new summary and approval. A new source, workflow, configuration, schema/ledger, plan, supported extension set, production baseline or expired backup/proof similarly requires a new eligible record. The preparation artifact upload, job-output pins and provider collector integration remain implementation prerequisites before activation; the existing workflow does not claim those steps already happen.

Production deployment/database/test credentials belong exclusively in the protected Production environment and are exposed only to that single approved job. This initial source slice references no such credentials because destination approval and scoped provisioning are pending. Repository/org secrets and alternative privileged workflows must be quarantined separately; deleting references from one workflow does not revoke credentials.

## Executable controller order

The tested `executeDelivery` control core requires readiness and verified approval, then:

1. Validate the immutable G0 record and actual current production baseline. Build a production-configured candidate with `vercel deploy --prod --skip-domain`, validate its exact source/project/configuration/release binding, withheld domains and READY state, then run candidate checks. Candidate creation is after approval.
2. Acquire the shared production lease and repeat approval, G0 freshness and actual baseline checks. Rehearse and prove the exact compatible additive plan before applying it; apply no database changes for a no-change plan.
3. Collect the actual result schema/ledger and data postconditions. Recheck the candidate and declared supported installed production extensions after database application. Compare current deployment/configuration/database/backup/aliases again immediately before promotion.
4. Promote that exact Production candidate ID and verify the served app. A Preview deployment is never promoted directly: Vercel documents that this would create a different production build. [Vercel deploy](https://vercel.com/docs/cli/deploy), [Vercel promote](https://vercel.com/docs/cli/promote).
5. If a served-app check fails, obtain a fresh receipt proving the previous app works with both the **current database** and the **declared installed extension versions**. Recheck actual state immediately before rolling back the app. Verify recovery before releasing the same lease. Otherwise retain the lease and stop for reconciliation.

There is no automatic database undo, rollback approval job, separate extension Store approval in this web/database flow, forceful release cancellation or lease stealing. A provider timeout may conceal a successful mutation; it stops the controller rather than triggering a blind retry or overwriting a newer release. Staging/production use separate target leases shared by CI and supported local release commands. This version provides no supported local production publication command.

## Activation evidence still required

The controller's injected `services` interface exists for simulation and reviewed future provider composition, not arbitrary modules selected by an operator. No production build, Supabase migration, Vercel promotion, alias readback, real runtime check or real rollback was executed by this slice. The CLI's mutation commands stop before provider access; the workflow layout alone is not a functioning hosted release.

Required completion work is: approved project/credential isolation and hosted settings readback; authenticated target schema/lineage/configuration/backup collectors; matching-baseline database rehearsal and approved migration execution; real candidate/source/runtime/isolation and installed-extension compatibility evidence; immutable summary artifact upload and job-output pins; fixed provider adapter wiring inside the same Production job; then actual denial and non-customer rehearsal evidence. No runtime flag may substitute for these missing implementations.

The provider's current served production baseline must be derived from the complete customer domain mapping, not merely “latest Production deployment”: a withheld candidate can be newer while customers still use the previous app. Check known customer domains `mintedpanel.com`, `www.mintedpanel.com`, and `mintedpanel.vercel.app`. Unexpected/missing mappings block release.

Backups remain target-specific. A staging restore is not production recovery evidence. Keep the selected ≤24-hour backup, ≤5-minute app rollback and ≤4-hour restore targets classified as unverified until demonstrated against the applicable target/scopes. The controller preserves the original G0 snapshot timestamp; long-running operations that outlive its freshness budget stop safely and retain the lease. The current implementation cannot claim smooth live promotion or recovery from its simulator results.

Run `node --test scripts/delivery/*.test.mjs` plus the existing release checks. The simulator covers denied approvals/reruns, wrong artifacts/producers, changed/stale baselines, build-after-approval ordering, DB checks before promotion, exact candidate selection, database and extension rollback incompatibility, concurrent CI/local owners and replacement-owner deletion races.
