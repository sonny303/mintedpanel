## Existing source seams and gaps

The shared selector ranks payer, state specificity, group specificity, and ownership; its public signature has no case type ([`mintedpanel/src/lib/pickTemplate.ts:1-28, 88-168`](../../src/lib/pickTemplate.ts)). Equal top-ranked rows are candidates for an explicit caller choice; deterministic ordering is not a product decision.

## Ownership and permission matrix

`admin`, `specialist`, and `billing` are organization membership roles; billing is read-only. The guarded API’s writer check accepts admin or specialist ([`src/server/guard.ts:12, 164-168`](../../src/server/guard.ts)); organization SOP CRUD is admin-write enforced by RLS ([`src/services/templates.ts:1-5`](../../src/services/templates.ts)).

| Catalog / operation | Read scope | Current write authority | Reset implication |
| --- | --- | --- | --- |
| Organization SOPs and map overrides | Own organization. Map reads additionally include shared/global rows. | Org SOP authoring is admin-only; org map proposal/review/learning routes require admin or specialist. Billing cannot write. RLS remains the final boundary. | An org role can act only in that org’s scope. It grants no ownership over a shared/global configuration. |
| Global SOP and portal catalog | Global entries visible through catalog rules plus the org’s own entries. | Global authoring/registry RPCs reject anonymous and restricted-external callers; the shared-edit design has no platform role gate. Current comments describe the interim rule as authenticated-user access ([`src/hooks/useGlobalAuthoring.ts:1-3`](../../src/hooks/useGlobalAuthoring.ts); [`20260925035408_e612_client_access_context.sql:512-517, 631-635`](../../supabase/migrations/20260925035408_e612_client_access_context.sql)). | Do not reinterpret an org admin as owner of every global row. |
| Global shared form maps, capture, and proof | Shared-only read for org-free Train; Work sees shared maps plus its own overrides. | Authenticated-user/JWT gate, with no admin/specialist platform role; Train proposal and manual proof run on the user-scoped guard ([`src/services/sharedFieldMaps.ts:1-21, 51-123`](../../src/services/sharedFieldMaps.ts); [`src/server/extensionRoutes.ts:328-366, 425-439`](../../src/server/extensionRoutes.ts)). | The resolved policy extends the existing signed-in, non-restricted shared-edit authorization to global reset; it is distinct from organization map-write authority. | Global reset receipt/audit | Not implemented. | No existing global reset role or global row in `audit_log`; that table requires `org_id`. | The resolved policy authorizes a reset only through server-side checks of exact global target/scope and expected generation. Preserve true global scope and actor, with an atomic idempotent receipt; do not invent an org ID to satisfy audit shape (see scenario plan lines 142-145 and 171-178). A multi-configuration bulk UI is not required. |

**Resolved reset policy (2026-09-30):** The existing signed-in, non-restricted shared-edit authorization covers global Reset form mapping, including bulk reset operations; no narrower platform capability is required. This is policy authorization, not evidence of an implemented reset or authorization to perform a live reset here. Enforce server-side authorization, exact target/owner scope, expected `mapping_generation`, and an atomic idempotent receipt. Confirmation must disclose shared impact; preserve historic receipts/fields and org overrides, leaving old overrides inactive until reviewed. Creating an independent key leaves the old mixed setup untouched; resetting an existing key invalidates its active maps/proof and can interrupt autofill until recapture. Do not infer global authority from organization-admin role ([scenario plan, lines 123-131](scenario-specific-form-workflows-plan.md#L123-L131)).

## Frozen v1 conventions — proposed, not implemented

These names and boundaries align tickets [MINT-44 through MINT-66](https://linear.app/sowmyeah/issue/MINT-42/cf-v1-start-here-case-types-independent-configurations-and) and the scenario plan. Treat them as the cross-ticket contract, not current schema/runtime claims.

| Name | Proposed owner and invariant |
| --- | --- |
| `case_type` | Closed set `contract | enrollment | recredentialing`. Nullable legacy rows mean unclassified, not “all.” Contract is owned by `contracts`/the Matrix; Enrollment is the supported provider-case type; Recredentialing is authoring/filtering only in v1. This is business purpose, separate from task `execution_type`. Do not change the four-part credential-case uniqueness. |
| `mapping_generation` | Monotonic integer, initially 1, on each portal configuration (owner scope + exact `portal_key`) and the relevant map/capture/proof/fill context. Identity is never URL. A reset advances it; only current-generation maps and proof are active. This is invalidation, not map history/publication. |
| `context_version` | Optimistic concurrency version on one Matrix-owned Contract SOP assignment (`context_version` in DB/API; `contextVersion` in the TypeScript handoff). Assignment pins contract, SOP head, and immutable SOP version. Replace only transactionally with the expected version and before recorded fill activity. |
| Exact task/step | Case fill/submission receipts bind the authorized case + stamped `task_id` + stamped `step_id` + exact configuration. Authored SOP steps have no ID today; the resolver currently stamps `step-${idx}`. Contract receipts bind `assignment_id` + immutable `sop_version` + zero-based `task_index`/`step_index`, because the versioned payload has ordered arrays but no authored stable step ID. A `portal_key`, label, or URL by itself is insufficient. |
| Capability marker | Add the exact boolean DB/API field `requires_explicit_selection` to a portal configuration; legacy defaults false. New same-URL scenarios require it. Registry/API filtering must prevent an old extension from opening a new configuration. |
| Versioned handoff | Keep `SET_ACTIVE_CASE` unchanged for legacy and add `SET_ACTIVE_WORK` with exact discriminator `protocolVersion: 2`. TypeScript handoff uses camelCase fields `ownerKind`, `ownerId`, `sopTemplateId`, `sopVersion`, `taskId` + `stepId` for a case or `assignmentId` + `contextVersion` + `taskIndex` + `stepIndex` for a Contract, `portalKey`, `providerId`, optional `facilityId`, `launchReceiptId`, and `portalUrl`. DB/API fields remain snake_case where applicable. The server revalidates the tuple; extension acknowledgement proves capability and selected context, not authorization. |

Reset remains one transaction at the existing configuration boundary: check authorization and expected generation; invalidate old maps/proof; append an idempotent, actor-stamped receipt; reject stale capture/proof/learning writes and require an online generation check before a new Fill. Keep immutable historic fills, old SOP publications, existing org overrides, and submitted payer work. Do not add a second mapper store, inheritance layer, generic workflow engine, publication UI, or cross-owner outcome writes ([scenario plan, lines 142-169, 182-207](scenario-specific-form-workflows-plan.md#L142-L207)).

## Overlap and implementation handoff

- [MINT-8](https://linear.app/sowmyeah/issue/MINT-8/p0-04-audit-actor-integrity) owns trusted audit-actor integrity. New reset/assignment receipts should use that actor boundary; this baseline does not open a generic audit remediation.
- [MINT-19](https://linear.app/sowmyeah/issue/MINT-19/p1-12-atomic-sop-step-completion) owns atomic SOP step completion. Typed fill/submission should supply exact step identity to its existing path, not create a parallel completion mechanism.
- [MINT-22](https://linear.app/sowmyeah/issue/MINT-22/p1-08-extension-runtime-release-gate) owns MV3 runtime release evidence. Recheck it for the actual feature artifact and capability marker; local source or a Panel deployment cannot establish the Chrome Web Store version.

Keep this focused source-test run separate from the earlier 60-test plan baseline and from future feature acceptance; it does not verify these new workflows or payer paths.

Known external evidence still needed before rollout: establish migration provenance for live 150100/150200-equivalent objects, verify the active staging alias against its Preview artifact, and verify the published/installed extension version. These are evidence gaps, not permission to deploy or mutate during this baseline.
