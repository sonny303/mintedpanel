# E6.12 Enrollment Explorer trust-boundary runbook

**Purpose:** implementation and evidence-boundary instructions for E6.12.
Run results belong in the PR description and CI record for the exact commit
that was tested. This runbook intentionally carries no volatile pass counts or
provisional status. Hosted migration, external invites, deployment, and release
remain separate approval gates.

The approved Option A flow requires the recipient to be an existing confirmed,
non-banned, non-deleted, non-anonymous Auth user when an invite is issued.
Claim rechecks the current verified email and Auth status. Invite-before-signup
provisioning is outside this slice.

## Evidence gates

| Gate                | Reproducible evidence                                    | Proves                                                                                                                 | Acceptance condition                                                                                      |
| ------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Native SQL          | Disposable Postgres command below                        | PostgreSQL ACL/RLS, RPC bodies, role behavior, lifecycle, and transaction/lock behavior                                | Every verifier assertion passes, including migration coverage, four lock barriers, and owned cleanup.     |
| Real synthetic HTTP | Build, manifest, and HTTP commands below                 | Local GoTrue, PostgREST, Storage, Nitro, and synthetic identity behavior                                               | The full matrix passes with observed read-barrier evidence and owned cleanup.                             |
| Intercepted browser | Playwright command below                                 | Browser context, chooser, denial, stale revision, and sign-out transitions against intercepted synthetic network calls | The full browser suite exits 0 under the normal CI browser setup; all network calls stay synthetic/local. |
| CI                  | Repository `build`, `e612-http-boundary`, and `e2e` jobs | Reproduction on the CI runner with the pinned images and Node/Chrome setup                                             | All required jobs pass on the exact PR commit under review.                                               |
| Hosted              | Operator-controlled migration and runtime gates          | Hosted Auth/PostgREST/Storage behavior and release eligibility                                                         | A separately approved hosted gate passes; this runbook does not authorize it.                             |

Native SQL is SQL-only evidence. It does not establish Auth, PostgREST,
Storage, or browser HTTP proof. Real synthetic HTTP is local and uses fresh
synthetic identities and resources; it does not establish hosted behavior.

## Local prerequisites

Run from `mintedpanel-e6.12-client-access` with Node 22 (`.nvmrc`) and the
approved local Docker context:

```sh
npm ci
docker --context colima-minted-staging-recovery info
```

The context must resolve to the local Unix Docker socket. Use only fresh,
uniquely labeled E6.12 resources. Never target existing recovery containers or
data. The native verifier creates a networkless, read-only Postgres container
with no host mounts; the HTTP verifier creates a fresh internal Docker network
and labeled disposable containers, copies the built bundle into its app
container, then owns cleanup. Neither verifier uses host mounts or pulls
implicitly.

## Reproducible local checks

### Production build artifact

Compile the production bundle with dummy local Supabase values and the default
Nitro preset. `NITRO_PRESET` must be unset for this check; the generated
artifact records the default `cloudflare-module` preset. This is a build
prerequisite, not hosted runtime evidence:

```sh
env -u NITRO_PRESET \
VITE_SUPABASE_URL=https://example.supabase.co \
VITE_SUPABASE_ANON_KEY=dummy-anon-key \
npm run build
```

### Native SQL

The native verifier applies the migration chain inside a fresh networkless
Postgres container and owns its cleanup. The explicit image variable prevents
the script's development default from being used:

```sh
E612_DOCKER_CONTEXT=colima-minted-staging-recovery \
E612_POSTGRES_IMAGE=postgres@sha256:a3b7f434b2dc57ce85a67e171163eb8ab1a1ebcb39d27484661f26b1dfbe30d6 \
node scripts/security/verify-e612-client-access.mjs
```

Record the native result as SQL/RLS evidence only. Apply the native acceptance
condition from the evidence table before treating the run as complete.

### Real synthetic HTTP

Build the Node server with the same synthetic build environment used by CI,
then write the source/runtime manifest before starting the HTTP verifier:

```sh
NITRO_PRESET=node_server \
VITE_SUPABASE_URL=http://gateway:8787 \
VITE_SUPABASE_ANON_KEY=e612-build-synthetic-anon-key \
npm run build
node scripts/security/e612-build-manifest.mjs --write
```

The manifest binds the source roots and `.output/server` bundle to the HTTP
run. The verifier fails if the manifest is missing or stale. It generates
short-lived synthetic credentials internally; no hosted URL, secret, or live
identity belongs in this runbook.

```sh
E612_DOCKER_CONTEXT=colima-minted-staging-recovery \
E612_HTTP_DB_IMAGE=supabase/postgres@sha256:ac581882596ed0e46937ea6dd53a627d09f53e005d7264c2082a7ff7b62eaaca \
E612_HTTP_AUTH_IMAGE=supabase/gotrue@sha256:3439d5affb9e96395d1348521f4c675eea7096d8d76d18d4e31fcc08df802116 \
E612_HTTP_REST_IMAGE=postgrest/postgrest@sha256:ba586907588f4c03fc1d7e5c57732cec80c396a164199ceeddfc8a89b24412f0 \
E612_HTTP_STORAGE_IMAGE=supabase/storage-api@sha256:f1546fac6d1c7e345428ac904bfaa7be7cecd50a1f549fe1cf38c628a7b15c85 \
E612_HTTP_NODE_IMAGE=node@sha256:752ea8a2f758c34002a0461bd9f1cee4f9a3c36d48494586f60ffce1fc708e0e \
```

This is real local synthetic HTTP evidence across the disposable Auth,
PostgREST, Storage, gateway, and built Node server containers. It is not
hosted Supabase evidence.

### Intercepted browser

The browser suite uses Chrome/Chromium and intercepts every Auth, Supabase
REST, and E6.12 API call locally. Install the browser, provide dummy-looking
local values. The focused E6.12 browser check is:

```sh
npm ci
npx playwright install --with-deps chromium
VITE_SUPABASE_URL=https://example.supabase.co \
VITE_SUPABASE_ANON_KEY=dummy-anon-key \
CI=true npm run test:e2e -- e2e/enrollment-explorer-auth.spec.ts --workers=1
```

The equivalent unfiltered full-suite acceptance check is:

```sh
CI=true npm run test:e2e -- --workers=1
```

CI uses the same Node 22 setup, installs Chromium with
`npx playwright install --with-deps chromium`, and writes
`VITE_SUPABASE_URL=https://example.supabase.co` plus
`VITE_SUPABASE_ANON_KEY=dummy-anon-key-for-ci`. Local macOS Chrome and the CI
Chromium path are selected by `playwright.config.ts`. This gate proves browser
lifecycle behavior; it is not Auth/REST/Storage UAT.

## Profile-save and lead-conversion acceptance

- A committed profile save or lead conversion produces exactly one confirmation
  for exactly one durable write while the originating actor and compatible scope
  remain current, even when context reload or refetch runs at the same time.
  Retries and reloads must not duplicate the confirmation.
- After an account switch, requests and cache entries from the prior account
  are aborted or ignored before the new context is applied. The new account
  must receive no prior Auth metadata, cache data, full name, notification, or
  membership side effect.
- A committed write and a refresh or mirror warning are separate outcomes.
  Report success only after the durable write commits; a later refresh or mirror
  warning may be surfaced and retried without changing the committed-write
  result.

## Boundary contract

- `private.internal_staff`, `client_identity_classifications`,
  `client_invites`, `client_access`, and grant tables are service-only.
- `app_authz.is_restricted_external()` is the only authenticated helper
  exception; it exposes a boolean and no private rows.
- The five browser gateways receive `p_actor_user_id` from the verified server
  actor, reject forged body/query/header actor fields, and recheck Auth status.
  The operator-only manifest RPC is a separate `p_operator_user_id` contract
  used by operator tooling and is not a browser gateway.
- Existing response bodies remain stable. Protected responses add only the
  `X-Minted-Context-Revision` header; access-context envelopes include the
  revision field.
- Changing auth, audience, organization, grants, or revision cancels in-flight
  work and clears affected query/cache state before remounting the shell.
- `POST /api/internal/client-invites` returns a caller-deliverable `inviteUrl`;
  `/client-invites/claim/:token` is the only E6.12 browser claim entrypoint.
  The recipient must already have an existing verified Auth account; there is
  no signup or outbound-email flow in this slice.

## Hosted gate

Hosted evidence is not established by this branch. Before any external client
token or UAT, an operator must apply the new migration through the approved
workflow, compare effective ACL/RLS/function definitions, and run the real
Auth/PostgREST/Storage role matrix against synthetic identities. No live data,
recovery container, hosted invite, deployment, or release is authorized by
this runbook.
