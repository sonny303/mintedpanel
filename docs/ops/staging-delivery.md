# Staging delivery controls

**Status: local control implementation; hosted activation is blocked.** Run `node scripts/delivery/cli.mjs status` for the explicit capability gaps. Its exit status is 2. Neither a green simulator test nor supplied JSON authorizes deployment.

The new `staging-delivery.yml` receives successful CI `workflow_run` events on main. It checks out the immutable trusted workflow revision, verifies the originating run through GitHub, and rejects forks, non-push CI runs, failed/skipped CI, wrong workflow paths, a mismatched source SHA or a source that is no longer current main. The hosted delivery entrypoint then stops before acquiring a lease or calling Vercel/Supabase. Existing product checks and defects retain their outcomes.

## What is implemented

- `github.mjs`: authenticated GitHub transport; successful main admission; run/artifact provenance checks; bounded archive download with its provider SHA-256 digest; a single expected JSON entry without extracting files to disk. Tokens are not forwarded to the artifact download host. Downloaded records still require reviewed provider collectors to establish the facts they contain.
- `qualification.mjs`: separate closed metadata envelopes for stage qualification and previously recorded production expectations. A stage preflight PASS cannot become delivered-stage proof. No phase helper grants production eligibility or decides the unresolved backup-approval policy.
- `lease.mjs`: one create-only GitHub ref per target, unique owner object, ownership checks and atomic expected-object removal through Git. CI and future supported local commands use this same module. The staging branch update is ancestry-only, uses `force: false`, checks current main again immediately before the update and verifies the resulting SHA. It never creates a missing staging branch or resolves divergence automatically.
- `controller.mjs`: a runnable transport-injected state machine. Staging admission precedes the lease; exact branch advancement, eligible additive plan, schema/data postconditions, staged build and runtime/installed-extension checks precede either fixed alias. Production has its own approval path. Every consequential transition repeats authority, original G0 evidence freshness and a newly collected current-state comparison.
- `*.test.mjs`: explicitly simulated transports exercise denied inputs, ordering, compatibility, stale evidence, concurrency and ownership replacement. These tests perform no hosted mutation and prove no product behavior.

## Required provider integration before activation

There is deliberately no loadable adapter module option, provider URL override, PASS-file input, secret-presence switch or environment flag that enables mutation. The hosted entrypoint is not yet wired to the control core: the missing collector/executor composition must be implemented and reviewed, then exercised with real authenticated evidence. This is an explicit incomplete activation prerequisite, not an operator configuration task.

The controller receives `{record, policy, releaseDigest}` from a trusted collector, never directly from a CLI file. `snapshot` returns `{observed, aliases}`, where `observed` follows G0. `aliases` is the complete fixed domain-to-deployment map. For staging, `observed.baseline` identifies the primary `staging.mintedpanel.com` app; the secondary alias moves first. `observed.staging` retains the last verified stage record until the primary alias moves, then binds the checked candidate and its check timestamp. Actual schema/ledger data remains current throughout.

A phase receipt binds `releaseDigest`, phase, exact candidate and the complete actual snapshot using `receiptBinding`. It carries status, artifact digest and completion time. Only the reviewed provider collector may produce it. Its JSON shape is not authentication; the injected simulator is never an activation option.

## Stage qualification artifact boundary

The future successful producer emits one `staging-qualification.json` file in artifact `minted-staging-qualification-<run>-<attempt>`. Its outer object contains `qualification` and `sourceCiRunId`. The qualification contains the original stage-only G0 record, trusted policy, real historical observation and `validatedAt`, plus a separate `DELIVERED` result. That result binds the exact candidate, result schema/ordered lineage, complete fixed alias map, original verification times and a passing served-postconditions receipt. The receipt hashes the same candidate and entire actual snapshot that it tested.

`loadStagingQualification` verifies the authenticated producer/artifact/digest, places qualification times inside that actual run, rechecks the successful originating main CI and rejects a source that is no longer current main. It validates the historical preflight at its recorded validation time and independently enforces evidence age at the current trusted clock. It never changes old timestamps or treats a historical observation as a current snapshot. Wrong target, alias, schema, lineage, receipt, source, phase, unknown fields or stale evidence reject the envelope.

The real controller-to-artifact emission remains unwired. Its current `DELIVERED` return alone supplies neither the stored final snapshot nor the served receipt required here; a reviewed collector must supply those actual facts. Synthetic fixture envelopes are only contract tests. Production expectations are a separate authenticated historical artifact, never production facts collected by staging.

## Shared lease and failures

Target refs are `refs/tags/minted-delivery-lock-staging` and `refs/tags/minted-delivery-lock-production`. Acquisition creates a unique annotated owner object and atomically creates the target ref. An existing ref blocks a second writer. There is no expiry, force takeover, or automatic lease stealing. GitHub concurrency uses `cancel-in-progress: false` as an additional CI control; it does not coordinate local operators by itself.

Release uses `git push --force-with-lease=<exact-ref>:<owned-object> ... :<exact-ref>`. An ownership replacement immediately before removal causes rejection; REST read-then-delete is not used. Credential material remains in the child process environment and is not printed in errors. The provider/Git permissions required for the namespace and compare-delete still need hosted verification. [GitHub reference API](https://docs.github.com/en/rest/git/refs), [Git expected-object lease semantics](https://git-scm.com/docs/git-push).

Any attempted target mutation with a failed or uncertain outcome retains the lease. Check the owning run and remote state; establish that the owner has stopped and no provider mutation remains in flight before planning reconciliation. This version exposes no break-lock or local deploy bypass. Do not delete the ref merely because it is old, cancel a database operation to free it, or reverse database changes automatically.

Alias assignments are separate provider operations. Passing checks precedes both assignments, but a transport failure during the second can leave a partial cutover. The controller stops with the lease retained for reconciliation; it does not claim atomic two-domain publication.

## Verification and current limits

Run `node --test scripts/delivery/*.test.mjs` and `npm run test:release`. The integration owner adds delivery tests to the existing required Release guardrails CI job. No test logins, private backup data or provider credential values belong in fixtures or artifacts.

Before DB/domain mutation, a newly collected and fully G0-valid observation of the unchanged actual baseline can replace an older observation, including after a long production build. Once target mutation begins, the last real G0 observation is retained as `preMutationSnapshot`, with its original timestamp. Actual post-application state is compared against the exact approved result schema/ledger, current served deployment/configuration, fixed aliases, backup and extension set. If that snapshot ages out while an operation runs, this first version stops conservatively; it never refreshes timestamps on old evidence. Supporting longer post-application operations needs a reviewed G0 phase extension, not larger arbitrary timeouts or fabricated “fresh” values.

The shared project's `gitProviderOptions.createDeployments` setting concerns GitHub deployment records; it is not proof that Vercel builds are frozen. Require actual Git disconnection and readback, plus the source control above. Read-only capability evidence and provider denial tests remain coordinator-owned. Local extension installation also does not prove that its bearer-authenticated API requests can pass current Vercel protection. That access blocker must be resolved through the approved testing path without packaging a protection bypass.
