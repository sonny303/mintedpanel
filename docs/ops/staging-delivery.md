# Staging delivery controls

**Status: local control implementation; hosted activation is blocked.** Run `node scripts/delivery/cli.mjs status` for the explicit capability gaps. Its exit status is 2. Neither a green simulator test nor supplied JSON authorizes deployment.

The `staging-delivery.yml` workflow is manually dispatched from main while private-repository branch and environment reviewer controls remain unenforced. The operator supplies the current successful main push CI run ID and exact source SHA. The job checks out the immutable trusted workflow revision and verifies both inputs against GitHub's run and current main. It rejects automatic events, reruns, forks, non-push CI runs, failed/skipped CI, wrong workflow paths and mismatched or stale source. The hosted delivery entrypoint then stops before acquiring a lease or calling Vercel/Supabase. Existing product checks and defects retain their outcomes. Production remains blocked.

Agreed release sequence: **PR → CI → merge to main → manually initiated staging deployment and verification → owner-approved production release.** Keep automatic Git deployments disabled, use existing resources within included allowances, and retain the hosted activation and credential-isolation gates.

## What is implemented

- `github.mjs`: authenticated GitHub transport; successful main admission; run/artifact provenance checks; bounded archive download with its provider SHA-256 digest; a single expected JSON entry without extracting files to disk. Tokens are not forwarded to the artifact download host. Downloaded records still require reviewed provider collectors to establish the facts they contain.
- `qualification.mjs`: separate closed metadata envelopes for stage qualification and previously recorded production expectations. A stage preflight PASS cannot become delivered-stage proof. Neither phase helper grants production eligibility. The approved backup policy and later production binding live in `intent.mjs` and `production.mjs`.
- `lease.mjs`: one create-only GitHub ref per target, unique owner object, ownership checks and atomic expected-object removal through Git. CI and future supported local commands use this same module. The staging branch update is ancestry-only, uses `force: false`, checks current main again immediately before the update and verifies the resulting SHA. It never creates a missing staging branch or resolves divergence automatically.
- `staging-source.mjs`: repeatable source-only admission using authenticated successful main CI, the exact remote staging ref and a real isolated local Git checkout. It compares the index and actual file bytes with the admitted commit. Its result is a prerequisite only; it neither deploys nor authenticates a hosted Vercel candidate.
- `staging-vercel.mjs`: a fixed-team/fixed-project Preview adapter for the dedicated staging project. It rejects Git linkage, automation protection bypasses, unexpected project/domain settings, shared environment inheritance, any environment key/scope/value drift and active deployments before upload. One validated actual Chrome ID drives an explicit single batch upsert of `VITE_MINTED_EXTENSION_ID` and its matching CORS origin; both stay Preview-only and the service returns sanitized before/after readbacks and configuration digests. Build never changes project settings and rejects until the complete desired inventory exists. It uploads only files from the twice-admitted staging manifest, creates a protected Preview with no fixed alias target, verifies the returned source/configuration metadata and complete provider file tree, and can assign only the two known staging aliases to a candidate created by that adapter. Its provider-only service seam cannot be mistaken for database/recovery G0. The hosted CLI still cannot reach it while the runtime/recovery composition below is incomplete. See [H10 staging Vercel identity](h10-staging-vercel.md).
- `controller.mjs`: a runnable transport-injected state machine. Staging admission precedes the lease; exact branch advancement, eligible additive plan, schema/data postconditions, staged build and runtime/installed-extension checks precede either fixed alias. Production has its own approval path. Every consequential transition repeats authority, original G0 evidence freshness and a newly collected current-state comparison.
- `*.test.mjs`: explicitly simulated transports exercise denied inputs, ordering, compatibility, stale evidence, concurrency and ownership replacement. These tests perform no hosted mutation and prove no product behavior.

The controller receives `{record, policy, releaseDigest}` from a trusted collector, never directly from a CLI file. `snapshot` returns `{observed, aliases}`, where `observed` follows G0. `aliases` is the complete fixed domain-to-deployment map. For staging, `observed.baseline` identifies the primary `staging.mintedpanel.com` app; the secondary alias moves first. `observed.staging` retains the last verified stage record until the primary alias moves, then binds the checked candidate and its check timestamp. Actual schema/ledger data remains current throughout.

Only the reviewed provider collector may produce it. Its JSON shape is not authentication; the injected simulator is never an activation option.

Keep workflow control code on the immutable trusted **main** revision. The future fixed composition may call `admitStagingSource({ github, checkoutRoot, ciRunId, sourceSha })`, using the existing trusted `createGitHub` adapter and an exclusively owned source checkout. No caller-supplied clean boolean, file manifest, branch metadata, command runner, target override or saved PASS is accepted. It reads successful main CI and current main through the existing admission helper, requires the exact remote `refs/heads/staging` commit, inspects local files, then repeats both authority and local checks, and re-admits remote authority once more after the final local inspect so a tip that moved during that inspect cannot inherit the earlier PASS. Missing, divergent, detached, non-staging or stale source rejects; it never creates or changes a Git ref or checkout.

Local inspection requires a canonical standalone clone with its own `.git` directory and canonical repository origin. Linked worktrees, external object alternates, replacement refs, submodules, symlinks, hardlinked working files and unsupported file modes are refused. Full strict `git fsck` checks loose and packed object integrity before deriving the tree manifest; recursive `ls-tree` alone can accept a corrupted nested object under an unchanged object filename. Its skip list is fixed to `/dev/null`. The complete index must match stage-zero entries from the admitted commit. Working files are streamed into Git blob hashes and compared independently, including executable mode; `assume-unchanged`, `skip-worktree` and local status settings cannot hide different bytes. No `git status`, diff, clean/process filter, hook, shell, fetch or install is used. The fixed Git child environment disables lazy fetching and allows no transport protocols, including local file transports; missing objects cannot trigger an implicit fetch. Extra files or directories are rejected even if ignored, including `.env`, `.vercel`, `node_modules` and build output. Inspection is bounded to 20,000 files, 64 MiB per file, 512 MiB total and 10 seconds per Git read; exceeding a limit fails closed. [Git object integrity checks](https://git-scm.com/docs/git-fsck)

This strict source-only checkout must remain separate from dependency installation, build credentials and output. The future reviewed executor must define and verify that handoff; the helper does not grant exceptions for generated files. Re-run it immediately before consuming the source, maintain exclusive checkout ownership, and bind the resulting source/tree identity to the actual build artifact. Repeated reads cannot freeze a repository against a concurrent same-user writer after the function returns.

The bounded result contains only status, repository, source SHA, CI run ID, fixed Git ref, tree SHA and file count, plus `hostedDeploymentVerified: false` and `deploymentEligibility: "NOT_EVALUATED"`. It contains no local paths, filenames, file contents, credentials or provider bodies. Errors use a closed static code set. The function has no CLI or provider-write path, and its GitHub dependency is an internal trusted-composition seam, not an operator-selectable adapter. It does not independently authenticate the current staging workflow runner or prove Vercel's returned source/configuration; those remain required integration checks.

The G0 staging allowlist now names the dedicated project, and the fixed adapter implements project/team-qualified REST requests, exact all-Preview metadata validation, automation-bypass denial, atomic Chrome-ID/CORS input derivation, content-addressed file upload, Preview candidate readback and fixed-alias assignment/readback. Generated Preview URLs retain Vercel Authentication; no automation bypass credential is accepted or packaged. This is reviewed code capability, not hosted proof: no application candidate has been created, the staging token has not exercised this path, and runtime/database/compatibility evidence services remain missing. The current controller also binds a single preflight target-configuration digest and does not yet model the explicit identity transition; the later integration PR must bind the after-digest before build. `assertHostedReady` therefore remains in place. Do not copy the local OAuth bootstrap command into scoped-token CI: CLI 59.11.7 scope discovery requires user/team reads, and owner-lookup fallback can omit a request team ID.

## Stage qualification artifact boundary

The future successful producer emits one `staging-qualification.json` file in artifact `minted-staging-qualification-<run>-<attempt>`. Its outer object contains `qualification` and `sourceCiRunId`. The qualification contains the original stage-only G0 record, trusted policy, real historical observation and `validatedAt`, plus a separate `DELIVERED` result. That result binds the exact candidate, result schema/ordered lineage, complete fixed alias map, original verification times and a passing served-postconditions receipt. The receipt hashes the same candidate and entire actual snapshot that it tested.

`loadStagingQualification` verifies the authenticated producer/artifact/digest, places qualification times inside that actual run, rechecks the successful originating main CI and rejects a source that is no longer current main. It validates the historical preflight at its recorded validation time and independently enforces evidence age at the current trusted clock. It never changes old timestamps or treats a historical observation as a current snapshot. Wrong target, alias, schema, lineage, receipt, source, phase, unknown fields or stale evidence reject the envelope.

The real controller-to-artifact emission remains unwired. Its current `DELIVERED` return alone supplies neither the stored final snapshot nor the served receipt required here; a reviewed collector must supply those actual facts. Synthetic fixture envelopes are only contract tests. Production expectations are a separate authenticated historical artifact, never production facts collected by staging.

Production preparation authenticates these stage-only facts and the historical Production baseline, then emits an immutable approval intent. It cannot obtain fresh production G0 or choose a production backup. After the single approval, the protected composition selects and verifies a fresh matching production backup, binds its exact identity into full production G0, and rechecks it before changes. See [the production release contract](production-release.md). G0 now names the dedicated staging project `prj_1t7NkRJMkjTuFXEBEP4GjfN4B6Ch`; its stable aliases remain on the prior baseline because no application candidate or cutover has been authorized.

## Shared lease and failures

Target refs are `refs/tags/minted-delivery-lock-staging` and `refs/tags/minted-delivery-lock-production`. Acquisition creates a unique annotated owner object and atomically creates the target ref. An existing ref blocks a second writer. There is no expiry, force takeover, or automatic lease stealing. GitHub concurrency uses `cancel-in-progress: false` as an additional CI control; it does not coordinate local operators by itself.

Release uses `git push --force-with-lease=<exact-ref>:<owned-object> ... :<exact-ref>`. An ownership replacement immediately before removal causes rejection; REST read-then-delete is not used. Credential material remains in the child process environment and is not printed in errors. The provider/Git permissions required for the namespace and compare-delete still need hosted verification. [GitHub reference API](https://docs.github.com/en/rest/git/refs), [Git expected-object lease semantics](https://git-scm.com/docs/git-push).

Any attempted target mutation with a failed or uncertain outcome retains the lease. Check the owning run and remote state; establish that the owner has stopped and no provider mutation remains in flight before planning reconciliation. This version exposes no break-lock or local deploy bypass. Do not delete the ref merely because it is old, cancel a database operation to free it, or reverse database changes automatically.

Alias assignments are separate provider operations. Passing checks precedes both assignments, but a transport failure during the second can leave a partial cutover. The controller stops with the lease retained for reconciliation; it does not claim atomic two-domain publication.

## Verification and current limits

Run `node --test scripts/delivery/*.test.mjs` and `npm run test:release`. The integration owner adds delivery tests to the existing required Release guardrails CI job. No test logins, private backup data or provider credential values belong in fixtures or artifacts.

Before DB/domain mutation, a newly collected and fully G0-valid observation of the unchanged actual baseline can replace an older observation, including after a long production build. Once target mutation begins, the last real G0 observation is retained as `preMutationSnapshot`, with its original timestamp. Actual post-application state is compared against the exact approved result schema/ledger, current served deployment/configuration, fixed aliases, backup and extension set. If that snapshot ages out while an operation runs, this first version stops conservatively; it never refreshes timestamps on old evidence. Supporting longer post-application operations needs a reviewed G0 phase extension, not larger arbitrary timeouts or fabricated “fresh” values.

The provider's `gitProviderOptions.createDeployments` setting concerns GitHub deployment records; it is not proof that Vercel builds are frozen. Require actual Git disconnection and readback, plus the source control above. The fixed adapter and current operator read validate Git disconnection in the dedicated project, but scoped-token capability and denial evidence remain coordinator-owned. Local extension installation also does not prove that its bearer-authenticated API requests can pass current Vercel protection. That access blocker must be resolved through the approved testing path without packaging a protection bypass.
