# E4.5 — Document Storage: Provider & Group Documents with Expiration Tracking

## Purpose and Context

`[r6]` decision D: credentialing work is document work — the "Assigned" phase
of every case is a specialist verifying required documents are active (A1).
This epic adds first-class document storage at two grains: **per-provider**
(State License, DEA, COI, CV, board certs, …) and **per-group** (W-9, COI,
CMS-460, Voided Check, …). **Expiration tracking is mandatory this release**
— upload/attach-only is just a file system; active credentialing software
tracks expiration dates (State License, DEA, COI) to feed the readiness radar
(R9), displayed in a clean, tight data table so specialists instantly spot
expiring credentials before they block a submission.

**Auto-attach via the extension is explicitly deferred** (D3): legacy portal
file inputs have variable security constraints and cross-origin file
injection trips portal security blocks. The specialist manually downloads /
drags-and-drops the PDF from secure storage. This is NOT a fast follow — it
is prioritized after the redesign — but the storage architecture chosen in
this epic **must support that future auto-attach** (documents individually
addressable and retrievable by the extension's authenticated API path with
scoped, audited, time-limited access; §5 records the concrete design).

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — verifies document
  readiness during the Assigned phase; downloads documents while submitting
  on portals.
- **P1 Credentialing Manager** — sees expiring credentials across the org
  before they block submissions.
- **P5 Practice / Organization Owner** — future ingress via onboarding
  (non-goal here beyond the seam).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Storage on Supabase Storage with org-scoped access rules matching the RLS
  model; metadata in additive tables (document kind, owner grain
  provider|group, issue/expiration dates, file ref). Reviewer records
  bucket/policy design in §5 — designed explicitly to satisfy the D3
  future-auto-attach requirement (per-document addressability via the
  server API path).
- PHI handling: documents are the most sensitive files in the system —
  no public URLs; signed, short-lived, audited access only.

## Features

### F4.5.1 — Provider & group document stores

- **Description:** A Documents surface on the provider record and on the
  provider group: upload (PDF/image), typed by document kind (managed
  vocabulary: State License, DEA, COI, W-9, CMS-460, Voided Check, CV,
  Other), with issue/expiration dates captured at upload where the kind
  expects them. Versioned by re-upload (prior versions retained, current
  clearly marked).
- **Persona:** P2, P1.
- **Benefit hypothesis:** D1's two grains match how payers actually ask for
  paperwork — provider docs vs. group docs — ending scattered local copies.
- **Acceptance criteria:**
  - Provider and group records each show their document table (kind,
    dates, current version, uploader, uploaded-at).
  - Uploads are org-scoped; no cross-org access; access is signed and
    audited.
  - Kinds that expire require an expiration date at upload.
- **Test/data scenario(s):** TS-88.

### F4.5.2 — Expiration tracking & expiring-credentials table

- **Description:** Expiration dates are structured columns, not file
  metadata. A tight data table (org-level and per-provider) lists documents
  by soonest expiration with clear expired / expiring-soon / current
  states, so specialists instantly spot what blocks a submission. Readiness
  (E1.8) gains the document dimension where it already checks credentials
  (COI check exists; license/DEA document status joins it), staying
  advisory per the locked readiness rule.
- **Persona:** P1, P2.
- **Benefit hypothesis:** D2 — expiration visibility feeds the readiness
  radar (R9) and prevents dead-on-arrival submissions.
- **Acceptance criteria:**
  - The expiring-credentials table sorts by expiration and renders
    expired / expiring-soon / current distinctly (derived, no stored
    flags).
  - E1.8 readiness reflects document expiration where the credential is
    already part of readiness — advisory only.
  - Thresholds for "expiring soon" are documented (reviewer default: 30 /
    60 / 90 days by kind; PM may adjust at review).
- **Test/data scenario(s):** TS-89.

```gherkin
Feature: Expiring credentials surface before they block
  Scenario: COI expiring inside the window
    Given a group COI expiring in 21 days
    When P1 opens the expiring-credentials table
    Then the COI row shows expiring-soon with its date
    And the group's readiness view carries the advisory warning
```

### F4.5.3 — Case-side document verification & manual attach flow

- **Description:** The case view (Assigned phase) shows the documents its
  SOP/checklist requires with their live status (present / missing /
  expired), and offers one-click download of each current document so the
  specialist can manually attach it on the payer portal (the documented D3
  interim path, also linked from the extension panel as download-only).
- **Persona:** P2.
- **Benefit hypothesis:** A1's Assigned phase ("verify all required
  documents are active") becomes a glance instead of a hunt, and portal
  attach is two clicks away.
- **Acceptance criteria:**
  - The case shows required-document status derived from the document
    store; missing/expired items are explicit.
  - Download delivers the current version via a signed, audited,
    short-lived URL.
  - The extension panel links the same downloads (no injection/auto-attach).
- **Test/data scenario(s):** TS-90.

## Dependencies

- Supabase Storage (first storage-bucket usage in the redesign — reviewer
  confirms org-scoped policy design in §5).
- E1.8 readiness (advisory document dimension), E1.7b SOPs (required-doc
  linkage), E4.0 case lifecycle (Assigned phase surface), E4.3 extension
  panel (download links).
- `[r6]` D3 architecture requirement: per-document addressability for
  future extension auto-attach (post-redesign roadmap item).

## Out of Scope / Non-Goals

- **No auto-attach / file injection via the extension** — deferred
  post-redesign by PM decision D3; this epic only guarantees the
  architecture supports it.
- No OCR/data extraction from uploaded documents.
- No provider/org-rep upload surfaces (onboarding document intake is a
  later epic; internal upload only in R6).
- No document e-signing or generation.
