# E4.5 — Document Storage: Provider & Group Documents with Expiration Tracking

## Purpose and Context

`[r6]` decision D: credentialing work is document work — the "Assigned" phase
of every case is a specialist verifying required documents are active (A1).
This epic adds first-class document storage at two grains: **per-provider**
(State License, DEA, COI, CV, board certs, …) and **per-group** (W-9, COI,
CMS-460, Voided Check, …). **Expiration tracking is mandatory this release**
— upload/attach-only is just a file system; active credentialing software
tracks expiration dates (State License, DEA, COI) to feed the readiness radar
(R9), displayed in a clean, tight data table so specialists instantly spot
expiring credentials before they block a submission.

**Auto-attach via the extension is explicitly deferred** (D3): legacy portal
file inputs have variable security constraints and cross-origin file
injection trips portal security blocks. The specialist manually downloads /
drags-and-drops the PDF from secure storage. This is NOT a fast follow — it
is prioritized after the redesign — but the storage architecture chosen in
this epic **must support that future auto-attach** (documents individually
addressable and retrievable by the extension's authenticated API path with
scoped, audited, time-limited access; §5 records the concrete design).

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — verifies document
  readiness during the Assigned phase; downloads documents while submitting
  on portals.
- **P1 Credentialing Manager** — sees expiring credentials across the org
  before they block submissions.
- **P5 Practice / Organization Owner** — future ingress via onboarding
  (non-goal here beyond the seam).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Storage on Supabase Storage with org-scoped access rules matching the RLS
  model; metadata in additive tables (document kind, owner grain
  provider|group, issue/expiration dates, file ref). Reviewer records
  bucket/policy design in §5 — designed explicitly to satisfy the D3
  future-auto-attach requirement (per-document addressability via the
  server API path).
- PHI handling: documents are the most sensitive files in the system —
  no public URLs; signed, short-lived, audited access only.

## Features

### F4.5.1 — Provider & group document stores

- **Description:** A Documents surface on the provider record and on the
  provider group: upload (PDF/image), typed by document kind (managed
  vocabulary: State License, DEA, COI, W-9, CMS-460, Voided Check, CV,
  Other), with issue/expiration dates captured at upload where the kind
  expects them. Versioned by re-upload (prior versions retained, current
  clearly marked).
- **Persona:** P2, P1.
- **Benefit hypothesis:** D1's two grains match how payers actually ask for
  paperwork — provider docs vs. group docs — ending scattered local copies.
- **Acceptance criteria:**
  - Provider and group records each show their document table (kind,
    dates, current version, uploader, uploaded-at).
  - Uploads are org-scoped; no cross-org access; access is signed and
    audited.
  - Kinds that expire require an expiration date at upload.
- **Test/data scenario(s):** TS-88.

### F4.5.2 — Expiration tracking & expiring-credentials table

- **Description:** Expiration dates are structured columns, not file
  metadata. A tight data table (org-level and per-provider) lists documents
  by soonest expiration with clear expired / expiring-soon / current
  states, so specialists instantly spot what blocks a submission. Readiness
  (E1.8) gains the document dimension where it already checks credentials
  (COI check exists; license/DEA document status joins it), staying
  advisory per the locked readiness rule.
- **Persona:** P1, P2.
- **Benefit hypothesis:** D2 — expiration visibility feeds the readiness
  radar (R9) and prevents dead-on-arrival submissions.
- **Acceptance criteria:**
  - The expiring-credentials table sorts by expiration and renders
    expired / expiring-soon / current distinctly (derived, no stored
    flags).
  - E1.8 readiness reflects document expiration where the credential is
    already part of readiness — advisory only.
  - Thresholds for "expiring soon" are documented (reviewer default: 30 /
    60 / 90 days by kind; PM may adjust at review).
- **Test/data scenario(s):** TS-89.

```gherkin
Feature: Expiring credentials surface before they block
  Scenario: COI expiring inside the window
    Given a group COI expiring in 21 days
    When P1 opens the expiring-credentials table
    Then the COI row shows expiring-soon with its date
    And the group's readiness view carries the advisory warning
```

### F4.5.3 — Case-side document verification & manual attach flow

- **Description:** The case view (Assigned phase) shows the documents its
  SOP/checklist requires with their live status (present / missing /
  expired), and offers one-click download of each current document so the
  specialist can manually attach it on the payer portal (the documented D3
  interim path, also linked from the extension panel as download-only).
- **Persona:** P2.
- **Benefit hypothesis:** A1's Assigned phase ("verify all required
  documents are active") becomes a glance instead of a hunt, and portal
  attach is two clicks away.
- **Acceptance criteria:**
  - The case shows required-document status derived from the document
    store; missing/expired items are explicit.
  - Download delivers the current version via a signed, audited,
    short-lived URL.
  - The extension panel links the same downloads (no injection/auto-attach).
- **Test/data scenario(s):** TS-90.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the existing document metadata table
(`provider_documents` in `20260704210000_baseline_live_schema.sql` — `doc_type`
CHECK `w9|coi|state_license|dea|diploma|board_cert|voided_check|filled_form|other`,
`file_path`, `file_name`, `effective_date`, `expiration_date`, owner grain via
nullable `provider_id`/`group_id`/`case_id` with the `provider_documents_owner_required`
CHECK, org-scoped RLS with writer INSERT/DELETE + member SELECT, FK-cover
indexes), readiness (`src/services/enrollmentReadiness.ts` already reads
`provider_documents` group docs — `w9|coi|voided_check` — presence + expiration
only), the E1.8 readiness rules (advisory), the extension `/api` surface + audit
contract (E4.3 §5), and `uiux-component-guide.md`. **Confirmed no Supabase
Storage bucket or `storage.*` policy exists anywhere in `supabase/` or `src/`.**
**Headline:** the metadata half of this epic already ships — the table, both
grains, and the expiration columns exist and readiness already consumes them.
The genuinely new work is (a) the first Supabase **Storage** bucket + org-scoped
access policy + signed-URL retrieval (the bytes, which today have only a
`file_path` pointer and no bucket), (b) re-upload versioning, and (c) the derived
expiring-credentials + case-verification surfaces. The D3 future-auto-attach
requirement is satisfied by making each document individually addressable and
retrievable over the authenticated `/api` path — no injection is built._

- **TE-1 — Reuse `provider_documents`; two additive changes only.** Do NOT add a
  new table. (i) Widen the `doc_type` CHECK with the drop-and-re-add-union
  pattern to add the kinds the epic names that are missing — `cms_460` and `cv`
  (State License/DEA/COI/W-9/Voided Check/Other and board-cert/diploma already
  exist) — keeping every existing value valid. (ii) Add re-upload versioning
  columns: `version int NOT NULL DEFAULT 1` + `superseded_by uuid NULL REFERENCES
provider_documents(id)` (or an `is_current boolean`) so a re-upload inserts a
  new current row and retains prior versions rather than mutating (F4.5.1
  "versioned by re-upload, prior versions retained, current clearly marked").
  Both additive, repo + hosted; `types.ts` regenerated; `DocumentKind` union +
  the `ProviderDocument` domain type extended additively; the `provider_documents`
  register row updated in the same PR.

- **TE-2 — First Supabase Storage bucket + org-scoped policy + signed URLs (the
  new surface).** Create a **private** bucket (e.g. `provider-documents`) with a
  storage-object path convention keyed by org (`{org_id}/{owner}/{document_id}/…`)
  and `storage.objects` RLS policies that gate read/write to members of that
  `org_id` (mirroring the table's `user_org_ids()`/`user_role` predicates via
  `storage.foldername(name)[1] = org_id::text`). No public URLs ever; retrieval is
  a **short-lived signed URL** (`createSignedUrl`) minted server-side and audited
  (a `READ` `audit_log` row per issuance — the profile-read precedent). `file_path`
  becomes the object key. Uploads are writer-role (`specialist|admin`) matching
  the existing table policy; DELETE stays writer per the shipped policy (or is
  disabled in favour of versioning — reviewer default: keep DELETE off the UI,
  supersede instead). New service `src/services/documents.ts` (upload → put object
  - insert metadata row; list; sign-download) → `src/hooks/useDocuments.ts`; the
    bucket/policy live in a migration + are documented as env setup (bucket
    creation is a Storage-admin step, flagged).

- **TE-3 — Expiration tracking & table are fully derived; readiness extends the
  existing reader (F4.5.2).** Expiration is the structured `expiration_date`
  column (already present), not file metadata. The expiring-credentials table
  (org-level + per-provider) sorts by soonest `expiration_date` and renders
  `expired | expiring-soon | current` derived at read time (no stored flag; E1.0
  derived rule). **Reviewer default thresholds:** expiring-soon at 30/60/90 days
  by kind (e.g. 30 for COI, 60 for DEA, 90 for State License) — documented and
  PM-adjustable at review. Readiness already reads group docs; extend
  `enrollmentReadiness.ts` to also read provider `state_license`/`dea` document
  expiration where the credential is already part of readiness, staying
  **advisory only** (locked readiness rule) — presence + expiration only, never
  file paths/contents (the existing reader's PHI posture).

- **TE-4 — Case-side verification + manual-attach download (F4.5.3).** The case
  (Assigned phase) shows the documents its SOP/checklist requires with live
  `present | missing | expired` status, derived by joining the SOP's required-doc
  list (E1.7b) against the document store for that provider/group — no stored
  status. One-click download delivers the current version via the TE-2 signed,
  short-lived, audited URL. The extension panel links the same download-only URLs
  (E4.3) — explicitly NO injection/auto-attach (D3 deferred). This is the
  documented interim manual path.

- **TE-5 — D3 future-auto-attach is satisfied by addressability, not built.**
  Each document is individually addressable by `id` and retrievable over the
  authenticated `/api` path with a scoped, audited, time-limited signed URL — so
  a future extension auto-attach has a per-document retrieval contract to build
  on. This epic ships only the retrieval contract + download-only links; no
  cross-origin file injection (the PM's D3 deferral; portal security blocks it).

- **TE-6 — Seed + tests.** Seed TS-88 (two-grain uploads, typed kinds,
  versioning, org scoping), TS-89 (staggered expirations across the three
  states), TS-90 (a case with SOP-required documents) on the Dillon
  provider/group fixtures. Because Storage objects are not part of the SQL seed,
  the file-bytes paths run through a mock harness / fixture upload; the metadata
  rows seed normally. e2e covers the expiring-credentials states, the derived
  case-verification status, and that download uses a signed (never public) URL.

### Open items / flags for the PM

  must be applied to the hosted project, not just declared in a migration.
- **Expiring-soon thresholds:** reviewer default 30/60/90 by kind — confirm or

- **Delete vs. supersede:** the shipped table has a writer DELETE policy;
  reviewer default is to prefer versioned supersession over hard delete in the
