# E4.5 — Document Storage: Provider & Group Documents with Expiration Tracking

## Purpose and Context

`[r6]` decision D: credentialing work is document work — the "Assigned" phase
of every case is a specialist verifying required documents are active (A1).
This epic adds first-class document storage at two grains: **per-provider**
(State License, DEA, COI, CV, board certs, …) and **per-group** (W-9, COI,
CMS-460, Voided Check, …). **Expiration tracking is mandatory this release**
— upload/attach-only is just a file system; active credentialing software
tracks expiration dates (State License, DEA, COI) to feed the readiness radar
(R9), displayed in a clean, tight data table so specialists instantly spot
expiring credentials before they block a submission.

**Auto-attach via the extension is explicitly deferred** (D3): legacy portal
file inputs have variable security constraints and cross-origin file
injection trips portal security blocks. The specialist manually downloads /
drags-and-drops the PDF from secure storage. This is NOT a fast follow — it
is prioritized after the redesign — but the storage architecture chosen in
this epic **must support that future auto-attach** (documents individually
addressable and retrievable by the extension's authenticated API path with
scoped, audited, time-limited access; §5 records the concrete design).

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — verifies document
  readiness during the Assigned phase; downloads documents while submitting
  on portals.
- **P1 Credentialing Manager** — sees expiring credentials across the org
  before they block submissions.
- **P5 Practice / Organization Owner** — future ingress via onboarding
  (non-goal here beyond the seam).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Storage on Supabase Storage with org-scoped access rules matching the RLS
  model; metadata in additive tables (document kind, owner grain
  provider|group, issue/expiration dates, file ref). Reviewer records
  bucket/policy design in §5 — designed explicitly to satisfy the D3
  future-auto-attach requirement (per-document addressability via the
  server API path).
- PHI handling: documents are the most sensitive files in the system —
  no public URLs; signed, short-lived, audited access only.

## Features

### F4.5.1 — Provider & group document stores

- **Description:** A Documents surface on the provider record and on the
  provider group: upload (PDF/image), typed by document kind (managed
  vocabulary: State License, DEA, COI, W-9, CMS-460, Voided Check, CV,
  Other), with issue/expiration dates captured at upload where the kind
  expects them. Versioned by re-upload (prior versions retained, current
  clearly marked).
- **Persona:** P2, P1.
- **Benefit hypothesis:** D1's two grains match how payers actually ask for
  paperwork — provider docs vs. group docs — ending scattered local copies.
- **Acceptance criteria:**
  - Provider and group records each show their document table (kind,
    dates, current version, uploader, uploaded-at).
  - Uploads are org-scoped; no cross-org access; access is signed and
    audited.
  - Kinds that expire require an expiration date at upload.
- **Test/data scenario(s):** TS-88.

### F4.5.2 — Expiration tracking & expiring-credentials table

- **Description:** Expiration dates are structured columns, not file
  metadata. A tight data table (org-level and per-provider) lists documents
  by soonest expiration with clear expired / expiring-soon / current
  states, so specialists instantly spot what blocks a submission. Readiness
  (E1.8) gains the document dimension where it already checks credentials
  (COI check exists; license/DEA document status joins it), staying
  advisory per the locked readiness rule.
- **Persona:** P1, P2.
- **Benefit hypothesis:** D2 — expiration visibility feeds the readiness
  radar (R9) and prevents dead-on-arrival submissions.
- **Acceptance criteria:**
  - The expiring-credentials table sorts by expiration and renders
    expired / expiring-soon / current distinctly (derived, no stored
    flags).
  - E1.8 readiness reflects document expiration where the credential is
    already part of readiness — advisory only.
  - Thresholds for "expiring soon" are documented (reviewer default: 30 /
    60 / 90 days by kind; PM may adjust at review).
- **Test/data scenario(s):** TS-89.

```gherkin
Feature: Expiring credentials surface before they block
  Scenario: COI expiring inside the window
    Given a group COI expiring in 21 days
    When P1 opens the expiring-credentials table
    Then the COI row shows expiring-soon with its date
    And the group's readiness view carries the advisory warning
```

### F4.5.3 — Case-side document verification & manual attach flow

- **Description:** The case view (Assigned phase) shows the documents its
  SOP/checklist requires with their live status (present / missing /
  expired), and offers one-click download of each current document so the
  specialist can manually attach it on the payer portal (the documented D3
  interim path, also linked from the extension panel as download-only).
- **Persona:** P2.
- **Benefit hypothesis:** A1's Assigned phase ("verify all required
  documents are active") becomes a glance instead of a hunt, and portal
  attach is two clicks away.
- **Acceptance criteria:**
  - The case shows required-document status derived from the document
    store; missing/expired items are explicit.
  - Download delivers the current version via a signed, audited,
    short-lived URL.
  - The extension panel links the same downloads (no injection/auto-attach).
- **Test/data scenario(s):** TS-90.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the dormant
`provider_documents` metadata table in the baseline schema and data-model
register, its current organization RLS/indexes, and the existing advisory
readiness read in `src/services/enrollmentReadiness.ts`. No repository-managed
Storage bucket, `storage.objects` policies, signed-download route, document
service/hook, or UI currently exists. The existing metadata table is the
starting point, but secure object storage and immutable version semantics are
required before it becomes an application feature._

- **TE-1 — Reuse `provider_documents` as immutable version metadata.** Keep its
  existing `org_id`, `provider_id`, `group_id`, optional `case_id`, `doc_type`,
  object path/name, effective/expiration dates, uploader, and created time.
  Add a stable document-family ID, positive version number, and nullable
  `supersedes_document_id`. E4.5 upload services require exactly one canonical
  provider or group owner; `case_id` may additionally record usage/context.
  Preserve the table's broader existing compatibility for case-linked
  `filled_form` rows rather than tightening the baseline owner check in a way
  that strands that workflow. Enforce unique
  `(org_id, document_family_id, version_number)` and one successor per
  superseded row. Replacement inserts a new row/object; it never updates or
  deletes the prior version. “Current” is derived as the family row with no
  successor, so history remains immutable.

- **TE-2 — Create one private, repository-managed Storage bucket with an
  organization-bound path contract.** Use a non-public bucket and paths such
  as
  `org/{orgId}/{provider|group}/{ownerId}/{familyId}/{version}/{safeFileName}`.
  `storage.objects` policies must validate the first path segment against the
  caller's organization membership. Writes remain limited to
  `admin`/`specialist`; reads follow the product's existing organization-role
  permissions rather than inventing a new role rule in Storage. Object keys
  are generated by the service, never accepted verbatim from the browser. No
  permanent public URL is stored or returned.

- **TE-3 — Signed upload/finalize and signed download are server-owned
  security boundaries.** Add narrow Nitro endpoints that use the shared
  authenticated organization guard to (a) issue a short-lived signed upload
  target for an allowed owner/kind/path, (b) finalize the immutable metadata
  row after object presence is verified, and (c) issue a short-lived signed
  download URL for an authorized current or historical version. Every query
  includes `org_id` and owner checks because the injected service-role client
  bypasses RLS. Responses use `Cache-Control: no-store`; audit rows record
  actor, document ID, owner, kind, and action, never file contents or reusable
  URLs.

- **TE-4 — Make upload/finalize failure recoverable and non-orphaning.** A
  finalize operation must verify object path, size, MIME type, owner, and
  expected family/version before inserting metadata. Failed/expired upload
  intents and objects without metadata are cleaned by a bounded maintenance
  job; metadata is not written for a missing object. The implementation should
  use an idempotency token or unique path/version constraint so retries cannot
  create duplicate current versions. Supported MIME types and size limits are
  centralized in the service and mirrored in UI validation.

- **TE-5 — Document kinds are typed and expiration requirements are
  centralized.** Extend the existing kind vocabulary additively (including
  `cms_460`) and keep one shared TypeScript metadata map for labels and whether
  expiration is required. State License, DEA, and COI require
  `expiration_date`; non-expiring kinds may omit it. Widen the database check
  and add a consistency constraint matching that rule. Historical values stay
  valid; components do not hard-code parallel kind arrays.

- **TE-6 — Advisory expiration/readiness remains derived.** A pure projection
  classifies current versions as `expired`, `expiring_soon`, or `current`,
  sorts by expiration, and joins only the document kinds already consumed by
  readiness/SOP requirements. Reviewer defaults are 90 days for State License,
  60 days for DEA, and 30 days for COI or any other expiration-tracked kind;
  keep the thresholds in the shared kind metadata map so a later PM change is
  one pure configuration edit, not a schema migration. Extend
  `enrollmentReadiness.ts` rather than storing readiness or warning flags. A
  document replacement or expiration-date correction occurs as a new version,
  then invalidates document, case, provider/group, and readiness query keys.

- **TE-7 — SOP-required verification uses stable document kinds.** Task/SOP
  requirements must reference the shared machine kind, not free-form display
  labels or filenames. Case detail derives present/missing/expired from the
  current provider/group document versions plus the task's required-kind list.
  This is a live advisory check; it does not copy document state onto the case
  or task. E1.7b version stamping continues to determine which SOP requirement
  set applies to an in-flight case.

- **TE-8 — Browser code follows Component → hook → service → API/Supabase.**
  Add `src/services/documents.ts`, organization-scoped hooks/keys in
  `src/hooks/`, and feature components under `src/components/documents/`.
  Components never call Storage or Supabase directly. Metadata list reads may
  use the standard `externalClient` service path under RLS; signed upload and
  download actions call the narrow server endpoints through the service.
  Successful mutations invalidate document-family/list, owner, case,
  readiness, and audit prefixes.

- **TE-9 — Tighten the dormant table's privileges before activation.** The
  baseline currently grants broad table privileges and exposes a delete
  policy. The activation migration must remove ordinary update/delete access,
  keep inserts writer-only, preserve organization-scoped selects, add version
  consistency constraints and indexes, and issue explicit least-privilege
  grants for both metadata and Storage policies. Add indexes for
  current-family resolution, provider/group lists, expiration ordering, case
  context, and organization ownership. Regenerate Supabase types and update
  the table register in the implementation PR.

- **TE-10 — UI uses dense tables and explicit upload forms.** Provider and
  group tabs reuse `Table`, `Badge`, `Dialog`, `Input`, `Select`, `Label`,
  `Button`, and `Tooltip`, with custom cells for kind, dates, status, version,
  and actions. Use one-pixel borders, approved tokens, compact rows/padding, no
  card shadows/gradients/decorative backgrounds, and no base64 previews.
  Download/upload icon controls require accessible labels and tooltips.
  Protected layout and primitive files are not changed.

- **TE-11 — The extension receives audited links, not object credentials.**
  E4.3 may list document metadata and request the same short-lived download
  endpoint after case/owner authorization. It must not receive bucket service
  credentials, permanent URLs, or direct object-list access. R6 supports
  manual download/drag-and-drop only; future auto-attach can reuse the stable
  document ID and authorized download contract without changing storage grain.

- **TE-12 — Test metadata, object, and authorization failure modes.** Unit and
  service tests cover current-version derivation, no version forks, required
  expirations, every 30/60/90-day boundary, SOP requirement matching,
  MIME/size/path validation, idempotent finalize, audit failure, and
  organization/role isolation. Storage-policy tests verify cross-org object
  denial. Playwright scenarios TS-88–TS-90 cover provider/group uploads,
  replacement history, expiration sorting/advisory warnings, case
  verification, and short-lived downloads with mocked Storage/API responses;
  CI uses generated non-PHI PDF fixtures.
