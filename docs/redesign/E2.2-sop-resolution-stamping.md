# E2.2 — SOP Resolution & Version Stamping at Generation

## Purpose and Context

When E2.1 creates a case, its task list comes from an SOP — and from now on,
from a **specific immutable version** of one (Model A, `[e1.7a]`). This epic
wires generation to E1.7b's version machinery: resolve the best-matching SOP
for the case's payer × state (× group/specialty per the existing
`pickTemplate` order), interpolate it through the resolver as today, and
stamp `(sop_template_id, sop_version)` on every created task alongside the
existing `sop_content` snapshot.

Per the `[r4]` Q4 decision, cases whose payer × state has **no authored SOP
get the generic fallback SOP** (E1.7b F1.7b.4) — never an empty task list,
never a "needs SOP" holding queue.

## Personas Empowered

- **P2 Credentialing Specialist** — every generated case arrives with an
  actionable task list; "which procedure version am I following" is visible.
- **P1 Credentialing Manager** — can audit what any case was generated from.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: the E1.7a task-stamp contract —
  `tasks.sop_template_id` + `tasks.sop_version` (nullable, both-or-neither
  CHECK, composite FK to the immutable version row) land in E1.7b's
  migration; this epic populates them via an additive extension of
  `create_case_with_tasks` (and the manual-case path). Legacy tasks stay
  NULL/NULL — no historical backfill.
- Implementation dependency: SOP selection stays in `pickTemplate` (exact
  payer+state+group → payer+state → fallback); the fallback branch is the
  only new selection behavior and must be pure and unit-tested.
- Implementation dependency: resolution reads the **head** content (Model A:
  head jsonb = current version) and stamps `current_version` — selection and
  stamping must happen in the same transaction to avoid racing a publish.

## Features

### F2.2.1 — Version-stamped task generation

- **Description:** Every task created by generation (or manual case
  creation) carries `(sop_template_id, sop_version)` plus the resolved
  `sop_content` snapshot exactly as today.
- **Persona:** P2.
- **Acceptance criteria:**
  - Tasks from a payer-matched SOP stamp that template + its current
    version; a publish between two batches yields different stamps (older
    batch keeps its version — Model A in action).
  - The case surface shows "generated from <SOP name> v<N>" linking to the
    read-only version view (E1.7b F1.7b.2).
  - Legacy tasks (NULL stamp) render unchanged.
- **Test/data scenario(s):** TS-53.

```gherkin
Feature: In-flight cases keep their version
  Scenario: SOP edited mid-quarter
    Given April's batch stamped tasks with (humana-ks, v1)
    And the Humana KS SOP was published to v2 in June
    When July's batch generates a Humana KS case
    Then July's tasks stamp (humana-ks, v2)
    And April's tasks still reference v1 and their content is unchanged
```

### F2.2.2 — Generic fallback resolution

- **Description:** When no SOP matches the case's payer × state, resolve the
  global generic fallback SOP (E1.7b) and stamp its template/version. The
  case is visibly marked "generic SOP" so authored coverage gaps are
  discoverable.
- **Persona:** P2, P1.
- **Benefit hypothesis:** Q4 — 15 of 40 cases without a written SOP still
  start moving on the standard enrollment checklist instead of sitting empty.
- **Acceptance criteria:**
  - No generated case ever has zero tasks.
  - Fallback-stamped cases are filterable ("using generic SOP") — the
    working list for which payer SOPs to author next.
  - Authoring a payer SOP later affects only future generations; existing
    fallback cases keep their stamped fallback version (no retro-swap).
- **Test/data scenario(s):** TS-54.

### F2.2.3 — Reapply restamps at current versions

- **Description:** E2.1's reapply action regenerates the case's new task set
  from the **current** best-match SOP and version (a payer SOP authored since
  the original generation now wins over the fallback).
- **Persona:** P2.
- **Acceptance criteria:**
  - Reapply tasks stamp the current selection/version; the original cycle's
    completed tasks and stamps are untouched.
- **Test/data scenario(s):** TS-54.

### TE-1 — Stamp transport: per-task keys inside `p_tasks`; no RPC signature change

The E1.7a §4 contract is stamped **on tasks**, so the stamps should ride
inside each `p_tasks` element (`v_task->>'sop_template_id'`,
`(v_task->>'sop_version')::int`), NOT as new function parameters.
`create_case_with_tasks(p_input jsonb, p_tasks jsonb)` (baseline line 510)
already iterates `jsonb_array_elements(p_tasks)`; adding two `NULLIF(...)`
reads to the task INSERT is the entire RPC change, keeps the function
signature identical (adding a defaulted parameter would create a second
overload next to the existing `(jsonb, jsonb)` signature and its explicit
GRANT/REVOKE rows at baseline 1220–1221), and is NULL-safe for every caller
that does not pass stamps — legacy callers keep producing NULL/NULL tasks,
valid under the E1.7b both-or-neither CHECK. Ship it as a new
`CREATE OR REPLACE` migration (repo + hosted), never an edit to the baseline
file. Per the epic's Dependencies, this RPC extension rides E2.1's PR train
(E2.1 extends the same function for `group_id` — note `credential_cases.group_id`
and its FK already exist in the baseline, lines 58/859, and the RPC already
inserts it; E2.1's migration is the widened uniqueness, not the column).

Trust honesty: the RPC is **not** `SECURITY DEFINER` — it runs as the caller
and its inserts pass the caller's own-org RLS. A buggy/malicious browser could
stamp a cross-org `sop_template_id`; the composite FK guarantees the pair
exists but does not org-check it. This is **not a new surface** — the same
caller already authors the entire `sop_content` payload — and the stamped id
stays unreadable (the `sop_template_versions` SELECT policy scopes through
the parent's visibility), so provenance renders as "version unavailable",
never leaking content. No isolation-gate work: this is a browser-RLS path,
not `/api`; the org-isolation gate is unaffected.

### TE-2 — Version-consistency contract (supersedes the body's "same transaction" wording)

The constraint line "selection and stamping must happen in the same
transaction to avoid racing a publish" is not implementable in this
architecture and points toward the one design that is actually wrong.
Selection (`pickTemplate`) and resolution (`resolveTemplate`) run in the
browser; the stamp is written by the RPC — they cannot share a database
transaction without moving resolution server-side, which nobody has scoped.
Worse, the "stamps `current_version`" phrasing invites the RPC to re-read
`current_version` at insert time: if a publish lands between the client's
head read and the RPC call, the task would stamp v(N+1) while its
`sop_content` was resolved from vN — a stamped-version/actual-content
mismatch, the exact corruption E1.7a exists to prevent.

The correct, sufficient contract: **stamp the version you resolved.**

1. Read `(task_definitions, current_version)` from the head row in ONE
   statement (single-statement snapshot ⇒ the pair is internally consistent;
   `listTemplates` already returns whole rows, so this falls out for free
   once E1.7b adds `current_version`).
2. Resolve tokens from that `task_definitions`.
3. Pass that same `(id, current_version)` pair to the RPC as the stamp.

A publish racing generation is then harmless and semantically correct: the
batch stamps the version whose content it actually resolved (Model A — the
older batch keeps its version, F2.2.1's own AC), and the composite FK to the
immutable `sop_template_versions` row guarantees the stamped pair exists no
matter how the race lands. No transaction spanning selection and stamping is
needed, and none should be built.

### TE-3 — BLOCKER dependency: the generic fallback SOP is invisible under current RLS

F2.2.2 cannot be built against the policy that exists today. The live
`sop_templates_select` policy (`20260707060000`, lines 85–96) admits global
rows only when `org_id IS NULL AND payer_id IS NOT NULL AND EXISTS (SELECT 1
FROM org_payer_assignments …)`. E1.7b F1.7b.4's fallback SOP is global
**and payer-less** ("no payer match key") — it fails the `payer_id IS NOT
NULL` conjunct for every org user, so `listTemplates` (whose
`.or(org_id.eq.<org>,org_id.is.null)` client filter would otherwise pass it,
`src/services/templates.ts` line 45) never receives it and the fallback
branch resolves nothing. Neither E1.7b nor this epic names the gap.

Required enabler, owned by **E1.7b's migration** (it ships the fallback row;
this epic must not start until it lands): an additive RLS widening admitting
the payer-less global fallback (e.g. extend the disjunct with `(org_id IS
NULL AND payer_id IS NULL)`, or key it to an explicit fallback marker — see
PM Q1), plus matching coverage in `scripts/verify-catalog-rls.sql` asserting
(a) the fallback is visible to an org user, (b) org users still cannot
forge/modify global rows, and (c) non-fallback global SOPs remain invisible
to unassigned orgs. Writes stay platform-only (service role) — the existing
own-org-only write policies already enforce that.

### TE-4 — Selection truth: `pickTemplate` matches payer+state+group only — no specialty

The body's "(× group/specialty per the existing `pickTemplate` order)"
overstates the existing behavior. `src/lib/pickTemplate.ts` takes
`(templates, payerId, state, groupId)` — **specialty is not an input**;
`sop_templates.specialty` (baseline line 384) is a stored match key nothing
selects on today. The true order: exact `payer + state + group` (a null-group
template counts as exact; array order decides among exact candidates), then
any `payer + state`, else null. This epic adds exactly one new branch: when
both miss, resolve the generic fallback (TE-3's row) and return it with its
template identity, so the caller stamps `(fallback_id, current_version)` like
any other selection. Keep the function pure and extend the existing
`src/lib/pickTemplate.test.ts` (fallback selected only on double miss;
payer-matched SOP beats fallback; archived fallback → null; no-fallback-row →
null — the "never zero tasks" AC then depends on the seeded fallback
existing, which is E1.7b's F1.7b.4 acceptance). Do not add specialty matching
here — that would be silent scope expansion; if the business wants the
specialty key honored, that is a PM decision (not raised as a question since
no epic asks for it).

### TE-5 — Protected-file honesty: no `sopResolver.ts` edit is required, and none is authorized

The Dependencies line labels "`src/lib/sopResolver.ts` / `pickTemplate`" as
protected. Only `sopResolver.ts` is on the AGENTS.md protected list;
`pickTemplate.ts` is an ordinary (pure, tested, load-bearing) module. More
importantly, **stamping needs no resolver change at all** — E1.7a Model A's
"zero resolver impact" holds: `resolveTemplate`'s callers hold the selected
`SOPTemplate` in hand, so the stamp pair is threaded at the call site into
the RPC task payload, and `ResolvedTaskInsert` stays as-is. This epic
therefore carries **no** `sopResolver.ts` authorization (the step-shape
carry-through is E1.7b's separately-authorized edit — E1.7a §3 "scope
honesty"). The one sanctioned protected-file touch is the **additive**
`src/types/index.ts` widening of `Task` with `sopTemplateId: string | null` /
`sopVersion: number | null` (plus `SOPTemplate.currentVersion` if E1.7b has
not already added it) — authorized here, additive only, alongside the
regenerated `src/integrations/supabase/types.ts` after E1.7b's DDL.

### TE-6 — Creation call-site inventory (what "every task" actually covers)

F2.2.1 says every task created by generation **or manual case creation**
carries the stamp. On `redesign` today, `create_case_with_tasks` has three
live SOP-resolving callers besides the E2.x paths this epic plans for:
`src/components/cases/NewCaseModal.tsx` (via `useCreateCase`,
`src/hooks/useCases.ts` line 63), the launch kickoff
`src/components/launches/CreateCasesDialog.tsx` (via
`src/services/launches.ts` line 170), and the starter-case auto-attach in
`src/routes/providers.new.tsx`. If only E2.1's batch/manual paths stamp,
those three keep writing NULL/NULL tasks and the AC fails as written. All
three already call `pickTemplate` and hold the template, so threading
`(template.id, template.currentVersion)` into their task payloads is a small
mechanical change — recommended, pending PM Q2 on whether those surfaces are
instead being retired before R4 exit. Non-SOP task writers
(`createFollowUpTask` in `src/services/tasks.ts`, the termination-task
builder in `src/services/providers.ts`) legitimately stay NULL/NULL — they
are not generated from a template and the nullable stamp is exactly for them.

### TE-7 — Case-surface provenance and the "using generic SOP" filter

- **"Generated from <SOP name> v<N>"** should read the **version row's**
  `name` (head name at publish time, per the E1.7a §4 sketch), not the live
  head's — a later rename must not rewrite history. Reading
  `sop_template_versions` from the browser rides its parent-scoped SELECT
  policy (E1.7a §3); an unresolvable stamp (cross-org/unreadable) renders a
  neutral "version unavailable", never an error. The case-detail tasks read
  (`getCase`'s tasks embed) must include the two new columns — verify the
  projection rather than assuming `select('*')`.
- **UI needs no new primitive**: the label is a `Link` to E1.7b's read-only
  version view (F1.7b.2 — that route is E1.7b's deliverable and a hard
  dependency of this AC), and the "generic SOP" marker is the existing
  legacy `StatusPill` `neutral` variant. No DESIGN-DEBT.md entry required.
- **The filter** ("using generic SOP") derives from stamps: a case uses the
  fallback iff it has a task stamped with the fallback template's id. The
  cases work view's URL-driven chip pattern (the `/providers?chip=` idiom) is
  the house mechanism; the cases list read must gain a data path for
  "distinct stamped template ids per case" (an embed or a second org-scoped
  read) — decide at build time, but do not widen a list payload with task
  bodies just for this.
