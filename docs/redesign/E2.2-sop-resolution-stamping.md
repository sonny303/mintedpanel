# E2.2 — SOP Resolution & Version Stamping at Generation

## Purpose and Context

When E2.1 creates a case, its task list comes from an SOP — and from now on,
from a **specific immutable version** of one (Model A, `[e1.7a]`). This epic
wires generation to E1.7b's version machinery: resolve the best-matching SOP
for the case's payer × state (× group/specialty per the existing
`pickTemplate` order), interpolate it through the resolver as today, and
stamp `(sop_template_id, sop_version)` on every created task alongside the
existing `sop_content` snapshot.

Per the `[r4]` Q4 decision, cases whose payer × state has **no authored SOP
get the generic fallback SOP** (E1.7b F1.7b.4) — never an empty task list,
never a "needs SOP" holding queue.

## Personas Empowered

- **P2 Credentialing Specialist** — every generated case arrives with an
  actionable task list; "which procedure version am I following" is visible.
- **P1 Credentialing Manager** — can audit what any case was generated from.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: the E1.7a task-stamp contract —
  `tasks.sop_template_id` + `tasks.sop_version` (nullable, both-or-neither
  CHECK, composite FK to the immutable version row) land in E1.7b's
  migration; this epic populates them via an additive extension of
  `create_case_with_tasks` (and the manual-case path). Legacy tasks stay
  NULL/NULL — no historical backfill.
- Implementation dependency: SOP selection stays in `pickTemplate` (exact
  payer+state+group → payer+state → fallback); the fallback branch is the
  only new selection behavior and must be pure and unit-tested.
- Implementation dependency: resolution reads the **head** content (Model A:
  head jsonb = current version) and stamps `current_version` — selection and
  stamping must happen in the same transaction to avoid racing a publish.

## Features

### F2.2.1 — Version-stamped task generation

- **Description:** Every task created by generation (or manual case
  creation) carries `(sop_template_id, sop_version)` plus the resolved
  `sop_content` snapshot exactly as today.
- **Persona:** P2.
- **Acceptance criteria:**
  - Tasks from a payer-matched SOP stamp that template + its current
    version; a publish between two batches yields different stamps (older
    batch keeps its version — Model A in action).
  - The case surface shows "generated from <SOP name> v<N>" linking to the
    read-only version view (E1.7b F1.7b.2).
  - Legacy tasks (NULL stamp) render unchanged.
- **Test/data scenario(s):** TS-53.

```gherkin
Feature: In-flight cases keep their version
  Scenario: SOP edited mid-quarter
    Given April's batch stamped tasks with (humana-ks, v1)
    And the Humana KS SOP was published to v2 in June
    When July's batch generates a Humana KS case
    Then July's tasks stamp (humana-ks, v2)
    And April's tasks still reference v1 and their content is unchanged
```

### F2.2.2 — Generic fallback resolution

- **Description:** When no SOP matches the case's payer × state, resolve the
  global generic fallback SOP (E1.7b) and stamp its template/version. The
  case is visibly marked "generic SOP" so authored coverage gaps are
  discoverable.
- **Persona:** P2, P1.
- **Benefit hypothesis:** Q4 — 15 of 40 cases without a written SOP still
  start moving on the standard enrollment checklist instead of sitting empty.
- **Acceptance criteria:**
  - No generated case ever has zero tasks.
  - Fallback-stamped cases are filterable ("using generic SOP") — the
    working list for which payer SOPs to author next.
  - Authoring a payer SOP later affects only future generations; existing
    fallback cases keep their stamped fallback version (no retro-swap).
- **Test/data scenario(s):** TS-54.

### F2.2.3 — Reapply restamps at current versions

- **Description:** E2.1's reapply action regenerates the case's new task set
  from the **current** best-match SOP and version (a payer SOP authored since
  the original generation now wins over the fallback).
- **Persona:** P2.
- **Acceptance criteria:**
  - Reapply tasks stamp the current selection/version; the original cycle's
    completed tasks and stamps are untouched.
- **Test/data scenario(s):** TS-54.

## Scenario/Seed Data Mapping

- TS-53 — Two batches straddling a publish stamp v1 vs v2.
- TS-54 — Fallback case generated; payer SOP authored later; reapply picks
  the payer SOP.

## Dependencies

- E1.7b (version table, fallback SOP, resolver carry-through) — hard
  prerequisite.
- E2.1 creation path (`create_case_with_tasks` extension rides its PR train).
- Protected `src/lib/sopResolver.ts` / `pickTemplate` — any additive edit
  must be explicitly authorized in §5 (E1.7a §6 TE-2 precedent).

## Out of Scope / Non-Goals

- SOP authoring/versioning UI (E1.7b).
- A "needs SOP" queue (rejected in Q4).
- Retroactive restamping of legacy or in-flight tasks.
