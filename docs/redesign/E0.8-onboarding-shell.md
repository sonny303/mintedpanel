# E0.8 — Standalone Onboarding Shell & Stage 0 Hardening Close-out

## Purpose and Context

E0.7 (PR #77) hardened the public surfaces (uniform responses, GRANT lockdown,
types regen, regression e2e). E0.8 ships the PM-directed onboarding-shell
rework that was specified alongside it, plus the two hardening items E0.7
deferred behind BD-1/BD-2 (now resolved): the in-Postgres rate limiter and the
scoped public-route accessibility pass.

The onboarding-shell rework: selecting **Add organization** from the org
switcher opens a new standalone authenticated onboarding page (not a modal).
That page becomes the single home for the org-intake form, the share-link
action, and the begin-onboarding workflow launcher. Account Detail becomes a
read-only summary of the intake outputs; People Enroll becomes the home for
roles, additional contacts, and the sales rep. It is the shell for future
CSV / facilities / providers ingestion, but E0.8 only wires the kickoff
experience and the current minimal data capture. No schema restructuring;
additive migrations only, per AGENTS.md.

## Personas Empowered

- P1 Credentialing Manager (Sowmya Seed) — one durable place to start and run
  organization onboarding, plus a safer public-link surface.
- P5 Practice Owner / P6 Office Manager — receive a branded, accessible
  onboarding form instead of a dry utility page.
- Internal onboarding operators — no longer jump between Account Detail and
  modals to start intake.

## Component & Data Constraints

- Must be built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and [README.md](./README.md).
- The Add organization entry point now routes to a new authenticated
  onboarding page; the Account Detail-hosted capture-link panel and
  begin-onboarding banner are removed from that page.
- Example/demo/test data must use scenario orgs and personas from
  [seed-universe.md](./seed-universe.md).
- All migrations are additive (AGENTS.md); no renames, no policy weakening.
- No new dependencies. Public-route rate limiting must be implementable inside
  Postgres (BD-1 decision, CLARIFICATIONS_NEEDED.md).

## Features

### F0.8.1 — Standalone onboarding page launched from Add organization

- **Description:** Selecting Add organization from the org switcher opens a new
  authenticated standalone onboarding page instead of a modal. The page uses a
  split layout: the left side is the org-intake form; the right side is a
  **persistent side panel** (always visible, not a drawer/tab) holding the two
  independent journeys (F0.8.3).
- **Persona:** P1 Credentialing Manager / internal onboarding operator.
- **Benefit hypothesis:** Keeps org creation and onboarding in one durable
  place, so later CSV/facilities/providers steps can layer in without moving
  the entry point again.
- **Acceptance criteria:**
  - The org switcher's Add organization item routes to the new onboarding page.
  - The current create-org form renders on that page (left side).
  - The right-side panel is persistent on the page with both journey actions.
  - Saving the intake form navigates to the new org's Account Detail.
  - The page is authenticated; the old modal path is no longer the entry point.
- **Test/data scenario(s):** TS-17.

```gherkin
Feature: Add organization opens the standalone onboarding page
  Scenario: Operator starts onboarding from the org switcher
    Given P1 Credentialing Manager is signed in with Rose City Rehab Collective active
    When she opens the org switcher and selects Add organization
    Then she lands on the standalone onboarding page
    And the org intake form renders on the left
    And the persistent side panel shows Share onboarding link and Begin onboarding
```

### F0.8.2 — Minimal viable org intake terminology cleanup

- **Description:** The onboarding page's left panel captures the minimal
  organization intake set with business-facing labels: organization name,
  authorized name/email (was "owner"), organization contact name/email/phone
  (was "customer escalation contact"), and org street address (moved out from
  under the contact grouping). The org intake form no longer includes the
  sales rep field.
- **Persona:** P1 Credentialing Manager / intake operator.
- **Benefit hypothesis:** Keeps the first-pass org record aligned to the person
  who can actually authorize the organization and the contact who can be
  reached, while moving sales-rep assignment to the people/roles surface.
- **Acceptance criteria:**
  - Form labels use authorized / organization-contact terminology; no
    owner / customer-escalation phrasing remains on the form.
  - The org street address is presented as the organization's address, not
    nested under a contact.
  - The submission persists the same core data through the existing
    create-org flow (labels change; the party model does not).
  - Sales rep is absent from the org intake form (Zeb default still applied
    server-side per E0.2; managed in People Enroll per F0.8.5).
- **Test/data scenario(s):** TS-17.

### F0.8.3 — Onboarding actions move off Account Detail into the side panel

- **Description:** The capture-link panel and the begin-onboarding launcher are
  relocated from Account Detail (`/get-started`) to the onboarding page's
  persistent right-side panel, as two actions:
  1. **Share onboarding link** (primary) — opens a popup where the operator
     enters recipient name (required) and recipient email (required) and
     shares the capture link. The "Send to / Someone else..." party dropdown
     is removed entirely — the flow always targets exactly one typed-in
     recipient.
  2. **Begin onboarding** (secondary) — opens a separate onboarding wizard
     page (F0.8.4).
- **Persona:** P1 Credentialing Manager / onboarding operator.
- **Benefit hypothesis:** Prevents Account Detail from being the only place to
  start onboarding work and keeps the operator on the same page as the intake
  form and link-sharing actions.
- **Acceptance criteria:**
  - The capture-link panel is no longer rendered on Account Detail.
  - The begin-onboarding banner/launcher is no longer rendered on Account
    Detail.
  - The side panel exposes `Share onboarding link` and `Begin onboarding`.
  - The share popup requires recipient name AND email; no party dropdown.
  - The primary popup CTA is labeled `Share onboarding link`.
- **Test/data scenario(s):** TS-17.

```gherkin
Feature: Share onboarding link targets exactly one typed-in recipient
  Scenario: Operator shares the onboarding link from the side panel
    Given P1 is on the onboarding page for Rose City Rehab Collective
    When she clicks Share onboarding link and submits without a recipient name
    Then the popup blocks submission with a required-field error
    When she enters a recipient name and email and clicks Share onboarding link
    Then a capture link is issued to that single recipient
    And no Send to / Someone else dropdown is present
```

### F0.8.4 — Onboarding wizard page (org-intake section live; rest placeholders)

- **Description:** `Begin onboarding` opens a separate wizard page: a single
  page with sections. E0.8 ships only the org-intake section live; CSV
  ingest, facilities import, and providers import render as clearly labeled
  placeholder sections for future increments.
- **Persona:** P1 Credentialing Manager / onboarding operator.
- **Benefit hypothesis:** Establishes the durable wizard shell now so future
  CSV/facility/provider ingestion lands without another IA change.
- **Acceptance criteria:**
  - A separate authenticated wizard route exists, reached from the side panel.
  - The page is a single page with sections (not a multi-step flow).
  - The org-intake section is functional; facilities / providers / CSV
    sections are placeholders using the shared not-yet-available pattern.
- **Test/data scenario(s):** TS-17.

### F0.8.5 — People Enroll becomes the home for roles and additional contacts

- **Description:** The existing people enrollment surface (PartiesManager) is
  the home for the authorized person, organization contact, sales rep, and
  later role-based assignments. Each row holds one role at a time and remains
  editable/removable.
- **Persona:** P1 Credentialing Manager / onboarding operator.
- **Benefit hypothesis:** Separates the organization shell from the people
  records that actually need role management.
- **Acceptance criteria:**
  - Each person row is one role at a time; the operator can edit or remove
    each row (existing guards, e.g. only-sales-rep block, still hold).
  - The sales rep role is managed here rather than on the org intake form.
  - Authorized person and organization-contact records created during org
    intake appear here for follow-on edits.
- **Test/data scenario(s):** TS-17 / TS-18.

### F0.8.6 — Account Detail mirrors the org-intake outputs (read-only)

- **Description:** Account Detail shows the outputs captured on the onboarding
  page — organization name, authorized person, organization contact, and
  address — as the read-only summary for the org, while the actual intake and
  link-workflow actions live on the onboarding page / People Enroll.
- **Persona:** P1 Credentialing Manager / onboarding operator.
- **Benefit hypothesis:** Preserves a familiar place to review the resulting
  org data without re-opening the intake flow.
- **Acceptance criteria:**
  - Account Detail renders the org-intake outputs as read-only data matching
    the submission exactly.
  - Account Detail does not reintroduce the capture-link or begin-onboarding
    surfaces.
  - Editing happens from the onboarding page / People Enroll surfaces.
- **Test/data scenario(s):** TS-17 / TS-19.

### F0.8.7 — Branding follows the new onboarding workflow

- **Description:** The Minted Panel logo moves to the top of the menu bar as a

- **Persona:** P1 Credentialing Manager / external recipient.

- **Acceptance criteria:**

- **Test/data scenario(s):** TS-17 / TS-19 / TS-20.

### F0.8.8 — In-Postgres rate limiting on the public anon RPCs (BD-1 close-out)

- **Description:** The four `anon` RPCs (`validate_capture_token`,
  `submit_capture`, `submit_inbound_lead`, `validate_report_share`) gain
  DB-side attempt throttling per the resolved BD-1: a small
  `public_rpc_attempts` table keyed by a coarse source fingerprint (RPC name +
  hashed caller hint), lazily pruned, conservative thresholds, uniform
  invalid/expired response once over threshold (no oracle).
- **Persona:** P1 (protected); anonymous abuser (defeated).
- **Benefit hypothesis:** A 64-hex-char token is unguessable in theory, but
  unmetered validation endpoints invite scripted probing and lead spam;
  throttling closes the practical attack while keeping legitimate one-click
  usage untouched.
- **Acceptance criteria:**
  - Additive migration only; `CREATE OR REPLACE` folds the check into the
    existing RPC bodies; no new deps or middleware.
  - A throttled caller receives the SAME generic invalid/expired response as
    a wrong token; invalid/revoked/expired/throttled are indistinguishable.
  - `submit_inbound_lead` enforces a per-source submission cap in addition to
    the honeypot.
  - Legitimate flows (TS-7, TS-13, TS-14, TS-15) still pass unchanged; no raw
    token is written to any log, table, or error message.
- **Test/data scenario(s):** TS-16 (abuse probe), TS-7/TS-13/TS-14/TS-15.

```gherkin
Feature: Public token endpoints resist enumeration
  Scenario: Scripted probing of capture tokens is throttled without an oracle
    Given an anonymous client has submitted 20 invalid tokens to validate_capture_token
    When it submits a 21st token, valid or not
    Then the response is the same generic invalid/expired result
    And a legitimate Lone Star Rehab Group link still validates once the window passes
```

### F0.8.9 — Scoped accessibility pass on public routes (BD-2 close-out)

- **Description:** Labels, focus order, keyboard submit, and error
  announcement are correct on `/capture/:token`, `/contact`, and
  `/share/:token`, per the resolved BD-2.
- **Persona:** P5/P6 recipients and inbound strangers.
- **Benefit hypothesis:** These are the only pages outsiders ever see; a form
  a keyboard or screen-reader user cannot complete costs disproportionate
  trust and lost intake.
- **Acceptance criteria:**
  - Every form control on the three routes has an associated label.
  - Focus order follows the visual order; submit works via keyboard.
  - Validation/submission errors are announced (aria-live or equivalent
    pattern already in the component library).
- **Test/data scenario(s):** TS-13, TS-14, TS-15.
