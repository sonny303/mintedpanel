# E6.2 — Groups & the Payer Network Board

## Purpose and Context

The data model is already group-grain everywhere — payers attach at
group × payer × state (`payer_network_targets`), facilities belong to one
group, cases are provider × group × payer × state — but the UI has no group
surface: attachment hides in a wizard section and fulfillment has no home at
all. Per decision record decision 3 and the four Payer Network screen mocks,
this epic gives the group the surface: a **Groups** menu item whose hub
carries group facts, the facilities list (same treatment as the provider
roster), and the **Payer Network fulfillment board** — the org's
promise-vs-reality screen, alive from day one with zero providers. It also
introduces **enrollment facts** as the migration-capture model (facts, never
auto-cases) that the board and E6.3's candidate math consume.

## Personas Empowered

- P1 Credentialing Manager — reads the contract's target state and its
  fulfillment on one board, from day 1 to done.
- P2 Credentialing Coordinator / Specialist — drills a payer row to see each
  provider's case status without leaving the board.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md); Shelby Sports Rehab (two states)
  exercises the facilities grouping; Outer Banks Rehab Group exercises the
  board.
- Implementation dependencies (flagged): (a) an additive **enrollment
  facts** store at provider × payer × state grain (payer, state, effective
  date, source=migration, expired_at) — new table, org-scoped RLS, additive
  migration + table-register row; (b) the board's derivations consume E6.0's
  status rollup functions; (c) facility → group link exists (no change);
  one-group-per-facility is a documented rule, not new schema.

## Features

### F6.2.1 — The Groups menu item and hub

- **Description:** Sidebar item **Groups** (org zone). Multi-group orgs see
  the A→Z group list; single-group orgs auto-land on their only group. The
  group hub carries three areas: group facts (legal name, TIN shown
  XX-XXXXXXX, operating states), Facilities, and Payer Network. A simple
  route-derived breadcrumb (`Groups › {Group} › {Area}`) renders on nested
  pages.
- **User story:** As P1, the entity my contracts, facilities, and payers
  actually hang off has its own front door.
- **Persona:** P1, P2.
- **Benefit hypothesis:** UI grain finally matches data grain; multi-group
  orgs get honest per-group boards instead of a conflated org rollup.
- **Acceptance criteria:**
  - Single-group orgs land directly on the group hub (zero extra clicks);
    multi-group orgs get an A→Z list.
  - Group facts are editable inline (admin), audited.
  - Breadcrumb renders and every crumb navigates.
- **Test/data scenario(s):** TS-108.

### F6.2.2 — Facilities: the same list treatment

- **Description:** The group's facilities render search-on-top,
  **state-grouped, A→Z within state**, with filters (state, has-providers)
  and per-row provider counts; a zero-provider facility carries an
  informational flag (it cannot generate cases). Facility CRUD lives here;
  each facility belongs to exactly ONE group — a shared street address
  across two groups is entered once per group (payers see per-TIN service
  locations), and the facility CSV template documents this rule. Facility
  CSV import lives on this page. Cross-group counts ("facilities with no
  providers", "locations per group") are Reporting Center reports (E6.6),
  not screen widgets.
- **User story:** As P1, a 40-location group is five collapsible state
  headers with search, not one endless unsorted page.
- **Persona:** P1.
- **Benefit hypothesis:** Fixes the long-unsorted-list accessibility
  problem the PM flagged on the live app.
- **Acceptance criteria:**
  - State groups with counts, A→Z within; search and filters compose;
    default collapse on orgs with many locations.
  - Go-live date is a plain date field on the facility (feeds the Launches
    report and quiet queue ranking; NO location status machine).
  - The zero-provider flag renders from the existing assignments data; no
    new queries beyond the page's own reads.
- **Test/data scenario(s):** TS-108.

### F6.2.3 — The Payer Network fulfillment board

- **Description:** Per payer target on the group, ONE row: derived status
  pill (`Targeted` = target exists, no case, no fact · `In Progress` = ≥1
  case not yet Approved, with open-case count · `Active` = ≥1 Approved case
  OR enrollment fact), provider drill-down (expand a payer row → each
  provider's case status or enrollment fact, including denial history with
  reason and reapply cycles), an excluded-row rendering (reason + Restore),
  and the **"candidates awaiting generation"** banner that explains WHERE
  candidates came from ("Dr. Chen joined Sept 3") and carries the Review &
  generate action (E6.3). The board exists from day 1 with zero providers,
  honestly explaining a zero buffer. Nobody can set any value on this board
  — it is entirely derived.
- **User story:** As P1, "we promised 7 payers — where are we?" is one
  screen, correct the moment any underlying status changes.
- **Persona:** P1, P2.
- **Benefit hypothesis:** The contract's target state finally has a home
  the team steers by, replacing spreadsheet tracking; the two named gaps
  from the alignment (day-1 fulfillment tracking, derived payer-active) are
  closed by one surface.
- **Acceptance criteria:**
  - All three statuses derive per E6.0 F6.0.5; setting a case Approved (or
    recording/expiring an enrollment fact) updates the row without any
    board-side write.
  - Drill-down shows per-provider case status, enrollment facts, prior
    denial (reason + date) beneath a reapply cycle.
  - The buffer banner count always equals candidates (E6.3 math) and names
    the most recent cause; zero states explain why.
  - Excluded targets stay visible on their rows with reason + one-click
    Restore; the board always accounts for every target ("7 of 7").
- **Test/data scenario(s):** TS-109.

### F6.2.4 — Eligibility-filtered attach (+ CSV)

- **Description:** Attach payers TO THE GROUP: the picker queries the
  catalog and presents the **eligible list** — payers whose covered states
  intersect the group's operating states — with an ineligible-payers
  explainer. One user-reviewed confirm creates the group × payer × state
  targets; the org-level enablement (`org_payer_assignments`) is created
  implicitly and never managed by the user. CSV alternative: one row per
  group × payer with `;`-delimited states, same eligibility validation at
  scan time. Removing a payer archives targets (never deletes), preserving
  the existing archive/restore semantics.
- **User story:** As P1, attaching the contract's seven payers is picking
  seven rows from a pre-filtered list, not hunting a 270-payer catalog.
- **Persona:** P1.
- **Benefit hypothesis:** Pushes the eligibility intelligence (today only
  at the scope step) up to the selection step; kills the two-layer
  subscribe-then-scope ceremony.
- **Acceptance criteria:**
  - The picker never offers a payer with zero state overlap; the states
    proposed per payer = payer states ∩ group operating states, user-
    reviewed before save.
  - Org-level enablement rows are created/archived implicitly and
    correctly; no UI exposes them.
  - CSV path: exact-header gate, one row per group × payer, eligibility
    errors named per row; commit is idempotent (skip-on-match).
- **Test/data scenario(s):** TS-110.

### F6.2.5 — Enrollment facts (the migration model)

- **Description:** The additive enrollment-facts store at provider × payer
  × state: payer, state, effective date, source (migration), and
  `expired_at`. A fact means "already enrolled with this payer UNDER THIS
  GROUP'S CONTRACT." Facts suppress generation candidates (E6.3), count a
  payer toward Active (F6.2.3), and **never create cases**. Expiring a fact
  re-opens the combination as a candidate in the buffer. Capture UI ships
  in E6.4 (provider record + onboarding); this epic ships the model and the
  board/candidate consumption.
- **Persona:** P1.
- **Benefit hypothesis:** Migrating an established practice records history
  as facts with zero queue noise — the PM's "auto-cases are noise" call.
- **Acceptance criteria:**
  - Facts are org/group-scoped, additive, auditable; expiry is a flip,
    never a delete.
  - A fact flips its payer row toward Active and suppresses the candidate;
    expiring reverses both, immediately.
- **Test/data scenario(s):** TS-109, TS-113.

```gherkin
Feature: The fulfillment board tells the contract's story
  Scenario: Day-1 targets, day-50 hire, derived Active
    Given Outer Banks Rehab Group has 7 payer targets and zero providers
    Then the board shows 7 Targeted rows and a zero buffer explaining "no providers yet"
    When a provider joins the group with enrollment facts for 2 of the payers
    Then those 2 rows read Active with zero cases and the banner reads "5 candidates awaiting generation"
    When one generated case is later set Approved
    Then that payer's row flips Active in the same render with no board-side write
```

## Dependencies

- E6.0 status derivations (build after E6.0).
- Additive migration: enrollment-facts table (+ RLS, grants, table-register
  row, types regen). No change to `payer_network_targets` or the facility →
  group link.
- The attach CSV rides the existing staged-import engine (section
  descriptor pattern); no second import pipeline.
- E6.3 consumes the buffer math; E6.4 ships fact-capture UI.

## Out of Scope / Non-Goals

- No org-level cross-group rollup view (future reporting if ever needed).
- No M:N facility↔group join — one group per facility is the rule.
- No board-side writes of any status, ever.
- Generation itself (grid, confirm) is E6.3.
