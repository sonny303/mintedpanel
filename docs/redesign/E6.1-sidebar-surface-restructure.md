# E6.1 — Sidebar & Surface Restructure: Six Items, Zero Backstage

## Purpose and Context

The app serves ~40 routed surfaces from a sidebar that reaches eight, with
six admin surfaces fully orphaned and three daily-work surfaces fallen out of
nav. Per the decision record (decision 2), this epic replaces the navigation
wholesale with six journey starting points — Cases · Payer Setup · Reporting
Center | Org Detail · Groups · Providers — retires sixteen surfaces with a
named new home for every job, makes Cases the login landing, and slims Org
Detail to the container page (matching the live screenshots reviewed
2026-07-19). It is presentation + routing only where possible; where a
retirement depends on a sibling epic (e.g. the Groups hub), this epic ships
the shell and redirects and the sibling fills it.

## Personas Empowered

- P1 Credentialing Manager — every surface reachable from six entries; no
  memorized URLs.
- P2 Credentialing Coordinator / Specialist — lands directly on the work
  queue at login.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md). This epic explicitly authorizes edits to
  `src/components/layout/*` (Sidebar, page shell) — the protected-files rule
  is lifted for exactly those files, per the shell-change precedent.
- Icons: lucide-react. Org Detail keeps the existing contact-card icon.
  Groups uses `user-cog` as the stock default; the PM's preferred
  three-people-under-gear mark may ship as a small custom SVG asset (one-word
  decision at build time — both acceptable).
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md).
- No legacy URL may dead-end: every retired route becomes a redirect
  (the `/portfolio` precedent), with a redirect table in the PR body and
  pinned in `legacy-routes.spec.ts`.

## Features

### F6.1.1 — The six-item sidebar

- **Description:** Workspace zone (cross-org): Cases, Payer Setup, Reporting
  Center. Org zone (below the org switcher tile): Org Detail, Groups,
  Providers. User footer unchanged. NO admin section exists — MSO Routing,
  Statuses, Data Import, and Settings are retired per their owning epics;
  Audit Log moves to Reporting Center (E6.6). Payer Setup renders for ALL
  roles for now (two trusted users; revisit at the third hire).
- **User story:** As P1, I can reach every workflow from a sidebar I can
  hold in my head.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Six starting points that mirror the four journeys
  beat eighteen mixed entries plus orphans; "where do I go" stops being a
  memory task.
- **Acceptance criteria:**
  - Exactly six primary items render, in the stated zones and order, with
    the stated icons; count chips: Cases (open cases), Payer Setup
    (needs-attention drift count, from E6.5's derivation).
  - No Admin section renders for any role.
  - Sidebar behavior at narrow widths follows the existing shell rules; no
    horizontal scroll (e2e viewport check).
  - **Branding is untouched:** the existing white layered-jack logo mark +
    "Minted Panel" wordmark at the top of the rail stay exactly as shipped
    (`src/assets/logo-white.png`). The gradient-square mark in the decision
    mocks is a placeholder, not a proposal — pinned by the existing
    sidebar logo e2e assertion.
- **Test/data scenario(s):** TS-106.

### F6.1.2 — Cases is the landing

- **Description:** Home is removed. The login/root landing resolver keeps
  its org-selection logic (last active org, else newest live org) but
  resolves to the Cases surface instead of a Home page. The legacy `/home`
  action-queue page retires; its queues are superseded by the Cases queue
  (its "Launches at risk" slice returns as a Reporting Center report in
  E6.6).
- **User story:** As P2, logging in puts me on the work, not on a lobby.
- **Persona:** P1, P2.
- **Benefit hypothesis:** The first screen of every session is the one
  users act on; the lobby page added a click and split attention across
  parallel queues.
- **Acceptance criteria:**
  - Post-login and `/` (client-nav) land on Cases in the resolved org.
  - `/home` redirects to Cases; no `/home`-only queue silently disappears
    without its named successor (report or Cases pivot) existing or being
    tracked in E6.6.
- **Test/data scenario(s):** TS-106.

### F6.1.3 — One Cases surface with three pivots

- **Description:** "My Cases" (`/work`) and "Cases" (`/cases`) merge into
  ONE surface named **Cases**: the ranked to-do queue is the default pivot,
  with by-provider and by-payer pivots re-slicing the same cases (URL-driven
  so pivots are shareable). MVP is org-wide — no per-analyst assignment
  fields. Ranking: overdue follow-ups → task due dates → provider start
  dates → the rest (facility go-live remains a quiet lower-priority signal).
- **User story:** As P2, one surface answers "what next," "how is this
  provider doing," and "how is this payer doing" without changing rooms.
- **Persona:** P2, P1.
- **Benefit hypothesis:** Two adjacent case surfaces were one surface with
  a filter; merging removes the "which one am I supposed to use" question.
- **Acceptance criteria:**
  - One route serves all three pivots; pivot state is in the URL.
  - The legacy `/work` and `/cases` URLs both land on the merged surface
    (one is the canonical route, the other redirects).
  - Existing case-detail deep links continue to resolve unchanged.
- **Test/data scenario(s):** TS-106.

### F6.1.4 — Org Detail, slimmed to the container

- **Description:** Org Detail (renamed from Account Detail) carries exactly:
  org summary, authorized/organization contacts, People Enroll, member
  management (relocated from the retired Settings page), capture-link
  re-issue, and a "Finish setup" banner while the one-time wizard is
  incomplete. The Organization-data and Payer-Network content moves to the
  Groups item (E6.2).
- **Persona:** P1.
- **Benefit hypothesis:** The container page stops carrying working-entity
  freight; matches the live screenshots the PM validated.
- **Acceptance criteria:**
  - Org Detail renders only the listed content; `/get-started` redirects.
  - Member management (invite, role change) works from Org Detail.
- **Test/data scenario(s):** TS-107.

### F6.1.5 — The wizard is a one-time flow

- **Description:** The onboarding wizard loses its nav entry; it is entered
  from the org switcher's Add organization and re-entered via the Finish
  setup banner until complete. Ongoing edits live where the data lives
  (Groups, Providers, Org Detail). The wizard's provider step IS the
  Providers surface (E6.4); its facility/group steps are the Groups
  surfaces (E6.2) shown in flow order.
- **Persona:** P1.
- **Benefit hypothesis:** "Onboarding" stops being a permanent menu label
  for a temporary activity; year-two edits stop routing through a wizard.
- **Acceptance criteria:**
  - No Onboarding nav entry; `/onboarding` and `/onboarding/wizard` stay
    URL-reachable (Add-organization flow + banner).
  - Post-create still lands in the wizard flow; completing it drops the
    banner.
- **Test/data scenario(s):** TS-107.

### F6.1.6 — Retirements and the redirect table

- **Description:** Every retired route redirects to its job's new home:
  `/home` → Cases · `/work` or `/cases` → the merged Cases route ·
  `/fix-it` → Payer Setup needs-attention (E6.5) · `/client-progress` →
  Reporting Center (deprecated surface; nearest report) · `/launches*` →
  Reporting Center Launches report (E6.6) · `/admin/import` → Providers
  (imports live with data) · `/admin/statuses` → Reporting/redirect stub
  (page retired, E6.0) · `/admin/mso-routing` → Payer Setup Catalog (E6.5)
  · `/admin/settings` → Org Detail · `/admin/payer-admin*`,
  `/admin/portals`, `/portals/$key/train`, `/admin/templates*`,
  `/admin/sops*`, `/admin/payers*`, `/payer-directory` → Payer Setup tabs
  (E6.5) · `/generation*` → the group's Payer Network (E6.2/E6.3) ·
  `/scope` → wizard · `/outcomes`, `/soon`, `/progress` → nearest
  successor. Named param-preservation set asserted in e2e: `?section=`,
  `?payerId`/`state`/`groupId`, `?draftId`.
- **Persona:** All.
- **Benefit hypothesis:** Zero dead ends; bookmarks and shared links
  survive the restructure.
- **Acceptance criteria:**
  - The full old→new table ships in the PR body AND is pinned in
    `legacy-routes.spec.ts`; every redirect preserves the named params.
  - No route file is deleted; each becomes a redirect stub with a dated
    comment (the `portfolio.tsx` precedent).
  - Existing e2e specs pass with entry-URL updates only — no assertion
    weakening; retired-surface specs are retargeted to the new homes.
- **Test/data scenario(s):** TS-106.

## Dependencies

- E6.0 statuses render in the Cases pivots (build after E6.0).
- E6.2 (Groups hub), E6.5 (Payer Setup module), E6.6 (reports) provide the
  redirect targets — this epic may land their redirect stubs pointing at
  interim homes if sequenced first, but the slate order builds E6.0 → E6.1
  with targets landing immediately after.
- Landing resolver (`src/lib/landing.ts` + `useLandingRedirect`) retargets;
  org-selection logic unchanged.

## Out of Scope / Non-Goals

- No breadcrumb framework epic — nested pages (Groups, records) carry a
  simple route-derived trail as part of their own epics.
- No per-analyst assignment; no role changes beyond "Payer Setup visible to
  all."
- No new queries for count chips — existing cached derivations only.
