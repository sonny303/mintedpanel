# E0.4 — First-Run and Next-Action Landing (Workspace Onboard)

## Purpose and Context

Ensures every Credentialing Manager (P1) always lands in a rich, appropriate workspace context: onboarding, post-create, and after state transitions. Seed-universe organizations and consulting team (Oregon group) always visible/testable. Deletion is not allowed—orgs "suppressed" by state only. This closes the onboarding funnel and eliminates confusing dead-ends or blank states.

## Personas Empowered

- P1 Credentialing Manager (Sowmya)

## Component & Data Constraints

- All UI leverages the Stage 0 build requirements ([uiux-component-guide.md](./uiux-component-guide.md)), E0.0 workspace, Portfolio navigation, seed-universe orgs/contacts
- "No org delete" (all orgs must persist, state-driven suppression only)
- Last active org stored deterministically (user/session/server as feasible)
- Demo/test consulting user always has Rose City Rehab Collective (Oregon) seeded and visible

---

## Features

### F0.4.1 — Land user in last active org workspace

- **Description:** On session start or navigation, the Credentialing Manager is always routed to their last active org workspace, never a generic portfolio or home page (unless all orgs are inactive or it is a new-user scenario).
- **Persona:** P1
- **Benefit:** Reduces navigation friction for P1, eliminates "uninitialized" UI in real-world workflows.
- **Acceptance Criteria:**
  - Always route to last-active org (unless all inactive or new user)
  - Session stores/recalls last active org
  - Playwright can test against seeded orgs (TS-4, TS-0)
- **Scenario mapping:** TS-4 (multi-org portfolio), TS-0 (first run, Oregon team demo)
- **Gherkin:**

```gherkin
Feature: Workspace always lands on last active org
  Scenario: User logs in with multiple seeded orgs (Rose City, Dillon, Point Place)
    Given I am P1
    And my last active org is "Rose City Rehab Collective"
    When I access Minted Panel
    Then I am placed directly in the "Rose City Rehab Collective" workspace

```

### F0.4.2 — Portfolio fallback and guidance when all orgs inactive

- **Description:** If all orgs have lifecycle state "inactive," present the Portfolio, clearly label all orgs as inactive, and offer a CTA to create a new organization.
- **Persona:** P1
- **Benefit:** Provides an actionable surface at every state; never leaves the user in a dead-end.
- **Acceptance Criteria:**
  - Inactive portfolio never blank; all orgs visible/flagged
  - "Create New Organization" CTA always available
  - Oregon consulting group must always be present in seed/demo
- **Scenario mapping:** TS-12 (all inactive), consulting/demo user, seed-universe sanity test
- **Gherkin:**

```gherkin
Feature: Portfolio provides guidance when all orgs inactive
  Scenario: User has only inactive orgs (Rose City, Point Place)
    Given I am P1 and have only inactive orgs
    When I access the workspace
    Then I see all orgs flagged as inactive
    And I see a "Create New Organization" call to action

```

### F0.4.3 — First-run and just-created onboarding banner/CTA

- **Description:** For new users or after onboarding a first org, always show a clear onboarding CTA/next-action banner. Never blanks.
- **Persona:** P1
- **Benefit:** Ensures new customers have frictionless onboarding and always "know what to do next." Drives funnel conversion.
- **Acceptance Criteria:**
  - First-run workspace is always present for new users
  - After org creation, the user lands in that org with explicit next-action guidance—suggest Stage 1 onboarding/scope if implemented
  - CTA/banner never blank; seed demo always shows Oregon consulting if the consulting role is tested
- **Gherkin:**

```gherkin
Feature: First-run/created onboarding CTA
  Scenario: User creates their first org as consulting (Oregon)
    Given P1 has no orgs
    When I create "Rose City Rehab Collective"
    Then I land in the Rose City workspace with an onboarding CTA/banner
    And the banner offers "Begin Onboarding" (even if link is not yet available)

```

## 5. Technical Considerations & Enablers — Devin section

This section is owned by Devin.

### Open-implementation-question resolutions (Devin, 2026-07-09)

- **F0.4.1 vs E0.0's landing default.** E0.0 established that authenticated redirects land on the Portfolio (`/portfolio`). E0.4 explicitly supersedes that default: the landing resolver (TE-1) routes to the last-active org workspace, with Portfolio as the fallback surface (all-inactive, no valid last-active) — Portfolio itself is unchanged and stays one click away in the nav. Reviewer-resolved in E0.4's favor (later epic, explicit intent).
- **"Clearly label all orgs as inactive" vs E0.0's locked "no lifecycle status label" decision.** Genuine conflict with a locked decision — logged in `CLARIFICATIONS_NEEDED.md` with a default assumed: in the all-inactive fallback state ONLY, inactive orgs render under an **"Inactive" group heading** (the same grouping mechanism as the existing "Prospects"/"In motion" sections, which is already user-visible lifecycle grouping) — no per-org status pill/label anywhere, preserving the E0.0 rule everywhere else.
- **"Consulting user / consulting role / Oregon group."** No consulting persona or role exists in the personas list, the party role reference table (E0.3), or the schema. Interpreted as: the demo user (Sowmya Seed) always has Rose City Rehab Collective (OR) in the baseline seed — already true (TS-5 baseline). No new role or persona is introduced (TD-3).
- **"Last active org stored … user/session/server as feasible."** Feasible today: the existing persisted Zustand store (`src/lib/auth-store.ts`, `activeOrgId`, localStorage key `minted-panel-active-org`) already survives sessions on a device. Stage 0 uses it as-is; server-side sync is deferred (TD-1).
- **Epic's TS-0 usage.** Seed-universe TS-0 is the zero-org cold start; this epic's F0.4.3 scenario (create Rose City as the first org) is TS-0 followed by the L1 UI-created step — compatible, no fixture change needed.

### Technical enablers (Devin populates)

- **TE-1 — Landing resolver.** One deterministic routing function applied at authenticated entry (root redirect in `__root.tsx` / router beforeLoad): (1) zero memberships → first-run screen (E0.0 TE-7, `NoOrgScreen`); (2) persisted `activeOrgId` valid (still a membership) and its org not `inactive` → that org's workspace home (`/get-started`, the Stage 0 org landing per E0.1 TE-4); (3) all orgs `inactive` → Portfolio fallback state (TE-3); (4) otherwise (no/stale last-active) → most recently created non-inactive org's workspace, falling back to Portfolio. Pure function, unit-tested; consumes the E0.0 portfolio data source (`listPortfolioOrgs`) so lifecycle comes from one place.
- **TE-2 — Last-active tracking.** Reuse the existing persisted store; extend the boot-time validation (which today falls back to the first membership) to be lifecycle-aware per TE-1. `setActiveOrg` already updates it on every switch — no new storage. No schema change.
- **TE-3 — Portfolio all-inactive fallback.** Extend pure `splitPortfolio` (`src/lib/portfolio.ts`) to also return the inactive bucket; `PortfolioContent` renders an "Inactive" group **only when** prospects + in-motion are both empty and inactive > 0 (otherwise inactive stays excluded, exactly as E0.0 shipped). The state includes the "Create New Organization" CTA reusing the E0.1 create flow (`CreateOrganizationModal`). Existing primitives only.
- **TE-4 — Onboarding banner/CTA.** A next-action banner composed from existing primitives (`card` + `button`) at the top of `/get-started`, shown for a just-created or empty org: copy states the next step and offers "Begin Onboarding" rendered via the shared `NotYetAvailable` disabled-CTA pattern until Stage 1 exists (the epic explicitly authorizes "even if link is not yet available"). No new route, no new primitive.
- **TE-5 — Seed/test extension (TS-12).** TS-12 = all-orgs-inactive is an **L2 scenario-mutation state** (Playwright helper flips every seeded org's `lifecycle_state` to `inactive`), not a baseline fixture — added to seed-universe's Stage 0 scenario mapping (reviewer-added). Rose City (OR) is already in the L0 baseline; no new fixture rows.

### Tech-debt findings (Devin populates)

- **TD-1 — Last-active is device-local.** localStorage persistence means a different device/browser lands via TE-1 rule (4), not the true last-active. Server-side preference storage is deferred until a real need (out-of-scope "pinning" UI is the likely vehicle).
- **TD-2 — "Org workspace" home is `/get-started`.** Until a real org overview/dashboard exists (explicitly out of scope here), landing "in the org workspace" means the Get started route with the E0.2 contacts section and TE-4 banner. Revisit when the dashboard epic arrives.
- **TD-3 — "Consulting" language is undefined.** No consulting persona/role exists anywhere in the model; this epic's references are treated as the demo user + Rose City fixture. If a real consulting concept is coming, it needs its own epic (and likely an E0.3 reserved role).
- **TD-4 — The all-inactive fallback is a dark path.** It is reachable only via the TS-12 mutation state; needs explicit Playwright coverage or it will silently rot (same class of risk as E0.3 TD-3).
