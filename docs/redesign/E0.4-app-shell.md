# E0.4 — First-Run and Next-Action Landing (Workspace Onboard)

## Purpose and Context

Guarantees every Credentialing Manager (P1) always lands in a context-rich workspace (E0.0) upon sign-in or navigation, either in their last active org or the Portfolio (if all orgs inactive/no org present). Promotes onboarding flow, eliminates dead-ends and blank states, and always surfaces seed-universe organizations—especially Oregon consulting. Implements business logic locked by E0.0–E0.3 and references canonical seed-universe and UI/component constraints docs.

## Personas Empowered

- P1 Credentialing Manager (Sowmya)

## Component & Data Constraints

- Built from shadcn/ui and Stage 0 build constraints (see [uiux-component-guide.md](./uiux-component-guide.md)).
- Demo/test uses only organizations and persons that exist in [seed-universe.md](./seed-universe.md), e.g., Rose City Rehab Collective (Oregon).
- No org delete — lifecycle state suppression only (per locked decisions from E0.0/E0.1).
- All scenario references must have valid TS/fixture in `seed-universe.md` or must be answered as open question.

## Features

### F0.4.1 — Last-Active Org Landing

- **Description:** When P1 logs in or navigates to the workspace, they are always routed to the last active org workspace (not Portfolio or home unless all orgs are inactive or no org exists for new user).
- **Persona:** P1
- **Benefit Hypothesis:** Reduces friction for daily users, preserves workflow context, closes navigation gaps.
- **Acceptance Criteria:**
  - User lands in last-active org workspace upon sign-in or navigation
  - If all orgs inactive: see F0.4.2
  - Last-active tracking must be deterministic across session/device if possible
- **Test/data Scenario(s):**
  - TS-4: User has multiple orgs, last used is Oregon; lands in Oregon workspace
- **Gherkin**

```gherkin
Feature: Land user in last active org workspace
  Scenario: Sowmya returns to the app with Oregon last active
    Given I am P1 (Sowmya) and my last active org is "Rose City Rehab Collective"
    When I access Minted Panel
    Then I am routed directly to the "Rose City Rehab Collective" workspace

```

### F0.4.2 — Portfolio Fallback and CTA if All Orgs Inactive

- **Description:** When all orgs are inactive, land user in Portfolio showing all (flagged as inactive), with "Create New Organization" CTA.
- **Persona:** P1
- **Benefit Hypothesis:** User never hits dead-end or blank state, always offered actionable onboarding step.
- **Acceptance Criteria:**
  - If every org for P1 is inactive, Portfolio shows full inactive list + "Create New Organization" CTA
  - "No organizations" is only shown for new user, never after usage
- **Test/data Scenario(s):**
  - TS-12: All orgs inactive for Sowmya (Rose City, etc.)
- **Gherkin**

```gherkin
Feature: Portfolio fallback when all orgs inactive
  Scenario: All seeded orgs are inactive
    Given I am P1 and all my orgs are inactive
    When I access the workspace
    Then I see the Portfolio, each org flagged as inactive
    And a "Create New Organization" call-to-action is present

```

### F0.4.3 — First-run/Onboard CTA (New User and Org Created)

- **Description:** For new users or after onboarding first org, show onboarding CTA/banner in workspace with next-action (Stage 1 prep if not available).
- **Persona:** P1
- **Benefit Hypothesis:** Ensures frictionless onboarding, closes gap between creation and next steps, avoids "what now?" confusion.
- **Acceptance Criteria:**
  - Brand new, no-org user sees onboarding CTA in Portfolio
  - Org newly created: workspace lands with onboarding banner (suggest Stage 1 onboarding/scope, even if not clickable)
- **Test/data Scenario(s):**
  - TS-0: P1 signs up, creates their first org ("Rose City Rehab Collective")
- **Gherkin**

```gherkin
Feature: First-run/created onboarding CTA
  Scenario: Sowmya creates first org (Oregon)
    Given P1 has no orgs
    When I create "Rose City Rehab Collective"
    Then I land in the Oregon workspace with an onboarding CTA/banner present

```

## 5. Technical Considerations & Enablers — Devin section

This section is owned by Devin.

### Open-implementation-question resolutions (Devin, 2026-07-09)

- **F0.4.1 vs E0.0's landing default.** E0.0 established that authenticated redirects land on the Portfolio (`/portfolio`). E0.4 explicitly supersedes that default: the landing resolver (TE-1) routes to the last-active org workspace, with Portfolio as the fallback surface (all-inactive, no valid last-active) — Portfolio itself is unchanged and stays one click away in the nav. Reviewer-resolved in E0.4's favor (later epic, explicit intent).
- **"Flagged as inactive" vs E0.0's locked "no lifecycle status label" decision.** Genuine conflict with a locked decision — logged in `CLARIFICATIONS_NEEDED.md` with a default assumed: in the all-inactive fallback state ONLY, inactive orgs render under an **"Inactive" group heading** (the same grouping mechanism as the existing "Prospects"/"In motion" sections, which is already user-visible lifecycle grouping) — no per-org status pill/label anywhere, preserving the E0.0 rule everywhere else.
- **First-run surface (v2 F0.4.3).** v2 says the brand-new no-org user "sees onboarding CTA in Portfolio". E0.0 ships the zero-org first-run as the restyled `NoOrgScreen` (its create-org CTA IS the onboarding CTA). Interpreted as: the first-run screen remains the zero-org surface and satisfies this AC; no separate Portfolio empty state is introduced for zero-org users (F0.4.2's fallback covers the all-inactive case, which is distinct from zero orgs).
- **"Oregon consulting."** No consulting persona or role exists in the personas list, the party role reference table (E0.3), or the schema. Interpreted as: the demo user (Sowmya Seed) always has Rose City Rehab Collective (OR) in the baseline seed — already true (TS-5 baseline). No new role or persona is introduced (TD-3).
- **"Deterministic across session/device if possible."** Feasible today: the existing persisted Zustand store (`src/lib/auth-store.ts`, `activeOrgId`, localStorage key `minted-panel-active-org`) survives sessions on a device. Stage 0 uses it as-is; cross-device sync is NOT feasible without server-side preference storage — deferred (TD-1), which the epic's "if possible" allows.
- **Epic's TS-0 usage.** Seed-universe TS-0 is the zero-org cold start; this epic's F0.4.3 scenario (create Rose City as the first org) is TS-0 followed by the L1 UI-created step — compatible, no fixture change needed.

### Technical enablers (Devin populates)

- **TE-1 — Landing resolver.** One deterministic routing function applied at authenticated entry (root redirect in `__root.tsx` / router beforeLoad): (1) zero memberships → first-run screen (E0.0 TE-7, `NoOrgScreen`); (2) persisted `activeOrgId` valid (still a membership) and its org not `inactive` → that org's workspace home (`/get-started`, the Stage 0 org landing per E0.1 TE-4); (3) all orgs `inactive` → Portfolio fallback state (TE-3); (4) otherwise (no/stale last-active) → most recently created non-inactive org's workspace, falling back to Portfolio. Pure function, unit-tested; consumes the E0.0 portfolio data source (`listPortfolioOrgs`) so lifecycle comes from one place.
- **TE-2 — Last-active tracking.** Reuse the existing persisted store; extend the boot-time validation (which today falls back to the first membership) to be lifecycle-aware per TE-1. `setActiveOrg` already updates it on every switch — no new storage. No schema change.
- **TE-3 — Portfolio all-inactive fallback.** Extend pure `splitPortfolio` (`src/lib/portfolio.ts`) to also return the inactive bucket; `PortfolioContent` renders an "Inactive" group **only when** prospects + in-motion are both empty and inactive > 0 (otherwise inactive stays excluded, exactly as E0.0 shipped). The state includes the "Create New Organization" CTA reusing the E0.1 create flow (`CreateOrganizationModal`). Existing primitives only.
- **TE-4 — Onboarding banner/CTA.** A next-action banner composed from existing primitives (`card` + `button`) at the top of `/get-started`, shown for a just-created or empty org: copy states the next step and offers "Begin Onboarding" rendered via the shared `NotYetAvailable` disabled-CTA pattern until Stage 1 exists (the epic explicitly allows "even if not clickable"). No new route, no new primitive.
- **TE-5 — Seed/test extension (TS-12).** TS-12 = all-orgs-inactive is an **L2 scenario-mutation state** (Playwright helper flips every seeded org's `lifecycle_state` to `inactive`), not a baseline fixture — added to seed-universe's Stage 0 scenario mapping (reviewer-added). Rose City (OR) is already in the L0 baseline; no new fixture rows.

### Tech-debt findings (Devin populates)

- **TD-1 — Last-active is device-local.** localStorage persistence means a different device/browser lands via TE-1 rule (4), not the true last-active. Server-side preference storage is deferred until a real need (out-of-scope "pinning" UI is the likely vehicle).
- **TD-2 — "Org workspace" home is `/get-started`.** Until a real org overview/dashboard exists (explicitly out of scope here), landing "in the org workspace" means the Get started route with the E0.2 contacts section and TE-4 banner. Revisit when the dashboard epic arrives.
- **TD-3 — "Consulting" language is undefined.** No consulting persona/role exists anywhere in the model; this epic's references are treated as the demo user + Rose City fixture. If a real consulting concept is coming, it needs its own epic (and likely an E0.3 reserved role).
- **TD-4 — The all-inactive fallback is a dark path.** It is reachable only via the TS-12 mutation state; needs explicit Playwright coverage or it will silently rot (same class of risk as E0.3 TD-3).
