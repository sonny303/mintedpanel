# E4.0 — Payer Pipeline: External State Machine, Tracking IDs & Structured Resolution

## Purpose and Context

`[r6]` decision A3 locks the core model: **internal operations are decoupled
from the payer's pipeline**. Internal task states ("Missing DEA", "Ready for
QA") stay in the SOP/task tracker (E1.7b/E2.2); the payer's side of a case is
a distinct, immutable state machine — **Not Started → Assigned → Drafting →
Submitted → In Review → Action Required (RFI) → Closed (Approved / Denied)**
(PM-updated vocabulary 2026-07-14) — because mixing internal
gathering tasks with external payer statuses breaks reporting (R8).

This epic gives every credentialing case that payer pipeline, captures the
payer's **Reference/Tracking ID** at submission (A1 — needed for follow-up
when credentialing is delayed), and makes resolution **structured**: approval
records effective dates + payer-issued provider IDs (provider becomes
In-Network / Credentialed with effective date); a case may also close
Out-of-Network or Denied, and every denial/return carries a **structured
reason code** (A4 — Missing Documentation, Network Closed, Demographic
Mismatch, …) so R8 can report on systemic issues instead of parsing notes.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — moves cases through the
  payer pipeline, records tracking IDs, logs RFIs, and closes cases with
  structured outcomes.
- **P1 Credentialing Manager** — reads pipeline state at a glance across the
  caseload; relies on structured outcomes for reporting.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only (AGENTS.md): the payer pipeline state, tracking ID,
  resolution fields, and denial reason codes are new additive columns/tables
  beside the existing `credential_cases` status machinery — nothing is
  renamed or restructured. The reviewer records the exact mechanism in §5.
- Pipeline transitions are append-only history (the existing
  `status_history`/touch spine pattern) — the pipeline is immutable in the
  sense that history is never rewritten; the current state only moves along
  the defined edges.

## Features

### F4.0.1 — Payer pipeline state machine on every case

- **Description:** Every credentialing case carries a payer-pipeline state:
  `Not Started → Assigned → Drafting → Submitted → In Review → Action
Required (RFI) → Closed (Approved / Denied)`. Generated cases start at
  Not Started; assignment to a specialist moves them to Assigned (the case
  keeps its assignee separately — this state marks the pickup). Transitions
  follow the defined edges only (e.g. In Review ↔ Action Required for RFI
  back-and-forth; Closed outcomes Approved/Denied/OON are terminal,
  subject to the existing reapply rule `[r4-review]` Q6). The pipeline state
  is displayed distinctly from internal task progress everywhere a case
  appears (case detail, case list, queue).
- **Persona:** P2, P1.
- **Benefit hypothesis:** internal-vs-external decoupling (A3) keeps
  reporting clean and lets a specialist see "where the payer is" without
  digging through tasks.
- **Acceptance criteria:**
  - The seven-state pipeline (Not Started → Assigned → Drafting →
    Submitted → In Review → Action Required → Closed, with terminal
    outcomes Approved/Denied/OON) exists on every case; invalid
    transitions are rejected.
  - Every transition writes an append-only history row (who, when,
    from → to).
  - **Failure path:** a rejected transition shows an inline error naming
    the current state and the allowed next states; NO history row and NO
    partial write occurs; the case remains unchanged and workable.
  - **Access control:** P1 and P2 perform normal forward transitions,
    including terminal outcomes (Approved/Denied — any P1 or P2, not
    assignee-restricted; PM confirmed 2026-07-14); **correction
    transitions and any post-terminal change are P1 (admin) only** (see
    Edge Cases). Billing role is read-only on the pipeline. Terminal
    cases (Approved/Denied/OON) are read-only except the admin
    correction path and the existing reapply rule.
  - **Attribution:** wherever the pipeline state renders on case detail,
    it shows "last updated by <name> · <relative time>" from the latest
    history row — no digging for who moved it.
  - **Visible audit trail (non-negotiable):** the case detail has a
    read-only "Payer pipeline history" timeline — every transition,
    correction (flagged, with justification), and tracking-ID/resolution
    edit, each attributed (who/when/from → to). Visible to all org roles
    on the case, not backend-only — visible to P1/P2/billing alike (PM
    confirmed 2026-07-14).
  - **Concurrency:** transitions are guarded against conflicting edits —
    if two users act on the same case, the second save is rejected with a
    "case was updated by <name> — refresh to continue" message; no silent
    overwrite, no duplicate history rows.
  - Case detail and case list render pipeline state separately from
    internal task/checklist progress — the two are never merged into one
    label.
  - Existing internal case statuses (`status_configs`) are untouched.
- **User journey:**
  - P2 opens the case → sees internal task progress and the payer
    pipeline pill side-by-side in the header, with last-updated
    attribution.
  - P2 clicks the pipeline pill → a transition menu offers only the legal
    next states; illegal moves are disabled with a tooltip naming why.
  - Confirming a transition shows a success toast; a rejected one shows
    an inline error with the allowed next states — never a dead end.
  - Anyone on the case opens "Payer pipeline history" to read the full
    attributed timeline, corrections included.
- **Test/data scenario(s):** TS-69.

```gherkin
Feature: Payer pipeline state machine
  Scenario: RFI round trip
    Given a case in payer-pipeline state "In Review"
    When P2 records an RFI from the payer
    Then the pipeline state becomes "Action Required (RFI)"
    And responding moves it back to "In Review"
    And both transitions appear in the case's pipeline history
```

### F4.0.2 — Reference/Tracking ID capture at submission

- **Description:** Moving a case to `Submitted` prompts for the payer
  portal's Reference/Tracking ID (optional at submit — some channels issue
  it later; it can be added/edited while the case is open and pre-terminal).
  The ID is displayed prominently on the case header and is searchable.
- **Persona:** P2.
- **Benefit hypothesis:** when credentialing is delayed, the specialist has
  the payer's own reference at hand for follow-up calls/portal checks (A1)
  instead of re-deriving it from emails.
- **Acceptance criteria:**
  - Submission transition offers a tracking-ID field; the value is stored
    on the case and rendered on the case header.
  - **UI placement:** case header (primary, copyable), a case-list column
    (hidden by default, toggleable via existing column prefs), and the
    case search matches on it. No new component primitives.
  - **Late entry / correction workflow:** an inline audited edit on the
    case header (pencil → input → save) available while the case is open
    and pre-terminal; every change writes an `audit_log` row carrying the
    prior and new value. Post-terminal edits are P1-only.
  - **Duplicate handling:** the same tracking ID on another case in the
    same org + payer triggers a non-blocking warning naming the other
    case (payers reuse/typo IDs; resubmissions legitimately share
    references) — save proceeds if confirmed.
  - Case search/filter finds a case by tracking ID (main case search, not
    an advanced-only option).
- **User journey:**
  - P2 moves the case to Submitted → the transition modal offers the
    tracking-ID field (skippable) → the ID lands on the case header,
    copyable.
  - The ID arrives late by mail → P2 clicks the pencil on the header,
    pastes it, saves — the edit is confirmed with a toast and logged in
    the visible history.
  - P1 needs a case from a payer call → types the reference into case
    search and lands on it.
- **Test/data scenario(s):** TS-70.

### F4.0.3 — Structured resolution: effective dates, provider IDs, outcome

- **Description:** Closing the pipeline as `Approved` requires the
  **effective date** and captures the payer-issued **enrollment
  identifier(s)**. Two distinct fields (ChatPRD round-3, 2026-07-14 —
  billing-integrity): the **Individual Provider ID** (tied to the
  provider's Type 1 NPI) and the **Group/Billing Provider ID** (tied to
  the group's Tax ID / Type 2 NPI) — one or both populated depending on
  the contract type; a single generic ID field would cause downstream
  claim denials when this data feeds EHR billing rules. Payers name the
  individual identifier differently (Aetna's welcome letter issues a
  "Provider PIN", BCBS a "Provider ID"), so that field's **label and
  whether one is expected are configured per payer** in the E4.2 admin
  module, with a generic "Payer-issued ID" default; the
  provider's enrollment for that payer × state becomes In-Network /
  Credentialed with that effective date (feeding readiness E1.8 and
  reporting R8). A case may alternatively close **Out-of-Network** (working
  relationship ends without joining the network) or **Denied**.
- **Persona:** P2, P1.
- **Benefit hypothesis:** resolution data (dates + IDs) is where the
  business value of the whole case lands; structured capture makes it
  reportable and reusable (claims, rosters, directories).
- **Acceptance criteria:**
  - Approved requires an effective date; the payer-issued identifiers are
    offered on the same step as **two distinct fields** — Individual
    Provider ID (rendered with the payer's configured label, e.g.
    "Provider PIN" for Aetna, "Provider ID" for BCBS; generic default
    when unconfigured) and Group/Billing Provider ID — either, both, or
    neither may be populated (skippable with confirmation).
  - The two IDs are stored in separate structured columns, never
    concatenated — downstream billing/EHR feeds must be able to
    distinguish Type 1-linked from Type 2-linked identifiers.
  - Payers configured as issuing an identifier prompt for it at approval
    (skippable with confirmation — welcome letters can lag); payers
    configured as not issuing one don't show the field. Optionality is
    per-payer config, never hardcoded.
  - The resolution writes are visible on the case and on the provider's
    payer-enrollment view.
  - OON and Denied are explicit close outcomes, distinct from Approved.
  - **Post-closure correction:** a wrong effective date or provider ID on
    a closed case is fixed by a P1 audited correction (prior value logged
    and visible in the case history) — users never need backend
    intervention.
- **Test/data scenario(s):** TS-71.

```gherkin

    Given a case in payer-pipeline state "In Review"
    When P2 marks it Approved with effective date 2026-08-01, individual provider ID "HUM-449" and group billing ID "GRP-2210"
    Then the case closes Approved
    And the provider's enrollment for that payer/state shows In-Network effective 2026-08-01

  Scenario: Payer-specific identifier label

    When P2 approves an Aetna case
    Then the approval step's identifier field is labeled "Provider PIN"
    And the captured value renders as "Provider PIN" on the enrollment view
```

### F4.0.4 — Structured denial/return reason codes

- **Description:** Every `Denied` close and every payer return/RFI kick-back
  requires a **reason code** from a managed list (initial set: Missing
  Documentation, Network Closed, Demographic Mismatch, Incomplete
  Application, Credentialing Criteria Not Met, Other + required context),
  plus the existing free-text note. The reason list is org-extensible via
  the E4.2 admin module.
- **Persona:** P2 (records), P1 (reports).
- **Benefit hypothesis:** structured reasons enable R8 predictive analytics
  — e.g. a payer consistently rejecting a specific facility's tax ID (A4) —
  which a status + paragraph note forfeits.
- **Acceptance criteria:**
  - Denied cannot be saved without a reason code; "Other" requires the
    single-line context.
  - Reason codes are stored structured (not concatenated into the note).
  - **RFI reason code is optional and binary:** if provided it is stored
    on the RFI history row; if absent the transition proceeds silently
    with a null reason — no warning, no block. (Denied is the only
    transition where the reason code is required.)
  - **RFI→task bridge (ChatPRD round-3, 2026-07-14):** confirming a
    transition to Action Required (RFI) immediately prompts the user to
    spawn an internal task on the case (title prefilled from the reason
    code/context, e.g. "Obtain updated COI from provider"; created
    through the existing case-task machinery). Skippable with
    confirmation — but the default path always offers it, so the
    pipeline state (where the case is) never leaves the task list (what
    to do next) empty and the case never silently stalls.
- **Test/data scenario(s):** TS-72.

## Edge Cases & Corrections

- **Mis-entered state / pipeline out of sync with payer reality:** history
  rows are never edited or deleted. A wrong state is fixed by an
  **admin-only (P1) correction transition** — a new history row flagged as
  a correction (who/when/from → to + required single-line justification)
  that moves the case to the true state, including backwards edges that
  normal transitions forbid. The wrong row stays visible in history,
  annotated by the correction.
- **Approval/denial reversal:** there is no "undo." Reversing a terminal
  outcome is exactly the admin correction transition above (e.g. payer
  rescinds an approval): P1 corrects the case to the true state with
  justification; the enrollment effective-date/provider-ID writes from the
  erroneous approval are cleared by the same audited action. P2 cannot
  reverse terminal outcomes.
- **Reopen after Denied:** the existing reapply rule holds unchanged
  (`[r4-review]` Q6: Denied → In Progress on the same case, recorded in
  history) — reapply is a normal P2 action, not a correction.
- **Delayed / lost-mail reality drift:** the system cannot see the payer;
  drift is surfaced operationally — a case sitting in Submitted / In
  Review with an overdue (or absent) follow-up surfaces in My Cases via
  E4.1 F4.1.3. That queue is the R6 observability mechanism; a
  pipeline-vs-touch-recency staleness report is R8 scope, out of scope
  here.
- **Tracking-ID reference change midstream:** handled by the audited
  inline edit (F4.0.2); prior values live in `audit_log`, not overwritten
  history, and surface in the visible case history.
- **Concurrent edits / race conditions:** two coordinators acting on the
  same case cannot silently overwrite each other — the second writer is
  rejected with an actionable "updated by <name> — refresh" prompt and
  re-drives from current state. History never records a transition that
  did not start from the true current state.
- **Stale-state nudge (user-facing sync guard):** a case sitting in
  Submitted / In Review / Action Required with no touch for N days is
  flagged "stale — verify with payer" on the case and surfaces in My
  Cases (via E4.1 overdue/queue machinery), prompting P2 to check the
  portal and reconcile — the system's answer to "the payer already
  approved but nobody updated the pipeline." N = 14 days by default,
  org-configurable in the F4.2.5 queue settings (PM confirmed
  2026-07-14). A full pipeline-vs-reality staleness report remains R8
  scope.
- **User reconciles a discrepancy:** on a portal check P2 finds the payer
  shows Approved while the system shows In Review — P2 logs the Portal
  Check touch and moves the case to Approved with effective date +
  provider ID (normal forward transition; no correction needed). If the
  discrepancy requires a backwards move (mis-entered state), P2 escalates
  to P1 for the justified correction transition.

## Data Model Sketch (illustrative — final shape is §5, reviewer-owned)

```text
credential_cases (additive columns)
  payer_pipeline_state  text  CHECK (not_started|assigned|drafting|submitted|in_review|action_required|approved|denied|oon)
  tracking_id           text  null
  network_effective_date date null   -- set on Approved
  payer_individual_provider_id text null  -- Type 1 NPI-linked payer ID
  payer_group_provider_id      text null  -- Type 2/Tax-ID-linked billing ID

payer_pipeline_history (new, append-only — status_history pattern)
  id, org_id, case_id, from_state, to_state,
  reason_code_id (null), is_correction bool default false,
  justification text (required when is_correction),
  actor (auth.uid()), created_at

denial_reason_codes (new; managed in E4.2)
  id, org_id (null = global default), code, label, active bool
```

Surface: transitions ride the existing browser → Supabase + RLS path
(services layer, `writeAudit` on mutations); the extension reads pipeline
state through the existing case-context endpoint. No new `/api` write
routes in this epic.

## What Good Looks Like (sign-off checklist)

- [ ] Every open case displays internal task progress and payer pipeline
      state side-by-side, always current, never merged into one label.
- [ ] Every transition and edit is attributed (who/when) and readable by
      end users in the case's visible pipeline history — not backend-only.
- [ ] P2 can search, filter, enter, and correct tracking IDs and P1 can
      correct outcomes without backend intervention, with all prior
      values logged.
- [ ] No action can put a case into an invalid or unreachable state;
      illegal moves are disabled up front and rejected server-side.
- [ ] Every state change gives clear, actionable feedback (toast on
      success; inline error naming allowed next states on rejection;
      refresh prompt on conflict) — no silent failures.
- [ ] Every Approved case carries an effective date + provider ID feeding
      readiness; every Denied case carries a structured reason code.
- [ ] Nothing is ever edited in place — corrections are visible,
      justified, admin-authored rows; stale cases are flagged to the user
      rather than rotting silently.

## Out of Scope / Non-Goals

- No change to internal `status_configs` vocabulary or SOP/task states.
- No email/fax ingestion (payer responses still arrive out-of-band; E4.1
  logs them as touches — inbox integration is a later release).
- No automation of pipeline transitions from portal scraping.
- **No "Ready to Submit" pipeline state** (ChatPRD round-3 evaluated,
  2026-07-14): the pipeline records the payer-facing truth; "ready to
  submit" is internal readiness — a case in `Drafting` with all prep
  tasks complete. It is served as a **derived queue/list filter** ("needs
  raw execution") over pipeline state + task completion, not a new enum
  value — keeping the PM-confirmed seven-state vocabulary intact. The
  filter itself ships with the E4.1/E4.2 queue surfaces.
- **No SLA clocks in R6** (ChatPRD round-3 evaluated): pause-on-`In
Review` / RFI-turnaround clocks are R8 reporting scope. The append-only
  `payer_pipeline_history` timestamps already capture every state entry/
  exit, so R8 can compute in-our-control vs in-payer-control durations
  retroactively — nothing further is needed now.
- Contracting cases (`contracts`) are untouched — credentialing only.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the credential-case spine
(`supabase/migrations/20260704210000_baseline_live_schema.sql` —
`credential_cases`, `status_history`, `touches`, `audit_log`; the
`payer_reference_id` column added by `20260707120200_case_payer_reference_id.sql`;
the touchlog widening in `20260707120000_touchlog_entry_types.sql`), the case
service layer (`src/services/cases.ts` — `setPayerReference`,
`appendStatusHistory`, `updateCaseStatus`, `createCase` via the
`create_case_with_tasks` RPC), `src/services/audit.ts`'s `writeAudit`, the role
model (`memberships.role ∈ {specialist, billing, admin}`, `user_role(org_id)`,
the `credential_cases_insert/_update` RLS policies gated to `specialist|admin`),
the extension case-context endpoint (`src/server/extensionRoutes.ts`
`handleCaseContext` → `src/services/caseContext.ts`), the E1.5 attachment grain
(`20260712190000_payer_network_targets.sql`), the reapply rule (`[r4-review]`
Q6), `docs/data-model/table-register.md`, and `uiux-component-guide.md`.
**Headline:** the payer pipeline is a NEW state machine that must not touch the
existing internal `status_configs`/`credentialing_status_id` machine (A3
decoupling). One of the four data-model needs already ships — the tracking ID
is the existing `credential_cases.payer_reference_id` column (+`setPayerReference`
service), so the sketch's proposed `tracking_id` is dropped in favour of it.
The two genuine design decisions are (a) the pipeline history table cannot ride
`status_history` (whose `from/to_status_id` are FKs to `status_configs` and
whose `track` is `credentialing|contracting`), so it is a dedicated append-only
sibling, and (b) the whole transition (state change + history row + optional
enrollment writes + audit) must be atomic to honour the F4.0.1 failure path
("NO history row and NO partial write"), which points at a SECURITY-INVOKER RPC
rather than the multi-statement client sequence `updateCaseStatus` uses today._

- **TE-1 — Payer pipeline state as an additive `credential_cases` column,
  independent of the internal status machine.** Add one nullable-then-defaulted
  column, never touching `credentialing_status_id`/`status_configs`:

  ```
  payer_pipeline_state text NOT NULL DEFAULT 'not_started'
    CHECK (payer_pipeline_state IN
      ('not_started','assigned','drafting','submitted','in_review','action_required','approved','denied','oon'))
  ```

  The label/edge vocabulary lives in a pure `src/lib/payerPipeline.ts`
  (allowed-edges map + `canTransition` + terminal-set, unit-tested) so both the
  UI (disable illegal moves) and the server (reject them authoritatively) share
  one source. The forward spine is Not Started → Assigned → Drafting →
  Submitted → In Review ↔ Action Required (RFI); the three terminal closes are
  **Approved**, **Denied**, and **OON** (PM approved for build 2026-07-14 —
  `[e4.0]` resolved via option 1). Approved is reachable from In Review /
  Action Required; **Denied and OON are non-Approved closes reachable from any
  open pre-terminal state** (Drafting, Submitted, In Review, Action Required),
  edge-symmetric to each other — OON is the "working relationship ends without
  joining the network" close. **Reapply after Denied** (`[r4-review]` Q6) is a
  normal forward transition **Denied → Drafting on the existing case** that
  opens a fresh pipeline cycle: the prior Denied `payer_pipeline_history` row is
  preserved (append-only) and the reopen is a new attributed forward row — not a
  correction (it does not carry `is_correction`). Existing rows default
  to `not_started`; no backfill and no re-map of internal statuses (F4.0.1 AC
  "existing internal case statuses untouched"). Additive migration applied
  repo + hosted per `docs/migration-baseline.md`, regenerate
  `src/integrations/supabase/types.ts`, add the field to the `CredentialCase`
  domain type (`src/types/index.ts`, additive), and update the
  `credential_cases` register row in the same PR (AGENTS.md).

- **TE-2 — New append-only `payer_pipeline_history` table (the sketch's shape,
  reconciled).** `status_history` cannot carry these rows — its
  `from_status_id`/`to_status_id` are FKs to `status_configs` (which does not
  and must not hold the fixed payer enum) and its `track` CHECK is
  `credentialing|contracting`. Add a dedicated append-only table mirroring the
  `status_history` pattern (org-scoped, append-only — no UPDATE/DELETE policy):

  ```
  payer_pipeline_history (
    id, org_id NOT NULL, case_id NOT NULL REFERENCES credential_cases(id),
    from_state text, to_state text NOT NULL,   -- same CHECK domain as TE-1
    reason_code_id uuid NULL REFERENCES denial_reason_codes(id),  -- TE-4
    is_correction boolean NOT NULL DEFAULT false,
    justification text,   -- CHECK (NOT is_correction OR justification IS NOT NULL)
    changed_by uuid, changed_at timestamptz DEFAULT now())
  ```

  RLS: member SELECT own-org; INSERT `specialist|admin` (same predicate as
  `credential_cases_update`); **no** UPDATE/DELETE grant or policy (append-only,
  AGENTS.md). FK-cover index on `case_id` (E0.10 convention). Register row added
  in the same PR. The `is_correction`/`justification` pair carries the Edge-Cases
  admin correction row; the wrong row is never edited, only annotated by the
  correction that follows it.

- **TE-3 — Tracking ID reuses the shipped `payer_reference_id`; do NOT add a new
  column.** `credential_cases.payer_reference_id` (migration
  `20260707120200`) + `cases.ts` `setPayerReference` (already writes an
  `audit_log` UPDATE row with the new value) satisfy F4.0.2's storage, late
  inline edit, and audit-trail requirements as-is. Work is UI + read-side only:
  a copyable header field, a default-hidden toggleable case-list column via the
  existing `user_table_prefs`/`tablePrefs.ts` machinery, and matching it in the
  existing case search/filter. The duplicate-ID warning (F4.0.2) is a derived
  read (same org + payer, different case) surfaced non-blockingly — no stored
  uniqueness constraint (payers legitimately reuse/typo references;
  resubmissions share them). `setPayerReference` currently records only the new
  value; extend its `writeAudit` call to include the prior value so the
  "prior and new value" AC holds (additive, one service edit). Post-terminal
  edits gate on the same admin-only rule as TE-6.

- **TE-4 — `denial_reason_codes` vocabulary table (defaults global, managed in
  E4.2).** Add a small governed table:

  ```
  denial_reason_codes (
    id, org_id uuid NULL,   -- NULL = global default (seeded), non-NULL = org-added
    code text NOT NULL, label text NOT NULL, active boolean NOT NULL DEFAULT true,
    created_at timestamptz DEFAULT now())
  ```

  Seed the six defaults (Missing Documentation, Network Closed, Demographic
  Mismatch, Incomplete Application, Credentialing Criteria Not Met, Other) as
  `org_id IS NULL` rows. Read predicate = `org_id IS NULL OR org_id = active`;
  org codes deactivate, never delete (E4.2 F4.2.3), so historical
  `payer_pipeline_history.reason_code_id` references never dangle. RLS: SELECT
  the global+own-org rows to any member; INSERT/UPDATE `admin` only (config
  surface is E4.2). This epic ships the table + defaults + the read; E4.2 owns
  the management UI. F4.0.4's "Denied requires a reason code; Other requires
  context; RFI reason optional/binary" is enforced in the transition RPC (TE-5),
  not by a table constraint (RFI rows carry a null `reason_code_id`).

- **TE-5 — Atomic transition via a SECURITY-INVOKER RPC (honours the failure
  path).** F4.0.1 requires that a rejected transition writes NO history row and
  NO partial state change. The current `updateCaseStatus` does three sequential
  client statements (update → append history → audit) which cannot guarantee
  that. Add `advance_payer_pipeline(p_case_id, p_to_state, p_reason_code_id,
p_justification, p_is_correction)` as a SECURITY-INVOKER function (runs under
  the caller's RLS, so no privilege escalation) that, in one transaction:
  validates the edge against the TE-1 domain (raising a named error the UI maps
  to the inline "current state / allowed next states" message), enforces the
  reason-code rules (TE-4), performs the correction/post-terminal admin gate
  (TE-6), updates `payer_pipeline_state`, inserts the `payer_pipeline_history`
  row, applies the TE-6 enrollment writes/clears, and lets the caller's
  `writeAudit` (or an in-RPC `audit_log` insert mirroring the baseline
  `create_case_with_tasks` pattern) record it. Surface it in `cases.ts`
  (`advancePayerPipeline`) → `src/hooks/useCases.ts`; **no new `/api` write
  route** — the extension continues to read only.

- **TE-6 — Structured resolution + access control on the existing role model.**
  `Approved` writes the effective date and payer-issued provider ID. Reuse the
  existing `credential_cases.confirmed_effective_date` (the shipped
  "effective date" column) for the network-effective date rather than adding
  `network_effective_date`, and add two additive columns for the payer-issued
  IDs: `payer_individual_provider_id text` (Type 1 NPI-linked; carries the
  per-payer configured label in the UI) and `payer_group_provider_id text`
  (Type 2 / Tax-ID-linked billing ID) — separate columns, never concatenated
  (F4.0.3 billing-integrity rule). **There is no separate provider×payer enrollment
  table today** — the approved case _is_ the enrollment record for that
  provider × payer × state (the 4-part key, E2.1); the "provider's
  payer-enrollment view" (F4.0.3) and E1.8 readiness both derive In-Network /
  effective-date from approved cases, so no new enrollment table is needed (TD-1
  records this so a future directory/roster feature doesn't assume one).
  Access: `specialist`+`admin` do forward transitions (existing
  `credential_cases_update` RLS); `billing` has no update policy so it is
  read-only automatically; **correction transitions, post-terminal edits, and
  the approval-reversal enrollment clear are admin-only**, enforced inside the
  TE-5 RPC via `user_role(org_id) = 'admin'` (RLS alone cannot express
  "only when `is_correction` or the case is terminal"). Reapply after Denied
  (`[r4-review]` Q6) stays the normal specialist path — the internal track
  reopens through `updateCaseStatus`/`appendCaseTasks` and the payer pipeline
  advances Denied → Drafting through the TE-5 RPC as a normal forward
  transition (TE-1), not a pipeline correction.

- **TE-7 — Extension + surfaces read pipeline state through existing paths.**
