# E4.0 — Payer Pipeline: External State Machine, Tracking IDs & Structured Resolution

## Purpose and Context

`[r6]` decision A3 locks the core model: **internal operations are decoupled
from the payer's pipeline**. Internal task states ("Missing DEA", "Ready for
QA") stay in the SOP/task tracker (E1.7b/E2.2); the payer's side of a case is
a distinct, immutable state machine — **Drafting → Submitted → In Review →
Action Required (RFI) → Approved / Denied** — because mixing internal
gathering tasks with external payer statuses breaks reporting (R8).

This epic gives every credentialing case that payer pipeline, captures the
payer's **Reference/Tracking ID** at submission (A1 — needed for follow-up
when credentialing is delayed), and makes resolution **structured**: approval
records effective dates + payer-issued provider IDs (provider becomes
In-Network / Credentialed with effective date); a case may also close
Out-of-Network or Denied, and every denial/return carries a **structured
reason code** (A4 — Missing Documentation, Network Closed, Demographic
Mismatch, …) so R8 can report on systemic issues instead of parsing notes.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — moves cases through the
  payer pipeline, records tracking IDs, logs RFIs, and closes cases with
  structured outcomes.
- **P1 Credentialing Manager** — reads pipeline state at a glance across the
  caseload; relies on structured outcomes for reporting.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only (AGENTS.md): the payer pipeline state, tracking ID,
  resolution fields, and denial reason codes are new additive columns/tables
  beside the existing `credential_cases` status machinery — nothing is
  renamed or restructured. The reviewer records the exact mechanism in §5.
- Pipeline transitions are append-only history (the existing
  `status_history`/touch spine pattern) — the pipeline is immutable in the
  sense that history is never rewritten; the current state only moves along
  the defined edges.

## Features

### F4.0.1 — Payer pipeline state machine on every case

- **Description:** Every credentialing case carries a payer-pipeline state:
  `Drafting → Submitted → In Review → Action Required (RFI) → Approved /
  Denied`. Transitions follow the defined edges only (e.g. In Review ↔
  Action Required for RFI back-and-forth; Approved/Denied are terminal,
  subject to the existing reapply rule `[r4-review]` Q6). The pipeline state
  is displayed distinctly from internal task progress everywhere a case
  appears (case detail, case list, queue).
- **Persona:** P2, P1.
- **Benefit hypothesis:** internal-vs-external decoupling (A3) keeps
  reporting clean and lets a specialist see "where the payer is" without
  digging through tasks.
- **Acceptance criteria:**
  - The five-state pipeline (plus terminal outcomes) exists on every case;
    invalid transitions are rejected.
  - Every transition writes an append-only history row (who, when,
    from → to).
  - Case detail and case list render pipeline state separately from
    internal task/checklist progress — the two are never merged into one
    label.
  - Existing internal case statuses (`status_configs`) are untouched.
- **Test/data scenario(s):** TS-69.

```gherkin
Feature: Payer pipeline state machine
  Scenario: RFI round trip
    Given a case in payer-pipeline state "In Review"
    When P2 records an RFI from the payer
    Then the pipeline state becomes "Action Required (RFI)"
    And responding moves it back to "In Review"
    And both transitions appear in the case's pipeline history
```

### F4.0.2 — Reference/Tracking ID capture at submission

- **Description:** Moving a case to `Submitted` prompts for the payer
  portal's Reference/Tracking ID (optional at submit — some channels issue
  it later; it can be added/edited while the case is open and pre-terminal).
  The ID is displayed prominently on the case header and is searchable.
- **Persona:** P2.
- **Benefit hypothesis:** when credentialing is delayed, the specialist has
  the payer's own reference at hand for follow-up calls/portal checks (A1)
  instead of re-deriving it from emails.
- **Acceptance criteria:**
  - Submission transition offers a tracking-ID field; the value is stored
    on the case and rendered on the case header.
  - Case search/filter finds a case by tracking ID.
  - Adding or correcting the ID after submission is possible and audited.
- **Test/data scenario(s):** TS-70.

### F4.0.3 — Structured resolution: effective dates, provider IDs, outcome

- **Description:** Closing the pipeline as `Approved` requires the
  **effective date** and captures the payer-issued **provider ID(s)**; the
  provider's enrollment for that payer × state becomes In-Network /
  Credentialed with that effective date (feeding readiness E1.8 and
  reporting R8). A case may alternatively close **Out-of-Network** (working
  relationship ends without joining the network) or **Denied**.
- **Persona:** P2, P1.
- **Benefit hypothesis:** resolution data (dates + IDs) is where the
  business value of the whole case lands; structured capture makes it
  reportable and reusable (claims, rosters, directories).
- **Acceptance criteria:**
  - Approved requires an effective date; provider ID capture is offered on
    the same step.
  - The resolution writes are visible on the case and on the provider's
    payer-enrollment view.
  - OON and Denied are explicit close outcomes, distinct from Approved.
- **Test/data scenario(s):** TS-71.

```gherkin
Feature: Structured approval
  Scenario: Approval records effective date and provider ID
    Given a case in payer-pipeline state "In Review"
    When P2 marks it Approved with effective date 2026-08-01 and provider ID "HUM-449"
    Then the case closes Approved
    And the provider's enrollment for that payer/state shows In-Network effective 2026-08-01
```

### F4.0.4 — Structured denial/return reason codes

- **Description:** Every `Denied` close and every payer return/RFI kick-back
  requires a **reason code** from a managed list (initial set: Missing
  Documentation, Network Closed, Demographic Mismatch, Incomplete
  Application, Credentialing Criteria Not Met, Other + required context),
  plus the existing free-text note. The reason list is org-extensible via
  the E4.2 admin module.
- **Persona:** P2 (records), P1 (reports).
- **Benefit hypothesis:** structured reasons enable R8 predictive analytics
  — e.g. a payer consistently rejecting a specific facility's tax ID (A4) —
  which a status + paragraph note forfeits.
- **Acceptance criteria:**
  - Denied cannot be saved without a reason code; "Other" requires the
    single-line context.
  - Reason codes are stored structured (not concatenated into the note).
  - RFI transitions may optionally carry a reason code from the same list.
- **Test/data scenario(s):** TS-72.

## Dependencies

- E2.1 case creation (4-part key) and existing `status_history` /`touches`
  append-only spine.
- E1.8 readiness (consumes In-Network effective dates).
- E4.1 (touch types reference pipeline states for follow-ups) and E4.2
  (reason-code list management) — drafted in the same release.

## Out of Scope / Non-Goals

- No change to internal `status_configs` vocabulary or SOP/task states.
- No email/fax ingestion (payer responses still arrive out-of-band; E4.1
  logs them as touches — inbox integration is a later release).
- No automation of pipeline transitions from portal scraping.
- Contracting cases (`contracts`) are untouched — credentialing only.
