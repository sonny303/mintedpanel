# E2.1 — Case Creation & the 4-Part Case Key

## Purpose and Context

The confirm step behind E2.0's preview: create one credentialing case per
checked row — and, first, land the **riskiest schema change in the program**:
the case-key migration. The live DB constraint today is one case per
`(provider_id, payer_id, state)`; the PM-approved target grain (AGENTS.md) is
`(provider_id, group_id, payer_id, state)` — a provider can have parallel
cases with the same payer/state under different groups because each group's
TIN contracts separately. This epic adds the additive `group_id` column,
backfills it, and widens the uniqueness to the 4-part key.

Dedupe semantics are locked (`[r4]` Q2): a case at an existing 4-part key is
**never re-created**; re-applications after a denial **continue on the same
case** to preserve the payer/provider history. And per Q3 there is **no
prerequisite-payer logic anywhere** — commercial and Medicare Advantage cases
generate and run in parallel; `payers.prerequisite_payer_id` stays dormant.

Q2a's manual escape hatch also lives here: a standalone "create case" action
(outside the preview) for rare one-offs such as a payer not on the attached
list, using the same key, dedupe, and SOP-stamping path.

## Personas Empowered

- **P1 Credentialing Manager** — confirms generation; occasionally creates a
  manual one-off case.
- **P2 Credentialing Specialist** — receives the created cases and their
  task lists.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency (THE migration): additive
  `credential_cases.group_id uuid NULL → provider_groups` + backfill from the
  provider's assignment lineage (single-group orgs are unambiguous; ambiguous
  rows resolved by a deterministic documented rule) + widened uniqueness at
  the 4-part grain that still enforces the 3-part rule for legacy NULL-group
  rows. Exact mechanism (partial unique indexes vs NOT VALID constraint) is a
  §5 review decision; the migration must be additive, reversible-safe, and
  applied repo + hosted in the same PR.
- Implementation dependency: creation goes through one transactional path
  (the existing `create_case_with_tasks` RPC, extended additively with
  `group_id` and the E2.2 version stamp) — a batch is N idempotent calls;
  a mid-batch failure never half-creates a single case.
- Implementation dependency: batch runs record a `case_generation_runs` row
  (who/when/counts) with `credential_cases.generation_run_id uuid NULL` for
  E2.4 traceability — additive, table-register rows included.

## Features

### F2.1.1 — The 4-part-key migration

- **Description:** Add `group_id` to `credential_cases`, backfill, widen the
  uniqueness to provider × group × payer × state.
- **Persona:** system (all case features downstream).
- **Acceptance criteria:**
  - Existing cases keep working untouched; every backfillable case gains its
    `group_id`.
  - Two cases for the same provider/payer/state under different groups can
    coexist; a duplicate at the same 4-part key is rejected by the database.
  - AGENTS.md's interim 3-part caveat is retired in the same PR (docs
    updated to the live 4-part rule).
- **Test/data scenario(s):** TS-50.

### F2.1.2 — Batch creation from the confirmed preview

- **Description:** Confirming E2.0's preview creates one case per checked
  row (org, provider, group, payer, state, generation-run id), each with its
  task list stamped from the resolved SOP version (E2.2 contract). Grayed
  "already exists" rows are never re-created.
- **Persona:** P1.
- **Acceptance criteria:**
  - Exactly the checked rows are created; counts reported (created /
    skipped-existing / excluded).
  - Re-confirming the same preview is idempotent (existing keys skip).
  - Every created case carries the generation-run id; a partial failure
    reports which rows failed without corrupting created ones.
  - On completion the user lands on the next-best-action queue (E2.3).
- **Test/data scenario(s):** TS-50, TS-51.

```gherkin
Feature: Batch creation respects the 4-part key
  Scenario: Same provider, same payer, two groups
    Given Jane is assigned to facilities in Group 1 and Group 2, both targeting BCBS-NC
    When P1 confirms a preview containing both rows
    Then two cases exist: Jane × Group 1 × BCBS-NC × NC and Jane × Group 2 × BCBS-NC × NC
    And re-running generation proposes neither again
```

### F2.1.3 — Reapplication continues on the existing case

- **Description:** After a denial, reapplying is a status transition and new
  tasks **on the same case** — never a second case at the same key. The case
  keeps its full history (touches, status_history) across cycles.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Q2 — a single case = the complete payer/provider
  history, the way the business actually reasons about a relationship.
- **Acceptance criteria:**
  - A denied case offers a "reapply" action that reopens it (status
    transition per the existing case-status model) and regenerates tasks
    from the **current** SOP version (Model A: new work gets latest).
  - Generation never proposes a new case at a key with a denied/closed case;
    the preview row links to that case instead ("reapply from the case").
- **Test/data scenario(s):** TS-51.

### F2.1.4 — Manual one-off case creation

- **Description:** A standalone "create case" action (case-list surface) for
  combinations the preview cannot derive — e.g. a payer outside the attached
  list. Same key, dedupe, SOP resolution, and run-less audit trail.
- **Persona:** P1.
- **Acceptance criteria:**
  - Requires provider, group, payer (full org-visible catalog, not just
    attached), state; blocks on an existing case at the key with a link to it.
  - Created case is indistinguishable downstream from a generated one except
    for its null generation-run id.
- **Test/data scenario(s):** TS-52.

### F2.1.5 — No prerequisite logic (negative feature, by decision)

- **Description:** Per Q3, generation performs **no** prerequisite blocking,
  flagging, or auto-creation. Commercial + MA cases generate and run in
  parallel. `payers.prerequisite_payer_id` remains dormant (R10 candidate).
- **Acceptance criteria:**
  - A MA payer with no base contract generates normally, no warnings.
  - No prerequisite code paths exist in the generation pipeline.

live hosted DB (constraint set, row counts, `create_case_with_tasks`
definition, PostgreSQL 17.6), `src/services/cases.ts`, `src/lib/dbErrors.ts`,

E2.4/E1.7b/E1.5 cross-epics._

- **TE-1 — Corrected migration sketch: `group_id` already exists; THE
  migration is a constraint swap, not a column add.** The epic's premise
  ("adds the additive `group_id` column, backfills it") does not match the
  repo or the live DB: `credential_cases.group_id uuid NULL` has existed
  since the baseline (line 58) with FK
  `credential_cases_group_id_fkey → provider_groups(id)` (line 859) and an
  FK-cover index (`20260710140000_fk_index_coverage.sql`); `createCase`
  passes it on every insert (`src/services/cases.ts` line 269) and the RPC
  inserts it (baseline lines 543–560). **All 61 live cases already carry a
  non-NULL `group_id` (0 NULL rows, verified on hosted 2026-07-13).** The
  actual migration is:
  1. **Safety-net backfill** (currently a no-op on hosted, kept for rows
     created between spec and apply): for `group_id IS NULL` rows, in
     deterministic order — (a) `facility_id → facilities.group_id`; (b) the
     provider's sole `provider_group_assignments` row; (c) the provider's
     `is_primary` assignment; (d) otherwise leave NULL (the legacy 3-part
     rule below still binds them). Do not read the frozen
     `providers.group_id` mirror (register: "no new readers").
  2. **Constraint swap:** drop
     `credential_cases_provider_id_payer_id_state_key` and add
     `UNIQUE NULLS NOT DISTINCT (provider_id, group_id, payer_id, state)`
     (hosted is PostgreSQL 17.6; `NULLS NOT DISTINCT` needs ≥15 and the
     local CLI stack satisfies it). One constraint yields BOTH required
     semantics: 4-part uniqueness for grouped rows AND the 3-part rule
     among legacy NULL-group rows (NULL = NULL under NULLS NOT DISTINCT).
     The epic's "NOT VALID constraint" alternative is **not viable** —
     Postgres supports NOT VALID only for CHECK/FK, never UNIQUE; the
     fallback, if NULLS NOT DISTINCT is ever a problem, is the two partial
     unique indexes (`WHERE group_id IS NOT NULL` on the 4 columns /
     `WHERE group_id IS NULL` on the 3). Keep the new index leading on
     `provider_id` so the dropped constraint's FK coverage for
     `provider_id` is preserved. Migration guarded per
     `docs/migration-baseline.md` (constraint-existence checks), applied
     repo + hosted in the same PR.
- **TE-2 — New table `case_generation_runs` + `generation_run_id` column,
  with explicit org-scoping/RLS (the epic omits both).** Sketch:
  `case_generation_runs (id uuid pk default gen_random_uuid(), org_id uuid
NOT NULL → organizations, created_by uuid → profiles, created_at
timestamptz NOT NULL default now(), proposed_count int NOT NULL,
created_count int NOT NULL, skipped_existing_count int NOT NULL,
excluded_count int NOT NULL, failed_count int NOT NULL)`. RLS: org-member
  SELECT (`org_id IN user_org_ids()`), writer (admin|specialist) INSERT with
  same-org WITH CHECK, **no UPDATE/DELETE policies** — runs are immutable by
  omission (E2.4 requires immutable dispositions; the per-row disposition
  payload shape is E2.4's §5 decision, deliberately not built here).
  `credential_cases.generation_run_id uuid NULL → case_generation_runs` +
  FK-cover index (the E0.10 convention). Every insert sets `org_id` from the
  active org (AGENTS.md). Same PR: table-register rows for
  `case_generation_runs` (work layer, support) and the `generation_run_id`
  note on `credential_cases`; regenerate
  `src/integrations/supabase/types.ts`.
- **TE-3 — RPC extension: `generation_run_id` and the E2.2 stamp params —
  NOT `group_id` (already handled).** `create_case_with_tasks` already
  inserts `group_id` from `p_input`; the additive extension this PR needs is
  (a) `p_input->>'generation_run_id'` on the case insert and (b) the E2.2
  per-task stamp fields (`sop_template_id`/`sop_version`, columns landed by
  E1.7b's migration — build order E1.7b → E2.0 → E2.1 per ROADMAP-STATUS
  guarantees they exist; E2.2 populates them, this PR only threads them).
  Ship as a new repo migration (`CREATE OR REPLACE FUNCTION`) applied repo +
  hosted; preserve the existing security posture (SECURITY INVOKER, RLS
  applies; EXECUTE for `authenticated, service_role`, baseline lines
  1220–1221). "N idempotent calls" is loose wording: the RPC is not
  replay-idempotent; batch semantics are **per-row transactionality +
  skip-on-unique-violation** — each call is its own transaction (no
  half-created case), and the confirm loop treats SQLSTATE 23505 on the new
  4-part constraint as `skipped-existing`, recording per-row dispositions
  for the run counts. A concurrent duplicate confirm degrades safely to a
  skip.
- **TE-4 — Duplicate-message translator must learn the new constraint name
  in the same PR.** `src/lib/dbErrors.ts` (line 32) fragment-matches
  `credential_cases_provider_id_payer_id_state_key` to produce "A case
  already exists for this provider, payer, and state." Dropping that
  constraint silently reverts duplicate errors to raw Postgres text. Add the
  new constraint-name fragment with group-aware wording (e.g. "A case
  already exists for this provider, group, payer, and state."); keep the old
  fragment row (harmless, additive).
- **TE-5 — Dedupe/graying reads the full key set regardless of status;
  reapply is a status transition + task append on the existing case.**
  Existing-case detection for the preview compares at the 4-part key against
  ALL of the org's cases — a denied case still occupies its key (DENIED sits
  in `action_bucket 'ours'`, `src/lib/canonicalStatuses.ts`, so "open case"
  filters must NOT be the dedupe filter). Reapply (F2.1.3) reuses the
  existing `updateCaseStatus` path (status_history + audit already written
  there) plus a new additive service function that appends the restamped
  task set to the existing case (`tasks` inserts follow the RPC's shape;
  E2.2 owns resolution/stamping). No schema change; `touches` /
  `status_history` / `audit_log` stay append-only and untouched
  semantically.
- **TE-6 — Manual one-off case (F2.1.4) composes from existing primitives —
  no component enablers.** Dialog/select/checkbox/table all exist in
  `src/components/ui/`; build the modal per the house mount-when-editing
  pattern under a feature dir (never `ui/`/`layout/`), so no DESIGN-DEBT
  entry is required. "Full org-visible catalog" = `listPayers` (own-org rows
  - assigned global rows) — deliberately NOT filtered to
    `payer_network_targets`; group select offers the provider's groups from
    `provider_group_assignments`; state input follows the E0.10 `^[A-Z]{2}$`
    format. Pre-check the 4-part key and render the block-with-link; keep the
    DB constraint as backstop (23505 → TE-4 message). `generation_run_id`
    stays NULL (the F2.1.4 "run-less" trail); creation audit rows come from
    the RPC as today.
- **TE-7 — Authoritative table trace (the epic omits one; AGENTS.md requires
  it).** Reads: `credential_cases` (existing-key set),
  `case_generation_exclusions` (E2.0), `payer_network_targets` (via the
