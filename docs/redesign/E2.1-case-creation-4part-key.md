# E2.1 — Case Creation & the 4-Part Case Key

## Purpose and Context

The confirm step behind E2.0's preview: create one credentialing case per
checked row — and, first, land the **riskiest schema change in the program**:
the case-key migration. The live DB constraint today is one case per
`(provider_id, payer_id, state)`; the PM-approved target grain (AGENTS.md) is
`(provider_id, group_id, payer_id, state)` — a provider can have parallel
cases with the same payer/state under different groups because each group's
TIN contracts separately. This epic adds the additive `group_id` column,
backfills it, and widens the uniqueness to the 4-part key.

Dedupe semantics are locked (`[r4]` Q2): a case at an existing 4-part key is
**never re-created**; re-applications after a denial **continue on the same
case** to preserve the payer/provider history. And per Q3 there is **no
prerequisite-payer logic anywhere** — commercial and Medicare Advantage cases
generate and run in parallel; `payers.prerequisite_payer_id` stays dormant.

Q2a's manual escape hatch also lives here: a standalone "create case" action
(outside the preview) for rare one-offs such as a payer not on the attached
list, using the same key, dedupe, and SOP-stamping path.

## Personas Empowered

- **P1 Credentialing Manager** — confirms generation; occasionally creates a
  manual one-off case.
- **P2 Credentialing Specialist** — receives the created cases and their
  task lists.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency (THE migration): additive
  `credential_cases.group_id uuid NULL → provider_groups` + backfill from the
  provider's assignment lineage (single-group orgs are unambiguous; ambiguous
  rows resolved by a deterministic documented rule) + widened uniqueness at
  the 4-part grain that still enforces the 3-part rule for legacy NULL-group
  rows. Exact mechanism (partial unique indexes vs NOT VALID constraint) is a
  §5 review decision; the migration must be additive, reversible-safe, and
  applied repo + hosted in the same PR.
- Implementation dependency: creation goes through one transactional path
  (the existing `create_case_with_tasks` RPC, extended additively with
  `group_id` and the E2.2 version stamp) — a batch is N idempotent calls;
  a mid-batch failure never half-creates a single case.
- Implementation dependency: batch runs record a `case_generation_runs` row
  (who/when/counts) with `credential_cases.generation_run_id uuid NULL` for
  E2.4 traceability — additive, table-register rows included.

## Features

### F2.1.1 — The 4-part-key migration

- **Description:** Add `group_id` to `credential_cases`, backfill, widen the
  uniqueness to provider × group × payer × state.
- **Persona:** system (all case features downstream).
- **Acceptance criteria:**
  - Existing cases keep working untouched; every backfillable case gains its
    `group_id`.
  - Two cases for the same provider/payer/state under different groups can
    coexist; a duplicate at the same 4-part key is rejected by the database.
  - AGENTS.md's interim 3-part caveat is retired in the same PR (docs
    updated to the live 4-part rule).
- **Test/data scenario(s):** TS-50.

### F2.1.2 — Batch creation from the confirmed preview

- **Description:** Confirming E2.0's preview creates one case per checked
  row (org, provider, group, payer, state, generation-run id), each with its
  task list stamped from the resolved SOP version (E2.2 contract). Grayed
  "already exists" rows are never re-created.
- **Persona:** P1.
- **Acceptance criteria:**
  - Exactly the checked rows are created; counts reported (created /
    skipped-existing / excluded).
  - Re-confirming the same preview is idempotent (existing keys skip).
  - Every created case carries the generation-run id; a partial failure
    reports which rows failed without corrupting created ones.
  - On completion the user lands on the next-best-action queue (E2.3).
- **Test/data scenario(s):** TS-50, TS-51.

```gherkin
Feature: Batch creation respects the 4-part key
  Scenario: Same provider, same payer, two groups
    Given Jane is assigned to facilities in Group 1 and Group 2, both targeting BCBS-NC
    When P1 confirms a preview containing both rows
    Then two cases exist: Jane × Group 1 × BCBS-NC × NC and Jane × Group 2 × BCBS-NC × NC
    And re-running generation proposes neither again
```

### F2.1.3 — Reapplication continues on the existing case

- **Description:** After a denial, reapplying is a status transition and new
  tasks **on the same case** — never a second case at the same key. The case
  keeps its full history (touches, status_history) across cycles.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Q2 — a single case = the complete payer/provider
  history, the way the business actually reasons about a relationship.
- **Acceptance criteria:**
  - A denied case offers a "reapply" action that reopens it (status
    transition per the existing case-status model) and regenerates tasks
    from the **current** SOP version (Model A: new work gets latest).
  - Generation never proposes a new case at a key with a denied/closed case;
    the preview row links to that case instead ("reapply from the case").
- **Test/data scenario(s):** TS-51.

### F2.1.4 — Manual one-off case creation

- **Description:** A standalone "create case" action (case-list surface) for
  combinations the preview cannot derive — e.g. a payer outside the attached
  list. Same key, dedupe, SOP resolution, and run-less audit trail.
- **Persona:** P1.
- **Acceptance criteria:**
  - Requires provider, group, payer (full org-visible catalog, not just
    attached), state; blocks on an existing case at the key with a link to it.
  - Created case is indistinguishable downstream from a generated one except
    for its null generation-run id.
- **Test/data scenario(s):** TS-52.

### F2.1.5 — No prerequisite logic (negative feature, by decision)

- **Description:** Per Q3, generation performs **no** prerequisite blocking,
  flagging, or auto-creation. Commercial + MA cases generate and run in
  parallel. `payers.prerequisite_payer_id` remains dormant (R10 candidate).
- **Acceptance criteria:**
  - A MA payer with no base contract generates normally, no warnings.
  - No prerequisite code paths exist in the generation pipeline.

## Scenario/Seed Data Mapping

- TS-50 — 4-part key: same provider/payer/state under two groups coexist;
  duplicate rejected.
- TS-51 — Denial → reapply on the same case; history continuous; tasks
  restamped at the current SOP version.
- TS-52 — Manual one-off case against a non-attached payer.

## Dependencies

- E2.0 preview (input set), E1.7b (SOP versions for the E2.2 stamp), E1.5
  targets, E1.3/E1.4 roster + assignments.
- Existing `create_case_with_tasks` RPC, case-status model, append-only
  spines (untouched).

## Out of Scope / Non-Goals

- SOP resolution/stamping details (E2.2 — contract consumed here).
- The landing queue (E2.3).
- Prerequisite-payer logic (dropped by decision, not deferred).
- Contracting status (lives on `contracts`, never on cases).
