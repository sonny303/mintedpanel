# E3.3 — Sectioned Intake Uniformity

## Purpose and Context

The `[r5-debt]` retro found a flow gap in E3.0: the three intake experiences —
(1) a credential manager filling out the webapp forms, (2) the sharable
onboarding link, (3) CSV upload — must all walk the same foundational ladder
**org → group → facilities → providers**, but E3.0 bolted one monolithic
20-column combined roster CSV onto a single wizard section instead of offering
an upload option beside the manual form in each section.

This epic closes the gap: after initial org setup, the wizard's **Provider
Group**, **Facilities**, and **Providers** sections each offer BOTH a manual
entry form (unchanged) and a CSV upload whose template mirrors exactly the
fields that section's manual form captures. Both surfaces (the internal
power tool at `/admin/import` and the wizard) move to per-section uploads —
one uniform, scalable model — and the E3.0 combined roster template is
**retired**. All prior `[r5]`/`[r5-review]` decisions carry over unchanged:
exact-header front gate, downloadable per-section templates, 10 MB ceiling,
drag-and-drop states, SSN reject-never-truncate, async staged scan,
error report, and E3.1's preview → staged commit before anything goes live.

The sharable link stays org-intake-only for now; on convert-to-customer the
recipient flows into this SAME onboarding experience (`[r5-debt]` decision 3)
— no parallel flow is built here.

## Personas Empowered

- **P1 Credentialing Manager** — imports groups, facilities, and providers
  per section with the same mental model as manual entry.
- **P5 Practice / Organization Owner** (org rep) — continues from the org
  intake into the identical sectioned experience, uploading or typing per
  section.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); reuse the E3.0
  import components (`RosterDropZone`, `RosterUploader`, `ImportRunPanel`,
  `ImportRunList`) and the E3.1 preview/commit engine — this epic is a
  template/surface split, not a new pipeline.
- Additive schema only. Expected shape: `import_runs` gains an additive
  entity discriminator (e.g. `entity_kind` `provider_group | facility |
provider`) so one runs/rows/preview/commit machine serves all three
  sections; reviewer verifies and records the exact mechanism in §5. Table
  register updated in the same PR.
- Each section's template is the SINGLE source shared by its downloadable
  template and its front gate, and mirrors exactly the fields of that
  section's manual form (`ProviderGroupForm`, `FacilityForm`,
  `ProviderRosterForm`) plus prior decisions (e.g. `ssn_last4`,
  `date_of_birth`, `caqh_id`, `license_issue_date`, middle initial on the
  providers template).
- SSN safety carries over verbatim from E3.0 TE-6: full-SSN values are
  rejected (never truncated or derived), never echoed, never persisted.
- No external API calls during import (`[r5]` decision 11); async scan and
  10 MB ceiling unchanged.

## Features

### F3.3.1 — Per-section upload beside every manual form

- **Description:** After org setup, the wizard's Provider Group, Facilities,
  and Providers sections each render BOTH paths: the existing manual entry
  form and a CSV upload (template download, exact-header gate, drag-and-drop
  with Uploading → Scanning → Success/Failed states, columns + sample-rows
  preview). One shared upload composition, parameterized by section.
- **Persona:** P1, P5.
- **Benefit hypothesis:** every intake experience walks the same
  org → group → facilities → providers ladder, so users switch freely
  between typing and uploading without changing mental model.
- **Acceptance criteria:**
  - Each of the three sections offers manual entry AND upload side by side;
    neither hides the other.
  - Each section's downloadable template contains exactly the fields its
    manual form captures — no more, no fewer; the gate enforces it.
  - Upload UX (states, preview, error report) is identical across sections.
- **Test/data scenario(s):** TS-65.

```gherkin
Feature: Uniform sectioned intake
  Scenario: Facilities section accepts a facilities CSV
    Given an org with a provider group and no facilities
    When P5 downloads the Facilities template, fills 8 rows, and uploads it
    Then the scan stages 8 facility rows for preview
    And the manual "Add facility" form remains available beside the upload
```

### F3.3.2 — Ladder enforcement across all experiences

- **Description:** The org → group → facilities → providers order holds
  uniformly (`[r5-debt]` decision 4): a section's upload (and manual form,
  where not already enforced) requires its parent entity to exist —
  facilities need a group; providers need a group (facility assignment rows
  reference existing or same-run staged facilities per the E3.1 rules).
- **Persona:** P1, P5.
- **Benefit hypothesis:** no orphaned records; imported data always lands
  attached to the right parent, matching the manual flow's guarantees.
- **Acceptance criteria:**
  - Uploading to a section whose parent step is incomplete is blocked with a
    clear pointer to the prerequisite section (never a silent failure).
  - The wizard's per-section status chips reflect upload-created data
    exactly as they do manually entered data.
- **Test/data scenario(s):** TS-66.

### F3.3.3 — Combined roster retirement + power-tool parity

- **Description:** The E3.0 20-column combined template is retired: the
  internal power tool at `/admin/import` moves to the same three per-section
  uploads (full column visibility, raw error detail — the power-user
  affordances stay). Old combined-template uploads are rejected at the gate
  with a message pointing to the per-section templates. In-flight
  `import_runs` from the combined era stay reviewable/cancelable.
- **Persona:** P1.
- **Benefit hypothesis:** one uniform model — no divergent template or write
  path to maintain, document, or train on.
- **Acceptance criteria:**
  - `/admin/import` offers the three per-section uploads and no combined
    upload; both surfaces feed identical validation and staging.
  - A combined-era template upload is rejected at the front gate naming the
    replacement templates.
  - Existing staged runs remain reviewable; nothing already staged is lost.
- **Test/data scenario(s):** TS-67.

```gherkin
Feature: Combined template retired
  Scenario: Legacy combined roster rejected with guidance
    Given the retired 20-column combined template filled with data
    When P1 uploads it to the Providers section
    Then the file is rejected at the header gate
    And the message names the per-section templates that replace it
```

### F3.3.4 — Seamless link continuation (fence, not build)

- **Description:** The sharable capture link stays org-intake-only. This
  epic only guarantees the fence and the seam: a captured org, once
  converted, lands its people in the SAME wizard experience (sections +
  per-section uploads) with the org-intake data already in place — no
  parallel or divergent onboarding flow exists.
- **Persona:** P5.
- **Benefit hypothesis:** conversion is a continuation, not a restart.
- **Acceptance criteria:**
  - The capture link surface gains no upload or group/facility/provider
    capability in this epic.
  - A converted org's wizard shows org details complete and the remaining
    ladder sections (with uploads) ready.
- **Test/data scenario(s):** TS-68.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-13 against the shipped E3.0 pipeline
(`src/lib/rosterImport.ts`, `src/components/import/RosterUploader.tsx` +
`RosterDropZone`/`ImportRunPanel`/`ImportRunList`, `src/services/importRuns.ts`,
`src/hooks/useImportRuns.ts`, the staging migration
`20260713180000_import_runs_rows_staging.sql`, `src/routes/admin.import.tsx`),
the wizard section framework (`src/routes/onboarding.wizard.tsx`,
`src/lib/onboardingProgress.ts`, `src/components/onboarding/sectionBodies.tsx`,
`ProviderRosterSection.tsx`), the three manual forms
(`ProviderGroupForm.tsx`, `FacilityForm.tsx`, `ProviderRosterForm.tsx`) and
their pure helpers (`src/lib/providerGroup.ts`, `src/lib/facilityHours.ts`,
`src/lib/facilityContact.ts`, `src/lib/groupAssignments.ts`), the create/assign
services (`src/services/orgSettings.ts` `createProviderGroup`/`createFacility`,
`src/services/providers.ts` `createProviderWithDetails`), the reviewed-but-not-
yet-built E3.1 preview/commit engine (`docs/redesign/E3.1-*.md` §5), the
E0.5 capture surface (`src/routes/capture.$token.tsx`,
`src/services/captureLinks.ts`), `docs/data-model/table-register.md`
(`import_runs`/`import_rows` rows), `docs/redesign/seed-universe.md`
(TS-65–TS-68), and `uiux-component-guide.md`. **Headline:** this epic is a
template/surface split, not a new pipeline — E3.0's one staging machine
(gate → chunked async scan → `import_runs`/`import_rows` → E3.1 commit) already
exists; the work is (a) an additive `entity_kind` discriminator so one machine
serves three sections, (b) three per-section template/gate modules derived
from the live manual-form field sets, and (c) retiring the combined template.
The one genuine design tension is that two of the three manual forms capture
**non-scalar** data (multiple purpose-keyed address blocks, an hours jsonb,
tag arrays) that a flat CSV cannot mirror one-to-one — TE-3 resolves this
explicitly rather than leaving "mirrors exactly the fields" as an unbuildable
literal._

- **TE-1 — One staging machine, parameterized by an additive
  `import_runs.entity_kind` discriminator (the central enabler).** E3.0 already
  routes every upload through a single pipeline keyed only by `source`
  (`internal | onboarding`); the run/rows/RPC/commit machinery is
  entity-agnostic (`raw`/`mapped` are opaque jsonb). Add an additive column so
  the same machine tells the three sections apart:

  ```
  entity_kind text NOT NULL DEFAULT 'combined'
    CHECK (entity_kind IN ('provider_group','facility','provider','combined'))
  ```

  New per-section uploads write `'provider_group' | 'facility' | 'provider'`;
  the `'combined'` value is the **default** so every in-flight E3.0 run keeps a
  valid, distinguishable kind with no backfill (F3.3.3 "in-flight runs stay
  reviewable" — TE-7). Additive migration applied repo + hosted per
  `docs/migration-baseline.md`, regenerates
  `src/integrations/supabase/types.ts`, adds `entity_kind` to `ImportRun` +
  `CreateImportRunInput` (`src/types/index.ts` additive, `importRuns.ts`), and
  updates the `import_runs` register row **in the same PR** (AGENTS.md). No new
  table; `import_rows` needs no change (its `run_id` inherits the kind). The
  `resumeStates` / in-flight logic in `RosterUploader` gains an `entity_kind`
  filter so a section only resumes its own runs.

- **TE-2 — Three per-section template/gate modules, each the SINGLE source its
  download and its front gate share (F3.3.1).** Generalize the E3.0
  `rosterImport.ts` pure core (header list → `rosterTemplateCsv` +
  `checkRosterHeaders`/`headerGateMessage` → `scanRosterRecord` → chunking →
  error report) from one hard-coded `ROSTER_TEMPLATE_HEADERS` into a
  per-section descriptor `{ headers, required, scan }`, one per `entity_kind`.
  The exact-match gate, the 10 MB / `.csv` file checks, `STAGE_CHUNK_SIZE`
  batching, `collectRowErrors`/`errorReportCsvRows`, and `previewRows` are all
  section-independent and reused verbatim. Each section's header list is
  **derived from that section's manual form** so "no more, no fewer" (F3.3.1
  AC) is literally checkable against the form:
  - **provider_group** ← `ProviderGroupForm`/`GroupFormValue`: `group_name`,
    `group_tin` (required; bare-store, `XX-XXXXXXX` accepted per existing
    `TIN_RE`), `npi_type2`, `operating_states`, plus the billing /
    correspondence / credentialing address+contact blocks (see TE-3 for the
    non-scalar handling).
  - **facility** ← `FacilityForm`/`FacilityInput`: `facility_name` (required),
    `group_name` **or** `group_tin` as the parent key (TE-5), `street`,
    `suite`, `city`, `state`, `zip`, `county`, `phone`, `fax`, `email`,
    `appointment_phone`, `contact_name`, plus the CAQH extras
    (`accepting_new_patients`, `languages_offered`, `interpreter_languages`,
    `ada_accessible`, `ada_notes`) and hours (TE-3).
  - **provider** ← `ProviderRosterForm`/`ProviderInput`: identity/contact/
    professional/malpractice/CAQH scalars + `ssn_last4` + `date_of_birth` +
    the group-assignment key + repeatable license columns — this is the E3.0
    provider-shaped subset minus the group/facility-creation columns the
    combined template bundled. Required: `provider_first_name`,
    `provider_last_name`, `npi`, and a parent-group key.
- **TE-3 — Non-scalar form fields are the one real gap; resolve with a
  documented flat encoding, do NOT pretend a CSV mirrors a nested form
  verbatim.** `FacilityForm` stores an **hours jsonb**
  (`src/lib/facilityHours.ts`) and two **tag arrays** (`languages_offered`,
  `interpreter_languages`); `ProviderGroupForm` stores **three purpose-keyed
  address+contact blocks** (billing/correspondence/credentialing) and a
  multi-select `operating_states`; `ProviderRosterForm` stores **0..n
  licenses**. A single flat CSV row cannot losslessly carry these. Concrete,
  buildable resolution (keeps F3.3.1's "matches its form's fields" honest):
  - Multi-value scalars ride **one delimited column** with a pure
    encode/decode helper — `operating_states` / `languages_offered` /
    `interpreter_languages` as `;`-separated, `NC;SC;CO`; the group's three
    blocks flatten to prefixed columns (`billing_street`, `corr_street`,
    `cred_street`, …) mirroring the form's block-by-block layout, and the
    manual form's "Same as billing" quick-fill becomes "leave the corr/cred
    columns blank ⇒ inherit billing" at scan time (same live-mirror
    semantics).
  - **Hours** are deferred from the CSV in R5 — the facility template omits the
    day-by-day grid (it is a jsonb weekly schedule, not a cell) and documents
    "set hours after import in the facility form." This is a scope-preserving
    interpretation of F3.3.1 (the template mirrors the form's **capturable-in-
    CSV** fields; hours stay manual-only) and is called out as tech debt, not a
    silent omission. Confirm with the PM (Open Question 1) — the alternative is
    a per-day column set, heavier and rarely used at import time.
  - **Licenses** reuse the E3.0 pattern already in `RosterUploader`'s helper
    text ("repeat rows per license"): one provider row per license, deduped
    into one provider on commit (E3.1 grain). The per-section provider template
    inherits this exactly.
    Each section's `scan` function is a pure, fully unit-testable descriptor
    over these rules (the E3.0 `scanRosterRecord` shape), so TS-65's
    "template matches the form" is a test assertion, not a hope.
- **TE-4 — `RosterUploader` becomes section-parameterized; no new upload
  composition (F3.3.1 "one shared upload composition").** It already takes
  `{ source, variant }` and renders the whole gate → preview → scan → run flow;
  add an `entityKind` prop that selects the TE-2 descriptor (template download,
  gate, scan) and is written onto the run via `createImportRun`. The three
  sections mount three instances of the SAME component — `admin.import.tsx`
  (variant `internal`) and the wizard section bodies (variant `streamlined`),
  so "upload UX identical across sections" (F3.3.1 AC) is structural, not
  re-implemented. `ImportRunPanel`/`ImportRunList`/`RosterDropZone` are
  unchanged; `ImportRunList` gains an `entity_kind` label/column so mixed-kind
  history reads clearly. Feature components stay in `src/components/import/`;
  nothing touches `layout/` or `ui/`.
- **TE-5 — Ladder enforcement is a render-time parent-exists gate over existing
  scope reads (F3.3.2), not new schema.** The wizard already knows scope state:
  `useOnboardingWizard` derives per-section status from the live provider-group
  / facility / provider reads (`onboardingProgress.ts`), and the manual forms
  already enforce the ladder (`FacilityForm` requires an owning group;
  `ProviderRosterForm`/`GroupAssignmentPicker` require ≥1 group assignment).
  Extend the SAME rule to each section's upload: gate the Facilities upload on
  "≥1 provider group exists," the Providers upload on "≥1 group exists," and
  render a disabled drop zone with a pointer to the prerequisite section
  instead of accepting a file (F3.3.2 AC "blocked with a clear pointer, never a
  silent failure"). Because staged rows are not yet live, cross-section
  references **within one run** (a provider row naming a same-run staged
  facility) follow the E3.1 rule — E3.1 dedupe/commit resolves staged-vs-
  existing parents; E3.3 adds no new resolution logic, it only fences entry.
  Upload-created data flows through the same reads, so the per-section status
  chips reflect it identically to manual entry (F3.3.2 AC) with no extra work.
- **TE-6 — SSN safety is unchanged and now section-scoped (verbatim from E3.0
  TE-6).** The full-SSN reject-never-truncate sweep, the non-echoing messages
  (`SSN_REJECT_REASON`/`SSN_LAST4_FORMAT_REASON`), and the `raw`-redaction all
  live in the shared scan core and carry into the per-section `scan` functions.
  Only the **provider** template carries `ssn_last4` / `date_of_birth`; the
  group template's `group_tin` keeps its existing bare-9-digit exemption
  (dashed `NNN-NN-NNNN` still rejected even there), and the facility template
  has no SSN-shaped column at all. No new PII surface — the same `import_rows`
  RLS + purge (TE-7 of E3.1) governs all three kinds.
- **TE-7 — Combined-template retirement is additive + backward-compatible
  (F3.3.3).** The E3.0 `ROSTER_TEMPLATE_HEADERS` (20-column combined) is
  superseded by the three TE-2 templates; the combined download is removed from
  both surfaces. A legacy combined file uploaded to any section fails the
  exact-match gate automatically (its headers ≠ that section's headers) — make
  the rejection **actionable** by detecting the combined header signature and
  naming the three replacement templates (F3.3.3 AC), rather than the generic
  missing/extra list. Retire the combined path itself (the single
  `ROSTER_TEMPLATE_HEADERS`/`checkRosterHeaders` default and the `admin.import`
  single `RosterUploader source="internal"` → three per-section uploaders);
  keep the `admin.import` URL (legacy-route contract) and the run-history list.
  **In-flight runs:** existing `import_runs` default to `entity_kind='combined'`
  (TE-1) and stay listable/reviewable/cancelable through the unchanged
  `ImportRunPanel`/`cancelImportRun` path — nothing already staged is lost
  (F3.3.3 AC).
- **TE-8 — Commit fan-out is per-`entity_kind` through the EXISTING create
  services; per-section dedupe grains differ (E3.1 dependency).** E3.1 builds
  the preview/dedupe/staged-commit engine against the **provider** grain
  (five-part dedupe, per-field conflict review, `verification_state`). E3.3
  routes commit by `entity_kind`:
  - **provider** → E3.1's existing path verbatim (`createProviderWithDetails`,
    five-part dedupe, Pending Verification) — no change.
  - **provider_group** → `createProviderGroup` (`orgSettings.ts`); dedupe grain
    is **TIN** (the group's natural key; `provider_groups.tin`), skip-on-match.
  - **facility** → `createFacility` (`orgSettings.ts`); dedupe grain is
    **(group, facility name + address)** — `provider_facility_assignments` and
    the group link already exist. Group/facility are simpler than the provider
    grain (no license/assignment fan-out), so their dedupe is a thin addition
    to E3.1's pure dedupe module, not a parallel engine. Reads/writes stay in
    services; components → hooks → services → `externalClient` throughout.
    **Sequencing note:** E3.1 should keep its commit dispatch open to
    non-provider kinds (or E3.3 adds the two extra branches) — flagged so E3.1
    does not hard-code a provider-only commit that E3.3 must then refactor.
- **TE-9 — Link continuation is a fence, not a build (F3.3.4).** The E0.5
  capture surface (`capture.$token.tsx` + `captureLinks.ts`) stays
  org-intake-only; this epic adds **zero** upload/group/facility/provider
  capability there (F3.3.4 AC) — the only verification is a guard/test that the
  capture route and service gain no such surface. "Converted org lands in the
  same wizard" is already true today: convert-to-customer flips the org
  lifecycle and the org rep (provisioned as an org admin per [r5-review]
  decision 2) opens `onboarding.wizard.tsx`, where org details read complete
  and the ladder sections (now with per-section uploads) are ready. No parallel
  onboarding flow is built. TS-68 asserts the fence over the existing E0.5
  fixtures.
- **TE-10 — UI reuses shipped primitives; no new component or dependency.**
  Each section renders the manual form (unchanged) beside a `RosterUploader`
  instance (TE-4); side-by-side layout is a `card`/section composition per
  `uiux-component-guide.md` (rows `h-10`, `p-4`, `gap-4`, tokens from AGENTS.md
  / the design system). No new shadcn primitive is required (drop zone,
  preview table, progress states all shipped in E3.0). Any unspecced component
  would be stock shadcn logged in `DESIGN-DEBT.md` (AGENTS.md E0.9) — none is
  expected. `npx prettier --write` on every edited file.
- **TE-11 — Authoritative table trace (AGENTS.md requires one).** Reads:
  `import_runs`, `import_rows`, `provider_groups` (ladder + group dedupe),
  `facilities` (facility dedupe), `providers` / `provider_group_assignments` /
  `provider_facility_assignments` / `state_licenses` (provider commit via
  E3.1). Writes: `import_runs` (INSERT with `entity_kind`; state/count UPDATE),
  `import_rows` (INSERT via `stage_import_rows`, DELETE on commit/cancel),
  plus — at commit, through E3.1 + the existing services — `provider_groups`,
  `facilities`, `providers`, `provider_group_assignments`,
  `provider_facility_assignments`, `state_licenses`, and `audit_log`
  (append-only). Reconciled against the register: `import_runs` gains the
  additive `entity_kind` column (row updated in the same PR); **no new table**.
- **TE-12 — Verification gates + build order.** Unit-test the pure per-section
  descriptors (each template's exact-header gate; the TE-3 delimited/prefixed
  encode-decode + "blank corr/cred ⇒ inherit billing"; the provider license
  repeat-row rule), and the ladder-gate predicate. e2e over existing fixtures
  (no new baselines, per seed-universe): **TS-65** (three sections each show
  manual + upload; each template matches its form; identical upload UX),
  **TS-66** (facilities upload blocked without a group, proceeds after one
  exists; status chips reflect upload-created data), **TS-67** (legacy combined
  file rejected naming the per-section templates; `/admin/import` shows three
  uploads and no combined; pre-existing staged runs still reviewable),
  **TS-68** (converted capture-link org continues into the sectioned wizard;
  capture surface gained nothing). Must pass `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`, and the touched Playwright specs.
  **Build order: E3.3 builds AFTER E3.1** (it reuses E3.1's preview/dedupe/
  staged-commit engine and extends its commit dispatch) — the roadmap queue is
  E3.1 → E3.3, with E3.2 parked at end of redesign.

### Likely tech debt / risk to contain

- **CSV cannot mirror a nested form losslessly (TE-3).** The facility hours
  jsonb and the group's three address blocks are the sharp edges. Ship the
  documented flat encoding (delimited multi-values, prefixed blocks,
  hours-deferred) and log the hours-in-CSV deferral in `TECH-DEBT.md`; do NOT
  let "mirrors exactly the fields" force an unusable per-day/nested column
  explosion into R5.
- **Two dedupe grains join the provider grain (TE-8).** Group (TIN) and
  facility (group + name/address) dedupe are new, small, and must stay in the
  pure E3.1 dedupe module — resist a second engine. Keep E3.1's commit dispatch
  extensible so E3.3 adds branches, not a rewrite.
- **`admin.import` retirement scope.** Retiring the combined uploader while
  keeping the URL + run history is a surface change to a shipped route — keep
  the diff to swapping one `RosterUploader` for three and adding the
  `entity_kind` label; do not disturb the admin gate or the legacy-route
  contract.
- **Repeated-row provider imports + per-section fencing.** A provider file that
  references facilities not yet created must fence per TE-5, not half-commit —
  lean on E3.1's staged-parent resolution rather than inventing new
  cross-section logic here.
