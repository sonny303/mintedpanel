# E0.10 — Data-Model Integrity Hardening — Constraints, MVD Floors & FK Indexes

## Purpose and Context

The Stage 0 data-model spike (`docs/data-model/spike-2026-07-10-findings.md`,
with the living inventory in `docs/data-model/table-register.md`) found the
schema's spine sound but under-constrained: several UNIQUE constraints contain
nullable columns (so core invariants like "one contract per group×payer×state"
are silently unenforced because Postgres never collides NULLs), the
jurisdiction `state` columns are free text, ~10 foreign keys have no index, and
a few tables allow structurally-meaningless rows (a contract with no party, a
task owned by neither a case nor a provider). E0.10 raises the
**database floor** — the minimum-viable-data (MVD) and integrity guarantees the
redesigned UI will build on — before that UI is written, when the fixes are
nearly free. Every change is additive per AGENTS.md: new `CHECK ... NOT VALID`
constraints then `VALIDATE`, new indexes, new UNIQUE constraints — no renames,
no drops, no column restructuring. This epic does NOT include the provider↔group
M:N change or the `provider_groups` address/contact normalization; those are
separate structural epics gated on the spike's open business decisions.

## Personas Empowered

- P1 Credentialing Manager (Sowmya Seed) — the data she relies on cannot enter a
  structurally-impossible state (a contract with no payer, two "primary"
  facilities, a case whose state is `Texas` in one row and `TX` in another); the
  Fix-it queue's job shrinks because the DB rejects the worst inputs outright.
- P2 Credentialing Coordinator / Specialist — same integrity guarantees on the
  operational write path.
- (Indirectly) developer agents (Claude Code / Devin) — enforced invariants mean
  services can trust the shape of rows they read instead of re-checking.

## Component & Data Constraints

- No new UI surfaces. E0.10 adds NO components; at most, existing service-layer
  error handling gains friendly messages for the new duplicate/not-null
  failures (see Devin section). Component/build rules still bind — see
  [uiux-component-guide.md](./uiux-component-guide.md) and [README.md](./README.md).
- All migrations are additive (AGENTS.md): `CHECK ... NOT VALID` → `VALIDATE
CONSTRAINT`, additive `CREATE INDEX`, additive `CREATE UNIQUE INDEX` /
  `ADD CONSTRAINT ... UNIQUE`. No renames, no drops, no policy weakening.
- Repo-first + hosted parity per `docs/migration-baseline.md`: each change is a
  new file in `supabase/migrations/` AND applied to the hosted project via MCP
  `apply_migration`; `src/integrations/supabase/types.ts` regenerated after DDL.
- The transactional tables this epic constrains (`contracts`, `credential_cases`,
  `state_licenses`, `provider_facility_assignments`, `tasks`, `status_configs`)
  are **not part of the Stage 0 seed universe** — see Dependencies. Verification
  is DB-level against synthetic rows + a hosted-data backfill audit, not the
  E0.0–E0.8 seed fixtures.

## Features

### F0.10.1 — Unique-key integrity: no NULLs inside uniqueness invariants

- **Description:** The invariants "one contract per (group, payer, state)", "one
  facility assignment per (provider, facility)", and "one license per (provider,
  state)" are declared UNIQUE but include nullable FK columns, so Postgres does
  not enforce them (two rows with a NULL `group_id` do not collide). Add
  `CHECK (<col> IS NOT NULL) NOT VALID` on the columns participating in each
  such uniqueness key, then `VALIDATE CONSTRAINT` once the backfill audit
  (BD-1) confirms zero offending rows.
- **Persona:** P1 (duplicate or party-less rows can no longer be created).
- **Benefit hypothesis:** A uniqueness rule that silently doesn't hold is worse
  than none — the app assumes it and breaks subtly. Closing the NULL hole makes
  the declared grain real.
- **Acceptance criteria:**
  - `contracts.group_id` and `contracts.payer_id`, `state_licenses.provider_id`,
    and `provider_facility_assignments.provider_id` / `.facility_id` carry a
    `NOT VALID` NOT-NULL check, validated after the audit.
  - Attempting to insert a row with any of those columns NULL is rejected at the
    DB, not just in the service.
  - The backfill audit (BD-1) result is recorded in this epic's Devin section:
    either "0 offending rows, validated" or a remediation migration in the same
    PR.
  - No existing valid row is affected; no constraint is validated while
    offending rows exist (an un-validated `NOT VALID` check is acceptable
    interim state, explicitly noted).
- **Test/data scenario(s):** DB-level constraint tests (see Devin section /
  proposed TS-25); no Stage 0 seed fixture exists for these tables.

```gherkin
Feature: Contract uniqueness invariant is real
  Scenario: A contract cannot be created without a payer
    Given the contracts NOT-NULL checks are validated
    When a service attempts to insert a contract row with payer_id = NULL
    Then the database rejects the insert
    And two contracts for the same (group, payer, state) cannot coexist
```

### F0.10.2 — State-code format floor

- **Description:** The jurisdiction/state columns are free text, so `TX`,
  `Tx`, `Texas`, and `` are all storable and break equality joins and grouping.
  Add `CHECK (state ~ '^[A-Z]{2}$') NOT VALID` per **in-scope** column — the
  pinned list in TE-2, covering operational jurisdiction fields
  (`credential_cases`, `contracts`, `state_licenses`) plus scalar
  physical-address fields — validated after a normalization audit (BD-2 sets
  the exact allowed set — US-only vs territories). Wildcard matching fields
  (`mso_routing_rules.state`, `sop_templates.state`, where `All` is a valid
  value today) are explicitly OUT of scope (PM decision 2026-07-10; see
  `CLARIFICATIONS_NEEDED.md` [e0.10]).
- **Persona:** P1 (state-scoped views and joins stop fragmenting on casing).
- **Benefit hypothesis:** `state` is a join key across the whole model; an
  unvalidated key silently splits a provider's Texas work across `TX`/`Texas`.
- **Acceptance criteria:**
  - Each in-scope `state` column (TE-2 pinned list) carries the
    two-uppercase-letter `NOT VALID` check, validated after the audit
    confirms/normalizes existing values; wildcard fields carry no check.
  - Lowercase, full-name, or empty state values are rejected at the DB.
  - The allowed-set decision (BD-2) is recorded; if territories/`XX` wildcards
    are permitted, the regex reflects it.
- **Test/data scenario(s):** DB-level constraint tests (proposed TS-25).

### F0.10.3 — Structural-validity checks (no meaningless rows)

- **Description:** Add owner/shape checks that reject rows the model can never
  act on: `tasks` with neither `case_id` nor `provider_id`
  (`CHECK (case_id IS NOT NULL OR provider_id IS NOT NULL)`); a second `is_primary`
  facility per provider (partial unique index
  `(provider_id) WHERE is_primary`); and duplicate status labels within a track
  (`UNIQUE (org_id, track, label)` on `status_configs`). All additive; CHECKs
  land `NOT VALID`, while unique constraints/indexes (which PostgreSQL cannot
  add `NOT VALID`) are audited for existing violations before they are added.
  The MSO routing-rule uniqueness constraint is DEFERRED out of this epic (PM
  decision 2026-07-10) — the resolver intentionally layers `All` wildcards with
  precedence, so the right invariant is a product decision; see
  `CLARIFICATIONS_NEEDED.md` [e0.10].
- **Persona:** P1 / P2 (the action engine and routing can't be fed ambiguous
  input).
- **Benefit hypothesis:** These are the rows that produce "impossible" bugs
  downstream (two primaries, a task attached to nothing, two matching routing
  rules with different answers); rejecting them at the floor removes a class of
  defect.
- **Acceptance criteria:**
  - The three checks/constraints exist and are validated (CHECKs may be
    `NOT VALID` with a recorded audit; uniques are audit-first).
  - A task with neither owner, a second primary facility, and a duplicate
    `(org, track, label)` are each rejected at the DB.
  - Existing valid data is unaffected; any offending live rows are remediated by
    an additive migration in the same PR or recorded as accepted with rationale.
- **Test/data scenario(s):** DB-level constraint tests (proposed TS-25).

### F0.10.4 — Foreign-key index coverage

- **Description:** Add indexes to the ~10 FK columns that lack them
  (`credential_cases.payer_id` / `.group_id` / `.mso_id` / `.assigned_to`,
  `contracts.group_id` / `.payer_id`, `state_licenses.provider_id`,
  `touches.coordinator_id`, `tasks.provider_id`, `status_history.changed_by` —
  final list verified against the live schema in the Devin section). Unindexed
  FKs degrade joins and make ON-DELETE cascades table-scan.
- **Persona:** Developer agents / P1 indirectly (list and detail views that join
  these stay fast as data grows).
- **Benefit hypothesis:** Cheap now, painful to retrofit under load; the
  redesigned UI will lean on exactly these joins.
- **Acceptance criteria:**
  - Every FK column without a covering index gets one additive `CREATE INDEX`
    (single migration).
  - The final column list is verified against the live schema (not assumed) and
    recorded in the Devin section.
  - No functional behavior changes; `npx tsc --noEmit`, lint, and tests stay
    green (no type surface change expected).
- **Test/data scenario(s):** none (non-behavioral); gates only.

### F0.10.5 — Middle-layer coherence with the new floor

- **Description:** Make `src/services/*` (the single write path) agree with the
  hardened DB: tighten the input types that the new NOT-NULLs make required
  (e.g. contract create requires `group_id` + `payer_id`), normalize `state` to
  the enforced format at the service boundary, and translate the new
  unique-violation / check-violation errors into friendly messages instead of
  raw Postgres text. No new endpoints; no frontend hook changes.
- **Persona:** P1 / P2 (a rejected write explains itself).
- **Benefit hypothesis:** The DB is the floor, but the service is where a human
  meets the error; a raw `23505`/`23514` is a dead end, a friendly message is a
  Fix-it.
- **Acceptance criteria:**
  - Service input types reflect the now-required fields (no `string | null`
    where the DB says NOT NULL); `npx tsc --noEmit` stays clean.
  - `state` is normalized (uppercased/trimmed) in the service before insert so
    valid user input isn't rejected on casing alone.
  - New duplicate/not-null/check violations surface as domain errors with
    human messages, consistent with existing service error handling.
  - No component or hook is modified; the browser-direct write path keeps
    working under RLS.
- **Test/data scenario(s):** service-level unit tests; existing gates.

## 5. Technical Considerations & Enablers — Devin section

All claims below are verified against the baseline schema
(`supabase/migrations/20260704210000_baseline_live_schema.sql`) and the table
register, not the spike prose. Column/constraint/index names are the live
identifiers. Everything is additive per AGENTS.md (new `CHECK ... NOT VALID` →
`VALIDATE`, `CREATE INDEX`, `ADD CONSTRAINT ... UNIQUE`); no renames, drops, or
policy weakening. Where a "verify against the live schema" acceptance criterion
exists (F0.10.1, F0.10.4), the authoritative list is pinned here.

### TE-1 — NOT-NULL floor under the uniqueness invariants (F0.10.1)

- Live UNIQUE constraints with a NULL hole:
  `contracts_group_id_payer_id_state_key` on `(group_id, payer_id, state)`,
  `provider_facility_assignments_provider_id_facility_id_key` on
  `(provider_id, facility_id)`, and the license grain
  `uq_state_licenses_provider_state_number` on
  `(provider_id, state, license_number)`. `group_id`, `payer_id`,
  `provider_id`, and `facility_id` are all nullable, so two rows sharing a NULL
  never collide — the invariant is declared but unenforced.
- Enabler: one **per-column** `CHECK (<col> IS NOT NULL) NOT VALID` on
  `contracts.group_id`, `contracts.payer_id`,
  `provider_facility_assignments.provider_id`,
  `provider_facility_assignments.facility_id`, and
  `state_licenses.provider_id`. Per-column (not a single table-level check) so a
  future backfill can `VALIDATE` each independently and the failure message
  names the offending column. `credential_cases`'s key columns
  (`provider_id`, `payer_id`, `state`) are already `NOT NULL` in the baseline —
  no change there.
- Sequencing: the `NOT VALID` checks land in the first migration; the matching
  `VALIDATE CONSTRAINT` statements are gated on the BD-1 audit (TE-7) and may
  ship in the same PR (if the audit returns zero rows) or a follow-up migration.
  An un-validated `NOT VALID` check already blocks all **new** bad inserts, so
  the floor is effective immediately even before validation.

### TE-2 — State-format check: authoritative column set (F0.10.2)

- The spike's "six state columns" is approximate; pinned scalar `state`-type
  columns in the live schema are: `credential_cases.state`, `contracts.state`,
  `state_licenses.state`, `facilities.state`,
  plus `providers.home_state` / `providers.license_state` and
  `provider_groups.billing_state` / `provider_groups.correspondence_state`.
  Decisions the reviewer pins so the builder does not guess:
  - **Exclude** `mso_routing_rules.state` — it is a matching wildcard, not a
    jurisdiction: the admin UI writes `'All'` and the resolver layers
    wildcard rules by precedence, so `^[A-Z]{2}$` would break routing
    (PM-confirmed 2026-07-10; see `CLARIFICATIONS_NEEDED.md` [e0.10]).
  - **Exclude** `launches.state` (table status `dead` in the register) and
    `sop_templates.state` (matching wildcard, not a jurisdiction; `'All'`-style
    values are valid there) — a two-letter check would be wrong for both.
  - `provider_groups.states` is a `text[]`, **not** a scalar — a scalar regex
    does not apply; either add a per-element check
    (`CHECK (states IS NULL OR array(...) ...)`) or leave it out of E0.10 and
    note it. Recommend leaving the array out of this epic and documenting it
    (its shape decision belongs with the group-address normalization epic).
- Enabler: `CHECK (<col> ~ '^[A-Z]{2}$') NOT VALID` per included scalar column.
  Nullable columns (`facilities.state`, `providers.*_state`,
  `provider_groups.*_state`) must allow NULL:
  `CHECK (<col> IS NULL OR <col> ~ '^[A-Z]{2}$')` — the format floor is not a
  presence requirement outside the F0.10.1 keys. The regex encodes the BD-2
  allowed-set decision (TE-7); if territories/`XX` wildcards are permitted the
  pattern widens (e.g. an explicit alternation) but stays `NOT VALID`-first.
- Empty string (`''`) fails `^[A-Z]{2}$` and is thus rejected, which matches the
  acceptance criterion (empty state rejected).

### TE-3 — Structural-validity constraints (F0.10.3)

- `tasks` owner: `CHECK (case_id IS NOT NULL OR provider_id IS NOT NULL)`, added
  `NOT VALID`. Both FKs are nullable today; `provider_documents` already ships
  this exact owner-CHECK shape, so it is a proven pattern in this schema.
- Single primary facility: a partial unique index
  `... ON provider_facility_assignments (provider_id) WHERE is_primary`
  (`is_primary boolean DEFAULT false`). This mirrors the
  `party_capture_links_one_active` partial-unique pattern already in the schema.
- MSO routing uniqueness: **DEFERRED out of E0.10** (PM decision 2026-07-10).
  The resolver intentionally permits layered `All` wildcard rules with
  exact-over-fallback precedence, so a `(org_id, payer_id, state, specialty)`
  UNIQUE neither expresses nor protects the real invariant; the right
  constraint (exact-duplicate-only vs no-overlap vs explicit priority field)
  is an open product decision tracked in `CLARIFICATIONS_NEEDED.md` [e0.10].
  Do not add any constraint to `mso_routing_rules` in this epic.
- **Unique mechanics:** PostgreSQL does not support `UNIQUE ... NOT VALID` —
  `ADD CONSTRAINT ... UNIQUE` and `CREATE UNIQUE INDEX` scan the table and fail
  on existing duplicates. The BD-1 duplicate audits (TE-7) therefore run
  BEFORE these statements, with remediation (or a recorded acceptance) landing
  first if duplicates exist. Only the CHECK constraints use `NOT VALID`.
- Status label uniqueness: `ADD CONSTRAINT ... UNIQUE (org_id, track, label)` on
  `status_configs`. All three columns are `NOT NULL` in the baseline, so no
  `NULLS NOT DISTINCT` is needed here.
- `audit_log.entity_type` CHECK (noted in the spike but NOT a numbered E0.10
  feature): out of scope for E0.10 unless the PM folds it in — the allowed
  entity-type set is not yet enumerated, so constraining it now would be a
  guess. Called out here so it is not silently dropped from the backlog.

### TE-4 — FK index coverage: pinned list (F0.10.4)

- Existing covering indexes on the candidate tables:
  `idx_credential_cases_org_id/_provider_id/_facility_id`,
  `idx_tasks_org_id/_case_id`, `idx_status_history_case_id`,
  `idx_touches_org_id/_case_id`, and the composite
  `uq_state_licenses_provider_state_number (provider_id, state,
license_number)`.
- **Refinement vs the epic's provisional list:** `state_licenses.provider_id`
  is already served by the leading column of that composite unique index, so a
  separate single-column index is redundant — **drop it** from the add list.
- Pinned columns still lacking an index (the F0.10.4 delivery set):
  `credential_cases.payer_id`, `credential_cases.group_id`,
  `credential_cases.mso_id`, `credential_cases.assigned_to`,
  `contracts.group_id`, `contracts.payer_id` (the `contracts` table has **zero**
  indexes today), `touches.coordinator_id`, `tasks.provider_id`,
  `status_history.changed_by`. Optional-but-recommended additions surfaced by
  the audit: `credential_cases.credentialing_status_id` and
  `status_history.contract_id` (both FKs, both unindexed) — include if the PM
  wants full FK coverage; otherwise document as known-thin.
- Single additive migration of `CREATE INDEX` statements; no type-surface
  change, so `types.ts` regen is a no-op for this feature.

### TE-5 — Middle-layer coherence (F0.10.5)

- `src/services/contracts.ts` `ContractInput` **already** types `groupId` and
  `payerId` as required `string` (not `string | null`), so the TE-1 NOT-NULLs
  need no type change there — verify the create payload always sends them. The
  service files on the affected write paths are `contracts.ts`, `cases.ts` /
  `providerCases.ts`, `tasks.ts`, `statusConfigs.ts`, `msos.ts`, and the
  license path in `providers.ts` / `providerProfile.ts`.
- `state` normalization: today services pass `state` through unchanged (see
  `contracts.ts`). Add trim+uppercase at the service boundary (a small shared
  helper in `src/lib/`, e.g. `normalizeStateCode`) before insert/update on the
  constrained columns, so valid user input (`tx`, `TX`) is not rejected on
  casing alone. Pure + unit-testable; no hook/component change.
- Error translation: there is **no** central Postgres-code → friendly-message
  utility today — services either `throw error` raw or `throw new
Error(error.message)`. F0.10.5's "consistent with existing service error
  handling" therefore means introducing a small shared translator (map `23505`
  unique-violation / `23514` check-violation → domain messages) rather than
  matching an existing one. Keep it in `src/lib/` and reuse across the affected
  services; this is a minor net-new surface, not a refactor. No new dependency.
- Explicitly unchanged: no hook (`src/hooks/*`) or component edits, no new
  endpoints; the browser-direct write path keeps working under RLS.

### TE-6 — Migration mechanics, parity & register

- Split into focused additive migrations (one concern each, all in
  `supabase/migrations/`): (a) FK indexes (TE-4), (b) NOT-NULL `NOT VALID`
  checks (TE-1), (c) state-format `NOT VALID` checks (TE-2), (d) structural
  constraints (TE-3; uniques audit-first per TE-3's unique mechanics), (e) the
  gated `VALIDATE CONSTRAINT` statements once BD-1/BD-2 audits pass. Repo-first + hosted parity per `docs/migration-baseline.md`:
  each file is also applied to the hosted project via MCP `apply_migration`.
- `src/integrations/supabase/types.ts` is regenerated after DDL; additive
  constraints/indexes do not change the generated column types, so expect a
  near-empty diff (regen only to stay honest with the baseline rule).
- Table-register upkeep (AGENTS.md): E0.10 adds constraints/indexes but no new
  tables/columns, so the register rows for `contracts`, `credential_cases`,
  `state_licenses`, `provider_facility_assignments`, `tasks`,
  and `status_configs` should have their "MVD gap" /
  "no uniqueness" notes updated to reflect the now-enforced floor in the same
  PR.

### TE-7 — Backfill / normalization audits (BD-1, BD-2) — to record here

- BD-1 (NOT-NULL): before each TE-1 / TE-3 `VALIDATE`, run a count of offending
  live rows per column (e.g. `SELECT count(*) FROM contracts WHERE group_id IS
NULL`, and the analogous task-owner / duplicate-primary / duplicate-label
  probes) via MCP `execute_sql`. For the unique targets the audit runs BEFORE
  the constraint is added (no `NOT VALID` option for uniques — TE-3). Record the result inline in this section as
  "0 offending rows → validated" or attach a remediation migration in the same
  PR. The `reviewfindings` sign-off pattern is the same one E0.7 used for the
  GRANT audit.
- BD-2 (state allowed-set): normalization audit
  (`SELECT DISTINCT state FROM ...` across the TE-2 columns) to size casing/
  full-name/blank cleanup and confirm the US-only vs territories decision before
  the state-format checks are validated. Record the chosen regex here.
- The audits gate the `VALIDATE` step for CHECKs and the creation itself for
  uniques; the `NOT VALID` CHECK constraints and all non-unique indexes are
  unconditional and land first.

- Service-layer unit tests cover `normalizeStateCode` and the error translator

- Gates before merge (README merge gate): `npm run lint`, `npm run test`,
