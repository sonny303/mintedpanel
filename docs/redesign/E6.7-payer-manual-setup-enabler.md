# E6.7 — Payer Manual Setup Enabler + Catalog Sync Retirement

**Backend tech debt + enablement only. Zero frontend UI ships in this epic** —
the only frontend code is the service/hook seam the future "+ Set up payer"
dialog (a separate design→build track) will call.

## Purpose and Context

The PM is retiring the precanned payer-catalog browse: instead of adding
payers from a curated 137-row list, a user **sets up a payer manually** by
filling fields our schema already holds, and it lands in their org's network.
Today there is **no in-app payer creation** — `payers` is global-catalog-only,
member-SELECT-only (org write paths revoked, `20260718120000`); rows are
written solely by the sync script and platform tooling. This epic adds the one
missing write path and retires the sync machinery whose only job was the
precanned pipeline. Full analysis: `payer-catalog-removal-impact.md`.

PM decisions (2026-07-26): manually created payers are **global** (`org_id
NULL` — authored once, template inheritance intact) · **no platform-role
gating anywhere** (two trusted users; this also unlocks the fallback
template) · duplicate handling is guard-only (merges stay platform-side) ·
the quarterly CSV sync retires · no review queue for new rows · delivered as
two PRs (enabler, then cleanup).

## Personas Empowered

- P1 Credentialing Manager (ops hat) — creates the payer they actually work
  with instead of hunting a precanned list.
- P2 Specialist — same path via the future dialog; nothing here is gated.

## Component & Data Constraints

- No UI components. `AGENTS.md` binds: additive migrations only; components →
  hooks → services → Supabase; table-register row updated in the same PR as
  any schema/RPC change; no `any`; named exports.
- Table trace — **read:** `payers`, `org_payer_assignments`, `memberships`;
  **written:** `payers` (INSERT via RPC only), `org_payer_assignments`
  (upsert via RPC), `sop_templates`/`sop_template_versions` (existing RPCs,
  lock check removed). No new tables. No column changes.

## Features

### F6.7.1 — `create_payer` RPC (PR 1)

- **Description:** One additive migration adding a SECURITY DEFINER
  `create_payer` RPC. EXECUTE granted to `authenticated` (revoked from
  `public`/`anon`; `anon` rejected in-body — `author_global_sop` precedent).
  Params: `p_org_id uuid` (caller must be a writer-member), `p_name text`
  (required, non-blank), `p_payer_kind text` (required; CHECK domain
  `commercial|medicare|medicare_advantage|medicaid|medicaid_mco|tricare`),
  `p_states text[]` (required, ≥1, each `^[A-Z]{2}$`), `p_aliases text[]`,
  `p_resolution_id_label text`, `p_resolution_id_expected boolean`,
  `p_delegation_note text` — all optional trailing params nullable. Inserts a
  **global** row (`org_id NULL`, `status 'active'`, `payer_slug NULL`,
  `last_synced_at NULL`) and, in the same transaction, upserts the caller
  org's `org_payer_assignments` row (reactivating an archived one). Returns
  the payer row.
- **User story:** As P1, I create the payer I work with and it is instantly
  in my network — one action, no platform request.
- **Benefit hypothesis:** Unblocks the entire manual-setup redesign with one
  RPC; creating = adding (there is no other reason to create a payer).
- **Acceptance criteria:**
  - Empty/blank name, kind outside the domain, empty `states[]`, or a
    malformed state code each raise a named exception — `states[]` is
    required because `groupPayerAttach`, `payerExpansion`, and the E6.2
    attach-CSV scan all intersect against it; an empty-states payer can
    never attach or generate a case.
  - Duplicate guard in-body: normalized name (lower/trim/collapse
    whitespace) matching any non-retired global row's name **or** alias
    raises `payer_duplicate`; when the match is `status='merged'`, the
    error message names the successor.
  - The payer INSERT and the assignment upsert are one transaction; a
    failure rolls both back.
  - Non-member / non-writer callers and `anon` are rejected in-body.
  - Migration dry-run passes; `docs/data-model/table-register.md` `payers`
    row gains the new writer in the same PR.
- **Test/data scenario(s):** unit-level pgTAP-style assertions are out of
  repo scope; Vitest covers the pure helpers (F6.7.3) and the service maps
  the named errors.

### F6.7.2 — Fallback-template unlock (PR 1)

- **Description:** Reissue `author_global_sop` and
  `publish_sop_template_version` with the `fallback_sop_locked` rejection for
  `authenticated` callers removed — the seeded generic fallback
  (`00000000-0000-4000-a000-00000000e17b`) becomes editable like any global
  SOP. Its structural guards stay: it remains the only payerless global row,
  cannot be archived, and cannot be given a payer/state (the
  `global_sop_match_key_incomplete` rule keeps binding every OTHER global
  SOP).
- **User story:** As P1, I can edit the General Enrollment default template
  from the app — the design's Edit button is real.
- **Benefit hypothesis:** Removes the last platform-only editing carve-out,
  per the PM's no-role-gating decision.
- **Acceptance criteria:** an authenticated user can publish a new version of
  the fallback; archiving it or setting a payer on it still fails; the
  table-register / register notes for the two RPCs are updated in the same
  PR.

### F6.7.3 — Frontend seam only (PR 1)

- **Description:** `createPayer(input): Promise<Payer>` in
  `src/services/payers.ts` (the file's first write path) calling the RPC;
  a mutation hook invalidating payer + assignment caches; pure
  `normalizePayerName` + `findPayerNearMatches(name, payers)` (name/alias)
  in `src/lib/` with Vitest coverage — the future dialog's "use this
  instead" picker consumes them. **No dialog, no route, no rendered UI.**
- **Acceptance criteria:** helpers are pure and tested (normalization rules,
  alias matching, merged-row successor surfacing); the service maps
  `payer_duplicate` to a typed error the UI can branch on.

### F6.7.4 — Catalog sync retirement (PR 2)

- **Description:** Retire `scripts/payer-catalog-sync.mjs` +
  `payer-catalog-sync.d.mts` + `src/lib/payerCatalogSync.test.ts`; mark
  `docs/redesign/data/payer-catalog/README.md` frozen (no longer synced).
  Table register: `payer_slug`, `last_synced_at` → deprecated in place
  (stop-write); `payer_catalog_changes` → dormant. No schema change.
- **Acceptance criteria:** no repo reference to the sync script remains
  outside historical docs; register rows updated.

### F6.7.5 — Stale-metadata stop-render (PR 2)

- **Description:** Stop rendering stored `avg_decision_days`
  (`PayerDetailContent`, reports `SummaryTab`) — it loses its only writer
  when the sync retires. Column stays (additive rule). `TECH-DEBT.md` gains
  two entries: derive decision-days from case outcomes (median
  created→approved); admin merge UI when duplicate volume justifies it.
- **Acceptance criteria:** no UI reads `avgDecisionDays`; both debt entries
  logged.
