## 1. Context — what exists today (verified against the repo)

- **`sop_templates`** (baseline `20260704210000`, lines 378–390) is the only
  SOP store: `id`, `org_id` (**nullable since
  `20260707060000_global_catalog_org_assignment.sql`** — a NULL row is a
  global-catalog SOP, visible to an org only when the org is assigned the
  SOP's `payer_id` via `org_payer_assignments`), match keys `group_id` /
  `state` / `specialty` / `payer_id`, the whole SOP body in
  **`task_definitions jsonb`**, `archived boolean`, `created_at`/`updated_at`.
  **There is no version column, no history table, and `updated_at` is the
  only edit evidence** (plus `audit_log` rows from
  `src/services/templates.ts`).
- **Authoring** is the Admin > Templates 4-step wizard
  (`TemplateWizard.tsx` → `createTemplate`/`updateTemplate`): save is ONE
  write of the full `task_definitions` jsonb. **An edit silently replaces the
  previous content** — today's model is last-write-wins with audit rows as
  the only trail.
- **Resolution** is `src/lib/sopResolver.ts` (**protected — this ADR proposes
  no change to it**): `resolveTemplate(template, provider, group, facility,
{mso}, licenseNumber)` interpolates `{{tokens}}` over
  `template.taskDefinitions` and returns `ResolvedTaskInsert[]`. Template
  _selection_ happens before resolution in `src/lib/pickTemplate.ts` (exact
  payer+state+group, then payer+state; a null-group template counts as
  "exact").
- **Generation** (`create_case_with_tasks` RPC; also the
  `providers.ts` termination-task builder) copies the **resolved** steps into
  **`tasks.sop_content jsonb`** (baseline line 438; RPC lines 572–578 read
  `v_task->'sop_content'`). **No column records which template — let alone
  which version of it — produced a task.** That is the concrete gap this
  spike closes (TE-2): E2.2 wants "what version stamped this task."
- **Type shapes the model must fit** (`src/types/index.ts`):
  `SOPTaskDefinition { title, description?, sortOrder?, dueOffsetDays?,
steps: [{ label, detail?, stepType?, emailTemplate?, dataFields?,
portalKey? }] }`, `SOPStep` (adds `id/order/isCompleted/completedAt/…` on
  the resolved side), `SOPStepType = "draft_email" | "online_form" | "pdf"`.
  `portalKey` on an `online_form` step is the extension fill/close-out join
  (2026-07-08 build) and is carried verbatim, never interpolated.

### Non-negotiable constraints (TE-3)

1. Additive-only migrations — no rename/restructure/drop, ever.
2. SOPs stay keyed to payer/state (+ group/specialty match keys).
3. Syncs/edits **never silently overwrite** — the E1.6
   `payer_catalog_changes` diff-log philosophy applies to SOP content.
4. Generation snapshots the version onto the task (E2.2 traceability).
5. Append-only `touches`/`status_history`/`audit_log` untouched.
6. The global-vs-org SOP pattern (`org_id IS NULL` + payer assignment
   visibility) must survive the chosen model.

## 2. Candidate models

### Model A — Immutable version rows (child table; template = head pointer)

A new `sop_template_versions` child table holds one **immutable** row per
publish; `sop_templates` remains the identity + match-key + head row, and its
`task_definitions` jsonb stays as the **materialized head copy** that all
existing readers keep reading.

| Dimension            | Assessment                                                                                                                                                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Authoring flow       | The wizard edits a working copy as today; **Publish** = insert `sop_template_versions` row (version N+1) + update the head jsonb + bump `current_version`, in one service call. Draft-in-progress needs no schema (wizard state), and E1.7b may later add `status='draft'` version rows without a new table. |
| `sopResolver` impact | **Zero.** Selection (`pickTemplate`) and resolution both keep reading the head `sop_templates.task_definitions`. The resolver is protected and stays untouched — the version id just travels alongside the template the caller already has.                                                                  |
| Task snapshot (E2.2) | Stamp `(sop_template_id, sop_version)` on the task at generation, alongside the existing resolved `sop_content` copy (the human-readable snapshot stays; the reference makes it traceable). Reconstructing "what the SOP said" = read the immutable version row.                                             |
| Storage / complexity | One new table + two additive columns. History cost is one jsonb row per publish — trivial at this scale. Lowest moving-part count of the three.                                                                                                                                                              |
| Migration path       | Purely additive: create the child table, backfill **version 1** from every existing `sop_templates.task_definitions` (an INSERT-only backfill), add `current_version DEFAULT 1`. No existing row is rewritten.                                                                                               |
| Global-vs-org        | The child row carries a denormalized nullable `org_id` mirroring its parent and reuses the parent's SELECT policy shape (own-org OR global-and-payer-assigned). Platform-managed global SOPs version identically.                                                                                            |

### Model B — Copy-on-publish (each publish is a new template row, chain-linked)

Every publish inserts a whole new `sop_templates` row;
`previous_template_id` links the chain; the head is flagged (or inferred as
chain tail).

| Dimension            | Assessment                                                                                                                                                                                                                                                                                                                          |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authoring flow       | Simple mental model ("save-as"), but archived/superseded rows share the live match-key space.                                                                                                                                                                                                                                       |
| `sopResolver` impact | Resolver itself unchanged, but **every selection path must learn to exclude superseded rows** — `pickTemplate`, `listTemplates`, the global-assignment visibility read, and the Admin list would all need an `is_head` filter. A missed filter silently resolves an old SOP — exactly the class of bug the spike exists to prevent. |
| Task snapshot        | `tasks.sop_template_id` alone suffices (each version IS a row) — the cleanest stamp of the three.                                                                                                                                                                                                                                   |
| Storage / complexity | No new table, but the primary table's row count multiplies and the match-key uniqueness story degrades (N rows per logical SOP with identical keys). FKs from `org_payer_assignments`-driven visibility and future E1.6 work would point at a moving head.                                                                          |
| Migration path       | Additive columns only (`previous_template_id`, `is_head`), but the **behavioral** migration (every reader gains a head filter) touches many call sites, including global-catalog reads.                                                                                                                                             |
| Global-vs-org        | Works, but the platform's global rows also multiply, and promote-via-MCP workflows must always target the head.                                                                                                                                                                                                                     |

### Model C — Append-only event/diff log + materialized current view

An `sop_template_events` append-only log (the E1.6 `payer_catalog_changes`
shape applied to content); `sop_templates.task_definitions` is the
materialized fold of the log.

| Dimension            | Assessment                                                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authoring flow       | Every edit is an event — the richest audit trail, and "never silently overwrite" is structural. But the wizard must emit diffs (or whole-body events, which collapses into Model A with extra steps).      |
| `sopResolver` impact | Zero (reads the materialized head), same as A.                                                                                                                                                             |
| Task snapshot        | No natural version identity — E2.2 would stamp an event id or a fold sequence number; reconstructing "the SOP at that point" requires replaying the log. Harder to explain to a reviewer than "version 3". |
| Storage / complexity | Highest: fold discipline, event-schema versioning of the events themselves, and a reconstruction path that must be tested forever.                                                                         |
| Migration path       | Additive, but E1.7b's build cost roughly doubles versus A for no R4-visible benefit.                                                                                                                       |
| Global-vs-org        | Works; same policy mirroring as A.                                                                                                                                                                         |

## 3. Recommendation

**Model A — immutable version rows — is recommended.**

It is the only model that simultaneously: leaves the protected resolver and
every existing reader untouched (head jsonb stays where it is), gives E2.2 a
crisp, human-legible version identity (`template × version N`), makes
"edits never silently overwrite" structural (versions are INSERT-only; the
head update is always accompanied by a preserved version row), keeps the
global-catalog pattern intact, and has the smallest additive migration.

**Runner-up (Model B) trade-off, explicitly:** B wins narrowly on task-stamp
simplicity (a bare FK) but loses badly on selection safety — the epic-wide
invariant "resolution never picks a superseded SOP" would depend on every
present and future reader remembering an `is_head` filter, including the
global-catalog visibility path. That is a standing footgun; A confines
history to a table nothing resolves from. Model C is the most audit-rich but
buys nothing R4 needs at roughly double the E1.7b build cost; its "never
overwrite" property is achieved in A by making version rows immutable.

### Version identity stamped on tasks (the E2.2 contract)

`(sop_template_id uuid, sop_version integer)` — stamped at generation time
next to the existing resolved `sop_content` copy (which remains, unchanged,
as the operational snapshot). Legacy tasks keep NULLs; nothing is backfilled
onto historical tasks.

### Edit semantics (draft vs published)

- The wizard keeps editing a working copy (client state), exactly as today.
- **Publish** is the only write: one service call inserts
  `sop_template_versions (version = current_version + 1)` with an optional
  `change_note`, updates the head `task_definitions`, and bumps
  `current_version`. `writeAudit` records it as today.
- `sop_template_versions` rows are **immutable** (INSERT-only policy — no
  UPDATE/DELETE grants); `archived` stays a head-level flag.
- **Rollback** = publish an old version's content as version N+1 (append,
  never rewrite) — history is preserved and the audit trail stays linear.

### Global-vs-org interaction

Version rows mirror the parent's scoping: `org_id` nullable, SELECT policy =
own-org OR (global AND payer-assigned) — the same disjunct shape as
`20260707060000`. Org users can never write versions of a global SOP
(platform/service-role only), matching the existing catalog rule.

## 4. Migration sketch for E1.7b (sketch only — no files in this epic)

Additive, in one E1.7b migration (repo + hosted):

```
sop_template_versions
  id                uuid PK default gen_random_uuid()
  template_id       uuid NOT NULL → sop_templates(id)
  org_id            uuid NULL            -- denormalized parent scope (RLS)
  version           integer NOT NULL     -- 1, 2, 3…
  name              text NOT NULL        -- head name at publish time
  task_definitions  jsonb NOT NULL       -- the immutable published body
  change_note       text                 -- author's "what changed"
  published_at      timestamptz NOT NULL default now()
  published_by      uuid                 -- auth.uid() at publish
  UNIQUE (template_id, version)
  INDEX (template_id); INDEX (org_id)
  RLS: SELECT mirrors sop_templates (own-org OR global-and-assigned);
       INSERT writer-only own-org; NO UPDATE/DELETE policies or grants
       (immutability is structural).

sop_templates
  + current_version integer NOT NULL DEFAULT 1

tasks
  + sop_template_id uuid NULL → sop_templates(id)
  + sop_version     integer NULL
  (stamped by E2.2 generation; legacy rows stay NULL)

Backfill (INSERT-only): one version-1 row per existing sop_templates row,
copying task_definitions/name; created inside the same migration.
```

`docs/data-model/table-register.md` gains the `sop_template_versions` row in
the E1.7b PR.

## 5. F1.7a.2 — SOP content-shape inventory

What the team's real credentialing SOPs must express, versus what
`SOPTaskDefinition` holds today:

| Content need                                          | Today                                                  | Gap                                                                                                                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordered tasks with ordered steps                      | `sortOrder` / step order                               | none                                                                                                                                                                                         |
| Per-step channel                                      | `stepType: draft_email \| online_form \| pdf`          | **no `fax` / `phone` / `mail` step types** — phone-verification and fax-submission steps are currently mislabeled as generic steps (the touchlog already speaks these channels; SOPs cannot) |
| Portal linkage for fill/close-out                     | `portalKey` on `online_form` steps                     | none (built 2026-07-08)                                                                                                                                                                      |
| Data fields to have on hand                           | `dataFields: {label, token}[]` over the closed catalog | none                                                                                                                                                                                         |
| Expected turnaround ("payer takes ~45 days")          | —                                                      | **missing**; only `dueOffsetDays` (internal due date) exists                                                                                                                                 |
| Follow-up cadence ("call every 14 days after submit") | —                                                      | **missing**; today cadence lives in specialists' heads / stalled-case queries                                                                                                                |
| Required artifacts ("save the confirmation PDF")      | —                                                      | **missing**; PR C's `pdf_filename` write-back has no SOP-side expectation to check against                                                                                                   |
| Email boilerplate                                     | `emailTemplate {subject, body}`                        | none                                                                                                                                                                                         |

**Proposed additive step-shape extension** for E1.7b (rides the existing
jsonb — no migration beyond §4): widen `SOPStepType` with
`fax | phone | mail`, and add optional step fields
`expectedTurnaroundDays?: number`, `followUpEveryDays?: number`,
`requiredArtifacts?: string[]`. All optional → every existing template stays
valid (the same degrade-gracefully pattern `portalKey` used).

Both examples resolve today with zero resolver changes (the new fields are
opaque to `TOKEN_PATTERN` interpolation and ride through verbatim, exactly
like `portalKey`); the two `phone`/`fax` step types and the three cadence /
artifact fields are the only shape gaps, listed above.

**Note the KS/NC pair also demonstrates why version identity must be
per-template, not global:** the same logical procedure diverges per state
(license PSV emphasis, portal, turnaround), so versions belong to the
payer×state template row — which is exactly what Model A gives us.
