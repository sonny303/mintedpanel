# E1.8 — Enrollment Readiness

## Purpose and Context

Before starting a credentialing application, Sowmya runs a pre-flight check
she tracks in a spreadsheet today: is the provider's license current and
board-verified, is CAQH attested recently, does the group have the required
documents on file, does the group have a clinic in the target state. E1.8
replaces that spreadsheet with a derived readiness view over the data captured
in R1–R3, evaluated at the case-key grain (provider × group × payer × state)
against the active payer network targets (E1.5).

Locked PM decisions (2026-07-11): readiness is **enrollment readiness only**
(location-launch readiness is a separate future epic); checks split into a
**group checklist** (W-9, COI, voided check, etc.) and a **provider checklist**
(CAQH, NPI, license, demographics/SSN-last4, DOB, etc.); readiness is
**advisory, never blocking** — case generation proceeds with a visible warning
(soft-warn, consistent with the E1.0/E2.0 decision); CAQH is current when
re-attested within the last **120 days**; gaps are shown as red items worked
directly from the screen — **no automatic task creation**.

## Personas Empowered

- **P1 Credentialing Manager** — reviews readiness before generating cases;
  works the red items.
- **P2 Credentialing Coordinator / Specialist** — closes individual gaps
  (uploads documents, records PSV).
- **P7 Provider** — the subject whose data gaps surface (context persona; no
  R3 UI).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: readiness is **fully derived** — no stored
  readiness flags. Inputs: `state_licenses` (+ E1.3 PSV columns),
  `providers` (CAQH ID, `caqh_last_attested_date`, demographics),
  `provider_group_assignments` (E1.3), `provider_facility_assignments` +
  facilities (state coverage, E1.4), `payer_network_targets` (E1.5),
  `provider_documents` / `group_insurance_policies` (group + provider docs).
- Implementation dependency: the readiness evaluator is a pure module in
  `src/lib/` (unit-tested rule set), fed by services; no Supabase calls
  outside services.
- E1.8 adds **no new tables**; if document-type coverage requires new
  `doc_type` values, that is an additive check-constraint migration + register
  update.

## Features

### F1.8.1 — Readiness matrix (provider × group × payer × state)

- **Description:** The wizard's Scope Review preview becomes the readiness
  screen: one row per provider × group × payer × state derived from active
  payer network targets and group membership, with a ready / gaps summary
  chip per row.
- **Persona:** P1.
- **Benefit hypothesis:** Replaces the spreadsheet; the exact pre-flight list
  Sowmya keeps by hand, always current because it derives from live data.
- **Acceptance criteria:**
  - Rows derive from active `payer_network_targets` × providers assigned to
    the target's group.
  - Each row shows Ready or the count of open gaps; drill-in lists each check.
  - No readiness state is stored; re-evaluation reflects data changes
    immediately (e.g. a license PSV recorded in E1.3 flips the check).
  - Filterable by group, payer, state, and gap type.
- **Test/data scenario(s):** TS-43.

```gherkin
Feature: Derived readiness matrix
  Scenario: License verification flips readiness live
    Given a provider whose NC license is unverified
    And an active BCBS-NC target for their group
    When P2 records the state-board PSV on the license
    Then the readiness row's license check turns green without any manual update
```

### F1.8.2 — Provider checklist and group checklist

- **Description:** Checks are grouped by owner. **Provider checklist:** state
  license exists for the target state, license not expired, license
  PSV-verified, CAQH ID present, CAQH attested within 120 days, NPI present,
  core demographics complete (DOB, SSN-last4, home address), malpractice/COI
  current. **Group checklist:** group has ≥ 1 facility in the target state,
  W-9 on file, group COI current, voided check on file.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Mirrors how the team actually works — some gaps are
  chased with the provider, others with the practice office; grouping by owner
  makes the follow-up obvious.
- **Acceptance criteria:**
  - Each check shows pass/fail with the underlying value (e.g. attestation
    date) and a link to the screen where it is fixed.
  - Group checks evaluate once per group × state and repeat across that
    group's provider rows without re-computation.
  - CAQH current = `caqh_last_attested_date` within 120 days.
  - Full SSN never appears anywhere in readiness (ssn_last4 presence only).
- **Test/data scenario(s):** TS-43, TS-44.

```gherkin
Feature: Group vs provider checklist split
  Scenario: Group missing a state facility
    Given Group 2 has an active BCBS-NC target but no NC facility
    When P1 opens readiness for a Group 2 provider
    Then the group checklist shows "No NC facility" as a red item
    And the provider checklist is evaluated independently
```

### F1.8.3 — Advisory red items, worked from the screen

- **Description:** Gaps render as red items with fix-here links; readiness
  never blocks anything. When R4 case generation arrives, generating against a
  row with open gaps shows a visible warning and proceeds (soft-warn). No
  automatic task/to-do creation.
- **Persona:** P1.
- **Benefit hypothesis:** Deadlines beat completeness (e.g. CAQH lapsed but
  payer deadline is tomorrow) — the team must always be able to proceed with
  eyes open.
- **Acceptance criteria:**
  - No check ever disables a button or gates a save.
  - Each red item links to the exact surface that fixes it (license editor,
    provider form, facility section, documents).
  - No tasks are auto-created from gaps.
  - The soft-warn contract for E2.0 is documented in this epic (interface:
    readiness summary for a case key), not implemented here.
- **Test/data scenario(s):** TS-44.

```gherkin
Feature: Readiness is advisory
  Scenario: Lapsed CAQH does not block work
    Given a provider whose CAQH attestation is 130 days old
    When P1 views the readiness row
    Then CAQH shows as a red item with the attestation date
    And no action anywhere is disabled by it
```

## Dependencies

- E1.3 roster + PSV columns; E1.4 assignments (state coverage via facilities);
  E1.5 `payer_network_targets` (row source); E1.6 catalog metadata.
- `provider_documents` / `group_insurance_policies` for document checks
  (existing tables; possible additive `doc_type` values).
- Consumed by E2.0 case-generation preview (soft-warn interface).

## Out of Scope / Non-Goals

- Location-launch readiness (separate future epic — PM decision).
- Blocking/gating case generation (advisory only).
- Automatic task creation from gaps.
- Expiration forecasting / renewal clocks (R9 Expiration Radar reads the same
  inputs later).

## 5. Technical Considerations & Enablers

_Reviewer-owned (independent review per REVIEW-HANDOFF). Every claim verified
against the baseline schema (`20260704210000_baseline_live_schema.sql`), the
E0.10 migrations, `docs/data-model/table-register.md`, `seed-universe.md`,
`CLARIFICATIONS_NEEDED.md` [stage-3], the E1.0–E1.6 epics, and the live
services/hooks/types on 2026-07-12._

- **TE-1 — Zero new storage, and build ordering.** E1.8 ships **no migration,
  no new table, no stored readiness flag, and no separately cached readiness
  summary** (the E1.0 TE-5 rule). Confirmations that gate the claim: every
  provider-checklist input already exists on `providers` (baseline lines
  325–376: `npi`, `caqh_id`, `caqh_last_attested_date`, `date_of_birth`,
  `ssn_last4`, `home_street/city/state/zip`, `malpractice_coverage_end`);
  `state_licenses` exists (lines 392–403) but its PSV columns
  (`verified_status` etc.) are **E1.3 §5 TE-2 deliverables**;
  `provider_group_assignments` is likewise E1.3's additive join table; and
  `payer_network_targets` is **E1.5's** additive table (`status
active|archived`, unique `(group_id, payer_id, state)`). Hard build order:
  **E1.3 and E1.5 must merge before E1.8**; E1.2 (facility state) is R1.
  The epic's "possible additive `doc_type` values" hedge is **unnecessary
  for the locked checklist** — the `provider_documents` `doc_type` CHECK
  (baseline line 820) already contains `w9`, `coi`, and `voided_check`.
- **TE-2 — Pure evaluator module `src/lib/enrollmentReadiness.ts` (+ test).**
  All readiness logic is one pure, truth-table-tested module — the
  `src/lib/clientProgress.ts` / `src/lib/launchReadiness.ts` precedent
  (derived, never stored). NB: `launchReadiness.ts` already exports
  `ReadinessInput`/`LaunchReadiness`; all new names are enrollment-prefixed.
  Inject `now: Date` so the 120-day CAQH boundary (119/120/121), license
  expiry, and COI expiry are deterministic under test. Exact predicates:
  - **Provider checklist (per provider × target state):** license row exists
    for the state; `expiration_date >= today` (null expiry fails); PSV
    `verified_status = 'verified'` (E1.3 column); `caqh_id` present;
    `caqh_last_attested_date` within 120 days (null fails); `npi` present;
    demographics presence — `date_of_birth`, `ssn_last4`,
    `home_street/city/state/zip` (presence only, see TE-5); malpractice
    current — `malpractice_coverage_end >= today`.
  - **Group checklist (per group × state, evaluated once and shared across
    that group's provider rows — memoize by `groupId:state` per F1.8.2):**
    ≥1 **active** (`is_active = true`) `facilities` row with `group_id` =
    target group and `state` = target state (soft-deleted facilities must
    not satisfy coverage, consistent with E1.2 F1.2.1); group COI current —
    a `group_insurance_policies` row (`insurance_type =
'professional_liability'`) with `policy_end_date >= today`; W-9 on file
    and voided check on file — `provider_documents` group-owned rows
    (`doc_type` `w9` / `voided_check`), **subject to redline 1 below** (the
    table is dormant with no writer).
  - Gap types are a closed union (`EnrollmentReadinessCheckKey`) so the
    F1.8.1 gap-type filter and F1.8.3 fix-here link map are exhaustive
    (an exhaustive `Record` keyed by the union, mirroring the
    `touchOutcomes.ts` `OUTCOMES_BY_CHANNEL` idiom).
- **TE-3 — The E2.0 soft-warn contract (documented here, consumed there).**
  Export a **stable named type** from the module:
  `EnrollmentReadinessSummary` — `{ providerId, groupId, payerId, state,
ready: boolean, openGapCount: number, checks: EnrollmentReadinessCheck[] }`
  where `EnrollmentReadinessCheck` = `{ key, owner: "provider" | "group",
status: "pass" | "gap", detail?: string | null }` (detail carries the
  underlying value, e.g. the attestation date). The entry point
  `evaluateEnrollmentReadiness(inputs, now)` returns one summary per case
  key. E2.0's generation preview imports the type and re-runs the evaluator
  over the same cached inputs to render its soft warning — E1.8 implements
  nothing generation-side; renaming/removing these exports later is a
  breaking cross-epic change and must not happen silently.
- **TE-4 — Row derivation (the matrix).** Rows = active
  `payer_network_targets` × the target group's members via
  `provider_group_assignments`, excluding `status = 'terminated'` providers
  (E1.3 soft delete). Archived targets never produce rows (E1.5 F1.5.3).
  One in-memory join in the pure module over batched org-wide reads — never
  a per-row query. Re-evaluation is render-time over the standard TanStack
  caches, so an E1.3 PSV write or facility edit flips the row on the
  existing invalidations (TS-43's "no manual update").
- **TE-5 — Reads, PHI boundary, and the table trace.** All reads are
  browser-RLS under `requireActiveOrg()` through the standard
  component → hook → service → `externalClient` layering; **no route or
  component touches Supabase**. Specifics:
  - **Providers:** a purpose-built narrow projection (the
    `src/services/clientProgress.ts` precedent — its header comment says
    exactly why: select an explicit PHI-safe column set instead of widening
    the shared list projection; no broad `select("*")` provider query, per
    E1.0 §5 TE-6).
    `PROVIDER_LIST_COLUMNS` lacks `malpractice_coverage_end`,
    `date_of_birth`, `ssn_last4`, and home-address columns by design. The
    readiness service selects only what the checks need and **folds PHI to
    presence booleans at the service boundary** (`hasDateOfBirth`,
    `hasSsnLast4`, `hasHomeAddress`) so raw DOB/address values never enter
    the query cache or the page; `malpractice_coverage_end` and
    `caqh_last_attested_date` pass through as dates (displayed per F1.8.2).
    Full SSN never exists anywhere (AGENTS.md; `ssn_last4` presence only).
  - **Licenses:** extend the existing org-wide read `getRosterAux()`
    (`src/services/reports.ts`, key `queryKeys.rosterAux`) with the E1.3
    `verified_status` column rather than adding a duplicate org-wide
    licenses read; the per-provider `stateLicenses` key stays untouched.
  - **Facilities/groups/payers/targets:** reuse `useFacilities`,
    `useProviderGroups`, the payers read (names only), and E1.5's
    targets hook + query key (do not mint a second).
  - **Documents:** new **read-only** service functions for the org's
    group-owned `provider_documents` metadata rows (never `file_path`
    contents) and an org-wide `group_insurance_policies` read (the existing
    `listGroupInsurancePolicies` is per-group). New `queryKeys` entries for
    both; snake↔camel via `camelizeRow` at the boundary.
  - **Table trace:** reads `payer_network_targets`,
    `provider_group_assignments`, `providers`, `state_licenses`,
    `facilities`, `provider_groups`, `payers`, `group_insurance_policies`,
    `provider_documents`. **Writes: none** — E1.8 itself mutates nothing,
    so no `audit_log` rows originate here; every fix-here surface (E1.3
    license editor, provider form, E1.2 facility section, `InsurancePanel`)
    already owns its own write + `writeAudit` path. Reconciled against
    `docs/data-model/table-register.md`.
- **TE-6 — RLS, grants, and the dormant-table wake.** All inputs have
  org-scoped RLS in the baseline; no new policy or grant is required for a
  derived read surface. Two notes for the build PR that first reads
  `provider_documents`: (a) the baseline still carries a leftover broad
  `GRANT ... TO anon` on it (lines 1157–1158) — RLS denies anon in practice
  (policies are `TO authenticated`), but ship the small additive revoke
  migration mirroring `20260710120000_stage0_grant_hardening.sql` as
  defense-in-depth, and (b) update the table's register row from
  "dormant — decide" to its new read-consumer status in the same PR
  (AGENTS.md register rule).
- **TE-7 — Wizard integration (Scope Review goes live).** F1.8.1 activates
  E1.0's disabled **Scope Review** preview in the ordered section registry
  of `src/routes/onboarding.wizard.tsx`; feature components live under
  `src/components/onboarding/` (or a `readiness/` module) — never in `ui/`
  or `layout/`. Because readiness is advisory it has **no completion
  state**: recommend excluding Scope Review from
  `getNextIncompleteSection`'s ordering and rendering an informational
  "N of M rows ready" count instead of the Not started/In progress/Complete
  chip set — otherwise the E1.0 "Next:" CTA points at it forever (PM
  question 2). No stored wizard flags of any kind (E1.0 TE-3).
- **TE-8 — UI composition and accessibility.** Matrix = hand-rolled table
  markup or row-card list (house convention; no generic DataTable), inside
  shadowless white cards, token border `#E8E5E0` 1px, panel radius. The
  Ready/gaps chip and per-check pass/fail use the conformed `StatusPill`
  with a text label — **color is never the sole signal** on red items.
  Filters (group / payer / state / gap type) compose from
  `DropdownMenuCheckboxItem` per the **shared multi-select enabler
  established by the E1.1/E1.2/E1.3 reviews** — reuse that one composition
  and log/extend its `DESIGN-DEBT.md` row in the build PR; never an
  epic-local one-off (no multi-select/combobox/popover primitive exists in
  `src/components/ui/`). Drill-in uses the existing `collapsible` or
  `dialog` primitive. Fix-here links are real `Link`s (object-form
  navigation) with descriptive text; keyboard focus visible throughout;
  label+control forms only; usable at 1280px and 1024px.
- **TE-9 — Advisory enforcement is testable, not aspirational.** No check
  ever disables a control, gates a save, or creates a task/touch/case.
  Codify it: the module exports no "blocked" concept, the UI renders no
  disabled state from readiness, and the TS-44 e2e asserts a red-item row
  leaves every action enabled and creates zero `tasks` rows. The append-only
  spine (`touches`/`status_history`/`audit_log`) is untouched by this epic.
- **TE-10 — Verification gates.** Unit truth tables for every predicate in
  `enrollmentReadiness.ts` (incl. the 120-day boundary at 119/120/121 days,
  null-input rows, terminated-provider exclusion, archived-target
  exclusion, and the group×state memoization sharing); e2e through the
  existing mock harness for **TS-43** (PSV write flips the license check
  with no manual update; assert no readiness write occurs) and **TS-44**
  (missing NC facility as a group red item + 130-day CAQH red item, nothing
  blocked, no task created). Must pass `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`, and the touched Playwright
  specs.
- **Likely tech debt to contain.**
  - `providers.malpractice_*` is a register-flagged sprawl target (planned
    `provider_insurance_policies` child). Isolate the malpractice read
    behind the TE-5 service projection so the future child-table swap
    repoints one boundary; do **not** introduce the child table here.
  - Waking dormant `provider_documents` as a read source without a write
    surface (redline 1) leaves a permanently-red pair of checks unless the
    PM picks an option; whatever the answer, keep it out of the pure
    module's contract until decided.
  - `license_type = 'compact'` semantics (does one row cover member
    states?) — default is per-state rows (matches the existing unique
    `(provider_id, state, license_number)` grain); PM question 3.
  - The all-org multi-table read joined in memory is fine at R3 scale
    (tens of providers × a few targets); if a future org breaks that,
    move aggregation server-side rather than caching readiness.

### Reviewer redlines (independent review per REVIEW-HANDOFF, 2026-07-12)

1. **blocker** — F1.8.2's "W-9 on file" / "voided check on file" and
   F1.8.3's fix-here links have **no data writer and no destination**:
   `provider_documents` is register-flagged "dormant — decide" with zero
   application code (`docs/data-model/table-register.md` line 77; repo grep
   hits only generated `types.ts`), `file_path` is `NOT NULL` (baseline
   lines 253–266) so even a metadata-only row needs a path decision, no
   Supabase Storage integration exists anywhere in `src/`, and E1.0
   explicitly scoped out "COI/document uploads". As written the two checks
   ship permanently red with a dead link. Resolution is a product call —
   PM question 1. (Group COI is NOT affected: `group_insurance_policies` +
   `src/components/settings/InsurancePanel.tsx` already exist.)
2. **should-fix** — the Component & Data Constraints input list names
   `provider_facility_assignments` "+ facilities (state coverage, E1.4)",
   but **no locked check consumes provider-facility assignments**: the
   [stage-3] group check is group-level state coverage via
   `facilities.group_id` + `facilities.state` — an **E1.2** deliverable
   (E1.2 §5 TE-5 says so verbatim). Drop the E1.4/assignments input, or if
   a "provider practices at a location in the target state" check is
   intended, that is a new requirement needing explicit PM sign-off.
3. **should-fix** — the "possible additive `doc_type` values" migration
   hedge is unnecessary: `w9`, `coi`, and `voided_check` are already in the
   `provider_documents_doc_type_check` CHECK (baseline line 820). No
   migration exists in this epic's honest scope; remove the hedge so the
   build doesn't ship a speculative constraint change.
4. **should-fix** — the epic names `providers` demographics + malpractice
   as inputs without flagging the PHI boundary: `PROVIDER_LIST_COLUMNS`
   (`src/services/providers.ts` lines 73–74) deliberately excludes
   `malpractice_*`, `date_of_birth`, `ssn_last4`, and home-address columns.
   TE-5 now pins the required purpose-built narrow projection
   (`src/services/clientProgress.ts` precedent) with presence-boolean
   folding at the service boundary — the build must not widen the shared
   projection or `select("*")`.
5. **nit** — module/type naming must be enrollment-prefixed:
   `src/lib/launchReadiness.ts` already exports
   `launchReadiness`/`ReadinessInput`/`LaunchReadiness`, and the PM
   decision explicitly splits enrollment vs location-launch readiness.
6. **nit** — the Dependencies line "E1.6 catalog metadata" is only
   transitive (via E1.5's curated attach); readiness reads payer **names**
   for display and consumes no E1.6 catalog column. Listing it as direct
   overstates the ordering constraint.
