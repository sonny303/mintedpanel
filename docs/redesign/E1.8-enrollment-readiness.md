# E1.8 — Enrollment Readiness

## Purpose and Context

Before starting a credentialing application, Sowmya runs a pre-flight check
she tracks in a spreadsheet today: is the provider's license current and
board-verified, is CAQH attested recently, does the group have the required
documents on file, does the group have a clinic in the target state. E1.8
replaces that spreadsheet with a derived readiness view over the data captured
in R1–R3, evaluated at the case-key grain (provider × group × payer × state)
against the active payer network targets (E1.5).

Locked PM decisions (2026-07-11): readiness is **enrollment readiness only**
(location-launch readiness is a separate future epic); checks split into a
**group checklist** (W-9, COI, voided check, etc.) and a **provider checklist**
(CAQH, NPI, license, demographics/SSN-last4, DOB, etc.); readiness is
**advisory, never blocking** — case generation proceeds with a visible warning
(soft-warn, consistent with the E1.0/E2.0 decision); CAQH is current when
re-attested within the last **120 days**; gaps are shown as red items worked
directly from the screen — **no automatic task creation**.

## Personas Empowered

- **P1 Credentialing Manager** — reviews readiness before generating cases;
  works the red items.
- **P2 Credentialing Coordinator / Specialist** — closes individual gaps
  (uploads documents, records PSV).
- **P7 Provider** — the subject whose data gaps surface (context persona; no
  R3 UI).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: readiness is **fully derived** — no stored
  readiness flags. Inputs: `state_licenses` (+ E1.3 PSV columns),
  `providers` (CAQH ID, `caqh_last_attested_date`, demographics),
  `provider_group_assignments` (E1.3), `provider_facility_assignments` +
  facilities (state coverage, E1.4), `payer_network_targets` (E1.5),
  `provider_documents` / `group_insurance_policies` (group + provider docs).
- Implementation dependency: the readiness evaluator is a pure module in
  `src/lib/` (unit-tested rule set), fed by services; no Supabase calls
  outside services.
- E1.8 adds **no new tables**; if document-type coverage requires new
  `doc_type` values, that is an additive check-constraint migration + register
  update.

## Features

### F1.8.1 — Readiness matrix (provider × group × payer × state)

- **Description:** The wizard's Scope Review preview becomes the readiness
  screen: one row per provider × group × payer × state derived from active
  payer network targets and group membership, with a ready / gaps summary
  chip per row.
- **Persona:** P1.
- **Benefit hypothesis:** Replaces the spreadsheet; the exact pre-flight list
  Sowmya keeps by hand, always current because it derives from live data.
- **Acceptance criteria:**
  - Rows derive from active `payer_network_targets` × providers assigned to
    the target's group.
  - Each row shows Ready or the count of open gaps; drill-in lists each check.
  - No readiness state is stored; re-evaluation reflects data changes
    immediately (e.g. a license PSV recorded in E1.3 flips the check).
  - Filterable by group, payer, state, and gap type.
- **Test/data scenario(s):** TS-43.

```gherkin
Feature: Derived readiness matrix
  Scenario: License verification flips readiness live
    Given a provider whose NC license is unverified
    And an active BCBS-NC target for their group
    When P2 records the state-board PSV on the license
    Then the readiness row's license check turns green without any manual update
```

### F1.8.2 — Provider checklist and group checklist

- **Description:** Checks are grouped by owner. **Provider checklist:** state
  license exists for the target state, license not expired, license
  PSV-verified, CAQH ID present, CAQH attested within 120 days, NPI present,
  core demographics complete (DOB, SSN-last4, home address), malpractice/COI
  current. **Group checklist:** group has ≥ 1 facility in the target state,
  W-9 on file, group COI current, voided check on file.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Mirrors how the team actually works — some gaps are
  chased with the provider, others with the practice office; grouping by owner
  makes the follow-up obvious.
- **Acceptance criteria:**
  - Each check shows pass/fail with the underlying value (e.g. attestation
    date) and a link to the screen where it is fixed.
  - Group checks evaluate once per group × state and repeat across that
    group's provider rows without re-computation.
  - CAQH current = `caqh_last_attested_date` within 120 days.
  - Full SSN never appears anywhere in readiness (ssn_last4 presence only).
- **Test/data scenario(s):** TS-43, TS-44.

```gherkin
Feature: Group vs provider checklist split
  Scenario: Group missing a state facility
    Given Group 2 has an active BCBS-NC target but no NC facility
    When P1 opens readiness for a Group 2 provider
    Then the group checklist shows "No NC facility" as a red item
    And the provider checklist is evaluated independently
```

### F1.8.3 — Advisory red items, worked from the screen

- **Description:** Gaps render as red items with fix-here links; readiness
  never blocks anything. When R4 case generation arrives, generating against a
  row with open gaps shows a visible warning and proceeds (soft-warn). No
  automatic task/to-do creation.
- **Persona:** P1.
- **Benefit hypothesis:** Deadlines beat completeness (e.g. CAQH lapsed but
  payer deadline is tomorrow) — the team must always be able to proceed with
  eyes open.
- **Acceptance criteria:**
  - No check ever disables a button or gates a save.
  - Each red item links to the exact surface that fixes it (license editor,
    provider form, facility section, documents).
  - No tasks are auto-created from gaps.
  - The soft-warn contract for E2.0 is documented in this epic (interface:
    readiness summary for a case key), not implemented here.
- **Test/data scenario(s):** TS-44.

```gherkin
Feature: Readiness is advisory
  Scenario: Lapsed CAQH does not block work
    Given a provider whose CAQH attestation is 130 days old
    When P1 views the readiness row
    Then CAQH shows as a red item with the attestation date
    And no action anywhere is disabled by it
```

## Scenario/Seed Data Mapping

- TS-43 — PSV flip drives readiness (Outer Banks provider, unverified → PSV
  recorded → check green).
- TS-44 — Group/state gap + advisory behavior (Group 2 targeting NC without an

## Dependencies

- E1.3 roster + PSV columns; E1.4 assignments (state coverage via facilities);
  E1.5 `payer_network_targets` (row source); E1.6 catalog metadata.
- `provider_documents` / `group_insurance_policies` for document checks
  (existing tables; possible additive `doc_type` values).
- Consumed by E2.0 case-generation preview (soft-warn interface).

## Out of Scope / Non-Goals

- Location-launch readiness (separate future epic — PM decision).
- Blocking/gating case generation (advisory only).
- Automatic task creation from gaps.
- Expiration forecasting / renewal clocks (R9 Expiration Radar reads the same
  inputs later).

## 5. Technical Considerations & Enablers

_Reviewer-owned (Devin). Verified 2026-07-12 against the baseline schema
(`20260704210000_baseline_live_schema.sql`), the E1.3 additive migrations (PSV
columns on `state_licenses`, `provider_group_assignments`), the
`docs/data-model/table-register.md` rows, and the existing derived-readiness
precedents (`src/lib/launchReadiness.ts`, `src/lib/clientProgress.ts`). E1.8 is
a pure derivation over data other epics already persist — no schema change is
required._

- **TE-1 — Fully derived, in a pure `src/lib` evaluator; nothing stored.** Add
  a pure, unit-tested module (working name `src/lib/enrollmentReadiness.ts` +
  `enrollmentReadiness.test.ts`) that takes typed inputs and returns the
  per-row check results — mirror the existing `launchReadiness.ts` /
  `clientProgress.ts` pattern (typed input interfaces, no Supabase, no clock
  reads baked in — pass "today" in). **Name it `enrollmentReadiness`, NOT
  `readiness`:** `src/lib/launchReadiness.ts` already exists for
  _location-launch_ readiness, which this epic explicitly scopes out (Purpose /
  Non-Goals). Keep the two modules distinct so the location-launch epic can
  reuse its own without collision.
- **TE-2 — Row source & grain (no new table).** Rows derive from active
  `payer_network_targets` (E1.5 — grain `group × payer × state`) joined to the
  providers in the target's group via `provider_group_assignments` (E1.3),
  yielding the **`provider × group × payer × state`** grain — exactly the E2.x
  case key. No readiness row, flag, or summary is persisted (F1.8.1); the
  matrix is recomputed on read. Assemble the inputs in `src/services/` (a new
  read module, e.g. `src/services/enrollmentReadiness.ts`, or reuse
  `reporting.ts`'s cross-cut read style) → a `src/hooks/` wrapper → the pure
  evaluator. Components never call Supabase; org-scoped RLS on every source
  table scopes the reads (no cross-org path here, unlike the reporting
  surfaces).
- **TE-3 — All inputs already exist; verified column-by-column.** No column is
  missing:
  - `providers` — `caqh_id`, `caqh_last_attested_date`, `npi`,
    `date_of_birth`, `ssn_last4`, `home_street/city/state/zip`,
    `malpractice_carrier`/`malpractice_coverage_end` (all present in baseline).
  - `state_licenses` — `state`, `expiration_date`, plus the **E1.3 additive PSV
    columns** `verified_status` (`unverified|verified|failed`), `verified_at`,
    `verified_by`, `verification_source_url` (already `reviewed: true` in E1.3
    §5; ships before this epic).
  - `provider_group_assignments` (E1.3), `provider_facility_assignments`
    (baseline; already carries `start_date` + `is_primary`) + `facilities`
    (`group_id`, `state`) for the "group has ≥ 1 facility in the target state"
    check (E1.4 coverage).
  - `payer_network_targets` (E1.5 additive; the row source).
  - `provider_documents` + `group_insurance_policies` for the document /
    insurance checks.
- **TE-4 — No `doc_type` migration is needed (corrects the epic's speculative
  note).** The Component & Data Constraints hedge ("if document-type coverage
  requires new `doc_type` values") does not fire for the checks as specced:
  `provider_documents` already carries a CHECK constraint whose allowed values
  include `'w9'`, `'coi'`, `'voided_check'`, `'state_license'`, `'dea'`,
  `'diploma'`, `'board_cert'`, `'filled_form'`, `'other'`
  (`provider_documents_doc_type_check`, baseline). The group checklist (W-9,
  COI, voided check) and the provider document checks map straight onto
  existing values — **build against them, add no migration.** Only a genuinely
  new document type (none is required here) would need an additive CHECK
  migration + table-register update.
- **TE-5 — Documents/insurance surface is a real dependency + tech-debt to
  contain (should-fix).** `provider_documents` is a **fully-built but dormant**
  table — the register marks it `dormant — decide` with **zero application code
  touching it**, and `group_insurance_policies` has only two touches. There is
  no service/hook/UI for either today. Two consequences the build must handle:
  (a) readiness needs a new **read** service over these tables (presence +
  `expiration_date` / `policy_end_date`), which is straightforward and
  in-scope; (b) F1.8.3's "each red item links to the exact surface that fixes
  it" has **no existing fix-here target for document/COI gaps** (no upload or
  group-insurance surface exists in R1–R3). The read-only readiness matrix can
  ship and evaluate document presence without that surface, but the fix-here
  link for document gaps should degrade gracefully (link to the owning
  provider/group screen) until a documents surface lands. Recorded as an open
  question for the PM below — not invented scope.
- **TE-6 — Check semantics are pure date/enum math (drive the unit suite).**
  Evaluate against a passed-in "today" (never `new Date()` inside the module):
  license present = a `state_licenses` row for the target state; not expired =
  `expiration_date >= today`; **verified** = `verified_status = 'verified'`;
  CAQH current = `caqh_last_attested_date` within **120 days** of today (the
  locked window); NPI present; demographics complete = `date_of_birth` +
  `ssn_last4` + home-address fields present; malpractice/COI current =
  `malpractice_coverage_end >= today` (provider) and
  `group_insurance_policies.policy_end_date >= today` or a current `coi`
  document (group); group state coverage = ≥ 1 `facilities` row with
  `group_id = target.group_id AND state = target.state`. Compare date-only
  values to avoid timezone/day-boundary drift.
- **TE-7 — Group checks computed once per `(group, state)`, reused across
  rows.** F1.8.2 requires group checks not to re-compute per provider row. The
  pure evaluator should return group-level results keyed by `(group_id, state)`
  and fan them out across that group's provider rows — a memoized sub-result,
  not a per-row recomputation.
- **TE-8 — UI activates the E1.0 "Scope Review" preview; all from the current
  inventory.** F1.8.1 turns the E1.0 disabled **Scope Review** wizard section
  (final Sidebar IA v2 name) into the live readiness matrix. Build from the
  approved inventory (`uiux-component-guide.md`): `table` primitive with custom
  cell markup for the ready/gaps status chip (`badge`, `rounded-full`,
  status/destructive tint only — red items use the destructive token, no
  decorative color); `collapsible` (already available) for per-row drill-in to
  the individual checks; `select` for the group/payer/state/gap-type filters.
  No new shadcn primitive is strictly required (drill-in via `collapsible`
  avoids needing `accordion`); if a build chooses `accordion`, add it via the
  shadcn generator into `src/components/ui/` in its own commit and log it, per
  the guide. **No `src/components/layout/*` or protected-file changes** — this
  epic does not touch the shell.
- **TE-9 — SSN/PHI safety (reinforces the AGENTS.md rule).** The demographics
  check reads **`ssn_last4` presence only**; a full SSN is never stored
  (baseline stores `ssn_last4` only) and must never appear in the matrix,
  drill-in, filters, logs, or any export (F1.8.2 AC). No sensitive value is
  rendered — checks show pass/fail plus non-sensitive underlying values
  (attestation date, expiration date), never the SSN itself.
- **TE-10 — E2.0 soft-warn interface (documented here, not built).** Per F1.8.3
  and the Non-Goals, define — but do not implement — the case-key readiness
  summary that E2.x case-generation will consume, e.g. a pure
  `readinessForCaseKey({ providerId, groupId, payerId, state, today, … }) →
{ ready: boolean; openGaps: ReadinessGap[] }` exported from the same module.
  Readiness is **advisory only**: no check disables a button or gates a save
  anywhere (F1.8.3 AC); the soft-warn lives in E2.0's generation preview, which
  reads this summary. No automatic task/`touches`/`status_history` writes from
  gaps.
- **TE-11 — Build-order dependency (sequencing gate).** E1.8 is the last R3
  epic and reads its siblings' outputs: E1.3 (`provider_group_assignments`,
  PSV columns — `reviewed`), E1.6 (catalog metadata — `reviewed`), **E1.4**
  (`provider_facility_assignments` state coverage) and **E1.5**
  (`payer_network_targets`, the row source) — the latter two are the direct row
  and state-coverage inputs, so **E1.4 and E1.5 must merge to `redesign` before
  E1.8 builds.** No contradiction with the neighbors — the grains line up with
  E1.5's `(group, payer, state)` target and the E2.x case key.
- **TE-12 — Verification gates.** Cover **TS-43** (PSV recorded → the license
  check flips green on re-read with nothing stored) and **TS-44** (Shelby
  Group 2 active BCBS-NC target with no NC facility → group "No NC facility" red
  item; 130-day-stale CAQH → red item, and nothing is blocked or auto-tasked)
  from `seed-universe.md`. The **pure evaluator unit suite is the primary
  coverage** (like `launchReadiness.test.ts`): boundary cases at 119/120/121
  days, `expiration_date` on/just-past today, missing-demographics permutations,
  and the group-check dedupe. Add e2e over the readiness matrix surface. Must
  pass `npm run lint`, `npx tsc --noEmit`, `npm run test`,
  `npx prettier --check .`, and any touched specs.

### Likely tech debt / risk to contain

- **Dormant document/insurance tables (TE-5).** Readiness is the first consumer
  of `provider_documents` and only the second of `group_insurance_policies`. A
  clean read service is easy; the risk is the **fix-here link target** for
  document gaps, which no surface owns yet — degrade to the provider/group
  screen until a documents surface exists.
- **No stored readiness = recomputation cost.** Correct per F1.8.1, but the
  matrix fans providers × targets and runs several sub-queries; keep the
  service reads batched (one query per source table, joined in memory) rather
  than per-row round-trips, and lean on TanStack Query caching with org-scoped
  keys.
