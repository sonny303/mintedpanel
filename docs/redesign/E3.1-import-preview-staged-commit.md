# E3.1 — Import Preview, Dedupe, Conflict Review & Staged Commit

## Purpose and Context

E3.0 stages scanned roster rows; this epic turns them into live data —
safely. Every import run lands as a **reviewable preview** with a summary
dashboard (new providers to create / existing providers to update / rows
with blocked errors) and explicit `Commit Changes` / `Cancel Import`
actions (`[r5]` decision 7). Duplicates are detected on the five-part grain
**name + NPI + TIN + group + facility** (`[r5]` decision 5), conflicts with
existing Minted Panel data resolve through a **per-field review screen**
for name, NPI, license, and specialty (`[r5]` decision 2), and committed
providers land in a **Pending Verification (Staged)** state that does NOT
feed E1.8 readiness or E2.x case generation until explicitly verified
(`[r5]` decision 10). Batch group/facility assignment is a one-step,
one-shot action at commit time (`[r5]` decisions 8–9).

## Personas Empowered

- **P1 Credentialing Manager** — reviews and commits import runs; resolves
  conflicts.
- **P2 Credentialing Coordinator / Specialist** — verifies staged providers
  after commit.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only: a provider verification state (e.g.
  `providers.verification_state` additive column, default preserving
  existing rows as verified) — the reviewer reconciles the exact shape
  against the live schema in §5. E1.8 readiness and E2.0 candidacy must
  exclude `pending_verification` providers.
- Dedupe/conflict detection is a pure, tested module in `src/lib/` over the
  staged rows + existing org data; commit writes go through services with
  the existing audit pattern (one audit row per created/updated entity plus
  a run-level commit row).
- Commit is transactional per run at 5–10k scale — the reviewer verifies
  the buildable batching mechanism (chunked RPC with run-scoped idempotency
  vs single RPC) and records it in §5. A failed commit leaves live tables
  untouched and the run resumable.
- The E2.0 preview idiom (include/exclude with reasons) is the visual
  precedent; reuse its patterns, not a new paradigm.

## Features

### F3.1.1 — Import preview summary dashboard

- **Description:** A pre-commit summary for the run: counts of new
  providers to create, existing providers to update, and rows with blocked
  errors, with drill-down to the row lists and `Commit Changes` /
  `Cancel Import` actions.
- **Persona:** P1.
- **Benefit hypothesis:** one visual confirmation step prevents accidental
  bulk data corruption before the undo-less audit trail is generated.
- **Acceptance criteria:**
  - The three counts reconcile exactly with the staged rows.
  - Cancel discards the run (staged rows purged); nothing reaches live
    tables until Commit.
  - The blocked-error rows link to the E3.0 downloadable error report.
- **Test/data scenario(s):** TS-61.

```gherkin
Feature: Preview before commit
  Scenario: Summary gates the commit
    Given a scanned run with 45 new providers, 12 updates and 3 blocked rows
    When P1 opens the run
    Then the summary shows 45 / 12 / 3 with Commit and Cancel actions
    And no provider rows exist in live tables yet
```

### F3.1.2 — Five-part dedupe

- **Description:** Staged rows are matched against existing data on
  name + NPI + TIN + group + facility. A full five-part match is a
  duplicate (skipped, with reason); a provider match (name + NPI) under a
  different group/facility is an update/extension of the existing provider,
  never a second provider record.
- **Persona:** P1.
- **Benefit hypothesis:** providers operating under multiple groups and
  locations import cleanly without duplicate provider records or lost
  assignments.
- **Acceptance criteria:**
  - Exact five-part matches are skipped and listed with the reason
    "already exists".
  - Name+NPI matches with a new group/facility propose new assignments on
    the existing provider (visible in the preview as updates).
  - Rows missing NPI fall back to exact-name matching flagged for manual
    review — never silently merged.
- **Test/data scenario(s):** TS-61.

```gherkin
Feature: Multi-group providers
  Scenario: Same provider, second group
    Given Jane (NPI 1234567890) exists under Shelby Group 1
    And the roster lists Jane under Shelby Group 2 at a new facility
    When the run is previewed
    Then Jane appears as an update proposing the Group 2 assignment
    And no second Jane provider record is proposed
```

### F3.1.3 — Per-field conflict review

- **Description:** When an imported row's name, NPI, license, or specialty
  conflicts with the existing record, a per-field review screen shows both
  values and lets the user pick per field (imported vs existing). Location/
  address conflicts are not per-field reviewed — imported location data
  proposes assignments per F3.1.2 instead.
- **Persona:** P1.
- **Benefit hypothesis:** the user always controls which value wins;
  imports never silently overwrite verified data.
- **Acceptance criteria:**
  - Conflicting fields render side-by-side with per-field selection; the
    default is the existing value (explicit action required to overwrite).
  - Unresolved conflicts block Commit for those rows only (they join the
    blocked-errors bucket, not the whole run).
- **Test/data scenario(s):** TS-62.

### F3.1.4 — Staged commit + Pending Verification

- **Description:** Commit writes the reviewed rows to live tables with
  providers in `pending_verification`. Staged providers are excluded from
  E1.8 readiness and E2.0 case-generation candidacy until a user verifies
  them (sample review → explicit verify action, single or bulk).
- **Persona:** P1, P2.
- **Benefit hypothesis:** a bad column mapping can no longer flood task
  queues or trigger erroneous payer submissions.
- **Acceptance criteria:**
  - Committed providers carry a visible Pending Verification state
    (status-pill idiom) on the roster.
  - Readiness and generation preview show zero candidacy from
    pending-verification providers; verifying flips them in without
    re-import.
  - Commit produces the run-level + per-entity audit trail; the run flips
    to `committed` and its staged rows purge.
- **Test/data scenario(s):** TS-62, TS-63.

```gherkin
Feature: Staging keeps downstream safe
  Scenario: Pending providers do not generate cases
    Given a committed run created 45 pending-verification providers
    When P1 opens the E2.0 generation preview
    Then none of the 45 providers appear as case candidates
    And verifying a provider makes them a candidate on the next preview
```

### F3.1.5 — One-step batch assignment

- **Description:** At commit time (or on the run's committed view), the user
  assigns the whole batch to a group + one or more facilities in one step —
  one-shot, applied to that run's providers only. No standing rules, no
  specialty/state rule engine.
- **Persona:** P1.
- **Benefit hypothesis:** a migrated roster becomes assigned, workable scope
  in one action instead of hundreds of clicks.
- **Acceptance criteria:**
  - The action creates the group/facility assignments for the run's
    providers (respecting rows that already carried explicit group/facility
    columns — explicit row data wins over the batch default).
  - Running it twice does not duplicate assignments.
- **Test/data scenario(s):** TS-63.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-13 against the live schema
(`20260704210000_baseline_live_schema.sql` — `providers`, `provider_groups`,
`provider_facility_assignments`; `20260712120000_provider_group_assignments.sql`),
the readiness/generation read path (`src/services/enrollmentReadiness.ts`
`listProviderReadinessFacts`, `src/hooks/useGenerationPreview.ts`,
`src/services/generationPreview.ts`), the create services
(`src/services/providers.ts` `createProviderWithDetails`,
`src/services/orgSettings.ts` `createFacility`, `src/services/launches.ts`
`assignProviderToFacility`), the legacy commit path
(`src/services/importCommit.ts`), the audit spine (`src/lib/audit.ts`,
`audit_log`), the E2.0 preview idiom, `docs/data-model/table-register.md`,
`docs/redesign/seed-universe.md` (TS-61–TS-63), and `uiux-component-guide.md`.
E3.1 turns E3.0's staged rows into live data behind one confirmation gate; the
one genuinely new stored decision is the provider verification state, and the
key architectural lever is that generation candidacy already flows through a
single readiness read._

- **TE-1 — Verification state: an additive `providers.verification_state`
  column, NOT a widening of `providers.status`.** `providers.status` is
  CHECK-constrained to `onboarding | active | terminated`
  (`providers_status_check`) and drives the action engine — overloading it
  with a verification value would collide with that CHECK and that semantics.
  Add an additive column instead:

  ```
  verification_state text NOT NULL DEFAULT 'verified'
    CHECK (verification_state IN ('verified','pending_verification'))
  ```

  The `'verified'` default **preserves every existing row as verified** (the
  epic's requirement), so nothing already in the roster falls out of readiness/
  generation. Committed import rows are inserted with
  `'pending_verification'`; the verify action flips them to `'verified'`.
  Additive migration applied repo + hosted per `docs/migration-baseline.md`,
  regenerates `src/integrations/supabase/types.ts`, and updates the
  `providers` register row (party layer) **in the same PR** (AGENTS.md).

- **TE-2 — The staging fence is a single additive filter on one shared read
  (the highest-leverage enabler).** Both E1.8 readiness AND E2.0 generation
  candidacy consume the **same** provider source:
  `useGenerationPreview` builds its candidates from
  `useProviderReadinessFacts()` (`providers: factsQ.data`, verified against
  `src/hooks/useGenerationPreview.ts` lines ~124–201), which is
  `listProviderReadinessFacts` in `enrollmentReadiness.ts`. That read already
  filters `.neq("status","terminated")`. Add `.neq("verification_state",
"pending_verification")` there and **both** readiness (F3.1.4 "excluded from
  E1.8 readiness") and generation candidacy (F3.1.4 "zero candidacy") are
  fenced in one place — no per-surface duplication, no risk of the two
  disagreeing. The read must also add `verification_state` to its column list.
  The roster list (`useProviders`) is deliberately **not** filtered — staged
  providers stay visible there with the Pending Verification pill (F3.1.4 AC).
  Verifying a provider (flip to `verified`) makes it a candidate on the next
  preview "without re-import" because the preview recomputes from live reads
  (E2.0 is fully derived) — no stored candidacy to invalidate.
- **TE-3 — Dedupe is a pure, tested `src/lib/` module over staged rows +
  existing org data (five-part grain).** New module (working name
  `src/lib/importDedupe.ts`), no I/O, mirroring the E2.0
  `generationPreview.ts` "batched reads → pure evaluator" shape. Inputs
  (org-scoped reads, joined in memory): staged `import_rows`, `providers`
  (name, `npi`), `provider_groups` (`tin`, name), `provider_group_assignments`,
  `facilities`, `provider_facility_assignments`. Matching per `[r5]` decision 5
  — **name + NPI + TIN + group + facility**:
  - full five-part match → **skip**, reason "already exists" (F3.1.2);
  - name + NPI match under a **different** group/facility → an **update on the
    existing provider** proposing the new group/facility assignment(s), never a
    second `providers` row (this is exactly why the dedupe grain includes
    group/facility — a provider legitimately operates under multiple TINs/
    locations);
  - a row **missing NPI** → fall back to exact-name matching, flagged for
    **manual review** (joins the blocked bucket) — never silently merged.
    The module is pure and fully unit-testable (TS-61 states seeded as fixture
    arrays).
- **TE-4 — Per-field conflict review is a pure diff; location is excluded by
  design.** For a matched existing provider, compare the four reviewable
  fields — **name, NPI, license, specialty** (`[r5]` decision 2) — staged vs
  existing; render side-by-side with per-field selection, **default = the
  existing value** (explicit action required to overwrite). Location/address
  conflicts are NOT per-field reviewed (decision 2) — imported location data
  proposes assignments via TE-3 instead. Unresolved conflicts block **only
  their own rows** (they join the blocked-errors bucket), not the whole run —
  so a resolvable run still commits its clean rows. The diff is a pure function
  over the staged row + the matched provider record; the review screen composes
  existing primitives (`table`/`card` + `button` per-field pickers).
- **TE-5 — Commit batching: chunked writes through the existing create/assign
  services with run-scoped idempotency; failure leaves live tables untouched
  and the run resumable.** The create path already exists and is
  audit/RLS-correct: `createProviderWithDetails` (`providers` + licenses),
  `assignProviderToFacility` (`provider_facility_assignments`), and the
  `provider_group_assignments` insert path. E3.1 commits reviewed rows through
  these (setting `verification_state='pending_verification'`, TE-1) rather than
  writing tables directly — exactly the layering the legacy `importCommit.ts`
  already follows, minus its live-at-preview problem. At 5–10k scale, batch in
  chunks keyed by `import_rows.line` so a **re-run does not double-create**
  (record each staged row's resulting `provider_id` back on the run, or check
  existence per line): a mid-batch failure then leaves the already-created rows
  present, the rest un-created, and the run **resumable from the last committed
  line** — honest and queryable, no partial-corruption. _Buildable
  alternative:_ a single SECURITY-DEFINER `commit_import_run(run_id)` RPC that
  does the inserts server-side in one transaction (mirrors
  `create_case_with_tasks`), giving true per-run atomicity; heavier but cleaner
  if the PM wants all-or-nothing. Either is acceptable; silent double-creation
  on re-run is not.
- **TE-6 — Audit: existing append-only pattern, one row per entity + a
  run-level commit row.** Reuse `writeAudit` (`src/lib/audit.ts`) — the create
  services already emit `CREATE` audit rows per provider/assignment; add a
  run-level `audit_log` row at commit (entity `import_run`, `after` = the
  create/update/blocked counts + run id, never row PII). `touches`/
  `status_history` semantics untouched. `audit_log.entity_type` is
  unconstrained `text`, so `import_run` needs no CHECK widening;
  `action_type` `CREATE`/`UPDATE` already exist for the entity writes.
- **TE-7 — One-step batch assignment must be idempotent; mind the missing
  natural key on `provider_facility_assignments` (F3.1.5).** Assign the run's
  providers to a group + one or more facilities in one action, **explicit row
  data winning over the batch default** (a row that carried its own group/
  facility columns keeps them). `provider_group_assignments` already has
  `UNIQUE (provider_id, group_id)`, so re-running is naturally idempotent for
  group assignments. **`provider_facility_assignments` has NO unique
  constraint** on `(provider_id, facility_id)` (baseline DDL) — so a naive
  re-run WOULD duplicate. Enabler: guard the facility-assign path with an
  existence check per pair, or add an additive unique index on
  `(provider_id, facility_id)` in this PR (respect the existing one-primary
  partial unique `uq_provider_facility_assignments_one_primary`). This one-shot action
  has no standing/rule engine (decisions 8–9).
- **TE-8 — Purge staged rows on the terminal transition.** On Commit, after
  the writes succeed, flip the run to `committed` and DELETE its `import_rows`
  (the E3.0 TE-7 counterpart — "committed → staged rows purge"); Cancel flips
  to `cancelled` and DELETEs the staged rows without any live write. The
  audit/commit record (TE-6) is the durable trace, not the staging rows.
- **TE-9 — UI reuses the E2.0 preview idiom; no new primitive expected.** The
  summary dashboard (create / update / blocked counts + drill-down + `Commit
Changes` / `Cancel Import`) reuses E2.0's include/exclude-with-reasons visual
  precedent (Component & Data Constraints already pins this) — `card` metrics +
  `table` row lists with custom cells; the Pending Verification state is a
  status pill (`badge` `rounded-full`, status semantics only) on the roster;
  per-field conflict review composes `table`/`button`. Feature components in
  `src/components/import/` (shared with E3.0), never `ui/`/`layout/`; nothing
  touches the shell. Design-system token deltas per `uiux-component-guide.md`.
- **TE-10 — Authoritative table trace (AGENTS.md requires one).** Reads:
  `import_runs`, `import_rows` (E3.0), `providers`, `provider_groups`,
  `provider_group_assignments`, `provider_facility_assignments`, `facilities`,
  `state_licenses` (license conflict field). Writes: `providers` (INSERT new +
  additive-column UPDATE on conflict-resolved fields;
  `verification_state='pending_verification'`), `provider_group_assignments` /
  `provider_facility_assignments` (INSERT, idempotent per TE-7),
  `state_licenses` (INSERT for new licenses), `import_runs` (state UPDATE →
  `committed`/`cancelled`), `import_rows` (DELETE on commit/cancel, TE-8),
  `audit_log` (append-only). Reconciled against the register: `providers` gains
  the `verification_state` column (row updated); no new tables (E3.0 owns
  `import_*`).
- **TE-11 — Verification gates + build order.** Unit-test the pure modules
  (five-part dedupe branches, per-field conflict diff, batch-assign
  explicit-wins + idempotency); e2e for **TS-61** (preview summary + skip/
  update/multi-group dedupe; nothing hits live tables before Commit),
  **TS-62** (per-field conflict review + staged commit with Pending
  Verification pills + audit rows), and **TS-63** (one-step batch assignment
  idempotent + pending-verification providers show zero readiness/generation
  candidacy until verified) — L1 runs over existing Jane/group fixtures, **no
  new baseline fixtures**. Must pass `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`, and touched Playwright specs.
  **Build order:** E3.1 builds after E3.0 (needs `ready_for_review` runs +
  `import_rows`); E1.8 (#127) and E2.0 (#143) are already merged, so the TE-2
  fence lands as an additive edit to their shared read.

### Likely tech debt / risk to contain

- **`reference_only` vs `verification_state` (see open question).** The legacy
  importer marks imported rows `reference_only=true` (visible but skipped by
  the action engine/Fix-it queue; `20260707150000_reference_only_flag.sql`).
  E3.1 introduces `pending_verification` as the new downstream fence. These are
  two different "not fully live yet" flags — resolve their interplay
  deliberately (TE / open question 1) rather than letting a provider carry a
  confusing mix.
- **`provider_facility_assignments` duplicate risk (TE-7).** The missing
  natural key is a real footgun for the "run twice doesn't duplicate" AC —
  don't rely on application-side de-dup alone; prefer the additive unique index.
- **Update-path scope creep.** "Existing provider gets a new assignment" must
  stay an _assignment_ add, not a silent overwrite of the provider's other
  fields — only conflict-resolved fields (TE-4) are updated. Keep the update
  surface narrow so an import can't quietly rewrite verified demographics.
- **Commit is undo-less (by design).** Non-Goals correctly exclude undo; the
  summary gate (F3.1.1) is the safety net. Make the Commit confirmation
  unambiguous about that finality.

### Open questions for the PM

1. **`reference_only` vs Pending Verification.** Should a committed import row
   be `pending_verification` only, or also `reference_only=true` until
   verified? Reviewer recommendation: use `verification_state` as the single
   R5 fence for readiness/generation (TE-2) and leave `reference_only` to its
   existing action-engine meaning, to avoid two overlapping "not live" flags.
   Confirm so the build doesn't set both and confuse downstream surfaces.
2. **Who may verify (F3.1.4).** The epic gives verify to P1/P2. Writes are
   currently `specialist | admin` (`canWrite`). Reviewer default: verify is a
   writer action (specialist/admin), consistent with the rest of the app.
   Flagging only if the business wants a narrower gate.
