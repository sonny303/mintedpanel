# E3.1 — Import Preview, Dedupe, Conflict Review & Staged Commit

## Purpose and Context

E3.0 stages scanned roster rows; this epic turns them into live data —
safely. Every import run lands as a **reviewable preview** with a summary
dashboard (new providers to create / existing providers to update / rows
with blocked errors) and explicit `Commit Changes` / `Cancel Import`
actions (`[r5]` decision 7). Duplicates are detected on the five-part grain
**name + NPI + TIN + group + facility** (`[r5]` decision 5), conflicts with
existing Minted Panel data resolve through a **per-field review screen**
for name, NPI, license, and specialty (`[r5]` decision 2), and committed
providers land in a **Pending Verification (Staged)** state that does NOT
feed E1.8 readiness or E2.x case generation until explicitly verified
(`[r5]` decision 10). Batch group/facility assignment is a one-step,
one-shot action at commit time (`[r5]` decisions 8–9).

## Personas Empowered

- **P1 Credentialing Manager** — reviews and commits import runs; resolves
  conflicts.
- **P2 Credentialing Coordinator / Specialist** — verifies staged providers
  after commit.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only: a provider verification state (e.g.
  `providers.verification_state` additive column, default preserving
  existing rows as verified) — the reviewer reconciles the exact shape
  against the live schema in §5. E1.8 readiness and E2.0 candidacy must
  exclude `pending_verification` providers.
- Dedupe/conflict detection is a pure, tested module in `src/lib/` over the
  staged rows + existing org data; commit writes go through services with
  the existing audit pattern (one audit row per created/updated entity plus
  a run-level commit row).
- Commit is transactional per run at 5–10k scale — the reviewer verifies
  the buildable batching mechanism (chunked RPC with run-scoped idempotency
  vs single RPC) and records it in §5. A failed commit leaves live tables
  untouched and the run resumable.
- The E2.0 preview idiom (include/exclude with reasons) is the visual
  precedent; reuse its patterns, not a new paradigm.

## Features

### F3.1.1 — Import preview summary dashboard

- **Description:** A pre-commit summary for the run: counts of new
  providers to create, existing providers to update, and rows with blocked
  errors, with drill-down to the row lists and `Commit Changes` /
  `Cancel Import` actions.
- **Persona:** P1.
- **Benefit hypothesis:** one visual confirmation step prevents accidental
  bulk data corruption before the undo-less audit trail is generated.
- **Acceptance criteria:**
  - The three counts reconcile exactly with the staged rows.
  - Cancel discards the run (staged rows purged); nothing reaches live
    tables until Commit.
  - The blocked-error rows link to the E3.0 downloadable error report.
- **Test/data scenario(s):** TS-61.

```gherkin
Feature: Preview before commit
  Scenario: Summary gates the commit
    Given a scanned run with 45 new providers, 12 updates and 3 blocked rows
    When P1 opens the run
    Then the summary shows 45 / 12 / 3 with Commit and Cancel actions
    And no provider rows exist in live tables yet
```

### F3.1.2 — Five-part dedupe

- **Description:** Staged rows are matched against existing data on
  name + NPI + TIN + group + facility. A full five-part match is a
  duplicate (skipped, with reason); a provider match (name + NPI) under a
  different group/facility is an update/extension of the existing provider,
  never a second provider record.
- **Persona:** P1.
- **Benefit hypothesis:** providers operating under multiple groups and
  locations import cleanly without duplicate provider records or lost
  assignments.
- **Acceptance criteria:**
  - Exact five-part matches are skipped and listed with the reason
    "already exists".
  - Name+NPI matches with a new group/facility propose new assignments on
    the existing provider (visible in the preview as updates).
  - Rows missing NPI fall back to exact-name matching flagged for manual
    review — never silently merged.
- **Test/data scenario(s):** TS-61.

```gherkin
Feature: Multi-group providers
  Scenario: Same provider, second group
    Given Jane (NPI 1234567890) exists under Shelby Group 1
    And the roster lists Jane under Shelby Group 2 at a new facility
    When the run is previewed
    Then Jane appears as an update proposing the Group 2 assignment
    And no second Jane provider record is proposed
```

### F3.1.3 — Per-field conflict review

- **Description:** When an imported row's name, NPI, license, or specialty
  conflicts with the existing record, a per-field review screen shows both
  values and lets the user pick per field (imported vs existing). Location/
  address conflicts are not per-field reviewed — imported location data
  proposes assignments per F3.1.2 instead.
- **Persona:** P1.
- **Benefit hypothesis:** the user always controls which value wins;
  imports never silently overwrite verified data.
- **Acceptance criteria:**
  - Conflicting fields render side-by-side with per-field selection; the
    default is the existing value (explicit action required to overwrite).
  - Unresolved conflicts block Commit for those rows only (they join the
    blocked-errors bucket, not the whole run).
- **Test/data scenario(s):** TS-62.

### F3.1.4 — Staged commit + Pending Verification

- **Description:** Commit writes the reviewed rows to live tables with
  providers in `pending_verification`. Staged providers are excluded from
  E1.8 readiness and E2.0 case-generation candidacy until a user verifies
  them (sample review → explicit verify action, single or bulk).
- **Persona:** P1, P2.
- **Benefit hypothesis:** a bad column mapping can no longer flood task
  queues or trigger erroneous payer submissions.
- **Acceptance criteria:**
  - Committed providers carry a visible Pending Verification state
    (status-pill idiom) on the roster.
  - Readiness and generation preview show zero candidacy from
    pending-verification providers; verifying flips them in without
    re-import.
  - Commit produces the run-level + per-entity audit trail; the run flips
    to `committed` and its staged rows purge.
- **Test/data scenario(s):** TS-62, TS-63.

```gherkin
Feature: Staging keeps downstream safe
  Scenario: Pending providers do not generate cases
    Given a committed run created 45 pending-verification providers
    When P1 opens the E2.0 generation preview
    Then none of the 45 providers appear as case candidates
    And verifying a provider makes them a candidate on the next preview
```

### F3.1.5 — One-step batch assignment

- **Description:** At commit time (or on the run's committed view), the user
  assigns the whole batch to a group + one or more facilities in one step —
  one-shot, applied to that run's providers only. No standing rules, no
  specialty/state rule engine.
- **Persona:** P1.
- **Benefit hypothesis:** a migrated roster becomes assigned, workable scope
  in one action instead of hundreds of clicks.
- **Acceptance criteria:**
  - The action creates the group/facility assignments for the run's
    providers (respecting rows that already carried explicit group/facility
    columns — explicit row data wins over the batch default).
  - Running it twice does not duplicate assignments.
- **Test/data scenario(s):** TS-63.

**Verification verdict:** the epic's core architecture is sound. The one
genuinely new stored decision is the additive verification column, and the
highest-leverage fact is that E1.8 readiness AND E2.0 generation candidacy
already flow through **one** provider read — so the staging fence is a
single additive filter, not a per-surface change. Two author-draft claims
were wrong and are corrected below (TE-7 pfa uniqueness — a load-bearing
factual error; TE-6 audit ↔ commit coherence), and the commit mechanism is
re-recorded so it actually satisfies the epic's own "failed commit leaves
live tables untouched" constraint (TE-5).

- **TE-1 — Verification state: an additive `providers.verification_state`
  column, NOT a widening of `providers.status` (VERIFIED CORRECT).**
  Live-confirmed: `providers_status_check` = `CHECK (status IN
('onboarding','active','terminated'))` and `providers.status` drives the
  action engine — overloading it would collide with that CHECK and its
  semantics. No `verification_state`/staged/pending column exists today
  (live column scan). Add:

  ```
  verification_state text NOT NULL DEFAULT 'verified'
    CHECK (verification_state IN ('verified','pending_verification'))
  ```

  The `'verified'` default **preserves every existing row as verified**, so
  nothing already in the roster falls out of readiness/generation. Committed
  import rows are inserted `'pending_verification'`; verify flips them to
  `'verified'`. Follow the E0.10 constraint-column convention: additive
  migration repo + hosted per `docs/migration-baseline.md`, regenerate
  `src/integrations/supabase/types.ts`, add the domain field to
  `src/types/index.ts` (`Provider.verificationState`), and update the
  `providers` register row **in the same PR** (AGENTS.md). (No `dbErrors.ts`
  mapping is needed — this CHECK is never hit by user free-text; the app only
  writes the two enum values.)

- **TE-2 — The staging fence is a single additive filter on ONE shared read
  — the highest-leverage enabler (VERIFIED CORRECT and robust).** Both E1.8
  readiness AND E2.0 generation candidacy consume the **same** provider
  source: `useGenerationPreview` passes `factsQ.data` — the
  `useProviderReadinessFacts()` → `listProviderReadinessFacts` result — into
  BOTH `buildGenerationPreview({ providers })`
  (`useGenerationPreview.ts` L189) AND `evaluateEnrollmentReadiness({
providers })` (L201). Crucially, the fence works as a **presence** filter,
  identical to how `terminated` is already excluded, so neither locked model
  is touched:
  - `buildGenerationPreview` L207-208: `const provider =
providerById.get(providerId); if (!provider) continue;` — a provider absent
    from `input.providers` produces **no candidate row**. Candidacy stays
    presence-based ([r4-review] Q4).
  - `evaluateEnrollmentReadiness` L349: `const facts =
factsById.get(a.providerId); if (!facts) continue;` — absent providers
    produce **no readiness rows**. Readiness stays advisory.
  - `listProviderReadinessFacts` (`enrollmentReadiness.ts` L44) already
    filters `.neq("status","terminated")`. Add
    `.neq("verification_state","pending_verification")` there (and add the
    column to its select list) and **both** surfaces are fenced in one place —
    no per-surface duplication, no risk of the two disagreeing.

  `useProviders` (the roster list projection) is deliberately **not**
  filtered — staged providers stay visible with the Pending Verification pill
  (F3.1.4 AC). Because E2.0 is fully derived and stores nothing, flipping a
  provider to `verified` makes it a candidate on the next preview with **no
  re-import** (nothing to invalidate — the read re-includes it). **Enforce
  the invariant:** no other candidacy/readiness path may bypass this one
  read; if a future surface reads a candidate set from `useProviders`/a new
  projection, the fence silently fails. TS-63 must pin that a
  `pending_verification` provider yields **zero readiness rows AND zero
  generation candidates**.

- **TE-3 — Dedupe is a pure, tested `src/lib/` module over staged rows +
  existing org data (five-part grain — expressible; TIN correction noted).**
  New pure module (working name `src/lib/importDedupe.ts`), no I/O, mirroring
  the E2.0 `generationPreview.ts` "batched reads → pure evaluator" shape.
  Inputs (org-scoped reads joined in memory): staged `import_rows`,
  `providers` (name, `npi`), `provider_groups` (`tin`, name),
  `provider_group_assignments`, `facilities`, `provider_facility_assignments`.
  Grain sources are all present and joinable: **name + NPI** on `providers`;
  **TIN** on `provider_groups.tin` (baseline L283 — a **group** attribute,
  reached via the group, not a provider column); **group** via
  `provider_group_assignments` (`UNIQUE (provider_id, group_id)`);
  **facility** via `provider_facility_assignments` (`UNIQUE (provider_id,
facility_id)`). Note the grain's TIN and group identify the **same** entity
  (a group has one TIN) — so the effective match is provider(name, NPI) ×
  group(resolved by TIN/name) × facility; the CSV carries both TIN and group
  name so a staged row resolves to an existing `provider_groups` row. Matching
  per `[r5]` decision 5:
  - full five-part match → **skip**, reason "already exists" (F3.1.2);
  - name + NPI match under a **different** group/facility → an **update on the
    existing provider** proposing new group/facility assignment(s), never a
    second `providers` row (this is exactly why the grain includes
    group/facility — a provider legitimately operates under multiple TINs/
    locations);
  - a row **missing NPI** → fall back to exact-name matching, flagged for
    **manual review** (joins the blocked bucket) — never silently merged.
    Fully unit-testable (TS-61 states seeded as fixture arrays).

- **TE-4 — Per-field conflict review is a pure diff; location is excluded by
  design.** For a matched existing provider, compare the four reviewable
  fields — **name, NPI, license, specialty** (`[r5]` decision 2) — staged vs
  existing; render side-by-side with per-field selection, **default = the
  existing value** (explicit action to overwrite). Location/address is NOT
  per-field reviewed (decision 2) — imported location data proposes
  assignments via TE-3. Unresolved conflicts block **only their own rows**
  (they join the blocked bucket), never the whole run, so a resolvable run
  still commits its clean rows. The diff is a pure function over the staged
  row + the matched records; the screen composes existing primitives
  (`ui/table` + `ui/button` per-field pickers — no new primitive). NB the
  `license` field lives on `state_licenses` (per provider × state), so
  resolving a license conflict is an UPDATE/INSERT to `state_licenses`, not a
  `providers` column — reflected in the TE-10 trace.

- **TE-5 — Commit mechanism: a single transactional RPC is the one that
  satisfies the epic's own "failed commit leaves live tables untouched"
  (REWRITTEN — the author's primary mechanism does not).** The epic's
  Component & Data Constraints require BOTH "transactional per run" AND "a
  failed commit leaves live tables untouched"; the reviewer is delegated the
  mechanism choice. The author's primary — chunked writes through the per-row
  create services with resume-from-last-line — leaves **partial writes** on
  failure and therefore does **not** meet "untouched." The buildable
  mechanism that does:
  - **Recommended — one SECURITY-DEFINER `commit_import_run(run_id)` RPC,
    set-based, one transaction.** Because E3.0 already stages parsed rows in a
    real `import_rows` table, the RPC does set-based `INSERT … SELECT` from
    `import_rows` into `providers` (with `verification_state =
'pending_verification'`), `provider_group_assignments`,
    `provider_facility_assignments`, and `state_licenses`, plus the audit rows
    (TE-6), inside ONE transaction — precedents: `create_organization`
    (SECURITY-DEFINER multi-insert bootstrap) and `create_case_with_tasks`
    (case + tasks + status_history + audit in one tx). This gives true
    "untouched on failure" (transaction rollback), **run-scoped idempotency**
    via a state guard (the RPC asserts `import_runs.state='ready_for_review'`
    and flips it to `'committed'` inside the same tx, so a replay/concurrent
    call sees `committed` and no-ops), and scale (set-based server-side, not
    5–10k PostgREST round-trips). SECURITY DEFINER must re-enforce org
    membership + writer role and pin `search_path` (the E0.5/E1.4 RPC
    pattern). **Cost/trade-off to accept:** the insert + audit logic is
    re-implemented in SQL — it cannot reuse the browser create services
    (`createProviderWithDetails` et al.), which are per-row PostgREST calls.
  - **Fallback (only if the PM relaxes "untouched") — chunked reuse of the
    existing services** in ~500-row batches with run-scoped idempotency
    (record each staged line's resulting `provider_id`, or the DB unique keys
    backstop re-runs — TE-7): reuses the audited/RLS-correct create path but
    leaves already-created rows on a mid-batch failure and resumes from the
    last committed line. **This trades atomicity for resumability and requires
    reconciling the "leaves live tables untouched" AC** — a PM decision (open
    question 1). Whichever is chosen, silent double-creation on re-run is not
    acceptable; the DB unique keys (TE-7) are the backstop for both.

- **TE-6 — Audit: run-level + per-entity, append-only — but its WRITER
  depends on the TE-5 mechanism (RECONCILED).** Live-confirmed:
  `audit_log_action_type_check` already allows `CREATE`/`UPDATE`/`DELETE`
  (and `STATUS_CHANGE`/`READ`/…), and `audit_log.entity_type` is unconstrained
  `text` — so the run-level entity `import_run` needs **no** CHECK widening,
  and per-entity `CREATE`/`UPDATE` rows use existing action types. The coherence
  point the author's draft missed: `writeAudit` (`src/lib/audit.ts` L17) is a
  **browser-side** single-INSERT that reads the auth store — it CANNOT run
  inside a server-side transaction. Therefore:
  - If the **atomic RPC** (TE-5 recommended) is chosen, the per-entity CREATE
    rows AND the run-level commit row are written **inside** the RPC (actor =
    `auth.uid()`), exactly as `create_case_with_tasks` writes its own audit
    rows — the service must NOT also call `writeAudit` (the E1.7b
    publish-RPC precedent).
  - If the **chunked** fallback is chosen, the create services' `writeAudit`
    calls emit the per-entity rows and a final `writeAudit` emits the
    run-level row.
    Either way: one row per created/updated entity + one run-level
    `import_run` row carrying ids + create/update/blocked counts + run id —
    **never row PII** (the E2.0/E2.4 audit-payload rule). `touches`/
    `status_history` are untouched by import.

- **TE-7 — Batch assignment is ALREADY idempotent at the DB — the author's
  "missing natural key" claim is FACTUALLY WRONG (CORRECTED; see blocker
  redline).** Live-confirmed via `pg_constraint`:
  `provider_facility_assignments_provider_id_facility_id_key UNIQUE
(provider_id, facility_id)` EXISTS (also baseline L824 and CLAUDE.md's domain
  model), and `provider_group_assignments_provider_id_group_id_key UNIQUE
(provider_id, group_id)` EXISTS. So F3.1.5 "running twice does not duplicate"
  is **already backstopped by DB unique constraints on both assignment
  tables** — **no new migration is needed** (the author's proposed additive
  unique index would be redundant/no-op). Build the batch-assign as
  insert-with-conflict-ignore, or route through the existing
  `providerAssignments.ts insertAssignmentRows` path which already respects
  the unique. **Explicit-row-data-wins** (a staged row carrying its own
  group/facility columns keeps them over the batch default) is pure precedence
  resolved in the dedupe/plan lib. Mind the **one-primary partial unique**
  `uq_provider_facility_assignments_one_primary` (`20260710170000`): a batch
  assign must insert as non-primary or follow the E1.4
  `planFacilityAssignmentSync` demote→delete→promote→insert order so the
  partial unique never trips.

- **TE-8 — Purge staged rows on the terminal transition (matches E3.0 §5
  TE-7).** On Commit, after the writes succeed (inside the same tx for the
  atomic RPC), flip the run to `committed` and DELETE its `import_rows`;
  Cancel flips to `cancelled` and DELETEs the staged rows with no live write.
  The run row itself is retained as the durable ledger (E3.0 §5 TE-2) — the
  audit/commit record (TE-6) is the durable trace, not the staging rows. (NB
  F3.1.1's "Cancel discards the run" wording means purge-staged-rows +
  flip-to-cancelled, not delete-the-run-row — consistent with E3.0.)

- **TE-9 — UI reuses the E2.0 preview idiom; no new primitive.** The summary
  dashboard (create / update / blocked counts + drill-down + `Commit Changes`
  / `Cancel Import`) reuses E2.0's include/exclude-with-reasons precedent
  (`src/components/generation/GenerationPreviewContent.tsx`) — `ui/card`
  metrics + `ui/table` row lists with custom cells; the Pending Verification
  state is a status pill (`rounded-full`, status semantics only) on the
  roster; per-field conflict review composes `ui/table`/`ui/button`. Feature
  components in `src/components/import/` (shared with E3.0), never
  `ui/`/`layout/`; nothing touches the shell. Any unspecced composite is stock
  shadcn, token-styled, and logged in `DESIGN-DEBT.md` (AGENTS.md/E0.9).

- **TE-10 — Authoritative table trace (AGENTS.md requires one).** **Reads:**
  `import_runs`, `import_rows` (E3.0), `providers`, `provider_groups`,
  `provider_group_assignments`, `provider_facility_assignments`, `facilities`,
  `state_licenses` (license conflict field). **Writes:** `providers` (INSERT
  new, `verification_state='pending_verification'`; UPDATE only for
  conflict-resolved name/NPI/specialty — TE-4, kept narrow),
  `provider_group_assignments` / `provider_facility_assignments` (INSERT,
  idempotent via existing DB unique — TE-7), `state_licenses` (INSERT for new
  licenses; UPDATE for a conflict-resolved license — TE-4), `import_runs`
  (state UPDATE → `committed`/`cancelled`), `import_rows` (DELETE on
  commit/cancel — TE-8), `audit_log` (append-only). **Never** writes
  `credential_cases`/`tasks` — staged providers are fenced out of generation
  until verified (TE-2), so no cases are created by import. Reconciled against
  the register: `providers` gains the `verification_state` column (row
  updated); no new tables (E3.0 owns `import_*`).

- **TE-11 — Verification gates + build order.** **Build order:** E3.1 builds
  **after** E3.0 (needs `ready_for_review` runs + `import_rows`, which E3.0
  §5 owns and which do not exist yet — see the sequencing redline); E1.8 and
  E2.0 are merged, so the TE-2 fence lands as an additive edit to their shared
  read. **Unit tests** (pure modules): five-part dedupe branches (skip /
  update-multi-group / missing-NPI manual-review), the per-field conflict
  diff (existing-default, per-field pick), and batch-assign explicit-wins +
  idempotency (a re-run inserts nothing new and swallows no error — the DB
  unique is the backstop, TE-7). **e2e** (L1 over existing Jane/group
  fixtures, **no new baseline fixtures**): **TS-61** (preview summary +
  skip/update/multi-group dedupe; nothing hits live tables before Commit),
  **TS-62** (per-field conflict review + staged commit with Pending
  Verification pills + run-level & per-entity audit rows), **TS-63** (one-step
  batch assignment idempotent + a `pending_verification` provider shows
  **zero** readiness AND **zero** generation candidacy until verified — the
  TE-2 single-fence regression). Gates: `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`, touched Playwright specs.

### Likely tech debt / risk to contain

- **`reference_only` vs `verification_state` (open question 2).** The legacy
  importer marks rows `reference_only=true` (visible but skipped by the action
  engine/Fix-it/Home queues; `20260707150000_reference_only_flag.sql`). E3.1
  introduces `pending_verification` as the readiness/generation fence. These
  are two different "not fully live" flags — resolve their interplay
  deliberately rather than letting a provider carry a confusing mix. Reviewer
  recommendation: the new pipeline sets `verification_state` only; leave
  `reference_only` to its existing action-engine meaning.
- **Commit atomicity vs service reuse (open question 1).** The atomic RPC
