How Journey A and Journey B hand off into case generation

The question this page answers: "why can I trust that all the right cases get generated under a provider — nothing missing, nothing extra?" Running example: BEST Physical Therapy · one group · one facility (NC) · seven payers targeted on day 1 · Dr. Riley Chen hired on day 50.

1

Two journeys, two kinds of facts — neither creates work

Journey A · per payer, once, global

Payer readiness

Ops team · no org context · authored once, inherited by every org
  • Catalog entry — canonical identity, covered states, what this payer calls its provider ID
  • SOP template — the step-by-step checklist for getting credentialed with this payer
  • Form setup inside the SOP — portal URL, captured fields, trained mappings, dry-run proven on masked mock data
Produces: "HOW to credential with this payer" — knowledge, zero cases.
Journey B · per org

Org reality

Admin / onboarding team · manual forms or CSV, unified summary at the end
  • Group — BEST PT Group (TIN, operating states: NC)
  • Facility — Harborview Clinic, NC
  • 7 payer targets on the group — the contract's promise, recorded day 1, zero providers needed
  • Dr. Chen (day 50) — roster + group membership + facility assignment + existing enrollments under this group's contract (new hire → none)
Produces: "WHO needs to be credentialed WHERE" — facts, zero cases.

Neither journey creates a single case. That is the decoupling: onboarding records reality, and only the confirm in step 4 creates work.

2

The candidate math — computed live, never stored, never guessed

For each provider on the group
group's payer targets − enrollments under this group − cases that already exist − standing exclusions = candidates awaiting generation
Dr. Chen joins the group → instantly a candidate for all 7 targets. Nobody assigns payers to a provider; membership in the group IS the assignment. Every subtraction is a fact someone deliberately recorded — a migration enrollment, a prior case, a reasoned exclusion — so nothing is ever dropped silently.

4

Confirm — the only moment cases are created, and where Journey A pays off

Case: Dr. Chen × Anthem BCBS NC
Created from run #14 · payer flips Targeted → In Progress
SOP lookup at confirm: Anthem NC SOP v3 found → its steps become this case's tasks, with Dr. Chen's real data substituted in.
  1. Verify CAQH attestation is current — Chen's CAQH ID pre-filled
  2. Complete Availity enrollment form — NPI, NC license #, group TIN pre-mapped auto-fill ready
  3. Submit and record the tracking ID
  4. Follow up every 14 days until determination
Case: Dr. Chen × UnitedHealthcare
Created from run #14 · same run, honest about the gap
SOP lookup: no UHC SOP exists yet → generic fallback checklist, case visibly flagged "generic SOP" until ops finishes Journey A for UHC.
  1. Confirm enrollment route with payer
  2. Prepare and submit application — no auto-fill until a form is trained
  3. Record tracking ID and follow up

Every task is stamped with which SOP version produced it, and the whole batch is recorded as one immutable run — so months later "why does this case look like this" always has an answer.

5

Why nothing slips through — and where you see it

The invariant

Every provider × target combination is always in exactly one visible bucket: proposed · already enrolled · existing case · excluded (with reason and author). The buckets sum to the target count on every screen that shows them. A case can only come into existence through a human confirm (batch generation, or the one-off manual escape hatch) — never as a side effect of onboarding.
