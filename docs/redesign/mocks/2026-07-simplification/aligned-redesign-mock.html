The org's case queue — one surface, three pivots. MVP is org-wide (no per-analyst assignment; that's a future idea, not a field today).

  • To-do pivot (default): ranked by overdue follow-ups → task due dates → provider start dates → the rest.
  • By provider / by payer pivots: the same cases, re-sliced. No separate "Cases" page — merged.
  • Case detail: SOP task checklist, portal fill via the extension (unchanged — human always submits), tracking IDs, status changes incl. Denied + reason.
  • "Add touch" is the one global logging action — the old separate "Log Payer Call" is gone; a payer call across N cases is an Add touch with N cases selected.
Payer SetupEveryone, for now

Journey A's home — global, authored once, inherited by every org. Tabs backed by real URLs: catalog · sops.

  • Payer Catalog: canonical payers + curated facts (covered states, what the payer calls its provider ID, delegation).
  • SOP Templates: the library + editor. Form setup lives inside the form step: portal URL, capture, train, mock-data dry run. MSO-delegated paths are just SOP steps.
  • Needs attention: drift repair (ex-Fix-it) — a broken mapping reopens the same form-step editor it was authored in.
  • No org data, no denials, no settings — those were mislocated and have been moved out.
Reporting Center

All read-only investigation, grouped:

  • Compliance: Audit Log (who did what, when).
  • Intake: Inbound leads queue, badge when leads await.
Section 2

Sidebar — Org space

Three entries for the active org. Org Detail is the container's page (slim); Groups is the working entity — everything operational hangs off the group, because the data does (payers attach to groups, facilities belong to a group, cases are group-grain); Providers is the consolidated people record. The onboarding wizard is not a menu item — a one-time flow from Add organization, with a "Finish setup" banner on Org Detail until complete.

Org Detail

The container only: org summary, authorized/organization contacts, People Enroll, member management (from the retired Settings page), capture-link re-issue, "Finish setup" banner. Matches the two live screenshots reviewed 2026-07-19.

Groups

Per group — single-group orgs auto-land on their only group:

  • Group facts: legal name, TIN, operating states.
  • Facilities: the same list treatment as Providers — search on top, state-grouped, A→Z within state, filters (state, has-providers); each facility belongs to exactly one group — a shared address across two groups is entered per group, mirroring how payers see per-TIN service locations. Facility CSV lives here. Occasional counts ("facilities with no providers", "locations per group") are Reporting Center reports, not screen widgets.
  • Payer Network: the fulfillment board at its true grain — Targeted → In Progress (open-case count) → Active (approved case OR enrollment fact), the "candidates awaiting generation" buffer, eligibility-filtered attach + CSV, and Generation as the in-tab action (preview → confirm → run history).
Providers

The consolidated people record, sorted A→Z by default: identity · licenses + verification · CAQH · documents · enrollment facts (migration capture — facts, never auto-cases; a new hire from another employer never records here) · all cases with statuses · denial history · gaps inline. Inline field editing (no monolithic edit form) and a first-class "+ Add facility" action on the record — fixing today's defect where editing a provider silently drops facility assignments. Provider CSV here; the wizard's provider step IS this surface.

What no longer exists as navigation, anywhere

Home · My Cases/Cases split · Fix-it · Client Progress · Onboarding tab · Launches page · Facilities entry · Data Import page · Statuses page · MSO Routing page · Settings page · the Admin section itself. Every job those did has a named new home — see the retirement ledger at the bottom.

Section 3

Journey A — make a payer ready for business

Standalone and org-independent: ops works any payer to "ready" outside any onboarding funnel, once, and every org inherits the result. Two steps.

  1. 1
    Payer Catalog payer-setup/catalog
    Confirm the canonical payer and its curated facts: covered states, kind, what it calls the provider ID on approval letters, and whether credentialing is delegated (MSO) — a payer fact, not an org rules table. A missing payer is a platform request, never free-text.
  2. 2
    SOP Template payer-setup/sops/$id
    Author the payer's checklist — tasks and steps, including the delegated-path steps where an MSO is involved. Inside an online form step, in place:
    Portal — pick an already-registered portal for this payer, or register the URL (user-driven, reusable, no separate module).
    Capture — pull the form's fields off the live page.
    Train — approve field-to-data mappings card by card; the label dictionary learns silently.
    Dry run — a fill against masked mock data. No org, no real PHI, once per payer — never re-tested per org. Mappings are proven before any user starts casework.
    Publish v1 — versioned; later edits publish v2, v3… history immutable.
Done state: the payer reads Ready on the Payer Setup funnel. Any group that attaches it inherits a working SOP and a proven fillable form with zero additional setup. Drift (the payer changes their form later) raises a needs-attention badge that reopens this same editor.
Section 4

Journey B — stand up an org and attach payers

The running example: BEST Physical Therapy · one group · one facility (NC) opening Nov 1 · contract promises 7 payers (4 commercial, 3 government) · no providers until a day-50 hire.

  1. DAY 1
    Add organization → one-time wizard
    Create the org (name + contacts), then: org details → provider group (TIN, operating states) → facility (address; Nov 1 recorded as its go-live date — feeds the Launches report and queue ranking, nothing else). Providers section skipped — no one hired yet. Each section: manual form or CSV, side by side.
  2. DAY 1
    Attach payers Groups › BEST PT Group › Payer Network
    The system queries the catalog and presents the eligible list — payers whose covered states intersect the org's operating states. Pick the 7; one user-reviewed confirm creates the group × payer × state targets. The org-level enablement happens implicitly. CSV alternative: one row per group × payer.
  3. DAY 1
    Target state on record
    The fulfillment view now reads: 7 Targeted · 0 candidates · 0 in progress · 0 active. The contract's promise is visible from day one, with zero providers — this is what admin and the credentialing team steer by.
  4. DAY 50
    Provider hired Providers
    Add Dr. Riley Chen: identity, licenses, CAQH → group membership → facility assignment → existing-enrollments section (empty — new hire; prior-employer status never carries over, full path regardless. If this were a migration, enrollments under this group's contract would be recorded here as enrollment facts — never cases).
  5. DAY 50
    The tie is derived — nobody assigns payers to a provider
    Group membership IS the payer assignment: Chen is instantly a candidate for all 7 targets. The fulfillment view flips to "7 candidates awaiting generation" — the visible buffer between onboarding and casework. Onboarding created zero cases.
Section 5

Journey C — generation: the only door cases come through

Entered from the group's Payer Network board (Groups › Review & generate). A human always confirms; nothing is ever created as a side effect of onboarding (starter cases: retired; launch-page creation: retired; the one-off manual modal remains as the escape hatch).

group's payer targets−enrollments under this group−existing cases−standing exclusions=candidates
Every subtraction is a fact someone deliberately recorded. The preview shows every combination in exactly one bucket, and the buckets always sum to the target count — nothing silently disappears.

After confirm

One immutable run records every disposition. The new cases land on Cases (the landing surface), ranked with Chen's start date in the mix. The fulfillment view flips those payers In Progress — and each one flips Active when its first case is Approved. Denials are recorded on the case with a reason and roll up to the provider for reporting.

Status model

One status list — the only status a human ever sets

Replaces four lists (~31 statuses): the internal credentialing track, the parallel payer pipeline, the contracting track, and the location track. Fixed and canonical — the per-org status configuration page retires with it.

Not Started→ In Progress→ Submitted→ In Review→ Action Required→ Approved orDenied + reason orNot Pursuing
Payer fulfillment (derived)
Targeted → In Progress → Active per group × payer, most-advanced-case-wins; Active = ≥1 approved case OR enrollment fact. Never hand-set.
Provider progress (derived)
x of y approved on the provider record; denial history alongside.
Contracts (fields, not a track)
Execution + effective dates are fields on the Approved case — the 6-status contracting machine retires.
Locations (a date, not a track)
Go-live is a date on the facility feeding the Launches report + queue ranking — the 7-status location machine retires.
