# E1.7b — SOP Worked Examples

The two real SOPs the business uses today, mapped into the Model A
versioned-SOP data model (per `E1.7a-sop-versioning-decision.md`). These are
the grounding fixtures for the E1.7b build: an authoring surface that cannot
represent these two documents is wrong.

**Source documents (PM-provided 2026-07-12, retained off-repo):**

1. _Kansas New Location & New provider SOPs_ — payer-specific: per-payer
   procedures for UnitedHealthCare/Optum, Humana, BCBS of Kansas, BCBS KC,
   Aetna under one group (Kansas Fitness Physio, P.A., fka Mowery Rehab
   Consultants, TIN 48-1158557).
2. _Fitness Physio Credentialing SOP_ — general onboarding: the per-provider
   enrollment checklist (staff folder → roster → CAQH/NPPES/PECOS → each
   payer) plus per-payer notes.

One plaintext portal credential found in source #2 has been **redacted** — see
"Data-hygiene findings" below.

## Example 1 — Kansas per-payer SOP (payer-specific shape)

What the document actually is: **one SOP per payer**, each with a different
`stepType` mix. Mapped to `sop_templates` rows (match keys payer + state +
group) with Model A versioning:

| Payer (state=KS) | Steps as authored                                                                                                        | Step types                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| UnitedHealthCare | 1. Apply to Optum (email template to network_PhysicalHealth@optum.com, 4 named attachments) 2. Update in UHC portal      | `draft_email`, `online_form`       |
| Humana           | Facility-only roster update (providers NOT individually credentialed — contract terminated May 2025, re-application WIP) | `draft_email` (roster + W9 attach) |
| BCBS of Kansas   | Provider Network Application via the BCBSKS enrollment form URL; supervising provider name + NPI required fields         | `online_form` (portal link)        |
| BCBS KC          | Online join-our-network form — **Kansas City locations only**, not all KS                                                | `online_form`                      |
| Aetna            | Online network form; reference a prior completed submission as the guide                                                 | `online_form`                      |

What this example proves the E1.7b model must support:

- **Email-template steps with token interpolation.** The Optum email is a
  classic `emailTemplate` with tokens: `{{provider.name}}`,
  `{{facility.name}}`, `{{group.name}}`, `{{group.tin}}`, plus a
  group-constant (Optum Group Provider ID 683917) that is _data on the
  group×payer relationship_, not prose — E1.7b needs a place for
  payer-relationship constants (today it would be hard-coded in the template
  body; acceptable v1, log as debt).
- **Named attachment checklists per step** (credentialing form, license, COA
  form, W9) — `dataFields` today; the checklist semantics ("attach these 4
  things") should survive resolution.
- **Payer-level caveats that gate applicability**: Humana is
  facility-only/no-provider-credentialing; BCBS KC applies only to KC-metro
  locations. Model A versions the SOP body — but these caveats are _match/
  scope_ concerns. v1: caveats live as a step `detail`; the KC-metro scoping
  is a known gap (match keys are payer+state+group, not sub-state region) —
  log as E1.7b debt, do not invent a region key.
- **Contract-state dependence**: the Humana SOP is only correct while the
  group is out-of-network. When KFP's re-application lands, the SOP changes —
  exactly the Model A edit case: in-flight Humana roster tasks keep v1; the
  next generated case gets v2 (in-network procedure).

## Example 2 — General enrollment checklist (provider-onboarding shape)

The Fitness Physio SOP is **not payer-specific** — it is the per-provider
onboarding runbook: staff folder → verify acknowledgment + license on file →
update roster → HSPO → NPI (new grads) → CAQH → NPPES → PECOS → then one step
per payer (UHC Onboard Pro, BCBS KS, BC KC, Aetna, Cigna phone-in, Humana,
Tricare/TriWest).

What this example proves:

- **A "general" SOP exists and precedes payer SOPs.** Its payer steps are
  pointers into the per-payer SOPs of Example 1 — supporting the null-payer
  match key (`pickTemplate` already treats null-group as generic; E1.7b's
  authoring must let a step reference another SOP by name/link rather than
  duplicate it).
- **Mixed step targets**: file-system steps (Shared Drive folder), roster
  spreadsheet steps, registry portals (CAQH/NPPES/PECOS), payer portals with
  `portalKey` candidates (UHC Onboard Pro), and phone steps (Cigna — a step
  type today's `draft_email|online_form|pdf` enum does not cover; v1 maps
  phone steps to a plain step with `detail`, enum widening is additive debt).
- **Conditional steps**: "Register for NPI (new grads only)" — conditionality
  on provider attributes is not in the current step shape; v1 keeps it as
  prose in `detail`, flagged for the R4 build to consider an optional
  `condition` field (additive).
- **Cross-references to living documents** (roster xlsx, COI pdf, internal
  workflow docs): steps reference documents the system does not store —
  consistent with the E1.8 Option 3 stance (link out, no document vault yet).

## Data-hygiene findings (PM action)

- Source #2 contains a **plaintext shared login/password for a payer portal**
  (Humana Tricare section). It is redacted from this document and must never
  be committed to the repo or entered into SOP bodies when E1.7b lands —
  credentials belong in a secret store, and SOP steps should reference "use
  the shared Tricare login" without the value. Recommend the business rotates
  that password since it circulates in a shared PDF.
- Source #2 mixes KS PT content with NC nutrition content (Aetna NC nutrition
  contract, BEST Health TIN 851502637) — two different groups in one
  document. Model A versioning is per-SOP; the E1.7b authoring flow should
  encourage splitting per group×payer×state so version diffs stay meaningful.

## What E1.7b must deliver (grounded acceptance)

1. Both documents fully representable as versioned SOPs with no lost
   information other than the redacted credential.
2. Editing the Humana KS SOP (out-of-network → in-network) creates v2;
   a case generated before the edit resolves v1 tasks, after resolves v2 —
   task stamp `(sop_template_id, sop_version)` per the E2.2 contract.
3. Steps carry: label, detail, stepType, emailTemplate + tokens, attachment
   checklist (`dataFields`), portalKey where a portal is automatable.
4. Gaps logged as debt, not hacked: phone step type, conditional steps,
   sub-state (KC-metro) scoping, group×payer relationship constants.
