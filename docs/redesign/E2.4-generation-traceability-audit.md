# E2.4 — Generation Traceability & Audit

## Purpose and Context

Case generation is the first feature that creates many operational records
in one gesture. This closing epic makes every batch fully explainable after
the fact: **what ran, who ran it, what was proposed, what was created,
skipped, or excluded and why, and from which SOP versions** — the program's
"never silently" principle applied to generation.

It builds on the hooks the earlier epics planted: `case_generation_runs` +
`credential_cases.generation_run_id` (E2.1), reasoned exclusions (E2.0), and
task version stamps (E2.2) — and gives them a reading surface plus the
`audit_log` writes that tie generation into the existing append-only audit
spine.

## Personas Empowered

- **P1 Credentialing Manager** — answers "why does/doesn't this case exist"
  and reviews past runs with the business.
- **P5 Practice / Organization Owner** — the downstream beneficiary of an
  explainable credentialing pipeline (context persona).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `case_generation_runs` gains an outcome payload
  (per-row disposition: created / skipped-existing / excluded(reason) /
  failed(reason), stored at confirm time — the immutable record of what the
  preview showed) — additive columns on the E2.1 table or a child rows table;
  §5 decides the shape against the register.
- Implementation dependency: `writeAudit` entries (append-only `audit_log`,
  untouched semantics) for run-confirmed, case-created, exclusion-added/
  restored, reapply — additive entity/action types only.
- Read-only surface; no mutations beyond the audit/disposition writes at
  generation time.

## Features

### F2.4.1 — Run history

- **Description:** A generation-runs list (who, when, counts: proposed /
  created / skipped / excluded / failed) with a run detail view showing every
  row's disposition and reason exactly as decided at confirm time.
- **Persona:** P1.
- **Acceptance criteria:**
  - Every confirm produces exactly one run record with immutable
    dispositions.
  - Run detail links each created row to its case and each exclusion to its
    exclusion record.
- **Test/data scenario(s):** TS-57.

### F2.4.2 — Case provenance

- **Description:** Every case answers "where did I come from": the
  generating run (or "created manually by X"), the SOP template + version
  its tasks were stamped from, and its reapply lineage on the same case.
- **Persona:** P1, P2.
- **Acceptance criteria:**
  - Case detail shows run link, SOP name + version link (read-only version
    view), and creation actor/date.
  - Manual cases show the manual origin distinctly.
- **Test/data scenario(s):** TS-57.

```gherkin
Feature: Explainable batches
  Scenario: Business review of last quarter's generation
    Given the July run created 38 cases, skipped 2 existing, excluded 1 (panel closed)
    When P1 opens that run's detail
    Then all 41 dispositions are listed with reasons
    And the excluded row links to its persistent exclusion
    And each created case links back to this run
```

### F2.4.3 — Audit spine integration

- **Description:** Generation actions write `audit_log` rows via the
  existing `writeAudit` path (additive entity types), so generation activity
  appears in the same audit stream as everything else.
- **Acceptance criteria:**
  - Run confirm, each case creation, exclusion add/restore, and reapply
    each produce an audit row; `touches`/`status_history` semantics are
    untouched.
- **Test/data scenario(s):** TS-57.

## Scenario/Seed Data Mapping

- TS-57 — Full batch trace: mixed-disposition run, case provenance links,

## Dependencies

- E2.0 exclusions, E2.1 runs + creation, E2.2 stamps — all hard
  prerequisites; this epic closes R4.
- Existing `audit_log` / `writeAudit` (append-only, additive types only).

## Out of Scope / Non-Goals

- Undo/rollback of a run (cases are archived/worked individually via
  existing flows).
- Cross-org reporting on generation (Reporting Center candidate, later).
- Any mutation of append-only spines.
