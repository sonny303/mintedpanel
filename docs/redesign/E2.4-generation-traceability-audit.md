# E2.4 — Generation Traceability & Audit

## Purpose and Context

Case generation is the first feature that creates many operational records
in one gesture. This closing epic makes every batch fully explainable after
the fact: **what ran, who ran it, what was proposed, what was created,
skipped, or excluded and why, and from which SOP versions** — the program's
"never silently" principle applied to generation.

It builds on the hooks the earlier epics planted: `case_generation_runs` +
`credential_cases.generation_run_id` (E2.1), reasoned exclusions (E2.0), and
task version stamps (E2.2) — and gives them a reading surface plus the
`audit_log` writes that tie generation into the existing append-only audit
spine.

## Personas Empowered

- **P1 Credentialing Manager** — answers "why does/doesn't this case exist"
  and reviews past runs with the business.
- **P5 Practice / Organization Owner** — the downstream beneficiary of an
  explainable credentialing pipeline (context persona).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `case_generation_runs` gains an outcome payload
  (per-row disposition: created / skipped-existing / excluded(reason) /
  failed(reason), stored at confirm time — the immutable record of what the
  preview showed) — additive columns on the E2.1 table or a child rows table;
  §5 decides the shape against the register.
- Implementation dependency: `writeAudit` entries (append-only `audit_log`,
  untouched semantics) for run-confirmed, case-created, exclusion-added/
  restored, reapply — additive entity/action types only.
- Read-only surface; no mutations beyond the audit/disposition writes at
  generation time.

## Features

### F2.4.1 — Run history

- **Description:** A generation-runs list (who, when, counts: proposed /
  created / skipped / excluded / failed) with a run detail view showing every
  row's disposition and reason exactly as decided at confirm time.
- **Persona:** P1.
- **Acceptance criteria:**
  - Every confirm produces exactly one run record with immutable
    dispositions.
  - Run detail links each created row to its case and each exclusion to its
    exclusion record.
- **Test/data scenario(s):** TS-57.

### F2.4.2 — Case provenance

- **Description:** Every case answers "where did I come from": the
  generating run (or "created manually by X"), the SOP template + version
  its tasks were stamped from, and its reapply lineage on the same case.
- **Persona:** P1, P2.
- **Acceptance criteria:**
  - Case detail shows run link, SOP name + version link (read-only version
    view), and creation actor/date.
  - Manual cases show the manual origin distinctly.
- **Test/data scenario(s):** TS-57.

```gherkin
Feature: Explainable batches
  Scenario: Business review of last quarter's generation
    Given the July run created 38 cases, skipped 2 existing, excluded 1 (panel closed)
    When P1 opens that run's detail
    Then all 41 dispositions are listed with reasons
    And the excluded row links to its persistent exclusion
    And each created case links back to this run
```

### F2.4.3 — Audit spine integration

- **Description:** Generation actions write `audit_log` rows via the
  existing `writeAudit` path (additive entity types), so generation activity
  appears in the same audit stream as everything else.
- **Acceptance criteria:**
  - Run confirm, each case creation, exclusion add/restore, and reapply
    each produce an audit row; `touches`/`status_history` semantics are
    untouched.
- **Test/data scenario(s):** TS-57.

## 5. Technical Considerations & Enablers

_Independent-reviewer-owned (Claude Code, per `REVIEW-HANDOFF.md`). Verified
2026-07-13 against the baseline schema
(`20260704210000_baseline_live_schema.sql` — `audit_log` DDL,
`credential_cases` columns, the `create_case_with_tasks` RPC body), the two
action-type widening migrations (`20260705190000_audit_log_read_action_type.sql`,
`20260712150200_audit_log_delete_action_type.sql`), `src/lib/audit.ts`,
`src/services/cases.ts`, `docs/data-model/table-register.md` (register + design
rules), `docs/redesign/seed-universe.md` (TS-57 + the E2.4 coverage row), the
sibling drafts E2.0–E2.3 / E1.7b, and `uiux-component-guide.md`. E2.4 is a
reading surface over hooks its prerequisites plant, plus one genuinely new
storage decision (the disposition payload) and a handful of `writeAudit`
calls._

- **TE-1 — Disposition storage: a child rows table, not columns or a jsonb
  blob on the run (the shape decision this epic delegates to §5).** Per-row
  dispositions vary by candidate row — exactly the register's grain rule 1
  ("a field that varies by state, purpose, or payer is a child row keyed by
  that dimension, never a new column"). A jsonb outcome payload on
  `case_generation_runs` would also make F2.4.1's per-row links (row → case,
  row → exclusion) unenforceable. Add one additive table (working name
  `case_generation_run_rows`), one row per candidate key per run:
  `(id uuid pk, org_id uuid NOT NULL → organizations, run_id uuid NOT NULL →
case_generation_runs, provider_id uuid NOT NULL → providers, group_id uuid
NOT NULL → provider_groups, payer_id uuid NOT NULL → payers, state text NOT
NULL CHECK (state ~ '^[A-Z]{2}$'), disposition text NOT NULL CHECK
(disposition IN ('created','skipped_existing','excluded','failed')), reason
text, case_id uuid NULL → credential_cases, exclusion_id uuid NULL →
case_generation_exclusions, created_at timestamptz NOT NULL DEFAULT now())`.
  Shape CHECKs: `disposition = 'created' → case_id IS NOT NULL`;
  `disposition IN ('excluded','failed') → reason IS NOT NULL`. Constraints/
  indexes: `UNIQUE (run_id, provider_id, group_id, payer_id, state)` (leading
  `run_id` covers that FK) + FK cover indexes on `provider_id`, `group_id`,
  `payer_id`, `case_id`, `exclusion_id`, `org_id` (the E0.10
  `20260710140000_fk_index_coverage.sql` convention). `skipped_existing` rows
  should also set `case_id` to the blocking case — it makes "why doesn't this
  case exist → it already does" a link, not a hunt. Migration is additive,
  applied repo + hosted per `docs/migration-baseline.md`, regenerates
  `src/integrations/supabase/types.ts`, and adds the table-register row
  (ledger layer — it is an immutable record, see TE-2) **in the same PR**
  (AGENTS.md). `case_generation_runs` itself (who/when/counts) and
  `credential_cases.generation_run_id` are E2.1 deliverables — this epic must
  not re-create them; if E2.1's review lands stored counts on the run row,
  prefer deriving counts from these child rows at read time so the two can
  never disagree (single-writer rule; a stored-counts vs child-rows mismatch
  is otherwise silently possible on a mid-batch abort).
- **TE-2 — Immutability is enforced by policy shape, not convention.**
  F2.4.1 requires "immutable dispositions … exactly as decided at confirm
  time". Mirror the `audit_log` policy shape on the new table: enable RLS;
  member SELECT (`org_id IN (SELECT user_org_ids())`), writer INSERT
  (`user_role(org_id) IN ('specialist','admin')` — generation confirm is a
  writer flow), and **no UPDATE or DELETE policy** (and no UPDATE/DELETE in
  the grant floor, per the `20260710120000_stage0_grant_hardening.sql`
  posture). Every insert sets `org_id` from the active org; `org_id` is
  deliberately denormalized (derivable via `run_id`) so RLS filters directly —
  the E1.5 TE precedent ("keep it and set it on insert"). Rows are written
  once, when their outcome is known: `skipped_existing`/`excluded` rows at
  confirm, `created`/`failed` rows as each `create_case_with_tasks` call
  resolves (E2.1's "batch is N idempotent calls"). A mid-batch crash then
  leaves a run whose row count is visibly short of its proposed count —
  honest and queryable, with no UPDATE needed anywhere.
- **TE-3 — Audit spine: zero migrations needed; verified against the live
  CHECK.** `audit_log.entity_type` is unconstrained `text NOT NULL` (baseline
  DDL) — new entity types are free and additive, exactly as the epic assumes.
  `audit_log.action_type` IS CHECK-constrained; after the two widenings the
  allowed set is `CREATE / UPDATE / STATUS_CHANGE / TOUCH_LOGGED /
TERMINATION / READ / DELETE`, matching the `AuditActionType` union
  (`src/types/index.ts`). Every F2.4.3 event maps onto existing values, so
  **no CHECK-widening migration is required**:
  - run confirm → `CREATE` / entity `case_generation_run` / `after` = counts
    summary + run id (never the disposition payload — that lives in TE-1's
    table; don't duplicate it into audit jsonb);
  - each case creation → **already written**: the `create_case_with_tasks`
    RPC body inserts `CREATE`/`credential_case` and `CREATE`/`task` rows per
    case (baseline lines ~588–612). E2.1's additive RPC extension must keep
    those writes; E2.4 verifies coverage rather than adding a duplicate
    client-side write;
  - exclusion add → `CREATE` / entity `case_generation_exclusion`; restore →
    `UPDATE` (with the TE-5 void semantic) or `DELETE` (if hard delete is
    kept);
  - reapply → the existing `STATUS_CHANGE` path (`updateCaseStatus` already
    writes `STATUS_CHANGE`/`status_history`, `src/services/cases.ts`) plus a
    distinguishing `description`; the regenerated tasks ride the same
    `CREATE`/`task` pattern.
    Browser writes go through the existing `writeAudit`
    (`src/lib/audit.ts`); its insert RLS already requires specialist/admin,
    which matches the P1 writer flows here. `touches`/`status_history`
    semantics untouched, as the AC requires.
- **TE-4 — Every provenance source for F2.4.2 exists or is a named
  prerequisite hook; nothing new is invented.** `credential_cases.created_by`
  and `created_at` are baseline columns (the RPC sets `created_by` from
  `auth.uid()`) → "creation actor/date". `generation_run_id` (E2.1) → run
  link; NULL run id + `created_by` → "created manually by X" (E2.1 F2.1.4
  already pins "indistinguishable … except for its null generation-run id").
  `(tasks.sop_template_id, tasks.sop_version)` (E1.7b migration, stamped by
  E2.2) → SOP name + version; the read-only version view is E1.7b F1.7b.2 —
  E2.4 links to it, never builds a second one. Note the overlap: E2.2
  F2.2.1's AC already ships the "generated from <SOP name> v<N>" case-surface
  line; E2.4's F2.4.2 extends that block (run link, actor/date, manual
  origin), it does not re-implement it. Actor display names resolve at read
  time via the existing `profiles` author-resolution pattern
  (`src/services/providerCases.ts`) or ride denormalized like
  `audit_log.user_name` — either is fine; don't invent a third pattern.
- **TE-5 — Exclusion-record permanence is a cross-epic gate (the one real
  design decision this epic forces).** F2.4.1 requires every excluded row to
  link to "its persistent exclusion", but E2.0 F2.0.2 leaves restore as
  "delete/void the exclusion". If restore hard-DELETEs, the immutable run
  rows point at nothing. Resolve in E2.0's build as **void, not delete**: a
  status flip (`active | voided`, the E1.5 archive-not-DELETE precedent),
  with E2.0's "unique on the 4-part key" becoming a partial unique index
  (`WHERE status = 'active'`) or restore/re-exclude flipping the same row.
  Belt-and-braces regardless of that outcome: `exclusion_id` FK is
  `ON DELETE SET NULL`, and the run row's own `reason` column (TE-1) snapshots
  the reason at confirm time, so run detail degrades to reason-without-link
  rather than breaking. Recorded as redline 1 for the E2.0 review session to
  reconcile.
- **TE-6 — Reapply lineage is derived, never stored.** A reapply is a status
  transition + a new task set on the same case (E2.1 F2.1.3). Its lineage is
  already fully recoverable from append-only data: `status_history` rows,
  task `created_at` clusters with their differing `(sop_template_id,
sop_version)` stamps (E2.2 F2.2.3 restamps at current), and the TE-3 audit
  rows. Render it as a derived timeline on case detail; add **no** lineage
  table, cycle column, or stored counter (the E1.0 derived-progress rule).
  Redline 5 asks the author to pin this with an AC, since the F2.4.2
  description promises it but no AC covers it.
- **TE-7 — Surfaces build entirely from the approved inventory; no new
  primitive, no DESIGN-DEBT row expected.** Run list + run detail: `table`
  primitive with custom cell markup (disposition pills via `badge`
  `rounded-full`, status semantics only — `skipped/excluded` neutral,
  `failed` destructive), `collapsible` or `tabs` (both available) for the
  detail's disposition sections, `PageHeader` on the route, `skeleton`
  loading, designed empty state ("no runs yet" + the generation CTA). Case
  provenance: a read-only block on the existing case detail
  (`src/routes/cases.$id.tsx`) composed of existing primitives + links.
  Feature components live in `src/components/[module]/` (suggest
  `src/components/generation/`), never `ui/`/`layout/`; **no
  `src/components/layout/*` changes** — nothing here touches the shell, so no
  protected-file authorization is needed beyond the additive `writeAudit`
  call sites (TE-11). Follow the design-system token deltas (4px pill radius
  etc.) per `uiux-component-guide.md` §"UX design system alignment".
- **TE-8 — Layering and reads.** Services → hooks → components as usual: a
  read service (working name `src/services/generationRuns.ts`) owning the
  runs/rows reads (org-scoped under RLS from the browser, the current-UI
  data path per locked decision 1 — no `/api` route; the extension pulls
  nothing here), a `useGenerationRuns` hook with org-scoped `queryKeys`
  entries, and any count/summary derivation in a pure tested `src/lib/`
  module. Run detail joins display names (provider/group/payer/profiles) at
  read time; the run rows store FKs + reason only — no denormalized display
  names, no PHI columns (nothing beyond ids, enum, reason text ever lands in
  this table).
- **TE-9 — Authoritative table trace (the epic body omits one; AGENTS.md
  requires it).** Reads: `case_generation_runs`, `case_generation_run_rows`,
  `case_generation_exclusions`, `credential_cases`, `tasks`,
  `sop_templates` + `sop_template_versions` (names for the version link),
  `providers`/`provider_groups`/`payers` (display names), `profiles` (actor
  names), `status_history` (reapply timeline), `audit_log` (only if run
  detail surfaces its audit rows; optional). Writes:
  `case_generation_run_rows` (INSERT-only, TE-2) and `audit_log`
  (append-only inserts via `writeAudit`/RPC). Reconciled against
  `docs/data-model/table-register.md`: every existing table above has a
  register row; the three `case_generation_*` tables are new — E2.0/E2.1 own
  their register rows, this epic adds the `case_generation_run_rows` row in
  its migration PR.
- **TE-10 — Verification gates.** Unit-test the pure derivations (disposition
  counts, reapply-timeline assembly, manual-vs-generated origin) in the
  `src/lib/` module suite; e2e for **TS-57** (mixed-disposition run: detail
  lists every disposition with reason; created rows link to cases; the
  excluded row links to its exclusion; audit rows exist for confirm/create/
  exclude — seeded over the TS-48–TS-52 states, **no new baseline fixtures**
  per the seed-universe coverage table). Must pass `npm run lint`,
  `npx tsc --noEmit`, `npm run test`, `npx prettier --check .`, and touched
  Playwright specs. Migration applied repo + hosted with the types regen in
  the same PR.
- **TE-11 — Build order + cross-service authorization.** E2.4 builds last
  (roadmap: sequential E1.7b → E2.0 → … → E2.4); E2.0/E2.1/E2.2 must be
  merged to `redesign` first — the run/exclusion tables and stamps this epic
  reads do not exist until then. E2.4's PR is explicitly authorized to make
  **additive** edits to the services those builds create (adding `writeAudit`
  calls for exclusion add/restore and the run-confirm write, and inserting
  TE-1 rows from the confirm loop) — small, traceable call-site additions,
  not behavior changes. If the E2.0/E2.1 review sessions choose to land their
  own audit calls at build time instead, E2.4's job narrows to verifying
  coverage — either sequencing is acceptable; silently double-writing audit
  rows is not.

### Likely tech debt / risk to contain

- **Partial-batch honesty.** With rows written as outcomes resolve (TE-2), an
  aborted batch yields a run whose rows < proposed. Surface that state in run
  detail ("run ended early — N of M candidates recorded") rather than
  papering over it; do not add a mutable run status to "fix" it.
- **Audit payload discipline.** `create_case_with_tasks` already stores
  `to_jsonb(v_case)` in `audit_log.after` (case rows carry no SSN/DOB — fine);
  the new writes should stay at ids + counts + reasons. Never token values,
  never the full disposition payload.
- **P5 is a context persona only.** No owner-facing surface ships here; the
  owner view (`/client-progress`) is untouched. Don't let "reviews past runs
  with the business" pull a P5 surface into scope — that is the Reporting
  Center deferral already recorded in Non-Goals.

### Reviewer redlines (independent review per REVIEW-HANDOFF, 2026-07-13)

1. **should-fix (cross-epic)** — F2.4.1's AC "each exclusion links to its
   exclusion record" collides with E2.0 F2.0.2's unresolved restore semantic
   "(delete/void the exclusion)". A hard delete dangles the immutable run
   row's link. E2.4's requirement forces the **void** semantic (status flip,
   E1.5 archive precedent) — or, minimally, `ON DELETE SET NULL` + the
   reason snapshot (TE-5). Needs a matching line in E2.0 (its review session
   or the author), not silent divergence.
2. **should-fix** — Personas Empowered lists only P1 and P5, but F2.4.2 names
   "Persona: P1, P2". P2 Credentialing Specialist is a canonical persona
   (used by E2.1–E2.3) and genuinely benefits ("where did this case come
   from" is a P2 question) — add P2 to the section, or drop it from F2.4.2.
3. **should-fix** — F2.4.3 has no Persona line, and none of F2.4.1–F2.4.3
   carries a **Benefit hypothesis**; the template requires
   persona + benefit hypothesis per feature (EPIC-TEMPLATE.md, and the
   REVIEW-HANDOFF checklist item 1 pins it). One line each suffices.
4. **nit** — Component & Data Constraints says "no mutations beyond the
   audit/disposition writes **at generation time**", but F2.4.3's exclusion
   add/restore and reapply audits occur outside generation time. Wording
   only; the mutation set itself is correctly scoped.
5. **nit** — F2.4.2's description promises "reapply lineage on the same
   case" but no acceptance criterion covers it. Add an AC (e.g. "a reapplied
   case's detail shows each cycle's status transition and task-set stamp in
   order"), derived per TE-6 — otherwise the promise is untestable.
6. **nit** — The Scenario/Seed Data Mapping uses a bullet where the template
   specifies a table (consistent with the R4 siblings, so style-only), and
   the epic body carries no explicit tables-read/tables-written trace
   (AGENTS.md database rule). TE-9 supplies the authoritative trace; the
   author may fold it into the body or leave TE-9 as the record.

### Open questions for the PM

1. **Where does Run History live in the Sidebar IA v2?** The epic names the
   surface but not its home. Reviewer recommendation (no new top-level nav
   item): reach the run list from the generation surface itself (E2.0's
   entry point) and let every case detail deep-link its run (F2.4.2); a
   standalone route (e.g. under the work area) stays URL-reachable without a
   nav slot. Placement is a product call — deciding it here would expand
   scope.
2. **Retention expectation for run records.** Dispositions are immutable and
   append-only forever (TE-2). If the business expects pruning/archiving of
   old runs (e.g. after a year), that is a later additive decision — flagging
   now so "immutable" is a conscious commitment, not a default.
