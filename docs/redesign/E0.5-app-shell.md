# E0.5 — Secure One-Time Org Data Capture Link

## Purpose and Context

This epic enables the Credentialing Manager (P1) to collect required organization data securely from an external recipient (owner/contact/office manager) via a one-time, email-specific form link. The flow ensures regulated, non-redundant intake of CRM/party/contact data for onboarding and billing. Only one link can be open per org; only the intended recipient can submit, and submission is blocked unless all required fields are present. Demo/test support references seed-universe data (e.g., Lone Star Rehab Group, Rose City Rehab Collective).

## Personas Empowered

- P1 Credentialing Manager (Sowmya)
- P5 Practice Owner
- P6 Office Manager (alternate recipient role in demo/test)

## Component & Data Constraints

- Only current UI library, Party/Contact schema fields, no freeform fields or notes
- Secure, recipient-specific link: only the intended email allows entry
- One link per org at a time; link expires after 72h or on first use
- Submission is blocked unless all required fields are complete
- All merged data ties to correct party row for audit, but no UI notification or review
- Supports/integrates seed-universe test/demos (Lone Star Rehab Group, Rose City Rehab Collective)

## Features

### F0.5.1 — Generate secure, email-tied link

- **Description:** P1 selects or enters recipient email; system sends a unique link to that address, tied to the target party (pre-existing or ad hoc)
- **Persona:** P1
- **Benefit hypothesis:** Dramatically reduces failure modes around voice/email transfers of onboarding info; accelerates time to clean, valid org records
- **Acceptance criteria:**
  - Can only generate a new link if no active link is open for the org
  - Recipient email must be party-typed and validated
  - Email copy can be customized (future-ready)
- **Test/data scenario(s):** TS-7 (Lone Star Rehab Group owner, link sent + consumed); TS-13 (Rose City alt recipient / office manager)

```gherkin
Feature: Secure, recipient-specific link to onboard data
  Scenario: P1 issues a link to lone.star.owner@seed.test
    Given "Lone Star Rehab Group" exists with owner
    When P1 generates a data capture link for lone.star.owner@seed.test
    Then only that address can submit the required data within 72h
```

### F0.5.2 — Single-use, expiry and used-state handling

- **Description:** The link is valid for a single submission/use or 72 hours—whichever comes first. If used or expired, subsequent visits show lockdown messaging.
- **Persona:** P5, P6 (recipient); P1 (sees status in UI)
- **Benefit hypothesis:** Enforces data consistency, prevents confusion from dupe or reused requests, gives the operator audit security
- **Acceptance criteria:**
  - Once link is used, any visitor after gets "Form already completed" message
  - If time expires before use, gets "Form expired, contact operator"
  - P1 can always re-issue
- **Test/data scenario(s):** TS-7 (used-then-revisited); TS-13 (expired-before-use)

```gherkin
Feature: Lock down used/expired capture links
  Scenario: Attempt to use link twice
    Given office manager receives capture link
    When they submit and return to form afterwards
    Then they see "This form is already completed"
```

### F0.5.3 — Field capture, data completeness, and merging

- **Description:** The external recipient must fill _all_ required organization/party fields. Submission is blocked otherwise. Result overwrites the party row for the recipient (Party table, not a local draft only).
- **Persona:** P5, P6 (fills form); P1 (sees clean, updated org/party)
- **Benefit hypothesis:** Prevents incomplete or junk records; aligns with compliance
- **Acceptance criteria:**
  - Must fill all required Party/CRM fields or cannot submit
  - If recipient data already present, can update/overwrite; all required fields must be present after save
  - No deletions possible, no multi-party field splitting
- **Test/data scenario(s):** TS-7 (Rose City recipient completes required fields)

```gherkin
Feature: Required fields for one-time CRM capture
  Scenario: Recipient skips required phone
    Given seeded org is "Rose City Rehab Collective"
    When office manager receives link and leaves phone blank
    Then form will not submit and asks for phone number
```

### F0.5.4 — Email delivery pattern and content

- **Description:** Email template must state recipient by name, explain link intent, note expiry window, and explicitly say "No login will be created." Content customizable in future.
- **Persona:** P1 (controls/edits message); P5/P6 (recipients)
- **Benefit hypothesis:** Ensures clear communication and supports Minted Panel's first secure self-serve onboarding comms pattern
- **Acceptance criteria:**
  - Message always states org, recipient, expiry, security
  - No login/pw creation required
  - "Contact the operator if issues" fallback included

## 5. Technical Considerations & Enablers — Devin section

This section is owned by Devin.

> **This is the first Stage 0 epic that crosses the app's trust boundary.** Every data path today requires an authenticated session under org-scoped RLS; E0.5's premise is an _unauthenticated external party_ submitting data. Two decisions were locked by the PM before build (below), and the PM directed adding an inbound flow (F0.5.5 / TE-7).

### PM decisions (RESOLVED — logged in `CLARIFICATIONS_NEEDED.md`)

- **BD-1 — Unauthenticated access model. RESOLVED: lightweight token link, no login.** Public token-validated route (`/capture/:token`) whose reads/writes go through a `SECURITY DEFINER` RPC that hash-validates the token server-side and touches only the single party/org the token authorizes — **no anonymous GoTrue session, no login ceremony** (consistent with the E0.0 "no login" default). PM confirmed the form data is basic org info (name/address/phone/contact email), so the token is not securing secret data — it exists only to bind a link to one org's record (prevent a forwarded/guessed link overwriting the wrong org or revealing which org it targets). An unguessable random token achieves that with zero login friction.
- **BD-2 — Email delivery. RESOLVED: Stage 0 renders copy-able email text only, no send infra.** `create_capture_link` returns the URL + the F0.5.4 template copy for P1 to send manually. Real transactional sending (Resend/Postmark/SES + domain verification) is a separate future decision, not part of Stage 0.

### Open-implementation-question resolutions (Devin, 2026-07-09)

- **Recipient maps to the E0.3 party model, not a parallel record.** The owner party already exists from E0.1; the capture **claims/updates that existing party** (F0.5.3 "overwrites party row"), it does not create a second owner record. For a non-owner recipient (P6 office manager, TS-13) the link targets the party bound to the recipient email — created ad hoc as a `person` party if none exists, then updated on submit. No new contact store (consistent with E0.2/E0.3 F0.3.6).
- **"One active link per org" is an invariant, not just UI.** Enforced in the schema (partial unique index on `org_id WHERE state = 'active'`), so a concurrent second issue fails deterministically rather than racing.
- **Used/expired are not dead-ends.** F0.5.2's lockdown pages ("already completed" / "expired, contact operator") are the _intended_ terminal states and are explicitly allowed here — they do **not** violate E0.4's "no dead-end states" rule (that rule governs the authenticated workspace, not a deliberately single-use external link). Both states carry the "contact the operator" fallback per F0.5.4.
- **Token is a credential.** Store only a hash of the token (never the raw token) in the DB; the raw token lives only in the emitted URL. Never log the raw token. Validation compares hashes.
- **"Party-typed" recipient email (F0.5.1 AC).** Interpreted as: the recipient email is validated with the existing `src/lib/contactValidation.ts` (format + typo nudge) and resolved to (or provisioned as) a party before a link can issue — no freeform, per the constraints.

### Reviewer-added scope — PM-directed inbound "contact us" (2026-07-09)

The PM directed folding an **inbound lead-capture** ("contact us now", like the homepage) into E0.5 alongside the outbound targeted link. These are two distinct flows sharing the same form component:

- **Outbound (F0.5.1–F0.5.4, as authored):** _you_ have someone's email tied to an **existing org + party**; a targeted single-use token link tops up that record. One active link per org, recipient-email binding, party overwrite.
- **Inbound (F0.5.5, reviewer-proposed below):** a **stranger** with **no org/party yet** submits interest via a public form; it creates a new **lead**. The one-active-link-per-org rule, recipient-email binding, and party-overwrite do **not** apply.

**Non-goal reconciliation:** the epic's "No 'anyone with link' flows" and "no P1 review (auto-save only)" non-goals were written for the outbound link. The PM's inbound direction overrides them **for the inbound flow only**; outbound keeps both non-goals. Inbound leads ARE triaged by P1 (they must not silently write into real orgs).

- **F0.5.5 (reviewer-proposed, pending ChatPRD ratification) — Inbound contact-us lead capture.** A public `/contact` form (no token) lets an unauthenticated visitor submit org name + contact fields. Submission creates a triaged **lead**, NOT a live org. P1 sees inbound leads in the workspace and converts a lead into a prospect org (reusing E0.1 `create_organization`). Acceptance: required fields enforced; spam-resistant; a submitted lead appears in P1's inbound list; converting a lead creates a `prospect` org + owner party; no auto-creation of orgs from raw submissions.
  - **Recommended default I built the enabler on (one product nuance for your awareness):** inbound submissions land as **triaged leads** that P1 converts, rather than auto-creating a prospect org on submit. This prevents spam orgs polluting the portfolio. Say the word if you'd rather inbound auto-create a `prospect` org directly.

### Technical enablers (Devin populates)

- **TE-1 — Capture-link table + state model.** Additive migration (repo-first + hosted): `party_capture_links` (`id`, `org_id` [org-scoped RLS as usual], `party_id`, `recipient_email`, `token_hash`, `state` `active|used|expired|revoked`, `expires_at` [issue + 72h], `used_at`, `created_by`, `created_at`). Partial unique index `(org_id) WHERE state = 'active'` enforces the single-active-link invariant. This is the additive "small column/table, not overloading `lifecycle_state`" recommended in the E0.5 pre-flight. Regenerate types after DDL.
- **TE-2 — Issue-link RPC (operator side, authenticated).** `create_capture_link(p_org_id, p_party_id, p_recipient_email)` SECURITY DEFINER, EXECUTE to `authenticated`: validates the email, resolves/provisions the recipient party, rejects if an active link already exists (BD-1 invariant), generates a random token, stores its hash, returns the raw token once for URL assembly. Writes an `audit_log` row. Frontend: `src/services/captureLinks.ts` → `src/hooks/useCaptureLinks.ts`, surfaced on the org workspace (`/get-started`) reusing existing primitives.
- **TE-3 — Public capture route + validate/submit RPCs (recipient side, unauthenticated).** `/capture/:token` renders outside the authenticated shell. `validate_capture_token(p_token)` (SECURITY DEFINER, EXECUTE to `anon`) returns `{ state, org_name, recipient_name, required_fields }` or the used/expired lockdown state — never leaks other orgs' data. `submit_capture(p_token, p_payload jsonb)` validates completeness server-side, writes into the party row, flips the link to `used`, sets `used_at`, writes audit. Both are hash-validated; grants scoped narrowly to these two functions only. Form assembled from existing `ContactFields`/primitives; no new UI library.
- **TE-4 — Operator link status surface.** P1 sees per-org link state (none / active-until / used / expired) and a "re-issue" action (F0.5.2 "P1 can always re-issue" — re-issue revokes any prior and creates a fresh one). Composed from existing primitives on `/get-started`.
- **TE-5 — Email template rendering (BD-2 default = copy/send).** A pure template function producing the F0.5.4 copy (org, recipient name, intent, expiry window, "No login will be created," operator-contact fallback) + the link URL, rendered for P1 to copy. Unit-tested on content. If BD-2 later chooses real sending, this template is the payload — no rework.
- **TE-6 — Seed/test extension.** TS-7 already seeds Lone Star with owner + link-pending readiness; extend with a link fixture (active/used/expired states as an L2 mutation helper). TS-13 (Rose City alt recipient / office manager) added to seed-universe. Playwright: issue → recipient completes → used-lockdown, plus expired-lockdown; the public routes are testable via the documented mock harness (no real backend reachable in-sandbox).
- **TE-7 — Inbound lead-capture (F0.5.5).** Additive migration: `inbound_leads` (`id`, `org_name`, contact fields [name/email/phone/address], `status` `new|converted|dismissed`, `converted_org_id` nullable FK, `created_at`). NOT org-scoped on insert (there is no org yet) — insert is via a `SECURITY DEFINER` RPC `submit_inbound_lead(p_payload jsonb)` granted to `anon` that validates required fields and inserts a `new` lead; a hidden honeypot field + required-field checks provide baseline anti-abuse (no new dependency; no CAPTCHA). Public route `/contact` renders outside the shell, reusing the same `ContactFields` form. Operator side: `listInboundLeads` (RLS: any authenticated org member of the tenant that owns triage — Stage 0 default, all internal users see the shared inbound queue) → an inbound-leads surface in the workspace with a **Convert** action calling E0.1 `create_organization` (sets `prospect`, links `converted_org_id`) and a **Dismiss** action. Regenerate types after DDL. Layering: `src/services/inboundLeads.ts` → `src/hooks/useInboundLeads.ts`; existing primitives only.

### Tech-debt findings (Devin populates)

- **TD-1 — Public unauthenticated surface is new attack surface.** First route reachable without a session. Token entropy (≥128 bit), hash-only storage, rate-limiting on `validate_capture_token`, and the narrow definer grants are the controls; must be explicitly covered by tests or it rots. No PII beyond the single authorized party is ever returned.
- **TD-2 — No real email sending in Stage 0 (BD-2 default).** P1 copies/sends the link manually. If deliverability/scale matters, a transactional provider + domain verification is a follow-up dependency decision — deliberately deferred, not forgotten.
- **TD-3 — Expiry is time-based, not a background job.** `expires_at` is evaluated at validate-time (lazy expiry); there is no sweeper flipping rows to `expired`. State returned to the recipient is correct; the stored `state` may lag until touched. Acceptable for Stage 0; a sweep job is future work.
- **TD-4 — Ad-hoc recipient parties can accumulate.** Issuing to a never-before-seen email provisions a party; if the link is never used, an orphan person party remains (no deletion in Stage 0, per non-goals). Identity resolution / cleanup is deferred (same class as E0.3 TD-2).
- **TD-5 — Inbound is a second public, unauthenticated write surface (F0.5.5/TE-7).** `submit_inbound_lead` is `anon`-executable with no token gate at all (that's the point of a public contact form), so it is the most abuse-exposed endpoint in Stage 0. Baseline controls are required-field validation + honeypot + rate-limiting; a real spam problem would need CAPTCHA or moderation (new dependency — deferred). Leads never touch live orgs until P1 converts, which contains the blast radius.
- **TD-6 — Inbound leads live outside org-RLS until converted.** `inbound_leads` rows have no `org_id` at insert (no org exists yet); the shared internal triage queue is the Stage 0 model. When multi-tenant triage routing matters, this table needs a tenant/routing column — deferred.
