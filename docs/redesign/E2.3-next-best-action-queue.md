# E2.3 — Next-Best-Action Queue (Post-Generation Landing)

## Purpose and Context

After generating 40 cases, "what do I do first?" needs an answer, not a wall
of rows. The `[r4]` Q5 decision: land on a **next-best-action queue ordered
by known upcoming deadlines** — provider start dates (E1.4
`start_date`), location launch dates, recredentialing deadlines, and task due
dates — so the most time-critical work surfaces first.

The queue is a fully **derived** view (the E1.0 derived-progress rule): no
stored priority, no dirty flags — it recomputes from cases, tasks, deadline
sources, and readiness every render. It is also the natural everyday home
for P2, not just a post-generation landing.

## Personas Empowered

- **P2 Credentialing Specialist** — works the queue top-down.
- **P1 Credentialing Manager** — lands here after generation; sees where the
  batch's urgency concentrates.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: prioritization is a pure ranked-reduction
  module in `src/lib/` (tested): inputs = open cases + their next actionable
  task, deadline signals (provider `start_date`, location launch date where
  modeled, recredentialing dates, task `dueOffsetDays`-derived due dates,
  `followUpEveryDays` cadence from stamped SOP content), readiness (E1.8);
  output = ordered queue entries with a human-readable "why this is next".
- Deadline-source honesty: only deadlines that exist in the schema today are
  ranked; sources not yet modeled (e.g. location launch date, if absent) are
  named in the epic's gap list and added additively or deferred — the review
  session verifies against the live schema in §5.
- Implementation dependency: no new tables expected (derived view); if a
  snooze/dismiss affordance is added it must be an explicit additive table,
  not a mutation of case/task rows.

## Features

### F2.3.1 — Deadline-ordered queue

- **Description:** A queue of "next actions" (one entry per open case's next
  actionable task), ordered by the earliest relevant deadline, each entry
  showing case identity (provider × group × payer × state), the action, the
  driving deadline, and the derivation reason.
- **Persona:** P2, P1.
- **Acceptance criteria:**
  - Ordering follows the earliest applicable deadline among: provider start
    date, recredentialing deadline, task due date, follow-up-cadence
    next-touch date; ties broken deterministically (documented).
  - Every entry states _why_ it ranks where it does.
  - Blocked/red-readiness cases surface their blocker as the action.
- **Test/data scenario(s):** TS-55.

```gherkin
Feature: Deadlines drive the order
  Scenario: Start date beats due offset
    Given Jane's case has a task due in 10 days
    And Marco starts seeing patients in 4 days with an unsubmitted application
    When P2 opens the queue
    Then Marco's submission ranks above Jane's task
    And Marco's entry says it is driven by his provider start date
```

### F2.3.2 — Post-generation landing

- **Description:** Confirming generation (E2.1) lands on the queue filtered
  to the new batch (generation-run id), with a one-click "all work" toggle.
- **Persona:** P1.
- **Acceptance criteria:**
  - Landing shows the batch's entries in deadline order with a created/
    skipped summary banner.
  - Clearing the filter shows the full org queue; the filter is URL-state,
    shareable.
- **Test/data scenario(s):** TS-55.

### F2.3.3 — Follow-up cadence surfacing

- **Description:** Tasks whose stamped SOP steps carry `followUpEveryDays`
  generate recurring "touch due" queue entries (derived from the last touch
  of that case — append-only `touches` is read, never written by the queue).
- **Persona:** P2.
- **Acceptance criteria:**
  - A case 14+ days since last touch with a 14-day cadence step surfaces a
    follow-up entry; touching the case (existing flows) re-derives it away.
- **Test/data scenario(s):** TS-56.

- **TE-1 — Deadline-source schema audit (the "gap list" the Component & Data
  Constraints promise; this section is it).** Verified column-by-column:

  - **Provider start date — EXISTS, two columns; the epic's "E1.4
    `start_date`" attribution is imprecise.** `providers.start_date date`
    (baseline; captured by the E1.3 roster form `ProviderRosterForm.tsx`) is
    the provider-level "starts seeing patients" date the F2.3.1 gherkin
    describes. E1.4's column is `provider_facility_assignments.start_date`
    (per-location practice start, captured by `AssignmentEditor.tsx`).
    **Rule for the build:** the provider-start signal is
    `providers.start_date`; where it is null, the earliest **future**
    `provider_facility_assignments.start_date` for the provider stands in.
    Past-dated start dates are history, not deadlines — a start date `<
today` never ranks (unit-tested).
  - **Task due date — EXISTS.** `tasks.due_date date` (baseline), stamped at
    generation from `dueOffsetDays` by `src/lib/sopResolver.ts` (verified:
    `resolveTemplate` computes `dueDate` → `cases.ts` writes `due_date`).
  - **Follow-up cadence — ARRIVES WITH E1.7b/E2.2, not in the repo today.**
    `followUpEveryDays` has zero occurrences in `src/` at review time; it is
    E1.7b F1.7b.3's additive `SOPStep` field, stamped into `tasks.sop_content`
    by E2.2. The dependency listing is correct; see TE-7 for the sequencing
    gate. The derivation base for "last touch" is the newest
    `entry_type='touchpoint'` row for the case (`touches.entry_type` exists —
    migration `20260707120000`; notes/system events must NOT reset the
    cadence clock, matching the existing `touches.ts` idiom where
    stalled/follow-up reads are scoped to touchpoints). A case with **no
    touch yet** starts its cadence clock at the case's `created_at`
    (deterministic, unit-tested).
  - **Explicit next-follow-up date — EXISTS and must be reconciled.**
    `touches.next_follow_up_date` (baseline) is a user-set per-case follow-up
    deadline already consumed read-only by the legacy Home action engine
    (`src/services/touches.ts` `getLatestFollowUps`, sanctioned M5 read). The
    queue's follow-up signal for a case is
    `min(latest touchpoint's next_follow_up_date, cadence-derived next-touch
date)` — ignoring the explicit date the team already records would rank
    known-due cases wrong.
  - **Location launch date — column EXISTS, no redesign capture surface.**
    `facilities.effective_date date` (baseline, legacy launch track; written
    only by the legacy `launches.ts` surface — the E1.2 wizard service
    `orgSettings.ts` does not write it). Rank it **if present** (future-dated
    `effective_date` on a facility reachable from the case via
    `credential_cases.facility_id` or the provider's assignments); expect it
    to be absent in redesign-era data. Capture belongs to the future
    location-launch epic (E1.4/E1.8 non-goals), not here.
  - **Recredentialing deadline — DOES NOT EXIST. Not rankable in R4.**
    Zero recredentialing columns anywhere in `supabase/migrations/` (verified
    by search) or the table register. R9 ("Recurring ops: expiration radar,
    recredentialing, PSV re-verify clocks") owns that modeling. F2.3.1's AC
    must be read through the epic's own deadline-source honesty rule:
    recredentialing is **named here as a gap and deferred** — no additive
    schema for it in this epic (see redline 1 and PM question 1).

- **TE-2 — Pure ranked-reduction module (the epic's stated dependency),
  named and specced.** `src/lib/nextBestActions.ts` +
  `nextBestActions.test.ts` — mirror the `payerExpansion.ts` /
  `enrollmentReadiness.ts` pattern: typed input interfaces, **no Supabase, no
  clock reads — pass `today` in** (the house rule from E1.8 TE-1/TE-6).
  Output: ordered entries `{ caseId, caseIdentity (provider × group × payer ×
state), action, drivingDeadline: { date, source }, reason }` where `reason`
  is the human-readable derivation string (F2.3.1 "why this is next", the
  E2.0 reason-string pattern). Rules the module owns, all unit-tested:
  - **One entry per open case** (F2.3.1). The entry's deadline = the earliest
    applicable signal from TE-1; its action = the case's next actionable task
    (lowest `sort_order` non-completed task), except that a cadence/follow-up
    signal renders a "touch due" action (F2.3.3) and a red-readiness case
    surfaces its gap as the action (see TE-5). A case never appears twice.
  - **Deterministic tie-breakers, documented in the module:** deadline date,
    then case `created_at` (oldest first), then case id. F2.3.1 requires the
    tie order be documented — the module docstring is that documentation.
  - **Entries with no deadline signal at all** rank after all dated entries
    (stable by the same tie-breakers), so the queue is total — nothing
    silently drops out.
- **TE-3 — "Open case" is derived from `status_configs.action_bucket`, never
  labels.** Open = credentialing status not in the `action_bucket
'complete'` bucket; status-less cases count as open (`credentialing_status_id`
  is nullable — register MVD note). This is the locked idiom from
  `GET /api/cases` (`src/services/providerCases.ts`); reuse the derivation,
  do not re-implement by label matching (`statusLabels.ts` rule).
- **TE-4 — Data assembly: services under RLS, batched, PHI-safe.** Reads go
  through `src/services/` (a new read module, e.g.
  `src/services/nextBestActions.ts`) → a `src/hooks/` wrapper (org-scoped
  `queryKeys` entry) → the pure module. One query per source table joined in
  memory — no per-case round-trips (the E1.8 recomputation-cost lesson).
  **`PROVIDER_LIST_COLUMNS` deliberately lacks `start_date`** (verified,
  `providers.ts:78`) — use a narrow scoped projection like
  `clientProgress.ts` does (id, name, `start_date`; never `select("*")`,
  no DOB/SSN/home-address columns in any queue payload). All source tables
  are org-scoped under RLS; the queue adds no server route, no service-role
  path, and therefore no isolation-gate assertion.
- **TE-5 — Readiness reuse (F2.3.1 blocker surfacing).** Consume
  `evaluateEnrollmentReadiness` / `readinessSummary` from
  `src/lib/enrollmentReadiness.ts` (built, E1.8) — do not fork the rule set.
  A case-key row with open gaps contributes the gap text as the entry's
  action ("Blocked/red-readiness" in the AC means **red readiness gaps**;
  E1.8 has no blocking state and the queue must not gate anything —
  advisory-only is a locked E1.8 decision). E2.0's group-contract-status
  readiness addition (its §5 decides the shape) flows in through the same
  module — no queue-local readiness logic.
- **TE-6 — Batch landing (F2.3.2) rides E2.1's traceability hooks.** The
  filter key is `credential_cases.generation_run_id` (additive, lands in
