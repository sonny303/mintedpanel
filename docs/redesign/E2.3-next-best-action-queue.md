# E2.3 — Next-Best-Action Queue (Post-Generation Landing)

## Purpose and Context

After generating 40 cases, "what do I do first?" needs an answer, not a wall
of rows. The `[r4]` Q5 decision: land on a **next-best-action queue ordered
by known upcoming deadlines** — provider start dates (E1.4
`start_date`), location launch dates, recredentialing deadlines, and task due
dates — so the most time-critical work surfaces first.

The queue is a fully **derived** view (the E1.0 derived-progress rule): no
stored priority, no dirty flags — it recomputes from cases, tasks, deadline
sources, and readiness every render. It is also the natural everyday home
for P2, not just a post-generation landing.

## Personas Empowered

- **P2 Credentialing Specialist** — works the queue top-down.
- **P1 Credentialing Manager** — lands here after generation; sees where the
  batch's urgency concentrates.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: prioritization is a pure ranked-reduction
  module in `src/lib/` (tested): inputs = open cases + their next actionable
  task, deadline signals (provider `start_date`, location launch date where
  modeled, recredentialing dates, task `dueOffsetDays`-derived due dates,
  `followUpEveryDays` cadence from stamped SOP content), readiness (E1.8);
  output = ordered queue entries with a human-readable "why this is next".
- Deadline-source honesty: only deadlines that exist in the schema today are
  ranked; sources not yet modeled (e.g. location launch date, if absent) are
  named in the epic's gap list and added additively or deferred — the review
  session verifies against the live schema in §5.
- Implementation dependency: no new tables expected (derived view); if a
  snooze/dismiss affordance is added it must be an explicit additive table,
  not a mutation of case/task rows.

## Features

### F2.3.1 — Deadline-ordered queue

- **Description:** A queue of "next actions" (one entry per open case's next
  actionable task), ordered by the earliest relevant deadline, each entry
  showing case identity (provider × group × payer × state), the action, the
  driving deadline, and the derivation reason.
- **Persona:** P2, P1.
- **Acceptance criteria:**
  - Ordering follows the earliest applicable deadline among: provider start
    date, recredentialing deadline, task due date, follow-up-cadence
    next-touch date; ties broken deterministically (documented).
  - Every entry states _why_ it ranks where it does.
  - Blocked/red-readiness cases surface their blocker as the action.
- **Test/data scenario(s):** TS-55.

```gherkin
Feature: Deadlines drive the order
  Scenario: Start date beats due offset
    Given Jane's case has a task due in 10 days
    And Marco starts seeing patients in 4 days with an unsubmitted application
    When P2 opens the queue
    Then Marco's submission ranks above Jane's task
    And Marco's entry says it is driven by his provider start date
```

### F2.3.2 — Post-generation landing

- **Description:** Confirming generation (E2.1) lands on the queue filtered
  to the new batch (generation-run id), with a one-click "all work" toggle.
- **Persona:** P1.
- **Acceptance criteria:**
  - Landing shows the batch's entries in deadline order with a created/
    skipped summary banner.
  - Clearing the filter shows the full org queue; the filter is URL-state,
    shareable.
- **Test/data scenario(s):** TS-55.

### F2.3.3 — Follow-up cadence surfacing

- **Description:** Tasks whose stamped SOP steps carry `followUpEveryDays`
  generate recurring "touch due" queue entries (derived from the last touch
  of that case — append-only `touches` is read, never written by the queue).
- **Persona:** P2.
- **Acceptance criteria:**
  - A case 14+ days since last touch with a 14-day cadence step surfaces a
    follow-up entry; touching the case (existing flows) re-derives it away.
- **Test/data scenario(s):** TS-56.

## Dependencies

## Out of Scope / Non-Goals

- Assignment/ownership routing of queue entries (single-team assumption
  holds; multi-assignee routing is later).
- Notifications/reminders outside the app.
- Stored priorities or manual re-ordering.
