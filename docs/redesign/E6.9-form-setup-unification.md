# E6.9 — Form Setup Unification, Field Registry & Workbench Journey Split

**Cross-repo.** Panel (`sonny303/mintedpanel`) and extension
(`sonny303/minted-extension`) ship together, following the E4.3 precedent
(panel #178 / extension #28). Three PRs — see the PR map below.

## Purpose and Context

E6.5 put the whole capture → train → prove loop inside the SOP editor
(`FormStepPanel`). Live testing against the Aetna "Request to Join the Aetna
Network" flow (template `9029b53a-3764-4001-b16e-ecb554d9a4c7`, payer
`3c823616-a4cf-412f-9214-b689cb3c79d9`, case C-1017) surfaced four structural
problems that make the loop unusable on a real multi-page payer form:

1. **Approved mappings disappear.** `FormStepPanel` builds its list from broken
   - `proposed` rows only. The moment a field is approved it drops out of the
     UI and collapses into the static `4 mapped · 19 to train` text. There is no
     way to review, re-map, or unmap it from the template editor.
2. **Two parallel field systems.** Captured portal mappings
   (`portal_field_maps`) and the step's **Data fields**
   (`steps[].dataFields` in template JSON) are independent lists with their own
   labels and their own copy of the same token catalog. The product's own copy
   admits it: "separate from the captured portal field mappings in Form setup
   above, and not part of its mapped/train count."
3. **"Proven" is not evidence.** `runDryTest()` passes when every captured
   non-manual field is decided, but its source-first filter drops every
   `source: manual` row before checking status. Capture creates proposed rows
   with that source, so 19 undecided fields disappear, 4 approved fields fill,
   and zero skipped fields produce **Proven** at 4 of 23 mapped and 0%
   first-pass submission. The real form's field count is not an input anywhere.
   The Templates tab's "Ready for business — nothing outstanding" banner reads
   off the same signal.
4. **The Workbench mixes two jobs.** The side panel has a single screen after
   sign-in that leads with provider and case pickers. Training a payer form is
   not case work — it happens _before_ cases exist — but the panel makes the
   operator select an org and a case to get to it.

This epic makes the per-step field list the single managed registry, replaces
Proven with honest coverage, and splits the Workbench into two named jobs.

### PM decisions carried into this epic (Sowmya, 2026-08-07, in-session)

| #   | Decision                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| D2  | Field values come from **tokens**. A required box with no token gets a **fixed literal value** rather than expanding the data model. "Human fills this" is the third option and does **not** count as mapped. |

| D4  | Fill logging shows live per-page progress and saves a per-page record on the case.                                                                                                                            |
| D5  | The unified list lives **inside the template editor's Form setup panel**.                                                                                                                                     |
| D6  | Generic captured field names are **renameable inline**; the payer's raw name is retained underneath and a re-capture never clobbers the rename.                                                               |
| D7  | On re-capture, field **order is re-derived from the live form**, even if that undoes manual arranging.                                                                                                        |
| D8  | The unified list adopts the Data fields picker's **grouped-by-family** token dropdown.                                                                                                                        |

### Notes on the source write-up

The PM's testing write-up assumed a crawler traverses the form and that a
"Capture Request ID for submission" task was a defect. Both were checked
against the code and the live case: there is **no crawler** (capture is a
one-pass DOM scan of the page the operator is on — `scanCapturableFields`),
and the task is legitimate pre-existing content. The write-up's other findings
(vanishing mappings, the Manual bug, the two field systems, Proven at 17%
coverage) all reproduce in the code.

## Personas Empowered

- **P1 Credentialing Manager** — trains payer forms and runs the coverage
  read-out; the primary user of every surface here.
- **P2 Credentialing Coordinator / Specialist** — runs the fill during case
  work and reads the per-page execution log.
- **P10 Payer Portal / System Boundary** — the multi-page payer wizard whose
  shape is captured.

No new persona is introduced. OQ-1 was resolved **ungated** (PM, 2026-08-07):
training mode is available to any signed-in user, so no staff capability and
no new persona exists anywhere in this epic.

## Component & Data Constraints

- Built from the current library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Design tokens per `AGENTS.md`: primary `#1B4D3E`, `#E8E5E0` 1px borders, no
  shadows, `rounded-md`, rows `h-10`, `gap-4` max.
- **Additive migrations only.** No column or table is renamed, restructured, or
  dropped. `steps[].dataFields` stays in template JSON on existing rows; the
  editor simply stops reading it for `online_form` steps.
- Data flow stays components → hooks → services → Supabase. The extension keeps
  its locked boundary: the background worker owns every API call, capture reads
  **shape only** (labels, selectors, control types — never a value).
- **Implementation dependencies, explicitly flagged (not assumptions):**
  - `portal_field_maps` already has `form_section`, `page_step`,
    `hardcoded_value`, `field_label`, `confidence`. `page_step` is declared in
    both repos and accepted by the propose API but **never populated** — the
    extension does not send it.
  - `reproposeFieldMap` (unmap) exists and is wired into the standalone
    training route, **not** into `FormStepPanel`.
  - The extension fills fixed values only when `source = 'hardcoded'`; the
    panel dry run currently infers a fixed mapping from `hardcoded_value`
    (`HARDCODED_PSEUDO_TOKEN`) instead. F6.9.4 must make both paths key off the
    same state.
  - The dry run currently filters `source !== 'manual'` before classifying
    status. Because capture creates `status = 'proposed', source = 'manual'`,
    undecided captured rows disappear instead of producing `needs_decision`.
    F6.9.4 replaces this with a shared `(status, source)` classifier.
  - `proposeFieldMap` inserts with `org_id: ctx.orgId` — there is **no**
    global-tier propose path today.
  - Global `portal_field_maps` rows fail browser RLS for both INSERT and UPDATE
    (`org_id IN user_org_ids()`). `trainGlobalFieldMap` can change decision
    state only; it cannot insert manual registry rows or write
    `display_label`, `section`, or `sort_order`. F6.9.2 must provide every
    global mutation used by F6.9.5–F6.9.7, not only hardcoded training.
  - Org rows use org-RLS mutations. Global rows use `trainGlobalFieldMap`,
    which already accepts `status: proposed`; the missing pieces are a
    `FormStepPanel` Unmap affordance, clearing `hardcoded_value` on repropose,
    and a canonical proposed source. The RPC also rejects
    `source = 'hardcoded'`, so global fixed values are impossible today.
  - `START_CAPTURE` / `SEND_CAPTURE` carry a tab id, portal key, and an
    optional `templateStepId` — no case and no provider. Capture already needs
    no case; only fill does.
  - `audit_log.org_id` is `NOT NULL` (baseline migration), so **global-tier
    writes cannot produce audit rows today**. `trainGlobalFieldMap` documents
    this interim posture ("the row's `updated_at` is the trail"); the new
    global paths in F6.9.2 and F6.9.6 follow the same posture. A
    platform-tier audit trail is R7 governance work, out of scope here.
  - `portal_field_maps.selector` is `NOT NULL` and `proposeFieldMap` rejects
    an empty selector; dropping the constraint would violate the additive-only
    rule. Manually added rows (F6.9.7) therefore carry a deterministic
    `manual:<uuid>` synthetic selector that the fill engine skips.
  - Form readiness is explicit, not inferred from coverage: F6.9.1 adds
    nullable `form_setup_reviewed_at` / `form_setup_reviewed_by` columns to
    `portals`; the reviewed-by column references `auth.users(id)` with
    `ON DELETE SET NULL`.
- Table trace — **read:** `portals`, `portal_field_maps`, `sop_templates`,
  `sop_template_versions`, `field_dictionary`, `memberships`; **written:**
  `portals` (form-setup review attestation),
  `portal_field_maps` (additive `display_label` / `section` / `sort_order`
  columns, backfill, capture/manual insert, decision changes, rename,
  sectioning and ordering at both tiers),
  `sop_template_versions` (pre-backfill snapshot, F6.9.1), `field_dictionary`
  (learning on the displayed name, F6.9.6), `audit_log` (append, org-tier
  actions only — see the audit posture above), and the existing fill-event
  storage (per-page attribution, F6.9.13). No renames, no deletes.

## Features

### F6.9.1 — Field registry schema (PR 1)

- **Description:** One additive migration gives `portal_field_maps` the three
  attributes the unified registry needs, adds the explicit form-review
  attestation to `portals`, and forces a template version snapshot before the
  backfill runs.
- **Persona:** P1 (indirectly — no UI in this feature).
- **Benefit hypothesis:** Sections, stable ordering, and renaming are all
  blocked on schema. Landing them in one reviewed migration keeps the UI PR
  free of DDL and gives the backfill a single rollback point.
- **Acceptance criteria:**
  - New nullable columns on `portal_field_maps`: `display_label text`,
    `section text`, `sort_order integer`.
  - New nullable columns on `portals`: `form_setup_reviewed_at timestamptz`
    and `form_setup_reviewed_by uuid REFERENCES auth.users(id) ON DELETE SET
    NULL`. Existing `proven_at` remains in place.
  - `display_label` is the admin's name; `field_label` remains the payer's raw
    captured text and is never overwritten by a rename.
  - `section` is the admin's grouping; `form_section` remains the heading read
    off the page and is never overwritten by a section edit.
  - Backfill: `sort_order` set from existing `created_at` order per
    `(portal_key, page_step)`; `display_label` and `section` left NULL
    (display falls back to `field_label` / `form_section`).
  - `docs/data-model/table-register.md` updated for both
    `portal_field_maps` and `portals` in the same PR (AGENTS.md rule).
  - A new template version snapshot is created before the backfill executes —
    the affected template has a single "v1 Current" and no rollback path.
  - No column or table is renamed, restructured, or dropped anywhere in the
    migration.
- **Test/data scenario(s):** TS-141.

```gherkin
Feature: Additive field-registry columns with a safe backfill
  Scenario: Existing captured fields survive the migration with stable order
    Given the global 5-page portal fixture has 23 captured field maps created over several sessions
    And the template has exactly one version, "v1 Current"
    When the E6.9 migration runs
    Then a new template version snapshot exists before the backfill
    And every field map has a sort_order matching its original created_at order
    And display_label and section are NULL on every row
    And the portal's form_setup_reviewed_at and form_setup_reviewed_by are NULL
    And field_label and form_section are byte-identical to their pre-migration values
```

### F6.9.2 — Global-tier registry write parity (PR 1)

- **Description:** The global tier gains the complete authenticated mutation
  surface required by the registry: capture/manual insert, decision changes,
  metadata/order edits, and review-attestation invalidation.
- **Persona:** P1.
- **Benefit hypothesis:** The Aetna template is **global** — authored once and
  inherited by every organization with no override. Extension capture can only
  create org-scoped rows; global-row RLS rejects direct INSERT and UPDATE; the
  existing RPC rejects the `hardcoded` source and cannot write registry
  metadata or order. Without this feature D10 is unreachable and F6.9.4–F6.9.7
  are read-only or error at the tier that matters.
- **Acceptance criteria:**
  - A global propose path creates `org_id IS NULL` rows from extension capture,
    idempotent on `(portal_key, selector)` exactly as the org path is.
  - The global insert path also supports F6.9.7 manual registry rows with their
    deterministic `manual:<uuid>` selector and required note. It validates the
    same field types and source invariants as the org path; callers never
    submit an `org_id`.
  - `train_global_field_map` accepts `source = 'hardcoded'` plus a non-empty
    `hardcoded_value`; that transition writes `status = 'approved'`, clears
    `token`, and rejects an empty literal. The service type and call mirror the
    RPC parameters.
  - The existing `status = 'proposed'` RPC shape is retained. Repropose clears
    both `token` and `hardcoded_value` and sets the canonical undecided shape
    used by captured rows: `status = 'proposed'`, `source = 'manual'` with the
    required note. It does not claim to restore a prior source that is not
    persisted.
  - A dedicated global registry-update RPC writes `display_label`, `section`,
    and `sort_order` on `org_id IS NULL` rows, including explicit clearing of
    nullable labels/sections. It accepts a batch for re-capture ordering so the
    page's order update and review-attestation invalidation are atomic.
  - F6.9.5 section/reorder actions, F6.9.6 rename, and F6.9.7 Add field call
    these global RPCs for global rows. None relies on browser INSERT/UPDATE RLS
    or repurposes `train_global_field_map`.
  - The global propose and training paths are open to **any signed-in user**
    (OQ-1 resolved: ungated). An unauthenticated caller is rejected, and the
    org-scoped behavior is completely unchanged.
  - An authenticated global-portal review RPC stamps or clears
    `form_setup_reviewed_at` / `form_setup_reviewed_by` without requiring an
    org. Every global capture or field-registry mutation clears those columns
    atomically in its write path. Org-override mutations do not mutate the
    global portal's attestation.
  - Global writes follow the existing interim no-audit posture
    (`audit_log.org_id` is `NOT NULL` — see Component & Data Constraints);
    the row's `updated_at` is the trail.
  - The existing org-scoped `approveFieldMap` / `markFieldMapManual` /
    `reproposeFieldMap` semantics are untouched.
  - Server-side isolation assertions cover the new paths: a global write never
    reads or mutates an org row and vice versa. Tests cover global capture and
    manual inserts, rename/clear, section assignment/clear, batch reorder,
    fixed value, repropose, and atomic attestation invalidation.
- **Test/data scenario(s):** TS-142, TS-143.

```gherkin
Feature: Global mappings can be captured, fixed, and unmapped
  Scenario: A signed-in user unmaps an approved global field
    Given a global field map on the fixture approved to provider.npi
    When a signed-in user unmaps it
    Then the row returns to the canonical proposed shape with no token or fixed value
    And every organization inheriting the global template sees it as unmapped
    And the row's updated_at records the change

  Scenario: A signed-in user sets a fixed value on a global field
    Given a proposed global field map with no matching token
    When the user saves the fixed literal "Credentialing Coordinator"
    Then the row is approved with source hardcoded and no token
    And every organization inheriting the global template fills that literal

  Scenario: A signed-in user edits the global registry
    Given a reviewed global registry inherited by multiple organizations
    When the user adds a manual field, renames it, assigns a section and reorders the page
    Then every write lands on an org_id NULL row through the global registry RPCs
    And no org override row is created or changed
    And the global Form setup reviewed attestation is cleared atomically

  Scenario: An unauthenticated caller cannot write the global tier
    Given a request with no authenticated session
    When it attempts a global unmap
    Then the request is rejected
    And no global row changes
```

### F6.9.3 — Unified field list: mapped rows stay visible (PR 2)

- **Description:** `FormStepPanel` lists **every** field for the step — broken,
  proposed, and decided — instead of only the ones needing attention. Each row
  shows its status, its current token or fixed value inline, and stays editable.
- **Persona:** P1.
- **Benefit hypothesis:** An approved mapping is currently unreachable from the
  editor, so a wrong mapping can only be found by running a fill and watching it
  put the wrong value in the box. Keeping rows visible turns the panel from a
  one-way queue into a reviewable registry.
- **Acceptance criteria:**
  - All non-retired maps for the step render, ordered by section then
    `sort_order`; broken rows still sort first within their section.
  - Each row shows: name, status pill (`Unmapped` / `Mapped` / `Broken`),
    current token or fixed value, and its tier when global.
  - The token on a decided row is editable in place via the same picker used to
    set it, and re-mapping never changes the row's position.
  - Each row has an **Unmap** action returning it to unmapped (org rows via the
    existing `reproposeFieldMap`, global rows via F6.9.2).
  - When both tiers contain the same selector, the org row is the effective
    mapping for that org. Both rows remain visible with tier labels; edits
    mutate the row's own tier, and the global row warns that it is shadowed for
    the active org. A global edit still reaches every org without an override.
    No edit implicitly creates, deletes, or switches an override (OQ-3 ruling).
  - The static `N mapped · M to train` text is replaced by the F6.9.8 coverage
    read-out.
  - The panel still mounts **collapsed** by default; the typing-latency contract
    (`TemplateTaskRow.test.ts`, `template-typing-latency.spec.ts`) still passes.
- **Test/data scenario(s):** TS-144.

```gherkin
Feature: Reviewing and correcting an approved mapping
  Scenario: P1 fixes a field mapped to the wrong token
    Given the fixture's online_form step has a field "Tax ID" approved to provider.ssnLast4
    When P1 opens Form setup
    Then the field is listed as Mapped showing provider.ssnLast4
    When P1 changes its token to group.tin
    Then the row still reads Mapped, now showing group.tin
    And the row has not moved in the list
```

### F6.9.4 — Three decision actions, and Manual stops counting as mapped (PR 2)

- **Description:** The single ambiguous **Manual** button splits into the three
  answers a trainer actually has: map to a token, set a fixed literal value, or
  hand the field to a human.
- **Persona:** P1.
- **Benefit hypothesis:** Today `Manual` ignores the dropdown entirely, stores
  **no value at all**, and the dry run filters every `source: manual` row before
  checking whether it is approved or still proposed. That is the exact path to
  "Proven" with 19 undecided rows hidden. Splitting the actions and classifying
  by `(status, source)` makes each state honest and gives
  required-but-untokenized boxes an answer that does not require expanding the
  data model (D2).
- **Acceptance criteria:**
  - **Map to token** — unchanged behavior; counts as mapped.
  - **Fixed value** — a dedicated text input writes `hardcoded_value` and sets
    `source: hardcoded`, `status: approved`, `token: null` (global rows use the
    F6.9.2 RPC). The row reads `Mapped (fixed)` showing the literal; it
    auto-fills on every run and counts toward coverage. It is a distinct
    control from the token picker and cannot be committed empty.
  - **Human fills this** — stores no value and sets `status: approved`,
    `source: manual`, `token: null`, `hardcoded_value: null`; the row reads
    `Human fills this`. It does **not** count as mapped and is a decided
    human-fill outcome, not an undecided-row failure.
  - No action can be committed from a stale or empty picker selection. The
    existing disabled-Approve guard remains, and F6.9.9 removes the redundant
    "No token" entry.
  - Dry run and coverage share one exhaustive `(status, source)` classifier;
    source is never filtered before status:
    - any non-retired `status = 'proposed'` row is `needs_decision`, including
      the canonical `source = 'manual'` captured shape;
    - `approved + token` and `approved + manual_partial` require a token and
      are mapped/autofillable;
    - `approved + hardcoded` requires a non-empty `hardcoded_value` and is
      mapped/autofillable;
    - `approved + manual` is the decided Human fills outcome: not
      autofillable, not mapped, and not `needs_decision`;
    - retired rows are ignored; every unsupported or payload-invalid pair
      fails closed as a configuration error.
  - The dry run reports every `needs_decision` and configuration-error row and
    cannot pass while either exists. Presence of `hardcoded_value` alone never
    changes classification.
  - A row's decision is reversible at any time via Unmap (F6.9.3).
- **Test/data scenario(s):** TS-145.

```gherkin
Feature: Answering a required field with no matching token
  Scenario: P1 sets a fixed literal on a required box
    Given a required fixture field "Submitter role" with no matching token
    When P1 chooses Fixed value and enters "Credentialing Coordinator"
    Then the row reads Mapped (fixed) showing that literal
    And it stores source hardcoded, status approved, no token, and that literal
    And the mock dry run fills it and counts it toward coverage

  Scenario: Human-filled fields never inflate coverage
    Given a field marked "Human fills this"
    Then the dry run classifies it as an approved human-fill outcome
    And coverage counts it as not mapped

  Scenario: Undecided captured fields cannot disappear from the dry run
    Given 19 captured rows with status proposed and source manual
    And 4 valid approved token or fixed rows
    When P1 runs the mock dry run
    Then all 19 proposed rows are reported as needs decision
    And the dry run does not pass
```

### F6.9.5 — Sections and real-form ordering (PR 2)

- **Description:** Fields group into named sections with per-section progress,
  ordered as they appear on the live form.
- **Persona:** P1.
- **Benefit hypothesis:** 23 fields in raw crawl order with one aggregate count
  is unreadable and gives no signal about which part of the form is unfinished.
  Sections make "Tax ID: 2 of 5 mapped" visible at the level a trainer works at.
- **Acceptance criteria:**
  - Fields display grouped by `section`, defaulting to
    `section ?? form_section ?? page_step ?? "Fields"`.
  - An admin can create a section, rename it, and reassign a field's section
    inline; sections collapse and expand. Global rows use F6.9.2's registry
    update RPC; org rows use the existing org-RLS service path.
  - Within a section, fields are ordered by `sort_order` — the order they appear
    on the real form.
  - Approving, unmapping, re-mapping, or renaming a field never changes its
    position (D7 governs re-capture only).
  - On re-capture the order is **re-derived from the live form** and existing
    rows are repositioned to match; the admin's `section` and `display_label`
    are preserved through this. Global reordering uses F6.9.2's atomic batch
    RPC and clears the review attestation in the same transaction.
  - Each section header shows its own progress; the step shows the aggregate.
- **Test/data scenario(s):** TS-146, TS-147.

```gherkin
Feature: Sectioned field list in real-form order
  Scenario: Per-section progress replaces one aggregate count
    Given the fixture step has sections Network Check, Submitter Info and Tax ID
    And Tax ID has 5 fields of which 2 are mapped
    Then the Tax ID header reads "2 of 5 mapped"

  Scenario: Re-capture re-derives order but keeps admin naming
    Given a field renamed to "Practice TIN" and assigned to section "Tax ID"
    And the payer moves that field earlier on the page
    When the page is re-captured
    Then the field moves to its new position in the list
    And it is still named "Practice TIN" in section "Tax ID"
```

### F6.9.6 — Inline rename of generic field names (PR 2)

- **Description:** The field name is an editable text box. The admin's name
  displays; the payer's raw captured text is retained beneath it.
- **Persona:** P1.
- **Benefit hypothesis:** Capture reads whatever the page offers — a `<label>`,
  an aria label, or a placeholder — so on forms like Tricare East many fields
  come back generic or empty and nobody can map them confidently. Renaming also
  feeds the field dictionary, which learns "a field called X means token Y" and
  reuses it on the next payer, so good names make later forms map themselves.
- **Acceptance criteria:**
  - Clicking the name turns it into an input; saving writes `display_label`.
    No dialog, no separate screen. Global rows write through F6.9.2's registry
    update RPC; org rows use the existing org-RLS service path.
  - Display is `display_label ?? field_label`; `field_label` is shown as
    secondary evidence when a rename exists.
  - Re-capture writes `field_label` only — a rename is never clobbered.
  - Dictionary learning (`upsertDictionaryEntry`) learns on the **displayed**
    name when one exists, so suggestions improve rather than degrade.
  - A rename on an org-tier row is audited; a global-tier rename follows the
    interim no-audit posture (`audit_log.org_id` is `NOT NULL` — see Component
    & Data Constraints) and the row's `updated_at` is the trail.
- **Test/data scenario(s):** TS-148.

```gherkin
Feature: Renaming a generic captured field
  Scenario: A junk capture label becomes meaningful and teaches the dictionary
    Given a captured field on the generic-markup fixture whose label is "Text field 3"
    When P1 renames it to "Group NPI"
    Then the list shows "Group NPI" with "Text field 3" as the raw captured name
    And approving it to group.npi teaches the dictionary on "Group NPI"
    And a later re-capture still shows "Group NPI"
```

### F6.9.7 — Data fields unified into the registry for online-form steps (PR 2)

- **Description:** For `online_form` steps, the separate **Data fields** list
  folds into the registry. Manually added reference fields become registry rows.
- **Persona:** P1.
- **Benefit hypothesis:** A field currently has to be mapped twice — once for
  the fill engine, once for the operator's reference list — with two labels and
  two pickers over the same catalog. One row, mapped once, serves both.
- **Acceptance criteria:**
  - On `online_form` steps the separate Data fields section no longer renders;
    "Add field" creates an undecided registry row with `status: proposed`,
    `source: manual` and a deterministic synthetic selector (`manual:<uuid>` —
    `portal_field_maps.selector` is `NOT NULL` and stays that way, see
    Component & Data Constraints), flagged as manually added rather than
    captured. The fill engine and capture drift repair ignore `manual:`
    selectors. A global manual row inserts through F6.9.2's global insert RPC;
    an org row uses the existing org-RLS path.
  - **All other step types keep `dataFields` exactly as today** — the control
    renders unchanged for them.
  - Existing `dataFields` entries on online-form steps are migrated into
    registry rows; the `dataFields` JSON key is **retained** on the template
    (additive-only rule) and simply stops being read for those steps.
  - The migration is idempotent and re-running it creates no duplicate rows.
  - A manually added row is a first-class registry row: renameable,
    sectionable, orderable, and decidable by all three F6.9.4 actions.
- **Test/data scenario(s):** TS-149.

### F6.9.8 — Coverage replaces Proven (PR 2)

- **Description:** The **Proven** status and the "Ready for business — nothing
  outstanding" claim are removed in favor of a coverage read-out and an
  explicit **Form setup reviewed** trainer attestation.
- **Persona:** P1.
- **Benefit hypothesis:** Proven means "every field we happened to capture is
  decided" — it passed on this template at 4 of 23 fields with 0% first-pass
  submission. Nothing in the system knows the real form's field count, so no
  badge can be honest; a coverage number is both honest and more actionable.
- **Acceptance criteria:**
  - The Form setup summary reads coverage, e.g. `4 of 23 mapped · 5 pages
captured`, with per-section counts in the section headers.
  - Coverage uses F6.9.4's shared pair classifier: the denominator is every
    non-retired registry row; only valid approved token, manual-partial, and
    hardcoded rows enter the mapped numerator. Proposed and approved-manual
    rows remain visible in the denominator.
  - The `Proven` status pill is removed from the Form setup panel.
  - A trainer can explicitly mark Form setup reviewed after confirming the
    known pages and field decisions. The action stamps
    `form_setup_reviewed_at = now()` and `form_setup_reviewed_by = auth.uid()`;
    coverage remains informational and never stamps the review state.
  - Mark reviewed is disabled while F6.9.4's classifier reports any
    `needs_decision` or configuration-error row. Approved Human fills rows are
    valid decisions, so a trainer may attest with coverage below 100%; that is
    the intentional distinction between reviewed and mapped.
  - Global re-capture, field add/remove, mapping/unmapping, fixed/manual
    decision, rename, section change, or reorder clears both review columns.
    The trainer must review the changed global setup again; a dry run by itself
    does not restore the attestation. Org-override edits do not clear the
    global readiness attestation.
  - `proven_at` is **not** dropped from `portals` (additive-only); it simply
    stops being read and stops being stamped by the dry run.
  - The dry run still runs and still reports filled/unmatched — it just no
    longer confers a status.
  - The readiness funnel replaces form state `proven` with `reviewed`; a
    published template requiring an online form reaches `ready` only when Form
    setup is reviewed and no higher-priority drift repair is outstanding.
  - The former `run_dry_test` terminal next action becomes
    `review_form_setup` and deep-links to Form setup; the dry-run control
    remains available inside that surface as evidence for the trainer.
  - The Payer Setup KPI becomes **Form setup not reviewed**. Templates copy,
    Payer Scorecard, funnel copy, filters, tests, and Slice F intent all use the
    reviewed state together; no surface renders Proven or equates coverage
    with readiness.
- **Test/data scenario(s):** TS-150.

```gherkin
Feature: Honest coverage instead of a Proven badge
  Scenario: A thinly mapped template stops claiming readiness
    Given the fixture template with 4 of 23 fields mapped and proven_at stamped
    When P1 opens Form setup after this epic
    Then no Proven pill is shown
    And the summary reads "4 of 23 mapped"
    And Mark Form setup reviewed is disabled while 19 rows need a decision
    When P1 decides those 19 rows as Human fills this
    And P1 marks Form setup reviewed
    Then the funnel, KPI, Templates copy and Scorecard all read it as reviewed
    When a global mapping is changed
    Then Form setup returns to not reviewed until P1 attests again
```

### F6.9.9 — Grouped token picker (PR 2)

### F6.9.10 — Workbench journey split (PR 3)

- **Description:** After sign-in the side panel asks which job is being done —
  **Train a form** or **Work a case** — instead of presenting one screen that
  leads with provider and case pickers.
- **Persona:** P1 (train), P2 (case).
- **Benefit hypothesis:** Payer setup happens _before_ cases exist, so making
  the operator pick a case to reach training is both confusing and sometimes
  impossible. The panel currently has a single `main` view; the two journeys are
  mixed in one screen for no technical reason — capture already requires no
  case.
- **Acceptance criteria:**
  - A job chooser renders after sign-in with the two named jobs; the current job
    is always visible and switchable without signing out.
  - **Train a form** shows the portal/capture surface only: no provider picker,
    no case picker, no quick cards, no touch logging.
  - **Work a case** is today's screen, unchanged, including org and case
    selection.
  - The E4.3 webapp hand-off (`SET_ACTIVE_CASE`) lands directly in **Work a
    case** with its case context intact — the chooser never interrupts a
    hand-off.
  - The locked rules hold unchanged: fill still requires an active case, the
    extension still never submits a form, and no auto-anything is added.
- **Test/data scenario(s):** TS-151.

```gherkin

  Scenario: Training a form before any case exists

    When they choose "Train a form" and open the fixture portal
```

### F6.9.11 — Org-free global training capture (PR 3)

- **Description:** In training mode, capture proposes **global** rows and asks
  for no org.
- **Persona:** P1.
- **Benefit hypothesis:** A trained form is a payer truth every org inherits.
  Today capture stamps the operator's org on every proposed row, so a global
  template can never accumulate global mappings and every org would re-train the
  same form independently.
- **Acceptance criteria:**
  - Training mode sends no `x-org-id` and selects no org, including for
    multi-org users.
  - Capture in training mode proposes through the F6.9.2 global path; rows land
    with `org_id IS NULL`.
  - Training mode is available to any signed-in user (OQ-1 resolved: ungated);
    every existing org-scoped behavior in case mode is unchanged.
  - Case mode's org resolution is untouched: single-org sends no header,
    multi-org must send one.
  - The propose payload remains shape-only — labels, selectors, control types,
    section, page. No value ever leaves the page.
- **Test/data scenario(s):** TS-152.

### F6.9.12 — Per-page capture stamping (PR 3)

- **Description:** Each capture records which page of the wizard it came from,
  so a person walking a 5-step form produces one correctly grouped, correctly
  ordered registry (D1).
- **Persona:** P1.
- **Benefit hypothesis:** Capture is a one-pass scan of the current page, so the
  Aetna registry contains page 1 only — Specialty Details, Contact, Location and
  Other are entirely missing, and nothing records that they exist. Stamping the
  page makes multi-page coverage countable without building traversal.
- **Acceptance criteria:**
  - `SEND_CAPTURE` populates `page_step` on every proposed row (the extension
    sends it today for no row, though both repos type it and the API accepts it).
  - The page identity is derived from the page — its URL and/or wizard heading —
    and is editable by the admin in the panel as a section (F6.9.5).
  - `sort_order` is assigned from DOM order within the captured page, and pages
    order by capture sequence.
  - Re-capturing a page it has already seen is drift repair as today
    (`diffCapture`): prior decisions carry, only genuine changes re-surface, and
    the admin's `display_label` / `section` survive.
  - The panel shows which pages have been captured, e.g. `5 pages captured`, so
    a trainer can see a page is missing.
  - No traversal, no clicking "Continue", no automated advance — explicitly out
    of scope (D1).
- **Test/data scenario(s):** TS-153.

```gherkin
Feature: Capturing a multi-page wizard page by page
  Scenario: A trainer walks all five Aetna pages
    Given the fixture wizard has 5 pages
    When P1 captures each page in turn while advancing the form themselves
    Then every field is registered with the page it came from
    And the fields within each page keep the order they appear in on the form
    And Form setup reports 5 pages captured
```

### F6.9.13 — Per-page fill progress and saved record (PR 3)

- **Description:** During a fill, the panel shows which page it is on, what it
  filled, and where it stopped; the same detail is saved on the case.
- **Persona:** P2.
- **Benefit hypothesis:** The only signal today is the aggregate `1 filled ·
0 unmatched`, which names no fields and no page. A fill that dies on page 3
  leaves nothing behind and has to be re-run blind to find out what happened.
- **Acceptance criteria:**
  - The panel shows live per-page progress: page, fields filled, fields skipped
    with reasons.
  - The saved fill record carries page attribution, reusing the existing
    fill-event shape rather than introducing new logging infrastructure.
  - The PHI boundary is unchanged: labels, counts and reasons only — never a
    field value.
  - A blocked or failed fill names the page and the reason it stopped.
  - The fill-event contract change is mirrored panel-side in the same
    coordinated change (`src/shared/apiTypes.ts` + the panel service).
- **Test/data scenario(s):** TS-154.

## Open Questions

**OQ-1 — the staff gate collides with a locked decision. RESOLVED (PM, 2026-08-07): (b) Ungated.**
D11 originally gated training mode to internal staff. E6.7 states "**no platform-role
gating**" as an explicitly PM-rejected concept, and E6.5 defers platform-role
hardening to R7 with `docs/redesign/E6.5-payer-setup-consolidation.md` recording
"No platform-role/permission system (R7)". Per authoring rule 4 this epic does
not silently override a locked decision.

Options:

- **(a) Recommended interim.** A single boolean capability on the user (or an
  explicit two-entry allowlist) that gates _only_ training mode and the global
  write paths. It is not a role model, introduces no persona, adds no
  permission surface to any org-facing screen, and can be deleted when R7's
  real role model lands. It matches the actual population — two people.
- **(b) Ungated.** Anyone signed in can train globally. Simplest, but a global
  row lands in every customer's account, which is the exact risk the global tier
  was designed around.
- **(c) Defer training mode to R7** and ship F6.9.1 – F6.9.9 (the panel work)
  only. The panel improvements do not depend on the gate; the extension work
  does.

**Ruling (Sowmya, 2026-08-07): (b) Ungated.** Anyone signed in can train
globally — simplest, and consistent with the letter of the E6.7 "no platform
roles" decision. The trade-off is accepted knowingly: every customer inherits
whatever any signed-in user captures. D11's staff gate is superseded; no
capability flag ships; R7's role model may revisit. The epic text is updated
throughout (D11, F6.9.2, F6.9.10, F6.9.11, TS-142/143/151/152), and the
resolution is recorded in `CLARIFICATIONS_NEEDED.md`.

**OQ-2 — page identity.** F6.9.12 derives a page identity from URL and/or
wizard heading. Neither is guaranteed stable on a SPA wizard that does not
change its URL between steps. If Aetna's wizard does not change URL, the
fallback is capture sequence plus the admin's section naming. Confirm this
degradation is acceptable rather than blocking capture.

**OQ-3 — global vs org override precedence in the registry UI.** When an org
override and a global row exist for the same selector, the registry must show
which one wins and to which tier an edit is being written. The existing
read-only registry view shows the tier; the editable registry needs an explicit
rule. Proposed: show both, edit the tier you are authoring in, and warn on an
override that shadows a global row.

**Ruling (PM, 2026-08-07):** An org override wins for that org. Show both rows
with tier labels, edit each row in its own tier, and warn when the org row
shadows global. Global edits continue to affect inheriting orgs without an
override. No implicit override creation, deletion, or tier switching.

**OQ-4 — what replaces Proven in payer readiness? RESOLVED (PM, 2026-08-07).**
D3 removes a status that is not evidence, but `proven` is also the terminal
form state that defines readiness today. It drives the readiness funnel's
`ready` result, the `run_dry_test` next action and Slice F `?intent=` deep link,
the Payer Setup "Form not proven" KPI card, and the Templates tab readiness
copy. Coverage cannot silently replace it as a readiness predicate because the
system still does not know the real form's complete field count.

Options considered:

- **(a) Remove form readiness from the funnel.** Delete the form KPI/next
  action and let the remaining readiness inputs define `ready`.
- **(b) Explicit trainer attestation.** Keep coverage informational and add an
  additive "form setup reviewed" state that alone satisfies the form-readiness
  input.
- **(c) Captured-coverage rule.** Treat all captured fields decided (plus the
  known-page count) as ready, accepting that uncaptured pages/fields remain
  unknowable.

**Ruling (PM, 2026-08-07): (b) Explicit trainer attestation.** Coverage stays
informational. A trainer marks **Form setup reviewed**, which stamps the actor
and time and supplies the form-readiness input. Any global registry or capture
change clears the attestation atomically; org-override edits do not mutate
global readiness. The funnel uses `reviewed`, its next action becomes
`review_form_setup`, and the KPI, Templates copy, Scorecard, filters, intents,
and tests move together. The decision is also recorded in
`CLARIFICATIONS_NEEDED.md`.
