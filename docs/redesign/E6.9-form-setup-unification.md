# E6.9 — Form Setup Simplification: Field Registry & Train Forms

**Cross-repo.** Panel (`sonny303/mintedpanel`) and extension
(`sonny303/minted-extension`) ship together, following the E4.3 precedent
(panel #178 / extension #28). Two PRs — see the PR map below.

> **2026-08-07 scope simplification (PM, in-session).** This epic was
> deliberately narrowed after a Muda review with the PM. The product is
> operated by **two people**; the earlier draft's org-override model,
> readiness attestation, coverage-replaces-Proven rework, global review
> RPCs, and per-page fill telemetry are **descoped** (deferred, not
> reversed — see Non-Goals). What remains is the smallest slice that makes
> payer-form training work end to end: one visible, editable field registry
> inside the existing Submit-form task editor, and a dedicated org-free
> **Train forms** module in the extension that captures form shape into the
> shared (global) tier.

## Purpose and Context

E6.5 put the whole capture → train → prove loop inside the SOP editor
(`FormStepPanel`). Live testing against the Aetna "Request to Join the Aetna
Network" flow (template `9029b53a-3764-4001-b16e-ecb554d9a4c7`, payer
`3c823616-a4cf-412f-9214-b689cb3c79d9`) surfaced structural problems that
make the loop unusable on a real multi-page payer form:

1. **Approved mappings disappear.** `FormStepPanel` builds its list from
   broken + `proposed` rows only. The moment a field is approved it drops out
   of the UI and collapses into the static `4 mapped · 19 to train` text.
   There is no way to review, re-map, or unmap it from the template editor.
2. **Two parallel field systems.** Captured portal mappings
   (`portal_field_maps`) and the step's **Data fields**
   (`steps[].dataFields` in template JSON) are independent lists with their
   own labels and their own copy of the same token catalog.
3. **The Manual button lies.** Clicking Manual silently marks a row mapped
   while storing no value, and the dry run's source-first filter drops every
   `source: manual` row before classifying status — undecided captured rows
   disappear instead of surfacing.
4. **The Workbench mixes two jobs.** The side panel has a single screen after
   sign-in that leads with provider and case pickers. Training a payer form is
   not case work — it happens _before_ cases exist — but the panel makes the
   operator select an org and a case to get to it, and capture can only write
   org-scoped rows, so the shared (global) template can never accumulate
   mappings from capture at all.

### The workflow this epic ships (PM-aligned, 2026-08-07)

- **Payer Setup → Templates** remains the authoring home. The template's
  operational tasks (**Submit form**, send email, check status) are the
  case-facing SOP; there is **no tracked "prepare form" task** and the
  generic Submit-form task owns **no portal and no mappings** — the system
  does nothing on the generic task.
- The extension has exactly **two modules** after sign-in: **Work cases**
  (today's screen, unchanged) and **Train forms**.
- **Train forms** is org-, provider-, and case-free: select the payer,
  find/select the portal, and capture the form's shape page by page while a
  person advances the wizard. A form the system has not seen is greeted as
  new and the user is guided to capture every section; a known form is
  recognized and its capture state shown, and the user decides what to do
  next. Capture submits **shape only** — portal identity, page/section
  structure, field labels/selectors, capture status. **Never a field value.**
- After capture the user returns to the **existing Submit-form task editor**
  under Payer Setup → Templates to review mappings. No new web-app surface is
  introduced.
- Trained forms live in the **shared tier** (`org_id IS NULL` rows): trained
  once, visible to both operators, **no org-specific overrides** in this
  version. Any signed-in user can train (OQ-1 resolved: ungated); no change
  history/undo in this version (accepted PM trade-off).
- **Cases are a different JTBD and are untouched**: case generation keeps
  selecting the authored SOP and snapshotting its tasks; fill still requires
  an active case; the extension still never submits a payer form.

## Component & Data Constraints

- Data flow stays components → hooks → services → Supabase. The extension
  keeps its locked boundary: the background worker owns every API call,
  capture reads **shape only** (labels, selectors, control types, sections,
  pages — never a value).
- **Implementation dependencies, explicitly flagged (verified against code):**
  - `portal_field_maps` already has `form_section`, `page_step`,
    `hardcoded_value`, `field_label`, `confidence`. `page_step` is declared in
    both repos and accepted by the propose API but **never populated** — the
    extension does not send it.
  - `reproposeFieldMap` (unmap) exists and is wired into the standalone
    training route, **not** into `FormStepPanel`.
  - The extension fills fixed values only when `source = 'hardcoded'`; the
    panel dry run currently infers a fixed mapping from `hardcoded_value`
    (`HARDCODED_PSEUDO_TOKEN`) instead. F6.9.4 must make both paths key off
    the same state.
  - The dry run currently filters `source !== 'manual'` before classifying
    status. Because capture creates `status = 'proposed', source = 'manual'`,
    undecided captured rows disappear instead of producing `needs_decision`.
    F6.9.4 replaces this with a shared `(status, source)` classifier.
  - `proposeFieldMap` inserts with `org_id: ctx.orgId` — there is **no**
    shared-tier propose path today. The shared path cannot reuse the org
    route's `authenticate()` guard: it interpolates and filters on
    `ctx.orgId`, and it 400s a multi-org caller that sends no `x-org-id`.
    The shared-tier routes run on the user-scoped `authenticateUser()` guard
    (the `/api/me/orgs` precedent) with an org-free context.
  - `portal_field_maps_notes_required` (baseline CHECK) requires a non-null
    `notes` whenever `source ∈ {manual, manual_partial}`. Every write landing
    `source = 'manual'` — Human fills this, the canonical repropose shape,
    and manual/captured inserts — supplies one, reusing
    `train_global_field_map`'s `coalesce(notes, …)` default shape.
  - There is **no unique index** behind the `(portal_key, selector)`
    idempotency claim — today it is a read-then-insert in `proposeFieldMap`,
    so concurrent captures can duplicate rows. F6.9.1 adds per-tier partial
    unique indexes and both propose paths move to `ON CONFLICT DO NOTHING` +
    re-read.
  - Shared-tier (`org_id IS NULL`) `portal_field_maps` rows fail browser RLS
    for both INSERT and UPDATE (`org_id IN user_org_ids()`).
    `trainGlobalFieldMap` can change decision state only; it cannot insert
    manual registry rows or write `display_label`, `section`, or
    `sort_order`. F6.9.2 must provide every shared-tier mutation used by
    F6.9.3–F6.9.6. The RPC also rejects `source = 'hardcoded'`, so shared
    fixed values are impossible today.
  - `START_CAPTURE` / `SEND_CAPTURE` carry a tab id, portal key, and an
    optional `templateStepId` — no case and no provider. Capture already
    needs no case; only fill does.
  - `audit_log.org_id` is `NOT NULL` (baseline migration), so shared-tier
    writes cannot produce audit rows. D14 accepts this: the row's
    `updated_at` is the trail. A platform-tier audit/history is R7 work.
  - `portal_field_maps.selector` is `NOT NULL`; manually added rows (F6.9.6)
    carry a deterministic `manual:` synthetic selector derived (e.g. UUIDv5)
    from the row's stable identity, so the data migration is mechanically
    idempotent under the F6.9.1 unique index. The fill engine and drift
    repair ignore `manual:` selectors.
  - Multiple forms per payer (D15) reuse the **portal registry**: each
    trained form is a portal row (payers already support several portal
    rows). No new form table. When URL/heading cannot distinguish a new
    form from an existing portal row, the extension creates a numbered
    candidate portal name (`<Payer> form 2`, …) that the admin renames —
    capture never blocks (OQ-2 precedent).
  - Re-capture drift (`diffCapture`) is the existing stale mechanism: fields
    missing from a new capture surface as drift/broken rows, never deleted
    (D7). No new column.
- Table trace — **read:** `portals`, `portal_field_maps`, `sop_templates`,
  `sop_template_versions`, `memberships`; **written:** `portal_field_maps`
  (additive `display_label` / `section` / `sort_order` columns, per-tier
  unique indexes, backfill, capture/manual insert, decision changes, rename,
  sectioning, ordering), `portals` (trained-form candidate rows from the
  Train forms flow, shared tier), `sop_templates` /
  `sop_template_versions` (pre-migration snapshot + `current_version` bump
  for the F6.9.6 Data-fields migration), `audit_log` (append, org-tier
  actions only). No renames, no deletes.

## Features

### F6.9.1 — Field registry schema (PR 1)

- **Description:** One additive migration gives `portal_field_maps` the three
  attributes the unified registry needs and the per-tier unique indexes
  behind propose idempotency.
- **Persona:** P1 (indirectly — no UI in this feature).
- **Acceptance criteria:**
  - New nullable columns on `portal_field_maps`: `display_label text`,
    `section text`, `sort_order integer`.
  - Per-tier partial unique indexes back the propose idempotency:
    `(portal_key, selector) WHERE org_id IS NULL` and `(org_id, portal_key,
selector) WHERE org_id IS NOT NULL`. Both propose paths become
    `ON CONFLICT DO NOTHING` + re-read. Live data is verified duplicate-free
    before the indexes are created; a non-empty result is raised to the PM as
    a data-cleanup question, never silently skipped.
  - `display_label` is the admin's name; `field_label` remains the payer's
    raw captured text and is never overwritten by a rename. `section` is the
    admin's grouping; `form_section` remains the heading read off the page.
  - Backfill: `sort_order` set from existing `created_at` order partitioned
    per tier — `(org_id, portal_key, page_step)` with the shared tier
    (`org_id IS NULL`) as its own partition. `display_label` and `section`
    left NULL (display falls back to `field_label` / `form_section`).
  - `docs/data-model/table-register.md` updated for `portal_field_maps` in
    the same PR (AGENTS.md rule).
  - No column or table is renamed, restructured, or dropped.
- **Test/data scenario(s):** TS-155.

```gherkin
Feature: Additive field-registry columns with a safe backfill
  Scenario: Existing captured fields survive the migration with stable order
    Given the shared 5-page portal fixture has 23 captured field maps created over several sessions
    When the E6.9 migration runs
    Then every field map has a sort_order matching its original created_at order within its own tier
    And display_label and section are NULL on every row
    And field_label and form_section are byte-identical to their pre-migration values
```

### F6.9.2 — Shared-tier registry write parity (PR 1)

- **Description:** The shared tier (`org_id IS NULL`) gains the complete
  authenticated mutation surface the registry needs: capture/manual insert,
  decision changes (approve/fixed/human-fill/unmap), and metadata/order
  edits.
- **Persona:** P1.
- **Benefit hypothesis:** Trained forms are shared payer truth (D10/D12), but
  extension capture can only create org-scoped rows and shared-row RLS
  rejects direct INSERT/UPDATE — a shared form can never accumulate mappings
  today.
- **Acceptance criteria:**
  - A shared propose path creates `org_id IS NULL` rows from extension
    capture. It does **not** reuse `proposeFieldMap` or the org-resolving
    `authenticate()` guard; it runs on the user-scoped `authenticateUser()`
    guard with an org-free context. Idempotency is index-backed per F6.9.1
    (`ON CONFLICT DO NOTHING` + re-read); the org path moves to the same
    mechanism.
  - The shared insert path also supports F6.9.6 manual registry rows with
    their deterministic `manual:` selector and required note. Callers never
    submit an `org_id`.
  - `train_global_field_map` accepts `source = 'hardcoded'` plus a non-empty
    `hardcoded_value`; that transition writes `status = 'approved'`, clears
    `token`, and rejects an empty literal.
  - Repropose (unmap) clears both `token` and `hardcoded_value` and sets the
    canonical undecided shape used by captured rows: `status = 'proposed'`,
    `source = 'manual'` with the required note.
  - A dedicated shared registry-update RPC writes `display_label`, `section`,
    and `sort_order` on `org_id IS NULL` rows, including explicit clearing of
    nullable labels/sections, and accepts a batch for re-capture ordering.
  - The shared paths are open to **any signed-in user** (D11); an
    unauthenticated caller is rejected; the org-scoped behavior is unchanged.
  - Shared writes follow the interim no-history posture (D14):
    `updated_at` is the trail.
  - Server-side isolation assertions cover the new paths: a shared write
    never reads or mutates an org row and vice versa.
- **Test/data scenario(s):** TS-156, TS-157.

```gherkin
Feature: Shared mappings can be captured, fixed, and unmapped
  Scenario: A signed-in user unmaps an approved shared field
    Given a shared field map on the fixture approved to provider.npi
    When a signed-in user unmaps it
    Then the row returns to the canonical proposed shape with no token or fixed value

  Scenario: A signed-in user sets a fixed value on a shared field
    Given a proposed shared field map with no matching token
    When the user saves the fixed literal "Credentialing Coordinator"
    Then the row is approved with source hardcoded and no token

  Scenario: An unauthenticated caller cannot write the shared tier
    Given a request with no authenticated session
    When it attempts a shared unmap
    Then the request is rejected
    And no shared row changes
```

### F6.9.3 — Unified field list: mapped rows stay visible (PR 1)

- **Description:** The Submit-form task editor's Form setup panel
  (`FormStepPanel`) lists **every** registry row for the bound portal —
  proposed, approved, broken, manual — with its current decision shown inline
  and editable at any time, plus an Unmap action.
- **Persona:** P1.
- **Benefit hypothesis:** Approved rows vanish today, so a trained form
  cannot be reviewed or corrected from the editor at all.
- **Acceptance criteria:**
  - All rows render grouped by section (F6.9.5) in `sort_order`, each showing
    display name, current decision (token / fixed value / human fills this /
    undecided / stale), and inline edit affordances.
  - Approving, unmapping, or re-mapping a field never changes its position.
  - An informational summary reads coverage, e.g. `4 of 23 mapped · 5 pages
captured` — display only, no readiness semantics (D13).
  - Shared rows mutate through the F6.9.2 RPCs; org rows keep the existing
    org-RLS paths.
- **Test/data scenario(s):** TS-144.

### F6.9.4 — Three decision actions with an exhaustive classifier (PR 1)

- **Description:** Each row offers exactly three decisions — **map a token**,
  **set a fixed value**, **human fills this** — and one shared exhaustive
  `(status, source)` classifier replaces the dry run's source-first filter.
- **Persona:** P1.
- **Acceptance criteria:**
  - **Map a token** — the existing approve path, with the grouped-by-family
    picker (D8, equivalent to `groupedTokens` in `TemplateTaskRow`; helper
    shared, not duplicated; the "No token" entry is removed).
  - **Fixed value** — a literal input writing `source: hardcoded`, non-empty
    `hardcoded_value`, `status: approved`, `token: null`. Counts as mapped;
    the extension and dry run both fill from `source = 'hardcoded'` (one
    rule, `HARDCODED_PSEUDO_TOKEN` inference retired).
  - **Human fills this** — stores no value: `status: approved`,
    `source: manual`, `token: null`, `hardcoded_value: null`, plus the
    non-null `notes` the `portal_field_maps_notes_required` CHECK demands.
    Does **not** count as mapped; excluded from automated fill; a decided
    outcome, not a failure.
  - The classifier is exhaustive over `(status, source)`, fails closed on
    invalid combinations, and is the single source for the list, the dry
    run, and the coverage read-out. No consumer filters by source before
    checking status.
- **Test/data scenario(s):** TS-145.

```gherkin
Feature: Deciding a field three ways
  Scenario: A required box with no token gets a fixed value
    Given a proposed field "Contact role" with no matching token
    When P1 saves the fixed value "Credentialing Coordinator"
    Then the row shows the literal inline and counts as mapped
    And the dry run fills it

  Scenario: Human-fill rows stop inflating the mapped count
    Given a proposed field "How did you hear about us?"
    When P1 marks it Human fills this
    Then the row shows "Human fills this" and does not count as mapped
    And the dry run reports it as intentionally skipped, not undecided
```

### F6.9.5 — Sections, inline rename, and real-form ordering (PR 1)

- **Description:** Fields group under admin-editable sections in live-form
  order; generic captured names are renameable inline.
- **Persona:** P1.
- **Acceptance criteria:**
  - Grouping falls back `section ?? form_section ?? page_step ?? "Fields"`;
    the admin can assign/clear a section inline and per-section progress
    renders (e.g. `Tax ID: 2 of 5 mapped`).
  - The display name is an inline-editable text box writing `display_label`;
    `field_label` is never overwritten and re-capture never clobbers a
    rename (D6).
  - Order is `sort_order` (capture-derived); decisions never reorder. On
    re-capture, order is re-derived from the live form while mappings,
    renames, and sections are preserved; fields missing from the new capture
    are marked stale via the existing drift mechanism, never deleted (D7).
  - Shared rows write through the F6.9.2 metadata RPC (batch for reorder);
    org rows use the existing org-RLS path.
- **Test/data scenario(s):** TS-146, TS-147, TS-148.


### F6.9.6 — Data fields unified into the registry (PR 1)

- **Description:** On `online_form` steps the separate Data fields section
  stops rendering; its entries migrate into the registry, and "Add field"
  creates registry rows directly.
- **Persona:** P1.
- **Acceptance criteria:**
  - "Add field" creates an undecided registry row with `status: proposed`,
    `source: manual`, the required note, and a deterministic `manual:`
    synthetic selector derived from the row's stable identity
    (`selector` stays `NOT NULL`). The fill engine and drift repair ignore
    `manual:` selectors. Shared rows insert through the F6.9.2 RPC.
  - Existing `dataFields` entries on online-form steps migrate into registry
    rows; the `dataFields` JSON key is **retained** (additive-only rule) and
    simply stops being read for those steps.
  - A new template version snapshot — version N+1 with identical content plus
    a `current_version` bump (`UNIQUE (template_id, version)` holds) — is
    created **before** the migration runs.
  - The migration is DML-only and mechanically idempotent: deterministic
    `manual:` selectors regenerate identically and the F6.9.1 unique index
    makes a re-run a no-op.
- **Test/data scenario(s):** TS-149.

### F6.9.8 — Org-free shared capture with page stamping (PR 2)

- **Description:** Train-forms capture proposes **shared** rows (no org) and
  stamps each capture with the wizard page it came from.
- **Persona:** P1.
- **Acceptance criteria:**
  - Training mode sends no `x-org-id` and selects no org, including for
    multi-org users; its routes run on `authenticateUser()` (the
    org-resolving `authenticate()` guard cannot serve this mode). The
    extension's header exemption is keyed by mode, not path literals.
  - Capture proposes through the F6.9.2 shared path; rows land with
    `org_id IS NULL`. Case mode's org resolution is untouched.
  - `SEND_CAPTURE` populates `page_step` on every proposed row. Page identity
    derives from URL and/or wizard heading, falling back to capture sequence
    (`Page 1`, `Page 2`, …) when neither distinguishes — capture never blocks
    or prompts; the admin renames pages in the editor (F6.9.5).
  - `sort_order` is assigned from DOM order within the captured page; pages
    order by capture sequence.
  - The payload remains shape-only — labels, selectors, control types,
    section, page. No value ever leaves the page.
- **Test/data scenario(s):** TS-152, TS-153.

```gherkin

  Scenario: A trainer walks all five fixture pages
    Given the fixture wizard has 5 pages
    When P1 captures each page in turn while advancing the form themselves
```

### F6.9.9 — New/existing form recognition (PR 2)

- **Description:** Train forms recognizes whether the page belongs to a form
  the system already knows (D15/D16) and behaves accordingly.
- **Persona:** P1.
- **Acceptance criteria:**
  - Multiple forms per payer are supported via the portal registry — each
    trained form is a portal row. A **new** form (no matching portal by
    URL/heading) is greeted as new; the extension guides the user to capture
    every section, then the user submits and returns to the web app to review
    mappings in the Submit-form task editor (D18).
  - When URL/heading cannot distinguish a new form from an existing portal
    row, a numbered candidate portal name is created (`<Payer> form 2`, …)
    that the admin renames; capture never blocks.
  - An **existing** form is recognized: the panel shows its capture state
    (pages seen, fields captured, mapped count) and the user chooses what
    happens next — re-capture as drift repair, or nothing. The extension
    never silently changes mappings.
  - Nothing is auto-attached to any template or task (D17); the captured
    form remains in the shared library for deliberate use.
- **Test/data scenario(s):** TS-150.

```gherkin
Feature: Recognizing a form during training
  Scenario: A brand-new payer form is greeted and captured
    Given the fixture payer has no portal matching the open page
    When P1 starts Train forms on that page
    Then the panel greets the form as new and creates a portal candidate
    And after capturing all sections P1 submits and reviews mappings in the web app

  Scenario: A known form is recognized, not modified
    Given the open page matches an existing trained portal
    When P1 starts Train forms
    Then the panel shows pages seen, fields captured and mapped count
    And no mapping changes until P1 explicitly chooses to re-capture
```

## Out of Scope / Non-Goals (deferred, not reversed)

- **Org-specific overrides of shared mappings** — the shared tier is the only
  authoring tier in this version (D12). The OQ-3 two-tier precedence model is
  deferred.
- **Readiness rework** — coverage-replaces-Proven, the Form-setup-reviewed
  attestation, funnel/KPI/Scorecard changes (the earlier D3/OQ-4 rulings) are
  deferred to a follow-up epic; existing Proven machinery is untouched here.
- **Change history / undo / audit for shared writes** (D14) — R7 governance.
- **Per-page fill telemetry** (`fill_sessions` page attribution) — case-fill
  work, a different JTBD; deferred.
- **Automated traversal** — no Continue-clicking, no auto-submit, no
  auto-advance (D1). At most one page is captured per explicit user action.
- **Any auto-attach of a trained form to a template or task** (D17).
- **A role/permission system** — training is ungated (D11).
- **Case model changes** — cases stay org-scoped; generation, fill-requires-
  a-case, and the E4.3 hand-off are untouched.
