# E1.7a — SOP Versioning Spike (decision doc, no build)

## Purpose and Context

SOPs-as-data is the longest-lead asset in the program: R4's case generation
(E2.x) snapshots SOP versions onto tasks for traceability, so the versioning
model must be decided **before** E1.7b builds it — a wrong grain here is the
most expensive retrofit in the roadmap. E1.7a is deliberately a **spike, not
a build**: its deliverable is a reviewed decision document (an ADR-style doc
in `docs/redesign/`), not code. It runs in the R2 lane parallel to R1 forms.
The spike grounds itself in what already exists: the legacy `sop_templates`
table (org-scoped, with the E1.6-era global-row capability from migration
`20260707060000`), `src/lib/sopResolver.ts` (protected file — resolution
logic by match keys), and the task-generation paths that consume SOPs today.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — indirect: the decision determines
  how her team's per-payer/per-state procedures are authored, versioned, and
  trusted.
- (Direct audience is the engineering/PM pair choosing the model; no
  end-user surface ships in this epic.)

## Component & Data Constraints

- No UI, no migrations, no code in this epic — decision document only.
- The document must be grounded in the actual repo artifacts: `sop_templates`
  schema, `sopResolver.ts` behavior, existing task-generation flow, and the
  E1.6 global-catalog pattern.
- Any recommendation must respect locked decisions: additive-only
  migrations; SOPs keyed to payer/state; syncs/edits never silently
  overwrite; generation snapshots version onto tasks (traceability, E2.2).

## Features

### F1.7a.1 — Versioning-model decision document

- **Description:** An ADR-style doc evaluating at least three models:
  (a) immutable version rows (`sop_template_versions` child table; template
  = head pointer), (b) copy-on-publish (each publish is a new template row,
  chain linked), (c) append-only event/diff log with materialized current
  view. For each: authoring flow, resolution impact (`sopResolver`), task
  snapshot mechanics for E2.2, storage/complexity cost, and migration path
  from today's `sop_templates` rows.
- **Persona:** P1 (outcome), engineering/PM (decision).
- **Benefit hypothesis:** A deliberate, cheap decision now instead of an
  expensive retrofit after R4 tasks reference SOP content.
- **Acceptance criteria:**
  - Doc lands at `docs/redesign/E1.7a-sop-versioning-decision.md` with a
    single recommended model and explicit runner-up trade-offs.
  - Covers: version identity (what E2.2 stamps on a task), edit semantics
    (draft vs published), global-vs-org SOP interaction (E1.6 pattern), and
    rollback/audit expectations.
  - Names the migration sketch for E1.7b (tables/columns, additive only) —
    sketch, not migration files.
  - PM sign-off recorded (doc reviewed → decision locked in
    `CLARIFICATIONS_NEEDED.md`).
- **Test/data scenario(s):** None — no build. (Scenario coverage arrives
  with E1.7b.)

### F1.7a.2 — SOP content-shape inventory

- **Description:** A companion section inventorying what a credentialing SOP

  per-step channel (portal/fax/phone/mail), portal keys (extension fill

- **Acceptance criteria:**
  - At least two real SOPs (one commercial payer × two states, e.g. BCBS-NC
    and BCBS-KS) transcribed into the candidate shape as worked examples.
  - Gaps between the candidate shape and `sop_templates` today are listed
    explicitly.

## 5. Technical Considerations & Enablers

_Reviewer-owned (Devin). This is a spike: **no code, no schema, no migration.**
The enablers here are the verified repo facts the decision document must be
grounded in, plus the constraints its recommendation must honor. Verified
against `sop_templates` (baseline + migration `20260707060000`),
`src/lib/sopResolver.ts`, `src/services/templates.ts`, and the task tables._

- **TE-1 — Grounding facts the doc must cite (current state).**
  - `sop_templates` is org-scoped (`org_id`, nullable since
    `20260707060000_global_catalog_org_assignment.sql`) with match-key columns
    `group_id`, `state`, `specialty`, `payer_id`, a `task_definitions jsonb`
    payload, and an `archived boolean` — **there is no version column today.**
    Global SOPs (`org_id IS NULL`) are visible to an org only when it is
    assigned the SOP's payer (same policy as E1.6 payers).
  - `src/lib/sopResolver.ts` (protected) resolves `SOPTaskDefinition[]` →
    `ResolvedTaskInsert[]`, interpolating `{{tokens}}` (provider/group/facility/
    mso) via `buildTokenMap` + `TOKEN_PATTERN`. Template **selection** —
    which template a case gets — keys off the match columns and lives in
    `src/lib/pickTemplate.ts` (exact payer + state + group first, a null-group
    template counting as exact, then payer + state; archived excluded; NOT a
    protected file), not in the resolver. The doc must state the
    version-identity impact on BOTH steps: which version `pickTemplate`'s
    candidates represent (e.g. published heads only) and what, if anything,
    the resolver sees — **without proposing changes to `sopResolver.ts`** (it
    is protected per AGENTS.md).
  - The type shapes the model must fit: `SOPTaskDefinition`, `SOPStep`,
    `SOPStepType` (`draft_email | online_form | pdf`) in `src/types/index.ts` —
    including the optional `portalKey` an `online_form` step may carry
    (bare/normalized via `normalizePortalKey` in `src/lib/tokenFormat.ts`,
    passed through the resolver **verbatim** as an identifier). F1.7a.2's
    inventory names portal keys explicitly; whichever version model wins must
    carry `portalKey` unchanged or the extension close-out join breaks.
  - Authoring today is the Admin > Templates 4-step wizard
    (`src/components/templates/TemplateWizard.tsx` + the `editableTemplate.ts`
    converters); save is ONE `createTemplate`/`updateTemplate` call
    (`src/services/templates.ts`) that **overwrites `task_definitions` in
    place** — no draft state exists, and the only edit history is the
    before/after JSON `writeAudit` stores in `audit_log`. That trail is
    diagnostics, not a version store: the doc's "edit semantics (draft vs
    published)" and "rollback/audit expectations" sections must start from
    this baseline.
- **TE-2 — The concrete gap the spike exists to close.** Task generation today
  copies the _resolved_ SOP steps into `tasks.sop_content jsonb` (the
  `create_case_with_tasks` RPC copies `sop_content` verbatim from its
  `p_tasks` rows — baseline migration — and `buildTerminationSteps` in
  `src/services/providers.ts` writes it directly) with **no reference back to
  which SOP template/version produced them** (`tasks.is_auto_generated` marks
  generated-ness, not identity). E2.2 wants
  traceability — "what version stamped this task." So the doc's core deliverable
  is deciding _what version identity gets stamped onto a task_ and how it is
  stored additively (e.g. `tasks.sop_template_id` + `sop_version` columns, or an
  embedded version tag in the existing `sop_content` jsonb) — a concrete,
  additive sketch, not a migration.
- **TE-3 — Constraints the recommendation must honor (non-negotiable).**
  Additive-only migrations; SOPs keyed to payer/state (+group/specialty match
  keys, do not drop them); syncs/edits never silently overwrite (the E1.6
  `payer_catalog_changes` diff-log philosophy applies to SOP content too);
  generation snapshots the version onto the task for traceability; append-only
  `touches`/`status_history`/`audit_log` untouched; the global-vs-org SOP
  interaction (the `20260707060000` pattern) must be preserved by whichever
  model wins. The three candidate models (immutable version rows / copy-on-
  publish / append-only event log) must each be scored against these.
- **TE-4 — Deliverable + gate (process, not build).** The doc lands at
  `docs/redesign/E1.7a-sop-versioning-decision.md` (a sibling file, ADR-style),
  names one recommended model + runner-up trade-offs, includes the two worked
  real-SOP examples (F1.7a.2) transcribed into the candidate shape with a gap
  list vs today's `sop_templates`, and sketches the additive E1.7b migration
  (tables/columns only). PM sign-off is recorded by appending a dated
  `[e1.7a]` decision entry to the root `CLARIFICATIONS_NEEDED.md` — the same
  mechanism prior stage decisions used. No lint/test/e2e gates apply (no code);
  run `npx prettier --write` on the decision doc for formatting consistency.
- **Likely tech debt to contain — none incurred: no new schema, no code.**
  By construction the spike adds nothing runnable. The only forward risk it
  manages is _deciding late_: E2.x case generation (R4) references SOP
  content, so the model must be locked before E1.7b builds it — which is
  exactly why this spike gates E1.7b.
