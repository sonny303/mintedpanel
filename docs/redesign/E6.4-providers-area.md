# E6.4 — Providers Area: the Consolidated People Record

## Purpose and Context

Provider information is scattered (wizard sections, detail page, documents
panel, licenses) and editing is dangerous: the monolithic edit form silently
drops facility assignments on save (a live defect — assignments are
effectively write-once at creation). Per decision record decision 5 and the
providers screen mocks, this epic makes Providers the single consolidated
people surface: an A→Z PHI-safe roster, a one-page record with inline field
editing, in-place facility/group management, **enrollment-fact capture**
(migration — facts, never auto-cases), and the per-provider case + denial
story. The wizard's provider step IS this surface, so there is never a second
place to add a provider.

## Personas Empowered

- P1 Credentialing Manager — onboards and maintains providers in one place.
- P2 Credentialing Coordinator / Specialist — looks up licenses, CAQH
  dates, and case status mid-work without changing rooms.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md); Outer Banks Rehab Group's Brooke
  Ostrander fixture (multi-license) anchors record tests.
- PHI rules bind: the roster list projection carries NO DOB, SSN, or home
  address columns; SSN renders last-4 masked on the record; full-SSN stays
  vault-only (E4.4 unchanged).
- Implementation dependencies (flagged): enrollment-facts store ships in
  E6.2; the assignment-sync defect fix touches the provider update path
  (assignments become ordinary editable data through the existing
  assignment services); the provider CSV extends to one-row-per-relationship
  using the existing staged-import engine.

## Features

### F6.4.1 — The roster: A→Z, PHI-safe, gaps ambient

- **Description:** The provider list sorted **A→Z by last name by default**
  (stated on screen; search/filters never change the sort), columns:
  name/credentials, NPI, groups, facility count, license states + soonest
  expiry, CAQH attestation date, cases summary, gap pills. Filters: group,
  license state, has-gaps. Gap pills carry the ex-Fix-it provider-data-gap
  job ambiently (missing W-9, stale CAQH, expiring license, **no facility
  assignment** — flagged because such a provider cannot generate cases);
  clicking a pill lands on the record with that section focused.
- **User story:** As P2, I find the right provider in seconds and see what
  needs attention without a separate queue.
- **Persona:** P1, P2.
- **Benefit hypothesis:** One glanceable roster replaces the Fix-it detour
  for provider-data problems and gives the alphabetical access the PM
  asked for.
- **Acceptance criteria:**
  - Default sort A→Z (last name), always; list projection stays PHI-safe.
  - Gap derivations reuse the existing readiness facts — no new gap engine.
  - Zero-facility providers are flagged on the roster and the record.
- **Test/data scenario(s):** TS-112.

### F6.4.2 — The one-page record with inline editing

- **Description:** One page per provider with section jump-nav (Identity ·
  Groups & facilities · Licenses · Enrollments · Cases · Documents). Every
  identity/contact field edits inline (pencil → change → save, audited);
  the monolithic edit form is retired. DOB renders masked-at-rest with
  reveal-on-edit; SSN shows last-4 only per the vault rules.
- **User story:** As P1, updating a phone number or specialty is one click
  on the field, not a trip through a form that touches everything.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Inline editing removes the blast radius of the
  monolithic form — including the defect it carried.
- **Acceptance criteria:**
  - Every editable field saves independently with audit; validation
    inline under the field.
  - The `/providers/$id/edit` route retires to a redirect; no full-form
    edit path remains.
  - Section nav is keyboard-reachable; sections deep-link (`#licenses`).
- **Test/data scenario(s):** TS-112.

### F6.4.3 — Groups & facilities, managed in place

- **Description:** The record's Groups & facilities panel: group membership
  chips (primary marked; add/remove via the existing assignment rules —
  ≥1 group, exactly one primary), and the facility list with start dates
  plus a first-class **+ Add facility** action opening a picker of the
  provider's groups' facilities (with start date). Assignments become
  ordinary, editable data — fixing the live defect where saving the edit
  form dropped them.
- **User story:** As P1, when Dr. Chen picks up shifts at a second clinic,
  adding it is one click on her record — and nothing I do elsewhere ever
  silently removes it.
- **Persona:** P1.
- **Benefit hypothesis:** Facility assignment stops being write-once;
  candidacy (which requires an assignment) becomes maintainable.
- **Acceptance criteria:**
  - Add/remove facility and group work from the record with start dates;
    the one-primary invariant holds through every path (existing RPC).
  - Regression test pins: no provider-record edit path can clear
    assignments as a side effect.
  - Adding a facility updates candidacy (E6.3 buffer) on next derivation.
- **Test/data scenario(s):** TS-112.

### F6.4.4 — Enrollment-facts capture (migration)

- **Description:** The record's Enrollments panel and the onboarding form's
  "Current enrollments under {group}'s contract" section capture facts:
  payer, state, effective date. The section is explicitly labeled that
  prior-employer status does NOT belong here (a new hire gets the full
  path regardless). Facts render with an **Expire** action; expiring
  re-opens the candidate in the group's buffer. Never creates a case.
- **User story:** As P1 migrating an established practice, I record what's
  already true and the system builds zero fake work from it.
- **Persona:** P1.
- **Benefit hypothesis:** Migration capture without queue noise — the PM's
  "auto-cases are noise" decision, operationalized.
- **Acceptance criteria:**
  - Capture in both places (record panel, onboarding section) writes the
    same fact store (E6.2); labeling guard text present.
  - Expire flips the fact (audited) and the combination reappears as a
    candidate; the payer row's Active derivation updates.
  - CSV capture: one row per enrollment on the provider template.
- **Test/data scenario(s):** TS-113.

### F6.4.5 — Cases & denial history on the record

- **Description:** The record's Cases panel: one line per case with the
  E6.0 status pill; a denied-then-reapplied payer shows the current cycle
  with the prior denial (reason + date) preserved beneath; provider
  progress ("x of y approved") in the header. Rows link into Cases.
- **Persona:** P1, P2.
- **Benefit hypothesis:** The provider-level denial rollup the PM asked
  for, readable in place and consistent with the E6.6 report.
- **Acceptance criteria:**
  - All statuses derive from E6.0; denial reasons render from the fixed
    word-list; nothing on this panel is settable.
- **Test/data scenario(s):** TS-112.

### F6.4.6 — Provider CSV: one row per relationship, prefilled templates

- **Description:** The provider import (living on this page) extends to
  one-row-per-relationship for multi-group/facility/license/enrollment
  (provider identity columns repeated; folded on commit — the existing
  license-fold pattern generalized). The downloadable template pre-fills a
  reference sheet of the org's ACTUAL group and facility names, replacing
  type-and-hope name matching. Commit ends in the unified summary: the
  resolved relationship graph ("2 providers · groups, facilities,
  enrollments as committed"), cross-referenced before moving on.
- **User story:** As P1 bulk-loading a migrated roster, I copy real names
  from the template's reference sheet and finish on one summary I can
  trust.
- **Persona:** P1.
- **Benefit hypothesis:** Kills the name-mismatch failure mode and the
  four-disconnected-confirmations problem in one stroke.
- **Acceptance criteria:**
  - Multi-row folding on the five-part dedupe grain; SSN sweep and staged
    commit semantics unchanged.
  - Template carries the real names reference; scan errors name rows and
    columns; unified summary renders post-commit.
- **Test/data scenario(s):** TS-112, TS-113.

## Dependencies

- E6.0 (status pills), E6.2 (enrollment-facts store, buffer), E6.3
  (candidacy consumption). Build after E6.2.
- Existing services reused: provider CRUD, assignment sync + one-primary
  RPC, license editors, staged import engine, readiness facts (for gaps).
- Wizard integration: the wizard's provider step mounts this surface
  (E6.1 F6.1.5).

## Out of Scope / Non-Goals

- No per-analyst assignment; no provider self-service portal.
- No SSN/DOB changes beyond existing vault + masking rules.
- No document-storage changes (E4.5 panel is composed as-is).
- Terminated-provider flows unchanged (terminate, never delete).
