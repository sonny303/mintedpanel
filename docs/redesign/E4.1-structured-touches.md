# E4.1 — Structured Touches & Follow-up Cadence

## Purpose and Context

`[r6]` decision A2: free-text notes are a dead end for SaaS analytics — you
cannot run operational-efficiency reports or trigger automations off
paragraphs of text. This epic makes the existing append-only touch log
**structured**: every touch carries a **touch type** (Call, Portal Check,
Email, Fax, CAQH Update) chosen from a dropdown plus a **single-line context**
input, keeping the UI high-density. Touches can set a **next follow-up date**,
and **overdue follow-ups explicitly surface in the E2.3 next-best-action
queue** so applications don't rot in payer purgatory (A1's "In
Review/Touches" phase — payer portals are black boxes and the back-and-forth
must be tracked against the case).

The extension's manual submission logging (R2 Workbench) continues to land in
this same touch log (`[r6]` decision B) and adopts the structured types.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — logs typed touches in one
  dropdown + one line; works overdue follow-ups from the queue.
- **P1 Credentialing Manager** — reads touch cadence and follow-up health
  across the caseload; future R8 reporting runs on touch types.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- `touches` is append-only (AGENTS.md) — structure is added additively
  (type/follow-up columns or an additive sibling), never by mutating
  existing rows; reviewer records the mechanism in §5.
- The queue integration extends E2.3's fully derived ranking — no stored
  priority (E1.0 derived-progress rule).

## Features

### F4.1.1 — Typed touches (dropdown + one line)

- **Description:** Logging a touch requires a type — **Call, Portal Check,
  Email, Fax, CAQH Update** — via dropdown, plus a single-line context
  input. The case touch log renders type as a compact pill with the context
  line; free-paragraph entry is retired from the touch flow (long-form
  narrative stays in case notes, not touches).
- **Persona:** P2.
- **Benefit hypothesis:** typed touches make cadence reportable and
  automatable (A2) with zero added logging friction — one dropdown, one
  line.
- **Acceptance criteria:**
  - A touch cannot be saved without a type; context is a single-line input.
  - The five types above ship as the fixed initial vocabulary (org
    extension, if any, is an E4.2 admin concern — not free-typed here).
  - Existing (untyped) historical touches render unchanged; no backfill.
  - Extension-logged submission touches carry a type through the same
    contract.
- **Test/data scenario(s):** TS-73.

```gherkin
Feature: Typed touch logging
  Scenario: High-density touch entry
    Given an open case in payer-pipeline state "In Review"
    When P2 logs a touch of type "Portal Check" with context "No status change; ref HUM-449"
    Then the touch log shows a Portal Check pill with that single line
    And the touch is stored with a structured type, not parsed from text
```

### F4.1.2 — Follow-up date on a touch

- **Description:** A touch may set a **next follow-up date** (e.g. "re-check
  portal in 14 days"). The case shows its single active next-follow-up; a
  newer touch with a follow-up date supersedes it (derived from the
  append-only log, latest wins).
- **Persona:** P2.
- **Benefit hypothesis:** the follow-up cadence lives on the case instead of
  in a specialist's memory or an external calendar.
- **Acceptance criteria:**
  - Follow-up date is optional per touch; the case's active follow-up is
    derived as the latest touch's follow-up value.
  - Case detail and case list show the next follow-up date; overdue renders
    distinctly.
- **Test/data scenario(s):** TS-74.

### F4.1.3 — Overdue follow-ups surface in the next-best-action queue

- **Description:** The E2.3 "My Cases" queue adds overdue follow-ups as a
  ranking input: a case whose follow-up date is past due surfaces explicitly
  (labeled with the overdue follow-up and its touch type). Per the resolved
  `[r6]` NBA-configurability decision (PM 2026-07-14), the ranking is
  **admin-configurable at the organization level with a shipped default**:
  by default, overdue follow-ups rank above deadline-only rows with ties by
  earliest deadline; an org admin may reorder/enable the ranking inputs in
  the E4.2 admin module (F4.2.5). The queue stays fully derived — the org
  config is an input to the derivation, never stored per-case priority.
- **Persona:** P2, P1.
- **Benefit hypothesis:** A2's explicit requirement — overdue follow-ups
  must surface in the queue to prevent applications from rotting in payer
  purgatory.
- **Acceptance criteria:**
  - An overdue follow-up places the case in the queue with an explicit
    "follow-up overdue" reason label.
  - Completing a follow-up (logging the touch) clears the overdue state
    without any stored flag — fully derived.
  - Queue ranking remains deterministic and documented; with no org
    config saved, the shipped default applies; a saved org config
    (F4.2.5) changes the ranking for that org only, immediately, for all
    its users.
  - Ranking settings are read from org-level config; no per-case or
    per-user priority is ever stored.
- **Test/data scenario(s):** TS-75.

```gherkin
Feature: Overdue follow-ups in the queue
  Scenario: Overdue portal check surfaces first
    Given a case whose latest touch set a follow-up date of yesterday
    When P2 opens My Cases
    Then that case appears above deadline-only rows
    And its row names the overdue follow-up and touch type
    And logging the follow-up touch removes the overdue reason on refresh
```

  responses are logged manually as Email/Fax touches; inbox integration is
  a later release (recorded as roadmap candidate).
- No reporting dashboards (R8 consumes the structured types later).

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the shipped touch spine
(`supabase/migrations/20260704210000_baseline_live_schema.sql` `touches`, widened
by `20260707120000_touchlog_entry_types.sql`), the touch service
(`src/services/touches.ts` — `logTouch`, `logNote`, `getLatestTouchFollowUps`,
`getLastTouchDates`), the extension submission-touch path
(`src/services/submissionTouches.ts`, `src/server/extensionRoutes.ts`), the E2.3
queue (`src/services/nextBestActions.ts` reads + the pure ranking module
`src/lib/nextBestActions.ts` and its test, surfaced by
`src/components/work/NextBestActionQueue.tsx`), `docs/data-model/table-register.md`,
and `uiux-component-guide.md`. **Headline:** almost all of this epic's storage
already ships — `touches` carries `touch_type`, `next_follow_up_date`,
`entry_type` (`touchpoint|note|system_event|task_update`), `source`
(`manual|email_webhook|extension`) and `notes`; `getLatestTouchFollowUps` already
derives the case's active (latest-wins) follow-up. The only schema change is
adding one touch-type value; the rest is UI + a queue-ranking extension. This is
a surface + derivation epic, not a new data model._

- **TE-1 — Add `caqh_update` to the `touches.touch_type` CHECK (the only
  migration).** The type is currently `call|email|portal|fax|mail`; "Portal
  Check" maps to the existing `portal`, "Call/Email/Fax" to `call|email|fax`,
  leaving `caqh_update` as the single new value. Follow the established
  drop-and-re-add-with-the-union pattern from `20260707120000` so every legacy
  row stays valid and NULL is still allowed for non-touchpoint entries:

  ```
  ALTER TABLE public.touches DROP CONSTRAINT IF EXISTS touches_touch_type_check;
  ALTER TABLE public.touches ADD CONSTRAINT touches_touch_type_check
    CHECK (touch_type IS NULL OR touch_type = ANY (ARRAY[
      'call','email','portal','fax','mail','caqh_update']));
  ```

  Additive, applied repo + hosted per `docs/migration-baseline.md`; regenerate
  `src/integrations/supabase/types.ts`; extend the `TouchType` union in
  `src/types/index.ts` (additive); update the `touches` register row in the same
  PR. `mail` is retained (Story 3) even though it is not in the F4.1.1 initial
  vocabulary — do NOT drop it (that would be destructive); the E4.1 dropdown
  simply offers the five named types.

- **TE-2 — Typed entry is a UI + validation change on `logTouch`, not new
  storage (F4.1.1).** The touch-entry form requires a `touch_type` (already the
  submit contract; make the picker required, no free-typed types), and its
  context uses the existing `notes` column constrained to a single-line `input`
  (not a `textarea`) in the touch flow — long-form narrative continues to go
  through `logNote` (`entry_type='note'`), so free-paragraph entry is retired
  from the touch flow without touching historical rows. The touch log renders
  the type as a status `badge` (`rounded-full`, tokens only) beside the
  single-line context. Existing untyped/legacy touchpoints render unchanged (no
  backfill) — the `touch_type`-null and older-vocabulary rows already coexist by
  the Story 3 shape check.

- **TE-3 — Follow-up date is already derived; this epic only surfaces it
  (F4.1.2).** `getLatestTouchFollowUps` returns the latest touchpoint's
  `next_follow_up_date` per case (latest-wins supersession, exactly F4.1.2). Add
  it to case detail and the case-list read (a small join in memory, the queue
  precedent) and render overdue distinctly (derived `< today`, no stored flag).
  No new service — reuse the existing selector.

- **TE-4 — Overdue follow-ups extend the E2.3 pure ranking, fully derived
  (F4.1.3).** The queue already joins cases/tasks/touches/readiness in
  `src/lib/nextBestActions.ts`. Add the per-case latest follow-up
  (`getLatestTouchFollowUps`, already an org-cache read) as a ranking input:
  a case whose follow-up date is past due sorts above deadline-only rows, with
  ties broken by earliest deadline, and carries an explicit "follow-up overdue"
  reason label naming the touch type. Because the state is derived from the
  append-only log, logging the follow-up touch (a newer touchpoint) clears the
  overdue reason on the next refresh with no stored flag to reset. Ranking stays
  deterministic and is documented in the module + covered by
  `nextBestActions.test.ts`. Per the resolved `[r6]` NBA-configurability
  decision (PM 2026-07-14), the shipped default is exactly this ordering
  (overdue follow-ups above deadline-only, ties by earliest deadline) **and** the
  ranking now reads the org-level queue config from E4.2 F4.2.5 as an input to
  the same pure derivation — no config ⇒ the shipped default, so E4.1 builds and
  behaves correctly whether or not an org has customised it. The config is a
  ranking input only; nothing per-case/per-user is stored (E1.0 derived rule).

- **TE-5 — Extension submission touches adopt the type through the existing
  contract (F4.1.1 AC).** `recordSubmissionTouch` /
  `POST /api/cases/:id/touches` (writer-role-gated, the one extension write)
  already lands rows in `touches`; extend its input to carry the structured
  `touch_type` + single-line context so extension-logged touches are identical
  to webapp ones (this is also E4.3 F4.3.4). No new endpoint; dual-path and the
  no-new-write-path posture are preserved. Coordinate the extension-side field
  in `sonny303/minted-extension`; this epic owns the platform contract.

- **TE-6 — Seed + tests.** Seed TS-73–TS-75 on the Dillon fixtures: a typed
  touch (Portal Check with a one-line context), a follow-up-date supersession
  pair, and a case with a past-due follow-up for the queue path. Unit tests
  extend `nextBestActions.test.ts` (overdue ranking, tie-break, clear-on-log);
  the `touches` register row is updated in the same PR.
