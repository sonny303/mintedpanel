# E4.1 — Structured Touches & Follow-up Cadence

## Purpose and Context

`[r6]` decision A2: free-text notes are a dead end for SaaS analytics — you
cannot run operational-efficiency reports or trigger automations off
paragraphs of text. This epic makes the existing append-only touch log
**structured**: every touch carries a **touch type** (Call, Portal Check,
Email, Fax, CAQH Update) chosen from a dropdown plus a **single-line context**
input, keeping the UI high-density. Touches can set a **next follow-up date**,
and **overdue follow-ups explicitly surface in the E2.3 next-best-action
queue** so applications don't rot in payer purgatory (A1's "In
Review/Touches" phase — payer portals are black boxes and the back-and-forth
must be tracked against the case).

The extension's manual submission logging (R2 Workbench) continues to land in
this same touch log (`[r6]` decision B) and adopts the structured types.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — logs typed touches in one
  dropdown + one line; works overdue follow-ups from the queue.
- **P1 Credentialing Manager** — reads touch cadence and follow-up health
  across the caseload; future R8 reporting runs on touch types.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- `touches` is append-only (AGENTS.md) — structure is added additively
  (type/follow-up columns or an additive sibling), never by mutating
  existing rows; reviewer records the mechanism in §5.
- The queue integration extends E2.3's fully derived ranking — no stored
  priority (E1.0 derived-progress rule).

## Features

### F4.1.1 — Typed touches (dropdown + one line)

- **Description:** Logging a touch requires a type — **Call, Portal Check,
  Email, Fax, CAQH Update** — via dropdown, plus a single-line context
  input. The case touch log renders type as a compact pill with the context
  line; free-paragraph entry is retired from the touch flow (long-form
  narrative stays in case notes, not touches).
- **Persona:** P2.
- **Benefit hypothesis:** typed touches make cadence reportable and
  automatable (A2) with zero added logging friction — one dropdown, one
  line.
- **Acceptance criteria:**
  - A touch cannot be saved without a type; context is a single-line input.
  - The five types above ship as the fixed initial vocabulary (org
    extension, if any, is an E4.2 admin concern — not free-typed here).
  - Existing (untyped) historical touches render unchanged; no backfill.
  - Extension-logged submission touches carry a type through the same
    contract.
- **Test/data scenario(s):** TS-73.

```gherkin
Feature: Typed touch logging
  Scenario: High-density touch entry
    Given an open case in payer-pipeline state "In Review"
    When P2 logs a touch of type "Portal Check" with context "No status change; ref HUM-449"
    Then the touch log shows a Portal Check pill with that single line
    And the touch is stored with a structured type, not parsed from text
```

### F4.1.2 — Follow-up date on a touch

- **Description:** A touch may set a **next follow-up date** (e.g. "re-check
  portal in 14 days"). The case shows its single active next-follow-up; a
  newer touch with a follow-up date supersedes it (derived from the
  append-only log, latest wins).
- **Persona:** P2.
- **Benefit hypothesis:** the follow-up cadence lives on the case instead of
  in a specialist's memory or an external calendar.
- **Acceptance criteria:**
  - Follow-up date is optional per touch; the case's active follow-up is
    derived as the latest touch's follow-up value.
  - Case detail and case list show the next follow-up date; overdue renders
    distinctly.
- **Test/data scenario(s):** TS-74.

### F4.1.3 — Overdue follow-ups surface in the next-best-action queue

- **Description:** The E2.3 "My Cases" queue adds overdue follow-ups as a
  ranking input: a case whose follow-up date is past due surfaces explicitly
  (labeled with the overdue follow-up and its touch type). Per the resolved
  `[r6]` NBA-configurability decision (PM 2026-07-14), the ranking is
  **admin-configurable at the organization level with a shipped default**:
  by default, overdue follow-ups rank above deadline-only rows with ties by
  earliest deadline; an org admin may reorder/enable the ranking inputs in
  the E4.2 admin module (F4.2.5). The queue stays fully derived — the org
  config is an input to the derivation, never stored per-case priority.
- **Persona:** P2, P1.
- **Benefit hypothesis:** A2's explicit requirement — overdue follow-ups
  must surface in the queue to prevent applications from rotting in payer
  purgatory.
- **Acceptance criteria:**
  - An overdue follow-up places the case in the queue with an explicit
    "follow-up overdue" reason label.
  - Completing a follow-up (logging the touch) clears the overdue state
    without any stored flag — fully derived.
  - Queue ranking remains deterministic and documented; with no org
    config saved, the shipped default applies; a saved org config
    (F4.2.5) changes the ranking for that org only, immediately, for all
    its users.
  - Ranking settings are read from org-level config; no per-case or
    per-user priority is ever stored.
- **Test/data scenario(s):** TS-75.

```gherkin
Feature: Overdue follow-ups in the queue
  Scenario: Overdue portal check surfaces first
    Given a case whose latest touch set a follow-up date of yesterday
    When P2 opens My Cases
    Then that case appears above deadline-only rows
    And its row names the overdue follow-up and touch type
    And logging the follow-up touch removes the overdue reason on refresh
```

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the current append-only touch log
(`src/services/touches.ts`, `src/hooks/useTouches.ts`,
`src/components/cases/CaseTouchesPanel.tsx`, `src/lib/touchOutcomes.ts`), the
derived next-best-action queue (`src/lib/nextBestActions.ts`,
`src/hooks/useNextBestActions.ts`), the touch-log shape migration
`20260707120000_touchlog_entry_types.sql`, and the organization/security rules
in `AGENTS.md`. The architecture already has touchpoint entries,
channel-aware outcomes, optional `next_follow_up_date`, extension/batch source
fields, audit writes, and a derived follow-up projection. This epic extends
that foundation; it must not create a second activity log or persist queue
state._

- **TE-1 — Extend the touch vocabulary without rewriting history.** Keep
  `touches` as the single append-only activity table and widen the
  `touch_type` contract to the five R6 product values. The UI-to-storage map is
  explicit:

  | Product label | Stored `touch_type` |
  | ------------- | ------------------- |
  | Call          | `call`              |
  | Portal Check  | `portal`            |
  | Email         | `email`             |
  | Fax           | `fax`               |
  | CAQH Update   | `caqh_update`       |

  Existing `mail` rows and historical outcome values remain valid and render
  unchanged. Add `caqh_update` to the TypeScript union, database check, label
  map, icon map, and tests. The R6 compact form requires type + one-line
  context; therefore widen the touchpoint shape constraint so `outcome` may be
  null for this structured flow while preserving existing outcomes as optional
  enrichment. Do not synthesize an outcome merely to satisfy the legacy
  constraint.

- **TE-2 — Append-only latest-wins semantics must be deterministic.** A new
  touch is always an insert through `logTouch`; no row is updated to carry the
  active follow-up. `getLatestTouchFollowUps` and the pure queue input must
  select the latest touchpoint by `(touch_date DESC, created_at DESC, id DESC)`,
  not by the current date-only comparison. A latest touch with
  `next_follow_up_date = null` explicitly clears the prior active follow-up
  because the current value is derived solely from the latest touchpoint. Add
  `created_at`, `id`, and `touch_type` to the projection and pure reducer input
  so browser, server, and tests use the same tie-break and reason label.

- **TE-3 — Preserve the Component → hook → service → Supabase boundary.**
  `CaseTouchesPanel` owns the compact picker/input/date composition;
  `useLogTouch` owns the mutation and invalidation; `touches.ts` sets
  `org_id`, `case_id`, coordinator, `entry_type = 'touchpoint'`, and source
  before inserting through `externalClient`. Components must not import
  Supabase. Extend the shared `Touch`, `TouchType`, and `TouchInput` contracts
  rather than introducing an R6-only duplicate type.

- **TE-4 — Query keys and invalidation already provide the required refresh
  fan-out.** Keep organization-scoped keys. A successful insert must continue
  invalidating `["touches", orgId]`, the case key, and audit-log keys; add the
  next-best-action key if it is not already reached by the touch-prefix
  invalidation. This refreshes case detail, active follow-up, queue ordering,
  and audit history without stored flags or manual cache mutation.

- **TE-5 — Overdue ranking consumes org-scoped configuration but remains
  pure.** Extend `buildNextBestActions` to accept the validated E4.2 F4.2.5
  input order/enabled set. The `follow_up` input covers both the existing
  explicit next-follow-up and SOP-cadence touch deadlines; the other keys map
  to task due, provider start, and location launch. With no saved row, use the
  shipped comparator: arrived/overdue follow-ups first, then all remaining
  deadline signals by earliest date and the existing stable source/case
  tie-breaks. A saved order ranks enabled source groups in that order, then by
  deadline and stable case tie-breaks within a group; disabled groups
  contribute no signal. Invalid or incomplete configuration falls back
  atomically to the shipped default rather than producing a partial queue.
  Load the setting once per organization through its hook/service and pass it
  into the pure reducer; do not read configuration inside the reducer or
  persist `is_overdue`, priority, or queue rows.

- **TE-6 — Source and audit behavior stay explicit.** Webapp entries use
  `source = 'manual'`; extension-confirmed entries use `source = 'extension'`;
  communication-event fan-out keeps `communication_event_id`. Every individual
  append writes one `TOUCH_LOGGED` audit row after the touch succeeds. Batch
  logging must preserve per-case touch rows and per-touch audit traceability;
  a batch-level summary may be additional, never a replacement. Audit payloads
  may include type, date, and case ID, but should not copy free-text context
  unnecessarily.

- **TE-7 — Schema changes are additive/widening and organization-scoped.**
  Widen the touch-type and touchpoint-shape checks; do not rename or delete
  existing columns. Preserve append-only RLS: authenticated organization
  members may select; `admin` and `specialist` may insert; ordinary clients
  receive no update/delete path. Keep explicit table/sequence grants aligned
  with RLS, regenerate `src/integrations/supabase/types.ts`, and update
  `docs/data-model/table-register.md` in the implementation PR.

- **TE-8 — UI follows the approved dense case pattern.** Reuse `Select`,
  `Input`, `Label`, `Button`, `Badge`, and the existing timeline/table
  composition. Use approved design tokens, one-pixel borders, no
  shadows/gradients/decorative backgrounds, and a concise type pill plus one
  line of context. Labels are explicit; icon-only actions require an accessible
  name and tooltip. Do not modify protected layout or primitive files.

- **TE-9 — Tests cover derivation, compatibility, and write safety.** Add pure
  tests for same-day ordering, null-follow-up clearing, overdue precedence,
  default/configured/disabled ranking inputs, invalid-config fallback,
  historical `mail`/outcome rendering, and the new `caqh_update` label. Service
  tests must verify organization filters, append-only inserts, source, and
  audit failure behavior. Playwright coverage should exercise TS-73–TS-75,
  including queue removal after the clearing touch and immediate reranking
  after an E4.2 setting change. Extension-origin tests use the mock harness; CI
  must not call payer portals.
