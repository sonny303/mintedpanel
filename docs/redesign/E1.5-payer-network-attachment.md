# E1.5 — Payer Network Attachment

## Purpose and Context

Case generation (R4) needs to know exactly which payers each group is pursuing
in which states. The PM decision (2026-07-11) is that the _user experience_ is
org-level — Sowmya thinks "this org works with BCBS" — while the _system_
expands that intent into group × state attachment rows derived from where the
group's clinics are, showing the expansion for review and allowing exceptions
to be unchecked. The precise grain (`group × payer × state`) therefore exists
underneath without the user thinking in rows, and it is exactly what E2.x case
generation reads (case key: provider × group × payer × state).

The payer list an org can attach from is the Minted-curated shortlist enabled
via the existing `org_payer_assignments` visibility layer (E1.6): curated
during onboarding, configurable afterward from group settings so more payers
can be enabled as the org's needs grow. Attachment carries no status of its
own — attach means "we intend to pursue"; all real status lives on the
contract/case once generated. Removal archives (hidden from new case
generation, history kept) and re-attachment is easy, because payers deny and
later reopen (attach → denied → reapply 6 months later is a normal cycle).

## Personas Empowered

- **P1 Credentialing Manager** — attaches payers for the org, reviews the
  group/state expansion, manages exceptions.
- **P5 Practice / Organization Owner** — the org-level intent ("we take BCBS")
  originates with the practice.
- **P9 Payer Enrollment / Provider-Relations Rep** — the counterpart whose
  network the attachment targets (context persona, no UI).

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `org_payer_assignments` (unique `(org_id,
payer_id)`) is the visibility/curation layer and CANNOT hold group×state
  grain — E1.5 adds a new child table (working name `payer_network_targets`:
  `id, org_id, payer_id, group_id, state, status active|archived, created_at`,
  unique `(group_id, payer_id, state)`) with an additive migration and a
  table-register row.
- Implementation dependency: state derivation reads `facilities.group_id` +
  `facilities.state`; the expansion preview must be a pure, testable module.
- Implementation dependency: E1.6 payer catalog metadata (payer states,
  `payer_kind`) for filtering the curated list to relevant states.

## Features

### F1.5.1 — Attach a payer (org-level intent, curated list)

- **Description:** From the wizard's Payer Network section (E1.0 preview goes
  live), P1 picks from the org's curated payer shortlist — only payers enabled
  for the org via `org_payer_assignments`, not the full national catalog.
- **Persona:** P1.
- **Benefit hypothesis:** A short, relevant list beats searching 3,000+
  payers; curation happens once at onboarding and stays configurable.
- **Acceptance criteria:**
  - Payer picker lists only org-assigned catalog payers not yet attached.
  - Payers show name, kind, and states (from E1.6 metadata).
  - Attaching requires no status choice — attach = intend to pursue.
- **Test/data scenario(s):** TS-41.

```gherkin
Feature: Curated payer shortlist
  Scenario: Org sees only its enabled payers
    Given Shelby Sports Rehab has BCBS-NC, BCBS-KS, and Cigna-NC enabled via org payer assignments
    And the global catalog contains many more payers
    When P1 opens the attach-payer picker
    Then only the three enabled payers are offered
```

### F1.5.2 — Group/state expansion with exceptions

- **Description:** On attach, the system expands the org-level intent into
  group × state target rows derived from the group's facilities (a group is
  targeted in a state where it has ≥ 1 facility and the payer operates in that
  state). The expansion is shown for review before save; P1 can uncheck
  exception rows.
- **Persona:** P1.
- **Benefit hypothesis:** Sowmya thinks "this org works with BCBS"; the system
  does the row-level thinking, but the reviewable expansion keeps precise
  control (a payer can be pursued in a state for only one of two groups).
- **Acceptance criteria:**
  - Expansion preview lists every derived `group × state` row with the reason
    (facility count in that state).
  - Unchecking a row excludes it; saving creates only checked rows in
    `payer_network_targets`.
  - Adding a facility later in a new state does NOT silently create targets —
    the section surfaces a "new expansion available" review affordance.
  - A payer not operating in any of the group's states yields an empty
    expansion with an explanatory message.
- **Test/data scenario(s):** TS-41, TS-42.

```gherkin
Feature: Attachment expands to group/state rows
  Scenario: Two-group org attaches BCBS
    Given Shelby's Group 1 has NC facilities and Group 2 has NC and KS facilities
    And BCBS-NC covers NC and BCBS-KS covers KS
    When P1 attaches BCBS-NC and BCBS-KS
    Then the preview shows Group 1 × NC and Group 2 × NC for BCBS-NC
    And Group 2 × KS for BCBS-KS
    And unchecking Group 1 × NC saves only the other two targets
```

### F1.5.3 — Archive and re-attach

- **Description:** Removing an attachment (payer-level or a single group/state
  target) archives it: hidden from new case generation, history preserved.
  Re-attaching restores or recreates targets in one action — supporting the
  deny-then-reapply cycle.
- **Persona:** P1.
- **Benefit hypothesis:** Payer relationships flip back and forth (denied now,
  invited to reapply later); archive/restore keeps history without data loss
  or re-entry.
- **Acceptance criteria:**
  - Archiving sets `status = archived`; the target disappears from active
    lists and from case-generation input.
  - Existing cases/contracts referencing the payer are untouched.
  - Archived targets are visible in an "archived" view and restorable in one
    click.
  - Re-attaching a fully archived payer re-runs the expansion (F1.5.2) with
    previously archived rows pre-unchecked for review.
- **Test/data scenario(s):** TS-42.

```gherkin
Feature: Archive keeps history and supports reapply
  Scenario: Payer denies, then reopens six months later
    Given Group 1 × Cigna-NC × NC is an active target with generated cases
    When P1 archives the Cigna attachment
    Then no new cases can be generated against it and existing cases are unchanged
    When P1 re-attaches Cigna after the payer reopens
    Then the expansion preview appears and restoring the target makes it active again
```

### F1.5.4 — Prerequisite awareness deferred marker

- **Description:** Payers with `prerequisite_payer_id` (E1.6) show an
  informational note in the picker ("requires X"), but attachment is never
  warned or blocked on prerequisites — that is case-generation-time logic
  (R4, per PM decision Q8).
- **Persona:** P1.
- **Benefit hypothesis:** Keeps attachment friction-free while planting the
  data hook R4 will enforce.
- **Acceptance criteria:**
  - Informational prerequisite note renders when metadata exists; no
    validation attaches to it.
- **Test/data scenario(s):** TS-41.

/ `useAdmin.ts` / `useOrgPayerAssignments.ts`, `src/lib/stateCode.ts` /
`dbErrors.ts`, `src/types/index.ts`, `seed-universe.md`, the resolved

- **TE-1 — New table `payer_network_targets` (one additive migration,
  repo + hosted).** Modeled on `provider_facility_assignments` (the
  register's template for org-scoped work joins) and its parent visibility
  layer `org_payer_assignments`. Sketch:

  ```sql
  CREATE TABLE IF NOT EXISTS public.payer_network_targets (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id uuid NOT NULL REFERENCES public.organizations (id)
      ON DELETE CASCADE,
    group_id uuid NOT NULL REFERENCES public.provider_groups (id),
    payer_id uuid NOT NULL REFERENCES public.payers (id),
    state text NOT NULL,
    status text NOT NULL DEFAULT 'active',
    created_at timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT payer_network_targets_group_payer_state_key
      UNIQUE (group_id, payer_id, state),
    CONSTRAINT payer_network_targets_state_format
      CHECK (state ~ '^[A-Z]{2}$'),
    CONSTRAINT payer_network_targets_status_check
      CHECK (status IN ('active', 'archived'))
  );
  CREATE INDEX IF NOT EXISTS idx_payer_network_targets_payer_id
    ON public.payer_network_targets (payer_id);
  CREATE INDEX IF NOT EXISTS idx_payer_network_targets_org_id
    ON public.payer_network_targets (org_id);
  ```

  `group_id` needs no single-column index: it is the leading column of the
  unique constraint — the exact reasoning `20260710140000` used to exclude
  `state_licenses.provider_id`. The `state` CHECK is born-valid on a new
  table, so no `NOT VALID`/`VALIDATE` dance; `normalizeStateCode` still runs
  at the write boundary (TE-5). Deliberately **no**
  `archived_at`/`archived_by` columns: transition history (who
  archived/restored, when) lives in `audit_log` per the register's ledger
  rule — do not grow lifecycle columns here. RLS is org-scoped, modeled on
  the `provider_facility_assignments` policies (member SELECT; writer
  INSERT/UPDATE, `USING` + `WITH CHECK` requiring org membership AND
  `user_role(org_id) IN ('specialist', 'admin')`), with **no DELETE policy
  and no DELETE grant** — archive-not-delete (F1.5.3) becomes a DB-level
  invariant, not a UI courtesy:

  ```sql
  ALTER TABLE public.payer_network_targets ENABLE ROW LEVEL SECURITY;
  GRANT SELECT, INSERT, UPDATE
    ON public.payer_network_targets TO authenticated;
  ```

  `anon` gets nothing (assert with the E0.7 audit pattern —
  `scripts/verify-stage0-rls-grants.sql` is the model). Guard every statement
  (`IF NOT EXISTS`, `DROP POLICY IF EXISTS`) so a repo-only rebuild passes.
  Same PR: `docs/data-model/table-register.md` row (layer `work`, status
  `core` — it is E2.x case generation's row source) and a
  `src/integrations/supabase/types.ts` regen via MCP (hand-add if regen
  flakes, per the stage-0 precedent; normalize on next regen). NOTE: the
  writer-role choice here follows the assignments template, not
  `org_payer_assignments`' admin-only write, which the Dependencies line
  names — see redline 1 / PM question 1 before building.

- **TE-2 — Grain reconciliation: a target is INTENT, a contract is the
  AGREEMENT.** `payer_network_targets` lands on the exact
  `group × payer × state` triple `contracts` already keys
  (`contracts_group_id_payer_id_state_key`, baseline line 784, hardened by
  E0.10 NOT-NULL CHECKs + `contracts_state_format`). The two tables must
  stay disjoint in meaning: a target says "we intend to pursue this
  network"; the contract is the entity-level agreement that may later
  materialize. Therefore: (a) **no contracting status, dates, or outcome
  fields ever land on targets** — contracting status lives on `contracts`
  only (AGENTS.md database rule); `payer_network_targets.status` is a
  lifecycle enum (`active|archived`), not a workflow, and must never grow
  values like `denied`/`in_network` — deny-then-reopen is modeled as
  archive/re-attach (F1.5.3) with the real status on the contract/case;
  (b) **no FK between targets and contracts** — when both exist for a
  triple they correlate by value join on the triple, the same idiom the
  register documents for cases↔contracts; (c) attaching never creates a
  `contracts` or `credential_cases` row — E2.x reads ACTIVE targets and
  generates cases at the 4-part key (provider × group × payer × state);
  the AGENTS.md case-key amendment belongs to the generation epic (E2.3)
  per E1.3 §5 TE-9, not here.

- **TE-3 — Archive/re-attach is an in-place status flip (the unique key
  forces it).** `UNIQUE (group_id, payer_id, state)` spans both statuses,
  so a triple has exactly ONE row forever: archive =
  `UPDATE status = 'archived'`; restore/re-attach =
  `UPDATE status = 'active'`. The F1.5.2 save therefore does per-row logic
  in the service: INSERT triples with no existing row; flip archived rows
  the operator re-checked; never a second row, never a DELETE (no grant
  exists, TE-1). That is what makes TS-42's "history preserved" real at the
  DB: the row and its audit trail survive the deny→reapply cycle, and
  existing cases/contracts are untouched because nothing references targets
  by FK. Payer-level archive (F1.5.3) archives every active target row for
  that payer in the org — audit each row (or one bulk update with one audit
  row naming the payer; pick one and test it). Re-attach re-runs the
  expansion with previously archived rows **pre-unchecked** for review;
  checking one restores it.

- **TE-4 — Pure expansion module (`src/lib/payerNetworkExpansion.ts` +
  test).** The epic requires the expansion preview be a pure, testable
  module. Inputs: the org's active groups, its facilities (`group_id`,
  `state` — filter out `is_active = false` and NULL-state rows;
  `facilities.state` is nullable per the baseline + E0.10 NULL-allowing
  format check), the payer's operating `states[]` (E1.6 metadata), and the
  org's existing target rows (both statuses). Outputs:
  - `expandAttachment(...)` — candidate `group × state` rows, each carrying
    the reason (facility count in that state): a group is a candidate in a
    state where it has ≥1 facility AND the payer operates there (F1.5.2). A
    payer sharing no state with any group yields an empty list (the UI
    renders the explanatory message). A payer with NULL/empty `states[]`
    metadata is treated as operating nowhere (conservative default —
    PM question 4).
  - `diffExpansion(candidates, existingTargets)` — splits candidates into
    `new` (no row), `active` (already attached), and `archived`
    (pre-unchecked on re-attach). The same diff drives the "new expansion
    available" review affordance when a facility later appears in a new
    state — derived at render time, never a silent insert (F1.5.2 AC).
    Deliberately unchecked rows have no persisted identity and WILL
    resurface here (PM question 3).

  Unit-test the truth table: the two-group TS-41 shape with an exception,
  empty expansion, archived pre-uncheck, and the new-facility delta. E1.8's
  readiness matrix consumes ACTIVE targets via the service read (TE-5), not
  this module.

- **TE-5 — Layering: one new service + hooks; the picker reuses the
  existing catalog reads.** New `src/services/payerNetworkTargets.ts` (the
  only new Supabase caller): `listTargets()` (org-scoped, both statuses —
  callers filter), `attachTargets(rows)` (insert/flip per TE-3),
  `archiveTarget(id)` / `restoreTarget(id)` / `archivePayerTargets(payerId)`.
  Every function scopes by `requireActiveOrg()` and sets `org_id` on insert;
  every mutation runs `normalizeStateCode` before writing `state`, wraps
  errors in `translateDbError`, and writes `audit_log` via `writeAudit`. Add
  the new unique-key fragment to `src/lib/dbErrors.ts` `UNIQUE_MESSAGES`
  (`payer_network_targets_group_payer_state_key` → "This payer is already
  targeted for this group and state."). The **attach picker** (F1.5.1)
  needs no new read path: join `useOrgPayerAssignments` (`listAssignments`)
  with `usePayers` (`listPayers` already returns own-org + assignment-gated
  global rows) and keep only payers that have an assignment row — that IS
  the Minted-curated shortlist; org-scoped legacy payer rows without an
  assignment are excluded by construction (TS-41), and payers with an
  active target drop out of the picker. Hooks in a new
  `src/hooks/usePayerNetworkTargets.ts` behind a
  `queryKeys.payerNetworkTargets(orgId)` entry (org-scoped,
  `src/hooks/queryKeys.ts`); mutations invalidate by that key prefix.

- **TE-6 — E1.6 dependency boundary (R2 merges before R3 builds).**

- **TE-9 — Security posture and the authoritative table trace.** No anon

- **TE-10 — Verification gates.** Unit-test the expansion truth table and

- **Likely tech debt to contain.**

    `org_id` (the same property `provider_facility_assignments` and

    hardening belongs to a future E0.10-style integrity pass, not here.

  - `Payer.orgId: string` must become `string | null` when global rows

  - Unchecked-exception resurfacing (TE-4) is accepted-by-default pending
    PM question 3; if the PM wants persistent exceptions, that is an AC

   requires every epic to list tables read/written, and the trace must
   include `audit_log` under writes (the service layer audits every
   mutation — the standing E1.1 review correction). TE-9 records the
   authoritative trace; the author should fold it into Dependencies.
3. **should-fix** — Cross-epic ownership gap: Out of Scope points the
   shortlist-curation UI at "E1.6's `org_payer_assignments` config surface in
   group settings", but E1.6 (already reviewed) contains no such feature —
