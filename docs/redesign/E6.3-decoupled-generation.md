# E6.3 — Decoupled Generation: One Door, Visible Buffer, Full Accounting

## Purpose and Context

Today parts of case creation happen as side effects of onboarding (starter
cases auto-spawn on provider create; the launch dialog is a second creation
UI), the deliberate batch path is invisible until someone remembers the URL,
and unchecking a preview row forces an exclusion reason even for ordinary
batching. Per decision record decision 4 and the generation-grid screen mock,
this epic makes generation THE single door cases come through: onboarding
records reality and creates zero cases; candidates accumulate in a visible
buffer; a human confirms; and the preview is a full accounting where every
provider × target lands in exactly one bucket that always sums. The trust
invariant is the product.

## Personas Empowered

- P1 Credentialing Manager — decides when work is created, in batch, with
  the full picture.
- P2 Credentialing Coordinator / Specialist — receives only deliberately
  created cases; the queue never carries side-effect noise.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md).
- Implementation dependencies (flagged): the existing generation machinery
  (preview derivation, per-row transactional RPC, run + run-row ledgers,
  exclusions store, SOP resolution + version stamping) is REUSED — this epic
  re-homes, re-triggers, and re-buckets it; it does not build a second
  engine. The candidate math gains the enrollment-facts subtraction (E6.2).
  Retiring starter cases removes the auto-attach path on provider create.

## Features

### F6.3.1 — The candidate buffer, always visible

- **Description:** For each provider on the group: candidates = group's
  payer targets − enrollment facts − existing cases − standing exclusions.
  Computed live, stored nowhere. The group's Payer Network board (E6.2)
  shows the count with its most recent cause and the Review & generate
  action; a provider's record (E6.4) shows their own slice ("7 candidates
  awaiting — review & generate for Chen"). Onboarding a provider creates
  ZERO cases.
- **User story:** As P1, hiring someone produces a visible, counted "work
  is waiting" state — never silent latency and never surprise cases.
- **Persona:** P1.
- **Benefit hypothesis:** Closes the discovery gap (nothing tells you to
  generate today) without automating creation; timing stays an operations
  choice.
- **Acceptance criteria:**
  - The buffer count updates on every contributing change (hire, group
    join, facility assignment, attach, fact expiry, exclusion restore) with
    no stored buffer state.
  - Provider onboarding (manual or CSV) never writes a case.
- **Test/data scenario(s):** TS-111, TS-113.

### F6.3.2 — The preview grid: pivotable, evidence-carrying

- **Description:** The full-screen preview launched from the board (or a
  payer row, or a provider record — same screen, pre-filtered). Grouped
  **by provider** or **by payer** (pivot chips; entry point picks the
  default), group headers carry check-alls; each row = one provider × payer
  × state candidate wearing its evidence: readiness chips (warn, never
  block), the SOP badge (payer SOP vN / generic fallback, flagged), and
  grayed non-selectable rows for already-enrolled and existing cases with
  the reason shown.
- **User stories:**
  - As P1 after the day-50 hire, I enter by provider and see Dr. Chen ×
    7 targets grouped under her name with a check-all.
  - As P1 after attaching a NEW payer to a 12-provider group, I enter from
    that payer's board row and see the same grid grouped by payer —
    12 candidates under one header.
  - As P1 scanning the grid, every row wears its evidence: readiness chips
    (W-9 missing — still generatable), the SOP badge (Anthem NC SOP v3 vs
    "generic — no SOP yet"), and grayed rows explaining themselves
    ("already enrolled under BEST PT Group").
  - As P2 (either actor — the gate is a capability, not a person), I can
    run the same confirm; nothing about generation queues behind one
    individual.
- **Persona:** P1, P2.
- **Benefit hypothesis:** The grid scales from 1×7 to 10×7 without losing
  comprehension, because the grouping matches the triggering event.
- **Acceptance criteria:**
  - Both pivots render the same underlying rows; check-alls operate per
    group header; selection grain is the row.
  - A payer with no SOP shows the generic-fallback flag on its rows and in
    the confirm summary — generatable, never blocked.
  - Readiness gaps render as chips and follow the created case as work.
- **Test/data scenario(s):** TS-111.

### F6.3.3 — Skip-for-now vs Exclude: two intents

- **Description:** Unchecking a row is **Skip for now**: no reason, no
  ceremony; the candidate stays in the buffer. **Exclude…** is the
  deliberate opt-out: reason from the fixed list (other requires note),
  persists across runs, leaves the buffer, renders on the board's payer row,
  restorable in one click. Exclusions remain admin-scoped and void-never-
  delete per the existing model.
- **User story:** As P1, "not in this batch" and "we're not pursuing this"
  are different decisions and the system treats them differently.
- **Persona:** P1.
- **Benefit hypothesis:** Removes the forced-reason friction that punished
  ordinary batching, while keeping deliberate exclusions loud and
  accounted for.
- **Acceptance criteria:**
  - A skipped row reappears checked on the next preview; the buffer count
    includes it.
  - An excluded row leaves the buffer, shows reason + author on the board,
    restores in one click, and reappears as a candidate on restore.
- **Test/data scenario(s):** TS-111.

### F6.3.4 — Confirm: reconciliation, creation, landing

- **Description:** The confirm bar always shows the reconciliation ("Create
  4 · 1 excluded · 2 enrolled — 7 of 7 targets accounted for") plus the
  generic-SOP warning line when applicable. Confirm runs the existing
  per-row transactional creation: cases born `Not Started` (E6.0), SOP
  resolved and version-stamped per payer, one immutable run + run-row
  ledger, concurrent duplicates skip safely, partial failure reported
  honestly. Landing: the Cases queue with the new cases ranked; the board's
  rows flip In Progress; run history remains reachable from the board.
- **User story:** As P1, I always know exactly what a confirm will create
  before I click, and exactly what it created after.
- **Persona:** P1.
- **Benefit hypothesis:** The sum-row invariant is the trust mechanism —
  a missing expected case is never gone, it is in another bucket with a
  named reason.
- **Acceptance criteria:**
  - Buckets (selected + skipped + excluded + enrolled + existing) sum to
    the target × provider count on every render; e2e pins the invariant.
  - Created cases carry SOP template id + version + tier stamps; the run
    ledger records every candidate's disposition including skips.
  - Full success lands on Cases filtered to the run; partial failure stays
    on the preview naming the failed rows.
- **Test/data scenario(s):** TS-111.

### F6.3.5 — One door: retire the side-effect creators

- **Description:** Starter cases (auto-spawn on provider create) are
  retired outright. The launch-dialog case creation is retired; a location
  context deep-links into the preview filtered to that facility's providers
  instead. The manual one-off case modal remains as the escape hatch for
  genuinely untargeted oddballs (duplicate pre-check + DB constraint
  backstop unchanged). Reapply stays a case-detail action (continuation,
  not creation).
- **User story:** As P1, "how do cases get created" has exactly one answer
  plus one documented exception.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Every case's existence is traceable to a human
  confirm; targets become the honest backbone of all casework.
- **Acceptance criteria:**
  - No code path creates a case on provider create; the starter flag UI is
    removed (data column may remain dormant per additive rules).
  - The launch-context entry opens the shared preview pre-filtered — no
    second creation UI remains.
  - A code-level test pins "no case writes outside the generation confirm
    path + manual modal + reapply append."
- **Test/data scenario(s):** TS-111.

## Dependencies

- E6.0 (case birth status), E6.2 (board home, buffer surface, enrollment
  facts, attach). Build after both.
- Existing machinery reused: preview derivation, `create_case_with_tasks`
  RPC path, run + run-row ledgers, exclusions store, SOP resolution/stamping
  (`pickTemplate`), readiness evaluation.
- Retirement of starter cases touches the provider-create flow; the launch
  dialog retirement follows E6.1's Launches-page retirement.

## Out of Scope / Non-Goals

- No auto-generation of any kind; no scheduling.
- No changes to SOP resolution tiers or stamping semantics.
- No per-analyst routing of created cases.
- Recredentialing cycles (future stage).
