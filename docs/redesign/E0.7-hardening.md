# E0.7 — Stage 0 Hardening — Public Surfaces, RLS Audit & Regression Coverage

## Purpose and Context

Stage 0 (E0.0–E0.6) shipped the redesigned shell, the org/party model, and —
for the first time — three **public, unauthenticated surfaces** that cross the
app's trust boundary: `/capture/:token` (E0.5), `/contact` (E0.5), and
`/share/:token` (E0.6), backed by `anon` SECURITY DEFINER RPCs. E0.7 hardens
what shipped before the PM promotes `redesign` → `main`: abuse resistance on
the public RPCs, a systematic RLS/GRANT audit of every table added in Stage 0,
type-system hygiene (hand-added `types.ts` entries), and regression e2e
coverage for gaps found during Stage 0 verification (e.g. the E0.6 TE-8
add-organization entry shipped with no spec). No new user-facing features; no
schema restructuring — additive migrations only, per AGENTS.md.

## Personas Empowered

- P1 Credentialing Manager (Sowmya Seed) — trusts that links she issues can't
  be brute-forced or replayed, and that revocation actually locks recipients out.
- P5 Practice Owner / P6 Office Manager — capture/share links keep working
  exactly as promised; no behavior change.
- (Indirectly) the business — the public surfaces cannot be used to enumerate
  tokens, spam leads, or probe org data.

## Component & Data Constraints

- Must be built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and [README.md](./README.md).
  E0.7 adds NO new UI surfaces; only existing error/lockdown states may be touched.
- Example/demo/test data must use scenario orgs and personas from
  [seed-universe.md](./seed-universe.md).
- All migrations are additive (AGENTS.md); no renames, no policy weakening.
- No new dependencies. Rate limiting must be implementable inside Postgres
  (the stack has no server middleware tier in Stage 0).

## Features

### F0.7.1 — Public RPC abuse resistance (rate limiting + uniform responses)

- **Description:** The four `anon`-callable RPCs (`validate_capture_token`,
  `submit_capture`, `submit_inbound_lead`, `validate_report_share`) gain
  DB-side attempt throttling and uniform failure responses so tokens cannot be
  enumerated and the lead queue cannot be spammed.
- **Persona:** P1 (protected); anonymous abuser (defeated).
- **Benefit hypothesis:** A 64-hex-char token is unguessable in theory, but
  unmetered validation endpoints invite scripted probing and lead spam;
  throttling closes the practical attack while keeping legitimate one-click
  usage untouched.
- **Acceptance criteria:**
  - Repeated failed validations from the same source are throttled after a
    threshold (BD-1 sets mechanism + numbers); a throttled caller receives the
    SAME generic "invalid or expired" response as a wrong token (no oracle).
  - Invalid, revoked, expired, and throttled outcomes are indistinguishable to
    an anonymous caller (existing lockdown pages render for all of them).
  - `submit_inbound_lead` enforces a per-source submission cap in addition to
    the existing honeypot; over-cap submissions are silently accepted-and-
    discarded or generically rejected (BD-1), never an error revealing the cap.
  - Legitimate flows (TS-7, TS-13, TS-14, TS-15) still pass unchanged.
  - No raw token is ever written to any log, table, or error message (audit of
    existing RPC bodies included).
- **Test/data scenario(s):** TS-16 (abuse probe), TS-7/TS-13/TS-14/TS-15
  (regression).

```gherkin
Feature: Public token endpoints resist enumeration
  Scenario: Scripted probing of capture tokens is throttled without an oracle
    Given an anonymous client has submitted 20 invalid tokens to validate_capture_token
    When it submits a 21st token, valid or not
    Then the response is the same generic invalid/expired result
    And a subsequently issued legitimate link for Lone Star Rehab Group still validates once the window passes
```

### F0.7.2 — Stage 0 RLS & GRANT audit (verified, not assumed)

- **Description:** A systematic, scripted audit of every table added in Stage 0
  (`parties`, `party_role_types`, `party_role_assignments`,
  `party_capture_links`, `inbound_leads`, `report_shares`) proving RLS is
  enabled, policies match the documented access model, GRANTs are explicit and
  minimal (AGENTS.md: every public table needs explicit GRANTs alongside RLS),
  and the `anon` role can reach ONLY the four intended RPCs.
- **Persona:** P1 and every org member (their data stays scoped).
- **Benefit hypothesis:** The access model was built piecewise across five
  epics; one adversarial pass catches any gap before promotion — cheaper now
  than as an incident later.
- **Acceptance criteria:**
  - An audit script (repo, re-runnable) asserts per table: RLS enabled,
    expected policy set, expected GRANTs, append-only where documented.
  - `anon` has EXECUTE on exactly the four public RPCs and nothing else; the
    SECURITY DEFINER helper functions from E0.2 remain client-revoked.
  - Cross-org checks: a member of org A cannot read org B's capture links,
    leads conversions, or shares via any browser path (TS-11 fixtures).
  - Findings are fixed by additive migration in the same PR, or explicitly
    recorded as accepted with rationale in this epic's Devin section.
- **Test/data scenario(s):** TS-9–TS-11 (party model), TS-16.

### F0.7.3 — Type-system & generated-artifact hygiene

- **Description:** Regenerate `src/integrations/supabase/types.ts` from the
  hosted schema so the hand-added `party_capture_links`, `inbound_leads`, and
  `report_shares` entries (added manually when MCP regen flaked in E0.5/E0.6)
  are normalized, and eliminate any drift between repo migrations and hosted DB.
- **Persona:** Developer agents (Claude Code/Devin) — indirect user benefit via
  fewer type-mismatch bugs.
- **Benefit hypothesis:** Hand-maintained generated files silently drift; one
  regen now prevents a class of future bugs.
- **Acceptance criteria:**
  - `types.ts` is regenerated (not hand-edited); `npx tsc --noEmit` stays clean.
  - A migration-vs-hosted diff shows zero drift, or drift is resolved by
    additive migration.
- **Test/data scenario(s):** gates only (tsc/lint/tests) — no seed scenario.

### F0.7.4 — Regression e2e coverage for Stage 0 gaps

- **Description:** Close the known Playwright coverage gaps: the E0.6 TE-8
  "Add organization" switcher entry (shipped with manual verification only),
  the E0.1 duplicate-name hard block, the E0.2/E0.3 only-sales-rep removal
  guard, and the E0.4 landing-resolver matrix (last-active / most-recent-live /
  first-run / all-inactive), all via the existing mock harness.
- **Persona:** P1 (regressions caught before they reach her).
- **Benefit hypothesis:** These flows are exactly the ones that broke or nearly
  broke during Stage 0 (the add-org entry point regression was user-reported);
  encoding them keeps them from regressing again.
- **Acceptance criteria:**
  - New specs under `e2e/` cover: switcher → Add organization → create → org
    switch (TS-4 fixtures); duplicate-name rejection (TS-6, exact
    normalized-name collision); only-sales-rep removal block (TS-9); landing
    resolver states (TS-0, TS-3, TS-12).
  - All specs run in the existing `Playwright smoke` CI job with no new infra.
- **Test/data scenario(s):** TS-0, TS-3, TS-4, TS-6, TS-9, TS-12.

### F0.7.5 — Public-surface UX lockdown consistency

- **Description:** One pass over the public routes (`/capture/:token`,
  `/contact`, `/share/:token`) verifying every terminal state (used, expired,
  revoked, invalid, throttled, submitted) renders the shared lockdown/empty
  pattern — no dead ends (E0.4's locked rule), no raw error text, pending/
  disabled states on all submit buttons.
- **Persona:** P5/P6 recipients and inbound strangers.
- **Benefit hypothesis:** These are the only pages outsiders ever see; a
  broken or leaking terminal state costs disproportionate trust.
- **Acceptance criteria:**
  - Every terminal state on the three routes renders a designed state with a
    path forward (matching existing lockdown components); verified in the e2e
    specs where mockable.
  - No server error shape (Postgres/PostgREST message) is ever rendered
    verbatim on a public route.
- **Test/data scenario(s):** TS-13, TS-14, TS-15, TS-16.
