# E6.0 — Unified Case Status: One Evidence-Based List

## Purpose and Context

A single case today carries two parallel state machines (the org-configurable
9-status credentialing track and the fixed 9-state payer pipeline), while
contracts carry a 6-status contracting track and facilities a 7-status
location track — ~31 statuses across four lists to answer one question:
*where does this application stand?* Per the PM decision record
(`DECISION-RECORD-2026-07-19-simplification.md`, decision 1), this epic
collapses them into ONE fixed, canonical case-status list, makes every
transition evidence-based (system-set when witnessed, human-set when
learned), and derives everything above case level. It is the foundation epic
of the simplification wave: every other E6.x epic renders these statuses.

## Personas Empowered

- P1 Credentialing Manager — one status to read, trust, and report on.
- P2 Credentialing Coordinator / Specialist — one status to set, with the
  evidence attached in the same gesture.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md). Status pills render via the existing shared
  `StatusPill` tone map; no new pill primitives.
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md) (Dillon Sports Medicine carries the
  richest case fixtures).
- Implementation dependency (flagged, not assumed): a data migration mapping
  every live case's `credentialing_status_id` + `payer_pipeline_state` pair
  to one canonical status, and contracting/location status data to their
  replacement fields. Live customer data (e.g. BEST Physical Therapy LLC)
  must map, never wipe. Append-only ledgers (`status_history`,
  `payer_pipeline_history`, `touches`, `audit_log`) are retained untouched.

## Features

### F6.0.1 — The canonical eight-status list

- **Description:** Every credential case carries exactly ONE status from the
  fixed list: `Not Started → In Progress → Submitted → In Review →
  Action Required → Approved | Denied | Not Pursuing`. The list is
  code-owned and canonical — no per-org configuration, labels, or colors.
  The payer-pipeline UI (badge, transition menu, history panel as a separate
  machine), the contracting status track, and the location status track are
  retired as user-facing state machines.
- **User stories:**
  - As P1, I want one status per case so that every screen, report, and
    conversation uses the same words for where an application stands.
  - As P1 reporting to a practice owner, I want the status I read on the
    case list to be the same value the denial report and the group board
    derive from, so I never reconcile two machines by hand.
  - As P1 with live customer data (e.g. BEST Physical Therapy), I want
    every existing case to arrive on the new list via a documented mapping
    — with its old history still readable — so the migration costs me
    nothing.
  - As P2, when the internal track and the payer pipeline used to disagree
    ("Submitted" vs "In Review"), I want that entire class of confusion to
    be structurally impossible.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Removes the dual-machine ambiguity ("internal says
  Submitted, pipeline says In Review — which is true?") that made status
  unreliable for reporting and queue ranking.
- **Acceptance criteria:**
  - A case exposes exactly one status; the eight values are the closed set.
  - Case list, case detail, provider record, group Payer Network board, and
    reports all render the same value from the same field.
  - The Admin › Statuses configuration page is retired (route redirects; no
    per-org status CRUD anywhere).
  - Contract execution/effective dates become plain fields on the case (set
    at Approved); no contracting status machine remains user-facing.
  - Location/go-live remains a facility date only; no location status
    machine remains user-facing.
  - Migration: every existing case's (credentialing status, pipeline state)
    pair maps deterministically to one canonical status via a documented
    mapping table; zero cases lose history (old ledgers retained read-only).
- **Test/data scenario(s):** TS-104.

### F6.0.2 — Evidence-based transitions: auto vs human

- **Description:** Statuses move for exactly two kinds of reasons. AUTO
  (the action is the proof): case creation → Not Started; first recorded
  work on the case (task completion, touch, or fill event) → In Progress;
  an extension-logged submission touch → Submitted. HUMAN (only a person
  can know): Submitted (for fax/mail/phone SOPs), In Review, Action
  Required (and back to In Review on response), Approved, Denied,
  Not Pursuing. Human transitions are performed from the case header's
  status control or via the Add-touch prompt (F6.0.3).
- **User stories:**
  - As P2, I never have to remember to flip a status the system already
    witnessed: creating a case, doing its first task, or submitting through
    the extension each move the status by themselves.
  - As P2 working a fax-based SOP (e.g. NC Medicaid), I want the system to
    NEVER presume my fax went out — I log the touch and accept the
    Submitted prompt, because I am the evidence.
  - As P2 opening an approval letter, I want the Approved dialog to demand
    the effective date and the payer's ID by the payer's own name for it
    ("Provider ID" for Anthem, "PTAN" for Medicare), so the terminal facts
    are captured at the moment I have the letter in hand.
  - As P2 recording a denial (e.g. Cigna, panel closed), I want the reason
    to be required from the fixed list, so the denial is reportable the
    moment it exists.
  - As P2 when Cigna's panel reopens, I want Reapply to return the SAME
    case to In Progress with a fresh task cycle — the prior denial intact
    underneath — never a second case for the same combination.
- **Persona:** P2.
- **Benefit hypothesis:** Statuses stay current without ceremony; the
  system only asserts what it observed, so trust in AUTO values is total.
- **Acceptance criteria:**
  - Creation, first-activity, and extension-submission transitions occur
    with zero user action and are attributed "system" in history.
  - A manual fax/mail submission is never auto-flipped; the Add-touch flow
    offers the bump instead (F6.0.3).
  - The Approved dialog REQUIRES an effective date and the payer's provider
    ID, labeled with the payer's own term from the catalog (e.g. Anthem
    "Provider ID", Medicare "PTAN").
  - The Denied dialog REQUIRES a reason from the fixed word-list; Not
    Pursuing requires a note.
  - Reapply on a Denied case returns it to In Progress and appends a new
    task cycle to the SAME case; prior cycle and denial stay visible.
- **Test/data scenario(s):** TS-104, TS-105.

### F6.0.3 — Add touch as the status evidence carrier

- **Description:** When a logged touch is itself the evidence of a status
  change ("called Anthem — application in review"), the Add-touch dialog
  offers the corresponding status bump in the same gesture; accepting
  records touch + transition together, with the touch linked as the
  transition's evidence in history.
- **User story:** As P2, logging what happened and updating where the case
  stands is one action, not two screens.
- **Persona:** P2.
- **Benefit hypothesis:** The touch log and the status can never drift
  apart, because the same gesture writes both.
- **Acceptance criteria:**
  - Add touch offers a status suggestion only when the touch type/outcome
    implies one; declining the suggestion logs the touch alone.
  - Status history entries carry a reference to the evidencing touch when
    one exists.
- **Test/data scenario(s):** TS-105.

### F6.0.4 — Corrections, append-only

- **Description:** An admin can correct a status backward (mis-click, wrong
  letter); corrections append to history with actor + note — never rewrite.
  `status_history`, `touches`, and `audit_log` remain append-only.
- **Persona:** P1.
- **Benefit hypothesis:** Mistakes are cheap to fix and impossible to hide.
- **Acceptance criteria:**
  - Backward transitions are admin-only and require a note.
  - History shows the correction as a new entry; the original stands.
- **Test/data scenario(s):** TS-105.

### F6.0.5 — Derived rollups (never set by anyone)

- **Description:** Everything above case level is math over case statuses
  and enrollment facts: payer fulfillment per group × payer (Targeted → In
  Progress → Active; most-advanced-case-wins; Active = ≥1 Approved case OR
  enrollment fact — consumed by E6.2's board), provider progress ("x of y
  approved" — consumed by E6.4), and the denial rollup (Denied + reason,
  provider-first — consumed by E6.6's report).
- **Persona:** P1.
- **Benefit hypothesis:** Zero hand-maintained summary state; the rollups
  are always exactly as current as the statuses underneath them.
- **Acceptance criteria:**
  - No UI exists anywhere to set a payer-level or provider-level status.
  - Setting a case Approved updates the group's payer row to Active in the
    same render cycle; a denial appears in the provider's history and the
    denial report immediately.
- **Test/data scenario(s):** TS-104, TS-115.

## Dependencies

- Migration: one additive status field + deterministic mapping from
  (credentialing_status_id × payer_pipeline_state) pairs; contracting →
  case-field mapping; documented in the implementation PR with a pre-drop
  inventory per AGENTS.md schema policy. Old ledgers retained.
- The payer's ID label read from the payer catalog (exists — `payers`
  resolution-ID columns / org settings chain).
- E6.2 (board), E6.4 (provider rollup), E6.6 (denial report) consume
  F6.0.5's derivations; E6.0 ships them as pure functions.
- The extension's submission-touch write path (exists) is the AUTO
  Submitted trigger; no extension change.

## Out of Scope / Non-Goals

- No per-org status configuration of any kind.
- No changes to the extension or its wire contracts.
- No SLA/timer mechanics on statuses.
- Per-analyst case assignment (future idea; not in this wave).
