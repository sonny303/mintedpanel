# E1.7b — SOP-as-Data: Versioned SOP Authoring (Model A)

## Purpose and Context

The E1.7a spike concluded and the PM signed off (2026-07-12, `[e1.7a]`):
**Model A** — every SOP publish creates an immutable version row; in-flight
cases keep the version their tasks were generated from; newly generated cases
pick up the latest. This epic builds that machinery plus the authoring-shape
extension, grounded against the two real business SOPs
(`E1.7b-sop-worked-examples.md`): the Kansas per-payer SOP and the Fitness
Physio general enrollment checklist. An authoring surface that cannot
represent those two documents is wrong.

It also delivers the **generic fallback SOP** required by the `[r4]` Q4
decision: a global (org_id NULL) general-enrollment SOP, modeled on worked
example 2, that E2.2 resolves when no payer+state SOP exists.

## Personas Empowered

- **P1 Credentialing Manager** — authors/edits SOPs; trusts that edits never
  disturb in-flight cases.
- **P2 Credentialing Specialist** — works tasks stamped from a known SOP
  version; can see "which version produced this task."

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: the E1.7a §4 migration sketch is the contract —
  additive `sop_template_versions` (immutable, no org_id, RLS through the
  parent, writes only via the `publish_sop_template_version` SECURITY DEFINER
  RPC with optimistic concurrency), `sop_templates.current_version`,
  `tasks.sop_template_id`/`tasks.sop_version` (nullable, both-null-or-both-
  present CHECK, composite FK), version-1 backfill, table-register row.
- Implementation dependency (protected-file authorization to be confirmed in
  §5): additive widening of `SOPStep`/`SOPTaskDefinition`/`SOPStepType` in
  `src/types/index.ts` (`fax | phone | mail` step types;
  `expectedTurnaroundDays?`, `followUpEveryDays?`, `requiredArtifacts?`) AND
  the matching additive carry-through edit to `src/lib/sopResolver.ts` — they
  ship together or not at all (E1.7a §3 "scope honesty").
- Implementation dependency: reconcile the catalog-vs-resolver token naming
  gap (`get_sop_field_tokens()` vs `buildTokenMap`) with a test asserting
  every advertised catalog token resolves.
- Credentials must never appear in SOP bodies (worked-examples data-hygiene
  rule): authoring guidance text; steps reference shared logins by name only.

## Features

### F1.7b.1 — Publish creates an immutable version

- **Description:** The template wizard's save becomes **Publish**: one
  transaction inserts version N+1, updates the head jsonb, bumps
  `current_version` (optimistic-concurrency guarded), and writes the audit
  row. Version rows are immutable; rollback = republish old content as N+1.
- **Persona:** P1.
- **Benefit hypothesis:** Edits never silently overwrite; "what did the SOP
  say when this case was generated" is always answerable.
- **Acceptance criteria:**
  - Editing and publishing an SOP creates a new `sop_template_versions` row
    with an optional change note; the previous version row is untouched.
  - A concurrent publish loses with a friendly conflict error.
  - Existing readers (pickTemplate, resolver, Admin list) read the head
    unchanged — no behavior change for unversioned consumers.
  - Every pre-existing SOP has a backfilled version 1.
- **Test/data scenario(s):** TS-45.

```gherkin
Feature: Model A immutable versions
  Scenario: Humana KS SOP goes in-network
    Given the Humana KS SOP is at version 1 (out-of-network roster procedure)
    When P1 edits it to the in-network procedure and publishes
    Then version 2 exists and version 1 is unchanged
    And tasks previously stamped (humana-ks, 1) still show version 1 content
```

### F1.7b.2 — Version history and per-version view

- **Description:** The template surface shows the version history (number,
  date, publisher, change note) and renders any past version read-only.
- **Persona:** P1, P2.
- **Acceptance criteria:**
  - History list per template; selecting a version shows its full content
    read-only with a "current version N" marker.
  - A task stamped `(template, version)` can be traced to that exact content.
- **Test/data scenario(s):** TS-45.

### F1.7b.3 — Authoring-shape extension (grounded on the real SOPs)

- **Description:** Widen the step shape so both worked examples are fully
  representable: step types `fax | phone | mail` (in addition to
  `draft_email | online_form | pdf`), optional `expectedTurnaroundDays`,
  `followUpEveryDays`, `requiredArtifacts[]`; email templates with tokens and
  attachment checklists (`dataFields`) as today.
- **Persona:** P1.
- **Acceptance criteria:**
  - Both worked-example documents are fully representable as versioned SOPs
    with no lost information other than the redacted credential.
  - New optional fields survive resolution into `tasks.sop_content`
    (resolver carry-through, verbatim like `portalKey`).
  - All existing templates remain valid (fields optional, additive).
  - Known gaps stay logged as debt, not hacked: conditional steps, sub-state
    (KC-metro) scoping, group×payer relationship constants, SOP-to-SOP step
    references (v1: prose in `detail`).
- **Test/data scenario(s):** TS-46.

### F1.7b.4 — Generic fallback SOP (global)

- **Description:** Ship the general enrollment checklist (worked example 2,
  credential-free) as a **global fallback SOP** (`org_id IS NULL`, no payer
  match key) that E2.2 resolves when a case's payer+state has no SOP. Visible
  in the template list, labeled as the fallback.
- **Persona:** P1, P2.
- **Benefit hypothesis:** `[r4]` Q4 — no-SOP cases start with the generic
  checklist instead of an empty task list, swapped for the payer SOP as those
  get authored (new generations pick the payer SOP; in-flight keep fallback).
- **Acceptance criteria:**
  - Fallback SOP exists as seeded global data with a version 1.
  - `pickTemplate` order is unchanged for payer-matched SOPs; the fallback
    is selected only when no payer+state (or payer-generic) SOP matches.
- **Test/data scenario(s):** TS-47.

### TE-1 — Migration: one additive file, repo + hosted (the E1.7a §4 sketch, corrected)

The E1.7a §4 sketch is confirmed additive-only and is the contract:
`sop_template_versions` (no `org_id`; `UNIQUE (template_id, version)` doubles
as the composite-FK target), `sop_templates.current_version integer NOT NULL
DEFAULT 1`, `tasks.sop_template_id`/`tasks.sop_version` (nullable,
both-null-or-both-present CHECK, composite FK), version-1 backfill for every
existing row (INSERT-only; use the template's `updated_at` as the backfilled
`published_at`, `published_by NULL`). Corrections and completions:

- **Grants must be explicit** (AGENTS.md: every public table needs explicit
  GRANTs alongside RLS): `GRANT SELECT ON sop_template_versions TO
authenticated` with the parent-EXISTS SELECT policy; grant and policy
  **nothing else** to `authenticated` — INSERTs happen only inside the publish
  RPC / creation trigger (TE-4) / backfill, which is the immutability
  mechanism.
- Ship repo-first and apply the identical SQL to hosted via MCP
  `apply_migration` in the same session (`docs/migration-baseline.md` rule);
  regenerate `src/integrations/supabase/types.ts` via
  `generate_typescript_types` + prettier after the DDL; update `SCHEMA.md` and
  `docs/data-model/table-register.md` in the same PR — the register gains the
  `sop_template_versions` row and updated `sop_templates`/`tasks` rows (the
  E1.7a TE-5(a) obligation).
- The `tasks` columns ship here but are **written by E2.2, not this epic**
  (legacy and E1.7b-era tasks stay NULL/NULL; the CHECK keeps them valid).

### TE-2 — RLS correction: the fallback SOP is invisible under the shipped policy (gates F1.7b.4)

The shipped `sop_templates_select`
(`20260707060000_global_catalog_org_assignment.sql`) deliberately makes a
global SOP with `payer_id NULL` **visible to no org** ("safe default:
invisible, never leaked"). F1.7b.4's fallback row is exactly that shape
(`org_id IS NULL`, no payer match key), so as authored it can never appear in
any org's template list and `pickTemplate` can never select it from a browser
session. Enablement (all additive, in the TE-1 migration):

- Replace the SELECT policy with the same disjunction **plus a third
  disjunct** `(org_id IS NULL AND payer_id IS NULL)` — payerless global SOPs
  (the fallback) become visible to all authenticated org members. Template
  bodies carry tokens, never tenant data or PHI, so nothing tenant-scoped is
  exposed; PM question 1 below confirms the posture change explicitly.
- Seed **exactly one** fallback row inside the migration (fixed well-known
  UUID + `ON CONFLICT DO NOTHING`, so repo rebuilds and hosted both carry it):
  `org_id NULL`, `payer_id/state/specialty/group_id NULL`, content transcribed
  credential-free from worked example 2. The fixed UUID lives as a code
  constant; the list labels any `orgId === null && payerId === null` row with
  the "fallback" marker F1.7b.4 requires.
- `getTemplate` (`src/services/templates.ts`) filters `.eq("org_id", orgId)`
  and would return `null` for the fallback even once RLS allows it — additively
  widen the **read** path to the `.or(org_id.eq.<org>,org_id.is.null)` form
  `listTemplates` already uses, so the fallback (and any assigned global SOP)
  can be opened read-only and its version history viewed. Write paths stay
  own-org (RLS enforces; the wizard renders global rows read-only for org
  users).

### TE-3 — Publish privilege is ADMIN, not "writer"

`sop_templates` INSERT/UPDATE policies are **admin-only** today (baseline
lines 1042/1044: `user_role(org_id) = 'admin'`), and the Templates wizard is
admin-gated (specialists get the read-only wizard). The E1.7a §4 sketch's
"writer-membership check" would silently widen publish rights to specialists.
The `publish_sop_template_version` RPC must check **admin** membership on the
parent's org for browser callers (and reject browser callers outright for
global templates — service-role only), mirroring the existing write policies.
This section is the binding correction; the E1.7a doc itself is not edited.

### TE-4 — Version-1 invariant for templates created AFTER the migration

F1.7b.1 backfills version 1 for **pre-existing** SOPs only. Post-migration
creates — the wizard's create path (`createTemplate`), its **Duplicate**
action (`handleDuplicate` in `TemplateWizard.tsx`), CSV/service-role seeding —
would produce heads with `current_version = 1` and **no version-1 row**: the
`tasks` composite FK then rejects E2.2's `(template, 1)` stamp for any
never-republished template, and F1.7b.2's "trace any stamped task to exact
content" breaks. Enabler: an `AFTER INSERT` trigger on `sop_templates` that
inserts the version-1 row (copying `name`/`task_definitions`), making the
invariant "every head has a version row for its `current_version`" true by
construction for **every** insert path with zero service changes. (A
create-RPC is the rejected alternative — it would miss Duplicate and
service-role seeds unless every caller migrates.) The publish RPC then always
operates on an existing head; add the invariant to the unit gate (TE-12).

### TE-5 — Versions snapshot name + content; match-key edits stay head-level

Version rows carry `name` + `task_definitions` only (the §4 sketch). Match
keys (`payer_id`/`state`/`specialty`/`group_id`) are template **identity**,
not content: keep them editable through the existing audited `updateTemplate`
head UPDATE (unversioned), excluded from the publish RPC's signature. The
wizard's single Save therefore splits: content/name changes go through
**Publish** (the RPC, with change note + expected version); Basics-step
match-key changes go through the plain head update (no version bump). Redline
6 asks the author to state this in the epic body so "edits never silently
overwrite" is not over-claimed for match keys (they remain audit-trail-only,
exactly as today).

### TE-7 — Token-catalog reconciliation: direction is constrained by the wire contract

Catalog token names are a **live wire contract**: `portal_field_maps.token`
rows (including the 24 promoted global `bcbs_ks_enrollment` rows), saved
view-prefs values (`user_table_prefs`, e.g. `license.licenseNumber`), the
extension's field-map ↔ profile join, and `src/services/providerProfile.ts`
all speak the bare catalog form. Therefore **do not rename
`get_sop_field_tokens()` output** to the resolver's names. Reconcile the
other direction, inside the TE-6(b) authorized resolver edit:

- Additively extend `buildTokenMap` with catalog-name aliases for values the
  resolve context already holds — e.g. `license.licenseNumber` (alias of the
  existing `provider.licenseNumber` value) and `facility.street` /
  `facility.city` / `facility.state` / `facility.zip` alongside the joined
  `facility.address`. Existing names stay (SOP bodies in the wild use them).
- Constrain the SOP authoring **token picker** to advertise only
  resolver-resolvable tokens: the catalog's case-scoped families
  (`payers.*`/`msos.*`/`contracts.*`) cannot resolve at SOP-resolution time
  and must be excluded from `dataFields` authoring (they stay available to
  the extension's server-side profile resolution, which is a different
  consumer of the same catalog).
- The epic's required test is then concrete: a unit test pinning
  **picker-advertised set ⊆ `buildTokenMap` keys** (every advertised token
  resolves), not "all 132 catalog tokens resolve" — the latter would require
  case-scoped reads the client resolver does not have and E2.x does not need.

### TE-8 — Fallback-selection seam with E2.2 (and the immediate manual-flow effect)

**E1.7b owns the pure `pickTemplate` fallback tier** (not protected; additive
third tier: only when no payer+state template matches, return the seeded

acceptance criterion and TS-47 testable inside this epic. E2.2 consumes the
tier and adds stamping; its §5 must be reconciled at its own review (it
currently claims the fallback branch as its own only-new selection behavior —

- Once E1.7b lands, the **existing manual flows** (`NewCaseModal`, the launch

  today are created with zero tasks will get the generic checklist. This
  matches `[r4]` Q4's intent but changes live-app behavior before E2.x; PM
  question 2 confirms.
- F1.7b.4's "(or payer-generic)" parenthetical names a selection tier that
  does not exist: `pickTemplate` matches exact payer+state+group then
  payer+state — a NULL-state payer template never matches. Drop the
  parenthetical or define the tier explicitly (redline 4); this section
  assumes it is dropped (fallback fires only when the two existing tiers
  miss).
