# E0.3 — Full Party Model (parties, roles, scoped assignments)

## Purpose and Context

E0.3 establishes the Full Party model: the single, reusable way Minted Panel represents the people (and, later, entities) connected to an organization and the roles they hold. It is the data-model foundation the earlier Stage 0 epics implicitly depend on — E0.1 captures an owner, E0.2 captures a customer contact and a sales rep, and both of those are, underneath, parties holding roles on an org.

This epic exists so the platform stops re-deriving "contacts" per feature and instead resolves every stakeholder to one Party record with scoped role assignments. That single source of truth is what later makes cross-org reporting possible (E0.6 portfolio, the shareable business dashboard, multi-org operator views). It implements the Full Party decision recorded in the sequencing artifact and the E0.0 "design to multiply" principle.

Scope discipline: E0.3 is the model plus a minimal manage-parties surface on the org. It does not assign credentialing managers, cases, or tasks — that routing lives at the SOP/case layer downstream, by explicit decision.

## Personas Empowered

- P1 Credentialing Manager (Sowmya) — sole Stage 0 actor; creates, edits, and reviews parties and their roles on an org.
- P5 Practice Owner — represented as a party holding the Owner role; not an actor in Stage 0.

Reference only (not actors here): P6 Office Manager and P8 Practice Biller are future role-holders whose scopes arrive in later stages (facility, billing). Named so the role list is complete, not to grant them a Stage 0 experience.

## Component and Data Constraints

- Built only from the current component library per Stage 0 build constraints (`./uiux-component-guide.md`; workflow in `./README.md`). No new primitives; unmet needs flag back to the PM.
- Example, demo, and test data use scenario orgs and personas from `./seed-universe.md`.
- Role labels come from a fixed reference list, never freeform text.
- No audit trail, edit history, or change logging on party/role edits (explicitly out of scope as noise).
- Any requirement tied to the live schema is flagged below as an implementation dependency, not an assumption.

## Data model (the Party shape)

Modeler's note: names below are the intended shape. Exact table/column names must be verified against the live schema before build (see Dependencies).

- Party
  - `party_type`: `person` | `organization`. Stage 0 creates only `person`; `organization` is reserved so entity-parties (MSO, billing company, payer entity) slot in later with no migration.
  - Person fields: name, email, phone (office and mobile), address block mapped to schema fields (`address_line1`, `address_line2`, `city`, `state`, `postal_code`, `country` if present).
- Role (reference list)
  - Active in Stage 0: Owner, Customer Escalation Contact, Sales Rep.
  - Reserved (defined, selectable-inactive, not surfaced as active Stage 0 assignments): Billing Contact, Contracting Signer, Credentialing Contact.
- Role Assignment (rows, not fields on the org)
  - Links one Party to one Role within a Scope.
  - `scope_type`: `org` active now; `facility` and `case` reserved for later stages.
  - A party may hold multiple role assignments; the same party may be assigned across multiple orgs.

Why rows and not fields: assignment-as-rows is what allows the query "every org where party X holds role Y," which every downstream reporting surface needs. Fields buried on the org cannot answer that.

## Features

### F0.3.1 — Create and manage a Party (person)

- Description: P1 can create a person Party with name, email, phone (office and mobile), and a schema-mapped address block, and edit or remove it from the org's party set. `party_type` is `person` in Stage 0; the `organization` type exists in the model but is not creatable here.
- Persona: P1.
- Benefit hypothesis: If every stakeholder is one reusable Party record, the same person is never entered twice and later reporting can follow that person across the whole book of business, eliminating duplicate-contact drift.
- Acceptance criteria:
  - P1 can create a person Party with name, email, phone (office and mobile), and address block (schema-mapped fields).
  - Email and phone validate to format; address uses split fields, never a single string.
  - A Party is editable and removable from the org at any time, with no audit/history captured.
  - `party_type` is recorded as `person`; `organization` is present in the model but not creatable in Stage 0.
- Test/data scenario(s): TS-9 (party fixture) using seed-universe persons — Zeb Loewenstine, Sowmya, and org owners.

```gherkin
Feature: Create and manage a person Party
  Scenario: P1 creates a person party with full contact fields
    Given I am the Credentialing Manager (P1) in "Point Place Physical Therapy"
    When I create a person party "Zeb Loewenstine" with email, office and mobile phone, and a schema-mapped address
    Then the party is saved with party_type "person"
    And the party is editable and removable with no audit trail

```

### F0.3.2 — Assign a role to a party (scoped)

- Description: P1 assigns a Role to a Party as a scoped Role Assignment row. Stage 0 assignments are `scope_type = org`. Roles are chosen from the fixed reference list; active choices are Owner, Customer Escalation Contact, Sales Rep.
- Persona: P1.
- Benefit hypothesis: If a role is an explicit scoped assignment rather than a label on the org, the platform can answer cross-org and, later, cross-facility questions without rework, turning stakeholder data into reportable structure.
- Acceptance criteria:
  - P1 can assign an active role (Owner, Customer Escalation Contact, Sales Rep) to a party at org scope.
  - The role is selected from the reference list; freeform role text is not possible.
  - Each assignment is stored as a row linking party, role, and scope (`scope_type = org` in Stage 0).
  - Reserved roles (Billing Contact, Contracting Signer, Credentialing Contact) exist in the reference list but are not assignable as active Stage 0 assignments.
- Test/data scenario(s): TS-9, TS-10.

```gherkin
Feature: Assign a scoped role to a party
  Scenario: P1 assigns the Sales Rep role at org scope
    Given the party "Zeb Loewenstine" exists
    And I am in "Outer Banks Rehab Group"
    When I assign the role "Sales Rep" at org scope
    Then a role assignment row is created linking Zeb, Sales Rep, and org scope
    And I could not type a freeform role

```

### F0.3.3 — One party, multiple roles

- Description: A single Party can hold more than one Role assignment (within an org and/or across orgs). Demonstrated by Zeb: Sales Rep across orgs and Owner of Point Place (WI).
- Persona: P1.
- Benefit hypothesis: If one person can legitimately wear multiple hats without duplicate records, small-company reality (a four-person operation) is modeled honestly and reporting stays accurate.
- Acceptance criteria:
  - The same Party can hold two or more role assignments.
  - Multiple roles for one party do not require duplicate Party records.
  - Assignments are independently editable and removable.
- Test/data scenario(s): TS-10 (Zeb = Sales Rep on all orgs and Owner of Point Place).

```gherkin
Feature: One party holds multiple roles
  Scenario: Zeb is both Sales Rep and Owner
    Given the party "Zeb Loewenstine" is Sales Rep on "Point Place Physical Therapy"
    When I also assign him the role "Owner" on "Point Place Physical Therapy"
    Then both role assignments exist for the same single party record
    And no duplicate party was created

```

### F0.3.4 — One party across multiple orgs

- Description: A Party may be assigned in more than one organization. The same Party record is reused; assignments differ per org.
- Persona: P1.
- Benefit hypothesis: If a party spans orgs on one record, the future portfolio and shareable dashboard can show "every org where this person acts," which is the payoff that makes the Party model visible value rather than plumbing.
- Acceptance criteria:
  - One Party record can carry role assignments in multiple orgs.
  - Reusing a party in a new org does not create a second Party record.
  - The model supports querying all orgs where a given party holds a given role (reporting-ready, even if no report UI ships here).
- Test/data scenario(s): TS-10, TS-11.

```gherkin
Feature: One party spans multiple orgs
  Scenario: Zeb is Sales Rep across the portfolio
    Given the party "Zeb Loewenstine" exists
    When he is assigned Sales Rep on "Outer Banks Rehab Group" and "Dillon Sports Medicine"
    Then both assignments reference the same single party record
    And the model can list every org where Zeb holds Sales Rep

```

### F0.3.5 — Role reference list (active and reserved)

- Description: Roles are governed by a fixed reference list. Active roles are surfaced for assignment; reserved roles are defined and selectable-inactive so later stages activate them without a migration.
- Persona: P1 (consumes the list); PM (governs it).
- Benefit hypothesis: If roles are a governed list rather than free text, data stays clean and consistent, and future roles arrive as configuration rather than schema change.
- Acceptance criteria:
  - Active roles: Owner, Customer Escalation Contact, Sales Rep.
  - Reserved roles present but inactive: Billing Contact, Contracting Signer, Credentialing Contact.
  - No freeform role entry anywhere.
  - Adding a future role does not require a schema migration (reference-list driven).
- Test/data scenario(s): TS-9.

```gherkin
Feature: Governed role reference list
  Scenario: Only active roles are assignable
    Given the role reference list
    When I open the role picker at org scope
    Then I can select Owner, Customer Escalation Contact, or Sales Rep
    And Billing Contact, Contracting Signer, and Credentialing Contact are present but not assignable yet

```

### F0.3.6 — Consolidation of E0.1 owner and E0.2 contacts into parties

- Description: The owner captured in E0.1 and the customer contact and sales rep captured in E0.2 resolve to Party records with role assignments, rather than living as separate parallel contact fields/tables. This is stated as the target model; the actual table wiring is an implementation dependency to verify, not an assumption.
- Persona: P1 (benefits from one source of truth); Claude Code (verifies wiring).
- Benefit hypothesis: If owner and contacts are the same underlying parties, there is one source of truth for every stakeholder, so edits propagate and reporting is trustworthy instead of split across tables.
- Acceptance criteria:
  - The E0.1 Owner is represented as a Party holding the Owner role at org scope.
  - The E0.2 Customer Escalation Contact and Sales Rep are represented as Parties holding their respective roles at org scope.
  - No parallel, separate contact store persists as a second source of truth once consolidation lands.
  - If the live schema does not yet link these, that gap is raised as an open implementation question (section below), not silently assumed.
- Test/data scenario(s): TS-9, cross-referenced with E0.1 and E0.2 fixtures.

```gherkin
Feature: Owner and contacts are parties
  Scenario: The E0.2 sales rep is a party with a role
    Given "Outer Banks Rehab Group" has a sales rep captured per E0.2
    When the Party model is applied
    Then that sales rep is a Party holding the Sales Rep role at org scope
    And it is not stored as a separate parallel contact record

```

## 5. Technical Considerations & Enablers — Devin section

This section is owned by Devin. **This is the canonical Stage 0 party schema** — it supersedes the provisional `parties`/`org_party_roles` sketch in E0.1 TE-2 and E0.2 TE-1 (roles become a reference table, not a CHECK list; assignments carry `scope_type`).

### Open-implementation-question resolutions (Devin, 2026-07-08)

- **Does the live schema have party/role/assignment structure?** No — nothing exists (verified against `SCHEMA.md` and the live baseline). Everything below is additive, net-new.
- **Are E0.1 owner / E0.2 contacts separate stores needing migration?** No — by PM decision E0.1–E0.3 build and ship together, so owner and contacts are created **directly** in this party model from day one. F0.3.6 consolidation is satisfied by construction; there is no parallel store and no mirror/migration path needed.
- **Address field names:** identical to E0.2 TE-1 — `address_line1`, `address_line2`, `city`, `state`, `postal_code`, `country`; split fields, never one string.

### Technical enablers (Devin populates)

- **TE-1 — `parties` table (additive migration).** `id uuid PK, party_type text NOT NULL DEFAULT 'person' CHECK (party_type IN ('person','organization')), name text NOT NULL, email text, phone_office text, phone_mobile text, address_line1 text, address_line2 text, city text, state text, postal_code text, country text, created_by uuid NOT NULL, created_at timestamptz`. **Deliberate RLS exception (flagged for PM visibility in `CLARIFICATIONS_NEEDED.md`):** parties carry no `org_id` — cross-org reuse (F0.3.4) is the point of the model, so a single-org scope column is impossible. RLS instead grants access where the caller has a membership in any org the party is assigned to (via TE-3) OR the caller created the party (covers create-before-assign). All other Stage 0 tables stay org-scoped as usual.
- **TE-2 — `party_role_types` reference table (additive migration).** `role_key text PK, label text NOT NULL, is_active boolean NOT NULL` seeded with the six roles: active `owner`, `customer_escalation_contact`, `sales_rep`; reserved (`is_active = false`) `billing_contact`, `contracting_signer`, `credentialing_contact`. Read-only to `authenticated` (no INSERT/UPDATE policies) — the PM governs it; future roles are data inserts (a seed migration), not schema changes (F0.3.5).
- **TE-3 — `party_role_assignments` table (additive migration).** `id uuid PK, org_id uuid NOT NULL, party_id uuid FK→parties, role_key text FK→party_role_types, scope_type text NOT NULL DEFAULT 'org' CHECK (scope_type IN ('org','facility','case')), scope_id uuid, created_at timestamptz` with `UNIQUE (org_id, party_id, role_key, scope_type, scope_id)`. Org-RLS-scoped per convention; Stage 0 writes only `scope_type = 'org'` (scope_id NULL). Assignment INSERTs reject `role_key` rows where `is_active = false` (trigger or RPC-level check) per F0.3.2/F0.3.5.
- **TE-4 — RPC alignment.** E0.1's `create_organization` v2 (E0.1 TE-1) writes into THIS schema: owner party + `owner` assignment, and (per E0.2 TE-2) customer contact + sales rep parties with their assignments — all in one transaction. One schema, three epics.
- **TE-5 — Manage-parties surface.** Org workspace section (with the E0.2 contacts display) composing existing primitives: parties list (`card`/`table`), create/edit forms (`dialog` + form controls), role picker (`select`/`dropdown-menu` fed from `party_role_types` — active roles selectable, reserved roles visible-disabled). Standard layering: `src/services/parties.ts` → `src/hooks/useParties.ts` → components under `src/components/org/` (or `parties/`). Email/phone format validation shared with E0.1 TE-3's validator.
- **TE-6 — Seed extension (TS-9–TS-11).** Stage 0 baseline seed adds: all seed-universe persons as parties (Zeb, Sowmya Seed, org owners, customer contacts), role assignments matching the CRM fixture tables, and the TS-10 demo state (Zeb additionally holds `owner` on Point Place Physical Therapy alongside the seeded owner). `seed-universe.md` gains TS-9–TS-11 rows (reviewer-added).

### Tech-debt findings (Devin populates)

- **TD-1 — Cross-org parties break the "every table org-scoped" convention.** Documented exception (TE-1); the membership-path RLS policy is more complex than the standard `org_id` check and needs explicit tests (cross-org visibility only via assignment, never via mere same-user coincidence).
- **TD-2 — No dedupe/identity resolution.** Nothing stops two Party records with the same email; "never entered twice" (F0.3.1) relies on the UI offering existing-party reuse when assigning. Stage 0 ships reuse-by-search, not enforced uniqueness — revisit if drift appears.
- **TD-3 — Reserved surface is dark.** `party_type = 'organization'`, `scope_type` facility/case, and the three reserved roles exist untested in the model until their stages arrive. Acceptable by design; noted so nothing silently depends on them.
- **TD-4 — Party removal semantics.** "Removable from the org" (F0.3.1) means deleting the org's assignments; the Party record itself is deleted only when it has no remaining assignments anywhere — otherwise cross-org reuse (F0.3.4) would break. Hard delete, no audit UI, per the epic; the standard `writeAudit` row still fires (append-only convention, invisible).
