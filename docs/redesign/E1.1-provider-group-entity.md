# E1.1 — Provider Group / Business Entity

## Purpose and Context

Stage 1's scope journey (E1.0) needs its first real data section: the **legal
billing entity** that every payer contract and application hangs off. A
provider group is the TIN-holding company — its Type 2 NPI, operating states,
and billing/correspondence addresses appear on every payer application and
define the `group × payer × state` contracting grain and the group leg of the
4-part case key (`provider × group × payer × state`, locked 2026-07-10).
E1.1 delivers the "Provider Group" wizard section as a working form over the
**existing** `provider_groups` table (TIN, Type 2 NPI, states[], billing +
correspondence address blocks already exist in the baseline schema) — this is
UI + service work, not new schema. It plugs into E1.0's derived-progress
framework: a saved group flips the section to Complete with zero wizard
flags.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — sole actor; enters the group from
  client intake documents. The wizard is internal-only through Stage 3
  (locked 2026-07-10).
- **P5 Practice Owner** — indirect beneficiary: their entity data is captured
  once, correctly, and reused on every application.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs and personas from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `provider_groups` table exists (baseline schema)
  with `name`, `tin`, `npi_type2`, `states[]`, billing/correspondence/
  credentialing address + contact columns. **No new schema in E1.1.**
- Downstream field usage (why these fields matter): TIN + Type 2 NPI feed
  every contract and payer application (R3/R4); `states[]` feeds case
  generation and the E1.8 readiness "group has facility/license in target
  state" check; address blocks feed application form-fill tokens
  (`{{group.*}}`) in the extension.

## Features

### F1.1.1 — Provider Group form (wizard section)

- **Description:** The E1.0 "Provider Group" section opens a form capturing
  the legal entity: legal name, TIN, Type 2 NPI, operating states
  (multi-select), and the billing / correspondence / credentialing address +
  contact blocks. Create and edit through the same section; the section start
  empty state (E1.0 F1.0.1) is replaced by the form entry point.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** The entity that appears on every payer application
  is captured once at onboarding instead of being re-typed per application;
  errors here are the most expensive in the whole funnel (a wrong TIN bounces
  every downstream application).
- **Acceptance criteria:**
  - Form fields map 1:1 to existing `provider_groups` columns; no new
    columns.
  - **TIN is required to save** (PM, 2026-07-10). Constrained to 9 digits
    (formatted XX-XXXXXXX for display); Type 2 NPI constrained to 10 digits.
    Validation is format-level only in v1 (no external NPI registry check —
    deferred to R5).
  - States multi-select uses the standard state list; at least one state
    required to save.
  - **All three address + contact blocks are in the R1 form** (PM,
    2026-07-10): billing, correspondence, and credentialing, each with
    contact name/phone/fax/email. Billing is required; correspondence and
    credentialing get a "same as billing" quick-fill.
  - Group phone/contact also serves as the default facility contact
    (E1.2 F1.2.1 fallback rule).
  - Save path follows Component → Hook → Service → Supabase; writes set
    `org_id` from the active org.
  - On save, the wizard section flips to Complete via derived progress
    (E1.0 F1.0.2) — no stored flags.
- **Test/data scenario(s):** TS-29 (new — see seed additions).

```gherkin
Feature: Provider Group entity capture
  Scenario: P1 enters Tree Hill's legal entity during onboarding
    Given Tree Hill Sports Therapy is a prospect org with no provider group
    And P1 opens the Provider Group section from the onboarding wizard
    When P1 enters the legal name, TIN, Type 2 NPI, selects NC, and saves
    Then a provider_groups row exists for the org

    And the wizard Next action advances to Facilities
```

### F1.1.2 — Multiple groups per organization

- **Description:** An organization can hold more than one provider group
  (multi-TIN clients are real — locked 4-part-key rationale). The section
  lists existing groups and supports adding another; the section is Complete
  when at least one group exists.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** Multi-company clients (the same therapists under
  two TINs) onboard without workarounds; the data model matches the case key
  from day one.
- **Acceptance criteria:**
  - Section renders a list of the org's groups (name, TIN, states) with an
    "Add another group" action.
  - **Dual-path exit (PM, 2026-07-10):** after saving a group, the section
    shows a primary "Next: Facilities" button alongside the secondary "Add
    another group" action — single-group users flow straight through;
    multi-group users stay and add. No "no more groups" confirmation gate.
  - Each group is editable from the list; deletion is soft
    (`is_active = false`), never a row delete.
  - Derived progress: ≥1 active group → Complete.
- **Test/data scenario(s):** TS-30 (new — see seed additions).

```gherkin
Feature: Multiple provider groups
  Scenario: P1 adds a second TIN to Shelby Sports Rehab
    Given Shelby Sports Rehab has one saved provider group
    When P1 adds a second group with a different TIN and saves
    Then both groups appear in the Provider Group section list
    And the section remains Complete
```

### F1.1.3 — Group summary on Account Detail

- **Description:** Account Detail (`/get-started`) gains a read-only
  provider-group summary (name, TIN, states) consistent with its existing
  read-only intake summary role (E0.8) — editing happens only in the wizard.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** One glanceable client record without creating a
  second editing surface (preserves E1.0's single-front-door rule).
- **Acceptance criteria:**
  - Read-only card listing the org's groups; empty state links to the wizard
    section.
  - No edit affordances on Account Detail.
- **Test/data scenario(s):** TS-29.
