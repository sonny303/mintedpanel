# E1.1 — Provider Group / Business Entity

## Purpose and Context

Stage 1's scope journey (E1.0) needs its first real data section: the **legal
billing entity** that every payer contract and application hangs off. A
provider group is the TIN-holding company — its Type 2 NPI, operating states,
and billing/correspondence addresses appear on every payer application and
define the `group × payer × state` contracting grain and the group leg of the
4-part case key (`provider × group × payer × state`, locked 2026-07-10).
E1.1 delivers the "Provider Group" wizard section as a working form over the
**existing** `provider_groups` table (TIN, Type 2 NPI, states[], billing +
correspondence address blocks already exist in the baseline schema) — this is
UI + service work, not new schema. It plugs into E1.0's derived-progress
framework: a saved group flips the section to Complete with zero wizard
flags.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — sole actor; enters the group from
  client intake documents. The wizard is internal-only through Stage 3
  (locked 2026-07-10).
- **P5 Practice Owner** — indirect beneficiary: their entity data is captured
  once, correctly, and reused on every application.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs and personas from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `provider_groups` table exists (baseline schema)
  with `name`, `tin`, `npi_type2`, `states[]`, billing/correspondence/
  credentialing address + contact columns. **No new schema in E1.1.**
- Downstream field usage (why these fields matter): TIN + Type 2 NPI feed
  every contract and payer application (R3/R4); `states[]` feeds case
  generation and the E1.8 readiness "group has facility/license in target
  state" check; address blocks feed application form-fill tokens
  (`{{group.*}}`) in the extension.

## Features

### F1.1.1 — Provider Group form (wizard section)

- **Description:** The E1.0 "Provider Group" section opens a form capturing
  the legal entity: legal name, TIN, Type 2 NPI, operating states
  (multi-select), and the billing / correspondence / credentialing address +
  contact blocks. Create and edit through the same section; the section start
  empty state (E1.0 F1.0.1) is replaced by the form entry point.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** The entity that appears on every payer application
  is captured once at onboarding instead of being re-typed per application;
  errors here are the most expensive in the whole funnel (a wrong TIN bounces
  every downstream application).
- **Acceptance criteria:**
  - Form fields map 1:1 to existing `provider_groups` columns; no new
    columns.
  - **TIN is required to save** (PM, 2026-07-10). Constrained to 9 digits
    (formatted XX-XXXXXXX for display); Type 2 NPI constrained to 10 digits.
    Validation is format-level only in v1 (no external NPI registry check —
    deferred to R5).
  - States multi-select uses the standard state list; at least one state
    required to save.
  - **All three address + contact blocks are in the R1 form** (PM,
    2026-07-10): billing, correspondence, and credentialing, each with
    contact name/phone/fax/email. Billing is required; correspondence and
    credentialing get a "same as billing" quick-fill.
  - Group phone/contact also serves as the default facility contact
    (E1.2 F1.2.1 fallback rule).
  - Save path follows Component → Hook → Service → Supabase; writes set
    `org_id` from the active org.
  - On save, the wizard section flips to Complete via derived progress
    (E1.0 F1.0.2) — no stored flags.
- **Test/data scenario(s):** TS-29 (new — see seed additions).

```gherkin
Feature: Provider Group entity capture
  Scenario: P1 enters Tree Hill's legal entity during onboarding
    Given Tree Hill Sports Therapy is a prospect org with no provider group
    And P1 opens the Provider Group section from the onboarding wizard
    When P1 enters the legal name, TIN, Type 2 NPI, selects NC, and saves
    Then a provider_groups row exists for the org
    And the Provider Group section shows Complete
    And the wizard Next action advances to Facilities
```

### F1.1.2 — Multiple groups per organization

- **Description:** An organization can hold more than one provider group
  (multi-TIN clients are real — locked 4-part-key rationale). The section
  lists existing groups and supports adding another; the section is Complete
  when at least one group exists.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** Multi-company clients (the same therapists under
  two TINs) onboard without workarounds; the data model matches the case key
  from day one.
- **Acceptance criteria:**
  - Section renders a list of the org's groups (name, TIN, states) with an
    "Add another group" action.
  - **Dual-path exit (PM, 2026-07-10):** after saving a group, the section
    shows a primary "Next: Facilities" button alongside the secondary "Add
    another group" action — single-group users flow straight through;
    multi-group users stay and add. No "no more groups" confirmation gate.
  - Each group is editable from the list; deletion is soft
    (`is_active = false`), never a row delete.
  - Derived progress: ≥1 active group → Complete.
- **Test/data scenario(s):** TS-30 (new — see seed additions).

```gherkin
Feature: Multiple provider groups
  Scenario: P1 adds a second TIN to Shelby Sports Rehab
    Given Shelby Sports Rehab has one saved provider group
    When P1 adds a second group with a different TIN and saves
    Then both groups appear in the Provider Group section list
    And the section remains Complete
```

### F1.1.3 — Group summary on Account Detail

- **Description:** Account Detail (`/get-started`) gains a read-only
  provider-group summary (name, TIN, states) consistent with its existing
  read-only intake summary role (E0.8) — editing happens only in the wizard.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** One glanceable client record without creating a
  second editing surface (preserves E1.0's single-front-door rule).
- **Acceptance criteria:**
  - Read-only card listing the org's groups; empty state links to the wizard
    section.
  - No edit affordances on Account Detail.
- **Test/data scenario(s):** TS-29.

## 5. Technical Considerations & Enablers

_Devin-owned section (appended at review). Authors do not edit above this line
for technical content; scope/requirements above are PM/ChatPRD-owned._

Reviewed against the current architecture (React 19 + TypeScript + Vite +
TanStack Start; strict Component → hook (`src/hooks`) → service
(`src/services`) → Supabase `externalClient` layering; additive-only
migrations; append-only `touches`/`status_history`/`audit_log`; org-scoped
RLS; shadcn/ui + Tailwind v4 tokens). **No migration is required** — every
field this epic captures already exists on `provider_groups`, and a working
create/update service + hook path is already in the codebase. E1.1 is UI +
a modest additive widening of the existing group input/type, plus a
progress-resolver refinement. Confirmations that gate the "no new schema"
claim:

- `provider_groups` (baseline `20260704210000_baseline_live_schema.sql`,
  lines 279–323) holds `name`, `tin`, `npi_type2`, `states text[]`,
  `is_active`, and **all three** address + contact blocks —
  `billing_*`, `correspondence_*`, and `credentialing_*` each with
  `street`/`suite`/`city`/`state`/`zip` and `contact_name`/`phone`/`fax`/
  `email` (plus `contracting_contact_*`, `contract_signer_*`, `website_url`,
  `tax_id_type`, `preferred_contact_method`). RLS is enabled and org-scoped;
  the FK is `provider_groups.org_id → organizations(id) ON DELETE CASCADE`.

### TE-1 — Route and component boundary (no new route)

Deliver the "Provider Group" section inside the **existing** E1.0 wizard
route (`src/routes/onboarding.wizard.tsx`) — do not add a route or move Stage 1
entry into Account Detail. Replace the E1.0 `NotYetAvailable`/empty-state
placeholder for the Provider Group section with the form entry point
(F1.1.1). Place the reusable form and list UI in a feature module under
`src/components/onboarding/` (e.g. a `ProviderGroupSection` composer + a group
form). Feature components live in `src/components/[module]/`, never in `ui/`
or `layout/`. **No new dependency is required, but there is one primitive
gap:** the existing `GroupsPanel` edit dialog
(`src/components/settings/GroupsPanel.tsx`) already composes most of the
needed shadcn primitives — `Dialog`, `Input`, `Label`, `Select`, `Checkbox`,
`Switch`, `Collapsible`, `Button`, `StatusPill` — all present in
`src/components/ui/`. The exception is the states **multi-select**: no
multi-select/combobox primitive exists in `src/components/ui/` or the design
system, and `GroupsPanel`'s states input is comma-separated free text — see
the component enabler in TE-5.

### TE-2 — Layering: reuse the existing service + hooks; do not add a third read path

A complete Component → hook → service → Supabase path for provider groups
already exists — reuse it, do not re-implement:

- **Service (writes):** `src/services/orgSettings.ts` —
  `createProviderGroup(input)` and `updateProviderGroup(id, patch)` (both set
  `org_id` from `requireActiveOrg()`, map camel→snake via `snakeizeRow`,
  normalize state codes, translate DB errors, and write `audit_log`).
- **Hooks (writes):** `src/hooks/useOrgSettings.ts` —
  `useCreateProviderGroup()` / `useUpdateProviderGroup(id)`, both invalidating
  `["provider-groups", orgId]` and the audit key.
- **Read hook:** `useProviderGroups()` in `src/hooks/useLookups.ts`
  (query key `queryKeys.providerGroups(orgId)`), backed by
  `getProviderGroups()` in `src/services/lookups.ts`.

The wizard section and the Account Detail summary must both consume the shared
`useProviderGroups()` read so there is a single cache the create/update
mutations already invalidate. **Do not introduce a third provider-group read
implementation** (see tech debt: `lookups.getProviderGroups` and
`orgSettings.listProviderGroups` already duplicate the same org-scoped
`select("*")`). No Supabase call and no mock array in any component.

### TE-3 — Extend `ProviderGroupInput` to cover the credentialing block + contact fields

`ProviderGroupInput` (`src/services/orgSettings.ts`, lines 50–64) currently
carries only `name`, `tin`, `npiType2`, `states`, `isActive`, and the
`billing*`/`correspondence*` **address** fields. F1.1.1 requires all three
blocks **with contacts**, so additively extend the input (and the
create/update payload mapping) with:

- Contact fields for each existing block: `billingContactName`,
  `billingPhone`, `billingFax`, `billingEmail`, and the
  `correspondence*`/`credentialing*` equivalents.
- The full credentialing address block: `credentialingStreet`,
  `credentialingSuite`, `credentialingCity`, `credentialingState`,
  `credentialingZip` (plus `billingSuite`/`correspondenceSuite` for parity
  with the schema).

These ride through the existing `snakeizeRow` mapping unchanged. Extend the
state-normalization guard in both `createProviderGroup` and
`updateProviderGroup` to also run `normalizeOptionalStateCode` on
`credentialingState` (today only `billingState`/`correspondenceState` are
normalized) so the third block gets the same uppercase-2-letter floor.

### TE-4 — Additively widen the `ProviderGroup` type (protected file, additive-only)

`src/types/index.ts` is a protected file but **additive changes are
explicitly allowed** (AGENTS.md). The `ProviderGroup` interface (lines 247–256)
today exposes only `id/orgId/name/tin/npiType2/states/isActive/createdAt`.
The form and the read-only summary need the address + contact fields, so add
the corresponding optional (`string | null`) properties for the
`billing*`/`correspondence*`/`credentialing*` address and contact columns.
This is the typed-field expansion E1.0's review deferred to E1.1 (E1.0 TE
"Likely tech debt": _"E1.1/E1.2 own any typed-field expansion needed by their
forms"_). Additive only — do not rename, remove, or retype existing fields.

### TE-5 — Field validation (format-only) and the states multi-select

- **TIN required to save** (PM 2026-07-10): constrain to 9 digits, display
  formatted `XX-XXXXXXX`, store the digits. **Type 2 NPI:** 10 digits.
  Validation is **format-level only** in v1 — no external NPI/TIN registry
  check (deferred to R5). Put this in a pure, unit-tested helper under
  `src/lib/` (mirror the existing `src/lib/contactValidation.ts` /
  `src/lib/stateCode.ts` pattern); no new dependency.
- **States multi-select:** at least one state required to save. Reuse the
  canonical `US_STATES` list — it currently lives in
  `src/components/settings/shared.ts`; promote/re-export it from a neutral
  location (`src/lib/` or `src/data/`) so the onboarding module does not
  import from a sibling feature module (`components/settings`). The current
  `GroupsPanel` uses a comma-separated free-text states input; the wizard
  section must use a real multi-select (F1.1.1 says multi-select).
  **Component enabler (independent review):** no multi-select primitive
  exists in `src/components/ui/` or `docs/redesign/design-system/`. Per the
  `DESIGN-DEBT.md` rule, compose it from approved primitives first —
  `DropdownMenuCheckboxItem` already exists in
  `src/components/ui/dropdown-menu.tsx` and can anchor a
  checkbox-list-in-dropdown multi-select with selected-state chips — and
  **log the composition as a `DESIGN-DEBT.md` row in the build PR** (an
  unlogged unapproved component is a merge blocker per that register). Never
  an epic-local one-off; no new dependency.
- **"Same as billing" quick-fill** for both correspondence **and**
  credentialing blocks (F1.1.1), extending the existing single-block
  `sameAsBilling` mirror pattern already in `GroupsPanel`.
- Inline validation messages under each field; no placeholder-only labels;
  no shipped placeholder text (anti-patterns).

### TE-6 — Soft delete + derived-progress refinement (no wizard flags)

- **Soft delete** = `updateProviderGroup(id, { isActive: false })`; never a
  row delete (F1.1.2, out-of-scope "no hard delete"). `provider_groups` is not
  an append-only table, so this is an ordinary org-scoped update (audited).
- **Multiple groups per org** (F1.1.2): the section lists the org's groups and
  offers "Add another group"; the dual-path exit shows a primary
  "Next: Facilities" alongside the secondary "Add another group" — no
  confirmation gate.
- **Derived progress:** E1.0's provider-group resolver in
  `src/lib/onboardingProgress.ts` (an E1.0 TE-3 deliverable — not yet in the
  repo; E1.1 builds only after E1.0 merges, per Dependencies) completes on
  **row presence**. E1.1
  refines it to complete on **≥1 _active_ group** (F1.1.2), and the wizard
  list should show active groups. This is the sanctioned broadening of a
  resolver input (E1.0 TE-3: _"E1.1–E1.3 may broaden their resolver inputs …
  they must not add wizard-only progress flags"_) — keep it pure/derived; add
  **no** stored progress column or flag. Update the resolver's unit truth
  table accordingly.

### TE-7 — Schema, RLS, grants, append-only assessment

- **No migration, RPC, or new grant is required.** All writes go through the
  browser `authenticated` role under existing org-scoped RLS on
  `provider_groups`; every insert sets `org_id` from the active org.
- **Append-only tables are untouched** except the existing, correct
  `audit_log` writes on create/update (`writeAudit` in the service) — no
  `touches`/`status_history` involvement.
- **Additive schema gaps to note (describe, do not implement in E1.1):**
  E0.10's state-format floor (`20260710160000_state_format_checks.sql`) added
  `^[A-Z]{2}$` `NOT VALID` CHECKs to `provider_groups.billing_state` and
  `correspondence_state` **only** — there is **no** check on
  `credentialing_state`, and the `states text[]` array was explicitly deferred
  ("shape decision deferred to the group-address normalization epic"). E1.1
  enforces valid 2-letter codes client-side (normalization + `US_STATES`
  select), which is sufficient for R1; a future additive migration could add
  the matching `credentialing_state` CHECK and a per-element constraint on
  `states[]` for defense-in-depth. Any such migration must update
  `docs/data-model/table-register.md` in the same PR — but it is **out of
  scope here**.
- **Table trace correction (independent review):** the Dependencies line
  ("reads/writes `provider_groups`; reads `organizations`") omits the
  `audit_log` **writes** this section already acknowledges —
  `createProviderGroup`/`updateProviderGroup` insert an audit row via
  `writeAudit` on every mutation. Authoritative R1 trace: reads
  `provider_groups`, `organizations`; writes `provider_groups` and
  `audit_log` (append-only inserts, the sanctioned pattern). Reconciled
  against `docs/data-model/table-register.md`.
- **Sprawl-target awareness (independent review):** the table register marks
  `provider_groups`' 30 purpose-keyed address/contact columns as a **sprawl
  target with planned `group_addresses`/`group_contacts` child tables**, and
  its design rule 1 names this very column block the grain-rule cautionary
  tale; E0.10 likewise defers the `states[]` shape to "the group-address
  normalization epic". E1.1 correctly adds no schema and builds on the
  existing columns, but the form/service mapping should be **block-shaped**
  (one address+contact object per purpose — billing / correspondence /
  credentialing — folded to the flat columns in a single mapping module) so
  a future child-table normalization repoints one boundary instead of
  rewriting the form. The normalization itself stays out of scope (PM
  question 3 below confirms sequencing).
