# E6.11 — Team Access & the User Record

**One repo (panel).** The extension needs no change: since 2026-07-28 its
quick-card picker renders from the **served** catalog rather than a bundled
mirror, so new `{{user.*}}` keys reach it through the existing
`GET /api/me/view-prefs` response with no extension release.

## Purpose and Context

Three findings from one sitting, which turn out to be the same subject — **the
user record is the least-built entity in the system**:

1. An admin demoted themselves in the Access table and could not undo it. The
   org sat at **zero admins** until the role was restored by direct SQL.
2. There is no way to add a teammate from the UI at all.
3. The person filling a payer form cannot put their own name, title or role
   into it, because the system stores almost nothing about them.

Minted Panel models organizations, providers, groups, facilities, payers and
cases in depth. The human operating it has three columns — `profiles.id`,
`email`, `full_name` — no editor, and two resolvable tokens. This epic gives the
user record the same treatment every other entity already has: a way in, a way
to edit, a way to use it, and an invariant that stops the org locking itself
out.

### What already exists (spike, 2026-08-13 — verified in code and against the live DB)

Most of this is built. Cited by path so the build session does not re-derive it:

1. **The invite backend is fully intact AND deployed.** `pending_invites`
   (carrying `email`, `role`, `full_name`, `invited_by`), the `claim_invites()`
   login RPC, `src/services/invites.ts`
   (`listPendingInvites`/`createPendingInvite`/`revokePendingInvite`/
   `inviteMember`), `src/hooks/useInvites.ts`, and the **`invite-member` edge
   function — status ACTIVE, version 6 on hosted**, which sends the invite
   email. `MembersPanel.tsx`'s own header comment records why nothing is
   missing: the flow was removed **UI-only** on 2026-07-19, backend deliberately
   kept "so the capability can return post-MVP". The Pending invites table still
   renders whenever legacy rows exist (there are zero today). **This feature is a
   restoration, not a build.**
2. **`profiles` already permits self-service writes.** Policies are
   `profiles_select_self`, `profiles_select_org_members`, and
   **`profiles_update_self`** — the write path an identity editor needs exists;
   only the columns, the service, and the UI are missing. (There is no INSERT
   policy: rows are minted alongside the auth user, and this epic does not
   change that.)
3. **The identity editor was deleted, not never-built.** `ProfilePanel`,
   `useUserProfile` and `src/services/userProfile.ts` were removed on
   2026-07-21 with the Org Detail Profile card. Already-set names persist and
   `{{user.name}}` still resolves them; nothing can set one now.
4. **The self-demotion half-guard is shipped.** `MembersPanel` disables your own
   row's role select and `updateMembershipRole` rejects a self role change
   (2026-08-13). **The database still permits it** —
   `memberships_update_admin` carries no self-restriction, unlike
   `memberships_delete_admin`, which has always carried `user_id <> auth.uid()`.
   F6.11.2 closes that asymmetry.
5. **The token append pattern is settled.** `USER_TOKEN_FIELDS` in
   `src/lib/quickCardCatalog.ts` and `src/server/userTokens.ts` are the
   code-owned family (`get_sop_field_tokens()` sweeps
   `information_schema.columns` and cannot express "the person filling this
   form"). The 2026-08-07 `orgContactTokens.ts` work is the precedent to copy,
   including its naming and irreversibility rules.

### The distinction this epic will not blur

**"Create a user" here means invite, not provision.** The flow is: an admin
writes a `pending_invites` row → the edge function emails the person → they sign
up themselves → `claim_invites()` converts the row into a membership at first
login. Minting an account directly (setting someone's password for them) needs
the GoTrue admin API behind a service-role `/api` route — a different trust
boundary, deliberately **out of scope** (see Non-Goals). The UI must therefore
say _invite_, and an invited person must appear as pending until they accept.

## Personas Empowered

- **P1 Credentialing Manager** — adds teammates, keeps their own identity
  current, and cannot accidentally strip the org of its last admin.
- **P2 Credentialing Coordinator / Specialist** — fills payer forms that ask who
  is submitting them.

## Features

### F6.11.1 — Invite a teammate (restore the removed UI)

- **Description:** An admin can invite someone by email with a role, see them
  as pending until they accept, and revoke a pending invite.
- **Persona:** P1.
- **Benefit hypothesis:** There is currently **no** path to a second user. Every
  new teammate is a support request. The backend is deployed and idle.
- **Acceptance criteria:**
  - Admin-only "Invite member" in the Access section, capturing email, role, and
    optional full name — the three fields `pending_invites` already stores.
  - Writes through the EXISTING `createPendingInvite`, then calls `inviteMember`
    for the email. Per that function's contract, **email failure is soft**: the
    invite still exists and is surfaced as a warning, never a thrown error — a
    person who never got the mail can still be told to sign up.
  - `DuplicateInviteError` is surfaced as a sentence, not a raw error.
  - The Pending invites table renders whenever invites exist (it already does)
    with revoke; the empty state stays absent rather than dead.
  - Copy says **invite**, never "create user" — the person completes signup
    themselves and `claim_invites()` grants the membership at first login.
  - No change to `claim_invites()`, the edge function, or the invite service's
    query logic.

```gherkin
Feature: Inviting a teammate
  Scenario: An admin invites a coordinator
    Given P1 is an admin of Shelby Sports Rehab
    When they invite coordinator@example.test as Specialist
    Then a pending invite row exists for that email and role
    And the invite appears as pending with a revoke action
    And a failure to send the email is shown as a warning, not an error
```

### F6.11.2 — An organization always keeps an admin

- **Description:** The database refuses the last step that would leave an org
  with zero admins.
- **Persona:** P1.
- **Benefit hypothesis:** The app-layer guard shipped 2026-08-13 closes the door
  that was actually walked through, but the invariant lives in the UI and one
  service function. An org that reaches zero admins is unmanageable by anyone
  inside it and needs direct SQL to recover — which is exactly what happened.
- **Acceptance criteria:**
  - The rule is enforced in the DB, not only in `updateMembershipRole` — so the
    restored invite flow, a future `/api` route, or direct PostgREST cannot
    reach the state either.
  - The invariant to enforce is **"at least one admin remains"**, which is more
    truthful than "you may not edit your own row": an admin may legitimately
    step down when another admin exists. (The narrower self-restriction mirroring
    `memberships_delete_admin` is the acceptable simpler alternative if the
    build session finds the count-based rule needs a trigger it judges too heavy
    — state which was chosen and why in the PR body.)
  - Concurrency is considered: two admins demoting themselves simultaneously
    must not both pass a count check. Follow the advisory-lock precedent in
    `trg_sop_template_state_overlap` (2026-08-12) if a trigger is used.
  - The rejection surfaces as a sentence through `translateDbError`, never a raw
    constraint name.
  - The shipped app-layer guard stays — defence in depth, and it explains the
    disabled control before the user clicks anything.
  - **Membership role changes are currently unaudited** — nothing recorded the
    original demotion, which is why it was invisible. Auditing them is in scope
    if it costs little; say so either way in the PR body.

### F6.11.3 — The user record gains real identity fields

- **Description:** `profiles` gains first name, last name, title, and the role
  field resolved by OQ-1.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Payer forms ask who is submitting them. Today the
  system can offer a single `full_name` blob and an email.
- **Acceptance criteria:**
  - Additive and nullable; every existing row keeps working, and `full_name`
    is **retained** (the additive rule; it is what `{{user.name}}` resolves from
    today and what the sidebar renders).
  - First/last backfill from `full_name` reuses the SQL split helper that
    `20260807130000` established for `parties`, so the two agree.
  - `full_name` becomes a **derived mirror** when first/last are present —
    composed at the service boundary via `personName.composeFullName`, the same
    lockstep rule `parties` follows. Never a second source of truth for display.
  - No new RLS work is expected: `profiles_update_self` already permits the
    write. Confirm that rather than assume it, and state the result.

### F6.11.4 — A person can edit their own details

- **Description:** A self-service identity editor returns, replacing the one
  deleted on 2026-07-21.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Fields nobody can set are fields that autofill blanks.
  This is the only surface that makes F6.11.3 real.
- **Acceptance criteria:**
  - Edits **only your own** profile row. This is not an admin surface — an admin
    does not edit a colleague's name here.
  - Follows the provider record's ONE master "Edit details" → whole-form →
    "Save changes" diff-only patch (2026-07-21), not per-field pencils.
  - Location is a placement decision, not a new page: the natural home is the
    user menu or Org Detail's People section. State the choice in the PR body.
  - Saving refreshes what the sidebar and touchlog author lines display, with no
    reload.
  - `{{user.name}}` resolution order is explicit and ordered:
    composed first/last → `profiles.full_name` → auth `user_metadata`. The last
    step preserves today's behaviour for anyone who set a name before the
    setter was deleted.

### F6.11.5 — User identity resolves as fillable tokens

- **Description:** The `{{user.*}}` family grows from two keys to cover the new
  identity fields.
- **Persona:** P2.
- **Benefit hypothesis:** This is the reason the PM asked for the fields — the
  submitter block on a payer form should autofill like everything else.
- **Acceptance criteria:**
  - Resolved in `src/server/userTokens.ts` beside the existing pair, reading the
    caller's profile row. Follow `orgContactTokens.ts` (2026-08-07) for shape,
    including an **honest unresolved reason** rather than a guessed value when a
    field is empty.
  - **Naming is effectively irreversible** — token keys join `portal_field_maps`
    ↔ profile ↔ quick cards by literal string match. Flat camelCase, matching
    `groupInsurance.*` / `billingContact.*`: `user.firstName`, `user.lastName`,
    `user.title`, plus OQ-1's role key. `user.name` and `user.email` are
    unchanged.
  - `user.name` stays the **composite** (the `facility.address` /
    `billingContact.fullName` precedent), so a one-box "Submitted by" form needs
    no mapping-time concatenation `portal_field_maps.token` cannot express.
  - Deliberately absent from `sopResolver.buildTokenMap` unless a case is made:
    a token in a SOP body is baked into `tasks.sop_content` at case creation and
    would go stale (D12). Pin the decision as a negative assertion either way.
  - The profile endpoint's PHI posture is unchanged — no new PHI, no new audit
    semantics; these are the operator's own details.

### F6.11.6 — The new keys are offered on extension quick cards

- **Description:** The identity keys join the quick-card catalog.
- **Persona:** P2.
- **Benefit hypothesis:** Closes the loop — the fields become visible where the
  person is actually working, with no extension release.
- **Acceptance criteria:**
  - Appended via `USER_TOKEN_FIELDS` in `quickCardCatalog.ts`, the shipped
    pattern.
  - `quickCardCatalog.test.ts` is updated, **not weakened** — its
    `ACKNOWLEDGED_TOKENS` snapshot is what makes the deny-list safe, and a new
    column must keep failing the suite by name until someone classifies it.
  - No extension change: the picker renders from the served catalog
    (2026-07-28), so the keys arrive through `GET /api/me/view-prefs`.

## Out of Scope / Non-Goals

- **Provisioning accounts directly.** No admin-sets-a-password screen; that
  needs the GoTrue admin API behind a service-role route and is a separate trust
  boundary. Invite + self-signup is the flow.
- **Admins editing other people's identity.** F6.11.4 is self-service only.
- **Reworking roles.** The three-role model (admin / specialist / billing)
  is untouched; no new role, no per-resource permissions.
- **Cross-org identity.** A profile is one person, not per-org — no per-org
  display names or titles.
- **Reviving the deleted `user_metadata` setter.** `profiles` is the store;
  auth metadata stays a read-only fallback.
- **Bulk invites / CSV.** One invite at a time.

## Locked Decisions

1. **Invite, never "create user"** — the wording matters because the person
   completes signup themselves; anything else misdescribes what the button does.
2. **The invite backend is consumed unchanged.** It is deployed and idle; this
   epic adds a surface, and any change to the RPC or edge function is a
   different epic.
3. **`profiles` is the identity store**, with `full_name` retained as a derived
   mirror per the additive rule.
4. **Token naming is irreversible** and follows `orgContactTokens.ts`.
5. **The zero-admin invariant belongs in the database.** The app-layer guard
   shipped 2026-08-13 stays, but it is not the wall.

## Open Questions

- **OQ-1 (blocking F6.11.3/F6.11.5) — what does "user role" mean?** The PM's
  handoff said "user role (role specifically for minted panel)". Two readings,
  and the wrong one autofills nonsense:
  - **A job role** — "Credentialing Coordinator". What a payer form asking
    "Your role" actually wants. **Recommended**, as `user.jobRole` or
    `user.roleTitle` (name it once, permanently).
  - **The access level** — admin / specialist / billing. This is **per-org**
    (a user can be admin in one org and billing in another), so it resolves
    against the active org rather than the person, and filling "billing" into a
    payer form would be wrong in a way nobody would catch.
    A third option is both, as separate keys — a free-text job role for filling
    plus the access role for internal display. That is the safe superset if the
    PM wants the access level visible at all.
- **OQ-2 — where does the identity editor live?** User menu vs Org Detail's
  People section. Org Detail is where People already lives; the user menu is
  where "my account" conventionally sits. A placement call, not a scope call.
- **OQ-3 — should membership role changes be audited?** Nothing recorded the
  demotion that motivated F6.11.2. Cheap to add and it closes the forensic gap.
