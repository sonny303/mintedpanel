# E6.6 — Reporting Center Organization & Touch Unification

## Purpose and Context

The simplification wave retires several surfaces whose *read* jobs survive
(Launches, Client Progress's owner story, Audit Log's admin page, the Home
"Launches at risk" slice) and the PM ruled that occasional counts are
reports, not screens. Per decision record decision 7, this epic organizes
the Reporting Center into four groups and lands every displaced read job
there — including the provider-first **denials rollup** built on E6.0's
unified statuses — and unifies activity logging into ONE global **Add
touch** action (multi-case capable; "Log Payer Call" retires). It also
executes the Settings-page retirement residue: members management moved to
Org Detail (E6.1), and the denial word-list + queue ranking ship as fixed
defaults with no admin editors.

## Personas Empowered

- P1 Credentialing Manager — every investigation question has a report;
  every activity is logged the same one way.
- P2 Credentialing Coordinator / Specialist — one logging gesture
  everywhere, including batch payer calls.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md). The report registry pattern (one entry + one
  route per report) is reused for every new report.
- Example/demo/test data uses scenario orgs from
  [seed-universe.md](./seed-universe.md); Dillon Sports Medicine's case and
  touch fixtures anchor the denial and touch tests.
- Implementation dependencies (flagged): the denials report reads E6.0's
  status + reason data; the Launches report reads facility go-live dates
  (no location status machine); touch unification extends the existing
  touch service (append-only ledger unchanged).

## Features

### F6.6.1 — The grouped report index

- **Description:** The Reporting Center index renders four groups:
  **Performance** (Portfolio; Launches), **Credentialing** (Denials;
  Expiring credentials), **Compliance** (Audit Log), **Intake** (Inbound
  leads, with the count badge rendered only when leads await). Org-scoped
  reports render inside the cross-org Center per the existing pattern.
- **User story:** As P1, the Center reads as a table of contents by
  question type, not a flat list.
- **Persona:** P1.
- **Benefit hypothesis:** Organization by question ("how are we
  performing / where are the problems / who did what / who's knocking")
  scales as reports accumulate.
- **Acceptance criteria:**
  - Four groups render with the stated membership; adding a report stays
    one registry entry + one route.
  - The leads badge renders only when leads await; leads triage moves off
    Org/Account Detail entirely.
- **Test/data scenario(s):** TS-115.

### F6.6.2 — The Launches report

- **Description:** The Launches page retires (E6.1); this report lists
  locations with future or recent go-live dates across the org — grouped
  by group, date-sorted, with provider counts — restoring the "what's
  opening when, and is anything at risk" read (the old Home "Launches at
  risk" slice's successor: a location is flagged when its date approaches
  with open cases or zero assigned providers).
- **Persona:** P1.
- **Benefit hypothesis:** Go-live tracking survives as the read it always
  was, without a status machine or a nav item.
- **Acceptance criteria:**
  - Derives from facility dates + assignments + open cases only; no
    location statuses anywhere.
  - The at-risk flag matches the stated rule and is explained inline.
- **Test/data scenario(s):** TS-115.

### F6.6.3 — The denials rollup report

- **Description:** Provider-first denials: per provider, each Denied case
  with payer, state, reason (fixed word-list), date, and current cycle
  state (reapplied / standing); pivotable payer-first to expose patterns
  ("Anthem denied 4 of 6 in NC — all panel closed"). Exportable CSV.
  Consistent by construction with the provider record's panel (E6.4) —
  same derivation, one source.
- **User story:** As P1, "who has been denied, by whom, and why" is one
  report I can hand to an owner.
- **Persona:** P1.
- **Benefit hypothesis:** The governed reason vocabulary finally pays off
  as aggregable reporting; replaces Client Progress's owner story with
  something more actionable.
- **Acceptance criteria:**
  - Both pivots derive from case statuses + reasons; zero stored rollup
    state; CSV export.
  - A denial recorded on a case appears in the report immediately.
- **Test/data scenario(s):** TS-115.

### F6.6.4 — Relocated reads: Audit Log & the basic counts

- **Description:** The Audit Log admin page retires into the Compliance
  group (same read surface, relocated; append-only ledger untouched). The
  PM's counts-as-reports ruling lands here as two basic reports:
  **Facilities without providers** and **Locations per group** — simple
  org-scoped tables, no screen widgets on the working surfaces.
- **Persona:** P1.
- **Benefit hypothesis:** Investigation reads live with investigation
  reads; working screens stay lean.
- **Acceptance criteria:**
  - Audit Log renders in the Center with existing filters; `/admin/audit`
    redirects.
  - The two count reports derive live from existing data; no new stored
    state.
- **Test/data scenario(s):** TS-115.

### F6.6.5 — Add touch: one global logging action

- **Description:** "Add touch" is THE logging action everywhere (case
  detail, Cases pivots, provider record): structured type + optional
  disposition/recipient/follow-up, and **multi-case selection** — a payer
  call spanning N cases is one Add touch with N cases selected (one touch
  per case + batch summary, per the existing batch semantics). The
  separate "Log Payer Call" dialog retires. The E6.0 status-bump
  suggestion (F6.0.3) rides this same dialog. The touch ledger stays
  append-only; corrections append.
- **User story:** As P2, there is exactly one way to say "this happened,"
  whether it touched one case or eleven.
- **Persona:** P2, P1.
- **Benefit hypothesis:** One verb, one dialog, one ledger — logging
  behavior becomes uniform and the batch path stops being a separate
  feature to know about.
- **Acceptance criteria:**
  - "Add touch" naming everywhere; the batch dialog's entry points fold
    into it; per-case touch rows + audit preserved exactly as the
    existing batch semantics.
  - Status-bump suggestions appear only where the touch implies one
    (F6.0.3 rules).
- **Test/data scenario(s):** TS-115.

### F6.6.6 — Fixed-default residue of the Settings retirement

- **Description:** With the Settings page retired (E6.1 moved members to
  Org Detail): the denial reason word-list ships as the fixed default set
  (no org editor; additions are a platform change), and queue ranking
  runs the shipped default order (no config UI). Both are documented in
  the module they affect.
- **Persona:** P1.
- **Benefit hypothesis:** For a two-user system, editors for rarely-
  touched vocabulary are surface area without payoff; defaults with a
  documented change path are enough.
- **Acceptance criteria:**
  - No reason-code or ranking editors render anywhere; the fixed sets are
    single-source constants; existing data referencing them is unaffected.
- **Test/data scenario(s):** TS-115.
