## Mission

Implement epic **E4.2 — Payer & SOP Admin Module** from
`docs/redesign/E4.2-payer-sop-admin-module.md` (frontmatter
`reviewed: true` — you are cleared to build). Read the whole epic first;
its `## 5. Technical Considerations & Enablers` section (TE-1 … TE-17)
pins the authoritative mechanics — build from the TE sections, not from
the feature prose alone. This epic is a **management surface over shipped
machinery** (E1.5/E1.6 payers, E1.7b SOP versioning, E2.0/E2.1/E2.4
generation) — you are consolidating and configuring, never re-implementing
a payer model, SOP resolver, or generator. In particular:

- **The module (F4.2.1/TE-1/TE-15):** one role-gated route subtree under
  `/admin/...` with module-local components in
  `src/components/payer-admin/`. NOT a separate deployment. Compose or
  relocate the existing payer/template screens; do not clone them. The
  import boundary is **machine-enforced both ways** (TE-15): an ESLint
  `no-restricted-imports` scoped config or an import-graph unit test that
  fails CI when specialist code imports `src/components/payer-admin/` or
  the module imports specialist workflow components (shared `src/lib` /
  `src/services` / design-system primitives are the only shared surface).
  One narrowly scoped `src/components/layout/Sidebar.tsx` change is
  authorized for the admin-only nav entry — nothing else in layout.
- **Roles (TE-2):** P4 maps to the existing `admin` role. Use the existing
  admin guard on the route; do NOT add a fourth role or capability system.
  Seed the P4 persona as an admin membership (TS-76).
- **Per-payer resolution-ID config (F4.2.1):** each payer's config stores
  the label of its payer-issued enrollment identifier (e.g. "Provider
  PIN") and whether one is expected at approval; unconfigured payers fall
  back to a generic optional "Payer-issued ID". Consumed by E4.0 F4.0.3's
  approval step — wire the label/expectedness into that existing dialog.
- **Execution type (F4.2.1/TE-12):** additive nullable `execution_type`
  (check `manual | extension_fill | auto_verify | document_attach`,
  null ⇒ `manual`) on SOP task definitions inside versions AND stamped
  additively onto generated case tasks. R6 renders a badge and stamps the
  value — **no automated execution runs in this epic.** Keep the union in
  one shared TypeScript module.
- **Draft state (F4.2.1, PM round-4):** save-as-draft for the SOP wizard.
  Implement as ONE additive org-scoped table (e.g. `sop_template_drafts`:
  `id`, `org_id`, optional template head reference, wizard payload
  `jsonb`, `updated_by`, timestamps; admin-member RLS + grants). Drafts
  persist across sessions, are visible/editable by other admin users, are
  deleted on successful publish, and are NEVER read by `pickTemplate()`
  or the readiness projection. E1.7b publish semantics are unchanged.
- **Minimum-content publish lint (F4.2.1, PM round-4):** Publish (and the
  wizard's Review step) rejects an SOP with zero tasks, any task with
  zero steps, or blank/default "New step" labels. Pure validation module
  - unit tests; enforce client-side in the wizard AND in the publish
    service path.
- **Global-tier publish gate (F4.2.1, PM round-4):** publishing a change
  to a **global/shared** template (`org_id IS NULL` tier) shows a
  publish-diff preview and an explicit blast-radius confirmation before
  calling the unchanged publish RPC. Org-specific templates publish as
  today. No schema change — this is a dialog layer.
- **Accessible reordering (F4.2.1, PM round-4):** every task/step row in
  the wizard gets explicit move up/down buttons — keyboard-operable,
  labeled, proper focus management — alongside the existing drag.
  Reordering must be fully achievable without a pointer. Same pattern for
  the F4.2.5 queue-settings input ordering (TE-10 — no drag dependency
  there at all).
- **Template tier visibility (F4.2.1):** list rows and resolution surfaces
  show org-specific vs global/shared, matching the shipped
  `pickTemplate()` precedence; one-click "create org-specific override"
  from a payer's row.
- **Readiness (F4.2.2/TE-4):** pure projection — group active
  `payer_network_targets` by attached payer × state; Ready = every
  underlying target resolves to an active payer-specific SOP; generic
  fallback ⇒ "Needs SOP" with a creation link carrying the prefilled
  match key. Never persist a readiness boolean. Each payer row links to
  its existing scorecard; the scorecard gains a derived SOP-readiness
  indicator (same projection, no second formula).
- **Form readiness (F4.2.2/TE-16):** when the resolved SOP version has at
  least one `extension_fill` task, show the portal's mapping-coverage
  ratio beside Ready/Needs-SOP using the SAME pure `mappingCoverage`
  computation from `src/lib/payerScorecard.ts`, with a link into
  `/portals/$key/train`.
- **Reason codes (F4.2.3/TE-5):** additive org-scoped
  `denial_reason_codes` table (stable id, `org_id`, code, label,
  `is_system`, `is_active`, `created_by`, timestamps; case-insensitive
  uniqueness per org; admin insert/update, NO delete policy; explicit
  grants). Seed the six defaults for every org including the
  org-bootstrap path. Deactivated codes disappear from new-entry
  dropdowns but keep rendering on historical records.
- **Bulk generation entry (F4.2.4/TE-6/TE-14):** "Generate cases" from a
  payer's row opens the EXISTING E2.0 preview pre-scoped to that payer.
  Release configuration (all / none / subset by explicit provider
  selection, count cap, or location filter) narrows the confirmed set
  passed to the UNCHANGED E2.1 RPC; the E2.4 run record additively
  carries the release scope; unreleased candidates remain candidates in
  the next preview via existing dedupe. No parallel generator, no
  persisted "pending release" queue, no change to [r4]-locked
  candidate/dedupe/exclusion logic.
- **Queue settings (F4.2.5/TE-7):** additive `next_best_action_configs`
  table, `org_id` primary key, storing an exact permutation of the four
  fixed input keys (`follow_up`, `task_due`, `provider_start`,
  `launch_date`) + disabled subset, `updated_by`/`updated_at`. Validation
  rejects unknown/duplicate keys; no row ⇒ shipped default; Reset deletes
  the row after an audit write. Org-member read, admin write policies.
  **Integration point:** E4.1 already shipped the consumer seam — point
  `getQueueRankingConfigRaw()` in `src/services/queueRankingConfig.ts` at
  this table (it currently returns `null`); `resolveQueueRankingConfig` /
  `buildNextBestActions` need NO change. Keep the default + key union in
  one pure shared module.
- **Profile gating (F4.2.6/TE-13):** requirements are a governed key list
  (one pure module mapping keys to existing provider-profile fields — no
  free-text field paths), stored additively with the SOP version (same
  immutability as TE-12). The E2.0 preview's pure candidate filter gains
  the gate evaluation producing per-provider unmet-attribute reasons
  rendered like existing skip rows; gated providers are simply absent
  from the confirmed set — the E2.1 RPC is unchanged. Outreach task via
  the existing task-creation service, offered per blocked provider, never
  auto-created. No stored blocked state — re-derived every preview.
  **Blocked-provider visibility:** the F4.2.2 readiness surface shows the
  derived count of currently gated providers per payer × state, linking
  to the list with the exact missing attributes.
- **Form onboarding & test runner (F4.2.7/TE-17):** the four-step flow —
  capture (existing capture contract → org-scoped `proposed` field-map
  rows), train (existing `/portals/$key/train` deck), dry-run fill
  against the designated test provider, fix-and-re-run. Additive marker
  on `fill_sessions` (e.g. `is_test boolean DEFAULT false`) excluded from
  `firstPassRate` and every metric reader. The test provider is an
  ordinary `providers` row with an additive exclusion flag honored by ONE
  shared pure predicate used by queue/generation/scorecard derivations.
  Tighten `fieldsSkipped` from `unknown` to a structured
  `{selector, label, reason: "unmapped" | "empty_token"}[]` additively.
  **Fill-time re-capture:** during ANY fill (test or real), observed
  fields with no field map land as org-scoped `proposed` field-map rows
  through the same capture contract — never dropped. No new extension
  write endpoints; nothing is ever submitted to a payer from the runner.

## Scope boundaries (one-directional dependencies)

- **No automated execution.** `extension_fill` behavior activates in E4.3,
  `document_attach` in E4.5, `auto_verify` in R7. This epic captures and
  stamps metadata only.
- **E4.1 is merged context** — its reducer, touch machinery, and the
  `queueRankingConfig` read seam are read-only except for the ONE
  authorized change: pointing `getQueueRankingConfigRaw()` at the new
  table.
- **No mid-flight SOP version adoption** (PM round-4): in-flight cases
  stay grandfathered on the version they generated with. Do not build an
  adopt/migrate path or mutate generated case tasks on publish.
- No payer-portal credential storage. No new SOP model or versioning
  semantics (E1.7b Model A locked). No changes to generation rules.
