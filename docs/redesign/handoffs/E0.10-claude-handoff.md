## Build order (mirrors TE-6)

Separate additive migration files in `supabase/migrations/`
(`YYYYMMDDHHMMSS_<slug>.sql`), each also applied to the hosted project via MCP
`apply_migration`:

1. **FK indexes** (F0.10.4 / TE-4) — use the _pinned_ list in TE-4, not the
   feature's provisional list (`state_licenses.provider_id` is already covered
   by a composite index — do not add it).
2. **NOT-NULL `CHECK ... NOT VALID`** per column (F0.10.1 / TE-1):
   `contracts.group_id`, `contracts.payer_id`,
   `provider_facility_assignments.provider_id` / `.facility_id`,
   `state_licenses.provider_id`.
3. **State-format `NOT VALID` checks** (F0.10.2 / TE-2) — TE-2's column set is
   authoritative, including its exclusions (`launches.state`, the wildcard
   fields `mso_routing_rules.state` / `sop_templates.state`, and the
   `provider_groups.states` array) and the NULL-allowing form for nullable
   columns.
4. **Structural constraints** (F0.10.3 / TE-3) — task owner CHECK, partial
   unique on `provider_facility_assignments(provider_id) WHERE is_primary`,
   `UNIQUE (org_id, track, label)` on `status_configs`. NO constraint on
   `mso_routing_rules` — the routing-rule uniqueness is deferred out of E0.10
   (PM decision; see TE-3 and `CLARIFICATIONS_NEEDED.md` [e0.10]). Uniques are
   **audit-first**: PostgreSQL has no `UNIQUE ... NOT VALID`, so run the
   duplicate audits before adding them.
5. **Audits then `VALIDATE`** (TE-7): run the BD-1 row counts and the BD-2
   `SELECT DISTINCT state` audit via MCP `execute_sql` BEFORE any
   `VALIDATE CONSTRAINT`. Validate only constraints whose audit returns zero
   offending rows; otherwise leave `NOT VALID` and report the counts in the PR.
   Do NOT write remediation/backfill UPDATEs without reporting first — data
   changes to live rows need PM sign-off.
6. **Service layer** (F0.10.5 / TE-5): `normalizeStateCode` helper in
   `src/lib/`, a small shared Postgres-error → domain-message translator in
   `src/lib/`, tightened service payloads. No hook, component, or route
   changes.
7. Regenerate `src/integrations/supabase/types.ts` via MCP
   `generate_typescript_types` (expect a near-empty diff) and update the
   affected rows' notes in `docs/data-model/table-register.md` in the same PR.

## Hard boundaries (do not cross)

- Additive only: no renames, drops, or restructures; never edit existing
  migration files.
- Out of scope (per the epic's Non-Goals): any `mso_routing_rules` constraint,
  state checks on wildcard fields (`mso_routing_rules.state`,
  `sop_templates.state`), provider↔group M:N /
  `provider_group_assignments`, `credential_cases` unique-key changes,
  `provider_groups` address/contact normalization,
  `credential_cases.credentialing_status_id` NOT-NULL,
  `audit_log.entity_type` CHECK, the optional FK indexes and
  `provider_groups.states` element check flagged in TE-2/TE-4 — include none
  of these without explicit PM direction.
- Never edit epic files, `CLARIFICATIONS_NEEDED.md`, or their frontmatter.
- No new UI, routes, or dependencies.

## Verification & gates (TE-8)

- DB-level constraint checks: for each new NOT-NULL / CHECK / UNIQUE, prove
  via MCP `execute_sql` that the bad row is rejected and the good row is
  admitted (use rollback-wrapped probes; do not leave test rows in hosted
  data). Record the probe results in the PR description.
- Unit tests for `normalizeStateCode` and the error translator.
- Gates before requesting review: `npm run lint`, `npm run test`,
  `npx tsc --noEmit`, `npx prettier --check .`, migration dry-run.

## Reporting back

In the PR description: per-feature FR trace, the BD-1/BD-2 audit results
(counts + distinct state values), which constraints were validated vs left
`NOT VALID`, and any deviation from the epic with its reason. Devin reviews
the PR against the epic and merges into `redesign` when aligned.
