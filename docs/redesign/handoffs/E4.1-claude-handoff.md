## Mission

Implement epic **E4.1 — Structured Touches & Follow-up Cadence** from
`docs/redesign/E4.1-structured-touches.md` (frontmatter `reviewed: true` —
you are cleared to build). Read the whole epic first; its
`## 5. Technical Considerations & Enablers` section (TE-1 … TE-10) pins the
authoritative schema, reducer, and access-control mechanics — build from the
TE sections, not from the feature prose alone. In particular:

- **Seven fixed touch types** (F4.1.1/TE-1): Call→`call`, Portal
  Check→`portal`, Email→`email`, Fax→`fax`, CAQH Update→`caqh_update`,
  Provider Outreach→`provider_outreach`, Internal Sync→`internal_sync`.
  Widen the TS union, DB check, label map, icon map, and tests additively.
  Existing `mail` rows and historical outcomes render unchanged — no
  backfill. The inward-facing pair must be distinguishable in reporting
  projections (payer-facing vs internal).
- **Follow-up carry-forward is the round-3 CRITICAL fix** (F4.1.2/TE-2): a
  date-less touch **carries the prior active follow-up forward** — it never
  clears it. Clearing is ONLY the explicit entry-form control, expressed as
  an additive `clears_follow_up boolean NOT NULL DEFAULT false`. The pure
  reducer resolves, latest-first by `(touch_date DESC, created_at DESC,
id DESC)`, the first touchpoint that set a date or has
  `clears_follow_up = true`. (If any older text mentions "null clears the
  follow-up", the carry-forward rule wins.)
- **Outcome/disposition is optional** (F4.1.4/TE-10): Successful /
  Attempted / No Response / Error / Other (+ required single-line context
  for Other), mapped onto the existing channel-aware `outcome` field —
  nullable, never synthesized to satisfy a legacy constraint (TE-1).
- **Recipient/contact capture is optional but PROMINENT** (F4.1.5/TE-10):
  additive nullable `recipient_name` + `recipient_contact` columns on
  `touches`, rendered on the log row, filterable.
- **Overdue follow-ups surface in the E2.3 queue** (F4.1.3/TE-5): extend the
  pure `buildNextBestActions` to accept the org-level E4.2 F4.2.5 config as
  an input. With no saved config, ship the default comparator: overdue
  follow-ups above deadline-only rows, ties by earliest deadline. Invalid or
  incomplete config falls back atomically to the shipped default. Load config
  once per org via hook/service; never read config inside the reducer; never
  persist `is_overdue`, priority, or queue rows — fully derived.
- **Bulk logging** (F4.1.7/TE-6/TE-10): one service call writes one touch row
  per selected case + one `TOUCH_LOGGED` audit row per touch (a batch summary
  may be additional, never a replacement); case selection is bounded to
  org-scoped case IDs server-side. The bulk confirmation offers a **one-click
  link to the filtered view of exactly the affected cases**; the exception
  fix is an appended per-case touch with the true outcome — never an edit.
- **Corrections are appends** (Edge Cases/TE-10): additive
  `corrects_touch_id` reference; the log renders the pair (original marked
  "corrected by …"); no UPDATE path exists, including for admins.
- **Source/channel explicit per row** (TE-6): `manual` (webapp) vs
  `extension`; keep `communication_event_id` fan-out semantics.
- **CSV export** (Compliance): reuse the existing export machinery,
  org-scoped, carrying type/outcome/recipient/source/dates/actor.
- **Action Bridge** (F4.1.8/TE-11 — PM round-4): every E4.0 pipeline
  transition dialog gains an **optional, off-by-default** "Log this as a
  touch" section (type preselected where sensible, context prefilled from
  the transition/reason). One confirm writes the pipeline history row (via
  the UNCHANGED `advance_payer_pipeline` RPC) then the touch row. A failed
  transition writes NO touch; a failed touch after a successful transition
  surfaces a retry-touch-only error path — never roll back or duplicate the
  transition. Client-side composition only: no new RPC, no schema change to
  the pipeline.

## Scope boundaries (one-directional dependencies)

- **E4.2 F4.2.5 queue settings UI is NOT built here.** F4.1.3 CONSUMES the
  org-level config through a read seam (validated shape + shipped default
  when absent) so E4.2 can plug the admin surface in later without reworking
  the reducer. Do not build any admin/config UI in this epic.
- **F4.1.6 attachments depend on E4.5's document store**, which has NOT been
  built. Per TE-10: build the additive `touch_documents` link table only
  with/after E4.5, or gate the feature behind its presence. For this PR,
  implement the entry-point seam (attach/link affordance may be hidden or
  disabled) and flag in the PR description that F4.1.6's full path activates
  with E4.5 — do not invent a parallel document store.
- **E4.0 is merged context** — the payer pipeline, its RPC, and its history
  table are read-only context here. Do not modify `advance_payer_pipeline`
  or `payer_pipeline_history`. **Exception (TE-11):** you ARE authorized to
  extend `src/components/cases/pipeline/PipelineDialogs.tsx` /
  `PayerPipelineControl.tsx` with the F4.1.8 optional touch section — that
  bridge only; pipeline semantics, edges, and the RPC stay untouched.
- Recurring/scheduled cadences, inbox ingestion, reporting dashboards, and
  the payer-contact directory/CRM are explicitly out of scope (Non-Goals).

## Hard guardrails (do not deviate — flag in the PR instead of guessing)

- **Never edit** epic files, `CLARIFICATIONS_NEEDED.md`, frontmatter, or
  anything in `docs/redesign/` — they are reviewer-owned. Your changes live
  in `src/`, `supabase/migrations/` (new files only), seeds, tests, and the
  table register.
- **Protected files:** never modify existing migrations,
  `src/lib/sopResolver.ts`, `tailwind.config.*`, `src/components/layout/*`,
  `src/components/ui/*`; `src/types/index.ts` is additive only.
- **`touches` is append-only** — no UPDATE/DELETE path in code or policy,
  ever, including corrections. Same for `status_history`, `audit_log`, and
  `payer_pipeline_history`.
- **Do not touch the internal status machine or the payer pipeline** —
  `status_configs`, `credentialing_status_id`, `status_history`,
  `updateCaseStatus`, and E4.0's `advance_payer_pipeline` stay exactly as
  they are.
- **Supabase access:** only via `src/services/*` importing
  `@/integrations/supabase/externalClient`; components → hooks → services;
  every query org-scoped; every insert sets `org_id`. `CaseTouchesPanel`
  owns composition; `useLogTouch` owns mutation/invalidation; `touches.ts`
  sets `org_id`, `case_id`, coordinator, `entry_type = 'touchpoint'`, and
  source (TE-3). Extend the shared `Touch`/`TouchType`/`TouchInput`
  contracts — no R6-only duplicate types.
- **Invalidation** (TE-4): a successful insert invalidates
  `["touches", orgId]`, the case key, audit-log keys, and the
  next-best-action key if not already reached by the touch-prefix
  invalidation.
- **No new dependencies. No `any`. No default exports. No `console.log` /
  `TODO`.** No new `/api` write routes — the extension contract stays as-is.
- **Scope:** exactly F4.1.1–F4.1.8 + TE-1…TE-11 (with the F4.1.6 gating
  above). Do not refactor adjacent code. If something in the epic seems
  contradictory or blocked, implement what is unambiguous and flag the rest
  in the PR description — do not invent scope or stall.
- **Migrations:** repo-first new files + identical SQL applied to hosted via
  MCP `apply_migration`; regenerate `src/integrations/supabase/types.ts` via
  MCP after DDL; never edit the baseline or any applied migration. Update
  `docs/data-model/table-register.md` in the same PR.
