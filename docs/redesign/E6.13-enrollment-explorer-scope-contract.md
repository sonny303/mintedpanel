## Features

### F6.13.1 — Curate actual products and group intent

- **Description:** Internal admins maintain named payer products and group/product/state targets.
- **Persona:** P1.
- **Benefit hypothesis:** Explicit catalog identity prevents a payer name or target from becoming an enrollment assertion.
- **Acceptance criteria:**
  - Product identity is global `(payer_id, product_key)` with no product org ownership. Existing payer visibility remains global-or-same-org; no guessed products or wildcard products are seeded.
  - Targets record intent only. Specialists and restricted clients cannot curate, publish, or revoke.
  - Every mutation rechecks actor, selected audience, staff allowlist, membership, organization and relevant group ownership; tables and RPCs deny direct anonymous/authenticated access.
- **Test/data scenario(s):** TS-167, TS-170.

### F6.13.2 — Save a concrete scope and immutable revision atomically

- **Description:** Specialists capture a selected product and exact facility at the six-part enrollment grain.
- **Persona:** P1, P2.
- **Benefit hypothesis:** A complete identity and retained history make corrections reviewable without altering the existing case workflow.
- **Acceptance criteria:**
  - Scope identity `(org, provider, group, product, facility, state)` is non-null, unique, and same-org coherent. Incomplete capture remains in triage.
  - Initial scope, first revision, non-null current pointer, source links, and existing `audit_log` event commit together or roll back together. The deferred composite current-revision FK references a nonpartial unique key and rejects cross-wiring.
  - Later saves append a revision and audit, then advance the pointer. Expected-revision contention commits once and returns HTTP 409 to the stale writer.
  - Reapplication increments a small cycle number; prior dates, references, sources and publication history remain immutable. Dates are captured explicitly, never inferred from `created_at`.
  - Retro is `unknown`, `not_supported`, or documented with one bounded day/date value and basis; it never implies billing readiness.
- **Test/data scenario(s):** TS-167, TS-168.

### F6.13.3 — Preserve source lineage and visible partial mappings

- **Description:** A staff-only keyset queue exposes unresolved cases/facts and incomplete product/location mappings.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Staff can resolve missing scope information without silently turning legacy approvals into product or facility coverage.
- **Acceptance criteria:**
  - Links preserve complete identity and the exact material snapshot/fingerprint defined in the parent contract. Bind, publish and read validate canonical sources; expiry, correction, deletion or changed facility membership invalidates assurance.
  - Source links have no FK/cascade to cases/facts. Existing case purge remains available and historical lineage remains intact.
  - Mapping completeness considers product and facility coordinates; a first link does not resolve other coordinates. Missing configuration remains visible. Targets/assignments are candidate mapping inputs, never proof.
  - All links for candidate revisions are validated, including deleted or earlier-page sibling sources. Distinct canonical sources are batched once per validation set; a real 100,000-record workload is measured without claiming an unmeasured latency target.
  - No queue materialization, automatic conversion/publication, case-key change, case status/history write, or report writeback occurs.
- **Test/data scenario(s):** TS-168.

### F6.13.4 — Publish summaries separately from reviewed proof

- **Description:** An internal admin publishes a revision's client-safe summary and separately binds reviewed document evidence.
- **Persona:** P1, P5.
- **Benefit hypothesis:** Clients can see honest progress while approval assertions remain tied to evidence of the exact scope.
- **Acceptance criteria:**
  - Pending summaries, safe blocker and action owner may publish without approval proof. Drafts and never-published scopes remain private; published test providers remain excluded from client DTOs.
  - Proof pins an existing immutable document version, scope revision, actual-byte SHA-256, evidence kind and explicit supported fields. Org/provider/group/case compatibility, supersession and applicable expiry are checked.
  - Approved product/location assurance, current effective dates and retro require applicable supported proof. License PSV supports only license; acknowledgement supports receipt only. No independent four-eyes requirement is invented.
  - Publication and revocation append events. A stale last publication exposes only a safe `Needs verification` shell with prior status labeled historical; current verified fields and proof are withheld. Retracted summaries deny visibility when no authorized publication remains.
  - Client DTOs exclude internal notes, source IDs/fingerprints, staff IDs, document storage paths and hashes.
- **Test/data scenario(s):** TS-169, TS-170.

### F6.13.5 — Reauthorize and stream pinned proof

- **Description:** A dedicated authenticated proxy delivers currently authorized published proof bytes.
- **Persona:** P5.
- **Benefit hypothesis:** Group or publication revocation takes effect before a new download can begin.
- **Acceptance criteria:**
  - The service computes SHA-256 from stored bytes at publication and checks the pinned digest before delivery; caller-supplied digests are not trusted.
  - Immediately before emitting bytes, recheck verified actor/context revision, selected audience/org/group grants, publication/retraction and document version. Denial emits no proof bytes.
  - Response is `Cache-Control: no-store`, with a safe attachment name and identifiers-only audit. No signed/public URL, browser storage access, new storage model, or persisted export artifact is created.
  - Native role/transaction tests and application route/service tests distinguish SQL authority from actual byte hashing and HTTP behavior. Existing org isolation and E6.12 denied surfaces remain covered.
- **Test/data scenario(s):** TS-170.

### E6.14 API integration contract

All paths below begin with `/api/enrollment-explorer`. The browser sends its
bearer token and explicit `x-org-id`, `x-enrollment-audience`, and
`x-minted-context-revision` headers. The server independently verifies them.
Wire inputs live in `src/types/index.ts`; the browser adapter is
`src/lib/enrollmentExplorerApi.ts` and the server boundary is
`src/server/enrollmentExplorerRoutes.ts`.

| Method/path                                | Input or result                                                                                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/catalog?groupId=`                    | Staff product/target choices; target intent remains private.                                                                                      |
| GET `/unresolved?groupId=&cursor=&limit=`  | Staff source queue; optional group filter within the selected org, base64url JSON cursor, source fingerprints and incomplete mapping coordinates. |
| POST `/products`, `/targets`               | Admin curation of explicit catalog identity or group/product/state intent.                                                                        |
| POST `/scopes`                             | `EnrollmentScopeSaveInput`: concrete scope keys, expected revision, captured revision and source links. Returns scope/revision/cycle identifiers. |
| GET `/scopes/:scopeId`                     | Staff detail or restricted client-safe published detail, according to selected audience.                                                          |
| POST `/scopes/:scopeId/summary`            | Admin publishes the specified revision.                                                                                                           |
| POST `/proofs`                             | Admin supplies scope/revision/document version, evidence kind, supported fields and reason; server computes the stored-byte digest.               |
| POST `/publications/:publicationId/revoke` | Admin retracts the named publication with a reason.                                                                                               |
| GET `/proofs/:publicationId/download`      | Authenticated, reauthorized, no-store byte stream; never a signed URL.                                                                            |

Client input does not carry actor identity. Expected-revision or stale-data
conflicts return 409; callers reload before another capture attempt. E6.14
owns context-aware query hooks, cancellation, and reachable staff controls;
it must preserve the adapter's context-change checks through body completion.
