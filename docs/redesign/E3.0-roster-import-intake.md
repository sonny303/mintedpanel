# E3.0 — Bulk Roster Import: Intake, File Gate & Async Processing

## Purpose and Context

R5's goal is maximizing good data at implementation-onboarding time without
manual row-by-row entry. This epic delivers the **ingestion front door**: a
role-gated CSV upload surface (internal power-user tool + a guarded org-rep
version inside the onboarding wizard's Provider Roster section), a strict file
gate (downloadable template, exact header matching), and asynchronous
processing sized for 5–10k-row rosters (`[r5]` decisions 1, 3, 4, 12).

Nothing in this epic writes to the live provider/group/facility tables —
uploads land as **staged import runs** that E3.1's preview/commit flow acts
on (`[r5]` decision 10). No external API calls occur during import (`[r5]`
decision 11).

## Personas Empowered

- **P1 Credentialing Manager** — runs internal bulk imports for rapid
  implementation and client migration.
- **P5 Practice / Organization Owner** (org rep) — uploads their own roster
  through the onboarding wizard, shifting data-entry burden off the internal
  team.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only: an `import_runs` table (org-scoped, RLS) holding run
  state (`uploading | scanning | ready_for_review | committed | failed |
cancelled`), the raw parsed rows (staging grain, e.g. `import_rows`), row
  counts, and the actor; plus the error-report payload. Table register
  updated in the same PR.
- CSV parsing must not require a new dependency — reviewer to verify a
  compliant approach exists with the current toolchain, or name the gap.
- Async processing: the reviewer verifies the buildable mechanism for
  background parsing/scanning within the existing Supabase/Nitro stack
  (chunked client-side parse + batched RPC inserts vs server-side job) and
  records it in §5. Whatever the mechanism, the UI must not block on a
  10k-row file.
- Security/compliance: rosters contain PII (names, NPIs, licenses). Staged
  rows are org-scoped RLS like everything else; never store full SSNs
  (`ssn_last4` only — the front gate structurally blocks any full-SSN column;
  a value-level guard rejects the row for any dashed `XXX-XX-XXXX` value or
  bare 9-digit token outside the TIN column, never persisting or echoing the
  value — reject, never truncate/derive a last-4 from a full SSN);
  staged rows and uploaded artifacts are purged when a run is committed or
  cancelled.

## Features

### F3.0.1 — Role-gated upload surfaces

- **Description:** Two entry points to the same import pipeline: an internal
  staff import tool (power-user: full column visibility, raw error detail)
  and a streamlined org-rep version inside the onboarding wizard's Provider
  Roster section, with tighter guardrails and simplified error handling.
  Per the PM's [r5-review] decision, v1 gating is **role-based**: the power
  tool is admin-gated (`useIsAdmin`); the org rep is provisioned as an admin
  of their own org (invite flow itself is out of E3.0 scope). A dedicated
  platform-staff flag is a deferred follow-up.
  The internal tool **supersedes the legacy direct-commit importer at
  `/admin/import`** — retire or redirect that route in the build (TE-8);
  never leave both write paths reachable.
- **Persona:** P1 (internal), P5 (org rep).
- **Benefit hypothesis:** internal teams migrate clients fast; org reps
  self-serve their roster without needing the power tool.
- **Acceptance criteria:**
  - The internal tool is reachable only by org-admin-role users (role-gated
    v1; platform-staff flag deferred); the org-rep surface lives in the
    onboarding wizard's Provider Roster section and shows the streamlined
    flow.
  - The legacy `/admin/import` route no longer offers a direct live-table
    commit path (retired or redirected to the new surface).
  - Both surfaces feed identical validation and staging — no divergent data
    paths.
- **Test/data scenario(s):** TS-58, TS-59.

```gherkin
Feature: Role-gated import surfaces
  Scenario: Org rep gets the guarded flow
    Given an org rep is in the onboarding wizard's roster section
    When they open the CSV upload
    Then they see the streamlined uploader with the template download
    And they do not see the internal power-user import tooling
```

### F3.0.2 — Template download + header front gate

- **Description:** A downloadable `.csv` template rendered directly inside
  the upload screen. The definitive header list (single source shared by the
  template and the gate):

  ```
  group_name, group_tin, provider_first_name, provider_middle_initial,
  provider_last_name, npi, caqh_id, specialty, taxonomy_code,
  license_number, license_state, license_issue_date,
  license_expiration_date, ssn_last4, date_of_birth, facility_name,
  facility_street, facility_city, facility_state, facility_zip
  ```

  (`provider_middle_initial`, `caqh_id`, and `license_issue_date` added per
  PM sign-off 2026-07-13 — all three map to existing `providers` columns.)

  (`ssn_last4` and `date_of_birth` included per the PM's [r5-review]
  decision; `ssn_last4` is 4-digit-validated with a non-echoing error — a
  pasted full SSN in that field rejects the row.) Row grain: one row per
  provider × group × facility — the same grain E3.1's five-part dedupe
  consumes; a provider under two facilities is two rows, and multi-license
  providers repeat rows per license. Uploaded files whose column headers do
  not match this list exactly are rejected immediately at the front gate.

- **Persona:** P1, P5.
- **Benefit hypothesis:** a strict, visible contract turns "mystery
  spreadsheet" failures into a one-click fix (download, refill, re-upload).
- **Acceptance criteria:**
  - The template is downloadable from both upload surfaces.
  - Header mismatch (missing, extra, or renamed columns) rejects the file
    before any row processing, naming the offending headers.
  - Non-`.csv` files and files above the size limit are rejected client-side
    with clear messaging.
- **Test/data scenario(s):** TS-58.

```gherkin
Feature: Front gate
  Scenario: Renamed column rejects at the gate
    Given a roster file whose "NPI" column is titled "npi number"
    When P1 drops it on the upload zone
    Then the file is rejected before any rows are scanned
    And the message names the mismatched header and offers the template
```

### F3.0.3 — Drag-and-drop upload UX with explicit states

- **Description:** A clearly defined drop zone with visual hover/active
  states, a progress bar for large files, and explicit
  Uploading → Scanning → Success/Failed states; a pre-processing preview of
  the parsed columns plus sample rows before the run is queued.
- **Persona:** P1, P5.
- **Benefit hypothesis:** users always know where the import is and what
  went wrong, instead of a spinner and a prayer.
- **Acceptance criteria:**
  - Drop-zone highlights on file hover; falls back to a file picker.
  - The four states render distinctly; Failed states say why and how to fix.
  - A columns-and-sample-rows preview renders before processing starts.
- **Test/data scenario(s):** TS-58, TS-59.

### F3.0.4 — Asynchronous scan sized for 5–10k rows

- **Description:** Row scanning (parse, type/format validation, required
  fields, full-SSN value rejection) runs in the background; the user can
  leave and return to a run in progress. Good rows stage; bad rows collect
  into a downloadable error report (`[r5]` decision 6) without failing the
  run.
- **Persona:** P1.
- **Benefit hypothesis:** thousand-row rosters import without freezing the
  browser or losing partial progress.
- **Acceptance criteria:**
  - A 5–10k-row file completes scanning without blocking the UI; progress is
    visible and survives navigation away/back.
  - Rows with blocked errors are excluded and enumerated in a downloadable
    error report (row number, column, reason).
  - Completed scans land the run in `ready_for_review` for E3.1 — nothing is
    written to live tables.
- **Test/data scenario(s):** TS-60.

```gherkin
Feature: Partial success with an error report
  Scenario: Good rows stage, bad rows report
    Given a 60-row roster where 3 rows have a malformed NPI
    When the scan completes
    Then 57 rows are staged and the run is ready for review
    And the error report download lists the 3 rows with column and reason
```

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-13 against the live schema
(`20260704210000_baseline_live_schema.sql` — `providers`,
`provider_facility_assignments`, `provider_groups`, `audit_log`), the existing
import path (`src/lib/csv.ts`, `src/lib/csvImport.ts`,
`src/services/importCommit.ts`, `src/routes/admin.import.tsx`), the role model
(`src/lib/permissions.ts`, `src/lib/auth-store.ts` `AppRole`), the onboarding
wizard (`src/routes/onboarding.wizard.tsx`, `src/lib/onboardingProgress.ts`),
the Nitro server (`src/server/api.ts`), `docs/data-model/table-register.md`,
`docs/redesign/seed-universe.md` (TS-58–TS-60), and `uiux-component-guide.md`.
The headline finding: **a synchronous, live-writing CSV import already exists**
(the "Epic 2c" admin tool) — E3.0 reuses its pure parser/coercion core and
supersedes its write path with a staged, async, single-run pipeline._

- **TE-1 — CSV parsing needs no new dependency; a compliant parser already
  ships (constraint discharged).** `src/lib/csvImport.ts` already contains a
  hand-rolled RFC4180 parser (`parseCsvRecords` → quoted fields, embedded
  commas/newlines, `""` escapes, CRLF/LF, 1-based physical line numbers on
  every record), header normalization (`normalizeHeader`), and reusable
  coercions (`coerceDate`, `coerceBool`, `coerceStringArray`) with a
  line/column error record shape (`CsvImportError` — file/line/column/message).
  No CSV package is a dependency and none is warranted (AGENTS.md
  "no new deps"). **Enabler:** extract the record parser + coercions into a
  shared pure module (or import them directly) and build the E3.0 single-file
  roster parser on top. Do NOT reuse the existing _forgiving_ package mapper
  wholesale: `csvImport.ts` tolerates missing/extra columns (it reads by name
  and skips absent ones), which is the opposite of F3.0.2's **exact** front
  gate — the gate is a new, stricter header check (see TE-4).
- **TE-2 — Additive staging schema: `import_runs` + `import_rows` (staging
  layer, not ledger).** Two additive org-scoped tables, both `org_id NOT NULL`
  with the standard member-SELECT / writer-INSERT RLS + explicit `GRANT`s
  (AGENTS.md) and FK cover indexes per the E0.10
  `20260710140000_fk_index_coverage.sql` convention:
  - `import_runs` — the run header (a working table, so UPDATE is allowed):

    ```
    id uuid pk, org_id uuid NOT NULL -> organizations,
    created_by uuid NOT NULL,
    source text NOT NULL CHECK (source IN ('internal','onboarding')),
    file_name text,
    state text NOT NULL DEFAULT 'uploading'
      CHECK (state IN ('uploading','scanning','ready_for_review',
                       'committed','failed','cancelled')),
    total_rows int, staged_rows int, error_rows int,
    error_report jsonb, created_at/updated_at timestamptz
    ```

    The run row is the **durable progress ledger** that makes "leave and
    return to a run in progress" (F3.0.4) work — progress is server-persisted,
    never in-memory.

  - `import_rows` — one row per parsed source line:

    ```
    id uuid pk, org_id uuid NOT NULL, run_id uuid NOT NULL -> import_runs,
    line int NOT NULL, raw jsonb NOT NULL, mapped jsonb,
    row_state text CHECK (row_state IN ('staged','error')),
    error_column text, error_reason text, created_at timestamptz,
    UNIQUE (run_id, line)
    ```

    `raw`/`mapped` hold the parsed cells (PII — see TE-6/TE-7), never a full
    SSN. **These are working (create/scan/discard) tables, not the append-only
    ledger** — they are DELETEd on commit/cancel (TE-7), so they take the
    `support` status in the register, not `ledger`.

  - Migration is additive, applied repo + hosted per
    `docs/migration-baseline.md`, regenerates
    `src/integrations/supabase/types.ts`, and adds both register rows **in the
    same PR** (AGENTS.md). E3.1 owns `providers.verification_state` and reads
    `ready_for_review` runs — it does not re-create these tables.
- **TE-3 — Async mechanism: chunked client parse + batched staging RPC, with
  the run row as the ledger (no new infra).** There is **no general
  server-side job runner** in the stack — Nitro (`src/server/api.ts`) is a
  stateless fetch router, and the only Deno edge function today is
  `supabase/functions/invite-member` (no pg_cron, no worker queue). The
  buildable, layering-compliant mechanism (components → hooks → services →
  Supabase): parse the file in the browser in bounded chunks off the main
  thread, and `INSERT` staged/error rows through a batched RPC (working name
  `stage_import_rows(run_id, rows jsonb[])`, SECURITY DEFINER, org-checked,
  ~500-row batches) while advancing `import_runs.state`/counts. Because
  progress lives on the run row + `import_rows` (not React state), navigating
  away and back **resumes by re-reading the run** (F3.0.4 AC). The scan itself
  (type/format validation, required fields, SSN rejection) reuses the TE-1
  coercions. The UI must never block on a 10k-row file — chunking + a progress
  bar bound to staged/total counts satisfies this. _Alternative recorded, not
  recommended for R5:_ a Deno edge function doing the whole parse server-side
  (mirrors `invite-member`) removes the browser from the loop but adds a new
  deploy/runtime surface and a service-role write path — heavier than the R5
  volume needs. If the PM later wants the browser fully out of the loop, that
  is the upgrade path.
- **TE-4 — Front gate is a new exact-match check ahead of any row work.**
  F3.0.2: reject header mismatch (missing / extra / renamed) before scanning,
  naming the offending headers, and offer the template. Build it as a pure
  function comparing `parseCsv(text).headers` (normalized) to the canonical
  template header list; non-`.csv` type and an over-limit size are rejected
  client-side at file pick (the existing `<input accept=".csv,text/csv">` in
  `admin.import.tsx` is the precedent; add an explicit size ceiling). The
  template download reuses `src/lib/csv.ts` `downloadCsv`/`toCsv` (already the
  roster-export mechanism). **Recommended canonical roster columns** (the wide
  single-file spec covering group + provider + location, from the existing
  provider/facility field sets):

  ```
  group_name, group_tin, provider_first_name, provider_last_name, npi,
  specialty, taxonomy_code, license_number, license_state,
  license_expiration_date, facility_name, facility_street, facility_city,
  facility_state, facility_zip
  ```

  The final column list is the author's/PM's call; the enabler is that every
  column maps to an existing `providers` / `provider_groups` / `facilities`
  field (no new provider columns needed).

- **TE-5 — Role-gating maps onto the existing membership-role model; the two
  surfaces are buildable, but "external org rep" identity is not yet in the
  model (open question).** Roles are the `AppRole` union of `specialist`,
  `billing`, and `admin` (`src/lib/auth-store.ts`); gating helpers are `useIsAdmin` /
  `useCanWrite` (`src/lib/permissions.ts`). Buildable interpretation of
  F3.0.1: the **internal power-user tool** is an admin-gated surface (the
  successor to `admin.import.tsx`, `useIsAdmin`); the **guarded org-rep
  surface** is a section inside the onboarding wizard
  (`src/routes/onboarding.wizard.tsx`, alongside the `providers` section in
  `ONBOARDING_SECTIONS`) with the streamlined error flow. Both feed the same
  parse/stage pipeline (TE-1/TE-2), satisfying "no divergent data paths".
  **Caveat for the PM (open question 1):** today _every_ authenticated user is
  an internal team member (org memberships with specialist/billing/admin);
  there is no authenticated "external org rep" identity — external parties
  interact only through the E0.5 _unauthenticated_ tokenized capture surface.
  So "the org rep uploads their own roster" is, in the current model, still an
  internal operator using the streamlined wizard surface. A truly
  external-rep-operated upload would need an external-user auth model (not in
  scope here). This does not block building the two surfaces; it bounds what
  "org rep" means until that model exists.
- **TE-6 — SSN safety at the gate.** Providers store `ssn_last4` only
  (AGENTS.md; `providers.ssn_last4`, and `csvImport.ts` already enforces
  `SSN4_RE = /^\d{4}$/`). The scan must **reject any SSN-like value** (a
  9-digit / `NNN-NN-NNNN` value — never truncate or derive a last-4 from it)
  rather than stage it: treat a full
  SSN as a blocked-row error (row joins the error report; the value is never
  echoed in the error message), and only ever persist a validated last-4 from
  the dedicated `ssn_last4` column into `import_rows.mapped`. Never derive a
  last-4 from an unconsented full SSN. No full SSN ever reaches
  `import_rows.raw` either — strip at parse before the row is written.
- **TE-7 — Staged PII lifecycle.** `import_rows` holds names, NPIs, licenses
  (PII) — org-scoped RLS like every other table, writer-only INSERT, and
  **purged on terminal transitions**: committing (E3.1) or cancelling a run
  DELETEs its `import_rows` (the "staged rows and uploaded artifacts are purged
  when a run is committed or cancelled" constraint). Uploaded file bytes are
  never persisted server-side (parsed in the browser, TE-3) — there is no
  Storage bucket in scope, which also sidesteps the E1.8 document-storage gap.
- **TE-8 — Reconcile the legacy import tool (the one real tech-debt decision).**
  `admin.import.tsx` + `src/services/importCommit.ts` are a pre-redesign
  ("Epic 2c") synchronous, best-effort, three-file package importer that writes
  **directly to live tables** through the create services with a
  `reference_only` toggle — no staging, no async, no dedupe, no preview
  summary. Shipping E3.0/E3.1 alongside it leaves two divergent write paths for
  the same job. **Recommendation:** the E3.0 internal power tool _supersedes_
  the legacy admin importer — retire or redirect `admin.import.tsx` to the new
  surface in the E3.0 PR (the pure `csvImport.ts` core is retained per TE-1;
  the live-writing `importCommit.ts` commit path is what E3.1's staged commit
  replaces). Do not silently leave both reachable. Recorded as the migration
  note for the E3.0 build.
- **TE-9 — UI from the approved inventory; no new primitive expected.** Drop
  zone = native HTML drag-and-drop events on a styled container + a hidden
  `<input type="file">` fallback (the `admin.import.tsx` file-picker pattern);
  states Uploading → Scanning → Success/Failed render as a status pill
  (`badge`, status-semantic colors only) + a progress element bound to
  staged/total; columns + sample-rows preview uses the `table` primitive with
  custom cells; errors and the run summary use designed panels (not raw text).
  Feature components live in `src/components/import/` (or similar), never in
  `ui/`/`layout/`; nothing here touches the shell. Follow the design-system
  token deltas (4px pill radius, 6px cards) per `uiux-component-guide.md`
  §"UX design system alignment". If a genuinely new primitive is needed (e.g.
  `progress`), add it via the shadcn generator in its own commit and log it —
  none is expected.
- **TE-10 — Authoritative table trace (AGENTS.md requires one).** Reads:
  `provider_groups` (group_name/TIN resolution at preview), `import_runs`,
  `import_rows`, `memberships`/role (gating). Writes: `import_runs` (INSERT +
  state/count UPDATE — a working table, so UPDATE is allowed here, unlike the
  ledger), `import_rows` (INSERT at scan, DELETE at commit/cancel), `audit_log`
  (append-only run lifecycle events: upload created, scan completed, run
  cancelled). **No writes to `providers`/`facilities`/assignments in E3.0** —
  that is E3.1's staged commit. Reconciled against the register: both
  `import_*` tables are new (added in this PR); all others have register rows.
- **TE-11 — Verification gates.** Unit-test the pure additions (exact
  header-gate function, SSN rejection, per-line error assembly, chunk
  batching boundaries) in the `src/lib/` suite; e2e for **TS-58**
  (template download + renamed-header/non-CSV reject + valid-file
  columns/sample preview + Uploading→Scanning→Success), **TS-59** (org-rep
  streamlined wizard upload stages identically), and **TS-60** (async scan of
  a large file survives navigation; good rows stage, run lands
  `ready_for_review`, error report lists bad rows with column + reason) — all
  L1 uploads of generated CSVs, **no new baseline fixtures** per the
  seed-universe coverage table. Must pass `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`, and the touched Playwright specs.
  Migration applied repo + hosted with the types regen in the same PR.

### Likely tech debt / risk to contain

- **Two import surfaces.** The single biggest risk (TE-8): leaving the legacy
  live-writing importer reachable next to the staged pipeline. Retire/redirect
  it in the build, don't defer.
- **Client-driven async honesty.** With the browser driving chunked inserts
  (TE-3), a closed tab mid-scan leaves a run stuck in `scanning`. Make the run
  resumable (re-open resumes from the last staged line via `import_rows`) and
  surface a stale-run state rather than a silent hang; do not fabricate a
  server worker to hide it.
- **Front-gate strictness vs. real spreadsheets.** Exact header matching
  (F3.0.2) is intentional but brittle against BOMs, trailing blank columns,
  and casing. Normalize defensively (BOM strip, trim, case-fold — the
  `normalizeHeader` posture) so a cosmetically-different-but-correct header
  isn't a false reject, while still rejecting genuinely missing/extra columns.
- **Size limit is a real ceiling.** A 10k-row roster is a few MB; set the
  client size limit comfortably above that and make the reject message state
  the limit, so a legitimate large roster isn't blocked by an arbitrary cap.
