# E3.0 — Bulk Roster Import: Intake, File Gate & Async Processing

## Purpose and Context

R5's goal is maximizing good data at implementation-onboarding time without
manual row-by-row entry. This epic delivers the **ingestion front door**: a
role-gated CSV upload surface (internal power-user tool + a guarded org-rep
version inside the E0.8 onboarding wizard's CSV placeholder), a strict file
gate (downloadable template, exact header matching), and asynchronous
processing sized for 5–10k-row rosters (`[r5]` decisions 1, 3, 4, 12).

Nothing in this epic writes to the live provider/group/facility tables —
uploads land as **staged import runs** that E3.1's preview/commit flow acts
on (`[r5]` decision 10). No external API calls occur during import (`[r5]`
decision 11).

## Personas Empowered

- **P1 Credentialing Manager** — runs internal bulk imports for rapid
  implementation and client migration.
- **P5 Practice / Organization Owner** (org rep) — uploads their own roster
  through the onboarding wizard, shifting data-entry burden off the internal
  team.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only: an `import_runs` table (org-scoped, RLS) holding run
  state (`uploading | scanning | ready_for_review | committed | failed |
cancelled`), the raw parsed rows (staging grain, e.g. `import_rows`), row
  counts, and the actor; plus the error-report payload. Table register
  updated in the same PR.
- CSV parsing must not require a new dependency — reviewer to verify a
  compliant approach exists with the current toolchain, or name the gap.
- Async processing: the reviewer verifies the buildable mechanism for
  background parsing/scanning within the existing Supabase/Nitro stack
  (chunked client-side parse + batched RPC inserts vs server-side job) and
  records it in §5. Whatever the mechanism, the UI must not block on a
  10k-row file.
- Security/compliance: rosters contain PII (names, NPIs, licenses). Staged
  rows are org-scoped RLS like everything else; never store full SSNs
  (`ssn_last4` only — reject/truncate any SSN-like column at scan time);
  staged rows and uploaded artifacts are purged when a run is committed or
  cancelled.

## Features

### F3.0.1 — Role-gated upload surfaces

- **Description:** Two entry points to the same import pipeline: an internal
  staff import tool (power-user: full column visibility, raw error detail)
  and a streamlined org-rep version inside the onboarding wizard's CSV
  section (E0.8 F0.8.4 placeholder goes live), with tighter guardrails and
  simplified error handling.
- **Persona:** P1 (internal), P5 (org rep).
- **Benefit hypothesis:** internal teams migrate clients fast; org reps
  self-serve their roster without needing the power tool.
- **Acceptance criteria:**
  - The internal tool is reachable only by authenticated internal staff; the
    org-rep surface lives in the onboarding wizard and shows the streamlined
    flow.
  - Both surfaces feed identical validation and staging — no divergent data
    paths.
- **Test/data scenario(s):** TS-58, TS-59.

```gherkin
Feature: Role-gated import surfaces
  Scenario: Org rep gets the guarded flow
    Given an org rep is in the onboarding wizard's roster section
    When they open the CSV upload
    Then they see the streamlined uploader with the template download
    And they do not see the internal power-user import tooling
```

### F3.0.2 — Template download + header front gate

- **Description:** A downloadable `.csv` template (the recommended column
  spec covering group, provider, and location data — TIN, group name,
  provider name, NPI, specialty, license number/state, facility name/address)
  rendered directly inside the upload screen. Uploaded files whose column
  headers do not match the template exactly are rejected immediately at the
  front gate.
- **Persona:** P1, P5.
- **Benefit hypothesis:** a strict, visible contract turns "mystery
  spreadsheet" failures into a one-click fix (download, refill, re-upload).
- **Acceptance criteria:**
  - The template is downloadable from both upload surfaces.
  - Header mismatch (missing, extra, or renamed columns) rejects the file
    before any row processing, naming the offending headers.
  - Non-`.csv` files and files above the size limit are rejected client-side
    with clear messaging.
- **Test/data scenario(s):** TS-58.

```gherkin
Feature: Front gate
  Scenario: Renamed column rejects at the gate
    Given a roster file whose "NPI" column is titled "npi number"
    When P1 drops it on the upload zone
    Then the file is rejected before any rows are scanned
    And the message names the mismatched header and offers the template
```

### F3.0.3 — Drag-and-drop upload UX with explicit states

- **Description:** A clearly defined drop zone with visual hover/active
  states, a progress bar for large files, and explicit
  Uploading → Scanning → Success/Failed states; a pre-processing preview of
  the parsed columns plus sample rows before the run is queued.
- **Persona:** P1, P5.
- **Benefit hypothesis:** users always know where the import is and what
  went wrong, instead of a spinner and a prayer.
- **Acceptance criteria:**
  - Drop-zone highlights on file hover; falls back to a file picker.
  - The four states render distinctly; Failed states say why and how to fix.
  - A columns-and-sample-rows preview renders before processing starts.
- **Test/data scenario(s):** TS-58, TS-59.

### F3.0.4 — Asynchronous scan sized for 5–10k rows

- **Description:** Row scanning (parse, type/format validation, required
  fields, SSN-like column rejection) runs in the background; the user can
  leave and return to a run in progress. Good rows stage; bad rows collect
  into a downloadable error report (`[r5]` decision 6) without failing the
  run.
- **Persona:** P1.
- **Benefit hypothesis:** thousand-row rosters import without freezing the
  browser or losing partial progress.
- **Acceptance criteria:**
  - A 5–10k-row file completes scanning without blocking the UI; progress is
    visible and survives navigation away/back.
  - Rows with blocked errors are excluded and enumerated in a downloadable
    error report (row number, column, reason).
  - Completed scans land the run in `ready_for_review` for E3.1 — nothing is
    written to live tables.
- **Test/data scenario(s):** TS-60.

```gherkin
Feature: Partial success with an error report
  Scenario: Good rows stage, bad rows report
    Given a 60-row roster where 3 rows have a malformed NPI
    When the scan completes
    Then 57 rows are staged and the run is ready for review
    And the error report download lists the 3 rows with column and reason
```

- **TE-1 — Async mechanism (the decision this epic delegates to §5): chunked
  client-side parse + batched PostgREST inserts. A server-side job is NOT
  buildable without new infrastructure.** Grounds: the app deploys as nitro
  on Vercel serverless (`docs/phase-0-audit.md` §1; `vercel.json` is `{}` —
  default request-scoped function lifetimes), and the repo has no job queue,
  worker, cron, or Supabase Edge Function anywhere — a "background" server
  job would die with its request or require new infra, a new dependency in
  all but name. The browser path is sufficient: the hand-rolled RFC4180-ish
  parser already exists and is tested (`parseCsvRecords`/`parseCsv`,
  `src/lib/csvImport.ts`); parsing 10k rows is sub-second, and the dominant
  cost is network writes, which are already async. Mechanism: (1) create the
  `import_runs` row (`state 'uploading'`), parse + front-gate client-side,
  render the columns/sample preview (F3.0.3), flip to `scanning`; (2)
  validate rows in chunks of ~500 with an `await` yield between chunks (keeps
  the main thread free — no Web Worker needed; note it as a fallback only if
  profiling disagrees), inserting each validated chunk into `import_rows` via
  ONE PostgREST `.insert(rows)` per chunk (a single multi-row INSERT is one
  atomic statement; ~10–20 requests for 5–10k rows; no RPC needed — RLS
  enforces org/role on the plain insert and scan-time rows are independent);
  (3) after each chunk, update the run's `staged_row_count` /
  `error_row_count` — progress is therefore READ FROM THE DB, so any screen
  and a returning user render it (TanStack Query, short refetch interval
  while `scanning`); (4) on completion flip to `ready_for_review` — nothing
  touches live tables (E3.1's contract). **"Survives navigating away"
  (TS-60):** the scan loop must live OUTSIDE component lifecycle — a
  module-scoped task or app-level mutation, never an effect in the route
  component — so in-SPA navigation never aborts it. A hard reload/tab close
  DOES abort it (the `File` handle is gone): the run is then stale in
  `scanning`. Handle honestly: when the import surface loads, offer stale
  `scanning` runs (no chunk progress for e.g. 15+ minutes) a one-click "mark
  failed" that purges rows per TE-3 (client-triggered cleanup; there is no
  pg_cron/TTL infra and adding one is out of scope). Re-upload restarts
  cleanly.
- **TE-2 — Staging schema sketch** (additive; repo + hosted per
  `docs/migration-baseline.md`; types regen + two `table-register.md` rows in
  the same PR):

  ```
  import_runs (
    id uuid PK DEFAULT gen_random_uuid(),
    org_id uuid NOT NULL → organizations ON DELETE CASCADE,
    filename text NOT NULL,
    source text NOT NULL CHECK (source IN ('internal','wizard')),  -- which surface; same pipeline (F3.0.1)
    state text NOT NULL DEFAULT 'uploading'
      CHECK (state IN ('uploading','scanning','ready_for_review','committed','failed','cancelled')),
    total_rows integer,                       -- known after parse
    staged_row_count integer NOT NULL DEFAULT 0,
    error_row_count integer NOT NULL DEFAULT 0,
    created_by uuid NOT NULL → profiles,
    created_at timestamptz NOT NULL DEFAULT now(),
    completed_at timestamptz
  )

  import_rows (
    id uuid PK DEFAULT gen_random_uuid(),
    run_id uuid NOT NULL → import_runs ON DELETE CASCADE,
    org_id uuid NOT NULL → organizations ON DELETE CASCADE,  -- denormalized so RLS filters directly (E2.0/E1.5 precedent)
    row_number integer NOT NULL,              -- 1-based source line (header = 1), the csvImport.ts convention
    raw jsonb NOT NULL,                       -- normalized-header → cell map; NEVER an SSN-shaped value (TE-5)
    status text NOT NULL CHECK (status IN ('staged','error')),
    error_column text, error_reason text,
    CHECK (status <> 'error' OR error_reason IS NOT NULL),
    UNIQUE (run_id, row_number)
  )
  ```

  RLS + grants (the `case_generation_exclusions` / `payer_network_targets`
  shape): ENABLE RLS on both; member SELECT
  (`org_id IN (SELECT user_org_ids())`); **admin-only writes**
  (`user_role(org_id) = 'admin'` — import is bulk-consequence like exclusions,
  the [r4-review] Q2 precedent, and both intended surfaces are admin personas:
  internal staff, and the org rep who is the org's admin via
  `create_organization`). `import_rows` INSERT/DELETE WITH CHECK additionally
  requires the run to belong to the same org
  (`EXISTS (SELECT 1 FROM import_runs r WHERE r.id = run_id AND r.org_id =
import_rows.org_id)`) — the stricter-WITH-CHECK posture of the E1.5/E2.0
  migrations. Grants: `GRANT SELECT, INSERT, UPDATE ON import_runs`;
  `GRANT SELECT, INSERT, DELETE ON import_rows` (DELETE is deliberate — TE-3);
  `REVOKE ALL ... FROM anon` on both (the `20260710120000` posture). No UPDATE
  grant on `import_rows` in this epic — if E3.1's conflict resolution needs
  one it adds it additively. FK cover indexes per the E0.10 `20260710140000`
  convention (`run_id` is covered by the unique's leading column; add
  `org_id` + `created_by` on runs, `org_id` on rows). These are browser-RLS
  surfaces with **no `/api` route** (locked decision 2 — no consumer pulls
  one), so the /api org-isolation gate does not cover them; RLS is verified by
  a rollback-wrapped SQL probe instead (TE-10).

- **TE-3 — Purge is a real DELETE, and that is a documented exception.**
  Recent redesign tables deliberately carry no DELETE grant
  (`case_generation_exclusions`, `case_generation_runs`); `import_rows` is
  the opposite case: ephemeral PII transport, not history, and `[r5]`
  decision 10 + this epic REQUIRE purge. Rows purge
  (`DELETE ... WHERE run_id = X`) when a run reaches `committed` (E3.1),
  `cancelled`, or `failed`; the `import_runs` row itself PERSISTS as the
  durable record (who/when/counts/state) and is never deleted. The AGENTS.md
  append-only rule names `touches`/`status_history`/`audit_log` only —
  untouched. Audit: one `writeAudit` row per run lifecycle transition (CREATE
  on run creation; UPDATE on ready_for_review/failed/cancelled, counts in the
  payload; the purge rides the same row) — **ids + counts ONLY, never row
  contents**, since `audit_log` is append-only forever and must not become
  the PII store the purge just emptied. The existing `action_type` CHECK
  (CREATE/UPDATE/…/DELETE after `20260705190000` + `20260712150200`) covers
  all of this — no CHECK-widening migration. Also: with the TE-1 mechanism
  there is **no stored file artifact** — the raw CSV never leaves the browser
  (no Supabase Storage bucket exists in the repo and none is added);
  "uploaded artifacts" reduces to the staged rows + run counts, and the error
  report is likewise derived, not stored (TE-8).
- **TE-4 — CSV parsing: reuse `src/lib/csvImport.ts`; no new dependency,
  confirmed.** The RFC4180-ish parser (quoted fields, embedded
  commas/newlines, `""` escape, CRLF/LF, 1-based source lines) plus the
  shared validation regexes (`NPI_RE`, `SSN4_RE`, state/date coercers)
  already exist with a substantial vitest suite. E3.0 adds a NEW pure module
  (working name `src/lib/rosterImport.ts`) for the single-file roster spec
  that imports `parseCsvRecords` and the shared regexes — do not fork the
  parser, and do not entangle the legacy three-file package logic
  (`parseImportPackage`), which stays as-is. The exact-match front gate
  compares `parseCsv().headers` (already case/space-normalized) against ONE
  exported header-list constant; the downloadable template (F3.0.2) is
  GENERATED from that same constant (client-side Blob download) so spec and
  gate cannot drift. Missing, extra, and renamed headers each name the
  offending header in the rejection message (F3.0.2 AC).
- **TE-5 — SSN rule, stated precisely** (the epic's "reject/truncate any
  SSN-like column at scan time" needs sharpening — redline 5). Structurally,
  the exact-header gate means an SSN COLUMN can never reach the scan: any
  header outside the pinned spec rejects the whole file, and the spec
  deliberately carries NO SSN column — not even `ssn_last4` (E3.1's dedupe
  key is name + NPI + TIN + group + facility and needs no SSN; imported
  providers leave `ssn_last4` null, editable later through the roster form,
  which is already maxLength-guarded). The residual risk is SSN-shaped
  VALUES in permitted columns (e.g. full SSNs pasted into the license-number
  column). Scan-time rule: any cell matching a dashed SSN shape
  (`\d{3}-\d{2}-\d{4}`) in any column, or a bare 9-digit token in any column
  other than the TIN column (TINs are legitimately 9 digits), errors the row
  with `error_column` + reason, and the value is **never persisted** — not in
  `raw`, not in `error_reason`, not in the error report. Precedent: the
  existing `ssn_last4` validator's message deliberately omits the offending
  value (`src/lib/csvImport.ts` — "SSN last-4 must be exactly 4 digits")
  while the NPI message echoes it; follow the SSN precedent for anything
  SSN-shaped. Never "truncate" a full SSN into a last-4 — silently deriving
  and storing data the uploader did not mean to submit; reject the value.
- **TE-6 — Role gates and the two surfaces, as buildable today.** Roles are
  per-org memberships `admin|specialist|billing` (baseline
  `memberships_role_check`) — there is NO platform-level "internal Minted
  Panel staff" concept anywhere in the schema or code (repo-wide grep).
  F3.0.1's AC "reachable only by authenticated internal staff" is therefore

  power tool ships on an admin route; the org-rep surface is the streamlined

### Likely tech debt / risk to contain

- **Stale `scanning` runs** (tab closed mid-scan) are handled manually
  (TE-1); if orgs accumulate them, a TTL needs infra (pg_cron or richer
  cleanup) — keep the client-triggered cleanup honest rather than adding a
  fake "background job".
- **Two admin CSV imports** until the legacy `/admin/import` is retired
  (redline 4): different specs (three-file vs single-file) and semantics
  (direct commit vs staged). The legacy route stays URL-reachable per the
  redesign convention (`legacy-routes` e2e) but should not gain new nav
  visibility once the internal tool ships.
- **`import_rows.raw` is a jsonb of PII** (names, NPIs, licenses). RLS +
  purge are the controls; never add an `/api` route or extension read over
  it without its own gate assertions.

### Reviewer redlines (independent review per REVIEW-HANDOFF, 2026-07-13)

1. **blocker** — F3.0.1's AC "reachable only by authenticated internal
   staff" names a gate the data model cannot express: roles are per-org
   `admin|specialist|billing` (baseline `memberships_role_check`) and no
   platform-staff flag exists anywhere in schema or code. Needs the PM's
   mechanism (PM question 1) plus an AC amendment; TE-6 records the
   buildable v1 default.
2. **should-fix** — The Dependencies line "E0.8 (onboarding wizard CSV
   placeholder becomes the org-rep surface)" is stale: E1.0 replaced the
   E0.8 placeholders with the section registry and E1.8 activated all seven
   sections (`src/lib/onboardingProgress.ts` — no CSV section exists).
   Re-target to the wizard's Provider Roster section / a new registry entry
   per TE-6.
3. **should-fix** — F3.0.2's column list ("TIN, group name, provider name,
   NPI, specialty, license number/state, facility name/address") is
   indicative, but the exact-match gate needs a definitive header list, and
   the single-file grain must be defined (one row per provider × group ×
   facility; how multi-license providers are represented), because E3.1's
   five-part dedupe consumes exactly that grain. TE-4 pins the single-source
   constant mechanism; the author should pin the headers or explicitly
