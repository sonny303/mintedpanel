# E3.0 — Bulk Roster Import: Intake, File Gate & Async Processing

## Purpose and Context

R5's goal is maximizing good data at implementation-onboarding time without
manual row-by-row entry. This epic delivers the **ingestion front door**: a
role-gated CSV upload surface (internal power-user tool + a guarded org-rep
version inside the E0.8 onboarding wizard's CSV placeholder), a strict file
gate (downloadable template, exact header matching), and asynchronous
processing sized for 5–10k-row rosters (`[r5]` decisions 1, 3, 4, 12).

Nothing in this epic writes to the live provider/group/facility tables —
uploads land as **staged import runs** that E3.1's preview/commit flow acts
on (`[r5]` decision 10). No external API calls occur during import (`[r5]`
decision 11).

## Personas Empowered

- **P1 Credentialing Manager** — runs internal bulk imports for rapid
  implementation and client migration.
- **P5 Practice / Organization Owner** (org rep) — uploads their own roster
  through the onboarding wizard, shifting data-entry burden off the internal
  team.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Additive schema only: an `import_runs` table (org-scoped, RLS) holding run
  state (`uploading | scanning | ready_for_review | committed | failed |
cancelled`), the raw parsed rows (staging grain, e.g. `import_rows`), row
  counts, and the actor; plus the error-report payload. Table register
  updated in the same PR.
- CSV parsing must not require a new dependency — reviewer to verify a
  compliant approach exists with the current toolchain, or name the gap.
- Async processing: the reviewer verifies the buildable mechanism for
  background parsing/scanning within the existing Supabase/Nitro stack
  (chunked client-side parse + batched RPC inserts vs server-side job) and
  records it in §5. Whatever the mechanism, the UI must not block on a
  10k-row file.
- Security/compliance: rosters contain PII (names, NPIs, licenses). Staged
  rows are org-scoped RLS like everything else; never store full SSNs
  (`ssn_last4` only — reject/truncate any SSN-like column at scan time);
  staged rows and uploaded artifacts are purged when a run is committed or
  cancelled.

## Features

### F3.0.1 — Role-gated upload surfaces

- **Description:** Two entry points to the same import pipeline: an internal
  staff import tool (power-user: full column visibility, raw error detail)
  and a streamlined org-rep version inside the onboarding wizard's CSV
  section (E0.8 F0.8.4 placeholder goes live), with tighter guardrails and
  simplified error handling.
- **Persona:** P1 (internal), P5 (org rep).
- **Benefit hypothesis:** internal teams migrate clients fast; org reps
  self-serve their roster without needing the power tool.
- **Acceptance criteria:**
  - The internal tool is reachable only by authenticated internal staff; the
    org-rep surface lives in the onboarding wizard and shows the streamlined
    flow.
  - Both surfaces feed identical validation and staging — no divergent data
    paths.
- **Test/data scenario(s):** TS-58, TS-59.

```gherkin
Feature: Role-gated import surfaces
  Scenario: Org rep gets the guarded flow
    Given an org rep is in the onboarding wizard's roster section
    When they open the CSV upload
    Then they see the streamlined uploader with the template download
    And they do not see the internal power-user import tooling
```

### F3.0.2 — Template download + header front gate

- **Description:** A downloadable `.csv` template (the recommended column
  spec covering group, provider, and location data — TIN, group name,
  provider name, NPI, specialty, license number/state, facility name/address)
  rendered directly inside the upload screen. Uploaded files whose column
  headers do not match the template exactly are rejected immediately at the
  front gate.
- **Persona:** P1, P5.
- **Benefit hypothesis:** a strict, visible contract turns "mystery
  spreadsheet" failures into a one-click fix (download, refill, re-upload).
- **Acceptance criteria:**
  - The template is downloadable from both upload surfaces.
  - Header mismatch (missing, extra, or renamed columns) rejects the file
    before any row processing, naming the offending headers.
  - Non-`.csv` files and files above the size limit are rejected client-side
    with clear messaging.
- **Test/data scenario(s):** TS-58.

```gherkin
Feature: Front gate
  Scenario: Renamed column rejects at the gate
    Given a roster file whose "NPI" column is titled "npi number"
    When P1 drops it on the upload zone
    Then the file is rejected before any rows are scanned
    And the message names the mismatched header and offers the template
```

### F3.0.3 — Drag-and-drop upload UX with explicit states

- **Description:** A clearly defined drop zone with visual hover/active
  states, a progress bar for large files, and explicit
  Uploading → Scanning → Success/Failed states; a pre-processing preview of
  the parsed columns plus sample rows before the run is queued.
- **Persona:** P1, P5.
- **Benefit hypothesis:** users always know where the import is and what
  went wrong, instead of a spinner and a prayer.
- **Acceptance criteria:**
  - Drop-zone highlights on file hover; falls back to a file picker.
  - The four states render distinctly; Failed states say why and how to fix.
  - A columns-and-sample-rows preview renders before processing starts.
- **Test/data scenario(s):** TS-58, TS-59.

### F3.0.4 — Asynchronous scan sized for 5–10k rows

- **Description:** Row scanning (parse, type/format validation, required
  fields, SSN-like column rejection) runs in the background; the user can
  leave and return to a run in progress. Good rows stage; bad rows collect
  into a downloadable error report (`[r5]` decision 6) without failing the
  run.
- **Persona:** P1.
- **Benefit hypothesis:** thousand-row rosters import without freezing the
  browser or losing partial progress.
- **Acceptance criteria:**
  - A 5–10k-row file completes scanning without blocking the UI; progress is
    visible and survives navigation away/back.
  - Rows with blocked errors are excluded and enumerated in a downloadable
    error report (row number, column, reason).
  - Completed scans land the run in `ready_for_review` for E3.1 — nothing is
    written to live tables.
- **Test/data scenario(s):** TS-60.

```gherkin
Feature: Partial success with an error report
  Scenario: Good rows stage, bad rows report
    Given a 60-row roster where 3 rows have a malformed NPI
    When the scan completes
    Then 57 rows are staged and the run is ready for review
    And the error report download lists the 3 rows with column and reason
```

## Scenario/Seed Data Mapping

- TS-58 — Internal upload through the front gate (template, header reject,
  drop-zone states).
- TS-59 — Org-rep guarded upload from the onboarding wizard.
- TS-60 — Async scan of a large file: partial success + downloadable error
  report; run lands ready-for-review.

## Dependencies

- E0.8 (onboarding wizard CSV placeholder becomes the org-rep surface).
- E3.1 consumes `ready_for_review` runs (preview/commit).
- Existing org-scoped RLS + audit patterns.

## Out of Scope / Non-Goals

- Committing staged rows to live tables (E3.1).
- Dedupe/conflict review (E3.1).
- NPPES lookup or any external API during import (`[r5]` decision 11; NPPES
  aid is E3.2).
- CAQH ProView integration (later release).
- Standing/recurring import rules (`[r5]` decision 9 — one-shot only).
- Multi-file document batches (CV/license/DEA uploads) — flagged in `[r5]`
  decision 3 as "consider"; deferred to a document-management epic unless
  the PM pulls it in.
