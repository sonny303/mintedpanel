# E1.3 — Provider Roster

## Purpose and Context

The roster is the people leg of the scope: the clinicians who will be
credentialed. E1.3 delivers the "Providers" wizard section (E1.0 framework)
capturing the **CAQH-anchored provider baseline** (PM, 2026-07-10: "baseline =
what CAQH requires," minus full SSN, work history, and disclosure questions —
those live in CAQH itself, proxied by a current attestation). E1.3 also lands
the two R1 schema decisions locked on 2026-07-10: the **M:N provider↔group
model** (`provider_group_assignments` join table — a provider always belongs
to at least one group; no unassigned parking lot) and **license primary-source
verification (PSV)** — the team verifies each license against the state board
website (e.g. KS, NC lookups), and that verification must be recorded, not
lost. Licenses are hand-entered in v1 (locked); CAQH/NPPES import is R5.
This epic's join table is the prerequisite for the 4-part case key
(`provider × group × payer × state`) — the AGENTS.md 3-part case-key rule is
amended by the epic that implements generation (E2.3), not here.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — sole actor; enters providers from
  client intake documents and CAQH profiles. Internal-only wizard through
  Stage 3 (locked).
- **P7 Provider** — NOT an actor in R1 (reserved persona); their data is
  captured about them, not by them.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Test data uses [seed-universe.md](./seed-universe.md) orgs.
- Implementation dependencies (explicit):
  - `providers` table exists with name, credentials, DOB, `ssn_last4`,
    contact + home address, `npi`, `caqh_id`, `caqh_last_attested_date`,
    taxonomy/specialty (PT defaults), start date, education (degree, school,
    graduation date), malpractice (carrier, policy, coverage dates), status
    (default `onboarding`).
  - `state_licenses` table exists (provider FK, state, license_number,
    license_type full|compact, issue/expiration dates, status; unique on
    provider+state+number) — multiple licenses per provider supported today.
  - **New schema (additive migrations in this epic):**
    `provider_group_assignments` (org_id, provider_id, group_id, is_primary,
    start/end dates; unique provider+group) and PSV columns on
    `state_licenses` (`verified_status`, `verified_at`, `verified_by`,
    `verification_source_url`). `providers.gender` added (CAQH-required,
    missing today). Table-register rows updated in the same PR.
  - `providers.group_id` becomes a frozen primary-group mirror (locked
    decision); new reads go through the join table.
- Downstream field usage: NPI/license/CAQH attestation → E1.8 readiness and
  R9 Expiration Radar clocks; group assignments → 4-part case key (R4);
  malpractice dates → readiness "COI current"; PSV trail → readiness
  "license verified".

## Features

### F1.3.1 — Provider form (CAQH-anchored baseline)

- **Description:** The Providers section lists the org's roster and opens a
  form capturing: first/last name, credentials, gender, DOB, SSN last-4,
  email/phone, home address, Type 1 NPI, taxonomy code + specialty
  (PT-defaulted), start date, education (degree/school/graduation),
  malpractice block (carrier, policy number, coverage start/end), CAQH ID +
  last attestation date, and group assignment(s) (F1.3.2).
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** An application-ready provider profile is captured
  once at the CAQH grain, so downstream payer applications and readiness
  checks never require a data round-trip back to the client.
- **Acceptance criteria:**
  - Required to save: name, Type 1 NPI (10 digits, format-level validation
    only in v1), and ≥1 group assignment. All other CAQH-baseline fields are
    on the form as optional — absence never blocks save (readiness, not
    entry, is the gate: E1.8).
  - SSN captured as **last-4 only** (hard rule; full-SSN storage is the
    future Sensitive Identifiers Vault epic, R6/R7 — PM, 2026-07-10).
  - Work history and disclosure questions are NOT on the form; "CAQH
    attestation current" is the proxy (PM, 2026-07-10).
  - Provider status stays hidden; new providers default to `onboarding`
    (PM, 2026-07-10 — no status picker in R1).
  - List view: name, credentials, NPI, groups, license states, CAQH
    attestation date; edit from the list; soft delete via terminated status,
    never a row delete.
  - Component → Hook → Service → Supabase; `org_id` from the active org.
  - Derived progress: ≥1 provider → section Complete (E1.0 F1.0.2).
- **Test/data scenario(s):** TS-33 (new — see seed additions).

```gherkin
Feature: Provider capture
  Scenario: P1 adds Tree Hill's first clinician
    Given Tree Hill Sports Therapy has a saved group and facility
    When P1 adds a provider with name, NPI, CAQH ID, and assigns the group
    Then a providers row and a provider_group_assignments row exist
    And the Providers section shows Complete
    And the wizard shows the all-complete state with future-section preview
```

### F1.3.2 — Group assignment (M:N, required at entry)

- **Description:** Group selection is step one of the add-provider form: a
  required picker over the org's E1.1 groups, multi-select (M:N from day
  one), with one group marked primary. No provider exists unassigned
  (PM, 2026-07-10: "we should always have a group").
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** The case key's group leg is populated at entry, so
  R4 generation never encounters an orphan provider; multi-TIN clinicians
  are representable the day they appear.
- **Acceptance criteria:**
  - Required multi-select of active groups; exactly one marked `is_primary`.
  - Writes `provider_group_assignments` rows; `providers.group_id` mirrors
    the primary (frozen legacy mirror, no new readers).
  - Assignments editable after creation (add/remove group, change primary);
    removing the last assignment is blocked.
- **Test/data scenario(s):** TS-34 (new — multi-group provider on Shelby
  Sports Rehab, mirroring the PM's two-TIN therapist example).

```gherkin
Feature: Multi-group provider
  Scenario: The same therapist works under two TINs
    Given Shelby Sports Rehab has two provider groups
    When P1 adds a provider assigned to both groups with the first as primary
    Then two provider_group_assignments rows exist for the provider
    And the roster list shows both groups on the provider row
```

### F1.3.3 — State licenses with PSV trail

- **Description:** Each provider carries one or more state licenses
  (number, state, type full/compact, issue/expiration). Each license row
  records its **primary-source verification**: verified status, date,
  verifier, and the state-board lookup URL used — capturing the team's real
  workflow of confirming the license on the state website (KS, NC, etc.).
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** The one-time-per-cycle verification is recorded
  instead of living in someone's memory; readiness (E1.8) can require
  "license verified," and renewals re-trigger verification (R9 clocks).
- **Acceptance criteria:**
  - Multiple licenses per provider supported in the form (locked — test
    cases exist).
  - License fields map to `state_licenses`; PSV fields are the new additive
    columns (`verified_status unverified|verified|failed`, `verified_at`,
    `verified_by`, `verification_source_url`).
  - Marking verified requires the lookup URL; the verifier and timestamp are
    set automatically.
  - **Re-verification at renewal** (PM, 2026-07-10): editing a license's
    expiration date resets `verified_status` to `unverified` — feeds the R9
    Expiration Radar re-verify workflow later.
  - Expiration date drives the roster list's license summary (soonest
    expiry shown).
- **Test/data scenario(s):** TS-35 (new — license entry + PSV + renewal
  reset).

```gherkin
Feature: License primary-source verification
  Scenario: P1 verifies an NC license against the state board
    Given a provider with an NC license marked unverified
    When P1 records the NC board lookup URL and marks it verified
    Then the license shows verified with P1 and today's date
    When P1 later updates the license expiration date after renewal
    Then the license returns to unverified
```

### F1.3.4 — Roster summary on Account Detail

- **Description:** Account Detail gains a read-only roster summary (count,
  names, license states), consistent with the E1.1/E1.2 summaries; editing
  stays in the wizard.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** One glanceable client record; single editing
  surface preserved.
- **Acceptance criteria:**
  - Read-only list; empty state links to the wizard section.
- **Test/data scenario(s):** TS-33.

## Out of Scope / Non-Goals

- No full-SSN storage (Sensitive Identifiers Vault epic, R6/R7 — encrypted
  vault, role-gated reveal/fill, access audit).
- No work-history or disclosure-question capture (CAQH holds them; R5 import
  may pull them).
- No CAQH/NPPES automated import or NPI registry validation (R5).
- No bulk roster import (E1.3b, R5).
- No provider↔facility assignment (E1.4, R3).
- No document uploads (COI, diplomas) — future.
- No status picker or status workflow (default `onboarding`).
- No AGENTS.md case-key amendment here (lands with E2.3 generation dedup).
