# E6.8 — Payer Lifecycle Enabler

**Backend only. Zero rendered UI ships in this epic** — the only frontend code
is the service/hook seam the Payer Detail Manage tab and the close dialogs
(payer-and-cases design bundle) will call.

## Purpose and Context

The approved payer-and-cases design bundle
(`design-reference/payer-and-cases/`, reviewed in
`payer-cases-ui-build-handoff.md`) needs three backend capabilities E6.7
deliberately excluded:

1. **Archive/reactivate a payer.** With the catalog gone (E6.7) the payer
   list IS the org's network, so "remove from network" collapsed into
   Archive: leaves the list, reversible, nothing deleted, no new cases;
   blocked while open cases exist. Payer Setup gains a Show-archived toggle
   with Reactivate.
2. **Merge a payer in-app.** E6.7 kept merges platform-side; the design puts
   Merge on Payer Detail → Manage: pick the survivor, templates/issued
   IDs/open cases move, the loser's name becomes an alias on the survivor.
3. **Approved close "Didn't receive" escape.** E6.7 F6.7.1a made
   `set_case_status` hard-require exactly the IDs the payer expects at
   Approved. The approved product behavior (bundle screen 5) is that every
   expected ID has a per-field "Didn't receive" escape — approval proceeds
   and the enrollment reads **Awaiting ID** — because approval letters often
   arrive late and a missing ID must never block a close. This deliberately
   supersedes the E6.7 strict-require acceptance criterion; flagged to the
   PM in the handoff review and approved via the design bundle.

PM decisions carried forward from E6.7: no platform-role gating anywhere;
lifecycle actions serve the two trusted users; migrations additive-only.

## Personas Empowered

- P1 Credentialing Manager — retires payers she no longer works with,
  repairs duplicates by merging, and closes approved cases the day the
  letter arrives even when the ID hasn't.
- P2 Specialist — same paths via the future dialogs; nothing here is gated.

## Component & Data Constraints

- No UI components ship. `AGENTS.md` binds: additive migrations only;
  components → hooks → services → Supabase; the table-register row updates in
  the same PR as any schema/RPC change; no `any`; named exports. Workflow +
  merge gate: [README.md](./README.md); component rules (for the later UI
  slices, not this epic): [uiux-component-guide.md](./uiux-component-guide.md).
- Test/demo data uses seed-universe fixtures (Dillon cases, the seeded
  global payers) — see the Scenario/Seed Data Mapping below.
- Table trace — **read:** `payers`, `credential_cases`, `memberships`,
  `org_payer_assignments`; **written:** `payers` (additive `archived_at`
  column; UPDATE via RPC only), `sop_templates`, `payer_network_targets`,
  `enrollment_facts`, `credential_cases` (merge re-point via RPC),
  `org_payer_assignments` (merge dedupe), `audit_log` (append),
  `status_history` (append, via `set_case_status`). No renames, no deletes,
  no destructive DDL.
- Implementation dependency (not an assumption): the one-case-per
  `(provider_id, group_id, payer_id, state)` unique key (E2.1, migration
  `20260713150000`) constrains F6.8.2's case re-point.

## Features

### F6.8.1 — `archive_payer` / `reactivate_payer` RPCs

- **Description:** Additive `payers.archived_at timestamptz NULL` (archive
  is reversible, so it is NOT `status = 'retired'`; the E6.7 status domain
  and CHECK are untouched). SECURITY DEFINER RPCs, EXECUTE granted to
  `authenticated` only, writer-member check, audit append. `archive_payer`
  rejects with a named error when the payer has open (non-terminal) cases,
  returning the open-case count so the future dialog can say how many;
  `reactivate_payer` clears the flag. Archived payers are excluded from
  generation candidates, attach eligibility, and the default payer-list read
  (client filters on `archived_at IS NULL`; no RLS change).
- **Persona:** P1 Credentialing Manager.
- **User story:** As P1, I archive a payer we no longer work with so it
  stops appearing in my working list and can never generate new cases — and
  I can bring it back if we re-engage, with all its history intact.
- **Benefit hypothesis:** Gives the payer list an honest lifecycle without
  deletion risk; the open-cases block prevents orphaning in-flight work;
  reversibility removes the fear of the action.
- **Acceptance criteria:**
  - Archiving a payer with open (non-terminal) cases raises a named error
    carrying the open-case count; nothing is written.
  - Archiving a payer with none flags the row, appends an audit record, and
    the payer disappears from attach eligibility, generation candidates, and
    default list reads.
  - Reactivating clears the flag and restores all of the above.
  - Closed cases, templates, contacts, and issued IDs are untouched by both
    operations.
  - Migration is additive; `docs/data-model/table-register.md` updated in
    the same PR; both RPCs are audited and rejected for `anon`.
- **Test/data scenario(s):** TS-138 (seed-universe).

```gherkin
Feature: Archive and reactivate a payer
  Scenario: Archive blocked by open cases, then clean (TS-138)
    Given a seeded payer with one open Dillon case
    When P1 calls archive_payer for that payer
    Then a named error is raised carrying the open-case count and nothing is written
    When the case is closed and P1 archives again, then reactivates
    Then the archive succeeds with an audit row and the payer is excluded from
      attach, generation, and default list reads until reactivation restores it
```

### F6.8.2 — `merge_payer` RPC

- **Description:** SECURITY DEFINER `merge_payer(p_loser_id, p_survivor_id)`,
  authenticated + writer-member, single transaction: re-points
  `sop_templates.payer_id`, `payer_network_targets.payer_id`,
  `enrollment_facts.payer_id`, open `credential_cases.payer_id` (respecting
  the 4-part case unique key — a collision raises a named error listing the
  conflicting cases; nothing partial commits), and `org_payer_assignments`
  (dedupe on conflict) to the survivor; appends the loser's name to the
  survivor's `aliases[]`; marks the loser `status = 'merged'`,
  `merged_into_id = survivor`. Audit append with before/after. Rejects
  self-merge, merging into a merged/archived payer, and non-existent rows.
- **Persona:** P1 Credentialing Manager.
- **User story:** As P1, when I discover two payer records for the same real
  payer, I merge the duplicate into the right one and everything — templates,
  issued IDs, open cases — follows, so future searches find one payer.
- **Benefit hypothesis:** Duplicates are the known failure mode of manual
  payer creation (E6.7 guards reduce but cannot eliminate them); an in-app
  merge repairs them without a platform request, keeping the identity spine
  clean.
- **Acceptance criteria:**
  - Post-merge, the loser resolves to the survivor via the existing
    merged-successor seam and its name is in the survivor's `aliases[]`.
  - The 4-part case unique key is never violated: a colliding re-point
    raises a named error listing the conflicting cases and commits nothing.
  - The operation is all-or-nothing; the audit record carries both ids and
    the moved-row counts.
  - Self-merge, merge into a merged or archived payer, and unknown ids are
    each rejected with named errors.
- **Test/data scenario(s):** TS-139 (seed-universe).

```gherkin
Feature: Merge a duplicate payer
  Scenario: Duplicate merged into the survivor (TS-139)
    Given two payer rows for the same real payer, one a manual duplicate
    When P1 calls merge_payer(duplicate, survivor)
    Then templates, network targets, enrollment facts, and open cases re-point
      to the survivor in one transaction
    And the duplicate reads status merged with merged_into_id set and its name
      appears in the survivor's aliases
```

### F6.8.3 — Approved close: per-ID "Didn't receive" acknowledgment

- **Description:** Reissue `set_case_status` (same-name replacement, params
  extended additively) with `p_provider_id_missing_ack boolean` and
  `p_group_id_missing_ack boolean`. At Approved, each expected ID must be
  EITHER supplied OR explicitly acknowledged missing — silence still raises
  the E6.7 named error, so the strict guard is relaxed only by deliberate
  action. An acknowledged-missing provider ID leaves
  `enrollment_facts.payer_issued_id` NULL (the existing set-later path
  already supports back-fill); same for the group ID on
  `payer_network_targets`. The acknowledgment is recorded in the
  audit/status-history payload so "Awaiting ID" is derivable
  (expected + approved + NULL id).
- **Persona:** P2 Specialist (closes the case); P1 sees Awaiting-ID rows.
- **User story:** As P2, when the approval letter arrives without the ID (it
  often does), I close the case as Approved and explicitly note the ID
  didn't come — the enrollment reads Awaiting ID and I back-fill it later,
  instead of the close being blocked.
- **Benefit hypothesis:** Removes the close-blocking failure mode of E6.7's
  strict rule while keeping capture discipline: every missing ID is a
  recorded decision, never an accident.
- **Acceptance criteria:**
  - Approve with an ack and no ID succeeds and leaves the corresponding fact
    row NULL; the ack is present in the appended history/audit payload.
  - Approve with neither the expected ID nor its ack still raises
    `case_status_approved_needs_group_provider_id`.
  - Back-filling the ID later via the existing set-later path keeps working.
  - Non-Approved transitions and payers expecting no IDs are unaffected.
  - The reissue keeps the E6.7 signature compatible (additive params only).
- **Test/data scenario(s):** TS-140 (seed-universe).

```gherkin
Feature: Approved close with a Didn't-receive acknowledgment
  Scenario: Both-expected payer approved with one ID and one ack (TS-140)
    Given a case for a payer expecting both a group and a provider ID
    When P2 approves with neither ID nor acknowledgment
    Then the E6.7 named error is raised and nothing is written
    When P2 approves with the group ID and the provider-ID missing-ack
    Then the close succeeds, enrollment_facts.payer_issued_id stays NULL, and
      the acknowledgment is recorded in the status history
```

### F6.8.4 — Service/hook seam (no rendered UI)

- **Description:** `archivePayer` / `reactivatePayer` / `mergePayer` in
  `src/services/payers.ts`; mutation hooks in `src/hooks/useAdmin.ts` with
  query-key invalidation (payers, payer, org-payer-assignments, cases); the
  case-close service path carries the two ack flags; typed named errors
  surfaced (open-case count, merge collisions). Vitest coverage for the pure
  parts and the error mapping; governance tests keep payer writes RPC-only.
- **Persona:** P1/P2 indirectly — this is the contract the UI slices call.
- **User story:** As the UI build session, I call ready-made hooks with
  typed errors so the Manage tab and close dialogs are wiring, not backend
  work.
- **Benefit hypothesis:** Keeps the UI slices (handoff §3) pure-frontend,
  matching the E6.7 seam pattern that let PR 1 ship without UI churn.
- **Acceptance criteria:**
  - Services are the only Supabase callers; no component change ships.
  - Hooks invalidate the four query keys above on success.
  - Named errors from F6.8.1–F6.8.3 map to typed results with unit tests.
  - `npm run lint`, `npx tsc --noEmit`, and `npm run test` pass.
- **Test/data scenario(s):** exercised through TS-138–TS-140 at the service
  layer (unit tests over mocked RPC responses).
