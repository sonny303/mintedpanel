# E6.8 — Payer Lifecycle Enabler

**Backend only. Zero rendered UI ships in this epic** — the only frontend code
is the service/hook seam the Payer Detail Manage tab and the close dialogs
(payer-and-cases design bundle) will call.

## Purpose and Context

The approved payer-and-cases design bundle
(`docs/redesign/design-reference/payer-and-cases/`) needs three backend
capabilities E6.7 deliberately excluded:

1. **Archive/reactivate a payer.** With the catalog gone the payer list IS the
   org's network, so "remove from network" collapsed into Archive: leaves the
   list, reversible, nothing deleted, no new cases; blocked while open cases
   exist. Payer Setup gains a Show-archived toggle with Reactivate.
2. **Merge a payer in-app.** E6.7 kept merges platform-side; the design puts
   Merge on Payer Detail → Manage: pick the survivor, templates/issued
   IDs/open cases move, the loser's name becomes an alias on the survivor.
3. **Approved close "Didn't receive" escape.** E6.7 PR 1 (#237) made
   `set_case_status` hard-require exactly the IDs the payer expects at
   Approved. The approved product behavior (screen 5) is that every expected
   ID has a per-field "Didn't receive" escape — approval proceeds and the
   enrollment reads **Awaiting ID** — because approval letters often arrive
   late and a missing ID must never block a close.

PM decisions carried forward from E6.7: no platform-role gating anywhere;
duplicate/lifecycle actions are for the two trusted users; additive-only.

## Personas Empowered

- P1 Credentialing Manager — retires payers she no longer works with, repairs
  duplicates by merging, and closes approved cases the day the letter's
  status arrives even when the ID hasn't.

## Component & Data Constraints

- No UI components. `AGENTS.md` binds: additive migrations only; components →
  hooks → services → Supabase; table-register row updated in the same PR as
  any schema/RPC change; no `any`; named exports.
- Table trace — **read:** `payers`, `credential_cases`, `memberships`,
  `org_payer_assignments`; **written:** `payers` (additive `archived_at`
  column; UPDATE via RPC only), `sop_templates`, `payer_network_targets`,
  `enrollment_facts`, `credential_cases` (merge re-point via RPC),
  `org_payer_assignments` (merge/archive alignment), `audit_log` (append),
  `enrollment_facts`/case ID columns (escape flags per F6.8.3). No renames,
  no deletes, no destructive DDL.

## Features

### F6.8.1 — `archive_payer` / `reactivate_payer` RPCs

- **Description:** Additive `payers.archived_at timestamptz NULL` (archive is
  reversible, so it is NOT `status = 'retired'`; the status domain and CHECK
  from E6.7 are untouched). SECURITY DEFINER RPCs, EXECUTE `authenticated`
  only, writer-member check, audit append. `archive_payer` **rejects with a
  named error when the payer has open (non-terminal) cases**, returning the
  open-case count so the dialog can say how many; `reactivate_payer` clears
  the flag. Archived payers are excluded from generation candidates, attach
  eligibility, and the default payer list read (client filters on
  `archived_at IS NULL`; no RLS change).
- **Acceptance criteria:** archive with open cases → named error + count;
  archive with none → row flagged, audit row, reversible; reactivate restores
  it; existing closed cases/templates/IDs are untouched; migration is
  additive; table register updated in the same PR.

### F6.8.2 — `merge_payer` RPC

- **Description:** SECURITY DEFINER `merge_payer(p_loser_id, p_survivor_id)`,
  authenticated + writer-member, single transaction: re-points
  `sop_templates.payer_id`, `payer_network_targets.payer_id`,
  `enrollment_facts.payer_id`, open `credential_cases.payer_id` (respecting
  the `(provider_id, group_id, payer_id, state)` unique key — a collision
  raises a named error listing the conflicting cases; nothing partial
  commits), and `org_payer_assignments` (dedupe on conflict) to the survivor;
  appends the loser's name to the survivor's `aliases[]`; marks the loser
  `status = 'merged'`, `merged_into_id = survivor`. Audit append with
  before/after. Rejects self-merge, merging into a merged/archived payer, and
  non-existent rows.
- **Acceptance criteria:** post-merge the loser resolves to the survivor via
  the existing merged-successor seam; the 4-part case unique key is never
  violated; the operation is all-or-nothing; audit records both ids.

### F6.8.3 — Approved close: per-ID "Didn't receive" acknowledgment

- **Description:** Reissue `set_case_status` (same-name replacement, params
  extended additively) with `p_provider_id_missing_ack boolean` and
  `p_group_id_missing_ack boolean`. At Approved, each expected ID must be
  EITHER supplied OR explicitly acknowledged missing — silence still raises
  the E6.7 named error, so the strict guard is relaxed only by deliberate
  action. An acknowledged-missing provider ID leaves
  `enrollment_facts.payer_issued_id` NULL (the existing set-later path
  already supports back-fill); same for the group ID on
  `payer_network_targets`. The acknowledgment is recorded in the audit/status
  history payload so "Awaiting ID" is derivable (expected + approved + NULL
  id).
- **Acceptance criteria:** approve with ack + no ID succeeds and leaves the
  fact row NULL; approve with neither ID nor ack still raises
  `case_status_approved_needs_group_provider_id`; back-filling the ID later
  keeps working; non-Approved transitions unaffected.

### F6.8.4 — Service/hook seam (no rendered UI)

- **Description:** `archivePayer`/`reactivatePayer`/`mergePayer` in
  `src/services/payers.ts`, mutation hooks in `useAdmin.ts` with query-key
  invalidation (payers, payer, org-payer-assignments, cases); `updateCase`
  close path carries the two ack flags; typed named errors surfaced (open
  -case count, merge collisions). Vitest coverage for the pure parts.
