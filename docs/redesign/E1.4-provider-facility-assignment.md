# E1.4 — Provider–Facility Assignment

## Purpose and Context

Payer applications ask "where does this provider actually practice" — the
practice-location section is on nearly every commercial form, and the browser
extension fills it from assignment data. Today `provider_facility_assignments`
exists in the schema (provider × facility unique, org-scoped, single primary
per provider enforced by E0.10) but there is no wizard surface to manage it,
and the one field Sowmya computes by hand today — **the date the provider
started at each location** — is not captured at all. E1.4 adds the Assignments
wizard section (the first of the E1.0 disabled previews to go live), scoped by
the locked R3 decisions: group-scoped facility picker, one primary location per
provider across all groups, hand-picked assignments (no auto-assign), and a
required start date per assignment.

Implements the R3 PM decisions (2026-07-11): picker limited to the provider's
group(s)' facilities; single primary even across groups; hand-pick every time;
per-location start date is a tracked data point; no unassigned resting state —
every provider needs a group and at least one location.

## Personas Empowered

- **P1 Credentialing Manager** — assigns providers to locations while
  onboarding; the wizard actor.
- **P2 Credentialing Coordinator / Specialist** — reads assignments when
  filling payer forms (practice-location sections).
- **P10 Payer Portal / System Boundary** — consumes assignment data via the
  extension's practice-location fill.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: `provider_facility_assignments` exists
  (`id, org_id, provider_id, facility_id, created_at`; unique
  `(provider_id, facility_id)`; E0.10 enforces NOT-NULL + single `is_primary`
  per provider). E1.4 adds a `start_date` column (additive migration +
  table-register update).
- Implementation dependency: E1.3's `provider_group_assignments` determines
  which groups a provider belongs to; the facility picker derives from those
  groups' facilities (`facilities.group_id`).
- Date picker component: shared enabler (also needed by E1.3); if not yet
  built, this epic's section 5 must name it as an enabler, not an epic-local
  widget.

## Features

### F1.4.1 — Assignments wizard section

- **Description:** The E1.0 "Assignments" preview becomes an active wizard
  section listing every provider in the org with their assigned facilities and
  primary flag. Section progress is derived: Complete when every provider has
  ≥ 1 facility assignment; incomplete providers are listed first with an
  "Assign locations" affordance.
- **Persona:** P1.
- **Benefit hypothesis:** One place to see and close the "who works where" gap
  before readiness/case generation; replaces tribal knowledge.
- **Acceptance criteria:**
  - Section appears in the wizard after Providers, enabled (no longer a
    disabled preview).
  - Lists providers with facility chips; providers with zero assignments are
    flagged and sorted first.
  - Progress chip derives from data (no stored completion flags, E1.0 rule).
  - Empty state when the org has no providers points back to the Providers
    section.
- **Test/data scenario(s):** TS-39.

```gherkin
Feature: Assignments wizard section derives completeness
  Scenario: Provider with no location keeps the section incomplete
    Given Tree Hill Sports Therapy has two providers and one facility
    And only one provider has a facility assignment
    When P1 opens the Assignments wizard section
    Then the unassigned provider is listed first with an "Assign locations" action
    And the section shows In progress, not Complete
```

### F1.4.2 — Group-scoped assignment editor with per-location start date

- **Description:** Assigning locations for a provider shows only facilities
  owned by the provider's group(s) (never the whole org). Each selected
  facility requires a **start date** (date the provider began practicing
  there). Assignments are always hand-picked — no bulk/auto-assign in R3.
- **Persona:** P1.
- **Benefit hypothesis:** Matches contracting reality (a therapist practices
  at her group's clinics) and captures the start date Sowmya currently
  reconstructs by hand per provider per location for payer forms.
- **Acceptance criteria:**
  - Facility picker lists only facilities where `facilities.group_id` is one
    of the provider's assigned groups; other org facilities never appear.
  - Each assignment requires `start_date` before save.
  - Unchecking a facility removes the assignment (archive/history concerns are
    out of scope for R3 — assignments are current-state plus start date).
  - No "assign to all" bulk action.
- **Test/data scenario(s):** TS-39, TS-40.

```gherkin
Feature: Facility picker is scoped to the provider's groups
  Scenario: Two-group org shows only the provider's group's clinics
    Given Shelby Sports Rehab has Group 1 with one facility and Group 2 with two facilities
    And a provider assigned only to Group 1
    When P1 opens the assignment editor for that provider
    Then only Group 1's facility is offered
    And saving requires a start date for the selected facility
```

### F1.4.3 — Single primary practice location

- **Description:** Exactly one assignment per provider is marked primary —
  across all groups (payer forms ask for one primary practice location). The
  first assignment defaults to primary; changing primary is a one-click swap.
- **Persona:** P1, P2 (reads primary when filling forms).
- **Benefit hypothesis:** Deterministic answer for every form's
  "primary practice location" field; the DB already enforces the invariant.
- **Acceptance criteria:**
  - First saved assignment for a provider is automatically primary.
  - Marking another assignment primary demotes the previous one atomically.
  - A provider with assignments always has exactly one primary (E0.10
    constraint surfaces as a friendly error if violated).
  - Removing the primary assignment while others exist prompts to pick a new
    primary.
- **Test/data scenario(s):** TS-40.

```gherkin
Feature: One primary location per provider across groups
  Scenario: Primary swap when provider works in two clinics
    Given a provider with two facility assignments where Clinic A is primary
    When P1 marks Clinic B as primary
    Then Clinic B is primary and Clinic A is not
    And the provider still has exactly one primary assignment
```

## 5. Technical Considerations & Enablers

_Reviewer-owned (Devin). Verified against the baseline schema
(`20260704210000_baseline_live_schema.sql`), the E0.10 constraint migrations,
the table register, and the existing provider/assignment services on
2026-07-12._

- **TE-1 — Schema audit: `provider_facility_assignments.start_date` ALREADY
  EXISTS — do not migrate it.** The baseline `public.provider_facility_assignments`
  table is `(id, org_id, provider_id, facility_id, created_at, is_primary,
start_date, practice_frequency)`. Both the `start_date date` column and the
  `is_primary boolean DEFAULT false` column are already present. The epic
  body's implementation-dependency note ("E1.4 adds a `start_date` column
  (additive migration + table-register update)") is inaccurate — **no column
  migration or table-register schema change is required for `start_date`.**
  The field-capture work is UI + service + hook; TE-2/TE-3 name the actual
  additive enforcement/RPC needs. (Body text left unedited per the
  reviewer/author-section split; this note is the authoritative schema
  correction, mirroring E1.3 TE-1.)
- **TE-2 — Existing constraints enforce non-null identities and at most one
  primary — not exactly one.** E0.10 shipped validated non-null CHECKs for
  `provider_id`/`facility_id`
  (`20260710150000_not_null_check_floor.sql` +
  `20260710180000_validate_integrity_checks.sql`), the partial unique index
  `uq_provider_facility_assignments_one_primary` on `provider_id` for rows
  where `is_primary` is true, and the baseline
  `UNIQUE (provider_id, facility_id)`. The partial index prevents **two**
  primary rows but permits **zero**; F1.4.3's lower bound ("a provider with
  assignments always has exactly one primary") remains a service invariant.
  Auto-mark the first assignment primary, and require a successor before
  removing the current primary when other rows remain. `start_date` itself is
  still nullable: add a `CHECK (start_date IS NOT NULL) NOT VALID` so new/
  updated rows comply immediately, remediate legacy null dates through this
  UI, then validate the constraint.
- **TE-3 — Consolidate both existing write paths behind one assignment
  service.** Assignments are written today in
  `src/services/providers.ts#createProviderWithDetails` (bulk insert) **and**
  `src/services/launches.ts#assignProviderToFacility` (upsert); both write only
  `org_id`/`provider_id`/`facility_id`, silently dropping `is_primary` and
  `start_date`. E1.4 adds an assignment-management service (own file, e.g.
  `src/services/providerAssignments.ts`, one table/domain per AGENTS.md),
  routes both callers through it, and exposes `listOrgAssignments`,
  `setAssignments(providerId, rows)` (diff-based insert/update/delete,
  mirroring the license diff pattern), and
  `setPrimaryAssignment(providerId, assignmentId)`. The primary swap must be
  transactional: add an org-scoped `SECURITY DEFINER` RPC that verifies the
  caller/provider/target assignment, demotes the old row, and promotes the new
  row in one database transaction; fix `search_path` and grant execution only
  to `authenticated`. Two browser PostgREST calls are not atomic, and
  multi-row UPDATE ordering is not a safe uniqueness guarantee. Reads go
  through a new `useProviderAssignments` hook (`src/hooks/`) with an org-scoped
  `queryKeys` entry + shared invalidator; the wizard section is a component →
  hook → service → `externalClient` stack. The extension token path
  (`src/services/providerProfile.ts`, already selects
  `PROFILE_ASSIGNMENT_COLUMNS` for practice-location fill) is a **downstream
  reader** — do not fork it; it benefits automatically once `start_date`/
  `is_primary` are populated.
- **TE-4 — Group-scoped facility picker derives from E1.3's join table.** The
  picker (F1.4.2) lists facilities where `facilities.group_id ∈` the
  provider's groups, resolved via E1.3's `provider_group_assignments`
  (provider → group ids) → `facilities` filtered by `group_id` (+ `org_id`,
  `is_active`). Keep this as a **pure, unit-tested selector** in `src/lib/`
  (e.g. `assignmentScope.ts`: `facilitiesForProviderGroups(groups, facilities)`)
  fed by services; no Supabase in the module. `facilities.group_id` is
  nullable in the baseline — a facility with no group can never appear in any
  provider's picker (correct per the group-scoped decision); flag org-level
  ungrouped facilities as out of reach here (they belong to E1.2's group
  linkage, not E1.4).
- **TE-5 — Derived progress, no stored flags.**
  Section completeness (F1.4.1) is computed live — "every provider has ≥ 1
  assignment" — consistent with the E1.0 no-stored-completion rule; sort
  zero-assignment providers first from the same query. There is **no** stored
  wizard state. The list read should be a scoped projection (provider id/name +
  their assignment facility ids/primary/start_date), not `select("*")`, to stay
  off PHI-heavy provider columns (the `PROVIDER_LIST_COLUMNS` PHI-safe posture
  from E1.3 TE-6 applies).
- **TE-6 — Shared date-picker enabler (blocking UI dependency, shared with
  E1.3).** `start_date` capture needs a real date input, but the approved
  shadcn inventory in `uiux-component-guide.md` does **not** include `calendar`
  or `popover` today (both are named as "missing, add via the shadcn generator
  in its own commit"). E1.4 (or E1.3, whichever lands first) must add
  `src/components/ui/calendar` + `src/components/ui/popover` via the shadcn
  generator, in their own commit, listed as enablers — Radix `@radix-ui/react-popover`
  and `react-day-picker` are the standard shadcn deps (justify per the
  no-new-deps rule; both are the canonical shadcn choices, published well over
  the 7-day floor). Do **not** hand-roll an epic-local date widget. Store
  `start_date` as a plain `date` (no time/zone).
- **TE-7 — Removal semantics are current-state only (R3).** Unchecking a
  facility is a hard DELETE of the assignment row (no archive/end-date in R3 —
  explicitly out of scope; `end_date` is not a column on this table). Removing
  the **primary** while other assignments remain must force a new-primary pick
  before the delete commits (F1.4.3), or the provider is left with assignments
  and no primary — allowed by the partial unique index but a product invariant
  violation. There is no "last assignment removal" block equivalent to E1.3's
  group rule here, because the wizard's completeness simply reflects the gap
  (the provider drops back to "needs locations"); the PM's "no unassigned
  resting state" is enforced by readiness/wizard surfacing, not a DB trigger.
- **TE-8 — Audit + verification gates.** Route assignment create/update/
  primary-swap/remove through the existing `writeAudit` (entityType
  `provider_facility_assignment`; `audit_log.entity_type` is unconstrained, so
  that name needs no enum migration). Unit-test the group-scoped selector, the
  primary-swap atomicity, and the "remove primary prompts re-pick" logic;
  extend Playwright for TS-39 (Tree Hill assignment-gap → In progress) and
  TS-40 (Shelby two-group picker + start dates + primary swap). Must pass
  `npm run lint`, `npx tsc --noEmit`, `npm run test`,
  `npx prettier --check .`, and the touched e2e specs.
- **Likely tech debt to contain.**
  - The unused baseline column `practice_frequency` is out of scope for R3 —
    do not surface or write it (leave it null; it is not part of the R3 form).
  - Do not resurrect the dead `providers.launch_id` / `launches` location
    track — facility assignment is the live model.
  - The existing `FacilityAssignment` interface already includes `isPrimary`
    but omits `startDate` and `practiceFrequency`; widen it additively for the
    fields E1.4 reads, never rename it.
  - `AuditActionType` includes `DELETE`, but the repo's latest
    `audit_log_action_type_check` migration does not. If assignment removal is
    audited as DELETE, widen that CHECK additively first (following the
    existing READ-widening migration); do not skip the append-only audit.
- **No open questions for the PM.** The R3 assignment decisions (group-scoped
  picker, single primary across groups, hand-pick only, required per-location
  start date, no unassigned resting state) are RESOLVED in
  `CLARIFICATIONS_NEEDED.md` ([stage-3], 2026-07-11). The only correction is
  TE-1 (`start_date`/`is_primary` already exist) — recorded here
  authoritatively, not a contradiction that blocks review.
