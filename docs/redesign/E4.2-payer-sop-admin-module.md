# E4.2 — Payer & SOP Admin Module: Upstream Configuration Space

## Purpose and Context

`[r6]` decision A0: **payer SOPs are a mandatory prerequisite for system
readiness** — case generation must be entirely deterministic, driven by
upstream configuration rather than downstream guesswork. This epic builds a
**dedicated administrative module for Payer and SOP management**, owned by a
designated configuration user (Ops Lead or Admin), where payer-specific
requirements, logic, and task sequences are defined BEFORE cases exist. With
SOP setup centralized upstream, generated cases arrive with complete,
accurate task checklists, and specialists log in to a clean, high-density
queue where they execute immediately — never investigating missing case
details.

The PM's "micro-frontend" architecture note is **confirmed** (PM
2026-07-14) to mean a **user-role-controlled admin module inside the
existing app** — NOT a separately deployed application: a cleanly
separable, role-gated route subtree with no coupling into specialist
workflow components. The reviewer records the concrete isolation mechanism
in this single-app TanStack Start codebase in §5.

The module also becomes the home for the vocabularies and settings R6
introduces: denial/return reason codes (E4.0) and the org-level
next-best-action queue settings (resolved `[r6]` NBA-configurability
decision, PM 2026-07-14: admin-configurable with a shipped default, at the
organization level).

## Personas Empowered

- **P4 Company Owner / Ops Lead** — the designated configuration user; owns
  payer + SOP setup. (First epic where P4 becomes an operating actor; a P4
  seed row is added per seed-universe's open item.)
- **P1 Credentialing Manager** (admin role) — alternate configuration owner.
- **P2 Credentialing Coordinator / Specialist** — indirect beneficiary:
  cases always arrive fully specified.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Reuses the shipped SOP-as-data model (E1.7b, Model A versioning) and the
  global payer catalog (E1.6) — this epic is a **management surface**, not a
  new SOP or payer model.
- Access is role-gated (admin/config role); RLS unchanged; additive schema
  only for readiness flags/vocabularies. Reviewer records mechanisms in §5.

## Features

### F4.2.1 — Dedicated admin module for payers & SOPs

- **Description:** A distinct admin space (own nav entry + route subtree,
  admin/config-role gated) consolidating: the payer directory with per-org
  attachment state (E1.6/E1.5), SOP templates with versions and match keys
  (E1.7b), and the mapping payer × state × specialty → SOP. Existing
  scattered admin surfaces for these move under (or link into) this module.
- **Persona:** P4, P1.
- **Benefit hypothesis:** one owned configuration space (A0) — the config
  user sees and maintains everything case generation depends on in one
  place.
- **Acceptance criteria:**
  - The module lists payers with their SOP coverage and attachment state.
  - **Per-payer resolution-identifier config:** each payer's config holds
    the label of its payer-issued enrollment identifier (e.g. "Provider
    PIN" for Aetna, "Provider ID" for BCBS) and whether one is expected
    at approval; unconfigured payers fall back to a generic
    "Payer-issued ID" optional field. Consumed by E4.0 F4.0.3's approval
    step.
  - SOP create/edit/version flows are reachable from the module and
    unchanged in behavior (E1.7b rules hold).
  - Non-admin/config roles cannot access the module (role-gated route).
  - The module is a cleanly isolated route subtree with no imports from
    specialist workflow components (isolation requirement; §5 records the
    mechanism).
- **Test/data scenario(s):** TS-76.

```gherkin
Feature: Payer & SOP admin module
  Scenario: Config user manages SOP coverage in one space
    Given P4 signs in with the config/admin role
    When she opens the Payer & SOP admin module
    Then she sees payers with attachment state and SOP coverage per state
    And can open a payer's SOP to edit tasks, producing a new version per E1.7b
```

### F4.2.2 — Payer readiness ("SOP baseline") signal

- **Description:** Each attached payer × state shows a derived readiness
  signal: **Ready** (a current SOP resolves for it) or **Needs SOP** (only
  the generic fallback would resolve). Generation previews (E2.0) and the
  case surfaces label fallback-resolved work as before; the module shows the
  gap list so the config user closes it upstream.
- **Persona:** P4, P1.
- **Benefit hypothesis:** A0's "SOPs as baseline for system readiness"
  becomes visible and actionable — the config user can drive coverage to
  100% before generation, keeping cases deterministic.
- **Acceptance criteria:**
  - The module lists every attached payer × state with Ready / Needs SOP,
    fully derived (no stored readiness).
  - The Needs-SOP list links straight into SOP creation with the match key
    prefilled.
  - No blocking behavior change to generation (fallback SOP still applies
    per [r4]); this is an upstream visibility surface.
- **Test/data scenario(s):** TS-77.

### F4.2.3 — Reason-code vocabulary management

- **Description:** The E4.0 denial/return reason-code list is managed here:
  the shipped defaults (Missing Documentation, Network Closed, Demographic
  Mismatch, Incomplete Application, Credentialing Criteria Not Met, Other)
  plus org-added codes; codes deactivate (never delete) so historical
  resolutions keep their meaning.
- **Persona:** P4, P1.
- **Benefit hypothesis:** structured vocabularies stay curated by the
  config owner instead of drifting via free text (A4).
- **Acceptance criteria:**
  - Defaults are seeded and non-deletable; org codes can be added and
    deactivated.
  - Deactivated codes disappear from new-entry dropdowns but render on
    historical records.
- **Test/data scenario(s):** TS-78.

### F4.2.4 — Bulk case generation entry point (new-contract flow)

- **Description:** The module (and the case-generation surface) exposes the
  **bulk generation** workflow A1 requires: a group signs a new contract /
  attaches a new payer, and the config user or manager generates cases for
  ALL eligible providers under that group × payer × state in one run — this
  is the existing E2.0/E2.1 preview → generate machinery, entered from the
  payer/contract context with the payer preselected. Ad hoc one-off creation
  (misses found during onboarding) remains via the existing manual case flow.
- **Persona:** P1, P4.
- **Benefit hypothesis:** new-contract onboarding becomes one deterministic
  bulk run with the E2.0 preview/exclusion safety net, not N manual
  creations.
- **Acceptance criteria:**
  - From a payer (or its attachment) in the module, "Generate cases" opens
    the E2.0 preview scoped to that payer; generation follows E2.1 rules
    (4-part key, dedupe, exclusions) unchanged.
  - The run is recorded with existing E2.4 traceability.
- **Test/data scenario(s):** TS-79.

### F4.2.5 — Next-best-action queue settings (org-level, with default)

- **Description:** An admin-only settings surface for the E2.3/E4.1 "My
  Cases" queue: the org admin can reorder and enable/disable the ranking
  inputs (overdue follow-ups, task due dates, provider start dates,
  location launch dates) for their organization. The system ships a
  default configuration (overdue follow-ups above deadline-only rows;
  ties by earliest deadline); "Reset to default" is always available.
  Config is org-scoped; the queue derivation reads it live — no per-case
  or per-user priority is ever stored.
- **Persona:** P4, P1 (admins); P2 experiences the resulting ordering.
- **Benefit hypothesis:** orgs differ in what "most urgent" means; an
  org-level dial with a sane default gives control without sacrificing
  the deterministic, fully derived queue.
- **Acceptance criteria:**
  - With no saved config, the queue uses the shipped default; saving a
    config changes ranking for that org only, immediately, for all users.
  - Reordering/enabling inputs and Reset-to-default are admin-only;
    changes are audited.
  - The queue remains fully derived; the config is an input to the
    derivation (E1.0 derived-progress rule holds).
- **Test/data scenario(s):** TS-91.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the existing payer administration
(`src/routes/admin.payers.tsx`, `src/services/payers.ts`), SOP administration
and immutable publishing (`src/routes/admin.templates.index.tsx`,
`src/components/templates/TemplateWizard.tsx`,
`src/services/templates.ts`, `src/hooks/useAdmin.ts`,
`src/lib/pickTemplate.ts`), payer-network targeting
(`src/services/payerNetworkTargets.ts`,
`src/hooks/usePayerNetworkTargets.ts`), and the E2 generation flow
(`src/routes/generation.tsx`, `src/services/generationPreview.ts`,
`src/services/generationConfirm.ts`). The module is a consolidation and
configuration boundary over those shipped domains, not a replacement payer,
SOP, or generation engine._

- **TE-1 — Implement “micro-frontend” as a bounded route/module inside the
  existing TanStack Start application.** Give the workspace its own
  `/admin/...` route namespace and module-local components under
  `src/components/payer-admin/`, but keep one Vite/TanStack Start deployment,
  shared auth store, query client, design system, and service layer. Compose or
  relocate the existing payer and template screens rather than cloning them.
  A separately built or deployed frontend would duplicate authentication,
  organization state, navigation, and data contracts and is outside the
  confirmed PM interpretation. F4.2.1's explicit “own nav entry” requirement
  authorizes one narrowly scoped protected-file change in
  `src/components/layout/Sidebar.tsx` for the admin-only link; no broader shell
  redesign is authorized.

- **TE-2 — P4 maps to the existing `admin` authorization role for R6.** The
  current role union is `admin | specialist | billing`; there is no `config`
  role. Seed the P4 Company Owner / Ops Lead persona with an `admin`
  membership, enforce the route with the existing admin guard, disable
  protected queries until that guard resolves, and keep module mutation
  controls admin-only. P2 (`specialist`) is denied at the route boundary.
  Per the epic's explicit “RLS unchanged” constraint, existing payer/SOP table
  policies are not narrowed here; that leaves a known defense-in-depth gap if
  “configuration user only” is later intended as a database-enforced security
  boundary. Do not add a fourth role or capability system unless the PM
  separately requires config-only users.

- **TE-3 — Reuse payer and SOP services; preserve published-version
  semantics.** Payer reads/writes remain in `payers.ts`; SOP head/version
  reads and the `publish_sop_template_version` RPC remain in `templates.ts`.
  The module must use the existing optimistic-concurrency and immutable-version
  behavior and the centralized `pickTemplate()` precedence. No component calls
  Supabase, no second template resolver is introduced, and no in-flight case is
  silently moved to a newer SOP version.

- **TE-4 — Readiness is a pure projection over attached payer targets and
  payer-specific SOP resolution.** Start from active
  `payer_network_targets`/organization payer assignments, group by attached
  payer × state for display, and evaluate every underlying group target through
  the existing resolver. “Ready” means every active target resolves to an
  active payer-specific SOP; a global generic fallback is deliberately shown
  as “Needs SOP.” If any grouped target is uncovered, the aggregate row is
  “Needs SOP” and the creation link carries the payer/state/group match inputs.
  Do not persist a readiness boolean; invalidate payer-target and template
  query prefixes after configuration writes.

- **TE-5 — Add one organization-scoped reason-code vocabulary, not enum text
  in components.** An additive `denial_reason_codes` table should carry a
  stable ID, `org_id`, machine code, label, `is_system`, `is_active`,
  `created_by`, and timestamps, with case-insensitive uniqueness per
  organization. Seed the default codes for every organization, including the
  organization-bootstrap RPC path. System defaults cannot be deleted;
  organization codes are deactivated, not deleted. Historical denial rows
  reference the stable ID and continue resolving inactive labels. Provide
  select/insert/update policies for admin members only, no delete policy, and
  explicit grants. E4.0 owns the eventual denial-event foreign key after its
  pipeline contract is clarified.

- **TE-6 — Bulk generation is an entry point into the E2 flow.** Add an
  optional payer/group scope to the existing generation route, preview input,
  and pure candidate filter. Launching “Generate cases” from payer context
  pre-filters the same E2.0 preview; confirmation still uses the same E2.1
  transaction/RPC and E2.4 run traceability. Preserve the locked candidate,
  exclusion, dedupe, reapplication, and audit rules. Do not create a parallel
  bulk generator or insert cases directly from the admin module.

- **TE-7 — Add one organization-level queue configuration row with a code
  default.** An additive `next_best_action_configs` table should use `org_id`
  as its primary key and store an exact permutation of the four fixed input
  keys—`follow_up`, `task_due`, `provider_start`, and `launch_date`—plus a
  subset of disabled keys, with `updated_by` and `updated_at`. `follow_up`
  governs both explicit next-follow-up and existing SOP-cadence touch
  deadlines. Database/service validation rejects unknown or duplicate keys.
  Absence of a row means the shipped comparator: arrived/overdue follow-ups
  first, then remaining signals by earliest deadline; “Reset to default”
  deletes the row after an audit write. Keep the default and input-key union in
  one pure TypeScript module shared by the admin service and
  `buildNextBestActions`; do not store a per-case score, priority, or queue
  row. Admin writes are organization-scoped, while authenticated organization
  members may read the effective setting used by their queue.

- **TE-8 — Query ownership remains organization-scoped and domain-specific.**
  Continue using TanStack Query hooks over services and shared keys in
  `src/hooks/queryKeys.ts`. Mutations invalidate only the relevant
  organization prefixes: payers/assignments, payer-network targets, templates
  and versions, reason codes, queue configuration/queue inputs, generation
  preview, and audit log. A successful queue-setting save/reset immediately
  reranks every user through the existing derived hook. Organization switching
  continues to clear cached server state through the existing auth store;
  Zustand is not used as a second database cache.

- **TE-9 — Preserve existing RLS while securing additive configuration
  data.** The epic explicitly leaves current payer/SOP RLS unchanged; retain
  those policies and enforce this consolidated surface through the admin route
  and module mutations. The new reason-code table is organization-scoped,
  permits admin configuration writes, has no delete policy, and remains
  readable where operational/history rendering requires labels. Queue-config
  rows permit organization-member reads and admin insert/update/delete so reset
  can remove the override. Every insert derives `org_id` from the active
  organization, every mutation writes audit, and all new public tables receive
  explicit least-privilege grants. Record the existing specialist-capable
  payer policy as technical debt rather than silently changing authorization
  scope in this epic.

- **TE-10 — UI uses a high-density table/workspace composition.** Reuse the
  approved `Table`, `Tabs`, `Badge`, `Select`, `Dialog`, `Input`, and `Button`
  primitives with custom cells for attachment/readiness pills and two-line SOP
  coverage. Queue settings use existing checkbox/toggle controls plus
  accessible move-up/move-down buttons rather than adding a drag-and-drop
  dependency. Use one-pixel borders, `rounded-md`, compact rows/padding,
  approved tokens, and no card shadows, gradients, or decorative backgrounds.
  Every form control has an explicit label; icon-only controls have labels and
  tooltips. Apart from the TE-1 sidebar link, no protected layout change is
  authorized; no primitive file is modified.

- **TE-11 — Test the boundary and reuse contracts.** Unit/service tests cover
  grouped readiness, fallback-only “Needs SOP,” inactive reason-code history,
  queue-config validation/default/reset and cross-org isolation,
  route/service/RLS authorization, and payer-scoped generation filtering.
  Playwright scenarios TS-76–TS-79 and TS-91 must verify P4 as seeded admin, P2
  denial, SOP-link prefilling, reason-code deactivation, queue reranking/reset,
  and handoff into the existing generation preview/run history. Add no live
  payer or extension dependency.
