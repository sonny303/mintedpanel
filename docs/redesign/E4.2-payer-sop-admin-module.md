# E4.2 — Payer & SOP Admin Module: Upstream Configuration Space

## Purpose and Context

`[r6]` decision A0: **payer SOPs are a mandatory prerequisite for system
readiness** — case generation must be entirely deterministic, driven by
upstream configuration rather than downstream guesswork. This epic builds a
**dedicated administrative module for Payer and SOP management**, owned by a
designated configuration user (Ops Lead or Admin), where payer-specific
requirements, logic, and task sequences are defined BEFORE cases exist. With
SOP setup centralized upstream, generated cases arrive with complete,
accurate task checklists, and specialists log in to a clean, high-density
queue where they execute immediately — never investigating missing case
details.

The PM's "micro-frontend" architecture note is **confirmed** (PM
2026-07-14) to mean a **user-role-controlled admin module inside the
existing app** — NOT a separately deployed application: a cleanly
separable, role-gated route subtree with no coupling into specialist
workflow components. The reviewer records the concrete isolation mechanism
in this single-app TanStack Start codebase in §5.

The module also becomes the home for the vocabularies and settings R6
introduces: denial/return reason codes (E4.0) and the org-level
next-best-action queue settings (resolved `[r6]` NBA-configurability
decision, PM 2026-07-14: admin-configurable with a shipped default, at the
organization level).

## Personas Empowered

- **P4 Company Owner / Ops Lead** — the designated configuration user; owns
  payer + SOP setup. (First epic where P4 becomes an operating actor; a P4
  seed row is added per seed-universe's open item.)
- **P1 Credentialing Manager** (admin role) — alternate configuration owner.
- **P2 Credentialing Coordinator / Specialist** — indirect beneficiary:
  cases always arrive fully specified.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Reuses the shipped SOP-as-data model (E1.7b, Model A versioning) and the
  global payer catalog (E1.6) — this epic is a **management surface**, not a
  new SOP or payer model.
- Access is role-gated (admin/config role); RLS unchanged; additive schema
  only for readiness flags/vocabularies. Reviewer records mechanisms in §5.

## Features

### F4.2.1 — Dedicated admin module for payers & SOPs

- **Description:** A distinct admin space (own nav entry + route subtree,
  admin/config-role gated) consolidating: the payer directory with per-org
  attachment state (E1.6/E1.5), SOP templates with versions and match keys
  (E1.7b), and the mapping payer × state × specialty → SOP. Existing
  scattered admin surfaces for these move under (or link into) this module.
- **Persona:** P4, P1.
- **Benefit hypothesis:** one owned configuration space (A0) — the config
  user sees and maintains everything case generation depends on in one
  place.
- **Acceptance criteria:**
  - The module lists payers with their SOP coverage and attachment state.
  - SOP create/edit/version flows are reachable from the module and
    unchanged in behavior (E1.7b rules hold).
  - Non-admin/config roles cannot access the module (role-gated route).
  - The module is a cleanly isolated route subtree with no imports from
    specialist workflow components (isolation requirement; §5 records the
    mechanism).
- **Test/data scenario(s):** TS-76.

```gherkin
Feature: Payer & SOP admin module
  Scenario: Config user manages SOP coverage in one space
    Given P4 signs in with the config/admin role
    When she opens the Payer & SOP admin module
    Then she sees payers with attachment state and SOP coverage per state
    And can open a payer's SOP to edit tasks, producing a new version per E1.7b
```

### F4.2.2 — Payer readiness ("SOP baseline") signal

- **Description:** Each attached payer × state shows a derived readiness
  signal: **Ready** (a current SOP resolves for it) or **Needs SOP** (only
  the generic fallback would resolve). Generation previews (E2.0) and the
  case surfaces label fallback-resolved work as before; the module shows the
  gap list so the config user closes it upstream.
- **Persona:** P4, P1.
- **Benefit hypothesis:** A0's "SOPs as baseline for system readiness"
  becomes visible and actionable — the config user can drive coverage to
  100% before generation, keeping cases deterministic.
- **Acceptance criteria:**
  - The module lists every attached payer × state with Ready / Needs SOP,
    fully derived (no stored readiness).
  - The Needs-SOP list links straight into SOP creation with the match key
    prefilled.
  - No blocking behavior change to generation (fallback SOP still applies
    per [r4]); this is an upstream visibility surface.
- **Test/data scenario(s):** TS-77.

### F4.2.3 — Reason-code vocabulary management

- **Description:** The E4.0 denial/return reason-code list is managed here:
  the shipped defaults (Missing Documentation, Network Closed, Demographic
  Mismatch, Incomplete Application, Credentialing Criteria Not Met, Other)
  plus org-added codes; codes deactivate (never delete) so historical
  resolutions keep their meaning.
- **Persona:** P4, P1.
- **Benefit hypothesis:** structured vocabularies stay curated by the
  config owner instead of drifting via free text (A4).
- **Acceptance criteria:**
  - Defaults are seeded and non-deletable; org codes can be added and
    deactivated.
  - Deactivated codes disappear from new-entry dropdowns but render on
    historical records.
- **Test/data scenario(s):** TS-78.

### F4.2.4 — Bulk case generation entry point (new-contract flow)

- **Description:** The module (and the case-generation surface) exposes the
  **bulk generation** workflow A1 requires: a group signs a new contract /
  attaches a new payer, and the config user or manager generates cases for
  ALL eligible providers under that group × payer × state in one run — this
  is the existing E2.0/E2.1 preview → generate machinery, entered from the
  payer/contract context with the payer preselected. Ad hoc one-off creation
  (misses found during onboarding) remains via the existing manual case flow.
- **Persona:** P1, P4.
- **Benefit hypothesis:** new-contract onboarding becomes one deterministic
  bulk run with the E2.0 preview/exclusion safety net, not N manual
  creations.
- **Acceptance criteria:**
  - From a payer (or its attachment) in the module, "Generate cases" opens
    the E2.0 preview scoped to that payer; generation follows E2.1 rules
    (4-part key, dedupe, exclusions) unchanged.
  - The run is recorded with existing E2.4 traceability.
- **Test/data scenario(s):** TS-79.

### F4.2.5 — Next-best-action queue settings (org-level, with default)

- **Description:** An admin-only settings surface for the E2.3/E4.1 "My
  Cases" queue: the org admin can reorder and enable/disable the ranking
  inputs (overdue follow-ups, task due dates, provider start dates,
  location launch dates) for their organization. The system ships a
  default configuration (overdue follow-ups above deadline-only rows;
  ties by earliest deadline); "Reset to default" is always available.
  Config is org-scoped; the queue derivation reads it live — no per-case
  or per-user priority is ever stored.
- **Persona:** P4, P1 (admins); P2 experiences the resulting ordering.
- **Benefit hypothesis:** orgs differ in what "most urgent" means; an
  org-level dial with a sane default gives control without sacrificing
  the deterministic, fully derived queue.
- **Acceptance criteria:**
  - With no saved config, the queue uses the shipped default; saving a
    config changes ranking for that org only, immediately, for all users.
  - Reordering/enabling inputs and Reset-to-default are admin-only;
    changes are audited.
  - The queue remains fully derived; the config is an input to the
    derivation (E1.0 derived-progress rule holds).
- **Test/data scenario(s):** TS-91.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the existing admin surfaces
(`src/routes/admin.payers.tsx`, `admin.sops.tsx`/`admin.sops.$id.tsx`/
`admin.sops.index.tsx`, `admin.templates*.tsx`, `admin.portals.tsx`,
`admin.mso-routing.tsx`, `admin.statuses.tsx`, `admin.settings.tsx`,
`admin.audit.tsx` — all flat `admin.*` leaves, role-gated in-component via
`useRole`, with no `admin` layout/parent route today), the role model
(`memberships.role ∈ {specialist, billing, admin}`, `user_role(org_id)`), the
SOP model (`sop_templates`, versions from `20260713120000_sop_template_versions.sql`,
`src/lib/sopResolver.ts` `resolveTemplate`, `src/services/templates.ts`
own-org-or-global read), the payer surfaces (`src/services/payerCatalog.ts`,
`orgPayerAssignments.ts`, `payerNetworkTargets.ts` from
`20260712190000`), the generation machinery (E2.0 `generationPreview.ts`, E2.1
`create_case_with_tasks`, E2.4 `generation_run_id` traceability), the shared
reserved-route pattern (`src/routes/soon.tsx`), the E4.0 `denial_reason_codes`
table (this epic's §5 TE-4 there), and `uiux-component-guide.md`. **Headline:**
this is a consolidation + role-gating surface, not new domain logic — every
model it manages (payer catalog, attachments, SOP-as-data versions, generation)
already ships. The two real decisions are (a) "micro-frontend" is delivered as an
isolation requirement (a role-gated route subtree with a no-cross-import rule),
not a literal separate deployment — flagged to the PM; and (b) there is no
distinct P4/Ops-Lead/config DB role — the config owner maps to the existing
`admin` membership role, and adding a real config role is an additive change we
flag rather than assume._

- **TE-1 — The module is a role-gated route subtree with a no-cross-import
  isolation rule (the "micro-frontend" mechanism).** Introduce a parent layout
  route (e.g. `src/routes/config.tsx` or an `admin.tsx` layout, renders only
  `<Outlet />` per AGENTS.md) whose `beforeLoad` redirects any non-admin
  (`user_role(activeOrg) !== 'admin'`) — this is the route-level gate F4.2.1
  requires, replacing the current per-component `useRole` checks for these
  surfaces. The existing payer/SOP/template/portal leaves move under (or are
  linked from) it. **Isolation requirement:** module components live in a new
  `src/components/config/` folder with a lint/architecture rule that it imports
  nothing from specialist-workflow folders (`src/components/cases/`,
  `src/components/work/`) — the "cleanly separable, independently evolvable
  surface" the PM means, achievable inside this single TanStack Start app. A
  literal separate-deployment micro-frontend is out of scope for R6 and flagged
  to the PM (see flags). Add one nav entry (the E0.6 segmented `Sidebar` top
  cross-org section, `src/components/layout/Sidebar.tsx` — an authorized shell
  edit noted here per the layout-protected rule).

- **TE-2 — Payer readiness ("Ready / Needs SOP") is fully derived from the SOP
  resolver, no stored flag (F4.2.2).** For each attached payer × state
  (`payer_network_targets` status `active`), run the same match-key resolution
  the generation preview uses (`sopResolver`/`templates.ts`): a **specific** SOP
  match (own-org or global, keyed on payer/state/specialty) ⇒ **Ready**; only
  the generic/fallback template resolving ⇒ **Needs SOP**. No readiness column is
  added (E1.0 derived-progress rule; matches F4.2.2 "fully derived"). The
  Needs-SOP list deep-links into SOP creation (`admin.templates.new`/
  `admin.sops`) with the match key prefilled. Generation behaviour is unchanged
  — fallback still applies per `[r4]`; this is a visibility surface only.

- **TE-3 — Reason-code management is CRUD over the E4.0 `denial_reason_codes`
  table (F4.2.3).** E4.0 §5 TE-4 ships the table (global defaults as
  `org_id IS NULL`, org rows as `org_id = active`, `active` flag). This epic adds
  the admin UI + service/hook: list global+own-org codes, add org codes,
  toggle `active` (deactivate, never DELETE — the six defaults are non-deletable
  because they are global rows an org cannot write). Deactivated codes drop out
  of new-entry dropdowns (the E4.0 transition + any future entry point read the
  `active` set) but historical `payer_pipeline_history.reason_code_id`
  references still resolve their label. RLS for the org write path is
  `user_role = 'admin'` (already the TE-4 predicate). **Build ordering:** E4.0
  before E4.2 (or ship the table in E4.0 unmanaged); the dependency is
  one-directional and noted in both epics.

- **TE-4 — Bulk generation reuses the E2.0/E2.1 machinery, entered from payer
  context (F4.2.4).** No new generation rules or RPC — "Generate cases" from a
  payer/attachment opens the existing E2.0 preview (`generationPreview.ts`)
  scoped to that payer × the group's eligible providers × state, then the E2.1
  `create_case_with_tasks` path applies the 4-part key, dedupe, and exclusions
  unchanged, recorded with the existing E2.4 `generation_run_id` traceability.
  The only new code is the entry-point wiring (pass the preselected payer/scope
  into the existing preview surface). Ad hoc one-off creation remains the
  existing manual case flow. `[r4]`/`[r4-review]` generation rules stay locked.

- **TE-5 — NBA queue settings: one small org-scoped config read live by the
  E2.3/E4.1 derivation (F4.2.5, resolved `[r6]` decision).** Store the org's
  ranking configuration additively — either a dedicated `nba_queue_config` row
  per org (`org_id` unique, `config jsonb` = the ordered/enabled ranking inputs,
  plus `updated_by`/`updated_at`) or a namespaced key on the existing per-org
  settings surface (`src/routes/admin.settings.tsx` + its service) if one already
  backs org settings. **Reviewer default: a dedicated `nba_queue_config` table**
  for a clean grain and register entry. Admin-only write (RLS
  `user_role = 'admin'`), member SELECT, audited on change; **no per-case or
  per-user priority is ever stored** (E1.0 derived rule). The config is consumed
  as an input to the pure `src/lib/nextBestActions.ts` ranking (E4.1 §5 TE-4):
  absent/empty ⇒ the shipped default (overdue follow-ups above deadline-only,
  ties by earliest deadline), so the queue is correct before any org customises
  it. The admin surface is a reorder + enable/disable list of the four inputs
  (overdue follow-ups, task due dates, provider start dates, location launch
  dates) with an always-available "Reset to default", built from existing shadcn
  primitives inside the TE-1 module. Additive migration (if a table) repo +
  hosted; `types.ts` regenerated; register row added in the same PR.

- **TE-6 — Seed + tests.** Adds the seed-universe P4 row (see flags) as a
  member with `role='admin'` on a Dillon-scoped org for TS-76; TS-77 needs an
  attached payer with no specific SOP (only fallback resolves) to exercise the
  Needs-SOP signal; TS-78 an org-added reason code; TS-79 a new payer attachment
  for the bulk-generation entry; TS-91 exercises the F4.2.5 NBA config (admin
  reorders inputs → P2's queue reorders, then Reset-to-default restores the
  shipped ordering). e2e covers the role gate (non-admin redirected), the
  derived readiness list, and the config round-trip. New table this epic owns is
  `nba_queue_config` (reviewer default); otherwise register is affected only
  through E4.0.
