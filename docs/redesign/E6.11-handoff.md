## What works end to end (code, not yet exercised against hosted)

1. **Setup** — a payer/SOP template with a payer form attached shows a
   collapsed **Field mapping** panel (`PayerFormFieldPanel`) under the form.
2. **Import** — "Import fields from the PDF" signs a download for the exact
   attached form row, reads its AcroForm fields in the browser, and proposes one
   shared registry row per fillable control, keyed
   `payer-form:<payer_forms.family_id>`. A flat scan says so explicitly instead
   of importing nothing silently.
3. **Train** — the same `FieldRegistryList` the online-form trainer uses: token,
   fixed value, "a person writes this", transform, row/section renaming, and the
   mapped/to-decide coverage readout.
4. **Sample fill** — "Download a sample fill" fills the real blank with the
   synthetic mock profile, labels the file `SAMPLE-do-not-send`, and records a
   `fill_sessions` row with `is_test=true, fill_mode='pdf'`.
5. **Case fill** — the case checklist's payer-form row gains **Fill & download**
   when the family has mappings that resolve. It fills the baked form version,
   downloads locally, leaves the PDF editable, records
   `fill_sessions(fill_mode='pdf', is_test=false)` counts-only, and does not
   touch task or case status.

## Decisions worth keeping

- Mappings are keyed by **family**, not by form row, so replacing a payer's PDF
  keeps the training. A payer that reorganizes its layout should be uploaded as
  a new family.
- `planPayerFormFill` delegates to `classifyFieldMap` — hardcoded rows fill, a
  "person writes this" row is reported as theirs and **not** as a coverage gap,
  and an undecided row is a gap that is never guessed at.
- The filled file never leaves the browser: the `payer-forms` bucket holds blank
  global forms only, and no field value is written to a row, an audit entry, or
  a log.
- The old dictionary-backed filler (`pdfFill.ts` + `field_dictionary`) is still
  in the tree, still inert (no UI path confirms a dictionary row). Nothing new
  depends on it.

## Next steps, in order

1. **Apply the migration to hosted.** `supabase/migrations/20260825120000_e611_pdf_field_maps.sql`
   replaces `propose_shared_field_map` with a 10-argument version taking
   `p_map_type text DEFAULT 'web'` (DROP + CREATE, per the PostgREST overload
   rule). It has **not** been applied — this session had no Supabase access
   token. Until it is, PDF import fails on hosted, because
   `portalFieldMaps.proposeSharedFieldMap` sends `p_map_type` for PDF rows.
   After applying, verify the object (not the filename) and regenerate
   `src/integrations/supabase/types.ts` with Supabase tooling — it was hand-
   narrowed here for exactly this argument.
2. **Walk the real flow on hosted** with a genuine payer PDF: import → decide
   every field → sample fill → generate a case → Fill & download. Confirm the
   sample fill lands values where the payer expects them; that is the check the
   panel exists to make cheap.
3. **B0, now answerable with real files** — how many payer PDFs in the library
   are AcroForm vs flat? If flat is common, the follow-up is a printable data
   sheet (a values page a coordinator copies from), not coordinate overlays.
4. **B1** — retire the inert dictionary filler. Deleting `pdfFill.ts` and its
   `field_dictionary` read path is safe only after confirming no route imports
   it; keep the tests that cover shared behavior.
5. **Coverage gaps to close:** `payerFormFillClient.ts` (browser-only, pdf-lib)
   has no test — a fixture-based test that fills a tiny generated AcroForm and
   reads the values back would pin option matching and checkbox coercion.
6. **Deferred deliberately:** roster-grain fills (one PDF, many providers),
   multi-page repeated field groups, and any transform beyond the two authorable
   ones. `applyRegistryTransform`'s `state_abbrev` normalizes case only — this
   repo has no state name→code table, and inventing one duplicates the
   extension's.
