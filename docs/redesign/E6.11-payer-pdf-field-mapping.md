# E6.11 — Payer PDF Field Mapping & Auto-Fill

Panel-only. The extension is untouched: its fill planner already hard-skips
`map.mapType !== "web"` (`minted-extension/src/background/fill.ts`), so PDF rows
in the shared catalog cannot leak into a web fill. The one place a cross-repo
change becomes unavoidable — new value-shaping transforms — is deliberately the
LAST bite (B8), and is deferred out of this epic's build.

## Purpose and Context

E6.x shipped the payer-PDF **file** loop: an admin uploads a payer's blank form
on a SOP template action (`src/components/templates/PayerFormStepPanel.tsx`,
`supabase/migrations/20260824170000_payer_forms.sql`), generation bakes the
exact row onto the case, and the coordinator downloads it and marks it sent
(`src/components/cases/PayerFormActionRow.tsx`). Nothing fills it. A
coordinator retypes ~71 boxes of data the system already holds, per provider,
per payer, per state.

This epic maps a blank payer form's AcroForm fields to catalog tokens **once per
form family**, using the field registry that already exists, and fills the baked
form on the case in the browser. The filled PDF is never submitted and never
persisted — a human reviews and sends it, exactly as today.

## Four corrections

1. **"No DDL is needed to start" is wrong.** No _table_ DDL is needed, but the
   only writer of shared registry rows, `propose_shared_field_map`, inserts a
   literal `'web'` for `map_type`
   (`supabase/migrations/20260813120000_e610_control_options.sql`). A PDF row
   cannot exist until that function takes a `p_map_type`. Function-level
   migration, additive, no data change (B2).
2. **Fix `computeTestRun` by delegating, not by adding a source branch.**
   `classifyFieldMap` already answers "does this row autofill?" exhaustively and
   fails closed. `DryRunFieldMap` carries no `source` at all, so the spike's
   "branch on source" would duplicate that classifier and re-open the E6.9 bug
   it was written to close. Widen the row shape and call the classifier.
3. **The mount points are now concrete, and they are not `FormStepPanel`.**
   The payer-PDF upload shipped after the spike (#339, #340). The trainer mounts
   inside `PayerFormStepPanel.tsx` (Template Editor → the Payer PDF action), and
   the fill mounts on `PayerFormActionRow.tsx` (case checklist). `FormStepPanel`
   stays the online-form panel; PDF gets the same registry _list_, not the same
   panel.
4. **Phase 0 and the new fill are different surfaces.** `PdfStep`
   (`src/components/cases/StepDetails.tsx:284`) is a file-**picker** on a `pdf`-type
   SOP step — the coordinator uploads a PDF from their own disk. The new fill
   reads the baked `payer_forms` row and needs no file picker. So retiring the
   dead dictionary path (B1) and building the fill (B6) do not overlap, and B1
   is safe to land first.

Hosted row counts from the spike's Appendix B (`field_dictionary` 0,
`payer_forms` 0, `portal_field_maps` 184) could not be re-verified this session —
no Supabase access token was available. Nothing in the plan depends on them
being exact.

## Personas Empowered

- **P1 Credentialing Manager** — maps a payer form once on the template.
- **P2 Credentialing Specialist** — fills the baked form on the case instead of
  retyping it.

## Component & Data Constraints

- Built from the current library — see [`uiux-component-guide.md`](./uiux-component-guide.md).
- Registry rows are **global tier** (`org_id IS NULL`), like `payer_forms` and
  the template that carries them: written through `propose_shared_field_map` /
  `train_global_field_map`, gated by `user_is_admin_anywhere()`.
- PHI: the filled PDF stays in the browser. It is never uploaded, never logged,
  and must never land in the global `payer-forms` bucket.
- `pdf-lib@1.17.1` is already a dependency and must stay client-only —
  `src/lib/pdfFill*.ts`'s pure/browser split is the pattern to follow.

## Features (bite-sized; each bite is one PR)

### B0 — Count the real library (½ day, no code)

- **Description:** Probe every blank payer form the business actually uses for
  AcroForm fields; record fillable vs flat.
- **Acceptance criteria:**
  - A count, by payer, of fillable vs flat forms, recorded in this epic's
    revision history or a linked doc.
  - If flat dominates, B8+ is re-scoped toward the printable data sheet
    (see Non-Goals) before any coordinate-overlay work is funded.
- **Note:** Not a build blocker for B1–B7 — those pay for themselves on the
  fillable subset — but it is the gate on anything after them.

### B1 — Retire the inert dictionary PDF filler

- **Description:** `PdfStep` reports "N fields · 0 will fill" for every org and
  always will, because its only mapping source can never be populated. Remove
  the dictionary-backed mapping from the PDF path.
- **Acceptance criteria:**
  - No user-visible surface claims a PDF auto-fill it cannot perform.
  - `field_dictionary` remains for the web label-suggestion path; only the PDF
    filler stops reading it.
  - Existing `pdfFill` unit tests still describe live behaviour (no test edited
    to make a removal pass).

```gherkin
Feature: The PDF step never promises a fill it cannot do
  Scenario: A coordinator opens a pdf-type SOP step
    Given no confirmed field_dictionary rules exist for the org
    When they open the step
    Then they are not offered an auto-fill that would fill zero fields
```

### B2 — `propose_shared_field_map` accepts `p_map_type`

- **Description:** Additive function migration so a PDF row can be proposed.
- **Acceptance criteria:**
  - `p_map_type text DEFAULT 'web'`, validated against `('web','pdf')`; every
    existing caller (extension capture, `/api` propose route) is unchanged in
    behaviour.
  - DROP + CREATE with the new arity so PostgREST sees no defaulted overload —
    the E6.10 precedent in the same file.
  - `src/integrations/supabase/types.ts` regenerated; hosted apply is an
    operator step named in the PR body.
  - Grant floor preserved (REVOKE from PUBLIC/anon, GRANT to authenticated +
    service_role).

### B3 — Read a blank PDF's fields into propose-ready rows (pure)

- **Description:** `src/lib/pdfFieldImport.ts` — descriptors in, registry
  propose inputs out. No pdf-lib import (that lives in the client wrapper,
  mirroring `pdfFill.ts` / `pdfFillClient.ts`).
- **Acceptance criteria:**
  - `portalKey` = `payer-form:<familyId>` (lowercase; `normalizePortalKey`-stable).
  - `selector` = the full AcroForm field name, verbatim — it is what the fill
    joins on.
  - `fieldLabel` = the `/TU` tooltip when present, else the camel-split leaf
    name; `formSection` = the subform path; `sortOrder` = widget order.
  - Field type maps to the registry's vocabulary (`text|select|radio|checkbox|date`);
    checkbox/radio export values become `controlOptions`.
  - Deterministic and order-stable, so a re-import produces the same rows.

### B4 — Import action on the Payer PDF panel

- **Description:** "Read fields from this form" on the attached payer form in
  `PayerFormStepPanel`, fetching the blank through the existing signed download
  route and proposing one row per field.
- **Acceptance criteria:**
  - Re-import is **repair**: presentation columns refresh, decisions never move
    (the `propose_shared_field_map` idempotency contract).
  - A form with zero AcroForm fields says so plainly ("this form has no fillable
    boxes — it has to be filled by hand") instead of importing nothing silently.
  - Import count and outcome are reported; failures never leave half a family
    mapped without saying so.

### B5 — Mount the registry list for the family

- **Description:** Render `FieldRegistryList` against the `payer-form:<familyId>`
  rows inside the Payer PDF panel: token / fixed value / a person fills this,
  rename, coverage read-out, undecided-first ordering. Feed
  `suggestTokenForLabel` the tooltip label so imported fields arrive with a
  suggestion and its evidence.
- **Acceptance criteria:**
  - Decisions write through `train_global_field_map` (global tier), never the
    org-tier path.
  - No new decision vocabulary and no new `classifyFieldMap` branch.
  - Suggestions are never auto-applied.
  - The panel stays collapsed by default — the Template Editor typing-latency
    contract (`template-typing-latency.spec.ts`) still passes.

### B6 — Fill & download on the case

- **Description:** `PayerFormActionRow` gains "Fill & download": fetch the baked
  blank, plan the fill from the family's approved rows and the case's token
  values, write the filled PDF to the user's disk.
- **Acceptance criteria:**
  - Only `approved` rows fill; `hardcoded` writes its literal; `manual` is
    listed, not filled; `manual_partial` fills and flags. `applyTransform` is
    honoured.
  - A `fill_sessions` row with `fill_mode='pdf'` and a touch are written; the
    case status does not move.
  - The filled bytes never leave the browser.
  - The button explains what will be left blank BEFORE the download, the way
    the old `PdfStep` preview did.

```gherkin
Feature: Fill a payer form from the case
  Scenario: Coordinator fills the Cigna PSCR on a generated case
    Given the form family has 32 approved token mappings
    When the coordinator clicks Fill & download
    Then the downloaded PDF carries those 32 values, stays editable,
      and the case activity shows a pdf fill
```

### B7 — In-panel test fill (mock profile)

- **Description:** Validate a mapping with no case and no provider: run
  `computeTestRun` against `MOCK_FILL_VALUES`, offer a "Sample fill" download of
  the real form so the trainer sees coverage rather than reading a percentage.
- **Acceptance criteria:**
  - `computeTestRun` delegates to `classifyFieldMap` (correction 2) — a
    `hardcoded` row reports filled, a `manual` row is not a gap, an undecided
    row is.
  - `recordTestFillFromApp` takes `fillMode: 'web' | 'pdf'` and writes it.
  - Every sample fill is labelled as synthetic ("Sample…" data) and is
    `is_test: true`, so no metric reader counts it.

### B8 — Value-shaping transforms (deferred, cross-repo)

- Part-extraction transforms (date month/day/year, phone area/prefix/line), the
  `facility.hours` per-day extractor, and a composite provider-name token.
  Worth ~19 more of the Cigna form's 71 boxes. Requires widening
  `portal_field_maps_transform_check` **and** the extension's `applyTransform`
  in the same coordinated change — an unknown transform there silently falls
  back to the raw value. Do not start before B0's count justifies it.

## Out of Scope / Non-Goals

- **Flat PDFs.** Three of the four sample forms have no form fields at all.
  Coordinate overlay is a different mechanism with its own authoring tool and
  drift story. If B0 finds the library is mostly flat, the cheaper win is a
  **printable data sheet** (every value the form needs, in the form's order, for
  a human to copy) — it reuses the token layer and needs no mapping.
- **Roster grain.** Forms taking several providers on one sheet
  (`PracName1/2`) need a product decision about which providers, chosen by whom.
  Every fill path resolves exactly one provider today.
- **Mapping reuse across different payer forms.** Measured transfer is ~2%, and
  colliding labels carry conflicting meanings. The reusable asset is the
  suggestion, not the mapping.
- **Storing filled PDFs.** A filled form is the most PHI-dense artifact the
  product makes; persistence needs its own retention decision.
- **Submitting anything to a payer.** Unchanged locked decision: the human sends.
