# E6.12 — Enrollment Explorer trust boundary and restricted audience context

## Purpose and Context

This is the first bounded build epic for the approved [WP1.1 parent requirements contract](./enrollment-explorer-wp1.1-requirements.md). It establishes the audience, organization, access, invite, and server-boundary prerequisites for a restricted external client report. It does not build the payer catalog, enrollment capture, proof publication, matrix, drawer, or CSV; those are separate sequential epics and build PRs listed in the parent contract. One epic is one build PR.

The current requirements base is main `ae7aff60cac28ee9e2ac5a7a30a8bb7bce6c5c3b`. This document is a requirements artifact only. Its status remains `draft` until the requirements PR is merged; that lifecycle state does not reopen the approved product defaults. No implementation, merge, release, or hosted activation is authorized by this file.

## Personas Empowered

| Persona                          | Outcome                                                                                                           |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| P1 Credentialing Manager         | Chooses an internal staff context and organization, retaining the existing six-link staff shell.                  |
| P2 Credentialing Specialist      | Works in the internal context and may draft future enrollment work without gaining client publication authority.  |
| P5 Practice / Organization Owner | Uses a verified, read-only client context limited to assigned provider groups and the Enrollment Explorer report. |

Use only synthetic `.test` identities and the named seed organizations in [seed-universe.md](./seed-universe.md). No real client or provider data is permitted.

## Component & Data Constraints

The protected context must resolve before `__root.tsx` can mount `NoOrgScreen`, `AppShell` can mount global search, `Sidebar` can mount internal case/status hooks, or `useLandingRedirect` can route to Cases/Portfolio. `auth-store` currently auto-claims invites on login; this epic must separate staff-invite behavior from the new hashed client invite claim. A valid dual-capability user gets an explicit audience and organization chooser; permission union is forbidden. Invalid, revoked, or unresolved context fails closed.

New access data is private and service-only: `private.internal_staff` is an operator-maintained allowlist, `client_access` is verified auth-user plus organization, `client_group_grants` contains explicit child provider-group grants, and `client_invites` stores a hashed single-use seven-day token and claim audit. The project owner/operator bootstraps staff through an owner-approved manifest; there is no self-bootstrap. A client receives no `memberships` row. Selected-group assignment by internal admin and specialist draft/internal-admin publish or revoke are approved WP1.1 defaults.

The existing signed-in internal global-training workflow remains legitimate. Actor-capability enforcement applies to every protected request, including direct REST/RPC/storage and auth-only training surfaces, regardless of page or current UI. It preserves successful internal request/response shapes and does not redesign unrelated platform roles or training. Restricted external clients still receive only their verified organization and group grants; existing member reads and extension/API contracts remain unchanged.

Private tables stay unexposed to PostgREST, deny `anon` and `authenticated` through RLS, and receive narrow service-role grants. Browser report reads use the sanctioned dedicated API exception. The server resolves the actor from the verified JWT; every read and write rechecks organization, staff authority, client access, and group grants. New public RPC seams revoke `EXECUTE` from `PUBLIC`, `anon`, and `authenticated`, grant only `service_role`, use `SECURITY INVOKER`, and recheck the server actor. The future implementation must name and review the narrow protected edits to `src/routes/__root.tsx`, auth store, landing/login routes, `AppShell`, `Sidebar`, `src/server/api.ts`, and `src/server/guard.ts`; no AGENTS rule is changed by this epic.

## Features

### F6.12.1 — Resolve audience and organization before shell hooks

- **Description:** Add the guarded context seam that resolves verified auth, audience, organization, membership/allowlist authority, and client group grants before staff or client shell hooks mount.
- **Persona:** P1, P2, P5.
- **Benefit hypothesis:** Early, explicit context prevents stale staff hooks and cross-organization data from appearing in a client report.
- **Acceptance criteria:**
  - A valid internal context preserves all six internal nav links. `/reporting/enrollment-explorer` and its registry entry are reserved integration contracts; E6.12 proves client context and a synthetic denied-route fixture only. The later matrix/drawer/CSV slice ships the route, registry, and report UI.
  - A valid dual-capability user chooses audience and organization explicitly; no permission union is computed. Invalid, revoked, nonmember, and no-grant states fail closed with distinct UI states.
  - Changing auth, organization, audience, or grant revision cancels in-flight requests and clears query caches, filters, and open drawers before the next context mounts.
  - `useLandingRedirect`, global search, and Sidebar case/status hooks do not execute in client context.
- **Test/data scenario(s):** TS-163 (internal context and dual-capability chooser); TS-164 (client context and no-grant/invalid-context denial).

### F6.12.2 — Maintain private staff authority and restricted client grants

- **Description:** Establish the service-only access records and operator-owned staff allowlist without using client memberships or self-created roles.
- **Persona:** P1, P2, P5.
- **Benefit hypothesis:** Explicit org/group grants make the client cohort reviewable and prevent a valid login from becoming organization-wide access.
- **Acceptance criteria:**
  - `private.internal_staff` requires the project owner/operator’s owner-approved manifest plus valid organization membership and admin or specialist authority; a browser cannot self-bootstrap.
  - `client_access` is scoped to one verified auth user and organization. `client_group_grants` is the only client provider-group scope. No client membership row is written.
  - All new relations enforce same-organization coherence in the transaction and retain an audit event. No existing case, status, enrollment fact, or extension row is written.
  - Internal admins assign selected groups. Specialists may draft; internal admins publish or revoke in later publication work. This epic only proves the authority boundary.
- **Test/data scenario(s):** TS-164 (selected-group access and wrong-group denial); TS-165 (operator bootstrap, no self-bootstrap, and org isolation).

### F6.12.3 — Claim client invites atomically

- **Description:** Implement the requirements seam for a hashed, single-use, seven-day client invite with verified email equality and explicit child grants.
- **Persona:** P1, P5.
- **Benefit hypothesis:** A bounded claim flow gives a practice owner access to exactly the intended groups without auto-claiming staff invitations or sending unapproved mail.
- **Acceptance criteria:**
  - Claim verifies the authenticated email against the invite, atomically creates or updates `client_access`, creates the listed child grants, marks the token claimed, and appends an audit event.
  - Expired, already-claimed, mismatched-email, wrong-organization, and replayed tokens fail closed with no partial access or grant.
  - Tokens are hashed at rest; the URL is generated for a caller to deliver. Outbound email, notifications, and automatic claim of existing staff invites are out of scope.
- **Test/data scenario(s):** TS-165 (successful claim plus email mismatch, expiry, and replay); TS-166 (staff invite remains separate from client claim).

### F6.12.4 — Expose only sanctioned report API seams

- **Description:** Define the narrow browser-to-server exception and the positive/negative authorization evidence required before any external identity is activated.
- **Persona:** P1, P2, P5.
- **Benefit hypothesis:** A dedicated API prevents private-table and storage access from being inferred from UI visibility.
- **Acceptance criteria:**
  - Client and staff report hooks call only dedicated report APIs; private tables are not directly reachable through PostgREST or browser storage access.
  - Every service-role read independently applies organization and granted-group predicates. The server derives actor identity from the verified JWT; browser claims are advisory only.
  - Direct REST, RPC, storage, and existing auth-only function tests include anonymous, wrong-org, wrong-group, revoked-grant, and client-draft protected-resource denial using a local synthetic fixture, plus the legitimate signed-in internal training path. Publication draft-denial is verified in the later publication slice.
  - Native denial and regression evidence is recorded before hosted external tokens or client UAT. Synthetic local identities may exercise local schema and route work; this is not permission for hosted repair or release.
- **Test/data scenario(s):** TS-166 (external direct-surface denial while internal training remains available); TS-157 remains the shared-tier unauthenticated denial regression.

### F6.12.5 — Preserve future slice boundaries and review evidence

- **Description:** Keep this PR limited to trust-boundary prerequisites and provide evidence hooks for the later catalog/publication and matrix/drawer/CSV epics.
- **Persona:** All three personas.
- **Benefit hypothesis:** Sequential review prevents a broad report build from hiding an authorization defect.
- **Acceptance criteria:**
  - The PR changes requirements/docs, access-context implementation files, and their focused tests only; it does not add payer products, nullable scopes, proof publication, report matrices, CSV export, or WP1.2 behavior.
  - Future protected edits are explicitly listed in the parent contract and reviewed as a narrow browser-to-API exception; no AGENTS change is made.
  - The dedicated auth/RLS/public-surface review records effective privilege closure for direct REST/RPC/storage and existing auth-only APIs before hosted activation.
  - Future build routing is Luna/xhigh with Astra/high review. No code merge, release, or WP1.2 start occurs before WP1.1 end-to-end UAT and release approval.
- **Test/data scenario(s):** TS-163–TS-166 plus the denial evidence matrix in the requirements PR description.
