# E6.5 — Payer Setup Consolidation: Catalog + SOPs, Forms Folded In

## Purpose and Context

Making a payer workable is scattered across five surfaces today (catalog
browse, SOP templates, a portals registry, a training deck, a test runner)
plus an org-level MSO rules engine that generation never consults. Per
decision record decision 6 and Journey A's two-step model, this epic
consolidates payer readiness into ONE module with two tabs — **Catalog** and
**SOPs** — where portal setup lives INSIDE the SOP's online-form step
(register/pick portal → capture fields → train mappings → mock-data dry run →
publish), drift repair reopens the same editor, MSO delegation becomes payer
knowledge (catalog fact + SOP content), and Journey A's output is **global:
authored once, inherited by every org**. The module is org-independent — an
ops person works any payer to "ready for business" outside any onboarding
funnel, and a payer left unfinished never blocks anything (generic fallback,
visibly flagged).

## Personas Empowered

- P1 Credentialing Manager (ops hat) — stands payers up once, for the whole
  portfolio.
- P2 Credentialing Coordinator / Specialist — reaches the mapping/training
  machinery via deep links (drift cards, assigned work) with the same
  in-editor experience.

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Example/demo/test data uses scenario orgs and the seeded global payer
  catalog from [seed-universe.md](./seed-universe.md).
- Implementation dependencies (flagged, each a real lift):
  - **Global authoring:** today global (`org_id NULL`) payers/SOPs are
    platform/service-role-only; in-app authoring of global SOP + form
    content requires a deliberate RLS/grant design. Interim posture per the
    PM's simplification (two trusted users): module visible to all
    authenticated users; the authoring path writes global rows through a
    guarded server path — the exact mechanism is a §5 reviewer/build
    decision, flagged loudly, with the platform-role hardening deferred to
    the R7 "richer roles" work.
  - **Mock-data dry run:** replaces the org-test-provider dry run with a
    masked synthetic profile (fake-but-realistic values; never real PHI);
    dry-run fills remain telemetry-only (`is_test`) and never touch live
    data or real portals in CI.
  - **Portal fold-in:** portal registration/capture/train UI re-homes into
    the SOP form step; the portal registry table remains as storage (reuse,
    not rebuild). Portal reuse across SOPs/steps is a user-driven picker.
  - **MSO retirement:** the rules engine and admin page retire; existing
    delegated paths are re-encoded as payer SOPs BEFORE the page dies
    (operator checklist in the implementation PR).

## Features

### F6.5.1 — The two-tab module

- **Description:** `Payer Setup` (workspace zone, all roles for now) with
  two tabs backed by real URL segments: **Catalog** (canonical payers,
  curated facts: covered states, kind, the payer's own name for its
  provider ID, delegation/MSO facts; missing payer = platform request,
  never free-text) and **SOPs** (the library + editor). The five legacy
  surfaces (payer-admin tabs, portals registry page, training deck route,
  test runner route, payer-directory admin actions) redirect here; the
  read-only public catalog browse stays available to non-admin roles.
  A per-payer readiness funnel row ("Ready for business" / what's missing)
  heads the module.
- **User story:** As P1 (ops), everything about making a payer workable is
  two tabs, and "is Anthem ready?" is one glance.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Five surfaces → one module; the funnel's next
  action always names the one thing to do next.
- **Acceptance criteria:**
  - Tabs are routes (shareable, breadcrumbed); redirects per E6.1's table.
  - The funnel derives per payer: SOP published? form proven? — separate
    signals, one dominant next action; a payer with neither still renders
    honestly.
  - No org data anywhere in the module; no denial vocabulary here.
- **Test/data scenario(s):** TS-114.

### F6.5.2 — Portal setup inside the SOP form step

- **Description:** Authoring an `online_form` step carries the full form
  machinery in place: pick an existing portal for this payer (user-driven
  reuse picker) or register URL + key → capture the form's fields → train
  field-to-token mappings card-by-card (dictionary keeps learning) →
  dry run → publish. One portal per task rule stands; the standalone
  Forms & Portals page and training deck retire into this editor.
- **User stories:**
  - As P1 authoring Anthem's SOP, proving the form fillable is part of
    writing the step, not a detour across three other pages.
  - As P1 authoring a SECOND SOP (or template version) that uses the same
    Anthem portal, the step editor's reuse picker offers the payer's
    existing portals first — user-driven, never auto-linked.
  - As P2 arriving via a drift card or an assigned task, I land inside the
    exact step whose mappings need work, with the same training UI ops
    used at authoring time.
  - As P1, the SOP list tells me at a glance which templates carry a
    proven form and which are still unproven.
- **Persona:** P1, P2 (via deep link).
- **Benefit hypothesis:** The thing you configure and the place you use it
  become the same place; the scattered forms pipeline disappears as a
  concept.
- **Acceptance criteria:**
  - Register/pick, capture, train all complete without leaving the step
    editor; reuse picker offers this payer's existing portals first.
  - Mapping approvals write the same stores as today (field maps,
    dictionary); the extension's fill behavior is unchanged.
  - The step shows its form-readiness state (unproven / trained / proven)
    inline and on the SOP list row.
- **Test/data scenario(s):** TS-114.

### F6.5.3 — The mock-data dry run

- **Description:** The dry run executes the fill against a **masked
  synthetic profile** (realistic shapes, fake values — never real PHI, no
  org context, no designated test provider). Run once per payer form —
  never re-tested per org. Passing flips the form to proven; the result is
  recorded as test telemetry only.
- **User story:** As P1, I prove the mappings BEFORE any user starts
  casework, without borrowing a real person's data.
- **Persona:** P1.
- **Benefit hypothesis:** Deletes the test-provider dependency (and its
  blocked empty state) entirely; proof moves to authoring time.
- **Acceptance criteria:**
  - Dry runs never read provider tables and never write anything but test
    telemetry; the synthetic profile is fixed, versioned fixture data.
  - A passing run marks the form proven on the funnel; a failing run lists
    the unmatched fields for immediate re-training.
  - Real-fill drift detection ignores dry runs (existing rule preserved).
- **Test/data scenario(s):** TS-114.

### F6.5.4 — Drift repair, in the same editor

- **Description:** When a real fill reports fields not found (a portal
  changed its form), a needs-attention badge appears on the module entry
  and the payer's funnel row; opening it lands INSIDE the owning SOP form
  step with the broken mappings queued for re-training. The Fix-it deck
  retires; casework continues manually on affected fields meanwhile
  (warn, never block).
- **User story:** As P2 hitting a broken fill, the fix is one deep link
  into the exact step that defined the mapping.
- **Persona:** P1, P2.
- **Benefit hypothesis:** Repair happens where authoring happened; no
  separate queue surface to learn.
- **Acceptance criteria:**
  - Drift derivation reuses the existing real-fill telemetry rules
    (dry runs excluded); badge counts appear on the sidebar entry and
    funnel row.
  - Repair flow = the F6.5.2 training UI scoped to broken mappings; a
    completed repair clears the badge.
- **Test/data scenario(s):** TS-114.

### F6.5.5 — MSO delegation becomes payer knowledge

- **Description:** The MSO routing rules engine and its admin page retire.
  Delegation is recorded where it belongs: the catalog entry carries the
  delegation fact ("credentialing delegated to {MSO} in {states}") and the
  payer's SOP (state-variant where needed) carries the delegated path's
  actual steps. Migration task: before retirement, every live delegated
  arrangement is re-encoded as payer SOP content (operator checklist in
  the implementation PR); UM-only arrangements are never encoded as
  credentialing routing.
- **User story:** As P1, "how do you credential with this payer in NC"
  has one answer in one place — the payer's SOP — whether direct or
  delegated.
- **Persona:** P1.
- **Benefit hypothesis:** Removes an org-level rules engine that
  generation never consulted; the concept survives at the grain where it
  is true (the payer).
- **Acceptance criteria:**
  - No MSO rules are consulted anywhere at case creation; the admin page
    redirects; the delegation facts render on catalog entries.
  - The re-encoding checklist is completed and verified before the page
    retires (build-gate, not an afterthought).
- **Test/data scenario(s):** TS-114.

### F6.5.6 — Authored once, inherited by every org

- **Description:** Journey A output (catalog facts, SOPs, form setup,
  proven mappings) is global: any org attaching the payer inherits a
  working SOP and fillable form with zero additional setup. Org-level SOP
  overrides remain possible (existing resolution tiers unchanged: org
  override → global payer → generic fallback). The authoring surface is
  open to all authenticated users for now (two trusted admins); the
  platform-role hardening is explicitly deferred to R7 and flagged as a
  governance risk in the module (visible note, not buried).
- **User story:** As P1 running an 11-org portfolio, standing Anthem up
  once means every current and future client org gets it.
- **Persona:** P1.
- **Benefit hypothesis:** Operational cost of payer management drops from
  per-org to once — the PM's stated goal for the standalone module.
- **Acceptance criteria:**
  - A second org attaching a globally-ready payer generates cases with the
    global SOP + proven form, zero setup steps.
  - Resolution tier order and stamping are unchanged; org overrides still
    beat global.
  - The interim-governance note renders in the module; the R7 deferral is
    recorded in the roadmap.
- **Test/data scenario(s):** TS-114.

## Dependencies

- E6.1 redirects point at this module; E6.3 consumes SOP resolution
  unchanged.
- Reused verbatim: SOP versioning/publish, resolution tiers + stamping,
  field-map + dictionary stores, fill telemetry, catalog data.
- Global-authoring write path and the mock-profile fixture are the two new
  technical enablers (loud §5 items for the reviewer).
- MSO re-encoding operator checklist gates the rules-engine retirement.

## Out of Scope / Non-Goals

- No platform-role/permission system (R7); no org data in the module.
- No BCC/auto-send or any extension contract change; the extension still
  fills, humans still submit — locked, forever.
- No free-text payer creation; catalog additions stay platform requests.
- Denial vocabulary and queue ranking are NOT here (fixed defaults; E6.6).
