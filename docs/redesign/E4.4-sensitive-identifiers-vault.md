# E4.4 — Sensitive Identifiers Vault: Zero-Trust Full SSN

## Purpose and Context

Payer portal fills need the full SSN, but today the system stores `ssn_last4`
only (locked decision, AGENTS.md — held "until the R6/R7 Sensitive
Identifiers Vault": this epic is that vault). `[r6]` decision C sets the
compliance bar as **zero-trust**: the full SSN is **fill-only** for the
extension and virtually never displayed in the application UI; the default UI
everywhere is tight minimalist masking (`***--1234`). Edge-case viewing goes
behind a deliberate Admin-only **Click to Reveal** that writes an immutable
audit event (Who, When, Which Provider, Justification). Ingress is ideally
the provider or an authorized org rep via a **secure, time-expiring intake
link**; when internal staff must transcribe from a legacy intake form, a
**secure input modal** encrypts the value immediately on save.

This epic supersedes the `ssn_last4`-only rule in a controlled way: the
last-4 remains the ONLY value ordinary reads ever return; the full value
lives encrypted in a separated vault surface with its own access path,
never in ordinary query results, exports, logs, or list payloads.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — fills portals with the
  full SSN via the extension without ever seeing it.
- **P1 Credentialing Manager (Admin)** — the only role able to reveal, with
  justification, when an edge case demands it.
- **P5 Practice / Organization Owner (org rep)** and providers — enter the
  SSN themselves via the secure intake link, keeping staff out of the
  loop entirely.

## Component & Data Constraints

- Additive schema only; the vault is a separated storage surface (never a
  column ordinary selects can touch) with encryption at rest and scoped,
  audited access paths — reviewer proposes the concrete mechanism
  (pgsodium/pgcrypto vs. app-layer envelope encryption, RLS + definer RPC
  shape) in §5.
- `audit_log` is append-only (AGENTS.md); reveal events ride it.
- The intake-link flow follows the E0.5 secure-token patterns (hashed
  token, single-use, expiry, uniform invalid responses per E0.7
  hardening).
- UI surfaces build from the current component library; scenario data from
  [seed-universe.md](./seed-universe.md).

## Features

### F4.4.1 — Vault storage & universal masking

- **Description:** Full SSNs are stored encrypted in the vault; every
  application surface (provider profile, lists, exports, API payloads,
  extension detail views) renders at most the mask `***--1234` sourced from
  `ssn_last4`. No ordinary read path can return the full value.
- **Persona:** all.
- **Benefit hypothesis:** zero-trust default (C1) — compliance exposure is
  reduced to explicitly audited moments.
- **Acceptance criteria:**
  - The full SSN appears in no list, detail, export, log, or standard API
    response; masking is `***--1234`.
  - Vault values are encrypted at rest; a direct table read (e.g. via
    PostgREST) cannot decrypt.
  - `ssn_last4` behavior everywhere else is unchanged.
- **Test/data scenario(s):** TS-84.

### F4.4.2 — Fill-only release to the extension

- **Description:** The extension's fill flow may request the full SSN for a
  provider it is actively filling — a dedicated, audited, fill-only release:
  the value goes into the portal form field, is never rendered in the
  extension UI (masked display only), and every release writes an audit row
  (actor, provider, case context).
- **Persona:** P2.
- **Benefit hypothesis:** the entire point of vaulting (C1) — portals get
  the value; humans don't.
- **Acceptance criteria:**
  - A fill-only endpoint/token category releases the full value solely in
    the fill payload path with `no-store` semantics; the extension UI shows
    the mask.
  - Each release writes an audit event with case/provider context.
  - Requests outside an active fill context are rejected.
- **Test/data scenario(s):** TS-85.

```gherkin
Feature: Fill-only SSN release
  Scenario: Portal fill uses the SSN the specialist never sees
    Given a vaulted SSN for a provider and P2 filling that provider's portal form
    When the extension fills the SSN field
    Then the portal input receives the full value
    And the extension UI displays only ***--1234
    And an audit row records the release with actor, provider, and case
```

### F4.4.3 — Admin Click-to-Reveal with justification

- **Description:** On the provider record, an Admin-only "Click to Reveal"
  requires a typed justification, reveals the value briefly (auto-rehide),
  and immediately logs an immutable audit event: Who, When, Which Provider,
  Justification.
- **Persona:** P1 (Admin only).
- **Benefit hypothesis:** the escape hatch exists (C2) without weakening the
  default — every reveal is deliberate and accountable.
- **Acceptance criteria:**
  - Non-admin roles never see the reveal control.
  - Reveal requires a non-empty justification; the audit row carries it.
  - The revealed value auto-rehides (short fixed window) and is never
    written into the DOM longer than displayed or into any log.
- **Test/data scenario(s):** TS-86.

### F4.4.4 — Secure ingress: time-expiring intake link + internal secure modal

- **Description:** Two ingress paths. (1) **Intake link:** an admin issues a
  secure, time-expiring, single-use link to the provider or authorized org
  rep, who enters the SSN on a minimal branded page (E0.5 patterns:
  recipient binding, expiry, used/expired lockdown, uniform invalid
  responses); the value encrypts on submit and is never echoed back. (2)
  **Internal secure modal:** for legacy paper intake, staff enter the value
  in a dedicated modal that encrypts immediately on save, displays the mask
  on success, and writes an ingress audit row.
- **Persona:** P5 / provider (link), P1/P2 (modal).
- **Benefit hypothesis:** ingress shifts to the data owner where possible
  (C3), and the internal fallback never leaves plaintext lying around.
- **Acceptance criteria:**
  - Link: single-use, expiring, provider-bound; used/expired states locked
    down; submission stores encrypted and confirms with the mask only.
  - Modal: value encrypts on save, is never shown again post-save, and the
    ingress is audited.
  - Neither path accepts the value into any other form field (the E3.0
    reject-never-truncate CSV rule stands — CSV import never carries full
    SSNs).
- **Test/data scenario(s):** TS-87.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the crypto surface
(`pgcrypto` is enabled `WITH SCHEMA "extensions"` in
`20260704210000_baseline_live_schema.sql`; **no** pgsodium and no Supabase Vault
extension present), the `ssn_last4`-only rule (`providers.ssn_last4` +
`providers_ssn_last4_check char_length = 4`, AGENTS.md), the audit spine
(`audit_log` with the `READ` action added by
`20260705190000_audit_log_read_action_type.sql`; append-only), the E0.5 secure
hashed-token pattern (`20260709140000_party_capture_links.sql` — 256-bit token
from two `gen_random_uuid()`s, only the `sha256` hash stored, single active,
lazy expiry, `anon` SECURITY DEFINER validate/submit RPCs that touch only the
authorized party/org) hardened by E0.7, the extension fill path (E4.3 §5 + the
`no-store` provider-profile contract), and `uiux-component-guide.md`.
**Headline:** this is a genuinely new, security-critical storage surface — the
first place the system holds a decryptable secret. The architecture is
well-precedented (definer RPCs + REVOKE-the-table + hashed-token ingress all
exist), and pgcrypto is available, so the build is feasible without new
infrastructure. The ONE decision that needs the PM/security owner is where the
encryption key lives (in-DB pgcrypto symmetric vs. app-layer envelope with an
external KMS) — everything else follows from it. This is flagged, not guessed._

- **TE-1 — Separated vault table, never selectable by ordinary paths
  (F4.4.1).** Store the ciphertext in a dedicated `provider_ssn_vault`
  (`provider_id` unique + `org_id` + `ssn_ciphertext bytea` + `algo`/`key_version`
  metadata + `created_by`/`created_at`), NOT a column on `providers`. Lock it
  down like the capture-link precedent: `REVOKE ALL` from `anon` **and**
  `authenticated` on the table, RLS enabled, and NO ordinary SELECT grant — the
  only access is through the SECURITY DEFINER RPCs below. `providers.ssn_last4`
  stays exactly as-is and remains the ONLY value any ordinary read, list,
  export, report, or `/api` payload ever returns; masking is `***--1234` derived
  from it. A direct PostgREST/`authenticated` read of the vault returns nothing
  (no grant) and could not decrypt anyway (TE-2). Additive migration repo +
  hosted; register row added; `types.ts` regenerated (the table carries no
  client-readable secret column).

- **TE-2 — Encryption mechanism: two viable options, key management is the PM
  decision.** pgcrypto is present, so both are buildable:
  - **Option A — in-DB pgcrypto symmetric.** `pgp_sym_encrypt/decrypt` inside
    SECURITY DEFINER RPCs; the symmetric key is supplied to the RPC (e.g. from a
    Postgres GUC/`current_setting` set from a server secret, or Supabase Vault if
    later enabled) and NEVER stored beside the ciphertext. Simplest; keeps
    plaintext only inside the definer function for the duration of a call.
  - **Option B — app-layer envelope encryption.** The Nitro server encrypts with
    a data key wrapped by an external KMS (AWS KMS/GCP KMS); the DB stores only
    ciphertext + wrapped-key metadata. Strongest key isolation (the DB never sees
    the key), at the cost of a KMS dependency and new server code.

  **Reviewer recommendation:** Option A for R6 (no new infra, matches the
  existing definer-RPC posture), with the table's `algo`/`key_version` columns
  designed so a later migration to Option B is additive. **PM/security-owner
  decision required** on which, and specifically on where the master key lives
  (server env secret vs. KMS) — see flags. Do not build until this is answered;
  the rest of the epic is independent of the choice.

- **TE-3 — Fill-only release + admin reveal are two audited SECURITY DEFINER
  RPCs (F4.4.2, F4.4.3).** Both decrypt only inside the function and return the
  plaintext exactly once:
  - `release_ssn_for_fill(p_provider_id, p_case_id)` — callable only in an active
    fill context (validates the case belongs to the caller's org and the
    provider is on it, mirroring the extension route guards); returns the full
    value solely into the fill payload path with `no-store`; writes an
    `audit_log` `READ` row (actor, provider, case) — never the value. The
    extension UI shows only the mask (E4.3 TE-5 seam). Requests outside an active
    fill are rejected.
  - `reveal_ssn(p_provider_id, p_justification)` — `user_role(org_id) = 'admin'`
    only; requires a non-empty justification; returns the value for a brief
    client-side auto-rehide window and writes an immutable `audit_log` `READ` row
    carrying Who/When/Which-provider/Justification (in `description`/`after`).
    Non-admins never receive the control (role-gated UI) and the RPC re-checks
    server-side. The revealed value is never written to any log and lives in the
    DOM only for the display window.

- **TE-4 — Ingress: intake link (E0.5 pattern) + internal secure modal
  (F4.4.4).** The intake link reuses the capture-link machinery: a new
  `provider_ssn_intake_links` table with the identical shape (hashed token only,
  single active, expiry, state `active|used|expired|revoked`, lazy expiry) and an
  `anon` SECURITY DEFINER `submit_ssn_intake(p_token, p_ssn)` that validates the
  hash, encrypts on submit via TE-2, sets `ssn_last4` from the last four, writes
  an ingress audit row, flips the link to `used`, and echoes back ONLY the mask —
  never the value. The internal secure modal calls an authenticated definer
  `store_ssn(p_provider_id, p_ssn)` (writer/admin per the PM's ingress-role call)
  that encrypts on save, returns the mask, and audits. **Neither path accepts the
  value into any other field**, and the E3.0 reject-never-truncate rule stands —
  CSV import never carries a full SSN (no code path from import to these RPCs).

- **TE-5 — No leakage surfaces.** Explicit build checks: the vault table is
  absent from every service SELECT and from `types.ts` client reads; the full
  value never enters `console`/server logs (the profile route's no-body-logging
  rule extends here); exports and reports read `ssn_last4` only; the extension
  fill payload marks the SSN token as fill-only-category (E4.3 TE-5) so it is
  placed into the portal input but not rendered. e2e (mock harness) covers
  TS-84–TS-87: masking everywhere / no ordinary decrypt, fill-only release + UI
  mask + audit, admin-vs-non-admin reveal with justification + immutable audit,
  and both ingress paths (link + modal) encrypt-on-save + lockdown.

### Open items / flags for the PM (one decision needed)

- **Encryption key management (REQUIRED before build):** choose Option A (in-DB
  pgcrypto symmetric, key from a server secret/GUC) or Option B (app-layer
  envelope with external KMS), and name where the master key lives. Reviewer
  recommends Option A for R6 with a Option-B-ready schema. This is the single
  gating decision; the epic is otherwise fully specified.
- **Ingress role for the internal modal (minor):** confirm whether the
  `store_ssn` modal is `specialist`+`admin` or `admin`-only. Reviewer default:
  writer roles (`specialist|admin`), consistent with other case-side writes;
  reveal stays admin-only regardless.
- **Controlled supersession of the `ssn_last4`-only locked decision** is explicit
  here per authoring rule 4: the last-4-only rule continues to govern every
  surface outside these vault RPCs. No silent contradiction — recorded for the PM.
