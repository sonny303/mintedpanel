# E0.6 — Reporting Center & Portfolio Dashboard

## Purpose and Context

Establishes a **Reporting Center** as a first-class, cross-org area of Minted Panel and delivers the **Portfolio dashboard** as its first report. This closes Stage 0 and is the first payoff of the Full Party model (E0.3): because a party (the Credentialing Manager) holds roles across many orgs, a cross-org portfolio view becomes meaningful. The Reporting Center is a container built to hold future reports (Stage 4 outcomes, Stage 5 recurring). Implements the Portfolio thread and the decoupled-shareable-dashboard requirement from E0.0, and the seed strategy in [seed-universe.md](./seed-universe.md).

This epic also introduces the app's **segmented navigation IA** (top employee/cross-org work vs. bottom organization/org-scoped). That model supersedes E0.0's journey-ordered sidebar — see the "Navigation IA" section and the flagged revision note.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — primary user; opens the Reporting Center, reads the Portfolio dashboard, generates shares.
- **P4 Company Owner / Ops Lead** — recipient of an internal secure share (full cross-org view of the business).
- **P5 Practice / Organization Owner** — recipient of a filtered secure share scoped to their own org only.

Personas match the E0.0 master table. No new personas introduced.

## Component & Data Constraints

- Built only from the current component library — see [uiux-component-guide.md](./uiux-component-guide.md) and [README.md](./README.md).
- Example/demo/test data uses scenario orgs and personas from [seed-universe.md](./seed-universe.md); the Oregon prospect org (Rose City Rehab Collective) is always present in demo/test.
- Portfolio report content MUST be rendered chrome-independent (decoupled from the workspace sidebar) per E0.0 F0.0.5, so the same content renders inside the Reporting Center and inside a standalone shared view.
- Org lifecycle state (prospect / active / inactive) is internal-only per E0.0; the dashboard uses it to compute metrics but never exposes a user-managed status label.
- Any requirement tied to schema (lifecycle state source, party/role reporting, share-token storage) is flagged as an implementation dependency, not an assumption.

## Features

### F0.6.1 — Reporting Center as a cross-org area

- **Description:** A top-segment "Reporting Center" destination in the left sidebar (cross-org; does not require an active org). It lists available reports; in Stage 0 it contains exactly one — the Portfolio dashboard. Built to hold more reports later.
- **Persona:** P1
- **Benefit hypothesis:** Giving reporting a dedicated home means Sowmya always knows where to look for a cross-org picture, and future reports have a consistent place to land rather than scattering across the app.
- **Acceptance criteria:**
  - "Reporting Center" appears in the TOP (cross-org) nav segment and opens without requiring an active org.
  - The Reporting Center lists available reports; the Portfolio dashboard is present.
  - Opening a report renders it within the Reporting Center.
  - The area is structured to accept additional reports without redesign.
- **Test/data scenario(s):** TS-4 (multi-org portfolio incl. Rose City Rehab Collective, OR).

```gherkin
Feature: Reporting Center is a cross-org destination
  Scenario: Sowmya opens the Reporting Center
    Given I am P1 with multiple orgs seeded
    When I select "Reporting Center" from the top nav segment
    Then it opens without requiring an active org
    And I see the Portfolio dashboard listed as an available report
```

### F0.6.2 — Portfolio metrics (prospects + in-motion)

- **Description:** The Portfolio dashboard shows two headline metrics — a prospects count and a separate in-motion count. Internally inactive/archived orgs are excluded from both.
- **Persona:** P1
- **Benefit hypothesis:** Separating prospects from in-motion prevents conflating "still selling" with "actively working," so Sowmya reads the true state of the business at a glance.
- **Acceptance criteria:**
  - A prospects count and a separate in-motion count are shown.
  - Inactive/archived orgs are excluded from both counts.
  - Metrics are computed from internal org lifecycle state, not a user-facing label.
- **Test/data scenario(s):** TS-3 (mixed portfolio: active + prospect + inactive).

```gherkin
Feature: Portfolio headline metrics
  Scenario: Prospects and in-motion counted separately, inactive excluded
    Given I have "Dillon Sports Medicine" (active), "Lone Star Rehab Group" (prospect), and "Outer Banks Therapy Group" (inactive)
    When I open the Portfolio dashboard
    Then "Lone Star Rehab Group" is counted in prospects
    And "Dillon Sports Medicine" is counted in in-motion
    And "Outer Banks Therapy Group" is excluded from both counts
```

### F0.6.3 — Org list

- **Description:** Below the metrics, a listing of the operator's orgs with key info (org name, state, and customer/sales context as available). Inactive orgs remain visible (never deleted) but are excluded from the in-motion/prospect counts.
- **Persona:** P1
- **Benefit hypothesis:** A single list of every org — including inactive — gives Sowmya a complete book of business in one place, with no record ever lost.
- **Acceptance criteria:**
  - All of the operator's orgs are listed, including inactive.
  - Each row shows at least org name and state.
  - Inactive orgs are visually distinguishable but present.
  - The list reads from the org + party/role data established in E0.1–E0.3.
- **Test/data scenario(s):** TS-5 (scale portfolio, all seed orgs).

```gherkin
Feature: Portfolio org list
  Scenario: All orgs listed including inactive
    Given I have the full seed portfolio including one inactive org
    When I open the Portfolio dashboard
    Then every org is listed with its name and state
    And inactive orgs are shown but visually distinct
```

### F0.6.4 — State / geography breakdown

- **Description:** A breakdown of the portfolio by state, aligned to the seed/payer-SOP states (NC, SC, CO, TX, WI, OR). Shows how the book of business distributes geographically.
- **Persona:** P1
- **Benefit hypothesis:** Because payer/SOP work is state-driven, a geographic breakdown tells Sowmya where her volume concentrates and which state playbooks matter most.
- **Acceptance criteria:**
  - The dashboard shows a count of orgs by state.
  - States reflect actual seed data (NC, SC, CO, TX, WI, OR).
  - Inactive orgs are excluded from the state in-motion breakdown (consistent with F0.6.2).
- **Test/data scenario(s):** TS-5 (scale portfolio spans multiple states).

```gherkin
Feature: Portfolio state breakdown
  Scenario: Orgs grouped by state
    Given my portfolio spans NC, SC, CO, TX, WI, and OR
    When I open the Portfolio dashboard
    Then I see a per-state count of orgs
    And the states shown match the seeded org states
```

### F0.6.5 — Secure, filtered, read-only share (outbound)

- **Description:** P1 can generate a secure link to share a **read-only** view of the Portfolio dashboard. The share is recipient-specific and expiring (E0.5-style rigor) and **filterable in scope**: a full portfolio share to an internal recipient (P4), or a share filtered to a single org for that org's owner (P5). This link is OUTBOUND and read-only — explicitly distinct from E0.5's inbound capture link (see the distinction table below).
- **Persona:** P1 (generates); P4 and P5 (recipients).
- **Benefit hypothesis:** A secure, scoped, read-only share lets Sowmya show the business (or one client their own progress) without exposing other clients' data or requiring a login — making the portfolio her first outbound reporting pattern.
- **Acceptance criteria:**
  - P1 can generate a share link for the Portfolio dashboard.
  - The share is recipient-specific and expires (30-day default, revocable — see Devin section; diverges from E0.5's 72h per PM decision).
  - The share is read-only — the recipient can view, never edit.
  - Scope is filterable: full portfolio (internal, P4) or single-org (P5 sees only their org).
  - A filtered single-org share never exposes other orgs' data.
  - The shared view renders the chrome-decoupled portfolio content (per E0.0), with no workspace nav.
- **Test/data scenario(s):** TS-4 (full share to P4); a single-org filtered share of "Rose City Rehab Collective" (OR) to its owner (P5).

```gherkin
Feature: Secure filtered read-only portfolio share
  Scenario: Filtered single-org share to a practice owner
    Given I am P1 viewing the Portfolio dashboard
    When I generate a share scoped to "Rose City Rehab Collective" for its owner's email
    Then a secure, expiring, read-only link is created
    And opening it shows only "Rose City Rehab Collective" data
    And no other org in my portfolio is visible in that shared view

  Scenario: A filtered share never leaks other orgs
    Given a single-org filtered share exists for one org
    When the recipient opens it
    Then they can view but not edit
    And they cannot see any org outside the shared scope
```

### F0.6.6 — Reporting Center is extensible (container)

- **Description:** The Reporting Center is structured so future reports (Stage 4 owner outcomes, Stage 5 recurring/expirations) can be added without re-architecting the area. Stage 0 ships only the Portfolio report; no other report content is scaffolded.
- **Persona:** P1
- **Benefit hypothesis:** Designing the Center as a container now means later reporting epics slot in cleanly, keeping all reporting in one coherent place instead of scattering.
- **Acceptance criteria:**
  - The Reporting Center can list more than one report without redesign.
  - Only the Portfolio report is delivered in Stage 0; no Stage 4/5 report content is stubbed.
  - Adding a future report does not require changing the Portfolio report.
- **Test/data scenario(s):** N/A (structural); validated via F0.6.1 scenario.

The single-org scope filter is enforced **server-side inside the SECURITY DEFINER function**, never client-side, so a filtered share cannot leak other orgs even if the client is tampered with.

### Tech-debt findings (Devin populates)

- **TD-1 — E0.0 nav supersession lands in this PR.** The old flat/journey routes (`home`/`providers`/`cases`/`admin.*`, and the E0.0 journey items) plus `/portfolio` must stay URL-reachable (redirect/alias) even though the nav no longer lists them — otherwise old links dead-end (violates E0.4). Covered by TE-3; must have a redirect test or it rots.
- **TD-2 — Second public unauthenticated surface (share route).** After E0.5's capture link, `/share/:token` is the second anon-reachable path. Controls: ≥128-bit token entropy, hash-only storage, rate-limit `validate_report_share`, server-side scope enforcement, narrow anon grants. Read-only (no write RPC) meaningfully lowers risk vs E0.5.
- **TD-3 — Lazy expiry.** `expires_at` is evaluated at validate-time; no background sweeper flips rows to `expired`. State returned to the recipient is correct; the stored `state` may lag. Acceptable for Stage 0 (same as E0.5 TD-3); a sweep job is future work.
- **TD-4 — 30-day shares accumulate; revoke is manual.** No auto-cleanup of expired/old shares; P1 revokes manually. A retention/sweep policy is deferred.
- **TD-5 — Org geography source.** The state breakdown depends on a reliable per-org state. If orgs lack an explicit state column, it is derived from the owner party's split-address state (E0.1–E0.3); orgs missing that address land in an "Unknown" bucket rather than being dropped. A first-class org-state field is future work if geography reporting becomes central.
