# E4.3 — Extension Workbench Handoff: Read-Only Fill, Cohesive Case Execution

## Purpose and Context

`[r6]` decision B: the workbench extension and the webapp platform must be a
**cohesive duo where handoff is seamless** — the user experiences nothing
missed between working a case on the platform and moving to a payer portal
with the extension guiding case completion, logging it, and bringing the next
best action, all from the same view. **The platform tells you what to do; the
extension is what you complete it with.** When SOP/fill data is missing, the
flow ties into the existing fix-it game (field dictionary) to increase the
data value the extension provides.

For this release the extension is **tightly scoped to read-only token
resolution** — reading case/provider data to fill portal forms — to establish
a reliable, low-latency form-fill experience first. Logging/submission stays
**manual** from the extension into the Touch log (the existing R2 Workbench
workflow remains, now with E4.1 structured types). The PM notes the extension
must eventually be more than a form filler (email tasks, etc.) — recorded as
a non-goal/roadmap note, not R6 scope.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — works a case's tasks on a
  payer portal with the extension filling from the same case context she
  left in the webapp, logs the touch, and moves to the next best action.
- **P1 Credentialing Manager** — trusts that portal work is logged against
  the right case with no duplicate bookkeeping.

## Component & Data Constraints

- Extension consumes the existing server API surface (`/api/*`, org/role
  guarded, dual-path rule) — read endpoints only for fill data; the one
  write remains the existing manual submission-touch endpoint.
- The most PHI-dense payload (provider profile) rules hold: `no-store`,
  no body logging, audit rows on reads (existing contract).
- Webapp surfaces build from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Full-SSN fill tokens are E4.4's contract; this epic only reserves the
  seam (fill-only token category) and must not render SSN values.

## Features

### F4.3.1 — Case-context handoff (platform → extension)

- **Description:** From a case (detail or My Cases queue row), "Work in
  portal" hands the exact case context to the extension: the extension's
  side panel opens on that case — provider, payer, state, facility, open
  SOP tasks, and tracking ID — without the specialist re-searching or
  re-selecting anything. The extension's existing case picker remains for
  direct entry, but the handoff path is primary.
- **Persona:** P2.
- **Benefit hypothesis:** seamless handoff (B) removes the re-orientation
  cost at exactly the moment work moves to the portal — nothing missed
  between the two surfaces.
- **Acceptance criteria:**
  - Launching from a case lands the extension on that same case (org,
    case, provider, facility context all correct).
  - The extension view shows the case's open tasks and pipeline state
    read-only, matching the webapp. Each task renders its E4.2
    **execution type** (`extension_fill` / `manual` / `auto_verify` /
    `document_attach`): `extension_fill` tasks are the ones offering the
    fill action; the others render as read-only checklist context (their
    automated behaviors belong to E4.5/R7). This is the "workbench
    payload tee-up" E4.2 F4.2.1 promised.
  - **Panel identity guard:** the panel header always names the org,
    provider, payer/state, and selected facility it is operating as —
    a multi-org user can never be silently filling from the wrong org
    or case.
  - **Degraded paths are explicit, never silent:** if Chrome messaging or
    the extension is unavailable, the portal tab still opens and the
    webapp shows a one-line non-blocking notice ("extension not detected
    — use its case search"); if the extension is signed out or on a
    different org, the panel prompts sign-in/org selection and discards
    the mismatched context rather than showing another org's case; when
    the handoff context expires (tab close / 60-min idle, TE-1) the panel
    says so and offers re-launch or the case picker — it never keeps
    filling from expired context.
  - A second "Work in portal" launch (same or different case) replaces
    the pending context — last launch wins, shown in the panel; no
    stacked or ambiguous contexts.
  - No new write path is introduced by the handoff.
- **User journey:**
  - P2 has the case open (or its My Cases row) → clicks "Work in
    portal" → the portal tab opens, the side panel is already on that
    case: identity header, open tasks with execution types, pipeline
    state, tracking ID → she starts the top `extension_fill` task
    without searching anything.
  - Extension missing: same click, portal opens, notice shown, she works
    from the panel's case picker exactly as in R2 — nothing is blocked.
- **Test/data scenario(s):** TS-80.

```gherkin
Feature: Seamless case handoff
  Scenario: Working a case moves to the portal without re-selection
    Given P2 has a case open in the webapp with 3 open SOP tasks
    When she launches the extension from that case
    Then the extension panel shows that case's provider, payer, tasks, and tracking ID
    And filling the portal uses that case's resolved tokens
```

### F4.3.2 — Reliable low-latency read-only fill

- **Description:** The extension fills portal forms via the existing
  token-resolution path (provider profile + field maps), scoped read-only.
  R6 hardens this into the dependable core loop: resolved values fill
  fast, unresolved tokens are visibly listed with reasons (existing
  `unresolved` contract), and facility selection follows the established
  needs-facility rules.
- **Persona:** P2.
- **Benefit hypothesis:** B's explicit priority — establish a reliable,
  low-latency form-fill experience before any write-back ambition.
- **Acceptance criteria:**
  - Fill uses only read endpoints; no extension-initiated data mutations
    besides the existing manual touch logging.
  - Unresolved tokens are surfaced to the user with reasons, never
    silently skipped.
  - **Per-field fill result, always:** after a fill pass the panel shows
    a compact per-field summary — filled / unresolved (with reason) /
    manual-skip — so a partial fill is never silent; the specialist
    verifies before submitting on the portal. The extension never
    auto-submits the portal form.
  - **Facility selection is explicit:** when the profile returns
    `needs_facility`, the panel presents the case's facility choices
    (from the handoff context / profile `facilities` set) and fills only
    after selection — the established never-guess rule, surfaced as UX
    rather than a dead end.
  - **Latency is an acceptance bar, not an aspiration:** on the seeded
    mock harness, case context visible ≤ 1s p95 and fill-ready ≤ 2s p95
    after launch (TE-3 budget), excluding portal DOM wait.
  - API/auth failures show a generic actionable error with a retry;
    an expired platform session prompts re-auth and clears in-memory
    PHI (TE-3) — no stale values fill after sign-out.
- **User journey:**
  - Panel shows "fill ready" → P2 clicks fill on the portal page →
    fields populate, the summary lists 2 unresolved rows ("CAQH ID —
    empty on provider", "Medicaid ID — case-scoped, not resolvable") →
    she completes those by hand, reviews, and submits on the portal.
- **Test/data scenario(s):** TS-81.

### F4.3.3 — Missing-mapping fix-it tie-in

- **Description:** When a portal field has no mapping (or a token resolves
  empty), the extension routes into the existing fix-it / field-dictionary
  flow inline: the specialist labels the field once, improving fill for
  every future case on that portal. The moment stays inside the work loop —
  fix, fill, continue.
- **Persona:** P2.
- **Benefit hypothesis:** every gap encountered becomes data value (B),
  compounding fill coverage instead of dead-ending the specialist.
- **Acceptance criteria:**
  - A missing mapping offers the fix-it action in place, carrying the
    portal/field context into the existing mapping flow (TE-4) — the
    specialist never has to re-find the field she just hit.
  - **Self-approve inline (PM decision 2026-07-15):** a specialist's
    completed fix-it is approved immediately — the mapping is usable in
    the live session (the extension refetches maps and retries the
    field) and for every future case on that portal. The safety valve is
    async QA, not a blocking gate: self-approved mappings write the
    normal audit rows and are **flagged distinctly in mapping review**
    (e.g. "self-approved via fix-it") so a config user can spot-check
    and revoke/correct after the fact — review becomes async quality
    control instead of a dead end for the fixer.
  - An empty-but-mapped token (value missing on the provider/case, not
    the mapping) routes to the data fix (provider record / outreach),
    not the mapping flow — the panel distinguishes "no mapping" from
    "no value" so the fix-it action is always the right fix.
  - Learned mappings persist via the existing field-dictionary mechanism.
- **User journey:**
  - Fill leaves "Group Medicare PTAN" unresolved (no mapping) → P2
    clicks Fix it → labels the field in the existing train flow → back
    in the panel, retry fills the field → every future case on this
    portal fills it automatically.
- **Test/data scenario(s):** TS-82.

### F4.3.4 — Log-and-advance loop (manual, structured)

- **Description:** After portal work, the specialist logs the touch from
  the extension exactly as today (manual — the existing submission-touch
  workflow remains), now carrying the E4.1 structured type + single-line
  context, and optionally the follow-up date and tracking ID (E4.0). The
  extension then shows the **next best action** (the specialist's E2.3
  queue top) so the loop continues without returning to the webapp.
- **Persona:** P2.
- **Benefit hypothesis:** complete the task, document quickly, move to the
  next case — the full B loop from one view.
- **Acceptance criteria:**
  - Touch logging from the extension requires a type and accepts the
    single-line context (same contract as E4.1, incl. optional
    outcome/recipient/follow-up); `source = 'extension'` is set
    server-side and renders in the webapp log like any E4.1 row.
  - The logged touch appears identically in the webapp case touch log.
  - If the touch write fails (network, session, case closed/reassigned
    since launch), the entered values are preserved and a retry is
    offered — the specialist's one line of context is never lost to an
    error.
  - After logging, the extension offers the next queue item read-only —
    the **server-derived** E2.3/E4.1 queue top under the org's F4.2.5
    ranking config (TE-6; no ranking logic in the extension) — with a
    handoff back into F4.3.1's flow and a deep link to the case in the
    webapp.
  - An empty queue renders an honest done state ("queue clear"), not a
    blank panel; if the top item is the case just worked (e.g. another
    open task), it says so rather than presenting it as new.
- **User journey:**
  - Portal submission done → panel touch form: type "Portal Check",
    context one-liner, follow-up in 14 days → Save → "Next: Dr. Patel /
    Humana KS — follow-up overdue" with Work in portal + open-in-webapp
    → the loop continues without returning to the webapp.
- **Test/data scenario(s):** TS-83.

### F4.3.5 — Standalone Search & Customizable Quick Cards (read-only)

_Added 2026-07-17 by PM spec; recorded faithfully. Reviewer enablers and
verified corrections live in the §5 amendment (TE-11–TE-18); the amendment's
open questions were resolved by PM decision 2026-07-17, recorded there._

- **Description:** The extension also works as a **standalone ad-hoc
  credentialing tool**: specialists pull core provider (Type 1) and group
  (Type 2) data from anywhere on the web **without an active case**. Launched
  without a handed-off case context, the panel defaults to a unified search
  bar querying Cases AND Providers; selecting a case loads the F4.3.1 fill
  view, selecting a provider loads the read-only Quick Cards. UX principles
  (PM, binding): native lightning-fast utility (Linear/Vercel visual craft);
  high-density minimalist layout, compact typography, subtle structural
  borders; ALL alphanumeric IDs (NPI, CAQH, TIN) in monospace; 1-click
  copy-to-clipboard on hover for all ID fields; no heavy primary buttons.
- **Persona:** P2 (primary); P1 benefits from the same ad-hoc lookup.
- **Benefit hypothesis:** the extension earns a place in the specialist's
  flow beyond active case work — core credentialing identifiers are one
  search away from any page, extending B's cohesive-duo value to ad-hoc
  lookups without another webapp tab or a context switch.
- **Acceptance criteria:**
  - **Unified global search (empty state, 3.1):** with no handed-off
    context the panel shows one search input querying cases and providers
    in the resolved org. A case result opens the F4.3.1 fill view; a
    provider result opens the Quick Cards. The F4.3.1 identity guard
    applies in standalone mode too: the header always names the org the
    search operates as, and a multi-org user resolves an explicit org
    before any search runs.
  - **Provider & Group Quick Cards, default layout (3.2, read-only):**
    - Type 1 header: full name, DOB (bold, compact).
    - Type 1 core IDs: NPI, CAQH, License # — 2-column grid, monospace,
      hover-copy. (PM decision 2026-07-17, resolving §5 Q1: the spec's
      Medicare ID slot has no schema backing today, so the default slot is
      the primary license number now; Medicare ID / Medicaid PTAN join the
      closed catalog in R10 when the enrollment-identifier child-row model
      lands.)
    - Type 1 state license: state, license number, expiration date; amber
      warning badge when < 30 days to expiry.
    - Type 2 header: group name (legal entity), visual divider from
      Type 1.
    - Type 2 core IDs: group NPI, Tax ID (TIN) — monospace, hover-copy.
    - Type 2 malpractice: insurer name, policy number, expiration date;
      amber warning badge when < 30 days to expiry.
    - Empty or unresolvable fields render honestly (muted em-dash or the
      profile's unresolved reason), never silently dropped — the F4.3.2
      per-field discipline applies to cards.
  - **User-configurable card layouts (3.3):** a lightweight "Edit Layout"
    toggle in extension settings lets the user swap default fields (the
    PM's swap example — Medicaid PTAN — is recorded as an R10 catalog
    addition per the Q1/Q2 decision) or add up to 3 custom fields from the
    provider data model, selectable ONLY from the server-defined closed
    catalog (TE-16). Layout preferences are saved server-side to the
    user's profile so they persist across machines/browser resets; a
    missing or invalid stored layout degrades to the default layout,
    never a broken card.
  - **The 1-to-many escape hatch (3.4):** cards show the PRIMARY license
    and PRIMARY group only; a subtle muted "Open in Minted Panel ↗" link
    (label per PM decision 2026-07-17, Q3; flush right in the card header
    or card bottom) deep-links to
    `/providers/:id` in a NEW tab, preserving the active portal session.
    No complex 1-to-many arrays in the panel.
  - **Active-cases hand-in (PM technical note 4):** from a Quick Card, the
    provider's active cases list at the bottom of the view; clicking a
    case triggers `SET_ACTIVE_CASE` (TE-1 semantics) and transitions to
    the F4.3.1 fill loop.
  - Quick-card data leverages the existing provider-profile endpoint
    surface — no net-new data models for default fields (PM technical
    note; the Medicare ID slot was swapped to License # per §5 Q1). Everything in this feature is read-only; the ONLY write is the
    layout-preference save (TE-15/TE-18), and DOB and all profile values
    follow the TE-3 PHI discipline (TE-14).
- **User journey:**
  - P2 is mid-research on a payer site with no case in flight → opens the
    panel → types "Ostrander" → picks the provider → the Type 1/Type 2
    cards render NPI/CAQH/TIN in monospace → she hover-copies the TIN
    into the payer's lookup form → spots the amber license-expiry badge →
    clicks "Open in Minted Panel ↗" to review the full license list in a new
    tab, portal session intact.
  - Same search, but she picks a case instead → the panel lands in the
    F4.3.1 fill view for that case, identity header correct.
- **Test/data scenario(s):** TS-100–TS-103 (seed-universe entries and the
  Scenario/Seed mapping rows recorded 2026-07-17).

## Edge Cases & Corrections

- **Case changes under the panel mid-session** (closed, reassigned,
  pipeline moved by someone else): the panel reflects reality on its
  next fetch; a touch against a closed case follows the same server
  validation as the webapp, with the error naming the case's current
  state. No silent writes against stale context.
- **Wrong-case touch:** corrected by the E4.1 append-only correction
  protocol (correction touch referencing the original) — the extension
  introduces no edit/delete path.
- **Portal DOM drift** (payer redesigns the form): affected fields
  surface as unresolved/unmatched rows routing into F4.3.3 fix-it — a
  drifted portal degrades to the manual + fix-it loop, never to wrong
  values in wrong fields.
- **Multi-org users:** the handoff message carries `orgId`; the panel
  operates under exactly that org (identity guard) and all `/api` calls
  send it — switching orgs in the panel clears case context and
  in-memory values (TE-3).
- **Task completion stays in the webapp for R6:** the panel's task list
  is read-only; marking an `extension_fill` task done happens in the
  webapp (deep link provided). Recorded as the known seam in the "one
  view" story — see Non-Goals.

## What Good Looks Like (exit criteria)

- [ ] From case → portal → fill → touch → next case without a single
      re-search or re-selection on the happy path (TS-80/83).
- [ ] No fill is ever silent-partial: every field is accounted for as
      filled, unresolved-with-reason, or manual (TS-81).
- [ ] Every mapping gap encountered in real work can be fixed in-flow
      and the fix demonstrably improves the same session when usable
      (TS-82).
- [ ] Extension-absent and context-expired paths are first-class UX
      (notice + picker fallback), not error states.
- [ ] Zero new write paths beyond the existing manual touch append and the
      one user-scoped F4.3.5 layout-preference upsert (TE-15/TE-18 —
      user-scoped, no org/case/provider data, no PHI); PHI handling passes
      TE-3/TE-8 (no-store, no body logging, audit on reads).

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the authenticated Nitro API
router (`src/server/api.ts`, `src/server/guard.ts`,
`src/server/extensionRoutes.ts`), the existing case-context/profile services
(`src/services/caseContext.ts`, `src/services/providerProfile.ts`), the
extension field-map/dictionary services
(`src/services/portalFieldMaps.ts`, `src/services/fieldDictionary.ts`), the R2
extension contract, and
`docs/minted-panel-extension-build-spec-v1.1.md`. The handoff protocol is
already defined: the webapp sends `SET_ACTIVE_CASE` through Chrome
`externally_connectable`, the service worker binds the next matching tab, and
the side panel retains manual case search as fallback. This epic completes and
hardens that contract; it does not introduce a second extension integration
model._

- **TE-1 — Preserve the established cross-extension handoff message.** Before
  the task-drawer portal link opens its tab, the app feature-detects
  `chrome.runtime.sendMessage` and sends:

  ```ts
  {
    type: "SET_ACTIVE_CASE",
    caseId,
    providerId,
    orgId,
    portalUrl,
  }
  ```

  The extension's `externally_connectable.matches` is restricted to approved
  app origins; the background worker associates the next tab opened to the
  portal origin, expires context at tab close or 60 minutes idle, and never
  keeps a global current provider. The message contains identifiers and URL
  only, not profile/token values. If Chrome or the extension is unavailable,
  the portal still opens and the side panel's existing searchable case picker
  remains the fallback.

- **TE-2 — Expand the server-owned case-context projection instead of adding
  browser joins.** Extend `GET /api/cases/:id/context` and
  `caseContext.ts` with explicit columns for the selected case's provider,
  payer, state, facility, open SOP tasks, payer-pipeline state, and latest
  tracking ID. The server guard authenticates the JWT, requires explicit
  organization selection where needed, and verifies case/provider/facility
  ownership before any service-role read. Return only the panel fields, set
  `Cache-Control: no-store`, never log the response body/token values, and
  write exactly one successful `READ` audit event. Pipeline/tracking columns
  are gated on E4.0's clarified contract; do not infer them from internal
  `status_configs`.

- **TE-3 — Read-only fill reuses the existing profile and field-map
  endpoints.** Token resolution continues through
  `GET /api/providers/:id/profile` and approved portal maps; content scripts
  receive only values required for the current step, not the whole provider
  record. The extension has no service-role key and no direct cross-org read.
  Keep exact host permissions, authenticated organization headers, generic
  server errors, and no-store handling. Empty/unresolved token results are
  first-class typed rows with reasons; they are never silently skipped or
  logged with their sensitive values. Reviewer performance budget: on the
  seeded mock harness, show case context within 1 second p95 and reach
  fill-ready state within 2 seconds p95 after launch, excluding time spent
  waiting for the payer portal DOM. Fetch context/profile/maps concurrently
  where dependencies allow. PHI responses are never put in HTTP cache,
  `chrome.storage`, or IndexedDB; a tab-bound in-memory value set may be reused
  during the active fill session and is cleared on case/org change, tab close,
  or the 60-minute context expiry.

- **TE-4 — “Fix-it” stays a deliberate user action through the existing
  platform mapping flow.** The extension offers the action with portal/field
  context and hands the user to the existing `/fix-it` or
  `/portals/$portalKey/train` workflow. Persistence continues through
  `useFixit`/`useMappingReview` and their services, RLS, and audit behavior;
  the extension then refetches approved field maps and retries the current
  field/session. Do not add an unrestricted extension-side field-map mutation
  endpoint or allow a content script to write mappings directly. This preserves
  the R6 read-only fill boundary while making the in-session correction
  visible and durable.

- **TE-5 — Manual touch logging uses the one existing append path.** Keep
  `POST /api/cases/:id/touches` as an explicit user-confirmed action after
  fill/submission; no fill event auto-creates a touch. Align its body with
  E4.1's structured type + single-line context contract, set
  `source = 'extension'` server-side, require `admin`/`specialist`, verify case
  ownership, append one touch, and write one audit event. The resulting row
  must render through the same case timeline and labels as a webapp entry.

- **TE-6 — Next-best action is a minimal guarded read over the existing pure
  queue.** Add a server endpoint that assembles organization-scoped queue
  inputs, calls the same pure reducer used by E2.3/E4.1, and returns only the
  top case ID, display label/reason, and webapp deep link. Do not duplicate
  ranking logic in the extension or persist queue rows. After a touch append,
  the extension refetches this read endpoint and offers a handoff back into the
  case/task flow; the webapp remains the execution authority.

- **TE-7 — Keep platform code in the normal layers.** Task-drawer UI calls a
  hook/service wrapper for handoff capability and API contract state; data
  reads/writes remain in services, with TanStack Query keys scoped by
