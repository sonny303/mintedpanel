# E4.3 — Extension Workbench Handoff: Read-Only Fill, Cohesive Case Execution

## Purpose and Context

`[r6]` decision B: the workbench extension and the webapp platform must be a
**cohesive duo where handoff is seamless** — the user experiences nothing
missed between working a case on the platform and moving to a payer portal
with the extension guiding case completion, logging it, and bringing the next
best action, all from the same view. **The platform tells you what to do; the
extension is what you complete it with.** When SOP/fill data is missing, the
flow ties into the existing fix-it game (field dictionary) to increase the
data value the extension provides.

For this release the extension is **tightly scoped to read-only token
resolution** — reading case/provider data to fill portal forms — to establish
a reliable, low-latency form-fill experience first. Logging/submission stays
**manual** from the extension into the Touch log (the existing R2 Workbench
workflow remains, now with E4.1 structured types). The PM notes the extension
must eventually be more than a form filler (email tasks, etc.) — recorded as
a non-goal/roadmap note, not R6 scope.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — works a case's tasks on a
  payer portal with the extension filling from the same case context she
  left in the webapp, logs the touch, and moves to the next best action.
- **P1 Credentialing Manager** — trusts that portal work is logged against
  the right case with no duplicate bookkeeping.

## Component & Data Constraints

- Extension consumes the existing server API surface (`/api/*`, org/role
  guarded, dual-path rule) — read endpoints only for fill data; the one
  write remains the existing manual submission-touch endpoint.
- The most PHI-dense payload (provider profile) rules hold: `no-store`,
  no body logging, audit rows on reads (existing contract).
- Webapp surfaces build from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Full-SSN fill tokens are E4.4's contract; this epic only reserves the
  seam (fill-only token category) and must not render SSN values.

## Features

### F4.3.1 — Case-context handoff (platform → extension)

- **Description:** From a case (detail or My Cases queue row), "Work in
  portal" hands the exact case context to the extension: the extension's
  side panel opens on that case — provider, payer, state, facility, open
  SOP tasks, and tracking ID — without the specialist re-searching or
  re-selecting anything. The extension's existing case picker remains for
  direct entry, but the handoff path is primary.
- **Persona:** P2.
- **Benefit hypothesis:** seamless handoff (B) removes the re-orientation
  cost at exactly the moment work moves to the portal — nothing missed
  between the two surfaces.
- **Acceptance criteria:**
  - Launching from a case lands the extension on that same case (org,
    case, provider, facility context all correct).
  - The extension view shows the case's open tasks and pipeline state
    read-only, matching the webapp.
  - No new write path is introduced by the handoff.
- **Test/data scenario(s):** TS-80.

```gherkin
Feature: Seamless case handoff
  Scenario: Working a case moves to the portal without re-selection
    Given P2 has a case open in the webapp with 3 open SOP tasks
    When she launches the extension from that case
    Then the extension panel shows that case's provider, payer, tasks, and tracking ID
    And filling the portal uses that case's resolved tokens
```

### F4.3.2 — Reliable low-latency read-only fill

- **Description:** The extension fills portal forms via the existing
  token-resolution path (provider profile + field maps), scoped read-only.
  R6 hardens this into the dependable core loop: resolved values fill
  fast, unresolved tokens are visibly listed with reasons (existing
  `unresolved` contract), and facility selection follows the established
  needs-facility rules.
- **Persona:** P2.
- **Benefit hypothesis:** B's explicit priority — establish a reliable,
  low-latency form-fill experience before any write-back ambition.
- **Acceptance criteria:**
  - Fill uses only read endpoints; no extension-initiated data mutations
    besides the existing manual touch logging.
  - Unresolved tokens are surfaced to the user with reasons, never
    silently skipped.
  - Perceived fill latency is addressed (§5 records the concrete budget /
    caching decisions within the no-store PHI constraint).
- **Test/data scenario(s):** TS-81.

### F4.3.3 — Missing-mapping fix-it tie-in

- **Description:** When a portal field has no mapping (or a token resolves
  empty), the extension routes into the existing fix-it / field-dictionary
  flow inline: the specialist labels the field once, improving fill for
  every future case on that portal. The moment stays inside the work loop —
  fix, fill, continue.
- **Persona:** P2.
- **Benefit hypothesis:** every gap encountered becomes data value (B),
  compounding fill coverage instead of dead-ending the specialist.
- **Acceptance criteria:**
  - A missing mapping offers the fix-it action in place; completing it
    immediately improves the current fill session.
  - Learned mappings persist via the existing field-dictionary mechanism.
- **Test/data scenario(s):** TS-82.

### F4.3.4 — Log-and-advance loop (manual, structured)

- **Description:** After portal work, the specialist logs the touch from
  the extension exactly as today (manual — the existing submission-touch
  workflow remains), now carrying the E4.1 structured type + single-line
  context, and optionally the follow-up date and tracking ID (E4.0). The
  extension then shows the **next best action** (the specialist's E2.3
  queue top) so the loop continues without returning to the webapp.
- **Persona:** P2.
- **Benefit hypothesis:** complete the task, document quickly, move to the
  next case — the full B loop from one view.
- **Acceptance criteria:**
  - Touch logging from the extension requires a type and accepts the
    single-line context (same contract as E4.1).
  - The logged touch appears identically in the webapp case touch log.
  - After logging, the extension offers the next queue item read-only with
    a handoff back into F4.3.1's flow.
- **Test/data scenario(s):** TS-83.

## Dependencies

- Existing extension endpoints (provider profile, field maps, fill events,
  open cases, submission touches, case context) and org-isolation gate.
- E4.0 (pipeline state + tracking ID shown in the panel), E4.1 (typed
  touches), E2.3 queue (next best action source).
- E4.4 vault (fill-only SSN token seam — contract only, built there).
- sonny303/minted-extension repo — the extension-side work is coordinated
  there; this epic owns the platform contract and the handoff UX spec.

## Out of Scope / Non-Goals

- No extension write-back automation (auto-logging fills/submissions) —
  logging stays manual this release (B).
- No non-form-fill task execution in the extension (emails etc.) — noted
  as the eventual direction, later release.
- No document auto-attach (see E4.5 / post-redesign roadmap, [r6] D3) —
  manual download / drag-and-drop remains the documented path.
- No new portal credential handling.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-14 against the shipped extension server
surface (`src/server/extensionRoutes.ts` — `GET /api/me/orgs`,
`GET /api/providers/:id/profile` (Cache-Control `no-store`, one audit row per
read, never the body/token values), `GET /api/portal-field-maps`,
`GET /api/cases?providerId`, `GET /api/cases/:id/context`,
`POST /api/cases/:id/touches` writer-gated, `POST /api/fill-events`), the
org/role guard (`src/server/guard.ts` `isWriter`, `AuthContext`), the case
context read (`src/services/caseContext.ts`), token resolution
(`src/lib/sopResolver.ts`, `src/services/providerProfile.ts`,
`portalFieldMaps.ts`), the field-dictionary / fix-it game
(`src/services/fieldDictionary.ts` `upsertDictionaryEntry`/`decideDictionaryEntry`,
`src/hooks/useFixit.ts`), the E2.3 queue derivation
(`src/services/nextBestActions.ts` + `src/lib/nextBestActions.ts`), and
`uiux-component-guide.md`. **Headline:** the whole extension read/fill/log
surface already exists and is org-isolation-gated — this epic is a *platform
contract + handoff-UX* spec, not new plumbing. It introduces **no new write
path** (the one write stays the existing manual submission touch), keeps fill
strictly read-only, and reserves — but does not build — the E4.4 full-SSN
fill-only seam. The extension client itself lives in `sonny303/minted-extension`;
this epic owns the webapp/`/api` contract and the in-webapp launch UX, and that
cross-repo split is the main coordination flag._

- **TE-1 — Case-context handoff is a deep-link into the extension over the
  existing read endpoints (F4.3.1).** A "Work in portal" action on case detail
  and the My Cases row hands `(org_id, case_id)` to the extension side panel
  (the extension's documented launch/deep-link mechanism, coordinated in
  `minted-extension`); the panel then pulls the case via the existing
  `GET /api/cases/:id/context` (cross-org access already rejected there) and the
  provider fill payload via `GET /api/providers/:id/profile`. Extend the
  `caseContext` payload to include the E4.0 `payer_pipeline_state` + tracking ID
  (that column change is E4.0 §5 TE-7) and the case's open SOP tasks
  (read-only), so the panel matches the webapp without re-selection. The
  extension's existing case picker (`GET /api/cases?providerId`) remains for
  direct entry; the handoff path is primary. No new write path (F4.3.1 AC).

- **TE-2 — Reliable low-latency fill reuses the resolver; caching respects the
  no-store PHI wall (F4.3.2).** Fill continues through the existing
  provider-profile token payload + `portal-field-maps`. The PHI-dense profile
  response is `Cache-Control: no-store` and MUST stay uncacheable — the latency
  budget is therefore met by (a) caching only the **non-PHI** global
  `portal-field-maps` rows (org-NULL catalog, safe to cache on the extension
  side), (b) a single round-trip profile fetch per case (no per-field calls),
  and (c) surfacing resolved values immediately while unresolved tokens are
  listed with reasons via the existing `unresolved` contract in the profile
  result — never silently skipped (F4.3.2 AC). §5 records the concrete budget as
  "one profile fetch + one field-map fetch per portal session; no PHI persisted
  in the extension." Facility selection follows the existing needs-facility
  rule (`needsFacility` / `?facilityId=` on the profile route).

- **TE-3 — Missing-mapping fix-it tie-in reuses the shipped field dictionary
  (F4.3.3).** When a portal field has no mapping or a token resolves empty, the
  extension routes into the existing fix-it flow — `upsertDictionaryEntry` /
  `decideDictionaryEntry` (`fieldDictionary.ts`, surfaced by `useFixit.ts`) —
  labelling the field once; the learned mapping persists via that mechanism and
  improves every future fill on that portal. The write is the existing dictionary
  upsert (writer-gated), not a new mutation category. The moment stays inside the
  work loop; no new storage.

- **TE-4 — Log-and-advance loop: one existing write + one likely-additive read
  (F4.3.4).** Touch logging from the extension stays the existing manual
  `POST /api/cases/:id/touches` (writer-gated), now carrying the E4.1 structured
  `touch_type` + single-line context (that field is E4.1 §5 TE-5) and optionally
  the follow-up date and tracking ID (E4.0) — the logged touch appears
  identically in the webapp touch log because it is the same table. To then show
  "next best action" without returning to the webapp, the extension needs the
  specialist's E2.3 queue top; the queue is a webapp-side derivation today, so
  this is the one **likely-additive read endpoint** (`GET /api/queue/next` or
  similar, read-only, PHI-minimal, org/role-gated — reusing the pure
  `src/lib/nextBestActions.ts` ranking server-side) — flagged so the builder
  scopes it. Handoff back into the F4.3.1 flow reuses TE-1.

- **TE-5 — SSN seam reserved only, not built here.** This epic reserves a
  fill-only token category for the full SSN (E4.4's contract) and MUST NOT render
  any SSN value; the profile payload continues to expose `ssn_last4`/masking
  only. The actual vault release path (`no-store`, audited, fill-only) is built
  in E4.4 §5 — this epic just guarantees the fill pipeline can carry a
  fill-only-category token without displaying it.

- **TE-6 — Seed + tests.** TS-80–TS-83 run through the existing extension mock
  harness (the `.di.test.ts` dependency-injection precedent —
  `caseContext.di.test.ts`, `fillSessions.di.test.ts`,
  `portalFieldMaps.di.test.ts`, `providerProfile.di.test.ts`): case-context
  handoff, read-only fill + unresolved-token surfacing, inline fix-it improving
  the live session, and the typed-touch + next-best-action loop. No new table;
  register unaffected.
