# E6.10 — Structured Control Autofill

**Cross-repo, deliberately.** Panel (`sonny303/mintedpanel`) and extension
(`sonny303/minted-extension`) ship together as two PRs, following the E4.3 /
E6.9 precedent. This is a knowing exception to the "one epic = one repo" rule
in [`EPIC-TEMPLATE.md`](./EPIC-TEMPLATE.md): the unit of work here is **one
wire shape** (a captured option list travelling capture → propose → registry →
fill). Splitting it puts the producer and the consumer of that shape in
separate approval cycles, which is exactly what the locked "contract changes
are panel-first, mirrored in the same coordinated change" rule forbids. Flagged
for the PM rather than silently taken.

## Purpose and Context

A trainer maps a payer's **State** dropdown to `provider.homeState` and the
fill reports "no option matches "Kansas"". The box was fillable the whole time;
the portal calls that option `KS`. Every structured control — `<select>`, radio
group, checkbox — fails the same way, and the failure is indistinguishable in
the UI from a mapping that was never made.

This epic closes the vocabulary gap. It is the **P1 slice** of the PM's
"Autofill beyond free-text" design (2026-08-13): capture what a control's
choices actually are, show the trainer what kind of control they are training,
and let a fixed value be _picked from the portal's own list_ instead of typed
into a free-text box and hoped for. Token↔option binding maps are deliberately
**deferred** (see Non-Goals) — the spike found a shipped mechanism that covers
the common cases first.

### What already exists (spike, 2026-08-13 — corrects the design doc)

Three premises of the source design were wrong or incomplete. Each is cited by
path; none of this needs building:

1. **The setters already exist and already fuzzy-match.**
   `minted-extension/src/content/fillEngine.ts` `applySelect` matches exact
   option value → normalized label → normalized value; `applyRadio` matches
   value or label text across the `name` group; `applyCheckbox` maps a small
   truthy set. Nothing here is missing a click path.
2. **`field_type` is already captured, stored and planned — it is only
   invisible.** `captureScan.ts` `controlType()` classifies it, the propose
   route validates it (`src/services/portalFieldMaps.ts` `PROPOSE_FIELD_TYPES`),
   the column has existed since the baseline schema, and `planFill` reads it.
   It is rendered **nowhere** in the training UI — `FieldRegistryList.tsx` and
   `FormStepPanel.tsx` contain zero references to it. The trainer therefore
   trains a dropdown and a text box through an identical control.
3. **`transform` is a live mechanism with no writer — dead code in
   production.** `minted-extension/src/background/fill.ts` `applyTransform`
   implements `state_abbrev` (Kansas → KS) and `date_mmddyyyy`, and both the
   real fill and the mock dry run apply it. But `transform` appears in this
   repo only inside the SELECT column list of
   `src/services/portalFieldMaps.ts` — no service, hook, or RPC ever writes it.
   Every live row is `transform = NULL`, so the one shipped fix for
   "Kansas" → `KS` cannot be switched on from any surface.

Finding 3 answers the design's Open Question 5 and sets this epic's direction:
**activate the mechanism that exists before inventing a second one.** A
per-map `valueBinding` map is the right tool for genuinely portal-specific
vocabularies (`Female` → `F` → `2`), and it stays a P2 proposal — but shipping
it first would leave two overlapping mechanisms and the tested one still
unreachable.

One further consequence worth stating: **the reporting half of the design's P0
is already shipped.** `applySelect` returns `no option matches "<value>"`, the
background carries it into `fields_skipped`, and the panel renders
`label - reason` verbatim. P0 collapses into F6.10.6 (name the control type in
that line) rather than a phase of its own.

## Features

### F6.10.1 — Capture the control's option vocabulary

- **Description:** When capture meets a `<select>`, a radio group, or a
  checkbox with a meaningful `value`, it records that control's choices as
  `{ value, label }` pairs alongside the existing label/selector/type.
- **Persona:** P1 (as the trainer whose later decisions depend on it).
- **Benefit hypothesis:** The portal's vocabulary is a _portal truth_ — stable,
  shareable, and knowable only from the page. Capturing it once removes the
  guesswork from every subsequent mapping decision on that field.
- **Acceptance criteria:**
  - `<select>`: one entry per `<option>`, using the option's `value` and its
    visible text. A placeholder option whose value is empty is omitted.
  - Radio: one entry per input in the `name` group, using each input's `value`
    and its associated label text. The group still collapses to **one**
    captured row, as today.
  - Checkbox: no options when the control is a plain boolean; an entry only
    when the input carries a meaningful `value`.
  - `text`, `date` and `file` controls capture no options.
  - **The PHI boundary is unmoved:** options are the choices the page offers,
    never which one is selected. Capture must not read `selected`, `checked`,
    or any typed value — the invariant already asserted at the top of
    `captureScan.ts`.
  - An option list from a control that renders no options (an AJAX-populated
    select that has not loaded) is captured as empty, never as an error.

```gherkin
Feature: Capture records what a control will accept
  Scenario: A state dropdown is captured with its codes
    Given the shared fixture portal has a "Practice State" <select> with options "KS", "MO" and "NE"
    When P1 captures that page in Train forms
    Then the captured field records control type "select" and the three value/label pairs
    And the capture payload contains no selected or checked state
```

### F6.10.2 — Persist options on propose, refresh them on re-capture

- **Description:** The captured option list rides the propose payload into an
  additive `control_options` column, and a re-capture refreshes it **without
  disturbing any decision already made about the field.**
- **Persona:** P1.
- **Benefit hypothesis:** A payer that adds a plan to a dropdown should cost a
  re-capture, not a re-training. This is the same drift-repair property E6.9
  established for labels and ordering, extended to vocabulary.
- **Acceptance criteria:**
  - `control_options` is additive and nullable; every existing row reads NULL
    and behaves exactly as it does today.
  - Written on propose through the shared RPC
    (`propose_shared_field_map`) and the org-tier propose route
    (`POST /api/portal-field-maps`), which stay **propose-only** — status,
    source and token semantics are untouched.
  - Re-capture updates `control_options` in the **presentation-refresh** set,
    beside `sort_order` / `field_label` / `form_section` — never
    `status`, `token`, `source`, `hardcoded_value`, `notes`, or the admin's
    `display_label` / `section`.
  - A re-capture that returns an **empty** option list (the dynamic-select
    case) leaves the stored vocabulary in place rather than erasing it.
    Erasing a good list because a page had not finished loading is the one
    failure mode that would make re-capture dangerous.
  - The shape is validated at the write boundary: an array of
    `{ value, label }` strings, or NULL.

### F6.10.3 — The registry shows what kind of control each field is

- **Description:** Every row in the field registry carries a control-type chip
  (Text · Dropdown · Radio · Checkbox · Date · File), and a structured control
  can show the choices it will accept.
- **Persona:** P1.
- **Benefit hypothesis:** The trainer is currently making a typed decision
  against an untyped UI. Showing the type is the smallest change that makes the
  existing `field_type` data do any work at all.
- **Acceptance criteria:**
  - The chip renders from the stored `field_type` on every row in
    `FieldRegistryList.tsx`, including rows captured before this epic.
  - Rows with a stored vocabulary can reveal it (value + label), read-only.
  - A structured row with **no** captured vocabulary says so plainly and points
    at re-capture — it is never presented as if it had no choices.
  - Ordering, grouping, rename, and the decision controls are unchanged;
    staleness still never locks a row (E6.9).

### F6.10.4 — A fixed value is chosen from the portal's own options

- **Description:** When a row has a captured vocabulary, the "fixed value"
  decision presents those options instead of a free-text box.
- **Persona:** P1.
- **Benefit hypothesis:** This is where most structured-control training
  actually lands — "this form is always Individual", "always Kansas" — and it
  is the case where free text is most likely to be silently wrong.
- **Acceptance criteria:**
  - Fixed value on a row with options is a picker over those options; the
    stored `hardcoded_value` is the option's **value**, so the fill's first,
    exact match hits.
  - Fixed value on a row **without** options (text/date, or an uncaptured
    structured control) stays a free-text input — unchanged behaviour.
  - A checkbox with no options offers the boolean choice, stored as a literal
    the shipped truthy set in `fillEngine.ts` already accepts.
  - A stored `hardcoded_value` that is no longer in a refreshed vocabulary is
    surfaced as needing attention. It is **not** auto-cleared: an option list
    that momentarily loaded short must never delete a human's decision.
  - Both tiers work: shared rows through `train_global_field_map`, org rows
    through the existing RLS mutation. A fixed value on an org row is still an
    explicit outcome, never a silent DB failure.

```gherkin
Feature: Fixed values come from the portal's vocabulary
  Scenario: Always-Kansas on a state dropdown
    Given the "Practice State" field is captured with options "KS", "MO" and "NE"
    When P1 chooses a fixed value and picks "KS — Kansas"
    Then the row stores the option's value "KS"
    And the dry run selects Kansas on the page with no unmatched-option gap
```

### F6.10.5 — Value shaping is authorable

- **Description:** The dormant `transform` column becomes settable from the
  registry, activating the `state_abbrev` and `date_mmddyyyy` transforms the
  extension already applies.
- **Persona:** P1.
- **Benefit hypothesis:** This is the highest ratio of outcome to new code in
  the epic: a tested, shipped code path that today cannot be reached from any
  surface. It resolves the design's Open Question 5 for the two rules that
  recur across every payer, without a second mechanism.
- **Acceptance criteria:**
  - A token-mapped row can select **No shaping** (default, NULL) ·
    **State name → 2-letter code** (`state_abbrev`) · **Date → MM/DD/YYYY**
    (`date_mmddyyyy`). The stored strings must match the `applyTransform`
    switch in `minted-extension/src/background/fill.ts` exactly — an unknown
    transform there fills the raw value rather than dropping the field, so a
    typo degrades quietly and must be prevented at the source.
  - Offered only where it can apply — a fixed value is already the literal
    that will be sent, so shaping it is meaningless.
  - Writable on both tiers, which means `train_global_field_map` takes the
    parameter. Per the E4.2 / E6.8 no-overload precedent, the existing
    signature is **dropped and recreated**, not overloaded, and a non-token
    transition clears the transform the way it already clears the literal.
  - The row states its effect in words ("Kansas → KS"), so the trainer is not
    reading an enum.
  - The dry run applies transforms — it already does
    (`mockFill.ts` `planMockFill`) — so "prove" continues to mean what it says.

### F6.10.6 — A vocabulary mismatch says so, by name

- **Description:** When a value does not match any option, the skip reason
  names the control and what it would have accepted.
- **Persona:** P2 (running the fill), P1 (fixing it afterwards).
- **Benefit hypothesis:** The reason line is already the diagnostic surface —
  it just under-reports. "no option matches "Kansas"" and "field not found on
  this page" currently read as the same class of problem to the person holding
  the portal open, and they route to completely different fixes.
- **Acceptance criteria:**
  - The mismatch reason distinguishes a **vocabulary** failure (control found,
    value unmatched) from a **selector** failure (control not found) — the
    latter is the drift signal `formDrift.ts` keys on and must not be diluted.
  - The reason names the control type and, where known, a bounded sample of
    what the control accepts. It never dumps a 50-option list into a report
    line.
  - Reasons stay values-free with respect to the _page_ — reporting the
    provider value we tried to fill is already the established behaviour and is
    unchanged; the option list is portal vocabulary, not PHI.
  - Existing `ReportedFieldKind` routing is unchanged; no new kind is
    introduced unless the drift layer needs one, which the build session
    decides against `formDrift.ts`.

## Out of Scope / Non-Goals

- **Per-map `valueBinding` maps** (token value → option value). This is the P2
  proposal from the source design and is the right answer for portal-specific
  vocabularies (`Female` → `F` → `2`). Deferred so that the shipped
  `transform` path is activated and observed first — not reversed.
- **Custom widgets** — React-Select, div-based radios, shadow DOM. The engine
  addresses native controls only; a custom widget is still a manual field.
- **File inputs.** Unchanged: never attempted, always listed for the human.
- **Multi-select and multi-checkbox "questions"** as a first-class grain. One
  row still means one control.
- **Any inference of options** — no LLM, no guessing a vocabulary the page did
  not state.
- **Auto-approval of anything.** Capture stays propose-only; only `approved`
  maps fill (S5.1). A captured vocabulary is evidence, never a decision.
- **Auto-submit.** Unchanged, forever.

## Locked Decisions

1. **Options are portal truth, and belong to the shared tier** by default —
   the same argument that put `portal_field_maps` selectors there. An org
   override may still carry its own vocabulary; nothing forces it to.
2. **Transforms before bindings** (PM, 2026-08-13). The shipped mechanism is
   activated first; `valueBinding` is reconsidered on evidence from real
   payer forms, not ahead of it.
3. **Re-capture never destroys a decision** — not the token, not the fixed
   value, and not a vocabulary it failed to read. This is the E6.9 property
   that makes re-capture safe to run habitually.
4. **DOM type wins at apply time.** Stored `field_type` drives the training UX
   and planning; it never becomes a second source of truth the engine trusts
   over the actual element.

## Open Questions

- **OQ-1 — Dynamic options.** An AJAX-populated `<select>` may be empty at
  capture time. F6.10.2 makes the failure safe (never erase), but does the
  trainer need an explicit "re-read this control's options" action, or is
  re-capturing the page enough? Recommend: page re-capture only, until a real
  payer form proves otherwise.
- **OQ-2 — Same control, different vocabularies per page step.** E6.9's grain
  is `(portal_key, selector)` per tier, and a wizard can reuse a selector on
  two steps with different option sets. Believed rare; the build session should
  confirm against the Aetna and BCBS KS fixtures before assuming it away.
- **OQ-3 — Sample size in the mismatch reason (F6.10.6).** How many options is
  useful without being noise? Suggest three plus a count.
