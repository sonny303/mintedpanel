# E1.2 — Facilities / Locations

## Purpose and Context

Facilities are the places of service payers ask about on every application:
address, contact channels, hours, languages, accessibility, and
accepting-new-patients status. E1.2 delivers the "Facilities" wizard section
(E1.0 framework) as org-scoped CRUD over the **existing** `facilities` table.
The one design decision this epic implements is the **locked facility-hours
shape** (PM, 2026-07-10): per-day jsonb in the existing `facilities.hours`
column — `{ "mon": { "status": "open", "open": "07:00", "close": "19:00" },
…, "sun": { "status": "closed" } }` — matching the per-day status/open/close
grain payer forms use (e.g. Humana provider certification) and doubling as
the extension fill contract (`{{facility.hours.mon.open}}`-style tokens
later). Facilities are NOT part of the case key (locked) but feed the E1.8
readiness check "group has a facility in the target state."

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — sole actor; enters locations from
  client intake. Internal-only wizard through Stage 3 (locked).
- **P6 Office Manager** — NOT an actor in R1; reserved as the future source
  of facility details when the wizard opens to clients (post-Stage 3).

## Component & Data Constraints

- Built from the current component library — see
  [uiux-component-guide.md](./uiux-component-guide.md) and
  [README.md](./README.md).
- Test data uses [seed-universe.md](./seed-universe.md) orgs.
- Implementation dependency: `facilities` table exists (baseline schema) with
  address, `phone/fax/email`, `appointment_phone`, `contact_name`,
  `accepting_new_patients`, `languages_offered[]`, `interpreter_languages[]`,
  `hours jsonb`, `ada_compliance jsonb`, `group_id`. **No new schema in
  E1.2** — the work is defining and enforcing the hours jsonb shape in code.
- Downstream field usage: address + contacts → payer applications and
  extension practice-address fill (live wire contract today); hours →
  per-day payer form fields; languages/ADA/accepting-new-patients → payer
  directory and provider-certification forms.

## Features

### F1.2.1 — Facility form (wizard section)

- **Description:** The Facilities section lists the org's facilities and
  opens a form aligned to the **CAQH practice-location dataset** (PM,
  2026-07-10): name, address (street/suite/city/state/zip/county),
  phone/fax/email, appointment phone, contact name, accepting new patients,
  languages offered, interpreter languages, ADA accessibility, and the
  owning provider group (`group_id`, from E1.1 groups).
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** Location data is entered once at the grain payer
  forms actually ask for, instead of re-deriving it per application.
- **Acceptance criteria:**
  - Fields map to existing `facilities` columns; no new columns.
  - Group picker sources the org's E1.1 groups; required.
  - State required (feeds the E1.8 target-state readiness check).
  - **Minimum to save** (PM, 2026-07-10): address + state + group, plus at
    least one reachable contact channel — if the facility has no
    phone/contact of its own, the owning group's phone/contact serves as the
    default (displayed as inherited, not copied).
  - CAQH-alignment fields (accepting new patients, languages, interpreter
    languages, ADA, appointment phone) are **in the R1 form as optional
    fields** (PM, 2026-07-10 — CAQH alignment supersedes the earlier
    exclude-from-R1 call); their absence never blocks save.
  - List view shows name, group, city/state, and hours summary; edit from
    the list; soft delete via `is_active`.
  - Component → Hook → Service → Supabase; `org_id` set from active org.
  - Derived progress: ≥1 active facility → section Complete (E1.0 F1.0.2).
- **Test/data scenario(s):** TS-31 (new — see seed additions).

```gherkin
Feature: Facility capture
  Scenario: P1 adds Tree Hill's first location
    Given Tree Hill Sports Therapy has a saved provider group and no facilities
    When P1 adds a facility with address, NC state, contact details, and saves
    Then a facilities row exists linked to the group
    And the Facilities section shows Complete
    And the wizard Next action advances to Providers
```

### F1.2.2 — Per-day hours editor with weekday quick-fill

- **Description:** Hours are edited per day: each of mon–sun has an
  Open/Closed status and, when open, opening and closing times. A
  **"Apply weekday default"** quick-fill sets one time range across Mon–Fri
  and marks Sat/Sun closed in one action — matching how the team actually
  enters hours today (7:00–19:00 M–F, closed weekends).
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** The common case is one entry instead of seven,
  while the stored shape stays at the exact grain payer forms need — no
  free-text hours that the extension can't fill from.
- **Acceptance criteria:**
  - Stored shape is exactly the locked jsonb contract:
    `{ "mon": { "status": "open"|"closed", "open": "HH:MM", "close": "HH:MM" }, … }`
    with `open`/`close` present only when `status = "open"`.
  - Quick-fill: enter one open/close pair → applies to Mon–Fri, sets Sat/Sun
    closed; individual days remain editable afterward.
  - Times are 24h `HH:MM` strings in storage; displayed in 12h format.
  - `close` must be after `open`; validation blocks save otherwise.
  - No split shifts (single range per day) in v1.
  - Shape encoding/decoding lives in a pure, unit-tested module (it is the
    extension fill contract).
- **Test/data scenario(s):** TS-31, TS-32 (new).

```gherkin
Feature: Weekday hours quick-fill
  Scenario: P1 enters standard clinic hours in one action
    Given P1 is editing a facility's hours
    When P1 enters 7:00 AM – 7:00 PM and applies the weekday default
    Then mon–fri are stored as status open with open 07:00 and close 19:00
    And sat and sun are stored as status closed
    And P1 can still edit Thursday individually afterward
```

### F1.2.3 — Facilities summary on Account Detail

- **Description:** Account Detail gains a read-only facilities summary
  (name, group, city/state), consistent with E1.1's group summary; editing
  stays in the wizard.
- **Persona:** P1 Credentialing Manager.
- **Benefit hypothesis:** One glanceable client record; single editing
  surface preserved.
- **Acceptance criteria:**
  - Read-only list; empty state links to the wizard section.
- **Test/data scenario(s):** TS-31.

## 5. Technical Considerations & Enablers

- **TE-1 — Layering and read-path reuse.** The facility CRUD already exists:
  `createFacility` / `updateFacility` / `listFacilities` in
  `src/services/orgSettings.ts`, plus `useFacilitiesAll` / `useCreateFacility`
  / `useUpdateFacility` (`src/hooks/useOrgSettings.ts`) and the shared read
  `useFacilities` / `getFacilities` (`src/hooks/useLookups.ts`,
  `src/services/lookups.ts`, keyed by `queryKeys.facilities`). The group picker
  (F1.2.1) sources active E1.1 groups via `useProviderGroups`. E1.2 is the
  wizard form over these; reuse them (Component → hook → service →
  `externalClient`), never call Supabase from a component, and do not add a
  third facility read path (two already exist).
- **TE-2 — Widen the typed contract (additive, no migration).** Every field
  the CAQH-aligned form captures already exists as a `facilities` column, but
  the code contracts expose only a subset. `FacilityInput` and the protected
  `Facility` interface today carry `name/groupId/street/city/state/zip/isActive`
  (plus `statusId`/`effectiveDate`/`referenceOnly` on the interface). The
  F1.2.1 form additionally needs `suite`, `county`, `phone`, `fax`, `email`,
  `appointment_phone`, `contact_name`, `accepting_new_patients`,
  `languages_offered[]`, `interpreter_languages[]`, `hours` jsonb, and
  `ada_compliance` jsonb. Extend `FacilityInput` additively and widen the
  `Facility` interface in `src/types/index.ts` (additive-only edits permitted);
  give `hours`/`ada_compliance` typed shapes (see TE-3).
- **TE-3 — Hours jsonb: the locked contract as a pure module.** The stored
  shape is the locked per-day jsonb
  `{ "mon": { "status": "open"|"closed", "open": "HH:MM", "close": "HH:MM" }, … }`
  with `open`/`close` present only when `status = "open"`. Nothing parses
  `facilities.hours` today — this is greenfield. Add a **pure, unit-tested**
  module under `src/lib/` (e.g. `facilityHours.ts`) that owns: a named TS type
  for the shape, encode/decode between the editor model and the jsonb, the
  weekday quick-fill (one open/close pair → Mon–Fri open, Sat/Sun closed), 24h
  storage / 12h display formatting, and the `close > open` validation. This
  module IS the extension fill contract (`facility.hours.mon.open`-style
  tokens), so it must be the single source of truth — do not inline hours logic
  in the component. No split shifts in v1 (single range per day).
- **TE-4 — Contact inheritance is display-only, not a copy.** F1.2.1's
  minimum-to-save is address + state + group + at least one reachable contact
  channel; when the facility has no own phone/contact, the owning group's
  phone/contact serves as the default, **displayed as inherited (not copied)**.
  Resolve the inherited value at render time from the facility's `group_id`
  group (via `useProviderGroups`), leaving the facility's own contact columns
  null so a later group edit is never silently frozen into a stale copy. This
  is a pure derivation, not a DB write.
- **TE-5 — State normalization/format floor and the group picker.**
  `createFacility` / `updateFacility` already run
  `normalizeOptionalStateCode(state)`, backed by the E0.10
  `facilities_state_format` `^[A-Z]{2}$` NOT VALID check; state is required to
  save (feeds the E1.8 target-state readiness check). Group is required at the
  UI level even though `facilities.group_id` is nullable in the DB (FK
  `ON DELETE SET NULL`); the picker offers only active groups but must still
  render an existing link to a soft-deleted group (see E1.1 §5).
- **TE-6 — Derived-progress hook-in.** E1.2 plugs into the E1.0 framework: the
  Facilities section's "start" empty state is replaced by the list + form, and
  on save the section flips via the pure E1.0 resolver
  (`src/lib/onboardingProgress.ts`) — no stored wizard flags. F1.2.1 requires
  "≥1 **active** facility → Complete", so the resolver input must count
  `is_active` rows (E1.0 §5 TE-3 permits E1.2 to broaden its resolver input).
  The shared `listFacilities` / `useFacilities` read returns inactive rows, so
  the list and progress count must filter `is_active` themselves. Reuse
  `queryKeys.facilities(orgId, groupId)`; existing mutation hooks invalidate
  the `["facilities", orgId]` prefix, so no new cache is introduced.
- **TE-7 — Hours editor and primitive gaps.** The per-day editor (mon–sun rows,
  Open/Closed status + open/close times) composes from `label` + `switch` /
  `checkbox` + `input` / `select`; there is no time-picker or multi-select
  primitive in `src/components/ui/` today (see `uiux-component-guide.md`). Times
  can use a masked `HH:MM` `input` or hour/minute `select`s; the
  `languages_offered` / `interpreter_languages` multi-selects need a composed
  checkbox/badge list or `command` + `popover` added via the shadcn generator
  (Radix-backed, in its own commit, logged under enablers). Prefer the composed
  approach; no brand-new dependency.
- **TE-8 — Account Detail summary.** F1.2.3 is a **read-only** facilities card
  on `/get-started` (name, group, city/state), rendered alongside E1.1's group
  summary and `AccountDetailSummary` and fed by the same `useFacilities` /
  `useFacilitiesAll` read — no second editing surface (E1.0 single-front-door
  rule).
- **TE-9 — Schema, RLS, grants, append-only.** No migration, RPC, or new grant.
  Writes go to `facilities` under the existing org-scoped RLS
  (`facilities_insert_writer` / `facilities_select_org` /
  `facilities_update_writer`; authenticated specialist/admin write, org members
  select), with `org_id` set from `requireActiveOrg()`; the service audits via
  `writeAudit` on create/update. The append-only spine is untouched. Table
  trace matches the epic: reads/writes `facilities`, reads `provider_groups`
  and `organizations`. Note `facilities` also carries `service_types` /
  `treating_categories` jsonb and the legacy location-track columns
  (`status_id`, `effective_date`, `reference_only`) — all out of scope here;
  leave them untouched.
- **TE-10 — Design system and accessibility.** Shadowless white cards, token
  border, 6px panel radius; reuse the E1.0 TE-7 status-pill treatment; inline
  field validation with no placeholder-only labels; `aria-label` on icon-only
  buttons; list/table rows at `h-10`. Interactive elements are
  keyboard-reachable with visible focus; layouts remain usable at 1280px and
  1024px.
- **TE-11 — Verification gates.** Exhaustively unit-test the hours module
  (encode/decode round-trip, quick-fill = Mon–Fri open + weekend closed,
  `close > open` rejection, no-split-shift invariant) and the contact-
  inheritance derivation. Extend the onboarding e2e for TS-31 (first facility +
  inherited contact + Account summary) and TS-32 (weekday quick-fill then a
  single-day override). Implementation must pass `npm run lint`,
  `npx tsc --noEmit`, `npm run test`, `npx prettier --check .`, and the touched
  Playwright specs.
- **Likely tech debt to contain.**
  - `facilities` absorbed the dead `launches` location-track (`status_id`,
    `effective_date`, `reference_only`, and the `launches` FK — see the
    table-register). The E1.2 form/list must not surface or disturb those
    columns; keep the wizard write payload limited to the CAQH / hours fields.
  - Two facility read paths exist (`lookups.getFacilities`, group-filterable,
    vs `orgSettings.listFacilities` / `useFacilitiesAll`); reuse the shared
    hooks and do not add a third. The `useOrgSettings` mutation hooks invalidate
    raw `["facilities", orgId]` literals (prefix-compatible with
    `queryKeys.facilities`).
  - `hours` is untyped jsonb with no DB shape guarantee; the pure code module is
    the only enforcement in v1. A future need for split shifts or a
    holiday/exception calendar is a new shape decision (out of scope; log in
    `TECH-DEBT.md` if not already tracked).
