# E1.6 — Global Payer Catalog (Commercial)

## Purpose and Context

Payer identity is Minted-owned global data, not per-org data (locked): every
org attaching "BCBS-NC" must mean the same payer. E1.6 builds the browsable,
curated **commercial** payer directory that R3's Payer Network attachment
(E1.5) selects from — and it ships standalone value first: a searchable
directory that replaces spreadsheet payer lists. Per the 2026-07-10 audit
decision, E1.6 **extends the existing catalog mechanism, it does not rebuild
it**: migration `20260707060000_global_catalog_org_assignment.sql` already
shipped the global-row pattern (`payers.org_id IS NULL` = global, visible to
an org only via `org_payer_assignments`, platform-managed via the service
role), and `payers` already carries curated credentialing fields
(`portal_url`, `avg_decision_days`, `caqh_pull_deadline_days`,
provisional/retro billing). Commercial-first is locked; `payer_kind` lands in
schema now with government workflows deferred to R10. Identity seeding comes
from the Stedi payer directory (identity spine only — Stedi's data is
EDI-oriented; credentialing fields stay Minted-curated).

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — browses/searches the directory,
  proposes corrections; today's payer spreadsheet retires.
- **P2 Credentialing Coordinator** — read access to the same directory.
- (Catalog curation is platform-level work by the Minted team via
  service-role tooling — not an org-user capability.)

  - Existing `payers` table + global-row RLS pattern + `org_payer_assignments`

  - **New additive columns on `payers`:** `payer_kind`
    (`commercial | medicare | medicaid | medicaid_mco | medicare_advantage`),

    `cms_hios_id`, `aliases text[]`, `states text[]`, `status`
    (`active | merged | retired`), `merged_into_id` (self-link),

  - **New table `payer_catalog_changes`** (append-only diff log: payer,

  - Stedi developer API key required as a repo secret before the seed

## Features

### F1.6.1 — Payer directory (browse & search)

- **Description:** A cross-org "Payer Directory" surface listing global
  commercial payers: name, aliases, kind, states, portal URL, and the
  curated credentialing fields (avg decision days, CAQH pull deadline,
  provisional/retro billing). Search by name/alias; filter by state and
  kind.
- **Persona:** P1 Credentialing Manager, P2 Coordinator.
- **Benefit hypothesis:** One canonical payer list with the operational
  facts attached — replaces the spreadsheet, and every future org attachment
  points at the same identity.
- **Acceptance criteria:**
  - Directory reads global rows (`org_id IS NULL`); org-scoped legacy payer
    rows are NOT shown here (they remain on their existing surfaces).
  - Search matches name and aliases; filters for state and `payer_kind`.
  - Government kinds may exist as dormant rows but the R2 UI filters to
    commercial by default (gov workflows are R10).
  - Read-only for org users; no org-user create/edit of global rows (RLS
    already enforces this — writes are service-role only).
- **Test/data scenario(s):** TS-36 (new — see seed additions).

```gherkin
Feature: Payer directory search
  Scenario: P1 finds BCBS-NC by alias
    Given the global catalog is seeded with commercial payers
    When P1 searches "Blue Cross NC" in the Payer Directory
    Then the BCBS-NC payer appears with its states, portal URL, and
      credentialing facts
```

### F1.6.2 — Stedi identity seed pipeline

- **Description:** A platform (service-role) pipeline that seeds and
  refreshes payer identity from the Stedi payer directory: name, aliases,
  Stedi payer ID. Credentialing fields are never touched by the sync —
  they are Minted-curated only.
- **Persona:** Platform/Minted team (P1 benefits via coverage).
- **Benefit hypothesis:** Identity coverage without hand-entering hundreds
  of payers; a stable external ID to reconcile against as payers merge and
  rename.
- **Acceptance criteria:**
  - Seed run populates global commercial payers with `stedi_payer_id`
    dedupe (re-runs are idempotent).
  - Sync writes go through the diff log (F1.6.3); no direct overwrite of an
    existing row's fields.
  - Cadence: quarterly scheduled + on-demand per-payer refresh (locked).
  - Runs via service-role tooling; never callable from the browser.
- **Test/data scenario(s):** TS-37 (new — idempotent re-seed produces zero
  unreviewed diffs on unchanged data).

```gherkin
Feature: Idempotent identity seeding
  Scenario: Quarterly sync with no upstream changes
    Given a seeded catalog synced last quarter
    When the scheduled sync runs and upstream data is unchanged
    Then no payer rows change and no diff entries are created
```

### F1.6.3 — Reviewable sync diffs (payer_catalog_changes)

- **Description:** Any sync-detected difference (renamed payer, changed
  alias, disappeared payer) lands as an append-only `payer_catalog_changes`
  row for human review instead of silently overwriting curated data.
  Accepting a diff applies it; rejecting records the decision. This is also
  the M&A detection hook (Payer Change Radar, R9).
- **Persona:** Platform/Minted team; P1 as reviewer.
- **Benefit hypothesis:** Curated data can't be clobbered by an upstream
  feed; payer M&A becomes visible instead of surprising.
- **Acceptance criteria:**
  - Diff rows are append-only (no UPDATE/DELETE of history; review state is
    the only mutable field).
  - Merged payers set `status = merged` + `merged_into_id`; retired payers
    `status = retired` — never row deletion.
  - A review queue lists unreviewed diffs with accept/reject.
- **Test/data scenario(s):** TS-38 (new — upstream rename produces a diff;
  accepting applies it and logs the change).

```gherkin
Feature: Reviewable catalog diffs
  Scenario: An upstream payer rename arrives
    Given BCBS-KS exists in the catalog
    When a sync reports a new name for the same stedi_payer_id
    Then a payer_catalog_changes row is created and the payer is unchanged
    When the reviewer accepts the diff
    Then the payer name updates and the diff is marked reviewed
```

## 5. Technical Considerations & Enablers

_Reviewer-owned (Devin). Verified against the global-catalog migration
(`20260707060000_global_catalog_org_assignment.sql`), the baseline `payers`
table, and the existing payer services on 2026-07-11._

- **TE-1 — Extend, don't rebuild: the global mechanism is already live.**
  `20260707060000` already (a) dropped `payers.org_id NOT NULL` so global rows
  (`org_id IS NULL`) are legal, (b) made global payers visible to an org only
  via an `org_payer_assignments` row, and (c) left INSERT/UPDATE own-org-only
  so **org users cannot create or edit global rows — writes are service-role
  only**. `payers` already carries the curated credentialing fields the
  directory shows (`portal_url`, `avg_decision_days`, `caqh_pull_deadline_days`,
  `provisional_billing_*`, `retro_billing_*`, `payer_billing_id`,
  `prior_auth_vendor`, `provider_type_path`). E1.6 layers columns + a diff-log
  table + a read UI + a service-role seed pipeline on top; it does not touch
  the existing RLS disjunction or `org_payer_assignments`.
- **TE-2 — Additive columns on `payers` (migration + register).** Add
  `payer_kind` (`commercial|medicare|medicaid|medicaid_mco|medicare_advantage`,
  CHECK-constrained, default `commercial`), `prerequisite_payer_id` (self-FK,
  dormant until R10), `stedi_payer_id`, `cms_hios_id`, `aliases text[]`,
  `states text[]`, `status` (`active|merged|retired`, default `active`),
  `merged_into_id` (self-FK), `last_synced_at`. All additive/nullable so
  existing org-scoped payer rows are unaffected. Add an index on
  `stedi_payer_id` (the sync dedupe key) and on the two self-FKs per the E0.10
  FK-index convention. Update `docs/data-model/table-register.md` in the same
  PR. **Reconcile `status` with the existing `payers.is_active` boolean
  (independent review):** the baseline already carries
  `is_active boolean DEFAULT true`, and today's surfaces (case kickoff's
  "active payers" ordering, Admin > Payers) read it — a `retired`/`merged`
  global row would default to `is_active = true` and still look active to
  every legacy reader. The build must define the relationship explicitly:
  keep `is_active` as the legacy/org-row flag, treat `status` as the
  global-catalog lifecycle, and have every `status` transition also set
  `is_active = (status = 'active')` on global rows so legacy readers can
  never disagree with the catalog. Record the pairing in the table-register
  row (supersede-don't-mutate: name `status` as the successor field for
  global rows). Also note `states text[]` repeats the deferred array-shape
  idiom (`provider_groups.states`, E0.10: per-element format enforcement
  deferred) — enforcement stays code-side (sync pipeline + `US_STATES`
  filters) in R2.
- **TE-3 — New table `payer_catalog_changes` (append-only diff log).** Columns:
  `id`, `payer_id` FK, `field`, `old_value`, `new_value`, `source`
  (`sync|manual`), `review_state` (`unreviewed|accepted|rejected`),
  `reviewed_by`, `reviewed_at`, `created_at`. It is append-only for history:
  **no UPDATE/DELETE of the diff facts — `review_state`/`reviewed_by`/
  `reviewed_at` are the only mutable fields** (a partial exception like the
  E0.5/E0.6 hashed-link tables, not a full append-only spine). Because catalog
  rows are global (`org_id IS NULL`), the diff log is **not org-scoped**;
  gate reads to authenticated reviewers (mirror the shared-queue pattern used
  by `inbound_leads` in E0.5) and keep all writes service-role or via a
  review RPC — never a blanket `authenticated` INSERT. Add explicit `GRANT`s
  alongside RLS (AGENTS.md).
- **TE-4 — Directory read surface & service.** F1.6.1 is a cross-org
  read-only surface listing global rows (`org_id IS NULL`) — it must **not**
  show org-scoped legacy payer rows. Add a `listGlobalPayers`
  (name/alias search, `state` + `payer_kind` filters, commercial-default) read
  to `src/services/payers.ts` (or a dedicated `payerCatalog.ts`) →
  `src/hooks/`; note the current `queryKeys.payers(orgId)` is org-scoped, so
  add a **cross-org** catalog key (compare the E0.6 `orgStates()` /
  `portfolio()` cross-org keys that deliberately omit org scoping). Reuse the
  `table` primitive with custom cells for pills; `badge` for kind/status.
  **Route/nav enabler (independent review — previously unstated):** neither
  the epic body nor this section named where the directory renders. Ship it
  as a new cross-org route surfaced from the Sidebar IA v2 **Payers** segment
  (E0.9 — today: Payer Management → `/admin/payers`), e.g. a sibling "Payer
  Directory" entry; it is a workspace-level (cross-org) surface like the
  Reporting Center, not an org-zone item. Final label/placement is a
  build-time design check, not a schema question.
- **TE-5 — Seed & sync pipeline is service-role only.** F1.6.2/F1.6.3 run via
  service-role tooling (RLS-bypassing), never callable from the browser — the
  same trust posture as global-row curation. Idempotency keys on
  `stedi_payer_id`; the sync only ever writes identity fields (name, aliases,
  `stedi_payer_id`) and **never** curated credentialing fields, and it emits a
  `payer_catalog_changes` row instead of overwriting — accept applies, reject
  records. Merged → `status='merged'` + `merged_into_id`; retired →
  `status='retired'`; never row deletion.
- **TE-6 — Verification gates.** Cover TS-36 (directory browse/search/filter),
  TS-37 (idempotent re-seed → zero unreviewed diffs), TS-38 (rename → diff →
  accept applies + marks reviewed). e2e for the read surface; the service-role
  pipeline is unit/integration-tested outside the browser harness. Must pass
  `npm run lint`, `npx tsc --noEmit`, `npm run test`, `npx prettier
--check .`, and touched specs. Both schema changes applied to repo + hosted
  and reflected in `src/integrations/supabase/types.ts` (hand-add if MCP regen
  flakes, as prior stage-0 tables did; normalize on next regen).
- **Likely tech debt / risk to contain.**
  - **Stedi API key is an external prerequisite (open provisioning item with
    the PM).** F1.6.1 (directory) and F1.6.3 (diff log/review) can be built
    and shipped against seeded global fixtures **without** the key; only
    F1.6.2 (live Stedi seed/refresh) is blocked on it. Store the key as a
    repo-scoped secret (never committed); the pipeline reads it from the
    environment. This is a known, epic-flagged dependency — not a review
    blocker — but the build PR for F1.6.2 must not merge until the key is
    provisioned.
  - Existing org-scoped payer rows are **not** migrated to global rows here
    (the original migration deferred that to a separate human-supervised
    step); E1.6 must not auto-convert them.
  - `payer_kind` government values + `prerequisite_payer_id` land as dormant
    schema only; the R2 UI filters to commercial by default. No government
    workflow logic in this epic (R10).
- **No open questions requiring a stop.** Locked decisions (commercial-first,
  extend-not-rebuild, diff-based sync, quarterly + on-demand cadence, Stedi =
  identity only) are consistent with the current schema and the 2026-07-10
  catalog audit. The Stedi-account provisioning item is tracked as a
  dependency above, not a contradiction.
