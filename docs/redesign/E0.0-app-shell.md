# E0.0 — App Shell & Navigation IA

Redesign requirement (Stage 0). Target path: `docs/redesign/E0.0-app-shell.md` on the `redesign` branch of `sonny303/mintedpanel`. Status: requirements only, not yet executed. Build only from components that already exist in the current library; this epic changes structure and experience, never primitives.

Devin does not own, reorder, or refactor our epic structure, scope, or feature design. We are the consultants and the product design is ours. ## Why this exists

Every Stage 0 epic (create org, first-run landing, portfolio view) needs a place to live: a navigation frame, an active-org context, and routing. Today the app is a flat, admin-heavy route set with no journey, and no org context in the frame despite the Credentialing Manager working across many client organizations. Handing the new front door to the builder against the current layout would build the new door into the old house. E0.0 defines the skeleton that the Stage 0 epics slot into — the Credentialing Manager workspace.

This is not the design system (owned separately) and not pixel-level UI. It is the shell: nav structure, where org context lives, the layout frame, routing, and first-run/empty states.

## Personas empowered

* P1 Credentialing Manager (Sowmya) — the sole Stage 0 actor. Every shell decision serves her.
* P4 Company Owner / Ops Lead — named only as a future consumer of the shared business dashboard, not a Stage 0 actor.

No other persona operates the workspace in Stage 0.

## Component constraint (hard rule)

Every surface built from these requirements must be assembled only from components that already exist in the current library. The builder never creates a new single component, never introduces a new primitive, and never adds a new styling system. If a requirement seems to need a component that does not exist, that is a flag back to the PM, not a license to build one. Design-system cleanup is owned separately and out of scope here. This rule applies to E0.0 and to every Stage 0 epic that follows.

Repo facts (from the existing codebase, for accuracy):

* Stack: React 19 + TypeScript + Vite, TanStack Start (file-based routing), TanStack Query (server state), Zustand (client state), Tailwind CSS v4 + shadcn/ui, Supabase with org-scoped RLS.
* Layout shell lives in `src/components/layout/` (AppShell, Sidebar, PageHeader, SearchDialog); shadcn primitives live in `src/components/ui/`.
* Data flow is Component → Hook → Service (`src/services/`) → Supabase. Components never call Supabase directly.
* Migrations are additive-only.

## Locked decisions carried into every feature

* No login, no login roles, no default landing. A single Credentialing Manager context with no auth ceremony.
* Org lifecycle state (prospect / active / inactive) is tracked internally only and is never surfaced to the Credentialing Manager as a status label she manages.
* Primary navigation is a persistent left sidebar.
* From any org-scoped surface there is always a one-step path back to the full Portfolio, including while an org is a prospect.
* The Portfolio content is built decoupled from the workspace chrome so the same content can also render in a standalone no-nav shareable link surface later.
* The shell is responsive from the start; the left sidebar collapses gracefully on small screens without losing the org switcher or the one-step return to Portfolio.
* E0.0 delivers the frame only. The Portfolio renders real org data; every other nav slot is an empty reserved route until its stage is built. Do not scaffold Stage 1+ business content.

## Current state (what we are replacing)

The live app exposes a flat route set — home, providers, cases, launches, tasks, reports, client-progress, plus a large admin cluster. The problems:

* No journey. Routes are a catalog, not a path from start to finish.
* No org context in the frame, despite a multi-org Credentialing Manager.
* No deliberate first-run or empty experience.

## Features

### F0.0.1 — Left sidebar, journey-ordered navigation

Description: Primary navigation is a persistent left sidebar whose items read as the Credentialing Manager's journey, not a flat catalog. Order: Portfolio (cross-org home), then within the active org — Get started, Scope, Work, Outcomes. The admin/configuration cluster is intentionally excluded (see non-goals).

Persona: P1.

Benefit hypothesis: If the nav reflects the journey the Credentialing Manager actually walks, she orients instantly and stops hunting across unrelated routes, reducing time-to-first-action on any org.

Acceptance criteria:

* The sidebar is persistent across every workspace screen.
* Sidebar items appear in journey order: Portfolio, Get started, Scope, Work, Outcomes.
* Org-scoped items are visually grouped under the active org; Portfolio sits above org context.
* No admin/configuration items appear in the sidebar.
* Every item routes to a live or reserved-empty route; no dead links.
* On small screens the sidebar collapses gracefully while preserving access to the org switcher and the return-to-Portfolio action.
* Open decision (TODO): whether "Get started" persists once an org is scoped is undecided; default to always-present until decided (see OQ-2).

```gherkin
Feature: Left sidebar journey navigation

  Scenario: The sidebar reflects the journey, not a flat catalog
    Given I am the Credentialing Manager (P1) in an active org
    When I view the left sidebar
    Then I see Portfolio above the org context
    And within the active org I see Get started, Scope, Work, and Outcomes in that order
    And I do not see any admin or configuration items

  Scenario: The sidebar collapses gracefully on small screens
    Given I am the Credentialing Manager (P1) on a small screen
    When I view the workspace
    Then the left sidebar collapses gracefully
    And I still have access to the org switcher and the return-to-Portfolio action

```

### F0.0.2 — Active-org context

Description: The workspace always shows which organization is active. All org-scoped surfaces render within that context. The internal lifecycle state is not shown to the Credentialing Manager.

Persona: P1.

Benefit hypothesis: If the active org is always visible in the frame, the Credentialing Manager never acts on the wrong client's data, eliminating a whole class of cross-org mistakes.

Acceptance criteria:

* The active org name is visible in the frame at all times on org-scoped surfaces.
* No lifecycle state label (prospect/active/inactive) is shown to the Credentialing Manager anywhere in the frame.
* Org-scoped surfaces render only the active org's data.
* Cross-org surfaces (Portfolio) do not require an active org.

```gherkin
Feature: Active-org context

  Scenario: The active org is always visible
    Given I am the Credentialing Manager (P1)
    And my active org is "Org A"
    When I am on any org-scoped surface
    Then the frame shows "Org A" as the active organization
    And no lifecycle status label is shown to me

  Scenario: Portfolio does not require an active org
    Given I have not selected an active org
    When I open the Portfolio
    Then it renders without requiring an active org

```

### F0.0.3 — Org switching with state clearing

Description: A multi-org Credentialing Manager can switch the active org from the frame. Switching cleanly rescopes the workspace and clears org-scoped view state before the new org loads.

Persona: P1.

Benefit hypothesis: If switching orgs reliably wipes the prior org's transient state, the Credentialing Manager trusts that nothing leaks between clients, so she switches freely without double-checking.

Acceptance criteria:

* The frame offers a way to switch the active org.
* On switch, the following clear before the new org loads: selected provider, selected case, selected facility/location, active filters, and any in-progress unsaved form state.
* After switch, all org-scoped surfaces reflect the newly selected org.
* No data or view state from the prior org remains visible.

```gherkin
Feature: Org switching with state clearing

  Scenario: Switching the active org rescopes and clears state
    Given I am a multi-org Credentialing Manager with "Org A" and "Org B"
    And my active org is "Org A"
    And I have a selected provider, a selected case, and active filters in "Org A"
    When I switch the active org to "Org B"
    Then the selected provider, selected case, selected facility, filters, and any unsaved form state are cleared
    And all org-scoped surfaces now reflect "Org B"
    And no view state from "Org A" remains visible

```

### F0.0.4 — One-step return to the Portfolio

Description: From any org-scoped surface, the Credentialing Manager can return to the full cross-org Portfolio in one step, including while an org is a prospect. There is no dead end inside an org.

Persona: P1.

Benefit hypothesis: If stepping back to the whole book of business is always one action away, the Credentialing Manager moves between prospecting and active work without friction, supporting the prospecting-capture flow.

Acceptance criteria:

* A one-step return to the Portfolio is available from every org-scoped surface.
* Return works identically whether the org is a prospect, active, or inactive internally.
* Returning to the Portfolio does not require selecting or deselecting anything first.

```gherkin
Feature: One-step return to the Portfolio

  Scenario: Return to the Portfolio from inside a prospect org
    Given I am the Credentialing Manager (P1) working inside "Org A"
    And "Org A" is a prospect internally
    When I choose to return to the Portfolio
    Then I land on the full cross-org Portfolio in one step
    And I did not have to change any selection first

```

### F0.0.5 — Portfolio as a decoupled, shareable business dashboard

Description: The Portfolio is the Credentialing Manager's cross-org working view and represents the business (orgs in motion now; facilities and providers in motion in later stages). Its content is built decoupled from the workspace chrome so the same content can render inside the workspace now and inside a standalone no-nav shareable link surface later. The Portfolio shows two separate metrics — prospects and in-motion — so a prospect (no real work yet) is not conflated with an org that has active work; internally inactive/archived orgs are excluded from both.

Persona: P1 (sole actor). P4 is named only as a future consumer of the shared dashboard, not an actor in E0.0.

Benefit hypothesis: If the Portfolio is built as chrome-independent content, we get the operator's cross-org view now and a shareable business dashboard later with no rework, turning the Party model into visible value.

Acceptance criteria:

* The Portfolio lists the Credentialing Manager's orgs and shows a prospects count and a separate in-motion count.
* Internally inactive/archived orgs are excluded from both counts.
* Portfolio content is rendered from a component that does not depend on the sidebar/chrome, so it can be embedded in a standalone surface later.
* E0.0 implements only the workspace-context rendering; the standalone link surface is out of scope here.

```gherkin
Feature: Portfolio as a decoupled shareable dashboard

  Scenario: Prospects and in-motion are shown separately
    Given I have "Org A" (active internally), "Org B" (prospect), and "Org C" (inactive)
    When I view the Portfolio
    Then "Org B" is shown in the prospects count
    And "Org A" is shown in the in-motion count
    And "Org C" is excluded from both counts

  Scenario: Portfolio content is chrome-independent
    Given the Portfolio content component
    When it is rendered
    Then it does not depend on the workspace sidebar or chrome to display

```

### F0.0.6 — First-run empty state

Description: When the Credentialing Manager has no organizations, the workspace lands on a first-run Portfolio state that guides her to create her first organization, handing directly to E0.1. Empty states elsewhere propose the next action rather than showing a blank region.

Persona: P1.

Benefit hypothesis: If a brand-new, empty workspace points straight at "create your first organization," the Credentialing Manager reaches the revenue-starting front door with zero guesswork.

Acceptance criteria:

* With zero orgs, the workspace shows a first-run Portfolio state, not a blank screen.
* The first-run state offers a clear action to create the first organization (hands to E0.1).
* No login or landing gate precedes the first-run state.
* Reserved-empty nav slots show a consistent "not yet available" next-action prompt rather than a blank region.

```gherkin
Feature: First-run empty state

  Scenario: A Credentialing Manager with no orgs is guided to the front door
    Given I am the Credentialing Manager (P1)
    And I have no organizations
    When I open the workspace
    Then I land on a first-run Portfolio state
    And I am offered a clear action to create my first organization
    And no login or landing gate preceded this

  Scenario: Reserved Stage 1+ routes show a consistent not-yet-available state
    Given a reserved route for a later stage
    When I navigate to it
    Then I see the shared "not yet available" empty state
    And no scaffolded content and no blank page is shown

```

## Routing requirements

* Routes map to the funnel structure so the URL reflects where in the journey the Credentialing Manager is.
* Org-scoped routes carry the active org context.
* Cross-org routes (Portfolio) do not require an active org.
* Reserved routes for Stage 1+ resolve to a single consistent "not yet available" empty state shared across all reserved slots — not scaffolded content and not a blank page.

### Known constraints (seeded by us, for Devin's context)

* No schema change is required by E0.0; it is a frame over existing org-scoped data via the Component → Hook → Service → Supabase flow.
