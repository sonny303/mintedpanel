# E2.0 — Case Generation Preview & Exclusions

## Purpose and Context

R4's front door. Sowmya today enumerates provider × payer × state
combinations by hand in a spreadsheet. The `[r4]` Q1 decision (2026-07-12):
the system computes every valid combination from the R1–R3 data (roster ×
assignments × payer network targets) and shows a **preview checklist** she
reviews before anything is created — with per-provider exceptions handled by
**persistent, reasoned exclusions** (Q1a) and existing cases shown grayed-out
as "already exists — in progress" (Q2) so she sees the full picture without
re-creating anything.

The candidate key is the locked case grain: **provider × group × payer ×
state**. A row is proposed when the provider **holds a facility (clinic)
assignment under the group** (`[r4-review]` Q4 — PM decision: group
membership alone is not enough; Jane may be a member of Group 2 but only
actually work at a Group 1 clinic), the group has an active
`payer_network_targets` row for that payer × state, and no exclusion or
existing case covers the key. The buildable rule reconciling this with §5
TE-4: candidate = TE-4's membership universe (un-ended
`provider_group_assignments`) **further filtered to providers with at least
one `provider_facility_assignments` row at a facility of the group**
(presence-based — the table has no end_date/status; an assignment-lifecycle
semantic is a later additive epic). Because the candidate set is a subset of
the E1.8 readiness universe, `readinessForCaseKey` resolves for every
candidate row.

Existing-case suppression is **status-linked** (`[r4-review]` Q5/Q6): a key
whose case is Credentialed (or final-Denied and excluded) stays suppressed
while that status holds; if the case's status is later changed off that
status, the suppression lifts and the key resurfaces as an existing-case row
(status-aware label, reapply on the same case) until manually excluded
again. The suppression is derived live from case status — nothing mutates
append-only history.

## Personas Empowered

- **P1 Credentialing Manager** — runs generation, reviews the preview,
  manages exclusions.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: the combination computation must be a pure,
  unit-tested module (the E1.5 `payerExpansion.ts` pattern) — inputs are
  roster, assignments, targets, exclusions, existing cases; output is typed
  preview rows with a human-readable derivation reason.
- Implementation dependency: one additive table `case_generation_exclusions`
  (org_id, provider_id, group_id, payer_id, state, reason enum
  `already_credentialed | panel_closed | not_pursuing | other` + note,
  created_by/at; unique on the 4-part key) + table-register row + org-scoped
  RLS.
- Implementation dependency: readiness display per row reuses E1.8 derivation;
  Q3a adds **group contract status** as a readiness input — surfaced here and
  reconciled with E1.8's advisory model (decide additively in §5).

## Features

### F2.0.1 — Computed preview checklist

- **Description:** "Generate applications" opens a preview listing every
  candidate provider × group × payer × state row, checked by default, with
  derivation reason, readiness signal (E1.8, incl. group contract status),
  and existing-case indicator. Nothing is created until confirm (E2.1).
- **Persona:** P1.
- **Benefit hypothesis:** Kills the spreadsheet; misses and duplicates become
  structurally impossible.
- **Acceptance criteria:**
  - Every valid combination appears exactly once; none the system cannot
    derive appears (manual one-offs live elsewhere, Q2a).
  - Each row shows provider, group, payer, state, readiness, and reason.
  - Rows for existing cases at the same key render grayed-out,
    non-selectable, with a **status-aware** label (§5 TE-7): in-flight cases
    read "already exists — in progress"; denied/closed cases read "reapply
    from the case" linking to it (never re-creatable from here).
  - Unchecking a row prevents its creation on confirm.
- **Test/data scenario(s):** TS-48.

```gherkin
Feature: Preview computes the full candidate set
  Scenario: Two-group org previews generation
    Given Shelby has 8 providers assigned across Group 1 (NC) and Group 2 (NC, KS)
    And active payer targets exist for BCBS-NC (both groups) and BCBS-KS (Group 2)
    And Jane already has an in-flight BCBS-NC case under Group 1
    When P1 opens the generation preview
    Then all derivable provider × group × payer × state rows are listed
    And Jane's Group 1 × BCBS-NC row is grayed out as "already exists — in progress"
```

### F2.0.2 — Persistent exclusions with reasons

- **Description:** Unchecking a row prompts for a reason (already
  credentialed / panel closed / not pursuing / other + note) and records a
  persistent exclusion: the row is not re-proposed on future runs, shown
  instead in a collapsible "excluded" section with reason, restorable in one
  click.
- **Persona:** P1.
- **Benefit hypothesis:** Q1a — exceptions are decided once, not re-litigated
  every generation run.
- **Acceptance criteria:**
  - Excluding requires a reason; the exclusion persists across runs.
  - Excluded rows appear in an "excluded" view with reason and are
    restorable (void the exclusion — never a hard delete, §5 TE-2 → row
    re-proposed next run).
  - Exclusion/restore writes are admin-only (`[r4-review]` Q5; mirrors
    `payer_network_targets`). The `other` reason (+ required note) is
    PM-approved.
  - An exclusion never touches existing cases.
- **Test/data scenario(s):** TS-48, TS-49.

```gherkin
Feature: Exclusions persist with reasons
  Scenario: Provider already credentialed with a payer
    Given P1 excludes Jane × Group 2 × Cigna-NC × NC with reason "already credentialed"
    When generation runs again next quarter after two new hires
    Then Jane's Cigna row is not proposed
    And it is visible under Excluded with its reason and a restore action
```

### F2.0.3 — Delta runs (re-generation)

- **Description:** Re-running generation after data changes (new hire, new
  payer target, new state) proposes only genuinely new keys: existing cases
  grayed, exclusions suppressed, everything else checked.
- **Persona:** P1.
- **Acceptance criteria:**
  - Adding one provider and re-running proposes only that provider's rows
    (plus any other new keys); nothing existing is re-created.
  - Archived payer targets produce no rows.
- **Test/data scenario(s):** TS-49.

## 5. Technical Considerations & Enablers

_Independent review (Claude Code) per REVIEW-HANDOFF, 2026-07-13. Verified
against: the baseline schema (`20260704210000_baseline_live_schema.sql`), the
E1.5 target migration (`20260712190000_payer_network_targets.sql`), the E1.3
join migration (`20260712120000_provider_group_assignments.sql`), the built
E1.8 evaluator `src/lib/enrollmentReadiness.ts` (including
`readinessForCaseKey`, the TE-10 soft-warn contract) and its read layer
`src/services/enrollmentReadiness.ts`, the E1.5 pure-module pattern
`src/lib/payerExpansion.ts`, `docs/data-model/table-register.md`, the [r4]
decisions in `CLARIFICATIONS_NEEDED.md`, `seed-universe.md` TS-48/TS-49, and
the approved component inventory (`uiux-component-guide.md` +
`src/components/ui/`). No blockers; four should-fix redlines and two PM
questions below._

- **TE-1 — One additive table: `case_generation_exclusions` (+ register row).**
  Additive migration creating
  `public.case_generation_exclusions`:
  `(id uuid PK DEFAULT gen_random_uuid(), org_id uuid NOT NULL →
organizations, provider_id uuid NOT NULL → providers, group_id uuid NOT NULL
→ provider_groups, payer_id uuid NOT NULL → payers, state text NOT NULL
CHECK (state ~ '^[A-Z]{2}$') [the E0.10 state-format floor, NOT-NULL form],
reason text NOT NULL CHECK (reason IN ('already_credentialed',
'panel_closed', 'not_pursuing', 'other')), note text NULL, status text NOT
NULL DEFAULT 'active' CHECK (status IN ('active','voided')), created_by uuid
NOT NULL → profiles [the `credential_cases.created_by` house pattern],
created_at timestamptz NOT NULL DEFAULT now(), voided_by uuid NULL →
profiles, voided_at timestamptz NULL)`. The "reason enum" is a **text +
  CHECK constraint, not a Postgres enum type** — every enum in this schema is a
  CHECK (`payer_network_targets_status_check` is the sibling precedent). Add
  `CHECK (reason <> 'other' OR (note IS NOT NULL AND btrim(note) <> ''))` so
  "other" always carries its note (the epic's "other + note"). The epic's
  "unique on the 4-part key" is realized as a **partial unique index**
  `ON (provider_id, group_id, payer_id, state) WHERE status = 'active'` so
  voided history rows never block a later re-exclusion (see TE-2). FK cover
  indexes on `group_id`, `payer_id`, `org_id` per the E0.10 convention
  (`provider_id` leads the partial unique). `org_id` is deliberately
  denormalized (derivable via `provider_id`/`group_id`) so RLS filters on it
  directly — the `payer_network_targets` precedent. Table-register row (work
  layer; the generation-input side-table to the `credential_cases` center) and
  `src/integrations/supabase/types.ts` regeneration land in the same PR.
- **TE-2 — Restore = void, never DELETE (decides F2.0.2's "delete/void"
  hedge).** E2.4 F2.4.1 requires run detail to link "each exclusion to its
  exclusion record"; a hard DELETE would dangle those links, and the program
  keeps history in rows plus the audit spine ("supersede, don't mutate" —
  table-register design rule 4; E1.5's archive-not-delete is the sibling
  precedent). Restore flips `status → 'voided'` and stamps
  `voided_by`/`voided_at`; a later re-exclusion inserts a fresh `active` row
  (the TE-1 partial unique permits this). Audit both writes via the existing
  `writeAudit` (`CREATE` on exclude, `UPDATE` on restore, additive entity type
  `case_generation_exclusion`): verified `audit_log.entity_type` carries **no
  CHECK constraint** (baseline) and both action types are already allowed, so
  **no audit migration is needed**. F2.0.2's "restorable in one click" is the
  void flip; "an exclusion never touches existing cases" is trivially true —
  this table references cases nowhere.
- **TE-3 — RLS: member SELECT, admin write, same-org WITH CHECKs, no DELETE
  grant.** Enable RLS; `GRANT SELECT, INSERT, UPDATE ON ... TO authenticated`
  — deliberately **no DELETE grant**, enforcing TE-2 at the grant layer;
  `REVOKE ALL FROM anon`. Member SELECT (`org_id IN (SELECT user_org_ids())`);
  INSERT/UPDATE admin-only (`user_role(org_id) = 'admin'`), mirroring
  `payer_network_targets` — the sibling scope-shaping table — including its
  stricter WITH CHECKs: `provider_id` and `group_id` must each belong to the
  same org (EXISTS subqueries), so a multi-org admin cannot cross tenant
  references. `payer_id` needs no org check (the payers catalog is shared;
  a payer id is not a tenant secret, and the org-scoped unique key rides
  `provider_id`). Every insert sets `org_id` from the active org (AGENTS.md).
  Role choice is PM question 2 (admin-only recommended).
- **TE-4 — Candidacy runs on `provider_group_assignments`, not facility
  assignment (corrects the Purpose's derivation phrase; redline 1).** The
  built E1.8 evaluator derives its rows as active `payer_network_targets` ×
  providers with an **un-ended `provider_group_assignments` row** in the
  target's group (`evaluateEnrollmentReadiness`, end-date semantics shipped in
  follow-up #131). The epic's "active assignment to a **facility** of the
  group" cannot be built as written: `provider_facility_assignments` has **no
  end_date or status column** (baseline: `is_primary`, `start_date`,
  `practice_frequency`), so "active" is undefined for it — and a
  facility-based candidate set would diverge from the readiness row set,
  making `readinessForCaseKey` return `{ ready: false, openGaps: [] }` for
  candidates with no membership row. Rule for the build: **candidate =
  active target × provider whose `provider_group_assignments` row in the
  target's group is not end-dated before today** — the exact E1.8 derivation,
  so preview rows and readiness rows are the same universe. Facility coverage
  stays what it already is: the `state_facility` **group readiness check**,
  not a candidacy filter. PM question 1 confirms.
- **TE-5 — The combination computation is a pure, unit-tested `src/lib`
  module.** `src/lib/generationPreview.ts` (+ `.test.ts`), per the epic's own
  constraint and the `payerExpansion.ts` / `enrollmentReadiness.ts` pattern:
  typed inputs (targets, group assignments, provider facts, exclusions,
  existing cases, `today` passed in — never a clock read inside), output
  typed preview rows `{ providerId, groupId, payerId, state, disposition:
'proposed' | 'existing' | 'excluded', reason }` where `reason` is the
  human-readable derivation ("Jane is in Group 1; Group 1 targets BCBS-NC in
  NC"). No Supabase in the module. Unit suite must cover: every key exactly
  once (dedupe), archived targets produce no rows (F2.0.3 AC), exclusion
  suppression + voided-exclusion re-proposal, existing-case gray-out at both
  matching branches of TE-6, and the delta run (add one provider → only that
  provider's keys are newly proposed).
- **TE-6 — Existing-case matching must handle the pre-E2.1 3-part reality.**
  `credential_cases` today has `UNIQUE (provider_id, payer_id, state)` and
  **no `group_id` column** — E2.1 adds it (register + AGENTS.md; build order
  is E2.0 → E2.1 per ROADMAP-STATUS). The preview's existing-case input is
  therefore `{ providerId, payerId, state, groupId: string | null, … }`, and
  the matching rule is: **a NULL-group case (every legacy row) covers ALL
  candidate rows at its (provider, payer, state) regardless of group; a
  group-stamped case (post-E2.1) covers only its exact 4-part key.** This is
  the preview-side mirror of E2.1's "widened uniqueness still enforces the
  3-part rule for legacy NULL-group rows." Encode it in the pure module and
  test both branches — do not gate the E2.0 build on the E2.1 migration.
- **TE-7 — The existing-case label is status-aware (reconciles F2.0.1 with
  E2.1 F2.1.3; redline 2).** E2.1 requires the preview row at a key with a
  denied/closed case to link "reapply from the case" — labeling every
  existing case "already exists — in progress" would be wrong for those.
  Derive the wording from the case's credentialing status `action_bucket`
  (the `status_configs`-derived idiom `src/services/providerCases.ts` already
  uses; status-less cases count as open): non-complete bucket → "already
  exists — in progress"; complete bucket → "already exists" + the status
  label (e.g. Denied). All existing-case rows stay grayed and non-selectable;
  the reapply **link** itself is E2.1 scope.
- **TE-8 — Group contract status readiness input (the delegated Q3a
  decision): an additive, optional evaluator input.** Extend
  `src/lib/enrollmentReadiness.ts` additively with an optional input
  `contracts?: ReadonlyArray<{ groupId, payerId, state, statusLabel: string |
null }>` and a new group-owner check key `group_contract`. When the input is
  **omitted**, no check is emitted — every existing E1.8 caller and test is
  bit-for-bit unchanged; the E2.0 preview passes it. The check is computed
  **per target (group × payer × state)** — it cannot ride the existing
  group-check cache, which is keyed `(group, state)` only (verified in
  `evaluateEnrollmentReadiness`); contracts vary by payer. Pass = a
  `contracts` row exists at the key (grain `UNIQUE (group_id, payer_id,
state)`, baseline) whose label canonicalizes to `CONTRACTED_LABEL`
  (`src/lib/statusLabels.ts` via `canonicalLabel` — never a re-hardcoded
  literal); detail shows the actual label or "No contract". Advisory always:
  it feeds the row's readiness signal and never disables anything (E1.8
  F1.8.3). Contracting status stays on `contracts` — nothing here writes or
  reads status onto cases (AGENTS.md).
- **TE-9 — One evaluation pass, joined by key — and honest no-data
  rendering.** Do not call `readinessForCaseKey` per preview row (it re-runs
  the full evaluation each call — O(rows²) for an org-wide preview); call
  `evaluateEnrollmentReadiness` once over the assembled inputs and join rows
  to candidates by the 4-part key. With TE-4 alignment every candidate has a
  readiness row; still, render a missing row as a neutral "no readiness data"
  — never a green Ready (the contract returns `{ ready: false, openGaps: []
}` for unknown keys, which must not display as "0 gaps = ready").
- **TE-10 — Services/hooks/UI wiring, all from the approved inventory.**
  Service `src/services/caseGenerationExclusions.ts` (list / create / void;
  `requireActiveOrg()`, `org_id` on insert, `writeAudit`, snake↔camel at the
  boundary) and a preview-assembly read that reuses
  `src/services/enrollmentReadiness.ts`'s batched style (one query per source
  table, joined in memory — never per-row round-trips), widened only by the
  narrow `credential_cases` and `contracts` projections (TE-13). Hooks
  `useGenerationPreview` / `useCaseGenerationExclusions` with new org-scoped
  `queryKeys` entries; mutations invalidate by prefix. Domain type
  `CaseGenerationExclusion` added additively to `src/types/index.ts`. Feature
  components under `src/components/generation/` (never `ui/` or `layout/` —
  no protected-file change is needed or authorized by this epic). Primitives —
  all verified present in `src/components/ui/`: `table` + `checkbox` with
  custom cell markup for the preview checklist (grayed rows are custom
  non-selectable rows), `dialog` + `select` + `textarea` for the reason
  prompt, `collapsible` for the excluded section, `badge` for the readiness
  chip. `radio-group` is NOT in the inventory; `select` suffices for four
  reasons — if a build prefers radios, add the primitive via the shadcn
  generator in its own commit and log it per the component guide (no
  DESIGN-DEBT entry is otherwise required). Entry affordance: the natural
  home for "Generate applications" is the E1.8 Scope Review readiness surface
  (same row universe per TE-4); placement is a build detail, not a scope
  change.
- **TE-11 — Delta runs are stateless recomputation; nothing is stored at
  preview time.** F2.0.3 needs no run storage: the preview recomputes from
  live inputs on every open (the E1.5 TE-7 derived-not-stored rule — no dirty
  flags, no cached proposals). The only persistent artifacts are exclusions
  (this epic) and E2.1's `case_generation_runs` at confirm (explicitly not
  here). "Only genuinely new keys proposed" falls out of derivation:
  unchanged keys are grayed (existing) or suppressed (excluded), never
  re-created.
- **TE-12 — PHI + isolation posture.** Preview rows carry provider name,
  group, payer, state, readiness, and reason — no demographics; readiness
  details are already non-sensitive presence booleans folded at the E1.8
  service boundary (its TE-9). The `credential_cases` read uses a narrow
  projection (`id, provider_id, payer_id, state, credentialing_status_id`) —
  never `select('*')`. Exclusion rows store keys + reason + note only; audit
  payloads carry ids and reason, never the note body wholesale if it might
  hold free text about a provider — keep audit `after` to the row's ids +
  reason. No `/api` route is added, so the org-isolation gate is untouched;
  tenant isolation here is browser RLS (TE-3), the same posture as every
  other redesign surface. `anon` is fully revoked on the new table.
- **TE-13 — Table trace + verification gates.** Reads:
  `payer_network_targets` (active), `provider_group_assignments`,
  `providers`, `provider_groups`, `payers`, `credential_cases` (narrow, TE-12),
  `contracts` + `status_configs` (TE-7/TE-8 labels), and — via the reused
  E1.8 readiness service — `state_licenses`, `facilities`,
  `provider_documents`, `group_insurance_policies`. Writes:
  `case_generation_exclusions` (new, TE-1) and `audit_log` via `writeAudit`.
  Reconciled against `docs/data-model/table-register.md` 2026-07-13; the one
  new row is TE-1's. Gates: the pure-module unit suite (TE-5) plus additive
  evaluator tests (TE-8) are the primary coverage; e2e for **TS-48** (all
  derivable rows exactly once, reasons + readiness shown, the in-flight case
  grayed with the status-aware label) and **TS-49** (exclude with reason →
  re-run after two new hires → exclusion holds, visible, restorable; only new
  keys proposed). Must pass `npm run lint`, `npx tsc --noEmit`,
  `npm run test`, `npx prettier --check .`; migration applied repo + hosted,
  types regenerated, register row added — all in the same PR.

### Reviewer redlines (independent review per REVIEW-HANDOFF, 2026-07-13)

1. **should-fix** — The candidacy rule "the provider has an active assignment
   to a **facility** of the group" (Purpose, ¶2) contradicts the built E1.8

   `src/lib/enrollmentReadiness.ts` derives rows from
   `provider_group_assignments` (end-date aware, follow-up #131), and
   `provider_facility_assignments` has no end_date/status column (baseline),
   so "active" is undefined for it. Reword to group membership per TE-4, or
   escalate to the PM if facility-based candidacy is genuinely intended (PM
   question 1).
2. **should-fix** — F2.0.1's AC hard-codes the label "already exists — in
   progress" for every existing-case row; E2.1 F2.1.3 requires denied/closed
   keys to surface "reapply from the case" instead. Make the label
   status-aware per TE-7 (grayed always; wording from the status
   `action_bucket`).
3. **should-fix** — F2.0.2's AC "(delete/void the exclusion → row re-proposed
   next run)" leaves the destructive choice open. E2.4 F2.4.1 links run
   details to exclusion records — a hard DELETE would dangle them. §5 decides
   void-not-delete (TE-2); drop "delete" from the AC.
4. **should-fix** — F2.0.2's gherkin names provider **"Maria"**, who does not
   exist anywhere in `seed-universe.md` (Jane is seeded via TS-50; no Maria
   fixture). Per the template's authoring rules 3/5: rename to a seeded
   provider or extend TS-49's fixture description in `seed-universe.md` to
   define Maria (author's edit, not the reviewer's).
5. **nit** — The reason enum adds `other` (+ note) beyond the [r4] decision's
   three reasons ("already credentialed / panel closed / not pursuing"). A
   sensible escape hatch — flagged only so the PM approves the extension
   knowingly (TE-1 requires the note when `other` is chosen).
6. **nit** — The epic omits an explicit table trace (AGENTS.md: "Epics and
   feature specs list a table trace"). TE-13 supplies the authoritative
   trace, matching the E1.5/E1.8 precedent of carrying it in §5.

### PM decisions applied (2026-07-13, `[r4-review]`)

  group-membership recommendation. The buildable rule (recorded in Purpose
  ¶2): TE-4's membership universe further filtered to providers holding at
  least one `provider_facility_assignments` row at a facility of the group.

  subset of the E1.8 universe. TE-4's warning about diverging row universes
  is accepted knowingly: the preview shows fewer rows than the readiness
  matrix, by design.
- **Q2 (write role) — admin-only**, per the reviewer's recommendation.
- **Exclusion lifecycle is status-linked** (Q5/Q6 of the review round): see
  Purpose ¶3; suppression for Credentialed / final-Denied keys derives live
  from case status and lifts on status change, without touching exclusions
  history or append-only spines.
