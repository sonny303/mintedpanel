# E2.0 — Case Generation Preview & Exclusions

## Purpose and Context

R4's front door. Sowmya today enumerates provider × payer × state
combinations by hand in a spreadsheet. The `[r4]` Q1 decision (2026-07-12):
the system computes every valid combination from the R1–R3 data (roster ×
assignments × payer network targets) and shows a **preview checklist** she
reviews before anything is created — with per-provider exceptions handled by
**persistent, reasoned exclusions** (Q1a) and existing cases shown grayed-out
as "already exists — in progress" (Q2) so she sees the full picture without
re-creating anything.

The candidate key is the locked case grain: **provider × group × payer ×
state**. A row is proposed when the provider has an active assignment to a
facility of the group, the group has an active `payer_network_targets` row
for that payer × state, and no exclusion or existing case covers the key.

## Personas Empowered

- **P1 Credentialing Manager** — runs generation, reviews the preview,
  manages exclusions.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- Implementation dependency: the combination computation must be a pure,
  unit-tested module (the E1.5 `payerExpansion.ts` pattern) — inputs are
  roster, assignments, targets, exclusions, existing cases; output is typed
  preview rows with a human-readable derivation reason.
- Implementation dependency: one additive table `case_generation_exclusions`
  (org_id, provider_id, group_id, payer_id, state, reason enum
  `already_credentialed | panel_closed | not_pursuing | other` + note,
  created_by/at; unique on the 4-part key) + table-register row + org-scoped
  RLS.
- Implementation dependency: readiness display per row reuses E1.8 derivation;
  Q3a adds **group contract status** as a readiness input — surfaced here and
  reconciled with E1.8's advisory model (decide additively in §5).

## Features

### F2.0.1 — Computed preview checklist

- **Description:** "Generate applications" opens a preview listing every
  candidate provider × group × payer × state row, checked by default, with
  derivation reason, readiness signal (E1.8, incl. group contract status),
  and existing-case indicator. Nothing is created until confirm (E2.1).
- **Persona:** P1.
- **Benefit hypothesis:** Kills the spreadsheet; misses and duplicates become
  structurally impossible.
- **Acceptance criteria:**
  - Every valid combination appears exactly once; none the system cannot
    derive appears (manual one-offs live elsewhere, Q2a).
  - Each row shows provider, group, payer, state, readiness, and reason.
  - Rows for existing cases at the same key render grayed-out,
    non-selectable, labeled "already exists — in progress" (never
    re-creatable from here).
  - Unchecking a row prevents its creation on confirm.
- **Test/data scenario(s):** TS-48.

```gherkin
Feature: Preview computes the full candidate set
  Scenario: Two-group org previews generation
    Given Shelby has 8 providers assigned across Group 1 (NC) and Group 2 (NC, KS)
    And active payer targets exist for BCBS-NC (both groups) and BCBS-KS (Group 2)
    And Jane already has an in-flight BCBS-NC case under Group 1
    When P1 opens the generation preview
    Then all derivable provider × group × payer × state rows are listed
    And Jane's Group 1 × BCBS-NC row is grayed out as "already exists — in progress"
```

### F2.0.2 — Persistent exclusions with reasons

- **Description:** Unchecking a row prompts for a reason (already
  credentialed / panel closed / not pursuing / other + note) and records a
  persistent exclusion: the row is not re-proposed on future runs, shown
  instead in a collapsible "excluded" section with reason, restorable in one
  click.
- **Persona:** P1.
- **Benefit hypothesis:** Q1a — exceptions are decided once, not re-litigated
  every generation run.
- **Acceptance criteria:**
  - Excluding requires a reason; the exclusion persists across runs.
  - Excluded rows appear in an "excluded" view with reason and are
    restorable (delete/void the exclusion → row re-proposed next run).
  - An exclusion never touches existing cases.
- **Test/data scenario(s):** TS-48, TS-49.

```gherkin
Feature: Exclusions persist with reasons
  Scenario: Provider already credentialed with a payer
    Given P1 excludes Maria × Group 2 × Cigna-NC × NC with reason "already credentialed"
    When generation runs again next quarter after two new hires
    Then Maria's Cigna row is not proposed
    And it is visible under Excluded with its reason and a restore action
```

### F2.0.3 — Delta runs (re-generation)

- **Description:** Re-running generation after data changes (new hire, new
  payer target, new state) proposes only genuinely new keys: existing cases
  grayed, exclusions suppressed, everything else checked.
- **Persona:** P1.
- **Acceptance criteria:**
  - Adding one provider and re-running proposes only that provider's rows
    (plus any other new keys); nothing existing is re-created.
  - Archived payer targets produce no rows.
- **Test/data scenario(s):** TS-49.

## Dependencies

- E1.3 roster, E1.4 assignments, E1.5 `payer_network_targets`, E1.8
  readiness derivation, E1.6 catalog metadata.
- E2.1 consumes the confirmed checked set (creation is E2.1, not this epic).

## Out of Scope / Non-Goals

- Creating cases (E2.1) and stamping SOPs (E2.2).
- Manual one-off case creation outside the derivable set — Q2a: a separate
  "create case" action, not a preview escape hatch (E2.1 scope).
- Prerequisite-payer logic — Q3: none, by decision; commercial + MA run in
  parallel.
