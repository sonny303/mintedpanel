# E3.2 — NPPES Lookup Aid (Post-Import Verification Helper)

## Purpose and Context

`[r5]` decision 1 keeps CAQH out of R5 but allows NPPES "if it's
straightforward to set up" — and decision 11 forbids external calls
**during** import. This epic threads that needle: NPPES (the free public
NPI Registry API) is a **user-triggered verification aid** that runs
downstream of an E3.1 commit, helping a user verify pending-verification
providers by comparing the stored record against the registry — never a
dependency of the import pipeline.

This epic is deliberately small and severable: if the reviewer finds the
NPPES integration non-straightforward (CORS, availability, terms), the PM
can defer it without touching E3.0/E3.1.

## Personas Empowered

- **P2 Credentialing Coordinator / Specialist** — verifies staged providers
  against the registry.
- **P1 Credentialing Manager** — spot-checks imports before bulk-verifying.

## Component & Data Constraints

- Built from the current component library per
  [uiux-component-guide.md](./uiux-component-guide.md); scenario data from
  [seed-universe.md](./seed-universe.md).
- No new dependencies: the NPI Registry API is a public, keyless JSON API —
  the reviewer verifies the buildable call path (browser fetch vs a thin
  Nitro proxy for CORS/rate hygiene) and records it in §5.
- Nothing auto-writes from NPPES: results render as a comparison; applying
  a registry value goes through the existing per-field edit flows with
  audit. Registry responses are not stored (display-only), avoiding a
  PHI/staleness liability.
- Failures degrade gracefully: NPPES being down never blocks verification —
  the user can always verify manually.

## Features

### F3.2.1 — Per-provider NPPES check

- **Description:** On a pending-verification provider, a "Check NPPES"
  action fetches the registry record by NPI and renders a side-by-side
  comparison (name, specialty/taxonomy, practice state) with match/mismatch
  indicators.
- **Persona:** P2, P1.
- **Benefit hypothesis:** verifying a staged provider takes seconds against
  the authoritative registry instead of a manual portal visit.
- **Acceptance criteria:**
  - Matching fields show a match indicator; mismatches are highlighted with
    both values visible.
  - NPI not found / API unavailable render distinct, non-blocking states.
  - Applying a registry value uses the existing edit flow (audited); nothing
    applies automatically.
- **Test/data scenario(s):** TS-64.

```gherkin
Feature: Registry comparison
  Scenario: Mismatched specialty is surfaced, not applied
    Given a pending-verification provider whose imported specialty differs from NPPES
    When P2 runs Check NPPES
    Then the specialty row shows both values highlighted as a mismatch
    And the stored record is unchanged until P2 explicitly applies a value
```

### F3.2.2 — Verification workflow integration

- **Description:** The NPPES check lives inside the E3.1 verification flow:
  from the pending-verification list, a user can check, resolve, and verify
  a provider in one pass; the verify action records whether an NPPES check
  was run (audit note, not a gate).
- **Persona:** P2.
- **Benefit hypothesis:** verification becomes a single loop instead of
  tab-hopping between the roster and the registry.
- **Acceptance criteria:**
  - The check is reachable from the pending-verification surface without
    leaving it.
  - Verification is never blocked on NPPES (advisory only, mirroring the
    E1.8 advisory model).
- **Test/data scenario(s):** TS-64.

## 5. Technical Considerations & Enablers

_Reviewer-owned. Verified 2026-07-13 against the Nitro server
(`src/server/api.ts` router + `authenticate` guard, `src/server/cors.ts`,
`src/server/envelope.ts`), the provider edit path (`src/services/providers.ts`,
`src/lib/audit.ts` `writeAudit`), the E1.8 advisory model
(`src/lib/enrollmentReadiness.ts`), `docs/redesign/seed-universe.md` (TS-64),
and `uiux-component-guide.md`. E3.2 is a deliberately small, **severable**
read-only aid downstream of an E3.1 commit — no schema, no storage, no in-import
dependency (`[r5]` decisions 1 + 11). The only real build decision is the
call path (browser fetch vs thin Nitro proxy)._

- **TE-1 — Call path: recommend a thin Nitro proxy route; no new dependency.**
  The NPI Registry API is public, keyless JSON
  (`https://npiregistry.cms.hhs.gov/api/?version=2.1&number=<npi>`); native
  `fetch` covers it (no dependency — AGENTS.md). Two buildable options:
  1. **Browser fetch** directly from a service — simplest, but bets on the
     registry's CORS headers and puts an external call on the client.
  2. **Thin Nitro proxy** — add one authenticated route (working name
     `/api/nppes/:npi`, GET only) to the existing `src/server/api.ts` router
     (register the regex, dispatch through the shared `authenticate` guard, and
     return via the `ok`/`fail` envelope). The server fetches the registry and
     returns the normalized comparison payload.
     **Recommendation: option 2.** It removes the CORS unknown entirely, keeps
     the third-party call server-side (rate hygiene, one place to add caching/
     backoff, no key even if one is later required), and matches the existing
     `/api` precedent. It costs one route handler; the CORS allowlist
     (`src/server/cors.ts`) is unaffected because the caller is same-origin.
- **TE-2 — No storage, no schema change (display-only).** Registry responses
  are **never persisted** (`[r5]` decision-aligned; avoids a PHI/staleness
  liability): the check renders a comparison and nothing more. Applying a
  registry value goes through the **existing per-field provider edit flow**
  (`src/services/providers.ts` update path, already audited via `writeAudit`) —
  E3.2 adds no write path of its own and no `providers` columns. Nothing
  auto-applies.
- **TE-3 — Comparison is a pure, tested module.** A `src/lib/` module (working
  name `src/lib/nppes.ts`) maps the registry JSON to the three comparison
  fields — name, specialty/taxonomy, practice state — and diffs them against
  the stored provider, returning match/mismatch per field. Type the registry
  response with `unknown` + explicit narrowing (AGENTS.md "no `any`"); the
  taxonomy→specialty mapping can reuse the existing PT-taxonomy helper
  (`src/lib/ptTaxonomy.ts`) where relevant. Pure and unit-testable against the
  mocked responses (TS-64).
- **TE-4 — Graceful degradation is a hard requirement, not a nicety.** NPI
  not-found, API-unavailable/timeout, and a successful match/mismatch are
  **distinct, non-blocking** states. Verification is **never gated on NPPES** —
  it mirrors the E1.8 advisory model (soft, informational, never blocks). A
  registry outage must leave manual verification fully available. Bound the
  fetch with a timeout so a hung registry can't wedge the UI.
- **TE-5 — Workflow integration rides E3.1's pending-verification surface.**
  The "Check NPPES" action lives on the E3.1 pending-verification list/detail
  (F3.2.2) so a user checks → resolves → verifies in one pass without leaving
  the surface. The verify action may record **whether** an NPPES check was run
  as an audit note (not a gate) — a single boolean/flag in the existing
  verify `audit_log` write, no new table.
- **TE-6 — Severability (the epic's own design goal, confirmed buildable).**
  E3.2 touches neither E3.0 nor E3.1 schema/write paths, so if the PM defers it
  (registry availability/terms, or a decision to keep external calls out
  entirely), E3.0/E3.1 ship unaffected. The Nitro-proxy path (TE-1) is what
  makes the "straightforward to set up" test (`[r5]` decision 1) pass — CORS is
  no longer a risk once the call is server-side.
- **TE-7 — UI, table trace, gates, build order.** UI from the approved
  inventory: a side-by-side comparison in a `dialog` or an inline `card`/
  `table` block with per-field match/mismatch indicators (status-semantic
  colors only), a `tooltip` on the icon-only "Check NPPES" trigger; feature
  components in `src/components/import/` (or `providers/`), never `ui/`/
  `layout/`. **Table trace** — reads: `providers`, `state_licenses`
  (specialty/taxonomy/license comparison inputs); external read: NPI Registry
  (not a table). Writes: none of its own — only the existing edit flow's
  `providers` UPDATE + `audit_log` append when a user applies a value. **Gates:**
  unit-test the pure comparison module; e2e for **TS-64** (match, specialty
  mismatch, NPI-not-found, API-down — each distinct and non-blocking; apply
  goes through the audited edit; verify stays possible throughout) with the
  **registry mocked through the harness — no live external calls in CI**. Must
  pass `npm run lint`, `npx tsc --noEmit`, `npm run test`,
  `npx prettier --check .`. **Build order:** after E3.1 (needs the
  pending-verification state + verification flow).

### Likely tech debt / risk to contain

- **External dependency discipline.** The registry is a third party — timeout,
  handle non-200/malformed JSON as "unavailable" (never a crash), and don't
  retry aggressively. If the proxy adds caching later, cache by NPI with a
  short TTL; do not persist responses (TE-2).
- **PHI/logging posture.** NPI itself is a public identifier, but the
  comparison surfaces provider names — never log registry payloads or the
  comparison to `console`, and keep responses out of any durable store.
- **Scope containment.** F3.2 is explicitly one-provider-at-a-time,
  user-triggered (Non-Goals). Resist any pull toward bulk auto-reconciliation
  or a background sweep — that contradicts `[r5]` decision 11's "no external
  calls in the pipeline" spirit.

### Open questions for the PM

- **None blocking.** The call-path choice (TE-1) is a reviewer-recommended
  engineering decision (thin Nitro proxy), not a product decision; flag only
  if there is a policy reason to forbid a server-side outbound call to the
  public registry.
