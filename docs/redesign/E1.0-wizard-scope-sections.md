# E1.0 — Onboarding Wizard: Scope Sections & Stage 1 Front Door

## Purpose and Context

E0.8 shipped the standalone onboarding page as the single home for org intake
(org switcher → **Add organization** → `/onboarding/wizard`), with Section 1
(org details) live from party data and the remaining sections rendered as
`NotYetAvailable` placeholders. E1.0 converts that placeholder shell into the
**Stage 1 front door**: a sectioned wizard that shows the full scope journey
(Provider Group → Facilities → Providers → later: Assignments, Payer Network,
Scope Review), tracks per-section progress **derived from scope data**, and always
tells the operator the next step. E1.0 builds the framework and navigation;
the section _forms_ land in E1.1 (group), E1.2 (facilities), E1.3 (providers).
Stage 1 entry is never scattered across Account Detail, modals, or old CRUD
routes (roadmap principle) — Account Detail stays a read-only summary.

E1.0 also carries the Stage 0 shell tech debt: the sidebar renders the wrong
Minted Panel logo, and menu/sidebar text contrast is too low.

## Personas Empowered

- **P1 Credentialing Manager (Sowmya)** — the sole R1 actor. She onboards
  every org, re-enters onboarding across days/weeks, and needs to know
  "where was I, what's next" instantly across a multi-org portfolio.
- **P5 Practice Owner / P6 Office Manager** — NOT actors in E1.0. The wizard
  is **internal-only through Stage 3** (PM decision, 2026-07-10; see
  CLARIFICATIONS_NEEDED.md). Named here only so the quality bar is set
  consciously, not accidentally.

## Workflow — initial state (as built today, post-E0.8/E0.9)

1. P1 clicks **Add organization** in the org-zone switcher.
2. Lands on the standalone onboarding page; completes the org-intake form
   (org identity + authorized contact + organization contact).
3. Section 1 shows intake outputs live; **all other sections are
   `NotYetAvailable` placeholders** — the journey dead-ends here.
4. People Enroll holds roles/contacts; Account Detail mirrors intake
   read-only.
5. Scope data (facilities, providers) is entered through **legacy flat routes**
   (`/providers`, existing admin CRUD) — disconnected from onboarding, with no notion of
   progress or completeness.
6. Re-entering an org gives no signal of what's done or what's next.

## Workflow — target state (E1.0 + R1)

1. P1 clicks **Add organization** (unchanged single entry) or opens
   onboarding for an existing in-progress org.
2. The wizard shows the **scope journey as sections**:
   - **Org details** (live — E0.8)
   - **Provider Group** (active shell → form lands in E1.1)
   - **Facilities** (active shell → E1.2)
   - **Providers** (active shell → E1.3)
   - **Assignments · Payer Network · Scope Review** (visible, disabled,
     labeled "coming next" — R3 preview; names use final Sidebar IA v2 /
     business vocabulary only)
3. Every section shows a **derived status chip**: Not started / In progress /
   Complete — computed from scope data (e.g. group row exists → Complete;
   0 facilities → Not started), never from stored wizard flags. Editing data
   outside the wizard updates the chips automatically.
4. A single **"Next: …" affordance** opens the first incomplete section —
   this IS the resume behavior (derived, no per-user "last section" storage;
   survives the org-switch state reset by design).
5. Shell debt fixed: correct Minted Panel logo; sidebar/menu text meets
   contrast spec.

```
Initial:  Add org → intake form → [dead end: placeholders] → legacy routes for everything else
Target:   Add org → intake form → Group → Facilities → Providers → (preview: Assignments → Payers → Scope Review)
                      ↑ derived progress chips + "Next:" guidance on every entry
```

## Features

### F1.0.1 — Scope-section framework

- **Description:** Replace the E0.8 placeholder sections with the R1 section
  framework: Org details, Provider Group, Facilities, Providers as active
  sections; Assignments, Payer Network, Scope Review rendered as visible,
  disabled previews. Each active section exposes a mount contract that E1.1–
  E1.3 fill with their forms; until then an active section renders its
  "start" empty state (not `NotYetAvailable`).
- **Persona:** P1.
- **Benefit hypothesis:** The full journey is visible from day one, so P1
  always sees the shape of the work; E1.1–E1.3 land as drop-ins with no
  navigation rework.
- **Acceptance criteria:**
  - Section list and order exactly as above; disabled sections are
    non-interactive, labeled with business terms matching Sidebar IA v2
    vocabulary; no modeling jargon anywhere.
  - Onboarding remains the single Stage 1 entry (no new routes; Account
    Detail unchanged read-only).
  - Each active section renders a start state with a clear CTA even before
    its epic lands.

```gherkin
Feature: Scope-section framework
  Scenario: Journey visible on a fresh org
    Given P1 has just created "Tree Hill Sports Therapy" via Add organization
    When the onboarding wizard loads
    Then she sees Org details complete and Provider Group, Facilities, Providers as actionable sections
    And Assignments, Payer Network, and Scope Review are visible but disabled with "coming next"
```

### F1.0.2 — Derived section progress

- **Description:** Per-section status chip (Not started / In progress /
  Complete) computed from scope data at render time: Org details from party
  rows (E0.8 outputs), Provider Group from group-entity presence/completeness,
  Facilities from facility count, Providers from roster count. No stored
  progress flags.
- **Persona:** P1.
- **Benefit hypothesis:** Progress can never lie — edits made outside the
  wizard (legacy routes, imports) are reflected instantly, eliminating
  stale-checklist failure modes.
- **Acceptance criteria:**
  - Status rules documented per section in the epic's §5 (implementation
    enabler) and unit-tested as pure functions.
  - Chips restyle per design system (4px tint+ink pills).
  - Data added via a non-wizard route flips the chip without any wizard
    interaction.

```gherkin
Feature: Derived progress
  Scenario: Outside edit updates the wizard
    Given "Outer Banks Rehab Group" shows Facilities as Not started
    When a facility is added through the existing admin facilities surface
    Then reopening the wizard shows Facilities as In progress or Complete with zero wizard writes
```

### F1.0.3 — Next-action guidance (resume)

- **Description:** A single persistent "Next: <section>" affordance that
  opens the first incomplete section, on wizard entry and after completing
  any section. This is also the resume mechanism — no per-user "last active
  section" persistence.
- **Persona:** P1.
- **Benefit hypothesis:** Re-entry cost across a multi-org portfolio drops to
  one click; guidance and resume are one mechanism, so they can't disagree.
- **Acceptance criteria:**
  - Entry with all sections complete shows the R3 preview ("Assignments
    coming next") instead of a next action.
  - Works after org switch (derived — unaffected by the E0.0 org-switch
    state reset).

```gherkin
Feature: Next-action guidance
  Scenario: Resume after days away
    Given "Lone Star Rehab Group" has Org details and Provider Group complete and nothing else
    When P1 switches to that org and opens onboarding
    Then the wizard highlights "Next: Facilities" and one click opens that section
```

### F1.0.4 — Shell tech-debt: logo + menu contrast

- **Description:** Replace the incorrect sidebar Minted Panel logo with the
  correct asset; raise sidebar/menu text contrast to the design-system spec
  (brighter/higher-contrast text on the dark rail).
- **Persona:** P1 (and every future user).
- **Benefit hypothesis:** Brand correctness and legibility; closes the two
  Stage 0 carry-over bugs so R1 starts clean.
- **Acceptance criteria:**
  - Correct logo at all sidebar states (expanded/collapsed) and on the
    onboarding shell.
  - Menu text passes the design-system contrast bar on the dark rail;
    focus-ring conformance (E0.9 TS-24) not regressed.

## 5. Technical Considerations & Enablers

- **TE-1 — Route and feature-component boundary.** Extend the existing TanStack
  Start file route, `src/routes/onboarding.wizard.tsx`, in place; do not add
  routes or move Stage 1 entry into Account Detail. Keep the route as the page
  composer and place reusable section-shell UI under
  `src/components/onboarding/` (for example, a section card, status treatment,
  disabled preview, and next-action control). Replace the E0.8
  `NotYetAvailable` instances with the exact ordered section registry from
  F1.0.1. Use the existing shadcn `Card`, `Button`, `Skeleton`, and `Separator`
  primitives; no new primitive or dependency is required.
- **TE-2 — Component → hook → service layering.** Add an onboarding composition
  hook under `src/hooks/` that supplies the route with the active org's
  contacts, provider groups, facilities, and providers through existing hooks:
  `useOrgContacts`, `useProviderGroups`, `useFacilities`, and `useProviders`.
  Those hooks remain the only browser-facing path to their services, and the
  services remain the only path to Supabase's `externalClient`. Do not call a
  service or Supabase from the route or feature components, and do not add a
  third provider-group/facility read implementation.
- **TE-3 — Pure progress contract.** Add
  `src/lib/onboardingProgress.ts` with a named
  `OnboardingSectionStatus = "not_started" | "in_progress" | "complete"` type,
  pure per-section resolvers, and a pure `getNextIncompleteSection` selector.
  Status is based on trimmed values and org-scoped rows only:
  - **Org details:** `complete` when the active organization has a nonblank
    name, the `owner` party has a nonblank name and valid email, and the
    `customer_escalation_contact` party satisfies the existing E0.8 required
    contact fields (name, valid email, office phone, street, city, state, and
    postal code). `not_started` means none of those inputs exists; any partial
    set is `in_progress`. Reuse the existing contact-validation semantics
    rather than inventing a second email rule.
  - **Provider Group:** `not_started` when the org has zero `provider_groups`
    rows; otherwise `complete`. This follows the authored R1 rule that group
    row presence completes the section.
  - **Facilities:** `not_started` when the org has zero `facilities` rows;
    otherwise `complete`.
  - **Providers:** `not_started` when the org has zero `providers` rows;
    otherwise `complete`.
  - **Status reachability:** Current provider-group, facility, and provider
    writes persist only valid rows, not drafts, so those three resolvers are
    intentionally binary in E1.0. E1.1–E1.3 may broaden their resolver inputs
    if they introduce a persisted partial-record definition; they must not add
    wizard-only progress flags. Disabled preview sections show `Coming next`
    and do not participate in the R1 completion calculation.
- **TE-4 — Next-action and section targeting.** Derive the next action from the
  first active section whose resolved status is not `complete`, using the same
  ordered registry that renders the page. Give each active section a stable DOM
  id and heading relationship; the CTA opens or scrolls to that section and
  moves focus to its heading without adding route state or Zustand state. Do not
  compute a next action while a required query is unresolved. When all four R1
  sections are complete, replace the CTA with the authored Assignments preview.
- **TE-5 — Loading, error, and refresh behavior.** Preserve section-shaped
  skeletons while reads load. A failed read must render an inline, retriable
  error for that section and must never be interpreted as `Not started`.
  Reuse the org-scoped `queryKeys` entries so provider-group, facility,
  provider, import, and party mutations invalidate the same caches consumed by
  the wizard; do not introduce a separately cached progress summary. The
  existing `setActiveOrg → removeQueries()` behavior and
  `<Outlet key={activeOrgId}>` remount remain the org-switch reset mechanism.
- **TE-6 — Read shape and sensitive-data boundary.** The group and facility
  hooks may supply their existing org-scoped row arrays because E1.0 needs only
  presence/counts. `useProviders` must continue through
  `src/services/providers.ts`, whose list projection omits `ssn_last4`, date of
  birth, and home-address fields; progress code receives only the returned row
  count. Do not add a broad `select("*")` provider query for the wizard. If
  roster size later makes full-row reads too expensive, add an org-filtered
  count function in the provider service and a hook above it rather than
  querying from the component.
- **TE-7 — Design-system composition and accessibility.** Render active
  sections as shadowless white cards with the design-token border and 6px
  panel radius. Reuse the conformed `StatusPill` treatment: neutral
  `Not started`, amber `In progress`, and green `Complete`, each with the
  fixed tint/ink pair, 4px radius, and a visible text label so color is never
  the sole signal. Disabled previews must be visibly disabled, expose
  `aria-disabled="true"`, and have no click handler. Preserve keyboard-visible
  focus, logical heading order, and usable layouts at 1280px and 1024px.
- **TE-8 — Authorized shell fix.** This section explicitly authorizes edits to
  the protected `src/components/layout/Sidebar.tsx` for F1.0.4 only. Replace
  the current `minted-mark.png.asset.json` image with the approved white
  layered-jack mark from
  `docs/redesign/design-system/design-system-reference/assets/logo-white.png`
  on the `#0C2A1D` rail, paired with the existing Geist 600 wordmark. Apply the
  reference's semantic white-alpha values instead of uniformly brightening
  every label. The code audit found the primary rail classes already aligned
  with the approved reference—white/35 section headings, white/40 organization
  eyebrow, white/50 secondary metadata, and white/60 inactive navigation—so
  contrast work is a visual verification plus repair of any individual
  deviation, not a blanket opacity increase. Preserve white/10 active fill,
  white/5 hover, the mint inset bar, and the E0.9 white-alpha focus ring. The
  onboarding page already renders inside the shared shell, so no `AppShell` or
  duplicated page-logo change is needed.
- **TE-9 — Schema, RLS, grants, and append-only assessment.** No migration,
  stored progress column, RPC, or write path is required. Reads trace to
  `organizations`, `parties`, `party_role_assignments`, `provider_groups`,
  `facilities`, and `providers`; all scope reads must stay filtered to the
  active `org_id` through existing services and protected by the existing RLS
  policies. No public object is added, so no new grant is required. E1.0 writes
  nothing to business tables and does not touch the append-only `touches`,
  `status_history`, or `audit_log` tables.
- **TE-10 — Verification gates.** Unit-test every progress truth table,
  unresolved/error handling, and first-incomplete ordering. Extend the
  onboarding e2e coverage for TS-25–TS-28, including an outside-admin-surface
  facility write, org switching, the all-complete preview, disabled preview
  semantics, keyboard focus, and the logo/rail visual sweep. Implementation
  must pass `npm run lint`, `npx tsc --noEmit`, `npm run test`,
  `npx prettier --check .`, and the touched Playwright specs.
- **Likely tech debt to contain.**
  - Provider-group and facility reads currently exist in both
    `src/services/lookups.ts` and `src/services/orgSettings.ts`, with some raw
    query-key literals in mutation hooks. E1.0 must reuse the current shared
    keys and must not create another summary service; consolidation can occur
    in a focused follow-up.
  - The protected `ProviderGroup` and `Facility` interfaces expose only the
    fields current screens need even though the tables contain additional
    Stage 1 columns. Presence/count progress does not require widening
    `src/types/index.ts`; E1.1/E1.2 own any typed-field expansion needed by
    their forms.
  - `In progress` is not reachable for the three row-count sections under the
    current valid-row-only persistence model. That is preferable to inferring
    completeness from nullable fields before E1.1–E1.3 define their form
    contracts.

## Locked R1 decisions this epic inherits (PM, 2026-07-10)

Recorded in CLARIFICATIONS_NEEDED.md; restated here because E1.1–E1.3 build
inside this epic's framework:

1. **Wizard audience:** internal-only through Stage 3.
2. **License source of truth (E1.3):** hand-entered in v1; CAQH/NPPES import
   deferred to the R5 scale pack.
3. **Facility hours shape (E1.2):** per-day jsonb
   `{ "mon": { "status": "open", "open": "07:00", "close": "19:00" }, ... }`
   in the existing `facilities.hours` column — matching the per-day
   status/open/close grain payer forms ask for (e.g. Humana provider
   certification). The E1.2 form includes a weekday quick-fill (one entry
   populates M–F, closed Sat/Sun). No split shifts in v1. This shape is also
   the extension fill contract (`facility.hours.*` tokens).
4. **Case key is 4-part (E1.3/R4):** provider × group × payer × state — the
   same provider may be credentialed with the same payer/state under
   multiple groups/TINs. Companion rules: contracts remain group × payer ×
   state (each group's own TIN enrollment is its own contracting effort);
   "group has a facility in the target state and the provider is licensed
   there" is an E1.8 readiness check / E2.0 soft warning, NOT a DB
   constraint. NOTE: this amends the locked AGENTS.md rule "one credentialing
   case per (provider_id, payer_id, state)" — the epic that implements the
   key change (E1.3/E2.3) must include the AGENTS.md amendment.
